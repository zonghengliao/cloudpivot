### 1.4 本规格的实测证据（全部为本机真跑，脚本见附录 A）

**(a) S2（ADR 字面：成本账 + 库位账都落库位行）在「第一次出库」后自己变红。**

```
=== A 生成后 ===                        === A 出库 1 件后 ===
A:成本账sum = 5.0000                    A:成本账sum = 9.0000   ← 5(库位行) + 4(NULL 桶重算)
A:库位账sum = 5.0000                    A:库位账sum = 5.0000
A:在库号数  = 5                         A:在库号数  = 4
```
⇒ B1 = |9 − 5| = 4（BLOCKER 红）、C5 = |4 − 9| = 5（WARN 红）。
成因：出库走 `link_inventory` → `recompute_quantity`（`serial_model.rs:733`），后者**只写 NULL 汇总桶**（`:602`），
而成本账的 5 件在库位行上 ⇒ 同一物料同仓出现两个桶，qty 被**加了第二遍**。

**(b) S1（两本账都落 NULL 桶）+ 现状出库代码（只改成本账）→ B1 仍红。**

```
=== B 出库 1 件后（现状代码：库位账不动） ===
B:成本账sum = 4.0000
B:库位账sum = 5.0000     ← 没人减它
B:在库号数  = 4
```

**(c) S1 + 新增「出库时库位账按件数重算」→ 全绿。**

```
=== C 出库 1 件 + 库位账重算后 ===
C:成本账sum = 4.0000    C:库位账sum = 4.0000    C:在库号数 = 4    C:avg_cost = 10.000000
```
⇒ 这就是 §6 那条「必须补的一步」。

**(d) 成本账加金额而不生成凭证 ⇒ B2 差值正好等于入库金额。**

```
=== 写 50 元库存、不记账凭证之后 ===
B2 库存金额 = 7507.5000   （改动前 7457.5000，+50）
B2 1405余额 = 20.0000     （不变）
```
prod 侧现存的「账户平衡」证据：`docs/datafix-20261031-p11-m-w1a-004-recur.md:157-159`
（`库存金额 435.0000 / 1405 435.0000`）⇒ 今天库存金额之所以为 435，是因为**唯一会加金额的入口是收货过账，
它在同事务里生成凭证**（`stockin_handler.rs:1074 voucher::create_for_stock_in`）。批量生成不生成凭证，
就会单方面抬高 `SUM(amount)`。

**(e) 数值口径（PG 实算）**

```
select round(3*12.345678,2)          -> 37.04
select round(round(3*12.345678,2)/3,6) -> 12.346667     ≠ 12.345678
select round(3*10.000000,2)/3            -> 10.000000    （可精确表示时才等于单价）
```

**(f) JSON 类型口径（`rust_decimal 1.43.0 + serde`，实测）**

```
OK  {"unit_cost": 12.34}   -> Some(12.34)      ← number 收
OK  {"unit_cost": "12.34"} -> Some(12.34)      ← 字符串也收（Visitor 的 deserialize_f64 + serde_json 数字解析）
OK  {}                     -> None             ← 可用 Option 承接「缺字段」
SER -> {"unit_cost":"12.345678"}               ← 序列化**始终是字符串**
```

**(g) 缺字段为什么会变 422（必须用 `Option` 才能给 400）**

`axum 0.8.9`（`backend/Cargo.lock:172-175`）的 `JsonDataError` 状态码写死 `UNPROCESSABLE_ENTITY`：
`~/.cargo/registry/src/…/axum-0.8.9/src/extract/rejection.rs:10-18`。
所以 `unit_cost: Decimal`（裸必填）在缺字段时返回 **422**，与本卡要求的「400 + 报文」不符。

**(h) 生产重启的服务管理器**

`scripts/deploy.sh:20` → `docker compose -f docker/docker-compose.prod.yml up -d --build`（不是 systemd）。
若目标机仍是 systemd 托管：本次实测，**terminal 里任何含 `systemctl restart` 字符的命令串都会被安全层直接 BLOCKED
（连 `grep "systemctl restart"` 都被拦）** ⇒ 必须写进脚本文件再 `bash 脚本.sh`，见 §7.3。

## 2. 接口契约

### 2.1 请求体 diff（`POST /business/erp/serial/batch-generate`）

```diff
 {
   "material_id": "b2b00004-…-000000000001",
   "warehouse_id": "b2b00001-…-000000000001",
   "location_id": null,
   "count": 5,
+  "unit_cost": 12.34,          // 新增，必填，不含税单价，> 0，最多 6 位小数
   "batch_no": "B001",
   "source_type": "PURCHASE",
   "source_id": null
 }
```

| 字段 | 类型（JSON） | 必填 | 规则 | 落库 |
|---|---|---|---|---|
| `unit_cost` | number（也接受字符串） | **是** | `> 0`，四舍五入到 6 位；上限 `< 100000000000`（防 `numeric(18,4)` 溢出：`1000 × 99999999999.999999 ≈ 9.9999e13` < `1e14`） | `biz_inventory_txn.unit_cost numeric(18,6)`；派生 `amount = round(N × unit_cost, 2)` |

`unit_cost` 允许的最大 6 位小数与收货入库同口径：`stockin_model.rs:179-181 unit_price()`（四舍五入 6 位，`ROUNDING = MidpointAwayFromZero`, `:124`）。

### 2.2 DTO 与校验位置

**DTO**：`backend/src/business/erp/serial_dto.rs:42-62`（`BatchGenerateReq`）新增一个字段，**类型必须能区分三种情形**：

```rust
/// `unit_cost` 的入参形态：区分「没传」「传了但不是数字」「传了数字」，
/// 三种都必须由 validate() 翻成 400（裸 `Decimal` 缺字段会被 axum 变成 422，见 §1.4(g)）。
#[derive(Debug, Clone, Deserialize)]
#[serde(untagged)]
pub enum OptionalDecimal {
    /// JSON 数字（前端 `t-input-number` 发的就是 number）
    Num(Decimal),
    /// JSON 字符串或其它形态（解析失败时落到这里，由 validate 报「不是合法数字」）
    Raw(String),
}

pub struct BatchGenerateReq {
    // …既有 7 个字段不变…
    /// 成本单价（不含税，> 0，6 位小数）—— 批量生成 = 无来源入库，必须录成本（ADR ①′）
    #[serde(default)]
    pub unit_cost: Option<OptionalDecimal>,
}
```

**校验位置**：`serial_dto.rs:69-106`（`BatchGenerateReq::validate`），**不碰数据库**。
校验顺序（错误优先级）与现有实现一致，成本校验放在 `count` 之后、`batch_no` 之前：

```rust

    None => return Err(ApiError::new(400, error_code_param(),
        "unit_cost 必填：批量生成按「期初/其他入库」记账，必须录成本单价（不含税）")),
    Some(OptionalDecimal::Num(v)) => *v,
    Some(OptionalDecimal::Raw(s)) => Decimal::from_str(s.trim()).map_err(|_| ApiError::new(
        400, error_code_param(), format!("unit_cost 不是合法数字：「{s}」")))?,

let unit_cost = stockin_model::unit_price(unit_cost);        // 6 位四舍五入（与收货入库同口径）
if unit_cost <= Decimal::ZERO {

        "unit_cost 必须 > 0（收到 {unit_cost}）：零成本入库会在成本账留下 qty>0/avg_cost=0 的行（巡检 C3），系统拒收")));
}
if unit_cost >= Decimal::from(100_000_000_000i64) {
    return Err(ApiError::new(400, error_code_param(), format!(
```

**「400 且零落库」的机制**：`validate()` 在 `generate_serials`（`serial_handler.rs:129`）**第一行**执行，
早于 `take_numbers`（`:209` → `serial_model.rs:765`）与 `db().begin()` 之前的任何写操作
（事务在 `:205` 才开）⇒ 既不会推进 `biz_seq`，也不会落号/流水/账。

### 2.4 breaking change 说明

- **破坏性**：老客户端（不带 `unit_cost`）从「200 成功」变为「400 拒绝」。这是**有意的**：老行为在产线上
  每次点击都会写 «qty>0 / amount=0 / 无库位账»，直接打红 B1（BLOCKER）+ C3（`docs/adr-…:22-26`）。
- **兼容窗口**：不设宽限期、不做「缺省 0」的向后兼容 —— 缺省 0 等于保留缺陷。若要灰度，只能
  **先发前端**（表单带单价）再发后端，两者同一次部署（`scripts/deploy.sh` 一次 compose up 同时更新前后端）。
- **必须同步的东西（少一样就 500 或 e2e 红）**：
  1. 前端表单与 api ts（§10）；
  2. `frontend/e2e/12-erp-serial-batch-walkthrough.spec.ts`（弹窗必须填单价，否则 e2e 400）；
  3. 发布记录：在 `docs/` 下当次发布文档里写一条「**BREAKING** `POST /erp/serial/batch-generate` 新增必填
     `unit_cost`（不含税单价 > 0）」+ 对客话术（见 §8.6）。
- **不破坏**：响应体只**新增**字段（§2.5），老调用方的 JSON 解析不受影响。

### 2.5 响应体：要回显本次入库金额（结论：**要**）

理由（三条，均有出处）：

1. ADR 验收 5 要求「提交成功后页面显示的库存数量/金额与库一致」（`docs/adr-…:91`）——不回显就得让前端再发一次
   查询，且查的是「当前值」而不是「本次入账值」；
2. 金额是会计凭据：操作人当场要知道「这次入账多少钱」，凭据链是 流水(`doc_no=首号`) → 凭证(Q1)；
3. 回显几乎零成本：`apply_cost` 已经 `RETURNING qty, amount, avg_cost`（`stockin_model.rs:1097`），
   返回结构体 `AppliedInventory { before, after }`（`stockin_model.rs:312-317`）本来就要拿。

`serial_dto.rs:110-134 SerialBatchRes` 新增：

```rust
pub struct SerialBatchRes {
    pub count: usize,
    pub period_key: String,
    pub serial_nos: Vec<String>,
    pub list: Vec<SerialRes>,
    /// 本次成本单价（不含税，6 位）—— Decimal 序列化为**字符串**，见 §1.4(f)
    pub unit_cost: Decimal,
    /// 本次入账金额（= round(count × unit_cost, 2)），写入 biz_inventory_txn.amount
    pub amount: Decimal,
```

### 3.1 取号：`take_numbers`（`serial_model.rs:472`）

- **调用点**：`batch_generate` 内，`params.count`（1..=1000）与 `period_key`（北京时区 `yyyyMMdd`，
  `today_period_key()`，`serial_handler.rs:202`）。
- **保持既有取舍**：先取号后落号，插入失败会浪费一段号（`serial_model.rs:744-745` 的注释，业务上
  只要求不重号）。
- **不许做**：不许把取号搬到事务外（会与 `biz_seq` 的并发行锁脱节）；不许自己拼号（`format_serial_no`
  `:768` 唯一入口）。

### 3.2 落号：一条 `INSERT … SELECT`（`serial_model.rs:775-797`，形态不变）

- `status` 仍写死 `'IN_STOCK'`（`:781`）、`inbound_at = now()`；`source_type` / `source_id` / `batch_no` /
  `location_id` 照旧从请求透传。
- **新增断言（本规格的硬要求）**：`exec_sql` 的返回影响行数必须等于 `params.count`
  （`SqlExecutor::exec_sql` 返回 `Result<u64>`：`backend/vendor/nik-db/src/query.rs:52,205`）。
  理由：数量记账用的是「请求条数 N」，若 `INSERT` 实际插入 ≠ N（payload 被污染、并发软删、唯一键部分冲突），
  记账就会凭空多计或少计。不等于 N ⇒ `DbError::InvalidValue(format!("批量生成落号条数不符：期望 {N}，实际 {m}"))`
  ⇒ 事务回滚，`biz_seq` 号段浪费（可接受）。
- **不许做**：不许逐条 `INSERT`（1000 次往返实测 1.5–2 s，`:741-742`）；不许改状态枚举
  （`V0138:95 ck_biz_material_serial_status` 只有 `IN_STOCK/OUTBOUND/SCRAPPED`）。

### 3.3 成本账：`stockin_model::apply_cost`（`stockin_model.rs:1059-1131`，`pub`）

调用（本期 S1）：


- `lock_inventory`（`:1014-1044`）先 `SELECT qty, amount, avg_cost … FOR UPDATE`，命中桶用

  —— **锁与冲突目标必须同形，否则 42P10**；

  3. 不许改 `ON CONFLICT` 目标表达式（写成两列 `(material, warehouse)` 会 42P10，`V0139:84-92`）。

### 3.5 不变式①仍须成立 —— 只允许「一处加数量」

**禁止同时调用 `recompute_quantity`（`serial_model.rs:592`）再加一次数量**。为什么是双计：

- `recompute_quantity` 是**绝对值重算**：`qty := count(IN_STOCK 号)`（`:600-612`），并且**只写 NULL 桶**；
- `apply_cost` 是**增量加法**：`qty := qty + N`；
- 先 `apply_cost`（+N）再 `recompute`（:= count）在本期 S1 下**碰巧**结果一致（都是 N）——但这是巧合：
  ① 若一次批量生成前该物料已有历史存量未纳管（`serial_required` 后开，`erp_invariants.py:308-309` 明确允许），
  `recompute` 会把「按数量记的旧库存」一次性抹成「序列号件数」，等于**静默销毁差额**；
  ② 若请求带了 `location_id`（S2），`recompute` 写 NULL 桶 + `apply_cost` 写库位桶 ⇒ **双计**（§1.4(a) 实测 9 vs 5）；
  ③ 两处加数量还意味着「数量真相」有两个来源，任何一方改口径都会静默错账。

**怎么保证不变式①仍然成立**（增量为 N 的等式证明）：

```
落号：本次新增 IN_STOCK 号 = N（§3.2 断言）
记账：本次新增成本账 qty = N（apply_cost 的 EXCLUDED.qty = N，加在同一 (物料,仓库,桶)）
⇒ 对该 (物料, 仓库)：Δcount(IN_STOCK) = ΔSUM(biz_inventory.qty) = N
⇒ 若操作前该 (物料,仓库) 已满足 ①（差=0），则操作后仍满足（差=0）
```

因此 **① 的保证是「增量等式」而不是「绝对值重算」**：本方案不修复历史差额（§8.2），只保证不再新增差额。

**落库后断言（单测与巡检共用一条 SQL，必须放进后端单测）**：

```sql
-- 任一为 0 即失败（按 物料×仓库，与 erp_invariants.py C5 同口径，:314-338）
WITH s AS (SELECT material_id, warehouse_id, count(*)::numeric q
             FROM biz_material_serial
            WHERE material_id = :m AND status='IN_STOCK' AND deleted_at IS NULL
            GROUP BY 1,2),
     i AS (SELECT material_id, warehouse_id, sum(qty) q
             FROM biz_inventory WHERE material_id = :m GROUP BY 1,2)
SELECT coalesce(s.q,0) AS 在库号, coalesce(i.q,0) AS 帐面,
       coalesce(s.q,0) - coalesce(i.q,0) AS 差
  FROM s FULL OUTER JOIN i USING (material_id, warehouse_id);
```

- `remark` 保留「批量生成 N 件（首号起）」并追加单价，格式固定为：

### 3.8 `post_serial_txn` 的桶过滤缺陷（必须修，否则 B4 红）

现状 SQL（`serial_model.rs:670-703`）：

```sql
INSERT INTO biz_inventory_txn (…)
SELECT … FROM biz_inventory i
 WHERE i.material_id = ?::uuid AND i.warehouse_id = ?::uuid         -- :681-682 没有 location 条件
```

⇒ 若同一 (物料, 仓库) 在 `biz_inventory` 有**多行**（例如收货按库位建的行 + 序列号汇总桶），
`INSERT … SELECT` 会为**每一行**写一条流水，每条 `qty = N` ⇒ `Σ IN 流水 = N × 行数` ⇒ B4（`:231-259`）红。

**修法**：给 `post_serial_txn` / `link_inventory` 增加 `bucket: Option<Uuid>` 参数，`WHERE` 里加

```sql
AND COALESCE(i.location_id, '00000000-0000-0000-0000-000000000000'::uuid)
  = COALESCE(NULLIF(?::text,'')::uuid, '00000000-0000-0000-0000-000000000000'::uuid)
```

并在 `exec_sql` 之后**断言影响行数 = 1**，否则 `DbError::InvalidValue("库存账桶缺失：…（物料 {m} / 仓 {w} / 桶 {b}）")`
—— 把「静默漏写流水」变成「整单回滚 + 明确报错」。

**上线前体检**（跑在 prod 只读；`0 行` 才允许上线）。这条 SQL 找「有在库号但没有汇总桶成本账行」的
(物料, 仓库)，它们在「出库」时会撞上 N5 的断言：

```sql
SELECT s.material_id, s.warehouse_id, s.q AS 在库号, coalesce(i.q,0) AS 汇总桶qty
  FROM (SELECT material_id, warehouse_id, count(*)::numeric q
          FROM biz_material_serial
         WHERE status='IN_STOCK' AND deleted_at IS NULL
         GROUP BY 1,2) s
  LEFT JOIN (SELECT material_id, warehouse_id, sum(qty) q FROM biz_inventory
              WHERE location_id IS NULL GROUP BY 1,2) i
    ON i.material_id = s.material_id AND i.warehouse_id = s.warehouse_id
 WHERE coalesce(i.q,0) = 0 AND s.q > 0;
```

写函数一律吃 `&impl SqlExecutor`（`stockin_model.rs:103-107` 的约定），事务由接口层
`serial_handler.rs:205` 开、`:209-221` 提交/回滚。模型层**不许** `begin()`（会变成嵌套事务）。

## 4. 账务粒度：S1（本期建议）vs S2（ADR 字面）

### 4.1 两个选项

| 选项 | 生成侧成本账 | 生成侧库位账 | 是否要改 `recompute_quantity` |
|---|---|---|---|
| **S1（建议）** | NULL 汇总桶 | NULL 汇总桶 | **不改**（它就是写 NULL 桶） |
| **S2（ADR 字面）** | `location_id` 行 | `location_id` 行 | **必须改成按桶重算**，否则第一次出库双计 |

### 4.2 为什么 S2 现在不可行（实测，非推测）

`recompute_quantity`（`serial_model.rs:592-629`）的 SQL 固定把**该物料该仓所有 IN_STOCK 号的总数**
写进 **NULL 桶**（`:600-612`），而 `transition_status_with`（`:996`）在 `IN_STOCK → OUTBOUND | SCRAPPED`
时**只调它**（`:1052-1072`，`link_inventory` 在 `:1070`）。`serial_model.rs` 全文**没有任何一句**
写 `biz_inventory_location`（`grep -n biz_inventory_location serial_model.rs` 只命中注释与
`:875` 的只读查询）⇒ 库位账在出库时**永远不动**。

于是 §1.4(a) 的 9 / 5 / 4 就是必然结果。要在 S2 下自洽，必须把 `recompute_quantity` 从
「总数写 NULL 桶」改成「按 `COALESCE(serial.location_id, 0-uuid)` 分组重算」（并同步重算库位账），
而它被 **出库、报废、调拨（`transfer_model.rs:1404` 注释）** 共用 ⇒ 影响面覆盖 W2b/W2c/W3b 三条已验收链路，
不适合塞进本卡。

### 4.3 如果总管选 S2，需要额外做的（只列差异）

1. `recompute_quantity` 改为：

```sql

       s.q * coalesce(i0.avg_cost,0), now()

  LEFT JOIN biz_inventory i0
    ON i0.material_id=s.material_id AND i0.warehouse_id=s.warehouse_id
   AND COALESCE(i0.location_id, 零uuid) = COALESCE(s.location_id, 零uuid)
ON CONFLICT (material_id, warehouse_id, COALESCE(location_id, 零uuid))
DO UPDATE SET qty = EXCLUDED.qty, amount = EXCLUDED.qty * i.avg_cost, …
```

2. 库位账同步按桶重算（把 §6 的 `recompute_location_qty` 的桶换成 `serial.location_id`）；
3. **既有 W2b/W2c 单测要重写**：`serial_handler.rs:1483 outbound_decrements_derived_quantity` 等断言的是
   「NULL 桶被改成 count」，S2 后会变。
4. 风险：S2 让同一物料同仓出现多个桶、每个桶各自 `avg_cost`（与 `V0137:402` 的注释
   「avg_cost 粒度=物料×仓库，不按库位分裂」冲突；收货入库其实已经这么干了，属于历史欠账）。

## 5. 硬伤 ①：成本账加金额而不生成凭证 ⇒ B2 直接红

### 5.1 事实

- B2（`erp_invariants.py:201-212`，**BLOCKER**）：`SUM(biz_inventory.amount)` 必须等于
  `Σ(1405 借−贷)`；
- 全仓唯一会「增加库存金额」的入口是收货过账，它在**同一事务**里生成凭证：
  `stockin_handler.rs:1074 voucher::create_for_stock_in(…)`（借 1405 存货 / 借 2221.01 进项税 /
  贷 2202 应付，`voucher.rs:29-36`）；
- 盘点巡检 `inventory_audit.rs` 只重算 `amount = qty × avg_cost`（`:168-197`），**不生成凭证**，也**不增加金额**；
- 实测（§1.4(d)）：库存金额 +50、不发凭证 ⇒ B2 差额 +50。

⇒ 按 ADR 字面「同事务写两本账」，`amount = N × unit_cost > 0` 而 1405 不动，**B2 从绿变红（BLOCKER）**。
等于用 B1/C3 换了一个更硬的 B2，验收判据「32/32、B1/C3 全绿」不可能成立。

### 5.2 三条可选口径（需总管拍板 = Q1）

| 方案 | 内容 | 代价 |
|---|---|---|
| **Q1-A（建议）** | 生成时同事务生成凭证：**借 1405 存货 / 贷「待处理财产损溢 1901」**，摘要「期初/其他入库 SN-… 首号」，金额 = `amount`，`source_type='SERIAL_BATCH'`、`source_id = 首号 id` | 需新增科目 1901 + 一条凭证规则种子 ⇒ **1 条种子迁移 V0159**；需新增 `voucher::create_for_serial_init()`（复用 `create_auto`，见 §5.3） |
| Q1-B | 贷方用「利润分配—未分配利润 4104」（期初建账常见做法） | 同上，只是科目不同；财务口述需确认 |
| Q1-C | 不生成凭证，**改 B2 判据**，把「无来源入库」金额从两边同时剔除 | **ADR 已明确「不改判据」**（`docs/adr-…:79`）；且等于让 B2 对这类库存永久失明 ⇒ 不推荐 |

> 注：**不能**复用收货那套「贷 2202 应付」，那会凭空造应付 ⇒ B3（`:214-229`）与 `biz_payable` 一致性直接崩
> （`resolve_accounts` 在没有规则时会**兜底到 2202**：`voucher.rs:536-547` ⇒ 规则行是必须的，不能靠兜底）。

### 5.3 生成凭证的最小实现（Q1-A/B 落地路径）

`voucher.rs` 已有能力（无需新表）：

1. `resolve_accounts(ex, biz_type, material_id, supplier_id)`（`voucher.rs:505+`）：按 `biz_voucher_rule.biz_type`
   解析「借存货 / 贷应付 / 借进项税」三个科目，**逐项独立退化**；
2. `create_auto(ex, &AutoVoucher{…}, operator, now)`（`voucher.rs:949-1007`）：组 2~3 行分录、
   校验借贷平衡、`entry_count >= 2`，落 `POSTED`；
3. `biz_voucher.source_type` 是 `VARCHAR(24)` 且**没有值域 CHECK**（`V0149:42`；CHECK 只约束
   `status/voucher_type/is_red/借贷平衡/entry_count`，`:62-73`）⇒ 新增 `'SERIAL_BATCH'` 不需要迁移。

需要新增的只有两处：

## 6. 硬伤 ②：出库/报废侧必须补「库位账重算」

### 6.1 问题

生成侧写了库位账（+N），出库侧（`transition_status_with`，`serial_model.rs:1052-1072`）**不动库位账**
⇒ 第一次出库后 `SUM(库位账) = N` 而 `SUM(成本账) = N−1` ⇒ B1 红（§1.4(b) 实测 4 vs 5）。

### 6.2 修法（本期 S1 口径，新增一个镜像函数）

在 `serial_model.rs` 新增（与 `recompute_quantity` 同一形状、同一把尺子 —— 都是「按件数绝对值重算」）：

```rust
/// 库位账重算：把 (物料, 仓库, NULL 汇总桶) 的 `biz_inventory_location.qty`
/// 重算成「该 物料×仓库 下 IN_STOCK 的件数」，与 `recompute_quantity` 同口径、同一桶。
/// 两个 Tab（即时库存 / 库位库存）因此永远同数 ⇒ 不变式③（B1）恒成立。
pub async fn recompute_location_qty(
    ex: &impl SqlExecutor, material_id: Uuid, warehouse_id: Uuid,
) -> DbResult<Decimal> {
    // INSERT INTO biz_inventory_location AS il (id, material_id, warehouse_id, location_id, qty, locked_qty, …)
    // SELECT ?, ?, ?, NULL, s.in_stock, 0, now(), now(), now()
    //   FROM (SELECT COUNT(*)::numeric in_stock FROM biz_material_serial
    //          WHERE material_id=?::uuid AND warehouse_id=?::uuid
    //            AND status='IN_STOCK' AND deleted_at IS NULL) s
    // ON CONFLICT (material_id, warehouse_id, location_id) DO UPDATE
    //   SET qty = EXCLUDED.qty, updated_at = now(), last_txn_at = now()
    // RETURNING qty
}
```

并在 `link_inventory`（`:715-735`）里，`recompute_quantity`（`:733`）之后加一行：

```rust
recompute_location_qty(ex, material_id, warehouse_id).await?;   // ← 新增：两本账同尺
```

`link_inventory` 只有 2 个调用点：`batch_generate`（本期**不再调用**它，见 §3.0）与
`transition_status_with`（`:1070`，出库/报废）⇒ 这一改动**只影响出库/报废**，不碰生成。

### 6.3 落在哪张表、为什么必须重算而不是 ±1

- 绝对值重算天然幂等、天然自愈（与 W2c 选 `recompute_quantity` 的理由一致，`:576-591`），
  且不需要判断「上一笔是谁记的账」；
- 增量 ±1 会在「历史上根本没有库位账行」时插入 `qty = -1` 的行 ⇒ 违反 C2（`erp_invariants.py:278-281` 负库位库存）
  与非负约束（`ck_biz_inv_loc_locked` 只管 locked_qty，qty 负数会直接被 C2 抓）。

### 6.4 影响面与风险

| 项 | 说明 |
|---|---|
| 现有 e2e/单测 | `serial_handler.rs:1483 outbound_decrements_derived_quantity` 等会**额外**看到库位账变化（若夹具清了库位账表，会在 `ON CONFLICT` 处新建行，断言需补一行「库位账 = N−1」） |
| 历史数据 | 已有「历史按数量记的库存 + 后开一物一码」的物料，出库会把库位账重算成「序列号件数」，可能与成本账保持同差（两者都是 count）⇒ 不加剧，但也不修复（§8.2） |
| 并发 | 与成本账同一顺序（成本账行先锁、库位账行后锁），不会死锁 |

## 8. 风险与回滚

### 8.1 与「批量生成不可复用于收货」的关系（`stockin_model.rs:51-70`）

那段注释记录的是：收货过账**故意不调用** `batch_generate`，原因是它会
① 多写一条 `SERIAL_IN` 流水（与 `PURCHASE_IN` 双计，B4 红）；
② 用 `recompute_quantity` 把 `amount` 改写成 `qty × avg_cost`（当时 avg_cost 还是 0）⇒ **静默抹掉过账算出的金额**。

本方案落地后：
- ① 仍然成立 ⇒ **收货侧继续不调用 `batch_generate`**，本方案**不放松**这条禁令（改完后 `batch_generate`
  会额外写凭证与两本账，收货复用只会更乱）；
- ② 仍然成立：`recompute_quantity` 依旧存在（出库/报废在用），它的 `amount = qty × avg_cost` 依旧会
  覆盖「非等比入账」的金额 ⇒ 这条禁令的唯一正确解法仍是「收货自己记账」，不是「统一走 batch_generate」。
- 反过来，本方案新增两条**给收货侧**的提醒（写进代码注释即可）：`apply_cost` 的桶参数必须与
  `apply_location_qty` 完全一致；`post_serial_txn` 的桶过滤（§3.8）同样作用于收货生成号之后的状态流转。

### 8.2 存量数据：不补账（增量口径）

- **不做**：不写迁移回填、不批量 `UPDATE biz_inventory`、不给历史号补成本、不回拨 `biz_seq` 号段。
  理由：历史零成本行**无法客观还原单价**（凭空定价 = 造账），且 P10 的口径就是「只前进不回退」
  （`docs/datafix-…-recur.md:147`）。
- **后果要明说**：prod 现存的 B1/B2/C3 红**不会因为本方案上线而变绿**。它们只能靠
  `scripts/datafix/p10/…`（残留清理）或业务重开单据解决。本方案的验收口径是**「不再新增红」**，
  不是「把红清掉」。这一点必须写进发布说明，否则测试卡会拿「上线后仍 32 项里有红」来打回。
- **历史差额定位 SQL**（上线前后各跑一次，量化「没有新增」）：

```sql
-- 与 erp_invariants.py C5 同口径：按 物料×仓库 列差额（差额不带时间戳的变化即「未新增」）
SELECT m.material_code, w.warehouse_code,
       coalesce(s.q,0) AS 在库号, coalesce(i.q,0) AS 帐面, coalesce(s.q,0)-coalesce(i.q,0) AS 差
  FROM (SELECT material_id, warehouse_id, count(*)::numeric q FROM biz_material_serial
         WHERE status='IN_STOCK' AND deleted_at IS NULL GROUP BY 1,2) s
  FULL JOIN (SELECT material_id, warehouse_id, sum(qty) q FROM biz_inventory GROUP BY 1,2) i
    ON i.material_id=s.material_id AND i.warehouse_id=s.warehouse_id
  JOIN biz_material m ON m.id=coalesce(s.material_id,i.material_id)
  JOIN biz_warehouse w ON w.id=coalesce(s.warehouse_id,i.warehouse_id)
 WHERE abs(coalesce(s.q,0)-coalesce(i.q,0)) > 0.0001;
```

### 8.3 移动加权数值例子（两次不同单价）

口径（与 `stockin_model.rs:38-43` 一致）：

```
new_qty    = old_qty + N
new_amount = old_amount + round(N × unit_cost, 2)        ← 加法，金额是权威值
new_avg    = round(new_amount / new_qty, 6)   (new_qty > 0)
```

**例 1（推荐给单测的「精确」用例，2 位小数单价）**

| 步骤 | 动作 | qty | amount | avg_cost |
|---|---|---|---|---|
| ① | 批量生成 5 件 @ 10.00 | 5 | `round(5×10,2)=50.00` | `round(50/5,6) = 10.000000` |
| ② | 同物料再生成 3 件 @ 12.50 | `5+3=8` | `50+37.50=87.50` | `round(87.50/8,6) = 10.937500` |

算式核对：`87.50 / 8 = 10.9375`（PG 实测 `round(87.5/8,6) = 10.937500`）。
流水两条：`IN 5 @10.00 amount 50.00`、`IN 3 @12.50 amount 37.50`；`Σ IN = 8 = Σ biz_inventory.qty`（B4 ✓）。

**例 2（6 位单价，用来钉住「avg_cost 不等于 unit_cost」这个坑）**

| 动作 | qty | amount | avg_cost |
|---|---|---|---|
| 生成 3 件 @ 12.345678 | 3 | `round(37.037034,2) = 37.04`（PG 实测） | `round(37.04/3,6) = 12.346667`（PG 实测） |

⇒ **ADR 验收 1 的「`avg_cost = unit_cost`」只在 `N × unit_cost` 能被 2 位小数精确表示时成立**。
验收口径请按 `avg_cost = round(round(N×unit_cost,2)/N, 6)` 表述（这是数值精确化，不是改口径）。
测试卡若坚持要「avg_cost 恰等于 unit_cost」，请用 `unit_cost` 为 2 位小数的用例（例 1）。

### 8.4 与 P10 残留判据的关系

`scripts/datafix/p10/20_residue_report.up.sql` 四道判据（`:14-19`）里第 ④ 道是「库存零价值
（`amount` 与 `avg_cost` 全为 0）」。本方案落地后 `amount > 0` ⇒ **第 ④ 道不再命中** ⇒
批量生成的库存**不再被判为夹具**（与 ADR `:32-33,80` 一致）。

要写进文档的推论（否则会有人照着旧习惯跑 P10 清数据）：
**此后走查点出来的库存是真实入库，撤销必须走红冲/盘点，不是跑 P10 就能清。**

### Q1（阻塞级，最硬）成本账加金额，凭证怎么办？

### Q2 账务粒度：库位还是仓级？（ADR `:60-61` 的字面要求与现有代码冲突）
