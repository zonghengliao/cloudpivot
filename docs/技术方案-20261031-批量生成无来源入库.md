## 0.5 决策记录（v1 的 3 个待拍板问题 → 本次定稿）

> v1 §11 提了 Q1/Q2/Q3 三个口径问题并 `kanban_block(needs_input)`。总管在把本卡重新入队时未给出新口径（卡片评论与
> 父卡 `t_5d52a72e` 的复查记录里都没有对 Q1–Q3 的答复）。因此**由架构侧按 ADR 的原始意图（①′：必须录成本 + 同事务写两本账 +
> 巡检判据不改）推导定论**，逐条给出「为什么不这么定就一定红」「反例」「否决成本（改一行即可）」。
> 这三条都**没有改变 ADR 的语义**（仍然是「无来源入库 + 两本账 + 判据不改」），只是把"判据不改"这个约束推导到底。

### A1 · 生成凭证（成本账加金额必须同事务发凭证）

- **定论**：生成、出库、报废三处**都在同事务生成凭证**；科目：
  - 生成（期初/其他入库）：借 `1405 库存商品` / 贷 `1901 待处理财产损溢`；
  - 出库（序列号发货）：借 `6401 主营业务成本` / 贷 `1405 库存商品`；
  - 报废：借 `1901 待处理财产损溢` / 贷 `1405 库存商品`；
  - 金额 = **账上 `biz_inventory.amount` 的实际增减额**（生成取 `after.amount − before.amount`，出库/报废取 `before.amount − after.amount`），
    4 位小数，Rust 侧不重算、不舍入（详见 §3.10）。
- **为什么不能只做生成侧**：B2（`scripts/verify/erp_invariants.py:201-212`，BLOCKER）比的是
  `SUM(biz_inventory.amount)` 与 `Σ(1405 借−贷)`，容差 `TOL = 0.0001`（`:35`）。
  - 生成加金额不发凭证 ⇒ 差额 `+N×unit_cost`（v1 实测 `probe_b2.sql`：库存金额 7457.5 → 7507.5，1405 不动）；
  - **出库减金额不发凭证 ⇒ 差额 `−成本`**（同一个 B2，方向相反）。也就是说：**只要有人出一次库，B2 就红**。
    所以"只做生成侧"等于把 B1/C3 的红换成一个必然触发的 B2 红，验收不可能过。
- **为什么贷方是 `1901` 而不是 `4104`/不生成**：`1901 待处理财产损溢` 是《企业会计准则》对**盘盈存货**的标准过渡科目
  （无来源入库 = 期初盘盈），报废损失的借方也用它，**一个科目同时覆盖两个"无来源"方向**；
  `4104 利润分配—未分配利润` 属于权益分配口径，用在日常入库会让利润分配凭证混入业务流水，报表口径脏；
  "不生成凭证"等于给 B2 开永久盲区，ADR 明写"判据不改"（`docs/adr-20261031-erp-serial-batch-generate-semantics.md`）。
- **反例（会被打回）**：用 `stockin_model::money()`（`:176-178`，2 位）去算流水/凭证金额 ⇒ 与 `numeric(18,4)` 的账面对不上，
  B2 差 0.00x 抖动（`TOL=0.0001`，2 位精度下必红）。
- **否决成本**：改科目 = 改 §7.1 的一条 `INSERT`（`V0160` 里的科目编码）+ §3.10 的两处 `account_required("1901")`。

### A2 · 账务粒度统一「按桶」（不再在 S1/S2 之间二选一）

- **定论**：成本账与库位账都以「物料 × 仓库 × **`biz_inventory_location` 行**」为桶；`NULL` = 仓级汇总桶。
  - 序列号表 `biz_material_serial.location_id` 存的是 **`biz_inventory_location.id`（行 id）**（`V0138:79` 的外键指向它）；
  - 成本账 `biz_inventory.location_id` 存的**也是行 id**（`V0139:61-74` 外键 + 注释）；
  - 库位账 `biz_inventory_location.location_id` 存的才是**库位字典 id**（`V0137:560`，弱引用 `biz_location.id`）。
- **为什么这不是"S2 扩范围"**：现有**生产数据里 100% 是 `NULL` 汇总桶**（`serial_model::recompute_quantity` 只写 NULL 桶，
  前端弹窗也没有库位选择器：`frontend/src/views/business/erp/serial/index.vue:240-322` 的表单项只有 物料/仓库/数量/来源类型/批次号），
  所以「按桶」对现有数据的实际行为**与 S1 完全一致**；差异只出现在"调用方显式传了 `location_id`"这一条 API 直调路径上。
  按桶实现是**唯一同时满足 ADR 字面（有库位落库位行）与巡检判据**的做法，且不需要"先做 S1、以后再重构"。
- **顺带修掉的既有隐患**：`serial_model.rs:658-706 post_serial_txn` 的 `INSERT … SELECT … FROM biz_inventory WHERE material_id, warehouse_id`
  无桶条件（`:681-682`）⇒ 同物料同仓多桶时会写**多条**流水、每条 `qty=N` ⇒ B4（`erp_invariants.py:231-259`，BLOCKER）红。
  改成 `INSERT … VALUES`（仓级快照由 Rust 侧聚合读一次），并断言影响行数 = 1（§6.2）。
- **反例（实测过）**：把序列号的 `location_id`（行 id）当库位字典 id 去 upsert `biz_inventory_location`
  ⇒ 多出一条"拿行 id 当字典 id"的行，库位账 13 vs 成本账 10，B1 立刻红。见 §1.4(e)。

### A3 · 出库/报废侧按桶重算两本账（纳入本次后端卡）

- **定论**：把 `serial_model::recompute_quantity`（`:592`）**改造成按桶版**（函数名与调用点不变，减少回归面），
  语义是"把该仓的两本账按桶对齐成在库件数"，在 `transition_status_with`（`:996-1075`，出库/报废）里替换现在的调用；并**同时**生成成本结转凭证。
- **为什么必须纳入**：`serial_model.rs` 全文没有一处写 `biz_inventory_location`（v1 已核），
  不改的话「B1 绿」只在生成那一刻成立，第一次出库就红（v1 实测 `probe_s1.sql` B 段：成本账 4 / 库位账 5 / 在库号 4）。
- **为什么不能只 ±1**：`locked_qty`、并发出库、以及"号被软删"都会让 ±1 与件数脱钩；绝对值重算天然幂等，
  且与既有 `recompute_quantity` 的口径同源（"数量真相 = 在库号件数"）。
- **范围外但在本文件核过的（v3 更正了一处 v2 的错误结论）**：调拨 `transfer_model::settle_transfer`（`:1578`）
  确实**按桶维护成本账**（`resolve_inventory_row` `:1860` / `deduct_inventory_row` `:1905` / `credit_inventory_row` `:1962`，
  `INSERT … ON CONFLICT (material_id, warehouse_id, COALESCE(location_id, …))` 在 `:2052-2070`），序列号随之移仓（`:1730-1733`）；
  **但 `transfer_model.rs` 全文没有一处写 `biz_inventory_location`**（`grep -n "biz_inventory_location" backend/src/business/erp/transfer_model.rs`
  → 只有 `:482/:484/:814` 三处注释 + `:818` 的 `SELECT`，**零写入**），其自检 `assert_settle_invariants`（`:2207-2244`）
  也只核对 `biz_inventory` / `biz_material_serial`，**不看库位账**。
  ⇒ 这是**既存缺口**（与本卡无关）：任何一次调拨结算后，`B1` 在调出仓/调入仓两侧必红。
  真库实证（`cloudpivot_test`，B1 原样 SQL）：

  ```
  W3B-E2E-M1 | W3B e2e 调入仓 | 成本账 7.0000  | 库位账 0
  W3B-E2E-M1 | W3B e2e 调出仓 | 成本账 93.0000 | 库位账 0
  W3B-E2E-M2 | W3B e2e 调入仓 | 成本账 2.0000  | 库位账 0
  -- 该物料流水：IN/TRANSFER_IN/STOCK_TRANSFER 9、OUT/TRANSFER_OUT/STOCK_TRANSFER 9，收货流水 0 条
  ```

  ⇒ **本卡不动调拨**（不在 batch-generate 范围），但单列 §11 R3 并单独开卡；后端卡跑验收必须用**不含调拨流水的干净副本库**，
  否则 32/32 达不到——那不是本卡引入的红，且脚本会明确打出是调拨物料。
- **否决成本**：不做出库侧 = B1 在第一次出库就红（有实测），且出库成本无处结转（B2 红）。

## 1. 事实基线（逐条可复核，HEAD = `origin/main 198e7c1`；v2 写作基线是 `557c881`，行号对照见 §0.6.2）

### 1.1 现状链路（代码定位）

```text

  → serial_handler::generate_serials               :125-222   （校验 → 开事务 :205-208 → commit :211）
```

现状的**两个缺陷**（ADR ①′ 的根因，行号已核）：

1. `recompute_quantity`（`:592-629`）只写 `location_id IS NULL` 桶，`amount = EXCLUDED.qty * i.avg_cost`（`:609`），

⇒ 任何合法用户点一次：`erp_invariants.py` 的 **B1**（`:172-199`，BLOCKER）与 **C3**（`:283-290`，WARN）必红。

### 1.2 不变量判据（本方案必须同时满足的 6 条）

| B1 | `erp_invariants.py:172-199` | BLOCKER | 每个 (物料, 仓库)：`Σ biz_inventory_location.qty` = `Σ biz_inventory.qty`（**跨桶求和**） |

| B4 | `:231-259` | BLOCKER | 每个 (物料, 仓库)：`Σ(IN qty − OUT qty)` = `Σ biz_inventory.qty` |
| C3 | `:283-290` | WARN | 不存在 `qty > 0 AND avg_cost = 0` 的行 |
| C4 | `:292-299` | WARN | 每行 `|amount − qty × avg_cost| ≤ 0.01` |

### 1.3 库口径（真库核实，`cloudpivot_test` 克隆，HEAD schema）

只有 **5 个科目**（`docs/evidence` 里 `select account_code … from biz_account` 实测）：


| 字段 | 类型（JSON） | 必填 | 规则 | 落库 / 用途 |
|---|---|---|---|---|
| `unit_cost` | number（也接受字符串） | **是** | `> 0`；6 位四舍五入（`stockin_model::unit_price`，`:179-181`，`MidpointAwayFromZero` `:125`）；`< 100000000000` | `biz_inventory_txn.unit_cost numeric(18,6)`；金额 = `round(N × unit_cost, 4)`（**4 位**，与 `biz_inventory.amount numeric(18,4)` 同精度） |

> `biz_inventory.amount` / `biz_inventory_txn.amount` 都是 `numeric(18,4)`，用 2 位会让 B2（容差 0.0001）当场红。
> 生成金额由 `apply_cost` 内部 `round_dp(4)`（`stockin_model.rs:1109-1110` 的 `qty_text/amount_text`）决定，
> Rust 侧**不要**再自己 `money()`（那是 2 位）。

### 2.4 breaking change 说明

- **破坏性**：老客户端（不带 `unit_cost`）从「200 成功」变成「400 拒绝」。这是**有意**的：老行为每次点击都会写
  「qty>0 / amount=0 / 无库位账」，直接打红 B1（BLOCKER）+ C3。
- **不设兼容窗口、不做"缺省 0"**：缺省 0 等于保留缺陷。
- **必须同步的 4 处**（少一处就 500 或 e2e 红）：
  1. 前端表单与 api ts（§10）；
  2. `frontend/e2e/12-erp-serial-batch-walkthrough.spec.ts`（弹窗必须填单价，否则 e2e 400）；
  3. 前端单测 `frontend/tests/unit/serial-logic.test.ts`（`emptyBatchForm` 多了 `unit_cost` 字段）；
  4. 发布记录 + 对客话术（§8.6）。
- **不破坏**：响应体只**新增**字段（§2.5），老调用方的 JSON 解析不受影响。

### 3.0 调用顺序总览

```text
interface 层 serial_handler::generate_serials（serial_handler.rs:125-224）
```

`bucket` = **`params.location_id`**（`Option<Uuid>`，含义是 `biz_inventory_location.id`）；未传 = `None` = 仓级汇总桶。

### 3.1 取号：`take_numbers`（`serial_model.rs:472`）

- 调用点不变：`batch_generate` 内，`params.count`（1..=1000）与 `period_key`（北京时区 `yyyyMMdd`）。
- **保持既有取舍**：先取号后落号，插入失败浪费一段号（`:744-745` 注释；业务只要求不重号）。
- **不许做**：不许把取号搬到事务外；不许自己拼号（`format_serial_no` `:768` 是唯一入口）。

### 3.2 落号：一条 `INSERT … SELECT`（`serial_model.rs:776-783`，形态不变）

- `status` 仍写死 `'IN_STOCK'`（`:781`）、`inbound_at = now()`；`source_type` / `source_id` / `batch_no` / `location_id` 照旧透传。
- **新增断言**：`exec_sql` 返回的影响行数必须 `== params.count`，否则
  `DbError::InvalidValue(format!("批量生成落号条数不符：期望 {N}，实际 {m}"))` ⇒ 整单回滚（号段浪费可接受）。
  理由：记账用的是"请求条数 N"，插入 ≠ N 就会凭空多记/少记。
- **不许做**：不许逐条 `INSERT`（1000 次往返实测 1.5–2 s）；不许改状态枚举（`V0138:95` 只有 `IN_STOCK/OUTBOUND/SCRAPPED`）。

### 3.3 成本账：`stockin_model::apply_cost`（`stockin_model.rs:1100-1172`，`pub`）

```rust
let qty    = Decimal::from(params.count);
let amount = qty * params.unit_cost;          // 4 位（apply_cost 内部再 round_dp(4)，见 :1071-1072）
let cost   = CostBasis { qty, amount, unit_cost: params.unit_cost };
let applied = stockin_model::apply_cost(ex, material_id, warehouse_id, params.location_id, cost, now).await?;
```

它做的事（逐条对应 SQL）：

- `lock_inventory`（`:1014-1044`）先 `SELECT … FOR UPDATE`，命中桶用 `COALESCE(location_id, 0-uuid)`，
  与 `uk_biz_inv_mat_wh_loc`（`V0139:88-96`）同形 —— **锁与冲突目标必须同形，否则 42P10**；
- `INSERT … ON CONFLICT … DO UPDATE`：`qty = i.qty + EXCLUDED.qty`、`amount = i.amount + EXCLUDED.amount`（**加法**，`:1087-1088`）；
- `avg_cost` 在 **SQL 里** `ROUND(…, 6)`（`:1080-1082` / `:1089-1094`）；
- `RETURNING qty, amount, avg_cost` → `AppliedInventory { before, after }`（`:1113-1130`）。

**不许做**：
1. 不许在 Rust 侧算 `avg_cost` 或自己 `round_dp(6)` 再写回（W3c 踩过"Rust 与 PG 舍入差 1 分钱"，`stockin_model.rs:121-123`）；
2. 不许用纯 `UPDATE` 代替 upsert（首次入库时无行，改 0 行 = 静默丢账，`:1053-1055`）；
3. 不许改 `ON CONFLICT` 目标表达式（写成两列会 42P10，`V0139:84-92`）。

### 3.4 库位账：`stockin_model::apply_location_qty`（`stockin_model.rs:1217-1328`，`pub`）

```rust
stockin_model::apply_location_qty(ex, material_id, warehouse_id, params.location_id,
                                  Decimal::from(params.count), now).await?;
```

- **`location_id` 的语义是 `biz_inventory_location.id`**（不是 `biz_location.id`，`:1150-1156` 的模块注释把这条钉死了）；
- `Some(row_id)` ⇒ 分支 A：按主键 `UPDATE` 并校验 `material_id/warehouse_id` 一致（`:1188-1234`）；
- `None` ⇒ 分支 B：往 `(material, warehouse, location_id IS NULL)` 桶加（`:1236-1289`），冲突目标
  `(material_id, warehouse_id, location_id)` 直接命中 `uk_biz_inv_loc … NULLS NOT DISTINCT`（`V0137:576-577`）。
  **不要**写成 `COALESCE(...)`（那是 `biz_inventory` 的口径，套到本表会 42P10）；
- 加锁顺序：**成本账行先锁（`apply_cost` 内）→ 库位账行后锁（本函数）**，与收货过账一致
  （`stockin_handler.rs:1207` `apply_cost` → `:1220` `apply_location_qty` → `:1230` `write_txn` 的调用顺序就是这条）。

**不许做**：不许"有行就 UPDATE、没行就 INSERT"的读改写（并发首件撞唯一键）；不许顺手改 `locked_qty`（入库不入锁定量，`stockin_model.rs:1213-1216`）。

### 3.5 不变式①仍须成立 —— 只允许「一处加数量」

**禁止在生成路径调用 `recompute_quantity`（`:592`）后再加一次数量**。为什么是双计：

- `recompute_quantity` 是**绝对值重算**：`qty := count(IN_STOCK 号)`（`:594-612`），且只写 NULL 桶（改造后按桶）；
- `apply_cost` 是**增量加法**：`qty := qty + N`；
- 两者叠加有三个坑：① 若该物料有"按数量记的旧库存"（`serial_required` 后开，巡检 `:308-309` 明确允许），
  `recompute` 会把旧库存**一次性抹成序列号件数**（静默销毁差额）；② 请求带 `location_id` 时，
  `recompute` 写 NULL 桶 + `apply_cost` 写库位桶 ⇒ **双计**（实测 9 vs 5）；③ 数量真相变成两个来源。

**怎么保证不变式①仍然成立**（增量等式，不是绝对值重算）：

```text
落号：本次新增 IN_STOCK 号 = N（§3.2 的断言行数 = N）
记账：本次新增成本账 qty = N（apply_cost 的 EXCLUDED.qty = N，落在同一个桶）
⇒ 对该 (物料, 仓库)：Δcount(IN_STOCK) = ΔSUM(biz_inventory.qty) = N
⇒ 操作前该 (物料,仓库) 若满足 ①（差=0），操作后仍满足（差=0）
```

因此本方案**不修复历史差额**（§8.2），只保证不再新增差额。
**落库后断言（后端单测直接用这条 SQL，与 C5 同口径）**：

```sql
WITH s AS (SELECT material_id, warehouse_id, count(*)::numeric q
             FROM biz_material_serial
            WHERE material_id = :m AND status='IN_STOCK' AND deleted_at IS NULL
            GROUP BY 1,2),
     i AS (SELECT material_id, warehouse_id, sum(qty) q
             FROM biz_inventory WHERE material_id = :m GROUP BY 1,2)
SELECT coalesce(s.q,0) AS 在库号, coalesce(i.q,0) AS 帐面,
       coalesce(s.q,0) - coalesce(i.q,0) AS 差
  FROM s FULL OUTER JOIN i USING (material_id, warehouse_id);
```

### 3.7 流水：保留 `SERIAL_IN / SERIAL_BATCH`，但写实值（`post_serial_txn` 的改法）

现状（`serial_model.rs:658-706`）：

```sql
INSERT INTO biz_inventory_txn (…)
SELECT …, NULLIF(?::text,'')::numeric, i.avg_cost, NULLIF(?::text,'')::numeric * i.avg_cost, …,
       i.qty, i.amount, i.avg_cost, …
  FROM biz_inventory i
 WHERE i.material_id = ?::uuid AND i.warehouse_id = ?::uuid      -- :681-682 没有 location 条件
```

两个问题：
1. **多桶时写多条**（同物料同仓 2 个桶 ⇒ 2 条流水，每条 `qty=N` ⇒ B4 红）；
2. `unit_cost` 恒取 `i.avg_cost`（`:676-677`）、`amount = qty × avg_cost` —— 生成时 `avg_cost` 还没含本次单价，**金额是错的**。

**改法（三步全部必须）**：

1. 签名加 `unit_cost: Decimal, amount: Decimal, before/after: &InventorySnapshot`，
   **`INSERT … VALUES`（不再 `… SELECT … FROM biz_inventory`）** —— 一条语句恰好一行；
2. `before` / `after` 是**仓级聚合快照**（`SUM(qty)`, `SUM(amount)`, `avg = amount/qty`），
   由调用方在同一事务里读（读法见 §6.2）；
3. `exec_sql` 之后断言影响行数 `== 1`，否则
   `DbError::InvalidValue("库存流水写入行数异常：期望 1，实际 {n}（物料 {m} / 仓 {w}）")`。

`txn_type` / `biz_type` / `doc_type` **一字不改**（N9）。各列取值：

| 列 | 生成 | 出库/报废 |
|---|---|---|
| `unit_cost` | `params.unit_cost`（6 位） | 该桶 `avg_cost`（6 位） |
| `amount` | `applied.after.amount − applied.before.amount` | 仓级 `before.amount − after.amount` |
| `before_*` / `after_*` | 仓级快照 | 仓级快照 |
| `remark` | `批量生成 5 件（SN-…-000101 起）｜单价 12.340000｜金额 61.7000`（≤255，`V0137:433`） | 既有文案不变 |

### 3.10 凭证：`voucher::create_for_serial_movement`（新增，唯一写入口）

```rust
/// 序列号的三种"无来源"库存变动对应的凭证。
pub enum SerialMovement<'a> {

/// `amount` **必须**由调用方传入"账上真实差额"（4 位）；为 0 时本函数直接返回 Ok(None)（不发凭证）。
pub async fn create_for_serial_movement(

    kind: SerialMovement<'_>,
    doc_id: Uuid,           // 批量生成 = 首号 id；单件流转 = 序列号 id
```

## 4. 账务粒度：统一「按桶」（A2 的完整口径）

### 4.1 三个 id 的正确用法（**最容易踩的一处**）

```text
请求体 location_id  ──(=)──  biz_inventory_location.id            （行 id）
                                 │
        ┌────────────────────────┼───────────────────────────┐
        │                        │                           │
biz_material_serial.location_id  biz_inventory.location_id   biz_inventory_location.location_id
        （行 id，V0138:79）        （行 id，V0139:61-74）        （**库位字典 id**，V0137:560）
```

- 成本账的桶键 = `biz_inventory.location_id`（行 id）；
- 序列号的桶 = `biz_material_serial.location_id`（行 id）⇒ **两者可以直连**，这是"按桶重算"能成立的原因；
- 库位账的键 = `biz_inventory_location.location_id`（字典 id）⇒ **不能**用序列号的 `location_id` 去 upsert 它，
  必须"以库位账自身的行为驱动"，用 `il.id` 去匹配序列号（§5.2 的 SQL，实测把 13≠10 修回 10=10）。

### 4.2 现有数据的影响面

| 场景 | 现状 | 按桶口径下的行为 |
|---|---|---|
| 生产数据（全部 `location_id IS NULL`） | 单一汇总桶 | **与现状完全一致**（NULL 桶的重算就是原来的 `recompute_quantity`） |
| 前端弹窗（无库位选择器，`index.vue:240-322`） | 恒 `location_id = null` | 同上，业务影响面 ≈ 0 |
| API 直调带 `location_id` | 现状：号记了库位、账不认 | 成本账与库位账都落该行；出库按桶扣减，B1 恒等 |

### 4.3 巡检脚本**不用改**

B1/B4/C5 都是"按 (物料, 仓库) 聚合后比较"（`erp_invariants.py:172-199 / 231-259 / 301-340`），
桶是成本明细的内部结构，不进判据。**任何人不要为了让巡检变绿去改 `erp_invariants.py`。**

### 5.2 按桶重算：`recompute_quantity` 的新实现（函数名与调用点不变）

语义：把某 (物料, 仓库) 的成本账与库位账**按桶**对齐成"该桶的在库件数"。
**只对减少/持平成立**：桶里有件数但成本账没有行 ⇒ **报错回滚**（记账断链；凭空造行只能给 `avg_cost=0`，直接打红 C3）。

```rust
/// 把 (物料, 仓库) 的两本账按桶对齐成在库件数。出库/报废/移仓的唯一收尾。
/// 返回重算后的**仓级** qty（= Σ 桶 qty = 在库件数）。
pub async fn recompute_quantity(
    ex: &impl SqlExecutor, material_id: Uuid, warehouse_id: Uuid,
) -> DbResult<Decimal>
```

**① 成本账（按桶，绝对值；`amount = qty × 该桶 avg`，avg 不动）**

```sql
-- 与 probe_design_v2.sql 逐字同形（已在真库跑绿）
INSERT INTO biz_inventory AS i
    (id, material_id, warehouse_id, location_id, qty, locked_qty, avg_cost, amount, last_txn_at)
SELECT gen_random_uuid(), :m, :w, s.bucket, s.q, 0, 0, 0, now()
  FROM (SELECT location_id AS bucket, count(*)::numeric AS q
          FROM biz_material_serial
         WHERE material_id = :m AND warehouse_id = :w
           AND status = 'IN_STOCK' AND deleted_at IS NULL
         GROUP BY 1) s
ON CONFLICT (material_id, warehouse_id,
             coalesce(location_id, '00000000-0000-0000-0000-000000000000'::uuid))
DO UPDATE SET qty         = EXCLUDED.qty,
              amount      = EXCLUDED.qty * i.avg_cost,
              last_txn_at = now();
```

随后**必须**断言（否则"新桶行 avg=0"会静默打红 C3）：

```sql
-- 任何一行 > 0 即 InvalidValue("成本账桶缺失：物料 {m} / 仓库 {w} 有在库件数但无成本账行（记账断链）")
SELECT count(*) FROM biz_inventory
 WHERE material_id = :m AND warehouse_id = :w AND qty > 0 AND avg_cost = 0;
```

**② 库位账（以自身行驱动，**不要**用序列号的 `location_id` 去 upsert）**

```sql
-- 关键：il.id 匹配 serial.location_id（行 id）；NULL 桶单独匹配 location_id IS NULL
UPDATE biz_inventory_location il
   SET qty = (SELECT count(*)
                FROM biz_material_serial s
               WHERE s.material_id = il.material_id
                 AND s.warehouse_id = il.warehouse_id
                 AND s.status = 'IN_STOCK' AND s.deleted_at IS NULL
                 AND ((il.location_id IS NULL AND s.location_id IS NULL) OR s.location_id = il.id)),
       last_txn_at = now()
 WHERE il.material_id = :m AND il.warehouse_id = :w;
```

**③ 返回仓级 qty**：`SELECT coalesce(sum(qty),0) FROM biz_inventory WHERE material_id=:m AND warehouse_id=:w`。

**锁顺序（防死锁，与收货同一口径）**：先 `SELECT … FROM biz_inventory WHERE m,w ORDER BY COALESCE(location_id,0-uuid) FOR UPDATE`
锁全部桶行 → 再 `SELECT … FROM biz_inventory_location … ORDER BY COALESCE(location_id,0-uuid) FOR UPDATE`。
全局只有一种顺序（**按 `biz_material.id` 升序 → 成本账 → 库位账**），与 `stockin_model.rs:1207-1216`（锁顺序 + `locked_qty` 注释）记录的 PRD §3.2.6 口径一致。

### 5.3 出库/报废的事务步骤（`transition_status_with` 的改动，`:996-1075`）

```text
① SELECT … FOR UPDATE 锁号行（既有，:1013-1023）
② 状态机校验（既有，:1030-1038）
③ UPDATE status/outbound_at（既有，:1040-1057）
④ 仓级 before 快照：SELECT id,qty,amount,… FROM biz_inventory WHERE m,w … FOR UPDATE 求和（新）
⑤ recompute_quantity（按桶版，§5.2）（新）
⑥ 仓级 after 快照（新）
⑦ 写 OUT 流水（§3.7 的新形态：一条 VALUES，unit_cost = 该桶 avg，amount = before.amount − after.amount）（改）
⑧ 凭证：Outbound → 借 6401 / 贷 1405；Scrapped → 借 1901 / 贷 1405；金额 = ④−⑥（新）
   金额 ≤ 0 ⇒ 跳过（历史零成本存量，§8.2）
```

**不许做**：
1. 不许只减成本账不减库位账（B1 立刻红，§1.4(b)）；
2. 不许用 `qty ± 1` 代替按桶重算（并发出库 / 软删号会让账面与件数脱钩）；
3. 不许 `OUTBOUND → SCRAPPED` 再减一次库存（件数在出库那一刻已减过，`:1060-1064` 的既有注释就是这个口径）；

### 6.2 仓级快照怎么读（`lock_inventory` 的改动）

现状 `serial_model::lock_inventory`（`:552-574`）用 `query_first_sql` ⇒ **多桶时只拿到一行**。改成：

```sql
SELECT id, qty, amount, avg_cost FROM biz_inventory
 WHERE material_id = :m AND warehouse_id = :w
 ORDER BY coalesce(location_id, '00000000-0000-0000-0000-000000000000'::uuid)
   FOR UPDATE
```

Rust 侧 `SUM(qty)` / `SUM(amount)`，`avg = if qty > 0 { round(amount/qty, 6) } else { 0 }`
（只用于流水的 `before_cost/after_cost` 展示，**不写回** `biz_inventory.avg_cost`）。

### 6.3 B4 为什么不会再红

B4（`erp_invariants.py:231-259`）按 (物料, 仓库) 求 `Σ(IN − OUT)` 与 `Σ biz_inventory.qty` 比。
新形态**每次库存变动恰好一条流水**（断言行数 = 1），`qty` = 本次件数，方向由 `txn_type` 决定 ⇒ 两边恒等。
旧形态在多桶时写多条（每条 `qty=N`），是 B4 的唯一风险源。

## 8. 风险与回滚

### 8.1 与「批量生成不可复用于收货」的关系（`stockin_model.rs:51-70`）

那段模块注释记录的是 W2b 的实测结论：**收货过账不能调 `batch_generate`**，因为 `batch_generate` 会
`recompute_quantity`（把 qty 重算成件数）并**再写一条 `SERIAL_IN` 流水** ⇒ 台账双计 + 过账金额被抹。
本方案**不改这条结论，也不需要改收货**：

- 收货仍自己落序列号行（`source_type='PURCHASE'`）+ 自己调 `apply_cost`/`apply_location_qty` + 写 `PURCHASE_IN` 流水（`stockin_handler.rs:1207` `apply_cost` / `:1220` `apply_location_qty` / `:1230` `write_txn`）；
- 生成路径本来就不该有 `PURCHASE_IN` 流水、不该有收货单（N5）；
- 唯一重叠是"两者都调 `apply_cost`"——那是**加法原语**，正是它存在的目的。

⇒ `stockin_model.rs:51-70` 的注释**保持原样**（它约束的是"收货别去调 batch_generate"，不是"batch_generate 别记账"）。
**建议追加一句**（可选，不阻塞）：`// 2026-10-31（ADR ①′）：batch_generate 已自带两本账 + 凭证，仍不可被收货复用（会双写流水）。`

### 8.2 历史存量：**不补账**（增量口径）

- 巡检已红的存量（若有）**不在本卡修**：`inventory_audit`（`inventory_audit.rs`）的 `dry_run=false` 是既有修复通道。
- **历史零成本库存**（改判前生成的号）出库/报废时：`amount` 差额 = 0 ⇒ **不发凭证**（§3.10 第一条）。
  这是唯一的"不记账"分支，必须打 `WARN` 日志点名，便于财务事后判断；
  想彻底消掉这类数据：走盘点单/报废单把数量清零，再按新口径重新入库。
- **明确不做**：不给历史号补 `avg_cost`、不给历史库存补凭证、不改历史 `SERIAL_IN` 流水的 `unit_cost`。

### 8.3 移动加权数值例子（两次不同单价，期望值算式）

前置：物料 M、仓库 W、桶 = NULL 汇总桶（前端正常路径）。

| 步骤 | 操作 | `qty` | `amount` | `avg_cost`（SQL 里 `ROUND(…,6)`） |
|---|---|---|---|---|
| 0 | 初始 | 0 | 0 | 0 |
| 1 | 生成 5 件 @10.00 | 5 | `0 + round(5×10, 4) = 50.0000` | `ROUND(50/5, 6) = 10.000000` |
| 2 | 出库 1 件（结转成本 10） | 4 | `round(4×10, 4) = 40.0000` | 10.000000（不变） |
| 3 | 生成 5 件 @13.00 | **9** | `40 + 65 = 105.0000` | `ROUND(105/9, 6) = 11.666667` |
| 4 | 报废 1 件 | 8 | `round(8×11.666667, 4) = 93.3333` | 11.666667 |
| 5 | 混桶：再生成 3 件 @15.00 到库位桶 L | NULL 桶 8 / L 桶 3 | 93.3333 / `round(3×15,4) = 45.0000` | 11.666667 / 15.000000 |
| 6 | 从 L 桶出库 1 件 | NULL 8 / L 2 | 93.3333 / `round(2×15,4) = 30.0000` | 11.666667 / 15.000000 |

**期望值算式（单测直接照抄）**：

- 二次生成后：`avg = ROUND((before.amount + N×unit_cost) / (before.qty + N), 6)`；
- 出库/报废凭证金额：`amount = before.amount − after.amount`，
  其中 `after.amount = round(after.qty × avg, 4)`（4 位，`numeric(18,4)`）；
- 步骤 4 的凭证金额 = `105.0000 − 93.3333 = 11.6667`。注意这是**差额**口径，
  单桶时恰好等于 `round(1 × 11.666667, 4)`，多桶时**不相等** ⇒ 一律以差额为准（N11）。

### 8.4 与 P10 残留判据的关系

`scripts/datafix/p10/20_residue_report.up.sql` 第 ③ 道判据是"库存零价值"（v1 已核 `:14-19,57-60`）。
改判后生成的库存**有金额** ⇒ P10 不再自动清它。对客话术必须写清（§8.6）：**走查点出来的就是真实入库，撤销要走报废/红冲。**

### 8.5 回滚方案

| 层 | 回滚动作 | 副作用 |
|---|---|---|
| 代码 | `git revert` 本卡提交 + 重发前后端 | 老的"零成本生成"回来，B1/C3 会立刻红（等于回到事故态） |
| 数据 | **不做反向迁移**：本卡只写账不删账；已生成的凭证/流水/两本账**保留**（删了就破坏 B2 与审计链） | 无 |
| 迁移 | `V0160` 的 `down.sql` 仅在无分录引用时删科目 | 若有凭证引用，down 自动 no-op |
| 业务 | 误生成：对号做**报废**（借 1901 / 贷 1405），再让财务做红冲/审批 | 数量与金额都归零，审计链完整 |

### 8.6 对客话术（写进发布说明 / 用户手册）

> 「批量生成序列号」从今天起等于**期初/其他入库**：必须填**成本单价**，系统会同时更新**库存数量、库存金额、库位库存**，
> 并自动生成**入库会计凭证**（借 库存商品 / 贷 待处理财产损溢）。
> 因此这批货**不能再被 P10 当测试夹具自动清掉**，撤销要走**报废单 + 红冲凭证**。
> 出库/报废也会自动结转成本（借 主营业务成本 或 待处理财产损溢 / 贷 库存商品）。

### R3 详情（真库实锤，含排查 SQL）

**结论**：`transfer_model::settle_transfer` 只写 `biz_inventory`（成本账，按 `location_id` 桶），
**从不写 `biz_inventory_location`（库位账）**，因此任何一次调拨结算都会让 `B1 库位账合计 = 成本账 qty` 变红。

**证据**（三条独立、可复跑）：

1. 代码：`grep -n "biz_inventory_location" backend/src/business/erp/transfer_model.rs`
   → `:482` / `:484` / `:814` 全是注释，`:818` 是 `SELECT`；**无一处 `INSERT/UPDATE/DELETE`**。
   自检 `assert_settle_invariants`（`:2207-2244`）只查 `biz_inventory` 与 `biz_material_serial`，不查库位账。
2. 真库（`cloudpivot_test`，用 `erp_invariants.py:173-189` 的原样 B1 SQL 跑）：
   `W3B-E2E-M1` 调出仓 成本账 `93.0000` / 库位账 `0`；调入仓 `7.0000` / `0`；`W3B-E2E-M2` 调入仓 `2.0000` / `0`。
3. 该物料流水只有 `TRANSFER_IN` / `TRANSFER_OUT`（各 9 件），**收货流水 0 条** ⇒ 差额不可能来自收货或批量生成。

**排查 SQL**（上线前/验收前跑，必须 0 行）：

```sql
-- 是不是「有调拨但没库位账」导致的 B1 红？
SELECT m.material_code, w.warehouse_name,
       coalesce(c.q,0)::text AS 成本账, coalesce(l.q,0)::text AS 库位账,
       (SELECT count(*) FROM biz_inventory_txn t
         WHERE t.material_id = coalesce(c.material_id,l.material_id)
           AND t.warehouse_id = coalesce(c.warehouse_id,l.warehouse_id)
           AND t.doc_type = 'STOCK_TRANSFER') AS 调拨流水数
  FROM (SELECT material_id, warehouse_id, sum(qty) q FROM biz_inventory GROUP BY 1,2) c
  FULL OUTER JOIN (SELECT material_id, warehouse_id, sum(qty) q FROM biz_inventory_location GROUP BY 1,2) l
    ON c.material_id = l.material_id AND c.warehouse_id = l.warehouse_id
  LEFT JOIN biz_material m ON m.id = coalesce(c.material_id, l.material_id)
  LEFT JOIN biz_warehouse w ON w.id = coalesce(c.warehouse_id, l.warehouse_id)
 WHERE abs(coalesce(c.q,0) - coalesce(l.q,0)) > 0.0001
 ORDER BY 调拨流水数 DESC;
```

**闭环安排**：已单独开卡 **`t_270b472e`**（`backend-developer`，父卡 = 本卡，会在本卡完成后自动解锁）——
补 `settle_transfer` 的库位账加减 + `assert_settle_invariants` 加一条 B1 断言 + U1–U3 三条真库单测。
本卡（`t_1daca7f4`）与后端卡（`t_421d8aa1`）**不承担**这个缺口，但后端卡验收库必须是干净副本库（§5.4 已写死判据）。

> 为什么不再 block：本卡已被总管从 `blocked` 重新入队且未给出新口径（父卡 `t_5d52a72e` 的复查记录里也没有 Q1–Q3 的答复）。
