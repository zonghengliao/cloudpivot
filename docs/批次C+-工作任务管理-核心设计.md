## 二、状态机（含依赖约束）

```
                前置任务未完成 → 拒绝进入 DOING（除非手动强开并留痕）
                                │
   ┌─────────┐      ┌─────────┐ │    ┌─────────┐      ┌──────┐
   │  TODO   │─────▶│  DOING  │─┴───▶│ REVIEW  │─────▶│ DONE │
   └────┬────┘      └────┬────┘      └────┬────┘      └───┬──┘
        │                │  打回（填原因）   │               │
        │                │◀─────────────────┘               │
        │                │                   重开（创建人/管理员）
        │                │              ┌───────────────────┘
        ▼                ▼              ▼
   ┌─────────────────────────────────────────┐
   │            CANCELLED 已取消              │
   └─────────────────────────────────────────┘
```

### 规则（8 条，每条定权限）

| # | 迁移 | 谁有权 | 附加约束 |
|---|---|---|---|
| 1 | TODO → DOING | 负责人 | **所有 FS 前置必须 DONE**，否则拒绝（见 §四） |
| 2 | DOING → REVIEW | 负责人 | 仅 `need_review=true` 时可用 |
| 3 | DOING → DONE | 负责人 | 仅 `need_review=false`；**有未完成子任务则拒绝** |
| 4 | REVIEW → DONE | 验收人（分派人/创建人） | 记录验收意见 |
| 5 | REVIEW → DOING | 验收人 | **必须填打回原因**，通知负责人 |
| 6 | 任意 → CANCELLED | 负责人/创建人/分派人/管理员 | 必须填取消原因 |
| 7 | DONE → DOING（重开） | 创建人/管理员 | 重置 `done_at`，进度回退 |
| 8 | 强开前置（绕过依赖） | 管理员 | 需填理由，`changelog` 留痕（防滥用） |

## 三、进度模型（两种模式）

```
有子任务 → 自动 = 已完成子任务数 / 总子任务数（手改无效）
无子任务 → 手动滑块（0~100，步长 10），随状态联动
```

| 状态 | 进度 |
|---|---|
| TODO | 0%（可手动 ≤30%） |
| DOING | 手动值（默认 10%） |
| REVIEW / DONE | 100% |
| CANCELLED | 冻结当时值 |

**父子不自动改状态**：子任务全完成 → 父进度 100% + 卡片标「可结项」，但状态不变。
**父任务 DONE 前置检查**：有未完成子任务 → 拒绝并提示数量。

## 四、任务依赖（v2 新增，完整设计）

### 支持类型
| 类型 | 含义 | 本版是否支持 |
|---|---|---|
| **FS**（Finish-to-Start） | 前置完成 → 后置才能开始 | ✅ **唯一支持的，也是唯一实用的** |
| SS / FF / SF | 同时开始 / 同时完成 / 开始才完成 | ❌ 不显示在 UI（数据库枚举预留） |

> 为什么只做 FS：项目管理的 95% 场景是"这个做完才能做那个"。其它三种类型是 MS Project 式的重型概念，会让界面和权限判断复杂度翻倍。

### 表
```sql
biz_task_dependency (
    task_id        uuid    -- 后置任务（被阻塞方）
    depends_on_id  uuid    -- 前置任务（阻塞方）
    dep_type       varchar(4) DEFAULT 'FS'
    created_at, create_by
    PRIMARY KEY (task_id, depends_on_id)
    CHECK (task_id <> depends_on_id)          -- 反自反
    -- 跨表校验：两者必须同 project（若都有 project_id）
)
```

### 循环检测（必须做，否则死锁）
插入依赖前：从 `depends_on_id` 出发 DFS 找是否可达 `task_id`
```sql
-- 用递归 CTE 实现（PG 原生）
WITH RECURSIVE reach(id) AS (
    SELECT :depends_on_id
    UNION
    SELECT d.depends_on_id FROM biz_task_dependency d JOIN reach r ON d.task_id = r.id
)
SELECT 1 FROM reach WHERE id = :task_id;
-- 命中 = 成环 → 拒绝（错误码 TASK_DEP_CYCLE）
```

### 运行时约束（这是"逻辑严密"的体现）
1. **进 DOING 前检查**：所有 FS 前置必须 DONE，否则拒绝
   - 错误信息要**点名**：「前置任务 TSK-202610-0012「数据库设计」尚未完成」
2. **看板卡片标记**：被阻塞的任务显示 🔒 + 「被 2 个前置阻塞」
3. **甘特图**：依赖用箭头连线，被阻塞段用斜纹底
4. **前置被取消**：后置任务的依赖视为"已解除"，但提醒负责人（前置取消了，你可能要调整计划）

### UI（简单）
- 任务详情页右栏底部「依赖」区块：
  ```
  前置任务（必须先完成）
    · TSK-... 数据库设计   [已完成 ✓]
    · TSK-... 接口联调     [进行中 60%]  ← 未完成，本任务被阻塞
    [+ 添加前置]
  后置任务（本任务完成后可做）
    · TSK-... 上线验收
  ```

## 五、甘特图（v2 新增）

### 视图设计
```
任务名              │ 10/27  10/28  10/29  10/30  10/31 │
────────────────────────────────────────────────────────
数据库设计          │ ████████                          │
接口联调            │          ████████████             │   ← FS 依赖箭头
前端开发            │          ░░░░░██████████          │   斜纹=被阻塞
上线验收            │                          ████     │
                    │              │今天                 │
```

### 要素
| 要素 | 说明 |
|---|---|
| 时间轴缩放 | 日 / 周 / 月 三档切换 |
| 任务条 | 从 `start_date` 到 `due_date`，颜色=优先级，进度用内条 |
| 依赖线 | 前置结束点 → 后置开始点的折线箭头（FS） |
| 今日线 | 红色竖线 |
| 逾期 | 已过 due_date 未完成 → 条形变红 + 虚线延长 |
| 里程碑 | P1（有 project 后再做） |

### 技术实现（不引重依赖）
- **自绘 SVG**（推荐）：任务行数 <300 时可流畅；拖拽用 pointer events
- 备选：`frappe-gantt`（轻，~30KB）——若要拖拽调期，引它更省事
- **本版只做"看"**：拖拽改日期放 P1（避免与依赖约束打架）

## 六、AI 作为执行者（v2 新增）

### 设计要点：机器人就是"特殊用户"，不新建主体
```sql
-- sys_user 加一个字段（底座改动，需报批）
ALTER TABLE sys_user ADD user_type varchar(8) NOT NULL DEFAULT 'HUMAN';
-- HUMAN | ROBOT
```
这样：
- 任务 `owner_id` 不需要改类型（仍指向 `sys_user.id`）
- 权限、审计、通知、变更日志**全部天然复用**
- 机器人的操作在 `changelog` 里 `operator_name` 显示为机器人名

### 机器人账号怎么用
| 项 | 设计 |
|---|---|
| 创建 | 管理员在用户管理里新建，勾选「机器人账号」→ `user_type=ROBOT` |
| 登录 Web | ❌ **禁止**（登录接口对 ROBOT 返回"机器人账号不可登录"） |
| API 访问 | ✅ 用 API Key（或长期 token）调任务接口 |
| 权限 | 按角色分配（可以只给"任务执行"相关权限） |
| 可见性 | 机器人作为负责人时，任务正常显示 |

### AI 接到任务的触发方式（两种，选一种即可）
**方案 A（推荐，简单）**：任务被指派给机器人 → `notice::dispatch()` 发一条特殊类型的通知 → 外部 agent 通过 **轮询任务列表** 或 **订阅通知 SSE** 接手
**方案 B（实时）**：指派时调 webhook（`sys_config` 配 URL）→ agent 收到 POST 后执行 → 回调 API 改状态

**先做 A**（零配置、可立刻用），B 作为 P1。

### AI 执行流程（约定）
```
1. agent 拉取「负责人=自己 且 状态=TODO」的任务
2. 置为 DOING（调 PATCH /status）
3. 执行中可写评论（进度说明）
4. 完成：若 need_review=false → DONE；true → REVIEW（等人工验收）
5. 失败：填 reject_reason（"执行失败原因"）→ 退回或 CANCELLED
```

### 安全
- 机器人**不能**分派任务给别人（除非显式授予）
- 机器人**不能**删除任务
- 机器人操作全部记 `changelog`（可审计）

## 八、分派（同 v1）

| 动作 | 负责人变 | 原负责人 | 用在哪 |
|---|---|---|---|
| **分派** | ✅ 变 | 不保留 | 上级派活 |
| **转派** | ✅ 变 | **变协作人** | 我不干了交给你 |
| **加协作人** | ❌ 不变 | 不变 | 一起干 |

- 不设层级限制（允许跨部门），但**分派即自动加协作人**（分派人能看到进度）
- 被分派方可「退回」+ 填原因
- 子任务深度限 2 层

## 十三、实施拆分（7 步）

| 步 | 内容 | 验收 |
|---|---|---|
| **T1** | 表（7 张）+ 任务 CRUD + 可见性（scope ∪ 参与） | 建/查任务；跨部门协作人可见 |
