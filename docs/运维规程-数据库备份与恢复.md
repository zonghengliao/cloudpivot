# 运维规程：数据库备份与恢复

> 适用范围：云枢通用后台（基础版）生产库 `cloudpivot`（144）与 145 演练/测试库 `cloudpivot_dev`。
> 脚本位置：`scripts/ops/backup_db.sh`、`scripts/ops/restore_db.sh`（均为纯 bash，无额外依赖，只需 `pg_dump` / `pg_restore` / `psql` / `flock`）。
> 首次落地记录与实测证据：`docs/evidence/2026-11-09-db-backup/`。

---

## 1. 备份

### 1.1 自动（cron）

| 环境 | 时间 | 保留 | cron 行 |
|---|---|---|---|
| 144 生产 | 每日 **02:30** | **14** 份 | `30 2 * * * bash /opt/cloudpivot/scripts/ops/backup_db.sh --keep 14 >> /var/log/cloudpivot/backup.log 2>&1` |
| 145 测试 | 每日 **03:30** | **7** 份 | `30 3 * * * bash /opt/cloudpivot/scripts/ops/backup_db.sh --keep 7 >> /var/log/cloudpivot/backup.log 2>&1` |

- 日志：`/var/log/cloudpivot/backup.log`（cron 追加写，**不含口令**）。
- 退出码 0 成功 / 1 失败，供 cron / 监控判断。
- cron 环境（`PATH=/usr/bin:/bin`、无登录 shell）已验证可跑：脚本自己 source `/etc/cloudpivot/cloudpivot.env`（144）或 `/etc/cloudpivot/cloudpivot-dev.env`（145），不依赖交互式环境变量。

### 1.2 手工

```bash
# 默认：读 env、备份到 /root/db-backup、保留 14 份
bash /opt/cloudpivot/scripts/ops/backup_db.sh

# 常用参数
bash scripts/ops/backup_db.sh --keep 7                 # 只留 7 份
bash scripts/ops/backup_db.sh --dir /data/bak          # 换目录
bash scripts/ops/backup_db.sh --db cloudpivot_dev      # 备份非当前 env 的库（如恢复前的临时库）
bash scripts/ops/backup_db.sh --dry-run                # 只做连通性 + 容量预检，不落盘
```

### 1.3 文件布局

```
/root/db-backup/                       700
├── <db>-<YYYYmmdd-HHMMSS>.dump        pg_dump -Fc（custom format，支持按表选择性恢复）
├── <db>-<YYYYmmdd-HHMMSS>.meta        基线 JSON（供恢复后自动比对，600）
├── .backup-<db>.lock                  flock 串行化锁
├── pre-restore/                       restore_db.sh 恢复前自动备份（保留 5 份）
├── logs/                              pg_restore 输出日志（restore-<db>-<ts>.log）
└── from-144/                          演练时从 144 拷过来的 dump（145 上）
```

### 1.4 校验备份是否正常

```bash
ls -lht /root/db-backup/ | head             # 最新几份 + 大小
tail -20 /var/log/cloudpivot/backup.log     # 最近一次 cron 结果
cat /root/db-backup/<db>-<ts>.meta          # 基线（迁移数 / 表数 / 关键表行数）
pg_restore --list /root/db-backup/<db>-<ts>.dump | head   # 归档可读性
```

判据：**每天应有一份新的 `.dump` + 同名 `.meta`**；若某天缺失，先看 `backup.log` 里当天是否有 `ERROR`。

### 1.5 脚本做了什么（行为契约）

1. 解析连接参数：`--env-file` → `$NIK_DATABASE_*` → 依次探测 `/etc/cloudpivot/cloudpivot.env`、`cloudpivot-test.env`、`cloudpivot-dev.env`。
2. 预检：能否连库；`pg_dump` 主版本 ≥ 服务端主版本（低版本 dump 会导出不完整，直接拒绝）。
3. 磁盘余量：要求可用空间 ≥ **2 ×** 预估 dump 大小（预估取上一份 dump 的实际大小，无历史时按库大小 20% 估）。不足直接失败，**不产生半截文件**。
4. `flock -w 600` 串行化（cron 与手工并发不会互相覆盖）。
5. `pg_dump -Fc` 写入 `.tmp`，成功后 `mv` 改名（半截文件不会被当成有效备份）。
6. `pg_restore --list` 校验归档；TOC 为空或「库里 N 张表但 dump 无任何 TABLE DATA」即判定损坏并删除该 dump。
7. 写同名 `.meta` 基线。
8. 保留策略：按 `--keep` 删除最旧的 `<db>-<ts>.dump` + `.meta`；**只删本脚本命名规则的文件**，不动目录里其它手工备份。

### 1.6 安全约定

- 口令只经 `PGPASSWORD` 环境变量传给客户端，**不出现在命令行参数**（`ps` 看不到）也不进日志。
- 备份目录 700，`.meta` 600。
- dump 里是**完整业务数据**（含口令哈希）：不得进 git、不得外发；需要跨机搬运走内网 + 用完即删。

## 2. 恢复

### 2.1 恢复演练步骤（先演练，后生产）

```bash
# ① 选 dump（一般取最新一份）
ls -lht /root/db-backup/*.dump | head -3

# ② 恢复到临时库（不存在会自动建，owner = 应用账号）
bash /opt/cloudpivot/scripts/ops/restore_db.sh /root/db-backup/cloudpivot-20261109-220753.dump \
     --target-db cloudpivot_restore_test --yes

# ③ 核对输出：脚本自己打印「基线 vs 恢复后」逐项比对表，末行 `基线比对 : PASS`
#    另可人工抽查：
psql -d cloudpivot_restore_test -c "select count(*) from information_schema.tables where table_schema='public' and table_type='BASE TABLE'"
psql -d cloudpivot_restore_test -c "select count(*), max(version::int) from schema_migrations where success"
psql -d cloudpivot_restore_test -c "select username from sys_user order by username"

# ④ 起一个临时实例连临时库做冒烟（登录 + 3 个关键接口），确认能真的把系统拉起来
#    144 的生产口令不要拿去演练：演练库里口令哈希替换成本地已知值再登录（见 §2.4）

# ⑤ 演练通过、且确认要回滚生产时，才考虑恢复生产：
bash scripts/ops/restore_db.sh <dump> --target-db cloudpivot \
     --force-prod --confirm-db-name cloudpivot --yes
```

### 2.2 脚本做了什么（行为契约）

1. `pg_restore --list` 校验 dump（损坏 / 非 custom format 直接拒绝）。
2. **生产库防护**：目标库命中「受保护库」时默认拒绝 —— 受保护库包括 `cloudpivot`（生产标准名）、当前 env 的库、`/etc/cloudpivot/cloudpivot.env` 里的库、`template0/1`、`postgres`、`$PROTECTED_DBS`。
   要恢复必须同时给 `--force-prod` **且** 完成库名二次确认（交互输入库名，或非交互给 `--confirm-db-name <同名>`）。
3. 打印「即将把 X 恢复到 Y，目标库现有数据会被清除」。
4. **必须 `--yes`**（非交互环境没给就中止；交互环境要输入 `yes`）。
5. **恢复前自动备份当前目标库**到 `pre-restore/`（保留 5 份）；备份失败即中止恢复 —— 不冒「恢复错了没退路」的险。目标库不存在时跳过（无数据可备）。
6. `pg_restore --clean --if-exists --no-owner --no-privileges`；日志落 `logs/restore-<db>-<ts>.log`。
   已知良性的报错只有一类：对 INHERITS 子表的继承约束做 `DROP CONSTRAINT IF EXISTS` 时 PG 报 `cannot drop inherited constraint`（数据本身由 TABLE DATA 整表重建）。**判定基准是恢复后的基线比对，不是 pg_restore 的退出码。**
7. 恢复后核对并打印比对表：`tables.count` / `migrations.count` / `migrations.max_version` / 每张关键表行数。
8. 退出码：**0 成功** / **1 参数或执行失败** / **2 恢复完成但基线不一致（需要人工判断，别切流量）**。

### 2.3 基线 `.meta` 与不一致处理

`.meta` 示例（真实产出）：

```json
{
  "db": "cloudpivot",
  "dumped_at": "2026-11-09T22:07:54+08:00",
  "dump_file": "cloudpivot-20261109-220753.dump",
  "server_version_num": 180006,
  "migrations": {"count": 295, "max_version": 362},
  "tables": {"count": 176},
  "key_tables": {"sys_user": 3, "sys_role": 11, "sys_menu": 435,
                 "biz_purchase_order": 0, "biz_voucher": 0, "biz_inventory": 0},
  "size_bytes": 1509164, "db_size_bytes": 37508799,
  "verify": {"toc_entries": 2332, "table_data_entries": 175}
}
```

任一指标不一致 → 脚本退出码 2 并逐行打 `ERROR 不一致：<指标> 期望 X，实际 Y`。

排查顺序：
1. 看 `logs/restore-<db>-<ts>.log` 有无非良性 ERROR；
2. 若只有「关键表行数」不一致，确认是不是恢复时目标库仍有业务写入（**恢复期间必须停服务**）；
3. 若 `migrations.count` 不一致，多半是恢复后应用自动跑了新迁移（先停服务再比对）；
4. 确认 dump 与服务端主版本匹配（`pg_dump` 18 → 服务端 18 才完整）。

### 2.4 演练库登录（口令问题）

生产 admin 口令属于用户本人（走 UI 自助改密，见生产 `password_change_logs`），**演练方不应持有、也不要为了演练去重置生产口令**。
演练库是 dump 的副本，因此演练时采用「只替换演练副本里 admin 的 password 哈希」的做法，其余（账号行 id、角色、菜单、业务数据）全部来自 dump：

```sql
-- 只在演练副本执行（示例：哈希取自演练环境 dev 库 admin，同一产品同一 argon2 参数）
UPDATE sys_user SET password = '<dev 库 admin 的 argon2 哈希>',
       must_change_password = false, is_locked = false, login_fail_count = 0
 WHERE username = 'admin';
```

参考脚本：`docs/evidence/2026-11-09-db-backup/login_smoke_145.sh`（起隔离实例 → 登录 → 5 个关键接口 → 断言 → 停实例）。

## 3. RPO / RTO

| 指标 | 数值 | 依据 |
|---|---|---|
| **RPO** | **24 小时**（每日全量一次；错过一次 = 最多 24h 数据丢失） | cron 每天 02:30 全量 `pg_dump -Fc` |
| **RTO** | **约 10 分钟** | 实测：1509164 字节（1.5 MB）dump 的 `pg_restore --clean --if-exists` **耗时 1s**（145 演练，176 张表）；余量留给停服务、恢复前自动备份、服务重启与冒烟 |
| 单份备份体积 | 约 1.5 MB（生产库物理 37.5 MB，custom format 压缩率约 4%） | `prod_144.meta` |
| 14 份占用 | 约 21 MB | 磁盘余量检查要求 ≥ 2 × 单份 |

**做不到的事（必须明说，别过度承诺）**：
- 没有 WAL 归档 / 流复制 → **不能**恢复到「任意时间点」（PITR），只能恢复到「最近一次备份」。
- 备份落在同一台机的 `/root/db-backup`，**磁盘整机故障会同时丢库和备份**。要真正抗整机故障，必须加一条「备份出机」（rsync/scp 到另一台机或对象存储），本卡未做，属于后续运维项。
- RPO 24h 是「日全量」口径；如果业务要求更小 RPO，需要改成「日全量 + 更频繁增量/归档」，不是调 cron 时间就能解决。

## 4. 恢复演练（每季度一次，硬性）

1. 用**最新** dump 恢复到临时库：`restore_db.sh <dump> --target-db cloudpivot_drill_<yyyymmdd> --yes`。
2. 起一个隔离实例连临时库（`NIK_DATABASE_NAME=<临时库>` + 独立端口，绝不动生产/在线实例）。
3. 冒烟：**登录** + 3 个关键接口（例：`/system/user/page`、`/system/menu/tree`、`/system/auth/menus`）。
4. 记录演练日期、dump 文件、基线比对结果、冒烟结果（追加到 `docs/evidence/` 对应目录）。

## 5. 常见故障

| 现象 | 原因 | 处理 |
|---|---|---|
| `backup.log` 里 `磁盘余量不足` | 备份堆积 / 目录所在分区被别的数据占满 | 清 `/root/db-backup` 旧备份、换 `--dir`、或扩容；**别调小阈值糊过去** |
| `pg_dump: permission denied` | 库里有不属于应用账号的表（历史 datafix 备份表/人工建表） | 按日志提示 `ALTER TABLE <表> OWNER TO <应用账号>` 或 `GRANT SELECT`；先自查非 owner 表 |
| `pg_dump 主版本 < 服务端` | 客户端工具太旧（会导出不完整） | 升级客户端到 ≥ 服务端大版本 |
| `另一个备份进程持有锁超过 600s` | 上一次备份卡住 | 查 `ps aux | grep pg_dump`；确认无残留后删 `.backup-<db>.lock` 或等其退出 |
| 恢复退出码 2 且只有行数不一致 | 恢复期间业务仍在写目标库 | 停服务（`systemctl stop cloudpivot`）后重跑恢复 |
| 恢复到生产被拒绝 | 生产库防护生效（预期行为） | 确认要走回滚流程再加 `--force-prod --confirm-db-name cloudpivot`；**先演练过再动生产** |
| cron 没跑 | PATH / env 探测失败 | 用 `env -i HOME=/root PATH=/usr/bin:/bin bash ... --dry-run` 复现；日志里第一行会打印用了哪个 env 文件 |
