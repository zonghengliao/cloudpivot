### 核心逻辑（`validate_parent`）

```text
1. parent_id == self_id            → 拒绝「父任务不能是任务自己」
2. parent 不存在 / 已软删           → 拒绝（原口径）
3. 一条 WITH RECURSIVE 取回祖先链    → 起点父任务 depth = 1，越往上越大
   · 链上同一 id 出现两次（库里已有 A→B→A）→ 拒绝「父任务链成环（数据异常）」，**不死循环**
   · self_id 出现在链里（= 我要挂到自己的子孙下）→ 拒绝「会成环」
   · 链长 >= MAX_TASK_DEPTH(8)      → 拒绝「子任务最多 8 层：父任务链已到第 N 层」
4. 通过
```

递归 CTE 自带 `depth < MAX_TASK_DEPTH + 1` 上限：既够判定「太深」，又保证脏环一定停。
**只发一条 SQL**（单测 `ancestor_chain_query_is_one_recursive_cte` 钉住：一个 `?::uuid` 参数、无分号拼接），不做 N+1。

## 五、与卡面的差异（逐条说明）

1. **测试库**：卡面写「测试用 `cloudpivot_test` 库」。实测该库停在 `schema_migrations_max=88`、`biz_task` 表根本不存在（`ERROR: relation "biz_task" does not exist`），跑本卡用例必然失败。按 W1a / W1b 的惯例改用**本卡隔离库 `cloudpivot_t8a`**（`createdb -O cloudpivot`，迁移到 `V0137`，94 条迁移）。
2. **测试数口径**：卡面写「当前 931 + 20 = 951」，实际基线是 **967**（W1b 的 36 条 ERP 用例已进 main），本卡 +10 → **977**。卡面数字已过期，不是缺陷。
3. **文案处数**：卡面点名 3 处，实际改了 **5 处**（`handler.rs` 251 / 305 / 1146 / 1152 + `model.rs` 的 63005 消息）+ `dto.rs` 1 处文档注释。全部是注释 / 文案，无逻辑变化。
4. **`depth` 字段**：按卡面「先做相对缩进」的决策**未加**。T8-B（前端）如需绝对深度再单开卡。
5. **`MAX_PARENT_DEPTH`**：从硬编码 `8` 改成 `MAX_TASK_DEPTH + 1`（= 9）。理由：业务允许 8 层 ⇒ 最深任务有 7 级祖先，8 够用；取 9 是给「历史数据 / 手工改库造出更深链」留余量，同时保证脏环一定停。
