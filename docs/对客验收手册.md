## 2. prod 走查前后的硬动作

### 2.1 前置条件

- 在一台能 `ssh root@172.18.10.144` 且**已配置免密（BatchMode）**的机器上执行（通常用开发机 `172.18.10.99`）。
- 仓库 clone 必须先 `git pull --ff-only` 到最新 main：
  脚本会把你**本机工作区这份**脚本 + 3 个检查文件 scp 到 prod 的 `/tmp/e2e-postrun` 再执行，
  **不用 prod 上那份可能过期的仓库副本**（脚本第 150 行注释：「当前工作区版本，prod 上的仓库副本可能过期」）。
- **不要在开发机上用 `--local`**：`--local` 是「prod 库就在本机」（即在 144 上直接跑）的模式，
  在开发机上跑会因找不到 `/etc/cloudpivot/cloudpivot.env` 而 exit 2。

### 2.2 走查前（只读闸门，必须先绿）

```bash
cd <仓库 clone 目录>
git pull --ff-only
bash scripts/e2e-postrun-check.sh --check-only
echo "exit=$?"
```

| 退出码 | 含义 | 该怎么办 |
|:---:|---|---|
| **0** | 库干净：无零成本夹具残留，且 `erp_invariants` **32/32 / BLOCKER 0 / WARN 0** | ✅ 可以开始走查 |
| **1** | 检出残留（`--check-only` 不清理） | ⛔ **先别走查**。这不是本次走查造成的，是上一次没清；找负责人处置后再重跑 |
| **2** | 环境问题（ssh / psql / env 文件不可用） | ⛔ **绝不能当成"干净"**。先修环境 |

`--check-only` 是**纯只读**：不写库、不删数据、不打备份。可以放心在生产上反复跑。

### 2.3 走查后（检出 → 清理 → 复验，一步都不能省）

```bash
bash scripts/e2e-postrun-check.sh
echo "exit=$?"
```

按脚本自己的分段（`scripts/e2e-postrun-check.sh`）：

| 段 | 动作 | 触发条件 |
|:---:|---|---|
| ① | 检出零成本夹具（只读，`scripts/verify/e2e_fixture_residue.py`） | 总是 |
| ② | `datafix/p10/00_backup.sh` 打快照 → `P10_GENERIC_APPLY=1 apply.sh` 清理（幂等、可回滚） | **仅当 ① 检出残留** |
| ②' | 复检残留，必须 `exit=0` | 仅当执行了 ② |
| ③ | 三账不变量 `scripts/verify/erp_invariants.py` 必须 **32/32 / BLOCKER 0 / WARN 0** | 总是 |

- 无残留时会**跳过** ②，直接进 ③ —— 这时整次调用实际上是只读的。
- **② 是本手册唯一会写 prod 的步骤**（打快照 + 按 P10 清夹具）。谁执行的、几点执行的，必须记名（§4.1）。
- 退出码含义同 §2.2；exit 1 表示「清理后仍有残留」或「不变量不达标」，**不许当成通过**。

每次走查必须留下两份记录：

## 3. 写库类按钮清单

### 3.1 三步判定一个按钮会不会写库

1. 看接口方法：`POST` / `PUT` / `PATCH` / `DELETE` → **写库**；只有 `GET`（page / list / detail / export）→ 只读。
2. 看有没有二次确认框（删除、作废、过账、取消、出库、报废）→ 基本可以确认**写库**。
3. 拿不准就**别点**，先在隔离实例上点一遍（`bash scripts/verify/e2e_isolated_instance.sh up`）。

### 3.2 本次走查的核心三件（已知会写库）

#### ① 批量生成（序列号页右上角 │ `data-testid="btn-batch-generate"`）

| 项 | 内容 |
|---|---|
| 页面 | `/business/erp/serial`（序列号列表 → 右上角「批量生成」→ 弹窗「批量生成序列号」） |
| 接口 | `POST /api/business/erp/serial/batch-generate` |
| 权限码 | `business:erp:serial:generate` |
| **ADR 落地前（当前 main `fe5952e`）** | 🚫 **prod 上一律不许点**。当前请求体（`BatchGenerateReq`）没有成本单价字段，点一次就是一次「零成本入库」——这正是 11:34 事故的成因 |
| **ADR 落地后** | 🟡 可点，**但必须填「成本单价（必填）」**；点完产生的是**真实入库**（§3.3） |
| 撤销 | 落地后**不能删掉重来**，只能走**红冲 / 盘点调整** |

#### ② 调拨单提交（调拨单页「提交审批」）

| 项 | 内容 |
|---|---|
| 页面 | `/business/erp/transfer`（单据详情/行动作「提交审批」） |
| 接口 | `PATCH /api/business/erp/transfer/{id}/status`，目标态 `PENDING` |
| 权限码 | `business:erp:transfer:status` |
| 走查可点 | 🟡 可点，但**必须提前约定**：它会起审批实例、进待办 |
| 数据性质 | **真实业务单据**（不是夹具），不会被 P10 清 |
| 撤销 | 「撤回」→ `CANCELLED`，**终态**（只能删除、不能再提交），且会终止在跑的审批单；发货 / 收货 / 撤回都要二次确认 |

#### ③ 审批通过 / 驳回

| 项 | 内容 |
|---|---|
| 页面 | 待办 / 待我审批（`/task/list`、流程详情） |
| 接口 | `POST /api/business/flow/task/{id}/approve`、`POST /api/business/flow/task/{id}/reject` |
| 权限码 | 均为 `business:flow:approve`（驳回若选「退任意节点 / 终止」还需 `business:flow:admin`，否则 403 + `65004`） |
| 走查可点 | 🟡 可点，但**必须两个不同的真实审批人账号**（§4.2） |
| 数据性质 | **真实业务数据**：会把业务单据推进到终态（如调拨单 → `APPROVED`） |
| 撤销 | **没有"点回去"**。驳回意见要求 ≥ 5 字（`65005`）；已结束的审批单 409 + `65024` |

### 3.3 🔴 点了之后算「真实业务数据」还是「夹具」（必须对客讲明白）

判定只有一条：**这笔库存有没有账载价值**（`amount` / `avg_cost` 是否为 0）。
依据是 P10 残留判据第 ④ 道「库存零价值」——**一旦有价值（= 有账载来源），一律不碰**。

| 场景 | 走查后 P10 会不会清 | 数据性质 | 怎么撤 |
|---|:---:|---|---|
| **ADR 落地前**在 prod 点「批量生成」 | **会清**（判据 ①SERIAL_IN+SERIAL_BATCH 流水、③序列号无真实来源、④库存零价值 同时成立） | 夹具 | 跑 §2.3 即可 |
| **ADR 落地后**带单价点「批量生成」 | **不会清**（第 ④ 道不成立：有成本就没价值为零） | **真实入库（期初 / 其他入库）** | **红冲 / 盘点调整**，跑 P10 没用 |
| 收货入库 / 调拨 / 出库 / 报废 | 不会清 | 真实业务数据 | 业务单据反向（红冲 / 撤回 / 盘点） |
| 新建物料 / 仓库 / 库位 / 供应商 / 单位 | 不会清（不是库存夹具） | 真实主数据 | 删除；被引用则改停用 |

> ⚠️ **对客一句话**：ADR 落地后，「走查时点出来的库存」是**要入账的真实库存**，不是演练数据。
> 走查前必须先选对物料、算好单价；**撤不回来，只能走红冲或盘点**。

### 3.4 其余 ERP 写库入口（按代码清点，扩展清单）

`backend/src/business/erp/*.rs` 里所有非 GET 路由：

| 写库入口 | 接口 | 走查建议 |
|---|---|---|
| 物料 / 仓库 / 库位 / 单位 / 供应商 新增改 | `POST/PUT/DELETE /business/erp/{material,warehouse,location,unit,supplier}` 及 `/{id}` | 🟢 可点（主数据，可删/停用） |

### 3.5 走查前问自己三句话（一页纸 SOP）

1. **这个按钮会写库吗？** → 查 §3.2 / §3.4。
2. **写出来算真实数据吗？** → 有没有金额：有金额 = 真实入库。
3. **这单能收尾吗？（会不会卡死、撤不撤得掉）**
   - 会起审批的单据（调拨、采购单…）：**先看它的审批节点是不是「全部超管 / 全部某角色」的会签（`assignee_type=ADMIN/ROLE` + 会签 `ALL`）**。
     是 ⇒ **别在 prod 提交**：会签的通过条件是**全员投票**，只要超管/该角色里有一个**测试号、停用号或离职未摘权的号**，
     这张单就**永久 PENDING**（2026-10-31 `TK-20261031-000007` 就是这么卡住的：4 个超管 2 票通过、2 票永远等不到）。
     会签人数与成员清单在 §4.4 核对。
   - 撤得掉吗？撤不掉 / 会卡死 ⇒ **不在 prod 演示**，改用隔离实例（`bash scripts/verify/e2e_isolated_instance.sh up`，客户看录屏/远程共享）。

走查结束后由登记人核对 `auth_logs`（`username / auth_type / ip / browser_type / os_type / created_at`），确认登录行为与登记一致。

### 4.2 铁律

1. **超管账号（含 `admin`）不得用于对客演示。** 演示审批请用**两个真实不同角色**的账号。
2. **禁止在同一台机器上换号演示。** 申请人与审批人同人同机时，审批约束与留痕全部失效。
3. 账号 ↔ 设备一一对应并登记；不允许共用账号。
4. 走查造出的单号 / 批次号 / 序列号段，全部进 §2.4 留档。
5. 🔴 **测试/自测账号（`*_test`、`qa.*`、`selftest-*`、`*-ai-test`）不得进入生产 `SUPER_ADMIN` 或任何会签角色；
   走查结束当天必须核对一次超管成员清单，成员必须等于甲方确认的名单。**
   - **为什么是铁律而不是建议**：超管集是**审批节点的会签名单来源**（`assignee_type=ADMIN` = 全部超管）。
     测试号在里面且节点是会签（`ALL`）⇒ 这个账号**永远不会投票** ⇒ 任何走该流程的单据**永久 PENDING**，
     业务卡死且系统不报警。2026-10-31 的 `TK-20261031-000007` 就是实例（4 个超管里 `laoliu_test` 是测试号，2/4 通过后永久挂起）。
   - **核对方法**：走查当天按 §4.4 的**只读** SQL 跑一次，把输出贴进走查记录；名单不符 ⇒ **先处理权限再走查**（不用走查单代替处理）。
   - **发现不符怎么办**：测试号摘权是**跨团队的生产权限变更**，本团队**不自行执行**——按 `docs/待决策.md` ② 报老大书面确认。
6. 走查前按 §3.5 第 ③ 句自检「这张单会不会卡死」（会签节点 + 全员来源）；会卡死的单据**不在 prod 提交**。

## 5. 批量生成 · 对客话术（可原文复制给客户）

> **内部使用说明**：本节正文是给客户看的，**不含内部术语**，可整段复制进邮件/微信/演示口播。
> 时效：随 ADR 落地（表单出现「成本单价（必填）」）后生效；**落地前请勿演示该按钮**。
> 若客户今天就要看，请在隔离实例上演示并明确说明"这是测试环境"。

<!-- ===== 对客正文开始（以下内容可直接发给客户） ===== -->

### 「批量生成」是什么

「批量生成」用于给**一物一码**的物料一次性生成一批序列号（条码）。

请把这一步理解为：**一次没有采购单的入库**——相当于期初建账或其他入库。号一生成，这批货就进了你选的仓库，系统就要按入库来处理，并计入**存货成本**。

### 为什么要填「成本单价」

- **库存金额 = 数量 × 成本单价**。这个金额会进入存货成本、进入库存账，之后这批货出库时结转成本也用它。
- 这一步没有采购单可以参照，所以单价必须由**操作人负责填写**（按实际的**不含税单价**填）。
- 同一物料以后再入库、单价不同，系统会自动按**移动加权平均**滚动成本，不需要你手工改。

### 为什么没填单价不让提交（错误提示怎么读）

提交时如果提示：

> **「批量生成即入库，请填写成本单价（期初/其他入库口径）」**

意思是：这一批序列号会立刻被当成库存入账，**没有金额就没法记账**。系统宁可在这里拦一下，也不允许出现「有数量、没金额」的库存——那种库存出库时没法结转成本，期末对账会对不上。

### 生成之后想改怎么办

生成之后这批货就是**真实入库**了，错了要走**红冲**或**盘点调整**，**不能删掉重来**。
所以点「生成」之前请确认三件事：**物料、仓库、数量、单价**都对。

### 一句话

> 「批量生成」= 一次直接入账的入库，**数量 × 单价 = 记进存货成本的钱**，单价由你填、由你负责；错了走红冲，不走删除。

## 6. 合同类型怎么选（对客判定表）

> **内部使用说明**：本节可直接发给客户；表单里的类型下拉也带同样口径的 tooltip。
> 合同类型是**已签冻结**字段（签完发现选错只能「终止 → 新签」），所以**建单时**就要选对。

| 你要做的事 | 选哪一类 | 乙方从哪选 |
|---|---|---|
| 会**下采购单**（收货 / 入库 / 应付）的采购行为（货物**或**服务物料） | `PURCHASE`（采购合同） | 供应商 |
| 会**开销售单**的销售行为 | `SALES`（销售合同） | 客户 |
| **不下任何订单**的长期服务（物业、维保、外包年框、软件订阅） | `SERVICE`（服务合同） | **供应商**（服务商在系统里按供应商登记） |
| **不下任何订单**的租赁（房租、设备租用） | `LEASE`（租赁合同） | **供应商**（出租方在系统里按供应商登记） |

一句话：**会下订单 → 采购 / 销售；不下订单 → 服务 / 租赁。**

### 为什么服务 / 租赁合同没有「履约进度条」

服务 / 租赁合同**不挂采购单、也不挂销售单**（系统在订单侧按合同类型拦住了，这是设计口径，不是漏校验），
所以「已执行金额 / 未关闭单据」对这两类**不适用**。详情页会明确显示「履约口径：不适用」，
**不会**显示 `0.00` 或 0% —— 看到「不适用」时请理解为「这类合同本来就不按订单算履约」，
不要理解成「一分钱都还没执行」。需要按合同跟付款进度时，请在合同的付款/应付单据上跟踪。
