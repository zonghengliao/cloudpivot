## 2. 第 1 步：抽公共函数（**先抽再接管**）

### 2.1 抽之前长什么样

```text
post_in_tx ⑦
  └── voucher::create_for_stock_in(ex, &locked, first_material, operator, now)
        └── 组装 AutoVoucher（摘要 / 金额 / 物料 / 供应商 / 仓库）
              └── create_auto()  → resolve_accounts → purchase_in_lines → 平衡校验 → post_voucher（取号 + 期间闸 + 落库）
```

问题：`create_for_stock_in` 需要一份**内存里的单头**（过账时手上有 `FOR UPDATE` 锁好的行），
而配置侧（联动动作）手上只有一个单据 id。照最省事的写法，配置侧会自己再查一次单头、
再拼一次摘要和金额——那就是**两套取数**，迟早有一天「摘要差一个空格 / 金额少 round 一次」。

### 2.2 抽成什么样

```rust
// 取数：唯一实现（纯函数，不查库）
impl VoucherBizCtx {
    pub fn of_stock_in(header: &StockInRow, first_material: Option<Uuid>) -> Self { … }
    pub fn with_voucher_date(&self, date: NaiveDate) -> Self { … }   // account_date 覆盖
}

// 生成：唯一实现（取号 + 平衡校验 + 落库全在这里）
pub async fn create_by_rule(
    ex: &impl SqlExecutor,
    template_code: Option<&str>,      // Some = biz_voucher_rule.rule_code（配置的「模板」）
    ctx: &VoucherBizCtx,
    operator: Option<Uuid>,
    now: DateTime<Utc>,
) -> DbResult<Uuid>;

// 旧路径变成薄封装（一行）
pub async fn create_for_stock_in(…) -> DbResult<Uuid> {
    let ctx = VoucherBizCtx::of_stock_in(header, first_material);
    create_by_rule(ex, None, &ctx, operator, now).await
}
```

配置侧的取数入口（`erp/stockin_query.rs`，走**调用方的事务**）：

```rust
pub async fn voucher_biz_ctx(ex, id) -> DbResult<Option<VoucherBizCtx>>   // header_on + first_material_of
pub async fn first_material_of(ex, id) -> DbResult<Option<Uuid>>
```

`first_material_of` 的排序是 `ORDER BY material_id, location_id, line_no` —— 与过账时
`ordered.sort_by(|a,b| (material_id, location_id, line_no))` + `ordered.first()` **逐字同序**。
存货分录的辅助核算只带这一个物料，排序错一位，凭证就和旧路差一个物料维度。

### 2.3 科目解析也只留一份

`resolve_accounts`（按 `biz_type`）与新的按模板取规则（`load_rule_by_code`）共用
`resolve_rule`（行 → 三个科目）与 `resolve_accounts_with`（规则 → 物料 → 默认 三层退化）。
新增的两个函数只是**换查询键**，不新增退化顺序。

### 2.4 行为不变的证明

| 断言 | 证据 |
|---|---|
| 凭证相关用例零改动、41 passed | `07-voucher-regression.txt` |
| 收货过账用例零改动、133 passed（含「过账生成凭证 / 作废红冲 / 应付金额」） | `06-stockin-regression.txt` |
| 新旧两路同一张单逐字段一致（含**凭证号**） | 单测 `voucher_new_path_matches_legacy_field_by_field` |

## 3. 第 2 步：实现 `GENERATE_VOUCHER`

```rust
ActionSpec {
    code: "GENERATE_VOUCHER", phase: Phase::InTx, severity: Severity::Critical,
    implemented: true,
    params: [ template_code?  biz_type  account_date?  mode?(SHADOW|TAKEOVER) ],
}
```

| 环节 | 谁做 | 说明 |
|---|---|---|
| 参数解析 | `VoucherSetting::from_params` | 缺省 `mode = SHADOW`（**默认不接管**） |
| 第 3 层校验 + 取数 | `prepare_voucher` | 实体必须 `STOCK_IN`；模板必须启用；单据必须存在且金额不为 0 |
| 落账 | `commit_voucher` → `voucher::create_by_rule` | **不新写任何取号 / 平衡算法** |
| 事务 | `InTx` | 用调用方（过账）的事务，引擎不再包一层 |
| 失败 | `Skipped` → 退回老路；`Failed` → `Err` → 整笔回滚 | 见 §3.2 |

### 3.1 为什么 `mode` 要放在参数里

第 3 步要求「先配规则但不接管」再「对比一致后接管」。没有 `mode` 就只有「配了 = 接管」一条路，
没法做并行对比。与 D2 的 `SEND_NOTICE.mode` 同一套打法（默认 SHADOW，安全侧默认）。
`mode` 只是一个键，**不改 schema**（jsonb 参数，库里 CHECK 只管动作码与禁 SQL 键）。

### 3.2 两种失败必须分开（这是本卡最容易做错的地方）

| 情形 | 归类 | 行为 | 理由 |
|---|---|---|---|
| 参数非法 / 模板停用 / 单据不存在 / 金额全 0 | `Skipped` | 打 ERROR，**退回旧逻辑发凭证** | 配置写错不能让用户丢凭证（漏记凭证 = 库存动了账没动） |
| 取号失败 / 借贷不平 / 期间已结账 | `Failed` | 引擎 `Err` → **整笔过账回滚** | 这类失败退回老路也一样失败（同一个 `post_voucher` 闸），退回去只是把错误换个地方报；而「配置说要生成却让过账成功」必然破坏不变式 |

`SEND_NOTICE` 是「失败一律退回旧逻辑」，凭证**不是**：通知可以重发，账不能半张。这点写进了
`engine::stockin_voucher` 的函数文档，避免后来者「照抄通知那套」把回滚语义悄悄降级。

## 4. 第 3 步：并行对比 → 切换

### 4.1 SHADOW 怎么做到「真跑一遍还不留数据」

```text
① BEGIN（调用方 post_in_tx 的事务）
② SAVEPOINT d3_voucher_shadow
③ 配置路径真落账：create_by_rule → 取号 → 写 biz_voucher + biz_voucher_entry + 状态日志
④ 读回快照 snapshot_of(voucher_id)（15 个字段 + 逐行分录）
⑤ ROLLBACK TO SAVEPOINT（凭证、分录、状态日志、biz_seq 的自增全部回退）
⑥ 旧逻辑照常走 create_for_stock_in → 拿到凭证 id
⑦ finish_stockin_voucher_shadow：旧凭证快照 vs 影子快照逐字段比 → 日志 matched / diffs
```

关键点：**先影子、后旧路**。因为影子回滚会把 `biz_seq` 的当日计数器一起回退，
所以旧路拿到的凭证号与影子完全相同 —— 连「凭证字号」都能比，而不是只能比金额。

真机日志（`02-e2e.txt` C9）：

```
configured_voucher_no=PZ-20261103-000002 / legacy_voucher_no=PZ-20261103-000002
matched=true diffs=[]
field_count=15
```

### 4.2 对比字段（15 项）

`voucher_count / voucher_word / voucher_no / voucher_type / source_type / source_id / source_no /
period / voucher_date / summary / total_debit / total_credit / entry_count / is_red / lines(逐行：行号+摘要+科目编码+借贷+三组辅助核算)`

「张数」也在里面：SHADOW 阶段库里若多出一张，`voucher_count` 立刻不等。

### 4.3 TAKEOVER 之后旧调用点怎么处理

`post_in_tx` ⑦ 现在是路由：

```rust
match linkage::engine::stockin_voucher(ex, &voucher_ctx).await {
    Ok(Configured { voucher_id, .. }) => voucher_id,          // 配置落账，旧路不执行
    Ok(Legacy { reason, shadow }) => {                        // 无规则 / SHADOW / 降级
        let id = voucher::create_for_stock_in(…)?;            //   ← 旧调用点，保留为兜底
        if let Some(shadow) = shadow { finish_stockin_voucher_shadow(…) }
        id
    }
    Err(error) => return Err(error),                          // 关键动作失败 → 整笔回滚
}
```

**为什么没有把 `create_for_stock_in` 的调用点删掉**：空表（0 条规则）必须「行为逐字不变」，
这是卡面与 D2 的硬要求；删掉调用点等于「不配规则就没有凭证」，直接把现有业务打断。
所以旧调用点从「唯一实现」降级为「无配置 / 影子 / 降级时的兜底」，
配置进入 TAKEOVER 后**运行期不再执行**（e2e D2：接管后恰好 1 张，D3/D4 日志可证）。

## 6. 还剩哪些动作是占位 + 各自的前置项

白名单 11 个动作，本卡之后 **3 个已实现**（`SEND_NOTICE` / `UPDATE_RECEIVED_QTY` / `GENERATE_VOUCHER`），
**8 个占位**。占位动作的三重保护不变：配置写入 400 / 绕过 API 写库则运行时 ERROR+跳过 / `spec.reuse` 写清复用谁。

| # | 动作码 | 前置项（照这个顺序做，别跳） |
|---|---|---|
| 1 | `WRITE_INVENTORY` | 先把 `post_in_tx` ③/③b 抽成不依赖「单头 + 明细结构体」的可独立调用函数（`stockin_model::apply_cost` / `apply_location_qty` 已具备大部分形态）；**牵动库存不变式 ①②③**（成本账 = 库位账 = 流水），必须单独一张卡 + 全量不变量 |
| 2 | `WRITE_INVENTORY_TXN` | 同 1，且要先定「谁写流水」的唯一序号口径（`write_txn` 吃 `applied` 的 before/after，不能由配置自由填） |
| 3 | `UPDATE_COST` | 同 1（移动加权），且必须与 `WRITE_INVENTORY` 同一事务、同一顺序，否则「单价错一轮」不可逆 |
| 4 | `REVERSE_VOUCHER` | 直接复用 `voucher_write::reverse_posted`（校验 + 红字号段 + `reversed_by` 回写已收口）；前置是「作废路径也走配置」——要先让 `cancel_in_tx` 的凭证红冲能被配置接管，否则同一个动作两处触发 |

## 7. 已知边界（本卡不做，如实记录）

1. **只有 `STOCK_IN` 的凭证能被配置生成**：`GENERATE_VOUCHER` 的取数口径只有「采购入库」一种
   （金额 = 不含税 / 税 / 价税合计 vs 应付）。付款凭证、出库结转成本的金额来源不同，硬套会生成错账，
   所以 `prepare_voucher` 显式拒绝其它实体（`Skipped` + 文案点名）。要接管它们，得先各自定义「取数」。
2. **配置仍然没有 HTTP 入口**：读写走 `linkage::model::{upsert_rule, list_rules}`，
   真机验收用 psql 直插（与 D2 同一处理，配置页留给前端卡）。
3. **SHADOW 必须在事务里跑**：没有事务时影子会真的落一张凭证，所以 `stockin_voucher`
   检测到 `post_commit_queue().is_none()` 就直接退回旧逻辑并打 ERROR。过账路径永远在事务里，
   这条只是防御（比如将来有人从 `db()` 直接调）。
4. **`mode` 没有「按比例灰度」**：只有 SHADOW / TAKEOVER 两档。真要按单据灰度得加参数 + 分流规则，
   当前不值得（先做到「对比一致再切」）。
5. **影子对比是日志，不是落库表**：与 D2 同一处理，要「对比看板」得另加一张执行流水表（另开卡）。
6. **`GENERATE_VOUCHER` 走的是专用路由，不是 `engine::run`**：过账路径用 `linkage::engine::stockin_voucher`
   （因为要「先影子后旧路」的顺序 + SAVEPOINT 回滚，通用 `run` 做不到）。
   `actions::run_in_tx` 里也挂了 `GENERATE_VOUCHER` 分支（保持白名单一致 / 将来通用触发点可用），
   但**同一个触发点不要同时走两条路**，否则一张单会出两张凭证。真要在 `STOCK_IN/POSTED` 上接
   `engine::run`，必须先把 `stockin_voucher` 摘掉。
