# 运维规程 —— 客户版本升级（`scripts/upgrade.sh`）

> 一句话：**有 `scripts/setup_new_env.sh` 管「从零建库」，就有 `scripts/upgrade.sh` 管「旧版本升到新版本」**。
> 新环境只能由迁移链建库（见 [新机器部署-纯迁移重建.md](./新机器部署-纯迁移重建.md)）；
> 已上线的环境只能由本脚本升级 —— 两者都不许 `pg_dump | psql` 跨机拷库。

| 项目 | 内容 |
| --- | --- |
| 脚本 | `scripts/upgrade.sh`（bash，`set -euo pipefail`，单文件自举，不依赖仓库里的其他脚本） |
| 日志 | `/var/log/cloudpivot/upgrade-YYYYmmdd-HHMMSS.log`（不可写时退到 `~/cloudpivot-logs/`，并在终端显红提示） |
| 备份 | `/var/backups/cloudpivot/<库名>-upgrade-<时间戳>/`（`db.dump` + `cloudpivot.old` + `upgrade-state.env` + `before.txt` / `after.txt` / `apply.log`） |
| 回滚点 | `/var/backups/cloudpivot/latest` 符号链接指向最近一次**正式**升级的备份（`--dry-run` 的备份落在 `dryrun-` 前缀目录，不登记为回滚点） |
| 退出码 | `0` 成功或已是最新 ｜ `1` 失败（已尽量自动回滚）｜ `2` 参数/环境问题 |

## 1. 什么时候用

- 客户现场从 v1 升到 v2（**库要动**：新增迁移文件）。只换二进制不动库的情况不需要本脚本。
- 升级前**必须先演练**：`--dry-run` 在真备份上把迁移跑一遍，生产零改动。
- 升级失败 / 冒烟不过 / 被人 `kill -9` 打断 → 用 `--rollback` 退回升级前。

## 2. 九步流程（顺序不能变）

| # | 步骤 | 做什么 | 失败时的状态 |
| --- | --- | --- | --- |
| ① | 版本检测 | 库内 `schema_migrations`（`kind='versioned' and success` 的 name 集合）与**目标 ref 树上**的 `backend/migrations/**/V*__*.up.sql` 做**集合差**，打印 `V0367 → V0371，共 4 条待应用`；同时校验 `applied_via` 合法、已应用迁移的 checksum 未被改写 | 未动任何东西 |
| ② | 前置检查 | 备份盘余量 ≥ 2× 库大小、DB 连通、服务是否在跑、psql/pg_dump/pg_restore/curl/cargo、工作区无未提交改动 | 未动任何东西 |
| ③ | 全库备份 | `pg_dump -Fc` → 校验非空 → `pg_restore --list` 可读 → 记 `before.txt`（表数/唯一索引/关键表行数）→ 备份现役二进制 | **备份不成立就退出**，绝不往下走 |
| ④ | 拉代码+编译 | `git fetch --tags` → 切到目标 tag/commit → `cargo build --profile <release|debug>`；编译完成后把新二进制快照到备份目录，并把旧二进制放回安装位 | 库一点没动 |
| ⑤ | **迁移预演** | 把③的备份恢复到临时库 → 在临时库上逐条应用待迁移（用目标树的 `scripts/verify/deploya_migrate.sh`，与生产同一套记账逻辑）→ 校验记账对账、表数、原有表是否还在、关键表与唯一索引 | 删临时库 + 退出，**生产一点没动** |
| ⑥ | 正式迁移 | 停服务 → 逐条应用 → 对账（记账增量 == 待跑条数）→ 集合复核（目标树 - 库 = 空） | 失败即从备份恢复 + 启服务 + 报错退出 |
| ⑦ | 换二进制 + 启动 | 停服状态 `cp → .new` + `mv -f` 原子换文件 → `systemctl start` → 轮询 `/health` | 启动失败给出回滚命令 |
| ⑧ | 冒烟 | `/health` 200 → 登录 200（`code=0`）→ 关键接口 3 个 200（默认 `auth/me`、`dept/tree`、`menu/tree`） | **任一失败自动回滚**：恢复库 + 换回旧二进制 + 切回旧代码 + 启服务 |
| ⑨ | 收尾报告 | 前后版本、应用了哪些迁移、代码前后提交、备份路径、耗时、关键表行数对比（`before.txt` vs `after.txt`） | —— |

## 3. 常用命令

```bash
# ① 先演练（客户现场第一件事；生产零改动）
bash scripts/upgrade.sh --dry-run

# ② 正式升级到 origin/main
bash scripts/upgrade.sh --yes

# ③ 升级到指定 tag / commit
bash scripts/upgrade.sh --target v1.2.0 --yes

# ④ 回滚（最近一次正式升级的备份 / 指定备份目录）
bash scripts/upgrade.sh --rollback latest --yes
bash scripts/upgrade.sh --rollback /var/backups/cloudpivot/cp-upgrade-20261110-210305 --yes
```

常用参数：

| 参数 | 说明 |
| --- | --- |
| `--target REF` | 目标 git ref（tag/commit/分支），默认 `origin/main` |
| `--repo PATH` | 仓库根（默认脚本所在仓库） |
| `--env-file PATH` | 环境变量文件（默认按 `/etc/cloudpivot/cloudpivot{,-prod,-dev,-test}.env` 顺序找） |
| `--service NAME` / `--no-service` | systemd 单元名；`--no-service` 表示脚本只管库与二进制，服务由现场自己停起 |
| `--db NAME` | 覆盖库名（凭据仍取 env 文件） |
| `--profile release\|debug` | 构建 profile（默认 release；测试环境可用 debug） |
| `--binary PATH` | 后端二进制路径（默认 `<repo>/backend/target/<profile>/cloudpivot`） |
| `--base-url` / `--smoke-user` / `--smoke-pass` / `--smoke-apis` | 冒烟地址与三项检查 |
| `--dry-run` | 只做 ①②③⑤ |
| `--rollback [SPEC]` | 回滚：`latest`（默认）/ 备份目录 / `.dump` 文件 |
| `--yes` | 跳过所有交互确认（CI） |
| `--skip-rehearsal` | **不推荐**，跳过⑤（会显红警告；V0359 事故就是这么来的） |
| `--skip-build` | 已手工编好，跳过编译（仍会切代码） |
| `--allow-drift` | 允许已应用迁移内容与库内 checksum 不一致（引擎启动会 FATAL，危险） |

## 4. 为什么这些设计（改脚本前先读）

1. **待应用清单 = 集合差，不是「版本号 > 库内最大版本」**。引擎 `needs_apply` 只认 `(kind,name)` 有没有 `success` 记录（`vendor/nik-db/src/migrate/mod.rs:1263-1275`），gap 里的低版本照样要跑。比大小的写法会把 gap 整批漏掉 —— 2026-11-05 发版中断的真因，详见 `scripts/deploy/migrate_plan.sh` 头注释。
2. **⑤ 迁移预演是硬要求**。V0359 撞已有数据的唯一约束，直接在生产升，服务中断 30 分钟。本脚本把备份恢复到临时库先跑一遍，同类问题在临时库上炸，生产零改动（实测见 §6 验收③）。
3. **回滚 = 换库，不是 `--clean` 覆盖**。恢复时先 `pg_restore` 到一个全新库，再 `ALTER DATABASE ... RENAME` 顶上（原子），被换下来的旧库改名留档 `<库名>_prerollback_<时间戳>`。`pg_restore --clean` 在分区表/扩展上会留残渣（继承约束删不掉、数据可能重复），本脚本不用它。
4. **回滚本身也要可回滚**：`--rollback` 先把**当前**状态再打一份 `rollback-safety-<ts>.dump`，才动线上库。
5. **二进制两段式**：④ 编译完先快照新二进制、把旧二进制放回安装位；⑥ 成功后 ⑦ 才原子换新。这样迁移窗口内若服务意外重启，跑的是与库一致的旧二进制，而不是「新二进制 × 半迁移的 schema」。
6. **状态文件边跑边写**：`upgrade-state.env` 每完成一步就落盘（`PHASE=backup_done|rehearsed|migrating|migrated|started|smoke_ok|done`）。被 `kill -9` 时没有 trap 兜底，`--rollback latest` 靠它判断该退回到哪 —— 实测见 §6 验收④。
7. **不假设 root**：非 root 且无免密 sudo 时，`systemctl` 一律拒绝（`--no-service` 可绕过）；日志/备份目录不可写就退到用户目录并显红提示，不假装成功。
8. **迁移不可变**：脚本动手前把库内 `checksum` 与目标树文件逐条比对（引擎口径：逐行去 CR + 行尾 `\n`，`history.rs:540`），改过就拒跑；「库里有、树里没有」只告警（引擎会忽略，但违反纪律）。
9. **自举**：④ 会 `git checkout`，脚本从仓库里执行会被原地改写 → 启动时先把自己复制到 `/tmp/cp-upgrade-self.*` 再跑。

## 5. 现场处置手册

| 现象 | 处置 |
| --- | --- |
| 脚本中途报错退出 | 看日志尾部的「############ 失败 ############」块：它按 `PHASE` 直接给出「生产有没有被改动 + 该怎么退」 |
| 服务停了、库已迁移 | `bash scripts/upgrade.sh --rollback latest --yes` |
| 只想把服务拉起来 | `systemctl start <服务名>`（脚本不会替你启动，除非再跑一次升级） |
| 回滚后版本对不上 | 日志会打 `恢复后迁移版本 V… ≠ 备份记录的升级前版本 V…`，人工确认后再决定 |
| 预演报「建临时库失败」 | 升级账号需要 `CREATEDB`；或用 root 跑（脚本会借 `postgres` 账号建库）。**不要**用 `--skip-rehearsal` 硬上 |
| `latest` 指向了 dry-run 目录 | 不会：dry-run 的备份落在 `dryrun-` 前缀目录，不登记回滚点 |
| 客户库已有未初始化的空库 | 本脚本直接拒绝并提示先跑 `scripts/setup_new_env.sh`（它才是建库入口） |

## 6. 验收证据（2026-11-10，145 独立环境实测）

测试环境：`/root/upgtest/repo`（独立 clone）+ 独立库 `cloudpivot_upgtest`（从 `cloudpivot_dev` dump 克隆，回退 V0368/V0369 模拟旧版本）+ 独立单元 `cloudpivot-upg.service`（8035）。

| 验收 | 做法 | 结果 |
| --- | --- | --- |
| ① 空库 → 建库 → 已是最新 | `setup_new_env.sh cloudpivot_upgfresh`（293 条迁移 / V0373）后跑 `upgrade.sh --db cloudpivot_upgfresh` | `✅ 已是最新`，退出 0 |
| ② 模拟旧版本 → 升级，数据不丢 | 库停 V0367，`upgrade.sh --yes` 升到 origin/main | `V0367(289) → V0371(293)`，4 条迁移；关键表行数 52/15/211/434 → 52/15/211/434 |
| ②' 增量升级 | 期间别的卡推了 V0372/V0373，再跑一次 | `V0371(293) → V0373(295)`，2 条迁移，自动完成 |
| ③ 故意失败的迁移 | 分支 `badmig` 加一条会撞唯一约束的迁移（复刻 V0359），`--dry-run` | ⑤ 报 `could not create unique index … Key (status, user_type)=(1, HUMAN) is duplicated`，退出 1；生产库表数/迁移数/行数**逐项不变**，服务仍 active，临时库已回收 |
| ④ 中途 kill -9 → 回滚 | 迁移完成后 `kill -9` 整个进程组（现场：服务停、库 V0373、二进制还是旧的、`PHASE=migrating`） | `--rollback latest` 恢复：库回 V0371(293)、关键表行数一致、旧二进制 md5 一致、代码切回旧提交、服务 active、登录 200 |
| ⑤ 日志内容 | 查 `/var/log/cloudpivot/upgrade-*.log` | 含「版本变化 V0367 → V0371」「应用迁移 4 条：…」「耗时 207s」「备份 /var/backups/cloudpivot/…」 |
| 附加：冒烟失败自动回滚 | `--smoke-pass` 传错口令 | ⑧ 报 `登录失败 HTTP 401` → 自动恢复库 + 换回旧二进制 + 切回旧代码，回滚后 health 200 |

## 7. 已知边界

- **不处理前端**：本脚本只管后端二进制与数据库；`frontend/dist` 的发布仍按 [deploy.sh](../scripts/deploy/README.md) 那套「typecheck → build → 双 rename → 比对入口 chunk」做（客户版通常随安装包整体替换，见交付物说明）。
- **库内 `add_user_token_security` / `add_password_reset_flag`**：这两条迁移在库里已记账、仓库里已无对应文件（历史遗留，引擎会忽略）。脚本会告警但不致命；要彻底消除需补一条 `baseline` 记录或说明文档，属于单独的技术债。
- **无 PITR**：回滚只能回到「升级前那一刻的 dump」，升级后到回滚之间的写入会丢（`--rollback` 会先打一份安全备份，但那是回滚后的状态，不是升级后的写入）。
- 同时有多人在同一台机器上跑升级/部署时，`systemctl stop/start` 会互相打架，动手前确认服务没被别人占着。
