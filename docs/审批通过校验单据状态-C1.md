# C1 · 审批通过时校验目标单据状态（修「任务已取消但审批通过」的孤儿）

卡面：`t_1e174431`，前缀 `fix(flow): C1 审批通过校验单据状态`。

## 1. 问题（实测形态）

```
TSK-202610-000813
  20:00:26  任务状态      → CANCELLED
  20:09:06  审批实例状态  → APPROVED
```

审批结论（APPROVED）与单据状态（CANCELLED）并存。事故的**直接危害**不是「任务被改回
DONE」（`task::state::callback_transition` 早就只开 `REVIEW → DONE|DOING`，CANCELLED
推不动），而是**过程完全静默**：

- `flow::task_bridge::settle` 在任务侧不满足条件时只 `tracing::debug!` 一句就 `return Ok(None)`；
- `erp::purchase_bridge` / `erp::stockin_bridge` / `erp::payable_bridge` / 调拨回调同样形态
  （`if row.status != STATUS_XXX { debug; return }`）；
- 结果：运维在**日志里查不到、审批时间线上看不到**「这条结论为什么没落到单据上」，
  只能人肉对两条时间线。P11 修的是反方向（任务取消 → 撤审批），这个方向一直没修。

## 2. 修法（三层，一层入口）

新增 `backend/src/business/flow/settle_guard.rs`：所有审批回调在**写目标状态之前**统一过一道
前置校验。

| 单据当前状态 | 判定 | 动作 |
|---|---|---|
| 仍在「等这个审批」的状态 + `当前 → 目标` 是状态机里的边 | `Apply` | 调用方照常落目标状态 |
| 已经是目标状态 | `AlreadySettled` | `debug` 后静默跳过（重复回调/重放幂等，**不留痕**，否则重放会刷满假告警） |
| 其它（已取消 / 已作废 / 被别的路径推走 / 边被配置禁用） | `Moved` | **不落目标状态** + `WARN` 全字段日志 + 审批实例留痕 |

三条红线（卡面）：

1. **不改审批实例状态**：GUE 走完就是 `APPROVED`，这一层只决定「还要不要落到单据上」；
2. **判定问状态机，不写 if-else**：
   - 任务 → `task::state::callback_transition`（`FlowCallback` 分支，`TRANSITIONS` 一行没动）；
   - 业务单据 → `shared::state_machine::effective_edges`（`BASE_EDGES ∩ biz_flow_state_edge` 配置，
     读配置失败自动退化到 BASE_EDGES）；注册表里**没登记**的历史边（例：调拨单驳回
     `PENDING → DRAFT` 走的是 `transfer_write::settle_approval` 的裸 SQL）只记 `debug` 放行，
     拦住它等于打断生产上可用的回退路径（补登记属于另一张卡：登记后「人工把 PENDING 改成
     DRAFT」也会合法）；
3. **留痕失败不许影响审批结论**：写痕迹失败只补一条 `warn`。

### 留痕落在哪

`biz_flow_task` 一条 `SKIPPED` 行（`is_auto=true`、`assignee=发起人`、`assignee_source=INITIATOR`、
`comment` = 「审批结论未落单据（目标已不可改，跳过落状态）：系统留痕 · <单据> <单号> 当前状态 X，
审批结论要落的 Y（等审批状态应为 Z）；审批单 <实例号> 已按结论结束，单据状态保持不变；
原因：…；时间 …」）。

- 与「自审 SKIP / 内控排除」同一套留痕口径（`assignee.rs` / `internal_control.rs`），
  审批详情的**时间线**（`flow::model::timeline`）直接可见，不占待办槽位
  （`uk_biz_flow_task_pending` 只约束 `PENDING`）；
- **同一实例只留一条**：`flow::model::has_skip_trace`（`SKIPPED + is_auto + comment LIKE 前缀`），
  重复回调不刷屏；
- 挂点取实例最新的节点行（`flow::model::last_node_anchor`）：`biz_flow_task.instance_node_id`
  是 NOT NULL + 外键，不能凭空造挂点；实例一条节点行都没有（历史/异常）时只记 `WARN`，放弃留痕。

### WARN 日志字段

`context=flow.settle_guard`，含 `instance_id / instance_no / instance_status / biz_type / entity /
biz_no / current / awaiting / target / reason / at`，一句话：
「审批结论未落单据：目标单据当前状态已不可改，跳过落状态（审批单本身已按结论结束）」。

## 3. 接入清单（7 处，一张不落）

`solve_target 不是唯一入口`：全后端「审批完成 → 改单据状态」共 7 处回调，全部接入同一道校验。

| # | 回调 | 单据 | 等审批状态 | 目标状态 |
|---|---|---|---|---|
| 1 | `flow::task_bridge::on_instance_settled` → `settle` | `biz_task` | `REVIEW` | `DONE` / `DOING` |
| 2 | `flow::task_bridge::on_transfer_settled` | `biz_stock_transfer` | `PENDING` | `APPROVED` / `DRAFT` |
| 3 | `erp::purchase_bridge::on_po_settled` | `biz_purchase_order` | `SUBMITTED` | `APPROVED` / `DRAFT` |
| 4 | `erp::stockin_bridge::on_cancel_settled` | `biz_stock_in` | `PENDING_CANCEL` | `CANCELLED` / `POSTED` |
| 5 | `erp::stockin_bridge::on_post_settled` | `biz_stock_in` | `PENDING_POST` | `POSTED` / `DRAFT` |
| 6 | `erp::payable_bridge::on_cancel_settled` | `biz_payable` | `PENDING_CANCEL` | `CANCELLED` / `OPEN` |
| 7 | `erp::payable_bridge::on_payment_settled` | `biz_payable_payment` | —（**已有等价闸**） | `PAID` / `CANCELLED` |

第 7 处没有接 `settle_guard`：它已经实现了同一语义（`payable_payment::settle_approved_payment`
返回 `SettledOutcome::{Cancelled, Rejected}` → 拒绝执行 + 强制通知发起人），
再套一层只会变成两份判定。**凭证红冲**（`erp::voucher_bridge`）同理不接：凭证没有状态流转
（`VOUCHER_EDGES` 为空），「红冲审批中」用 `biz_voucher.pending_reverse_instance_id` 表达，
回调按**实例 id 指针**判定（`Some(other)` 时已经 `WARN` + 跳过），不存在「已作废单据被激活」的形态。

### 真机 e2e 复现的事故形态

`scripts/verify/c1_settle_guard_e2e.py`（隔离实例 18098 / 库 `cloudpivot_c1e`）：

1. 建任务 → `DOING` → `REVIEW`（真实发起 `TASK_ACCEPT` 审批，实例 PENDING + 待办 PENDING）；
2. **改库把任务置 `CANCELLED`**（模拟 P11 没把审批撤掉的孤儿 = 事故现场，实例仍 PENDING）；
3. 走真实接口 `POST /api/business/flow/task/{id}/approve` 审批通过；
4. 断言：实例 `APPROVED`、任务**仍 `CANCELLED`**、进度未被改写（30 不变）、
   实例上一条 `SKIPPED/is_auto` 留痕、服务日志一条 `WARN`（含实例号/任务号/两个状态/时间）。

## 5. 与卡面的两点偏差（如实记录）

1. **卡面写「任务 DOING + 审批 APPROVED → 正常变 DONE（不误伤）」**：本仓的真实口径不是这样。
   `task::state::callback_transition`（D3b）**只开 `REVIEW → DONE|DOING`**，放开 `from`
   就等于让一条审批通过把任意任务跳级推到 `DONE`（D3 门闸白设）。系统里也不存在
   「`DOING` 的任务挂着 `TASK_ACCEPT` 审批」的合法路径：提交验收一定是 `DOING → REVIEW`
   同事务发起审批。所以「不误伤」按真实正常路径验证：`REVIEW + APPROVED → DONE`（进度 100）；
   `DOING + APPROVED` 按「跳级」处理 → 不落状态 + 留痕（单测
   `doing_task_is_not_pushed_to_done_by_approval` 钉住）。
2. **不变量条数**：卡面写 32/32，`scripts/verify/erp_invariants.py` 已扩到 **36 条**（A–H 八组），
   本次实测 36/36、BLOCKER 0 / WARN 0。

## 6. 已知边界

- 留痕挂在**审批实例**上（`biz_flow_task` 的 `SKIPPED` 行），不进 `biz_status_log`：
  后者是「单据状态变更日志」，而本次动作的语义恰恰是**没有变更**。
- 实例没有任何节点行（历史脏数据）时留痕写不出来，只有 WARN 日志（`last_node_anchor` 返回 None）。
- `settle_guard` 只负责「判定 + 日志 + 留痕」，**不重试、不补偿**：单据停在原状态下一次
  由各模块自己的 reconcile 兜扫（`stockin_bridge::reconcile_orphan_cancels` 等）负责。
