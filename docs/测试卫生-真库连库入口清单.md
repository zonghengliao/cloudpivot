## 1. 判定框架（为什么这处能复用、那处必须独占）

「`try_db().is_some()` 就复用」这件事**本身并不邪恶**——`set_db()` 是进程级 `OnceLock`
（`backend/vendor/nik-web/src/resources.rs`），一个测试进程只能装一个全局连接，
**大多数模块本来就该共用同一个测试库**（夜间全量回归 1771 条就是这么跑绿的）。
真正决定「能不能复用」的是三条判据：

| 判据 | 问什么 | 命中后果 |
|---|---|---|
| **A. 库身份断言** | 这组用例是否断言「我连的是哪个库」？（`url.contains("p0fix")`、`current_database()`、库内特定种子行的存在） | 命中 ⇒ **必须独占**：复用等于让这条断言不执行 |
| **B. 清理范围** | 清场是按**本模块前缀**（`p3a_*` / `p0fix_*` / `td_*`），还是**全表 / 整期**（`period LIKE '2033-%'`）？ | 只有 B 命中 ⇒ 复用仍可以，但「同库并发/串跑」需互斥（**数据隔离**问题） |
| **C. 跨口径数据** | 这组用例是否造**别人会按全库口径断言**的数据（`PUBLISHED` 流程定义、`PENDING` 审批实例）？ | 只有 C 命中 ⇒ 同上，属数据隔离问题 |

> 判据 A 是**连接身份**问题（本卡修的），判据 B/C 是**数据隔离**问题（上游卡 `t_e2a368f0` 用「模块 × 进程 × 库」解决）。
> 两者别混：改 `ensure_db` 修不了数据残留，分库跑法也修不了「静默连错库」。

| 分组的实测依据 | 结论 |
|---|---|
| `internal_control`：A+B+C 全中（库名硬断言 / 造 `PUBLISHED` 定义 + `PENDING` 实例 / 会污染 `dc01`、`zz_teardown` 的全库口径断言） | **必须独占进程** |
| 其余 42 处：A 不中（0 处），B/C 部分中 | **可复用（须同库）**；B/C 命中的几处已在表里单独标注 |

## 3. 「可复用（须同库）」到底是什么意思

写的是 `return true`，读起来是「库已经好了，用吧」，实际做的是「**假设**库已经是我要的那一个」。
这个假设在以下两种情况下会破：

1. 同进程里 `ERP_DB_URL` 与 `TASK_DB_URL` / `SYS_DB_URL` 指向**不同**的库 —— 先到的赢，后者静默跑在前面那个库上。
   当前跑法脚本（`scripts/verify/run_lib_tests_by_module.sh`）三者的库名始终一致，所以**没有暴露**；
   但没有任何代码阻止这么配。
2. 有人把 `P0FIX_DB_URL` 与其它变量混配（本卡的坑）。

所以「可复用」的准确说法是：**复用是安全的，前提是复用的连接真的指向本次要的那个库**。
这一条前提**目前没有任何地方校验**——这就是 42 处共有的残余风险（严重度低于 `internal_control`：它们没有断言会被跳过，
只在「配错了库」时把用例跑在不该跑的库上）。

## 4. 统一建议（给后续卡）

### 4.1 形态

新增一个测试专用入口（`#[cfg(test)]`，不动业务代码）：

```rust
/// 真库测试的统一连库入口。
/// - 未设置 `env_key` 指向的环境变量 → 打印 SKIP，返回 None（与现在一致，CI 无库仍然全绿）；
/// - 全局 db() 已存在 → `SELECT current_database()` 与 url 里的库名比对：
///   一致则复用；不一致则 **panic 并指路**（别静默跑在别人的库上）；
/// - 不存在 → 连接 + `set_db`。
pub(crate) async fn ensure_test_db(env_key: &str) -> Option<bool>;
```

判据 A 命中的模块（目前只有 `internal_control`）可以额外传一个「库名必须满足」的断言闭包。

### 4.2 迁移顺序（风险从低到高）

| 顺序 | 对象 | 理由 |
|---|---|---|
| 1 | 新增入口 + 单测（不迁移任何调用点） | 纯增量，零风险 |
| 2 | `internal_control::db_tests` 改为调用新入口（删掉本卡内联的 `db_name_of` / `current_db_name`） | 已有本卡的前后对比日志当回归基线 |
| 3 | 22 处**纯前缀清理**模块（`attachment` / `erp::batch` / `erp::voucher*` / `task::task_model_*` 等） | 机械替换，判据 B/C 都只有「低」 |
| 4 | 4 处 **B/C 命中**模块（`purchase_handler` 全库口径 / `period`、`period_test_support` 整期清场 / `stockin_handler_tests_fixtures` a4 共享夹具） | 替换前先跑一次 `MODULES='erp' RUNS=2` 留基线 |
| 5 | `system/tests_support.rs::db_url()` | 它是辅助函数不是 `ensure_db`，需要连带改造 system 段用例的 `Option` 处理 |

### 4.3 不建议做的事

- **不要**把 42 处的 `try_db().is_some()` 全改成 `panic`（不复用）：那会让「同库跑全量」直接不可用，
  而全量同库跑是**允许**的（只是要分模块分进程跑不同的库）。
- **不要**用「环境变量字符串相等」判断同库：同一台机的 `localhost` 与 `127.0.0.1`、
  带不带 `?sslmode=` 都会让字符串不等；`SELECT current_database()` 才是唯一可靠口径。
