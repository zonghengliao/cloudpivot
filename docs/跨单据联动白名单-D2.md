## 0. 一句话

把「单据状态变了以后还要做哪些事」从代码搬到配置里，但**只允许配置白名单动作**：
用户能配「在 `TASK/DOING` 之后发一条通知」，配不了「执行这段 SQL」——
后者在 **数据库 CHECK、写入校验、运行时校验** 三层都被拦住，而且**引擎里根本没有执行语句的代码路径**。

## 2. 表 `biz_flow_linkage_rule`（V0205）

```sql
CREATE TABLE biz_flow_linkage_rule (
  id uuid PK, name varchar(128) NOT NULL,
  trigger_entity varchar(32) NOT NULL,   -- STOCK_IN / TASK / …
  trigger_status varchar(32) NOT NULL,   -- POSTED / DOING / …
  action_code varchar(64) NOT NULL,      -- 白名单动作码
  action_params jsonb NOT NULL DEFAULT '{}',
  enabled boolean NOT NULL DEFAULT true,
  seq integer NOT NULL DEFAULT 0,
  created_at / updated_at / create_by / update_by / deleted_at,
  CONSTRAINT ck_flow_linkage_action_code CHECK (action_code IN (11 个码)),
  CONSTRAINT ck_flow_linkage_no_sql_key CHECK (NOT (action_params ?| ARRAY['sql','statement','query',…])),
  CONSTRAINT ck_flow_linkage_params_object CHECK (jsonb_typeof(action_params) = 'object'),
  CONSTRAINT uk_flow_linkage_rule UNIQUE (trigger_entity, trigger_status, action_code)
);
```

设计取舍（与卡面的差异，逐条说明）：

1. **迁移号 V0202 → V0205**：卡面要求「先复核号段」，实测 V0202–V0204 都已被占用。
2. **唯一键按卡面** `(trigger_entity, trigger_status, action_code)`：同一触发点同一动作只许一行
   （两行 = 「参数取哪份」不可判的双真相）。副作用：同一触发点的多条规则**必然是不同动作**，
   这点写进了 `engine_runs_in_seq_order` 的注释（`seq` 排序用的是「不同动作」的组合）。
3. **额外的 `ck_flow_linkage_no_sql_key` / `ck_flow_linkage_params_object`**：卡面只要求
   `action_code` 的 CHECK；但「禁配 SQL」是这张卡的核心禁令，只靠应用层拦不住
   `psql` 直接写库的人，所以在数据库层也钉了一道（实测见 §3.1）。
4. **不种任何数据**：空表 = 引擎读到 0 条规则 = 现有业务行为逐字不变。

| 场景 | 行为 | 单测 |
|---|---|---|

## 5. 执行引擎与事务边界（卡面点名要写清）

### 5.1 事务边界表（唯一权威）

| 栏位 | 谁执行 | 在事务里？ | 失败怎么办 |
|---|---|---|---|
| `InTx` + `Critical`（写库存 / 凭证 / 累计量 / 改状态） | `engine::run(&tx, ctx)`，用**调用方**的事务器 | **是**（引擎不新开事务） | `run` 返回 `Err` → 调用方 `tx.rollback()`，整笔状态变更一起回滚 |
| `InTx` + `NonCritical` | 同上 | 是 | 记 `Failed`，流程继续 |
| `AfterCommit`（发通知 / 建任务） | `engine::run_deferred(ctx, rules)`，**提交之后** | **否**（各自事务） | 记 `Failed`，永不回滚业务 |

**为什么 `InTx` 不在引擎里再包一层事务**：调用方（如 `stockin_handler::post_in_tx`）已经在事务里，
PG 没有嵌套事务；套 `SAVEPOINT` 只能局部回滚，会把「关键动作失败 → 整笔回滚」偷偷降级成
「只有这一段回滚」——正是卡面三令五申不要的。

调用范式：

```rust
let run = linkage::engine::run(&tx, &ctx).await?;   // 关键动作；失败即 Err
tx.commit().await?;
let _ = linkage::engine::run_deferred(&ctx, run.deferred).await;  // 通知这类
```

### 5.2 执行流程

```
① rules_for(entity, status)      # fail-safe：读失败 → 空 + 节流 WARN（SAVEPOINT 保护事务）
② 按 (seq, id) 升序
③ 逐条：动作码在白名单？→ 已接管？→ 参数复校 → 按 Phase 分栏
④ 每条结果进 RuleRun（Success / Skipped / Failed）+ 结构化日志
   字段：trigger_entity / trigger_status / doc_id / doc_no / rule_id / action_code / seq / outcome / reason
⑤ Critical 失败 → Err（整笔回滚）；NonCritical 失败 → 记日志继续
```

日志级别：成功 `INFO`，跳过与失败 `ERROR`（卡面「运行阶段 → 打 ERROR 日志 + 跳过」）。

### 5.3 对应单测

| 卡面要求的用例 | 单测 |
|---|---|
| 配置非法 action_code → 400 | `upsert_rejects_unknown_action_code` |
| 配置非法 action_params 键 → 400 | `upsert_rejects_params_with_sql_key`（含「SQL 键」与数据库 CHECK 双证） |
| 运行时 target 不存在 → ERROR + 跳过 | `engine_skips_missing_target` |
| 关键动作失败 → 回滚 | `engine_critical_failure_rolls_back`（两条规则，第一条成功也被回滚） |
| 非关键动作失败 → 流程继续 | `status_notice_bad_params_fall_back_to_legacy` + `engine_runs_in_seq_order`（前一条被跳过不挡后一条） |
| seq 顺序执行 | `engine_runs_in_seq_order` |
| enabled=false 不执行 | `engine_skips_disabled_rules` |
| 同一 trigger 多条规则按 seq 跑 | `engine_runs_in_seq_order` |

## 6. 第 2 步：SEND_NOTICE 接管任务状态通知

### 6.1 为什么挑这个点

任务状态变更通知是**既有逻辑**（`task/handler.rs::notify_status_change`，修正 8 的分级表）：
副作用、非财务、失败不影响账务，正好符合卡面「挑最简单的联动」。
接管方式不是「再写一份通知逻辑」，而是：

1. 把 `dispatch_task_notice` 拆成 `task_notice_draft`（只组装）+ `send_task_notice_draft`（只投递）——
   **文案/收件人/链接仍然只有一处计算**；
2. 组装好的草稿交给 `linkage::engine::status_notice`：
   - 没有 `SEND_NOTICE` 规则 → `Legacy`，原样照旧发（**行为逐字不变**）；
   - `mode = SHADOW`（默认）→ 逐字段对比 + 打日志（`matched` / `diffs`），仍由旧逻辑发；
   - `mode = TAKEOVER` → 引擎发，旧逻辑**不发**（否则用户会收到两条一样的）；
   - 任何校验不过 → 退回旧逻辑（**通知漏发是事故，配置写错不能让它变成事故**）。

### 6.2 真机证据（`docs/evidence/20261103-d2/03-e2e.txt`，PASS=28 FAIL=0）

## 7. 现状盘点：哪些实现了、哪些是占位、第 3 步怎么接

### 7.1 已实现（2 个）

- **`SEND_NOTICE`**（第 2 步）：`actions::send_notice` → `notice::dispatch`；
  参数支持 `mode` / `title` / `content` / `force` / `recipient` 覆盖，
  不写任何覆盖键时逐字沿用触发点文案（单测 `shape_notice_defaults_are_identical` 钉死）。
- **`UPDATE_RECEIVED_QTY`**（关键动作样本）：`actions::update_received_qty` 直接调
  `stockin_purchase::add_received_qty`（`post_in_tx` ⑤ 用的同一个函数）。
  **没有接进任何生产路径**——它存在的意义是让「关键动作失败 → 整笔回滚」这条语义
  有活的可测样本（否则只能拿占位动作假装回滚，那是假绿）。

### 7.2 占位（9 个）

`WRITE_INVENTORY` / `WRITE_INVENTORY_TXN` / `UPDATE_COST` / `GENERATE_VOUCHER` /
`REVERSE_VOUCHER` / `UPDATE_DOC_STATUS` / `UPDATE_PAYABLE_BALANCE` / `CREATE_TASK` / `LOCK_DOCUMENT`。

占位动作的三重保护：
1. 配置写入直接 `400`（「尚未接管」）；
2. 万一绕过 API 写进库，运行时打 ERROR + 跳过，**一行数据都不写**（单测 `engine_skips_placeholder_action`）；
3. `spec.reuse` 写清第 3 步要复用的既有函数 —— 防止后来者顺手重写一套算法（双真相）。

**为什么本卡不接管财务动作**：卡面明令（「不在本卡接管 GENERATE_VOUCHER / WRITE_INVENTORY 等财务动作」）。
这不是偷懒：`post_in_tx` 是一个 ①–⑦ 步的单一事务（锁单头 → CAS 改状态 → 成本账/库位账/流水 →
序列号 → 采购已收 → 采购单状态 → 凭证 + 应付），把它拆成「配置驱动的原子动作」需要先决定
「谁是数量的唯一写入者」「序列号与账的先后」「凭证与应付的引用顺序」这些口径，
一次做完风险不可控。第 3 步的正确顺序是**先抽公共函数、再逐个接管、每接一个并行对比一段**。

### 7.3 第 3 步怎么接（建议顺序）

1. **`GENERATE_VOUCHER`**（卡面点名的第 3 步）：把 `voucher::create_for_stock_in` 里的
   「取数 + 取号 + 借贷平衡校验」抽成 `create_by_template(ex, template_code, biz_ctx)`，
   配置侧只传 `template_code` + `biz_type`。验收判据：凭证有唯一编号，新旧两路各跑一遍对比。
2. 接着 `WRITE_INVENTORY` / `WRITE_INVENTORY_TXN` / `UPDATE_COST`：前提是先把
   `post_in_tx` ③/③b 抽成 3 个可独立调用的函数（当前它们已经是 `stockin_model` 的函数，
   只需去掉对「单头行结构体」的依赖）。
3. `UPDATE_DOC_STATUS`：需要一张「实体 → 合法边 + apply_status」的注册表（D1 的
   `state_machine::Entity` 已有边，`apply_status` 是各 model 的私有函数，要加一层 trait）。
4. `LOCK_DOCUMENT`：**先加列**（`biz_*` 表 `locked_at/locked_by/lock_reason`）+ 让 6 个 update
   入口统一过锁闸，再谈动作。
5. `CREATE_TASK`：`task::model::create_task` 吃 `&Transaction`（不是通用执行器），
   要么改签名（影响 3 个调用点），要么在 `AfterCommit` 里自己开一个短事务。

### 7.4 已知边界（本卡不做，如实记录）

- **没有 HTTP 配置入口**：配置读写走 `linkage::model::{upsert_rule, delete_rule, list_rules}`
  （超管 + 二次确认 + 留痕齐备），界面/接口留给后续的前端配置页卡（与 D1 边配置同款处理）。
  真机验收里配置是用 psql 直插的（`d2_linkage_e2e.py` 的 `upsert_rule`）。
- **执行日志是 tracing，不是落库表**：结构化字段可 grep（`linkage` + `rule_id` + `outcome`），
  但没有独立的执行流水表。要做「联动执行看板」需要再加一张
  `biz_flow_linkage_log`（另开卡，不在本卡范围）。
- **`trigger_status` 的合法值来自代码**：`model::known_statuses` 用状态机 `base_edges` 的
  from/to 全集（TASK 用 5 态、FLOW_INSTANCE 用 5 态）。新加状态要同步那里。
- **同一触发点同一动作只能一条规则**（唯一键决定），要「同动作跑两次」必须改 schema。

### 8.1 行为不变的证明方式

- **静态**：空表（迁移不种数据）+ 引擎「0 条规则 → `run` 返回空 → 调用方照旧」；
  `notify_status_change` 在没有规则时走的是**同一个** `send_task_notice_draft(draft)`
  （拆函数前后逐行相同，只有 `targets.clone()` 换成从 draft 里取）。
- **动态**：真机 B1（无规则，1 条通知）与 D1（接管，1 条通知）对比 —— 条数一致、
  标题/正文模板/`biz_type`/接收人数一致（D4–D7）。
- **降级**：规则表改名（模拟迁移未上）时 `engine_is_fail_safe_when_table_missing` 断言
  「读不到 → 空规则集 → 事务仍可写」，不会把业务写死（D1 的 SAVEPOINT 教训）。
