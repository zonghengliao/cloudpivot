## ⑤ 批量导入导出 3 页能不能授给业务角色（2026-11-05，已核实 · 暂不授）

**问题**：`t_db2506d2` / `t_34cee9ea` 之后，业务角色仍进不了 `/business/impexp/` 的 3 页
（导入向导 `business:impexp:import:upload`、导入任务 `business:impexp:import:list`、
导出任务 `business:impexp:export:list`）。当初排除的理由是"导出内容是否按数据范围过滤没核实"。

**核实结论（卡 `t_e464a285`，逐字证据在 `docs/evidence/20261105-impexp-scope/`）**：

1. **导出内容确实没有逐模块注入数据范围**：5 个导出定义里只有 `system.user` 覆写了带 scope 的入口
   （`masking/user_export.rs:154/173`），其余 4 个（字典项 / 入库单 / 应付单 / 凭证）落回默认实现，
   默认实现**把 principal 丢掉**（`definition.rs:893-906`、`910-923`），跑裸 SQL（`erp_doc.rs:466/481`）。
2. **更硬的一条：导出通道不认模块权限码**。`export_create` / `export_sync` 只校验
   `business:impexp:export:create`，`biz_type` 只查注册表存在性（`handler.rs:1093`、`def/list` 返回全部定义）。
   实测 `laoliu_test` 对凭证列表 **403**，但一旦有 `export:create`，导出 `erp.voucher` 会返回
   **21 张全公司凭证** —— 这是权限绕过，不只是数据范围问题。
3. **"补几行 scope 过滤"做不出来**：`biz_stock_in` / `biz_payable` / `biz_voucher` **没有 `dept_id`**
   （实测 `information_schema`，只有 `create_by`），强按 `create_by` 注入会退化成"仅本人"
   （`shared/scope.rs:459-470`）⇒ 列表 14 行 / 导出 5 行，口径分叉。

**数量化**（生产实测 + 隔离副本）：

| 实体 | 列表里 3 档账号能看到 | 授 `FULL` 后导出会返回 | 其中"非本人部门" |
|---|---|---|---|
| 收货入库单 `erp.stock_in` | 14 | 14 | 14（全部落在 `云枢总部`，TECH 子树 0 行） |
| 应付单 `erp.payable` | 12 | 12 | 12（HQ 11 + 归属人未落部门 1） |
| 凭证 `erp.voucher` | **403（无权看列表）** | **21** | 21（HQ 20 + 归属人未落部门 1） |

**所以**：3 页维持**不授**（`scripts/datafix/bizperm/plan.sql` 未改，生产授权一行未动，
`laoliu` / `laoliu_test` / `henry.liao` 四个导入导出接口仍 403）。

**顺带测清的一件事**：只授 `READ` 是安全的（隔离副本用仓库原文 `expand.sql` 展开实测：每个角色 7 个去重码，
`export:create` / `import:confirm` 均为 0）—— 但**没有业务价值**：导入向导会卡在"确认入库"、
导出任务页永远空。不建议用"授 READ"结案。

**如果老大要开，必须按顺序补三步**（详见决策文档 §6）：

| 步 | 做什么 | 不做的后果 |
|---|---|---|
| S1 | impexp 加 `biz_type → 模块权限码` 映射，`export_create` / `export_sync` / `batch_export` 统一校验 | 有 `export:create` 就能导自己连列表都无权看的实体（凭证就是实例） |
| S2 | 给 `biz_stock_in/payable/voucher` 补部门归属（加列+回填+巡检），**列表与导出同时**切到 `scope::paginate` / `count_scoped` | 只改一边 = 口径分叉；只改导出 = 外带 |
| S3 | 再考虑 `FULL` | S1+S2 未落地时，"能看能办"就等于"能外带" |

> 另：导入侧本来就没有范围校验（`ImportCtx` 里只有 `task_id/operator/mode`，`definition.rs:790-797`），
> 6 张主数据表也没有 `dept_id`（实测 0 列），写入是**全局 upsert**（`ON CONFLICT … DO UPDATE`）。
> 所以 `import:confirm` 本质是"能改全公司主数据"的授权，授权时必须对客讲清，别指望数据范围兜底。
