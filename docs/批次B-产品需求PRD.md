**先读第 0 章。** 第 0 章有 **31 条代码事实（F1–F31，全部带文件路径与行号）** 和 **13 条已定产品口径（D1–D13）**。批次 B 全是"横切面"能力——它不新建业务模块，而是给**所有业务表**加一层行过滤 + 列打码 + 角色约束。这类需求最容易死在"某个接口忘了加过滤"和"导出/详情绕过去了"。所以本文的写法是：**先把框架能做什么、不能做什么钉死在 F 表，再把"哪些地方必须堵"写成可勾选的清单**。

**三条一句话结论（先记住，细节后面展开）：**

1. **数据权限不是"列表筛选器"，而是"查询条件的强制前缀"**——列表、详情、导出、统计四条路径共用同一个 `ScopeFilter`，详情按 ID 越权一律 404（D4）。
2. **列级脱敏不是"前端打码"，而是"响应组装时就换了值"**——脱敏发生在 DTO 组装期，导出与打印拿到的是同一份被打过码的数据（D9/D10）。
3. **角色互斥不是"提示一下"，而是"拒绝写入"**——授予、改用户角色、改规则三个入口全部阻断，且改规则时先扫全量冲突（D12）。

## 0.5 十三个必须先定的产品口径（本文已定，开发照做）

| # | 问题 | 本文的定法 | 为什么这么定 |
|---|---|---|---|
| **D1** | 数据范围存在哪 | `sys_role` **新增 1 列** `data_scope VARCHAR(20) NOT NULL DEFAULT 'ALL'`（枚举 `ALL/DEPT/DEPT_AND_CHILD/SELF/CUSTOM`）+ **新建明细表** `sys_role_data_dept(role_id, dept_id)` | 范围类型是角色的 1:1 属性 → 放主表（角色列表直读，不用 JOIN）；自定义部门是 1:N → 明细表 + 唯一约束（照 `sys_role_menu` 硬删模式，F12）。**不存 JSON 数组**：部门被删/停用要能 JOIN 体检（D7） |
| **D2** | 新列的默认值给什么 | **默认 `ALL`（全部）**，并在角色列表对"仍为默认全部"的角色打 ⚠ 提示 + 提供"数据范围体检"清单 | 批次 A 已上生产。若默认给"仅本人/空集"，上线当天全公司业务停摆（**兼容性 > 理论安全**）。风险用"体检清单"消化，而不是用"默认收紧"制造事故。**替代方案见附录 B-B1** |
| **D3** | 数据范围在哪一层生效 | **服务层统一入口 `shared::data_scope`**，产出 `ScopeFilter`，由各业务查询**强制**拼接；**不允许**各 handler 自己写 `if dept ...`。同时定义"表接入契约"（附录 E.1）：任何纳入数据权限的表必须有 `dept_id`（或映射列）+ `created_by` 两列 | 三道防线必然被绕过（详情、导出、统计），只有"唯一入口 + 契约检查"能收敛。批次 B 先接入 3 张存量表（`sys_user`/`sys_file`/`sys_impexp_task`）+ 本批新表（附录 E.2） |
| **D4** | 详情按 ID 越权返回 403 还是 404 | **业务数据一律 404**（`10002 RESOURCE_NOT_FOUND`，文案「数据不存在或你没有访问权限」）；**仅"配置类"资源**（角色/菜单/部门/规则本身）越权返回 **403** | 业务数据返 403 = 告诉攻击者"这条 ID 存在，只是你看不到"，可用于**枚举探测**（如试探"有多少订单属于华东区"）。404 让"不存在"与"无权"不可区分。配置类是管理员界面，本就在菜单里可见，403 更有指示性 |
| **D5** | 多角色数据范围怎么叠加 | **取并集**。判定顺序：①任一角色为 `ALL` → 不限；②把每个角色翻译成条件片段，用 `OR` 连接：`DEPT`→`dept_id = 我的部门`；`DEPT_AND_CHILD`→`dept_id IN (子树)`；`SELF`→`created_by = 我`；`CUSTOM`→`dept_id IN (自定义集合)`；③最终形态 `(A OR B OR C)` | 并集是唯一符合直觉的语义（"我又管华东又管华南"）。若取交集，一个人多兼一个角色反而**看到的更少**——业务上不可解释，且会诱发"给全员挂个 ALL 角色"的绕道 |
| **D6** | 用户无部门 / 自定义部门为空 | ①**用户无部门**（F18 真实存在）：`DEPT`/`DEPT_AND_CHILD` 视为**空集**（看不到任何行），页面顶部提示「你尚未归属部门，数据范围为「本部门」，当前无可查看数据」；②**自定义部门为空**：**保存时直接报错拒绝**，不允许存出空集合配置 | ①空集是"安全优先"的选择：无部门往往是离职/未分配账号，宁可看不到也不能全看到。不便由"管理员体检清单"消化（B2 列为可拍板项：要不要降级为"仅本人"）。②空集合配置是"看起来配了、其实全看不见"的暗坑，必须挡在保存前 |
| **D7** | 部门树变更（停用/删除/搬迁）怎么处理 | ①**停用**（`status=0`）：仍算在范围内，但在配置页标灰「已停用」；②**删除**（软删）：递归查询自带 `deleted_at IS NULL`（F14）→ 自动出范围，配置页标红「已删除」并提供「一键清理失效引用」；③**搬迁**：用递归按 `parent_id` 现算（F16），不缓存、不用 `dept_path` 前缀 | 三种变更里，只有"搬迁"会造成**静默数据错误**（用 `dept_path` 匹配会漏），所以必须写死"用递归、禁用前缀匹配"这条硬约束 |
| **D8** | 谁能看明文（脱敏豁免） | 判定顺序（命中即停）：①该表该字段**没有命中任何启用规则** → 不脱敏；②命中规则且**用户在规则适用角色内** → 脱敏；③**`SUPER_ADMIN`** 或持有 **`system:field-mask:view-plain`** → 明文（`SUPER_ADMIN` 豁免可用参数 `mask.super_admin_exempt` 关闭，默认开）；④**值长度不足**（如 5 位"手机号"）也**必须打码**（补 F21 的短值漏洞：不足时输出 `***`） | ②"适用角色"是业务语义（"客服被脱敏、财务不脱敏"直接配）；③两个通道：超管用于救火排障、独立权限码用于给财务/审计等**长期需要明文**的岗位——避免把这些人统统塞进超管。④短值原样返回是**现成的泄露点**，必须在规则层堵掉 |
| **D9** | 脱敏在哪一层落地 | **在响应 DTO 组装期显式调用** `shared::field_mask::apply()`（拿到当前用户 + 表名 + 行数据 → 就地改值），**不用全局中间件**（F24 已证不可行）。配套两道保险：①**代码评审清单**（附录 E.3，新增"含敏感列的查询必须显式调 apply"）；②P1 上"**漏脱敏哨兵**"——debug/预发环境在响应中扫描"声明为敏感但值为原文"的字段并打 ERROR 日志 | 在中间件统一洗会①不懂表与角色、②波及导入校验/审计等非展示响应、③把"哪些字段敏感"变成全局硬编码（与"由管理员配规则"直接冲突）。组装期是唯一既"有上下文"又"可配置"的位置 |
| **D10** | 导出 / 打印怎么保证不绕过 | ①**导出**走同一判定（同一份脱敏后的行数据落文件），**不存在"导出专用明文路径"**；②**明文导出**须**同时**持有 `system:field-mask:view-plain` **和**批次 A 的 `business:impexp:export:sensitive`（双闸门），且每次写审计「含明文敏感字段」+ 字段清单 + 行数；③**打印**：P0 依赖"页面已是脱敏值 + 浏览器打印"（F30 无打印基础设施），P1 再做打印模板 | 只留一个闸门时，总有一个岗位会拿到不该拿的明文。双闸门语义不同：`export:sensitive` 答"你能不能导敏感数据"，`view-plain` 答"你能不能看原文"——两个都该有才算完整授权。导出**绝不**另开明文接口，否则脱敏就成了"只挡前端" |
| **D11** | 互斥规则怎么存 | 新建 `sys_role_mutex`：`role_a_id / role_b_id / reason / status`，**无向**（存前规范化 `role_a_id < role_b_id`），`UNIQUE(role_a_id, role_b_id)` + `CHECK (role_a_id < role_b_id)` + `CHECK (role_a_id <> role_b_id)` | 无向两两规则可表达任意"互斥组"（三互相斥 = 3 条规则），P0 不必做"互斥组"实体。`a<b` 规范化让"重复添加反向规则"天然被唯一索引挡住 |
| **D12** | 改互斥规则时已有用户同时持有怎么办 | **阻断保存**（不提供"强制保存"），返回冲突清单：前 20 条（用户名/姓名/部门/角色）+ 命中总数 + 「导出调整清单」，并给「先去调整这些用户的角色」入口。**迁移期不带任何互斥规则**（只建表），存量若存在违规组合**不阻止上线**——由合规在页面上配置规则时被这个阻断自然接管 | 静默产生违规（"先存后告警"）在合规场景等于没做：违规记录一旦落库，事后追责时"系统允许过"就是抗辩理由。阻断 + 给清单 + 给导出，是唯一让合规敢用的形态。而**上线时**强制清理存量违规，会卡住发布（且没人能自动决定"该撤谁的哪个角色"）——所以迁移不建规则，把决定权留给合规 |
| **D13** | 互斥里的"持有"怎么算 | 只算**生效角色**：`sys_role.status=1` **且** `(ur.expire_time IS NULL OR ur.expire_time > now())`（口径同 F5/F6）。停用角色、过期授权**不算持有**，但**会在用户详情的角色标签上标「已停用/已过期」**，且互斥校验的提示语里注明这一口径 | 若把过期授权也算持有，用户会收到"你和某人互斥"的假告警，且**无法自救**（授权记录还在，只能让管理员删）。口径与权限判定一致，才不会出现"报了冲突但两角色都不生效"的怪事 |

# 第 1 章 角色与场景

## 1.1 角色总览

批次 B 有四类直接角色 + 一类间接受影响者。**注意：这四类不是"四个新账号"，而是四类"岗位诉求"**——同一家公司里往往是一个人兼着"系统管理员"和"数据管理员"。

| 角色 | 谁在干 | 核心诉求 | 主要用到的能力 | 使用频率 |
|---|---|---|---|---|
| **系统管理员** | IT 主管 / 平台运维 | 给不同角色配**不同的数据范围**，一次配好长期有效 | 数据权限（角色编辑页） | 上线首次集中配置，之后每月几次 |
| **数据管理员** | 业务系统负责人 / 数据治理岗 | 配**字段脱敏规则**：谁能看全、谁只能看打码 | 字段脱敏规则 + 预览 | 每有新表接入时配一次 |
| **合规 / 风控** | 内审、财务内控、合规岗 | 配**角色互斥（SoD）**：不相容职务不能由同一人兼任 | 角色互斥规则 + 冲突清单 | 季度审计前集中复核 |
| **普通用户** | 销售员、客服、财务专员 | **无感知**：只能看到该看的行、敏感字段自动打码 | 无需任何操作 | 每天 |
| （间接）开发/测试 | 开发团队 | 新表接入时按契约接入，不重复造轮子 | 表接入契约（附录 E.1） | 每个批次 |

**一句关键定位**：批次 B **不产生新的业务页面**，它只做三件事——给"已经存在的角色"加一个**数据范围属性**、给"已经存在的字段"加一层**打码规则**、给"已经存在的角色组合"加一条**禁止共存规则**。所以本批的验收重点不是"新页面好不好看"，而是**存量页面有没有被堵住**。

## 1.2 八个数字化故事（全部带数字，含一个反场景）

### 故事 1（系统管理员 · 销售总监看全公司订单）

老周是云枢的系统管理员。销售中心下设 4 个大区、17 个城市办事处，共 63 个销售账号。**销售总监**这个角色要能看全公司订单，他打开「系统管理 → 角色管理 → 销售总监 → 编辑 → 数据权限」，选「全部」，保存。**从这一刻起，持有「销售总监」的 2 个账号看到的就是全量数据，不需要逐个改账号。**

老周不知道的是：**他没在这一步做任何"给权限"的动作**——因为"能看到订单"这件事在批次 A 之前就由菜单权限决定了。**数据权限只回答"能看到哪些行的"，不回答"能不能进这个页面"**。这个分工必须写在角色编辑页的说明里（8.2.4），否则管理员会以为"配了数据范围就等于授权了"。

### 故事 2（系统管理员 · 区域经理只看本区域）

**华东大区经理**老李，部门是「销售中心 / 华东大区」，下面挂 5 个城市办事处（杭州、南京、苏州、上海、宁波）。老周给他配「本部门及以下」，保存。

老李登录，订单列表显示 **1,842 条**（华东大区 + 5 个办事处汇总）。而在他配置之前，这个数字是 **9,317 条**（全公司）。**配错一个下拉，数字差 5 倍**——所以第 9 章要求验收必须记录"配置前后条数"，不接受"看起来对了"。

老李试着把浏览器地址栏里的订单 ID 改成华南的一张单子（`/erp/order/detail/8f3a...`）——**页面返回 404「数据不存在或你没有访问权限」**（D4）。他不会知道那张单子到底存不存在。

### 故事 3（数据管理员 · 客服看手机号打码）

小赵是数据管理员。客户中心新上线了「客户档案」，里面有客户手机号。他打开「系统管理 → 字段脱敏」，新建一条规则：表 `crm_customer`、字段 `mobile`、类型「手机号」、适用角色「客服专员」、启用。

**客服小陈**刷新客户列表：手机号显示 `138****5678`。**同一个列表，财务专员小刘**（不在"客服专员"范围内，且持有 `system:field-mask:view-plain`）看到的是 `13812345678`。

小陈还发现：**他点"详情"、点"打印"、导出的 Excel，全都是 `138****5678`**。他没有"绕过按钮"可点——因为脱敏发生在服务端组装响应的时候（D9），前端拿到手的就已经是打了码的字符串。

### 故事 4（数据管理员 · 导出 Excel 也是脱敏的，明文要双闸门）

销售运营小周要把 3,000 条客户联系方式导给领导。她点了「导出 Excel」，系统弹提示：「本次导出包含 2 个敏感字段（手机号、邮箱），已按脱敏规则输出」。文件里是 `138

****5678` / `z***@mail.com`。

她要明文，去找财务小刘。小刘**同时持有** `system:field-mask:view-plain` 和 `business:impexp:export:sensitive`（批次 A 定义的导出总闸），他导出的就是明文——**同时审计日志里落一条**：「小刘 于 14:32:07 导出客户档案（含明文敏感字段：手机号、邮箱，3,000 行）」。

**只有其中一个权限码的人导不出明文**：只持 `view-plain` 的人导出仍是脱敏（"你能看，不代表你能批量带走"）；只持 `export:sensitive` 的人导出也是脱敏（"你能导敏感数据，但看不到原文"）。这个**双闸门**是 D10 的核心。

### 故事 5（合规 · 采购员与付款审批不能是同一人）

内审老陈要落一条 SoD 规则：**「采购员」与「付款审批」不能由同一人同时持有**（自己采购、自己审批付款 = 经典舞弊路径）。他打开「系统管理 → 角色互斥」，新增规则：角色 A「采购员」↔ 角色 B「付款审批」，说明「内控要求：采购与付款审批职责分离（COSO 职责分离原则）」，启用。

保存时系统做了两件事：①检查规则本身合法（不是自己跟自己、不重复）；②**全量扫描现有用户**——发现 **0 个**违规组合，通过。**如果发现有 3 个违规用户，保存会被拒绝**，并弹出清单让他先处理（故事 6）。

### 故事 6（合规 · 改规则撞上 3 个存量用户）

三个月后老陈想再加一条：「仓库管理员」↔「应付会计」。保存时被拦下来：

> **「保存失败：新规则「仓库管理员」↔「应付会计」与 3 位用户的现有角色冲突，请先调整这些用户的角色后再启用。」**

弹窗下方列出 3 行：`zhangwei / 张伟 / 仓储部 / 仓库管理员、应付会计`、…，还有「导出调整清单（CSV）」按钮。老陈把清单发给 HR，HR 撤掉 1 人的「应付会计」，另外 2 人本来就是**同一人跨岗**（历史遗留），调整为只留一个。

**老陈没有"强制保存"按钮可点**——这是故意的（D12）：如果允许先存后告警，那么违规记录一旦落库，"系统允许过"就成了事后追责时的抗辩理由，合规规则等于没做。

### 故事 7（普通用户 · 销售员只看到自己的 37 条）

小王是杭州办事处的销售员，角色「销售员」，数据范围「仅本人」。他打开订单列表：**37 条**，全是他自己录的。他不觉得有什么特别——**列表上没有"你被限制了"的横幅**（这是设计：普通用户应当无感知，8.4.5 有反向论证）。只有当他的数据为空时，才在列表中间显示「当前没有符合条件的数据」。

### 故事 8（普通用户 · 无部门账号的空列表）

小郑是刚入职的实习生，账号建好了但**还没分配部门**（`sys_user.dept_id` 为空，F18 是真实存在的状态）。他的角色是「销售员」，数据范围「仅本人」——所以能看到自己录的 2 条。**但**如果他所在的角色被配成「本部门」，他会看到**空列表 + 顶部一行浅色提示**：

> 「你尚未归属部门，当前数据范围为「本部门」，暂时没有可查看的数据。请联系管理员分配部门。」

这个提示只对**因数据范围为部门类而查不到数据**的用户显示（且每会话只弹一次），不会打扰其他人。

### 反场景（明确不做什么，防止后面扯皮）

| 反场景 | 为什么不做 |
|---|---|
| ❌ 数据权限**不影响菜单可见性** | 菜单可见性由 `sys_role_menu` 决定（F1/F2）。"看不到数据"和"进不去页面"是两件事。混在一起会让"配了范围就把菜单也藏了"变成常见事故（用户报"功能不见了"）。**例外**：字段脱敏规则页、角色互斥规则页这类**纯配置页**由权限码控制菜单（6.1） |
| ❌ 数据权限**不做"按字段值过滤"**（如"只看金额 > 10 万的订单"） | 那是**业务筛选条件**，不是权限。让权限系统承载任意业务条件 = 每个页面配一套 DSL，运维不可维护，且性能不可控 |
| ❌ 脱敏**不做"行级选择性脱敏"**（同一行里 A 字段打码、B 字段打码按行不同） | 规则粒度是"表 + 字段 + 角色"（4.2）。按行不同=需要在响应里逐行判断业务状态，语义混乱、无法解释 |
| ❌ 脱敏**不是加密** | 打码后原值仍在库里（`138****5678` 只是展示层替换）。真要"不可逆"，那是加密字段 + 密钥管理，属另一件事（附录 D） |
| ❌ 角色互斥**不阻止存量数据的业务流转** | 它只在"授予/修改"三个入口拦截（5.3）。已存在的违规组合不会被系统自动撤销角色（那是人事决策）；用户仍能正常登录使用——但会出现在"冲突清单"里（5.6） |
| ❌ 角色互斥**不处理"同一用户不同时段的兼任"** | 本批不支持"有效期错开即视为合规"的复杂语义。若业务需要，"任职期间管理"属 HR 域（附录 D） |
| ❌ 本批**不做数据权限的"审批式临时提权"** | 属 D 批次工作流审批的地盘。本批只留字段位与权限码位（第 10 章） |

# 第 3 章 数据权限详设

## 3.0 一句话：本模块在改什么

**给每个角色加一个"数据范围"属性，并让这个属性成为所有业务查询的强制前缀。** 不是筛选器（用户可关），不是前端过滤（能被绕过），而是**服务端在拼 SQL 之前就注入的 WHERE 条件**。

要做对，必须同时满足四件事：

1. **五选一的范围语义清晰**（谁算"本部门"、下级怎么算）；
2. **多角色并集**（3.3）；
3. **四条路径全覆盖**：列表 / 详情 / 导出 / 统计（3.4）；
4. **三类边界有明确行为**：无部门 / 空集合 / 部门树变更（3.6）。

## 3.1 数据模型

### 3.1.1 `sys_role` 表改造（加 1 列）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `data_scope` | `VARCHAR(20)` | `NOT NULL DEFAULT 'ALL'` | 数据范围类型：`ALL` 全部 / `DEPT` 本部门 / `DEPT_AND_CHILD` 本部门及以下 / `SELF` 仅本人 / `CUSTOM` 自定义部门 |

**为什么放主表**：范围类型是角色的 1:1 属性，角色列表页要直接显示（"这个角色能看哪些数据"是管理员最关心的第二列）；放明细表会导致列表页 JOIN 或 N+1。

**为什么不存 JSON**：部门被删/停用后要能"体检出失效引用"（D7/3.7），JSON 数组没法 JOIN `sys_dept`。

**默认值为什么是 `ALL`**：见 D2。上线首日**所有现有角色的行为零变化**——这是"批次 A 已上生产"这个前提下的硬要求。

**枚举值校验**：仅接受上述 5 个字符串，其它值 → `400 / 30014 DATA_SCOPE_INVALID`「数据范围类型不合法」。**不要**用 `SMALLINT`（1/2/3/4/5），字符串可读性远高于省 18 字节——排查线上问题时，"`data_scope='DEPT_AND_CHILD'`"比"`data_scope=3`"值钱得多。

### 3.1.2 `sys_role_data_dept` 表（新建 · 角色自定义部门明细）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `UUID` | `PRIMARY KEY DEFAULT gen_random_uuid()` | 主键 |
| `role_id` | `UUID` | `NOT NULL REFERENCES sys_role(id)` | 角色 ID |
| `dept_id` | `UUID` | `NOT NULL` | 部门 ID（弱引用 `sys_dept.id`，**不建外键**——与 `sys_user.dept_id` 一致，F18） |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT CURRENT_TIMESTAMP` | 创建时间 |

**索引与约束**：

- `UNIQUE (role_id, dept_id)` —— 同一角色对同一部门只允许一条；
- `INDEX idx_sys_role_data_dept_role_id (role_id)` —— 保存/回显都按角色查；
- `INDEX idx_sys_role_data_dept_dept_id (dept_id)` —— "哪个角色引用了这个部门"（D7 体检）反向查；
- **硬删表**（整批重建，照 `sys_role_menu` 模式，F12）：保存时"先删该角色全部明细，再批量插入本次勾选"，**不做软删**——软删 + 整批重建会累积重复行，且唯一索引失效。

**只存叶子还是全存**：**只存用户勾选的部门**（父节点被勾选时，只存父节点，不展开子节点）。原因：范围语义里"本部门及以下"已经是"含下级"的意思，如果自定义也展开存，部门树改结构（新增下级）后范围不会自动跟进——而用户预期是"这个部门及其将来新增的下级都算"。**展开动作发生在查询时**（用 `find_dept_subtree_ids`，F14），不落库。

> ⚠️ **产品决策（写死）**：`CUSTOM` 范围视为「所选部门 **及其全部下级**」（与 RuoYi 的 `CUSTOM` 语义一致）。如果业务要"只要这一个部门、不要下级"，用「本部门」那条路走不通（那是"我自己的部门"），需要的是**第 6 种范围类型**——本批**不做**，列入附录 B-B3 待拍板。**理由**：组织机构里 99% 的"选部门"意图是"这个部门的人（含下级）"，只选本级是罕见诉求，为它加一个类型会让角色编辑页的 5 个选项变成 6 个并引来"到底选哪个"的咨询。

### 3.1.3 表清单变化

| 项 | 变化 |
|---|---|
| 新增表 | `sys_role_data_dept`（1 张） |
| 改造表 | `sys_role`（+1 列 `data_scope`） |
| 生产表总数 | 27 → **28**（本批只加这 1 张；脱敏与互斥的表见 4.1 / 5.1） |

## 3.2 五种范围类型（定义与判定）

设当前用户为 `U`，`U.dept_id = D`（可能为空，F18）。

| 类型 | 展示名 | 判定（行 `r` 的可见条件） | 若无 `dept_id` | 典型岗位 |
|---|---|---|---|---|
| `ALL` | 全部数据 | 无条件（`1=1`） | 不受影响 | 总经理、销售总监、财务总监 |
| `DEPT` | 本部门 | `r.dept_id = U.dept_id` | **空集**（D6） | 部门主管、办事处主任 |
| `DEPT_AND_CHILD` | 本部门及以下 | `r.dept_id IN find_dept_subtree_ids(U.dept_id)` | **空集**（D6） | 大区经理、事业部总监 |
| `SELF` | 仅本人 | `r.created_by = U.id` | 正常（只看自己的） | 销售员、客服、普通员工 |
| `CUSTOM` | 自定义部门 | `r.dept_id IN (所选部门 ∪ 其全部下级)` | 正常（与本人部门无关） | 跨区支援、项目组、共享服务中心 |

**四条必须写清的语义**：

1. **"本部门"不含下级**。这是最容易吵的一条：大区经理如果在「本部门」，他看不到 5 个办事处——必须选「本部门及以下」。**因此在角色编辑页，"本部门"选项的说明文字必须显式写「仅本部门，不含下级部门」**（8.2.4），否则一定有人配错然后当成 bug 报上来。
2. **"本部门及以下"用递归，不用 `dept_path` 前缀**（F16 硬约束）。部门搬迁后 `dept_path` 是旧值，前缀匹配会静默漏数据。
3. **"仅本人"看的是 `created_by`（创建人），不是"最后修改人"**。理由：销售员 A 录入的单子被主管 B 修改过，单据应该还在 A 的可见范围里（否则 A 会觉得"我的单子丢了"）。所有纳入范围的表必须有 `created_by` 列（附录 E.1）。
4. **`CUSTOM` 与用户自己的部门无关**。一个挂在"北京总部"的共享服务中心人员，可以被配成"华东 + 华南"的自定义范围。

## 3.3 多角色并集（D5 的算法）

### 3.3.1 判定顺序（必须按这个顺序，短路即停）

```
输入：用户 U 的全部「生效角色」R = {r1, r2, ...}
     （生效 = status=1 且 (expire_time IS NULL OR expire_time > now())，口径同 F5/F6）

1. 若 U 是 SUPER_ADMIN            → 返回 Unrestricted（超管不受限，3.5）
2. 若 R 为空集（用户没角色）        → 返回 DenyAll（看不到任何行，安全优先）
3. 若 R 中任一角色 data_scope=ALL  → 返回 Unrestricted
4. 否则，把每个 r 翻译成一个条件片段：
     ALL                → Unrestricted（已在第 3 步短路，不会走到这）
     DEPT               → U.dept_id 为空 ? Empty : dept_id = U.dept_id
     DEPT_AND_CHILD     → U.dept_id 为空 ? Empty : dept_id IN subtree(U.dept_id)
     SELF               → created_by = U.id
     CUSTOM             → dept_id IN (自定义部门 ∪ 各自全部下级)
                          （若该角色明细为空 → Empty，见 3.6.2）
5. 用 OR 连接全部分片 → ScopeFilter{ any_of: [片段...] }
```

### 3.3.2 并集的三个例子（验收要按这个数）

设 `U` 部门 = 华东大区，`U.id = u-001`，用户持两个角色：

| 角色 A | 角色 B | 结果 | 说明 |
|---|---|---|---|
| 华东区经理（`CUSTOM` = 华东大区） | 华南区经理（`CUSTOM` = 华南大区） | 华东 + 华南（含各自下级） | **任务书要求的核心场景**（验收 9.3） |
| 销售员（`SELF`） | 华东区经理（`DEPT_AND_CHILD`） | 华东子树 ∪ 本人创建 | "本人"与"部门"是两种不同维度，用 OR 并起来 |
| 任何角色 | 总经理（`ALL`） | **不限** | `ALL` 短路一切。**副作用**：只要有人给了用户一个 ALL 角色，其它角色的限制**全部失效**——这是并集语义的必然结果，需在 3.7 体检清单里提示"该用户因角色 X 而不受限" |

### 3.3.3 为什么是并集而不是交集

| 方案 | 结果 | 问题 |
|---|---|---|
| **并集（采用）** | 多兼一个角色 → 看得更多 | 无。符合"授权叠加"直觉 |
| 交集 | 多兼一个角色 → **看得更少** | 不可解释。真实事故：员工兼两个区域角色后，发现自己看不到任何一个区域的数据，报障后运维只能给他加 ALL 角色——**权限被系统性放大**，比并集危险得多 |
| 优先级（ALL > DEPT... 取第一个） | 结果取决于角色排序 | 隐式行为，无法让管理员预测 |

## 3.4 四条生效路径（**本模块的安全底线，逐条必做**）

> 🔴 一句话：**只在列表加过滤 = 等于没做。** 以下四条路径，每条都要有独立验收用例（第 9 章）。

### 3.4.1 路径一：列表分页

**要求**：

- 范围条件必须拼在 WHERE **最前**（作为 `(…)` 包起来的前缀），用户表单里的筛选条件一律 `AND` 在后；
- 分页 `total` 必须与 `list` 同源（同一 WHERE），禁止"total 查全量、list 查范围"——否则用户会看到"共 9,317 条"但只能翻 3 页；
- `dept_ids` 的 IN 列表来自递归查询（F14），**不要**在 SQL 里写 `dept_path LIKE`（F16）。

**反例（必须避免）**：把范围当成"默认筛选值"传给前端，前端再回传 → 用户改一下请求参数就绕过了。**范围条件永不接受来自客户端的输入**，只接受服务端会话里的身份。

### 3.4.2 路径二：详情（按 ID 取单条）—— **最容易被绕过的一处**

**要求**：

- 所有 `GET /xxx/{id}` 在**取到记录之后、返回之前**，用同一 ScopeFilter 判定这条记录是否在范围内；不在 → **404**（D4，`10002 RESOURCE_NOT_FOUND`，文案「数据不存在或你没有访问权限」）；
- **禁止**用"前端隐藏入口"代替（用户能改 URL、能用收藏夹里的旧链接、能把 ID 从 1 改成 2）；
- 校验必须用**同一份** ScopeFilter（不能"详情用 dept 判断、列表用 created_by 判断"）；
- 关联子表（明细行、附件、日志、审批记录）**跟着主记录走**：主记录不可见 → 子表接口同样 404。**这是最隐蔽的绕过点**（`/orders/{id}` 挡住了，`/orders/{id}/items` 没挡）。

**实现形态（产品要求，不给代码）**：在 `shared::data_scope` 提供 `assert_row_visible(table, row, principal) -> Result<(), ApiError>`，业务 handler 取到行后调用一次。**代码评审强制项**：每个 `by-id` 接口必须有这一行（附录 E.3）。

### 3.4.3 路径三：导出

**要求**：

- 导出**复用**批次 A 的导出管线，但查询入口必须与列表**同一个函数**（同一 ScopeFilter）；
- **禁止**为导出另写一条 `SELECT * FROM t WHERE ...`（那正是历史上"列表挡住了、导出漏了"的经典事故）；
- 导出文件里的行数必须等于"列表能翻到的总行数"——不一致即视为缺陷（验收 9.4 有专项）。

### 3.4.4 路径四：统计 / 聚合 / 看板

**要求**：

- 列表页顶部的"共 N 条"、分组汇总、图表、首页卡片、待办计数，**全部**用同一 ScopeFilter；
- 特别提醒：`COUNT(*)`、`SUM(amount)`、`GROUP BY status` 这类查询**常年被写在另一个 service 里**，是最容易漏的一处。验收要求"统计数字 = 列表手动累加"（9.5）。

### 3.4.5 路径覆盖清单（开发自检用）

| 路径 | 接口形态 | 必须做的事 | 漏了会怎样 |
|---|---|---|---|
| 列表 | `GET /x/page`、`GET /x/list` | WHERE 前缀 | 数据直接泄露 |
| 详情 | `GET /x/{id}` | `assert_row_visible` → 404 | 改 URL 就能看 |
| 子表 | `GET /x/{id}/children` | 先校验主记录 | 最隐蔽的绕过点 |
| 编辑回填 | `GET /x/{id}` （同上接口） | 同上 | 同上 |
| 更新/删除 | `PUT/DELETE /x/{id}` | **写操作前也要校验**（否则能改范围外的行） | 越权修改/删除，比越权读更严重 |
| 导出 | `POST /x/export`、异步导出任务 | 同列表 | 批量泄露 |
| 统计 | `GET /x/stats`、首页聚合 | 同列表 | 泄露总量信息（如"华东区有 1842 单"） |
| 下拉/选项 | `GET /x/options` | 同列表 | 通过选项列表推测范围外数据 |
| 关联查询 | 订单里带客户名、附件列表 | 主记录校验 + 关联记录按本表也校验 | 间接泄露 |

## 3.5 超管不受限（明确说明）

| 项 | 结论 |
|---|---|
| 判定依据 | **角色编码 `SUPER_ADMIN`**（`is_super_admin()`，F3），不是"持有 `*:*:*`" |
| 行为 | 数据范围短路为 `Unrestricted`；**同时**脱敏默认豁免（4.4） |
| 界面说明 | 角色数据范围区块顶部固定一行灰字：「超级管理员不受数据范围限制，可查看全部数据（脱敏规则默认豁免，可在参数管理中关闭）」 |
| 清空/不可配 | `SUPER_ADMIN` 角色的数据范围下拉**禁用**并固定显示「全部数据（内置，不可修改）」 |
| 审计 | 超管查看任何数据**不额外记日志**（否则日志量爆炸且无信息量）；但超管的**配置类操作**照常审计（6.4） |
| 可关性 | 数据权限豁免**不可关**（关掉会让系统无法排障）；脱敏豁免**可关**（参数 `mask.super_admin_exempt`，4.4.3） |

## 3.6 三类边界（必须给出确定行为，不留"看情况"）

### 3.6.1 用户无部门（`sys_user.dept_id IS NULL`，F18 真实存在）

| 该角色的范围 | 行为 |
|---|---|
| `ALL` | 不受影响 |
| `DEPT` / `DEPT_AND_CHILD` | **空集**：看不到任何行 |
| `SELF` | 正常（只看自己创建的） |
| `CUSTOM` | 正常（与本人部门无关） |

**界面表现**：列表为空时，若"该用户所有角色都是部门类范围且 `dept_id` 为空"，在列表区上方显示一次浅色提示（不是弹窗、不遮挡操作）：

> 「你尚未归属部门，当前数据范围为「本部门」，暂时没有可查看的数据。请联系管理员分配部门。」

**管理员侧**：3.7 体检清单列出"无部门用户"（含所属角色），供一次性补全。

**为什么不降级为"仅本人"**：无部门账号常见于**离职未删、外包临时账号、待分配新人**。让它"仅本人"意味着它能看自己创建的全部历史数据——对一个即将离职的账号，这是**不该保留的可见性**。安全优先，用提示 + 体检清单消化不便。**如果老大认为"新人看不到数据影响开工"，可改为降级 SELF，列入附录 B-B2。**

### 3.6.2 自定义部门为空

- **保存时拒绝**：`400 / 30015 DATA_SCOPE_DEPT_EMPTY`，文案「自定义数据范围至少需要选择 1 个部门」；
- **切换到「自定义」但未选任何部门时，"保存"按钮禁用**，并在部门树下方显示红字提示（8.2.5）；
- **存量兜底**：万一历史数据里存在"`data_scope='CUSTOM'` 但明细为空"（如数据被人直接改库），运行时按**空集**处理（安全优先），并在角色列表把该角色标红「自定义部门为空，当前看不到任何数据」。

### 3.6.3 部门树变更（停用 / 删除 / 搬迁）

| 变更 | 数据范围行为 | 配置页表现 | 备注 |
|---|---|---|---|
| **停用**（`status=0`） | **仍算在范围内**（停用只是不能再往里挂人，已有数据仍属该部门） | 树上灰显 + 标签「已停用」 | 停用部门下的人如果被迁走，数据范围不变 |
| **删除**（软删） | **自动出范围**：`find_dept_subtree_ids` 两侧都过滤 `deleted_at IS NULL`（F14），已删部门不再出现在子树里 | 树上红显 + 标签「已删除」，区块底部出现「清理失效引用」按钮 | 删除时本来就被"有子部门/有用户"双重保护（F15），所以只会删掉空部门——影响面小 |
| **搬迁**（改 `parent_id`） | **实时生效**：每次查询按 `parent_id` 递归现算（F16），不缓存部门集合 | 树上位置随组织架构变 | ⚠️ **硬约束：禁止用 `dept_path LIKE` 前缀匹配**（搬迁后子部门 path 是旧值，会静默漏数据） |
| **新增下级** | 对 `DEPT_AND_CHILD` / `CUSTOM` **自动包含**（递归现算） | 树上自动出现 | 这是"只存勾选节点、查询时展开"（3.1.2）带来的正确行为 |

**失效引用清理**：配置页底部「清理失效引用」→ 二次确认「将从本角色的自定义范围中移除 N 个已删除部门，是否继续？」→ 执行后写审计。

## 3.7 数据范围体检清单（DS-11 · P1）

一个页面（`/system/role` 顶部按钮「数据范围体检」），三块内容：

| 区块 | 内容 | 为什么重要 |
|---|---|---|
| ① **未配置角色** | `data_scope='ALL'` 且**创建时间早于本批上线日**的角色清单（"它们只是继承了默认值，不是管理员主动选的"） | D2 的默认值会用"全部"兜底，风险必须可见 |
| ② **失效引用** | 自定义范围里引用了"已删除部门"的角色 + 引用数 | D7 |
| ③ **无部门用户** | `dept_id IS NULL` 且持有部门类范围角色的用户 | 3.6.1 |
| ④ **因 ALL 而不受限的用户** | 持有任一 `ALL` 角色的用户数（并按角色分组） | 3.3.2 的副作用，合规审查必看 |

导出：整份清单可导出 CSV（走批次 A 导出管线）。

## 3.8 表接入契约 + 启动自检（DS-12）

**问题**：数据权限要"全站生效"，但每张表的"归属部门"列不一定叫 `dept_id`（有的叫 `org_id`、`owner_dept`）。如果不统一，就会出现"这张表漏了"。

**做法**：一张**代码内注册表**（不是数据库表），声明：

| 表名 | 部门列 | 创建人列 | 是否纳入 | 备注 |
|---|---|---|---|---|
| `sys_user` | `dept_id` | `id`（自己是自己的创建人语义不适用） | 纳入 | 用户管理页按数据范围过滤 |
| `sys_file` | 归属部门列（见附录 E.2） | `uploaded_by` | 纳入 | 批次 A 表 |
| `sys_impexp_task` | — | `created_by` | 纳入（仅 SELF 维度） | 批次 A 表 |
| 本批新表 | — | `create_by` | **不纳入**（配置类） | 规则本身不该被范围过滤，否则"配规则的人看不到规则" |

**启动自检**：应用启动时逐条校验注册表 → 表存在？列存在？列类型是 UUID？缺失则**启动失败并打印明确错误**（不允许"静默跳过"，否则上线后一周才发现"某个模块没生效"）。

**新表接入规则（附录 E.1，C/D 批次必须遵守）**：任何需要按部门/人隔离的业务表，必须①有 `dept_id`（或注册映射列）+ `created_by`；②在注册表登记；③列表/详情/导出/统计四处接 `ScopeFilter`。不满足的表默认"不纳入"——但**必须在注册表里显式写 `纳入=false` + 理由**，禁止"忘了写"。

## 3.9 越权拦截日志（DS-13 · P1）

- 记录内容：`时间 / 用户 / 表 / 请求的 ID / 判定结果（不在范围）/ 请求 IP`；
- 落哪里：**不落 `audit_logs`**（那是"变更"审计，量级不同），落独立的 `WARN` 级日志 + 每日聚合到"安全日报"；
- 保留：明细 7 天，聚合 90 天；
- 为什么 P1：P0 阶段先把"堵住"做好（返回 404），日志是"发现有没有人在试"的运营能力。

## 3.10 性能与实现约束（给架构师）

| 项 | 约束 |
|---|---|
| 部门集合规模 | 单公司部门数 < 500；`dept_ids` IN 列表上限设 **1,000**，超过则改用"子查询 JOIN"形态（不做硬性截断，避免漏数据） |
| 索引 | 纳入范围的表必须有 `(dept_id)`、`(created_by)` 索引；`sys_role_data_dept.dept_id`、`(role_id)` 索引（3.1.2） |
| 递归开销 | `find_dept_subtree_ids` 每请求调用；用户主体缓存（F10 已有）里可以缓存"该用户的 dept 子树 ID 列表"，**但必须在部门增删改时失效**（`sys_dept` 写操作后调 `invalidate_users_principal` 全员或按部门反查） |
| 缓存一致性 | 改角色数据范围 → `invalidate_role_holders(role_id)`（F10）；部门变更 → 失效相关用户；**不做"定时刷新兜底"**（会掩盖失效逻辑的 bug） |
| 生效延迟 | 配置保存后，**下一次请求即生效**（缓存已失效）；不需要用户重新登录 |

# 第 4 章 列级脱敏详设

## 4.0 一句话：本模块在改什么

**把"某个表的某个字段，对某类角色只显示打码值"变成一条可配置的规则，并在服务端组装响应时就替换掉原值——列表、详情、导出、打印拿到的都是同一份打过码的数据。**

三个"不是"必须先说清：

1. **不是前端打码**。前端打码在 F12 开发者工具里改个变量就穿了，且导出 Excel 完全走另一条路（4.6）。
2. **不是全局响应中间件**。F24 已证：现有中间件只按字段名白名单洗**审计副本**，不懂"表 + 角色 + 规则"，也不能拿它改业务响应（会把导入校验、审计日志一起洗坏）。
3. **不是加密**。打码只改展示，库里仍是原值。要"不可逆"是加密字段 + 密钥管理，属另一个课题（附录 D）。

## 4.1 数据模型

### 4.1.1 `sys_field_mask` 表（新建 · 字段脱敏规则）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `UUID` | `PRIMARY KEY DEFAULT gen_random_uuid()` | 主键 |
| `table_name` | `VARCHAR(64)` | `NOT NULL` | 表名（物理表名，如 `crm_customer`） |
| `field_name` | `VARCHAR(64)` | `NOT NULL` | 字段名（物理列名，如 `mobile`） |
| `field_label` | `VARCHAR(64)` | `NOT NULL` | 字段中文名（如「客户手机号」），用于界面展示与导出表头提示 |
| `mask_type` | `VARCHAR(20)` | `NOT NULL` | 类型码：`MOBILE` / `ID_CARD` / `EMAIL` / `NAME` / `BANK_CARD` / `AMOUNT` / `REGEX` |
| `mask_config` | `JSONB` | `NULL` | 类型参数：`REGEX` 时 `{"pattern":"...","replacement":"${1}****${2}"}`；`AMOUNT` 时 `{"keep_last_digits":2,"currency":"CNY"}`；其它类型为 `NULL` |
| `apply_role_ids` | `JSONB` | `NOT NULL DEFAULT '[]'` | 适用角色 ID 数组；**空数组 = 全部角色**（含未登录以外的所有角色，超管豁免见 4.4） |
| `status` | `SMALLINT` | `NOT NULL DEFAULT 1` | 1 启用 / 0 停用（与 `sys_role.status` 同语义） |
| `remark` | `TEXT` | `NULL` | 备注（如「依据《客户信息保护规范》第 12 条」） |
| `created_at` / `updated_at` / `create_by` / `update_by` / `deleted_at` | 审计列 | 同全站约定 | 软删表（与 `sys_role` 一致）；规则删除用软删，便于审计回溯 |

**唯一约束**：

- `UNIQUE (table_name, field_name) WHERE deleted_at IS NULL` —— **一张表的一个字段只能有一条规则**。

> **为什么不做"同一字段多条规则、按角色区分"**：那会出现"一个字段同时命中两条不同类型规则"的语义冲突（比如手机号同时被配成"手机号打码"和"正则打码"），需要再定义优先级，管理员永远说不清最后是什么结果。**"一个字段一条规则 + 规则内选多个适用角色"** 已经能表达业务全部诉求（"客服脱敏、财务不脱敏"= 适用角色选客服，财务不在名单里所以不脱敏）。
>
> **副作用（要在界面说明）**：如果业务想说"客服看打码、销售看打码、财务看明文"，就在同一条规则的适用角色里选「客服 + 销售」。财务不需要在任何地方被"排除"——**没被列进适用角色 = 不脱敏**。

- `INDEX idx_sys_field_mask_table (table_name, status)` —— 组装期高频按表查规则。

### 4.1.2 规则怎么被加载（性能）

| 项 | 结论 |
|---|---|
| 加载时机 | 启动时全量加载到进程内存（规则总数预期 < 200 行），变更时重建（写操作后主动 reload） |
| 数据结构 | `HashMap<表名, Vec<Rule>>`，Rule 内含字段名/类型/参数/适用角色集合 |
| 缓存失效 | 规则写操作 → 重建内存规则表 **+** 失效受影响角色的主体缓存（F10：因为"该用户是否有 `view-plain`"与"用户角色集合"都在主体缓存里） |
| 多实例部署 | 多实例下需**版本号广播**：规则表写操作后把版本号 +1 写缓存，各实例发现版本变化即重载（否则 A 实例配了规则，B 实例还跑旧规则 → "刷新几次结果不一样"） |
| 生效延迟 | **≤ 5 秒**（版本号轮询间隔）。验收要求"保存后 5 秒内生效"，不给"要重启"的口子 |

## 4.2 规则维度与命中语义

一条规则 = **（表, 字段）+ 脱敏类型 + 适用角色集合 + 启停**。

**命中判定（对某个用户在某个表的某一行/某个字段）**：

```
1. 该 (表, 字段) 没有启用状态的规则              → 不打码（保持原值）
2. 规则启用，但用户不在 apply_role_ids 中（且非空） → 不打码
3. 规则启用，用户在适用角色内（或 apply_role_ids 为空=全部）→ 进入 4.4 的豁免判定
4. 豁免命中（超管 / view-plain）                → 明文
5. 否则                                        → 按 mask_type 打码
```

**"字段是否敏感"由规则决定，不由代码硬编码**——这是本模块与"批次 A 导出默认脱敏"的本质区别：批次 A 是"知道常见敏感字段名就默认打码"（保守但不可配），批次 B 是"由数据管理员声明哪些字段敏感"（可配、可审计、可扩展）。

**存量兼容**：批次 A 的导出脱敏（`Mask::mobile/email/id_card/bank_card`，批次 A D10）**继续保留**作为兜底——即：即使管理员没配规则，导出时仍会按"字段名像敏感"的默认清单打码。两条机制**不冲突**：规则命中则按规则（可配类型、可配角色），规则未命中但字段名命中默认清单则按默认类型打码。**界面上要提示"以下字段已被默认兜底脱敏，建议补一条规则以便按角色控制"**（4.7 覆盖率扫描）。

## 4.3 七种脱敏类型（逐条给输入输出，验收按这张表）

> ⚠️ 下表输出**以框架实测代码为准**（F21）。`bank_card` 的框架注释示例与实现不一致（注释写 `6222****7890`，实现输出 `6222 **** 7890` 带两个空格），**本批统一按实现**，并把"修正框架注释"列进交付前提（附录 C.3）。

### 4.3.1 手机号 `MOBILE`

| 项 | 内容 |
|---|---|
| 输入 → 输出 | `13812345678` → `138****5678`（保留前 3 后 4） |
| 实现 | `Mask::mobile()`（F20），零改动复用 |
| 短值规则 | 原实现：少于 7 位**原样返回**（F21，安全缺口）→ **本批覆写为**：少于 7 位但非空 → `***`；空/null → 空 |
| 适用字段例 | `crm_customer.mobile`、`sys_user.mobile`、`erp_supplier.contact_phone` |

### 4.3.2 身份证 `ID_CARD`

| 项 | 内容 |
|---|---|
| 输入 → 输出 | `320112199001011234` → `3201****1234`（保留前 4 后 4） |
| 实现 | `Mask::id_card()` |
| 短值规则 | 少于 8 位 → `***` |
| 说明 | 保留前 4 位可用于"识别地区"，这是业务查询常见需求（HR 核对同省人员），不额外砍 |

### 4.3.3 邮箱 `EMAIL`

| 项 | 内容 |
|---|---|
| 输入 → 输出 | `alice@mail.com` → `a***@mail.com`；前缀 ≤ 2 字符时 `ab@mail.com` → `*@mail.com` |
| 实现 | `Mask::email()` |
| 无 `@` 时 | 原样返回（F21 的实现）→ **本批覆写为**：无 `@` 且长度 ≥ 3 → 按"保留前 1 后 1"打码；长度 < 3 → `***` |
| 原因 | 无 `@` 说明是脏数据，原样返回等于"脏数据不打码"，正好是最容易泄露的那一类 |

### 4.3.4 姓名 `NAME`

| 项 | 内容 |
|---|---|
| 输入 → 输出 | `张三丰` → `张**`；`欧阳娜娜` → `欧***` |
| 实现 | `Mask::name()`（保留首字符，其余 `*`） |
| 单字姓名 | 原样返回（F21：`len<=1` 原样）→ **本批保留原样**（单字姓名打码后是 `*`，完全无法区分谁是张三谁是李四，业务上不可用；单字姓名的泄露风险由数据权限控制） |
| 例外说明 | 这是七种类型里**唯一允许"短值不打码"**的例外，需在规则表单的说明里写明 |

### 4.3.5 银行卡 `BANK_CARD`

| 项 | 内容 |
|---|---|
| 输入 → 输出 | `6222021234567890` → `6222 **** 7890`（保留前 4 后 4，中间**带空格**） |
| 实现 | `Mask::bank_card()` |
| 短值规则 | 少于 8 位 → `***` |
| 展示 | 前端按原字符串展示（含空格），**不要**再做分组格式化，否则会出现 `6222  ****  7890` 双空格 |

### 4.3.6 金额 `AMOUNT`（**本批新增，框架无此原语**，F23）

这是唯一需要"业务自己定义语义"的类型，必须给死规则：

| 参数 | 默认 | 说明 |
|---|---|---|
| `keep_last_digits` | `0` | 保留末尾 N 位数字（用于对账核对），其余用 `*` 替换 |
| `currency` | `CNY` | 币种符号，输出时保留（`¥` / `$`） |
| `keep_scale` | `true` | 是否保留小数部分（默认保留，因为小数位往往不敏感，去掉反而看不出量级） |

**输出示例**（`keep_last_digits=0`）：

| 输入 | 输出 |
|---|---|
| `12345.67` | `¥**,***.67` |
| `980.00` | `¥***.00` |
| `0.00` | `¥0.00`（零值原样，打码无意义） |
| `1234567.89`（`keep_last_digits=2`） | `¥*****89.89` |

**三条硬约束**：

1. **金额脱敏只影响展示，不影响任何计算**：列表汇总、导出合计、报表统计一律用原值计算，只有"单元格里显示的那个数"被打码（4.8.2）。否则"脱敏"会变成"数据错误"。
2. **不能只打码整数部分而保留全部小数**（如 `¥12,345.67` → `¥**,***.67` 是允许的；但不允许 `¥***.**` 这种"什么都没了"的输出，会让人以为数据异常）。
3. **金额类型的字段必须声明为数值型**；若字段是字符串（`VARCHAR` 存金额），先按字符串转数值，转不动 → 输出 `¥***`。

### 4.3.7 自定义正则 `REGEX`（**本批新增**，F26 已证 `regex` 可用）

| 项 | 内容 |
|---|---|
| 配置 | `pattern`（正则）+ `replacement`（替换模板，支持 `$1..$9` 与字面量） |
| 校验 | 保存时**编译正则**；编译失败 → `400 / 30023 FIELD_MASK_PATTERN_INVALID`，文案「正则表达式不合法：{具体原因}」（如「正则表达式不合法：缺少右括号」） |
| 危险模式拦截 | 拒绝可能灾难性回溯的写法（嵌套量词 `(a+)+`、`(.*)*`）→ 文案「正则表达式存在性能风险，请改用更精确的写法」；同时**执行时设超时上限**（单值 10ms，超时则整值替换为 `***` 并记 WARN） |
| 示例 | `图案: ^(.{3})(\d{4})(\d{4})$` + `replacement: ${1}****${3}` 对 `AB123456789` → `AB1****6789` |
| ⚠️ 硬约束 | **绝对不要**走 `Mask::mask_by_type()` 的兜底分支（F22：它按字节切片，中文会 panic）。自定义类型必须用独立实现 |
| 分组校验 | 保存时检查 `replacement` 引用的 `$n` 不超过 `pattern` 的捕获组数 → 文案「替换模板引用了不存在的分组 ${3}」 |

**为什么 P0 就做正则**：企业里"员工工号 `EMP-2026-00123`"、"设备序列号"、"合同编号"这类标识符的打码需求非常普遍，而它们不属于标准 7 类中的任何一类。`regex` 已在 `Cargo.lock`（F26），零依赖成本，不做反而会逼业务去改代码。

| `ID_CARD` | 身份证 | `320112199001011234` | `3201****1234` | `Mask::id_card` | → `***` |

## 4.4 谁能看明文（D8 的完整判定）

### 4.4.1 判定顺序（命中即停，与 4.2 的规则命中合并成一条判定链）

| 步 | 条件 | 结果 |
|---|---|---|
| 1 | 该字段无启用规则 | 原值 |
| 2 | 用户在规则的适用角色内（或规则适用角色为空） | 继续 |
| 3 | 用户是 `SUPER_ADMIN` **且** 参数 `mask.super_admin_exempt = true`（默认 true） | **明文** |
| 4 | 用户持有权限码 `system:field-mask:view-plain` | **明文** |
| 5 | 其它 | 按类型打码 |

### 4.4.2 两条明文通道的定位（必须写进界面说明）

| 通道 | 给谁 | 特点 | 审计 |
|---|---|---|---|
| `SUPER_ADMIN`（默认可关） | 平台运维、救火排障 | 无需额外配置；范围最广 | **页面查看不审计**（否则噪声淹没真事件）；**导出明文必审计**（4.6.2） |
| `system:field-mask:view-plain` | 财务、审计、客服主管等**长期需要原文**的岗位 | 精确到人；可随时收回 | 同上 |

**为什么两条都要**：只有超管通道 → 所有需要明文的岗位都被塞进超管（范围失控，超管还能改配置）；只有权限码通道 → 出故障时排障要先去给自己授权（耽误事）。

### 4.4.3 参数 `mask.super_admin_exempt`

- 存放：`sys_config`（批次 A 已有参数管理页），键 `mask.super_admin_exempt`，布尔，默认 `true`；
- 关闭后：**超管也按规则打码**（用于"合规要求全员脱敏"的强监管场景）；
- 注意：`sys_config` 的读接口会把值返回前端（批次 A F23 已提示），但这是布尔开关、非敏感值，**可以**放这里。

### 4.4.4 明文查看的界面标识

用户看到明文时，**不显示任何"你正在看明文"的横幅**（那会让财务每次都被打扰）；但：
- 字段旁无特殊标记，保持业务界面清爽；
- 规则管理页的"命中预览"里可以模拟"某个角色看到什么"（8.3.3），管理员据此自查。

## 4.5 生效点（哪里必须打码）

| # | 生效点 | 要求 | 漏了会怎样 |
|---|---|---|---|
| 1 | **列表**（分页/滚动） | 组装 `Vec<RowRes>` 时逐行打码 | 最直观的泄露 |
| 2 | **详情** | 同一函数（禁止另写一份） | "列表打码、详情明文"——历史上最常见的偏差 |
| 3 | **导出**（同步 Excel/CSV、异步导出产物） | 4.6.1 | 文件带走后无法追回 |
| 4 | **打印** | 4.6.3（P1） | 纸质件外流 |
| 5 | **关联展示** | 订单详情里嵌的客户手机号、附件列表里的上传人手机号 | 间接泄露 |
| 6 | **下拉/自动完成** | 远程搜索返回的"客户名（手机尾号）" | 通过联想泄露 |
| 7 | **变更历史/审计详情页** | `audit_logs.before_data/after_data` 里的原值 → 展示时**同样按规则打码**（存储保留原值，展示打码；已有 `mask_json_value` 兜底但不懂规则，需要接同一 service） | 从"操作日志"页面看到明文 |
| 8 | **导入结果回显** | 导入校验失败行回显里的敏感列（批次 A 能力） | 通过错误报告导出明文 |
| 9 | **站内信/通知正文** | 批次 A 通知里如果引用了敏感值 | 通知外泄 |

> 🔴 **实现要求（D9）**：`shared::field_mask::apply(&mut Value /*行数据*/, table: &str, principal: &Principal)`，**所有返回业务行的 handler 在组装后调用一次**。第 9 条与第 7 条最容易漏，因为它们都在"别人的模块"里——**评审清单（附录 E.3）把这两条列成强制项**。

### 4.5.3 漏脱敏哨兵（MK-11 · P1）

在 debug / staging profile 下开启一个响应后置检查：若响应体里出现"规则声明为敏感、且用户本应被打码"的字段，**且值等于原文**（通过比对"打了码的值"是否与响应值不同来判断），打 `ERROR` 日志并计入"漏脱敏计数"，暴露为 `/health/mask-leaks` 计数。

**为什么 P1**：它本身有性能与误报成本（需要采样），P0 先用"评审清单 + 验收用例"覆盖。

## 4.6 导出与打印（D10）

### 4.6.1 导出（P0）

| 项 | 结论 |
|---|---|
| 数据来源 | 导出查询复用列表的 service（同一 ScopeFilter + 同一组装逻辑），**导出拿到的是已脱敏的行** |
| 明文分支 | **不存在"导出明文"的独立接口**。所有导出接口都走同一组装 → 打码与否由 4.4 判定 |
| 表头 | 被打码的列，导出表头加「（脱敏）」后缀，如 `客户手机号（脱敏）`——让收到文件的人知道这不是原始数据 |
| 提示 | 导出前后端返回"本次导出涉及 N 个敏感字段（手机号、邮箱）"，前端在成功提示里显示（批次 A 已有类似能力，复用） |
| 文件命名 | 含明文时文件名加 `_含敏感明文` 后缀（4.6.2），提醒接收者 |

### 4.6.2 明文导出（P0 · 双闸门）

**必须同时满足**：

1. 持有 `system:field-mask:view-plain`（**能不能看原文**）；
2. 持有 `business:impexp:export:sensitive`（**能不能批量导出敏感数据**，批次 A D10 定义）；
3. 导出**必然写一条审计**：`operation = FIELD_MASK_EXPORT_PLAIN`，`detail` 里含：涉及字段清单（`[{"table":"crm_customer","field":"mobile","label":"客户手机号"}]`）、行数、导出任务 ID。

**只满足一条时的表现**：

| 持有情况 | 导出结果 | 界面表现 |
|---|---|---|
| 两个都没有 | 全脱敏 | 正常导出 |
| 只有 `view-plain` | **全脱敏** | 导出按钮旁提示「你可以在页面查看原文，但导出敏感数据需要额外授权」 |
| 只有 `export:sensitive` | **全脱敏** | 提示「已按脱敏规则导出；如需明文请联系数据管理员授予明文查看权限」 |
| 两个都有 | **明文** | 二次确认弹窗（8.6.3）+ 审计 + 文件名后缀 |

**为什么这么严**：批次 A 的 D10 是"导出默认脱敏 + 独立权限可导明文"。批次 B 引入"按角色脱敏"后，如果仅凭 `export:sensitive` 就能导明文，那么"给客服配了打码规则"这件事在导出这一个动作上被完全绕过——客服岗通常也需要导报表。**双闸门让"打码治理"与"批量带出"解耦。**

### 4.6.3 打印（MK-10 · P1）

**P0 的现状与结论**（F30：前端当前没有任何打印基础设施）：

- 页面上的值**本身就是打码后的值**（4.5），所以**浏览器 Ctrl+P 打印出来天然是打码的**——这是 P0 的安全兜底，验收按 9.4 的"打印预览"抽查；
- P0 提供**打印样式约定**（一段 `@media print` 规则）：隐藏筛选区、操作列、分页器、顶部导航；表格边框加深；页脚显示「打印人 / 打印时间 / 数据范围：本部门」；
- **P1** 再做"打印模板"（可选列、表头公司名、A4 横版），仍复用打码后的数据源，**不开明文打印通道**。

## 4.8 与数据权限、统计的关系（**给结论**）

### 4.8.1 顺序：先过滤行，再打码列（D 结论）

```
请求 → ① 认证（who）→ ② 功能权限（能不能调这个接口）
     → ③ 数据范围（哪些行可见：ScopeFilter）  ← 第 3 章
     → ④ 行组装（DTO）
     → ⑤ 列脱敏（可见行里的敏感字段打码）      ← 第 4 章
     → 返回
```

**三条理由**：

1. **性能**：先过滤再打码，打码只作用在"用户本来就能看到的行"上。反过来的话要给全表打码再丢弃，纯浪费。
2. **安全**：顺序反了不会更安全（打码是值级替换，与行过滤无关），但**如果先打码后过滤，过滤条件若依赖敏感字段值（如按手机号筛选）就会失效**。
3. **可解释**：用户问"为什么我看到 1,842 条且手机号打码"，答案是两个独立规则叠加，互不干扰。若混在一起（比如"打码后仍能按明文搜索"），解释成本高（见 4.9.3）。

### 4.8.2 金额脱敏与统计

| 场景 | 行为 |
|---|---|
| 列表某行金额 | 打码（`¥**,***.67`） |
| 列表底部合计 / 页脚汇总 | **用原值算，显示**（合计金额不打码——否则合计没意义） |
| 导出文件的合计行 | 同上：用原值，显示 |
| 报表/图表 | 用原值 |
| 明细单元格 | 打码 |

> ⚠️ **这条会被质疑（"合计明文不就泄露了吗"）**：合计值是**聚合结果**，无法反推单条；而"合计也打码"会让金额字段的脱敏变成"这个页面不能用于对账"，直接废掉业务价值。**若某字段确实连合计都不能露（如薪酬），那它应该被配成 `SELF` 数据范围或干脆不给这个角色的菜单权限**——不是靠列脱敏解决。

### 4.8.3 脱敏与"字段级可编辑性"无关

本批**不做**"能否编辑某字段"（附录 D）。打码值是**只读展示值**，若表单回填用了打码值并提交，会把 `138****5678` 写回库——**这是必须堵的数据损坏风险**：

- 编辑表单回填时，被打码的字段：①显示打码值；②**提交时该字段不参与更新**（后端按"未传/未变更"处理）；
- 若用户修改了该字段 → 必须输入完整新值（前端校验"含 `*` 的值不允许保存"，文案「手机号包含脱敏占位符，请重新输入完整号码」）。

## 4.9 边界与已知风险

### 4.9.1 NULL / 空串 / 已是打码值

| 输入 | 输出 |
|---|---|
| `NULL` | `NULL`（不显示任何东西，不显示 `***`） |
| 空串 `""` | 空串 |
| 已是打码值（`138****5678`，如重复处理） | 检测到含 `****` → 原样返回（**幂等**，防止二次打码变成 `138****5678` → `138****5678` 之外的无意义变化） |

### 4.9.2 类型不匹配

字段声明 `MOBILE` 但值是 `"未知"` → 长度不足 → 按短值规则 → `***`（不是原样返回）。**原则：宁可过度打码，不可漏打**。

### 4.9.3 ⚠️ 已知风险：按明文搜索

**现状**：列表的搜索框若支持按手机号搜索，服务端是拿**明文**做 `LIKE` 匹配（打码在返回时发生），所以：
- 客服可以用"输入完整手机号 → 有没有结果"来**验证**某手机号是否存在（撞库/探测）；
- 无法从前端彻底消除（业务确实需要按手机号查客户）。

**缓解（P0 必须做）**：

1. 对**被打码用户**的精确搜索（等值/`LIKE '1381234%'`）**返回条数不超 1 条时，不返回"未找到/找到 1 条"的差异化提示**——统一为"没有找到匹配的客户，请确认号码是否完整"（避免二元探测）；
2. 搜索行为**记入访问日志**（DS-13 同一日志通道），异常高频（同一用户每分钟 > 30 次按敏感字段搜索）→ 记 WARN；
3. **不提供**"手机号模糊搜索 + 返回打码值"的组合（模糊搜索只对姓名/客户编号开放，不对打码字段开放）——**P0 直接不给打码字段做模糊搜索**，只允许完整值精确搜索。

> 这是本批**唯一一个"产品上做了妥协"的地方**：完全禁止搜索会废掉客服业务，完全放开会被当探测工具。上面的三条是折中，**列入附录 B-B4 待老大确认**（若内控要求更严，可改为"打码字段只允许精确搜索 + 单日 20 次上限"）。

# 第 5 章 角色互斥（SoD / 职责分离）详设

## 5.0 一句话：本模块在改什么

**把"这两个角色不能由同一个人同时持有"变成一条可配置的规则，并在三个写入入口（授予角色、改用户角色、改规则本身）把它变成硬拦截。**

SoD（Segregation of Duties）是内控的基石概念：**同一个人不能同时掌握"发起"与"审批"、"执行"与"记录"、"保管"与"核对"**。经典舞弊路径——采购员自己下单、自己审批付款——在系统里就是"一个人同时持有采购员与付款审批两个角色"。

**本模块的边界**：只管"角色组合不能共存"，不管"某个人历史上做过什么"（那是操作日志与审计的事），也不管"临时兼任"（附录 D）。

## 5.1 数据模型

### 5.1.1 `sys_role_mutex` 表（新建 · 角色互斥规则）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `UUID` | `PRIMARY KEY DEFAULT gen_random_uuid()` | 主键 |
| `role_a_id` | `UUID` | `NOT NULL REFERENCES sys_role(id)` | 角色 A（**规范化：始终取两个角色 ID 中较小者**） |
| `role_b_id` | `UUID` | `NOT NULL REFERENCES sys_role(id)` | 角色 B（始终取较大者） |
| `reason` | `VARCHAR(255)` | `NOT NULL` | 互斥原因/依据（**必填**，如「内控要求：采购与付款审批职责分离」） |
| `status` | `SMALLINT` | `NOT NULL DEFAULT 1` | 1 启用 / 0 停用 |
| `remark` | `TEXT` | `NULL` | 备注 |
| `created_at` / `updated_at` / `create_by` / `update_by` / `deleted_at` | 审计列 | 全站约定 | 软删表 |

**约束**：

- `UNIQUE (role_a_id, role_b_id) WHERE deleted_at IS NULL` —— 同一对角色只能有一条规则（**因为已规范化 `a<b`，所以"反向再加一次"会被这条唯一索引挡住**）；
- `CHECK (role_a_id < role_b_id)` —— 数据库层强制规范化，防止代码漏写；
- `CHECK (role_a_id <> role_b_id)` —— 不能自己跟自己互斥；
- `INDEX idx_sys_role_mutex_a (role_a_id)`、`INDEX idx_sys_role_mutex_b (role_b_id)` —— 校验时按"我持有的角色"反查规则。

**为什么是"无向两两"而不是"互斥组"**：

| 方案 | 表达"采购/付款/仓库三者两两互斥" | 复杂度 |
|---|---|---|
| **无向两两（采用）** | 3 条规则 | 表结构最简单；校验就是"任意一对是否命中规则"；界面就是"选两个角色" |
| 互斥组（一个组含 N 个角色，组内两两互斥） | 1 个组 + 3 个成员 | 要新增 2 张表；界面要设计"组管理 + 成员管理"两层；校验要先展开成两两再判断（等价于方案一） |

**结论**：组的能力被两两方案完全覆盖（N 个角色两两互斥 = C(N,2) 条规则）。企业里典型互斥组 3~5 个角色 → 最多 10 条规则，可接受。界面用「互斥矩阵」（P1）解决"看不清全貌"的问题。

### 5.1.2 内置角色的特殊处理

| 角色 | 能否进互斥规则 | 原因 |
|---|---|---|
| `SUPER_ADMIN` | **不能**（下拉里不出现） | 若把超管配成与某角色互斥，会导致"只有超管能进系统，但超管不能持有该角色"→ 该角色永远无人能用，**系统被锁死**。真要限制超管，应通过"减少超管人数"管理 |
| 其它内置/自定义角色 | 可以 | — |

## 5.2 规则语义（四条必须写清）

1. **无向**：规则「采购员 ↔ 付款审批」同时约束"给采购员加付款审批"和"给付款审批加采购员"两个方向。
2. **成对生效**：只有当**两个角色都生效持有**时才违规。只持有 A 或只持有 B 都不违规。
3. **"持有"的口径（D13）**：`sys_role.status = 1` **且** `(sys_user_role.expire_time IS NULL OR expire_time > now())`（与 F5/F6 一致）。停用角色、过期授权**不算持有**——但用户详情里仍显示绑定，并标注「已停用 / 已过期」。
4. **启停**：规则 `status=0`（停用）→ 不做任何校验（用于"临时放开"或"规则待生效"）。**注意：停用规则不会撤销已存在的违规组合**，它们会重新出现在"冲突清单"里（5.6.3）。

## 5.3 三个校验时机（**缺一个就等于没做**）

### 5.3.1 时机一：授予角色时（单用户「分配角色」）

**接口**：`PUT /system/user/{id}/roles`（现有，F 未改动签名）。

**校验算法**：

```
输入：目标用户 U、提交的完整角色集合 R_new（这是"覆盖式"接口，不是增量）
1. 过滤出"生效"的角色 R_eff = R_new ∩ {status=1 且未过期}
   （注意：提交时可能带了停用角色，停用角色不参与判定，但要照常保存绑定）
2. 对 R_eff 做两两组合 (ri, rj)，i<j：
     - 规范化成 (min, max)
     - 查启用状态的互斥规则
     - 命中 → 收集违规对 [(ri, rj, rule.reason)]
3. 若违规对非空：
     → 拒绝整个请求（HTTP 409，code=30017 ROLE_MUTEX_CONFLICT）
     → 返回全部违规对（不是只返回第一条！否则用户改一条再提交又撞第二条）
4. 通过 → 保存（照现有逻辑整批重建 sys_user_role），写审计 USER_ASSIGN_ROLE
   （审计 detail 里额外记录：本次是否存在"停用角色被提交"的情况）
```

**关键细节**：

- **覆盖式提交**：`PUT /roles` 是"把角色设成这个集合"。所以校验必须对**提交后的完整集合**做两两判断，而不是"只校验新加的那个"。否则"删掉 A 的同时加 B"这种操作会被误判（A 不存在了，怎么还会冲突）。
- **返回全部违规对**：只用第一条错误会让用户来回试 3 次（"改完这个又撞那个"），体验极差且会让人以为系统有 bug。
- **停用角色的坑**：管理员可能"提交了互斥的两个角色，但一个是停用状态"——此时**放行**（D13），但界面要提示「角色「X」当前为停用状态，不构成互斥；启用后将无法同时持有」。

### 5.3.2 时机二：修改用户角色时（含三个入口，全都要拦）

| 入口 | 接口 | 校验要求 |
|---|---|---|
| 新增用户（带角色） | `POST /system/user` | 创建前校验提交的角色集合（现有 `parse_and_check_roles`，F 未改动） |
| 编辑用户（改角色） | `PUT /system/user/{id}`（若含 role_ids） | 同 5.3.1 |
| 单独「分配角色」 | `PUT /system/user/{id}/roles` | 同 5.3.1（主路径） |
| **批量授予/批量调整** | 批次 A 的批量操作或未来的批量授权 | **逐用户校验，整批事务**：只要有 1 个用户违规 → **整批拒绝**，返回「共 12 个用户，其中 3 个存在角色互斥冲突」+ 逐用户清单 |
| **用户导入**（批次 A 能力） | 导入含角色列的模板 | 同批量：违规行进"失败明细"，不阻断其它行（与批次 A 的导入策略一致：默认全量事务，可配"允许部分导入"） |

> **为什么批量要"整批拒绝"而不是"跳过违规的"**：批量授权是**高权限操作**（往往一次给几十人加角色）。静默跳过会造成"我以为全给了，实际给了 9 个"的错觉，而这个错觉在合规场景就是事故。整批拒绝 + 明确清单，让人重做一遍比事后审计便宜。

### 5.3.3 时机三：修改互斥规则时（**本模块最关键的产品决策**）

新建 / 编辑 / 启用一条规则时，**先全量扫描存量冲突**：

```
1. 规则合法性与唯一性校验（5.1.1 的 CHECK + 唯一索引）
   - role_a == role_b            → 400 / 30020 ROLE_MUTEX_SELF
   - 任一角色是 SUPER_ADMIN        → 400 / 30017 附说明「内置角色不能参与互斥规则」
   - 已存在同对规则（含反向）      → 409 / 30019 ROLE_MUTEX_EXISTS
2. 全量扫描：查持有 role_a 生效授权 且 同时持有 role_b 生效授权 的用户集合
   （口径：status=1 且未过期，D13）
3. 若集合非空：
   → 拒绝保存（HTTP 409，code=30018 ROLE_MUTEX_IN_USE）
   → 返回：命中总数 + 前 20 条明细（用户名/姓名/部门/持有角色/授权时间）
   → 前端展示「导出调整清单（CSV）」按钮
4. 若集合为空 → 保存成功，写审计 ROLE_MUTEX_CREATE / ROLE_MUTEX_UPDATE
```

**四个产品决策（写死，不留"看情况"）**：

| 决策 | 结论 | 理由 |
|---|---|---|
| 提供"强制保存"吗 | **不提供** | 静默落库的违规记录会成为事后追责的抗辩理由（"系统当时允许了"）。合规规则一旦可被绕过，就等于没做（D12） |
| **编辑**规则时也要扫吗 | **要**。三个编辑动作都扫：①把停用规则**启用**；②改规则的角色 A/B（等于新建一条）；③改说明（**不扫**，说明不影响判定） | 最容易漏的是"启用停用规则"——规则是停用期间建的，存量冲突没被拦，一启用就产生违规 |
| **停用**规则要扫吗 | **不扫**（停用是"放宽"，永远合法） | 停用只会减少限制 |
| 扫描不到用户也算"通过"，还是"无法判定" | **通过**（空集合 = 0 冲突） | 这里不存在"无法判定"的情形：规则只依赖 `sys_user_role` 与 `sys_role`，查询是全量确定的 |

### 5.3.4 校验的性能口径

| 场景 | 数据量 | 目标 | 手段 |
|---|---|---|---|
| 单用户授予 | 角色数 ≤ 50 | < 50ms | 内存里两两比对（规则总数 < 200）；一次 SQL 取"启用规则"全量，进程内缓存 |
| 改规则全量扫描 | 用户 10 万级 | < 3s | 一条 SQL：`SELECT u.* FROM sys_user u WHERE EXISTS(...role_a...) AND EXISTS(...role_b...)`，命中索引 `idx_sys_user_role_role_id`（批次 A 已有）；前 20 条分页取，总数用 `COUNT(*)` 同条件 |
| 前端超时 | — | 设 **30s**（F29：全局 15s） | "保存规则"接口单独 `timeout: 30000`；若 30s 未返回，前端显示「正在扫描存量用户，请稍候…」而不是报超时错误 |

## 5.4 错误提示与冲突清单（用户看到的原文）

### 5.4.1 授予角色时（时机一 / 时机二）

**单条违规**（最常见）：

> **角色「采购员」与「付款审批」互斥，不能同时授予。**
> 互斥依据：内控要求：采购与付款审批职责分离。

**多条违规**（一次性列全）：

> **以下 2 组角色互斥，不能同时授予：**
> 1. 角色「采购员」与「付款审批」互斥 —— 内控要求：采购与付款审批职责分离。
> 2. 角色「仓库管理员」与「应付会计」互斥 —— 内控要求：货物保管与账务记录职责分离。

**停用角色提示**（放行但提示）：

> 角色「付款审批」当前为**停用状态**，不构成互斥；若后续启用该角色，将无法同时持有「采购员」。

### 5.4.2 改规则时（时机三）

**保存被拒**：

> **保存失败：新规则「仓库管理员」↔「应付会计」与 3 位用户的现有角色冲突，请先调整这些用户的角色后再启用。**
>
> | 用户名 | 姓名 | 部门 | 当前持有角色 |
> |---|---|---|---|
> | zhangwei | 张伟 | 仓储部 | 仓库管理员、应付会计 |
> | lina | 李娜 | 财务部 | 应付会计、仓库管理员 |
> | wangqiang | 王强 | 仓储部 | 仓库管理员、应付会计 |
>
> 〔导出调整清单（CSV）〕〔我知道了〕

**启用停用规则被拒**：同上，标题改为「启用失败：规则「X」↔「Y」与 3 位用户的现有角色冲突…」。

**规则本身非法**：

| 场景 | 提示原文 |
|---|---|
| 选了同一个角色两次 | 「不能把同一个角色设为互斥」 |
| 规则已存在（含反向） | 「角色「采购员」与「付款审批」的互斥规则已存在，无需重复添加」 |
| 选了超管 | 「超级管理员不能参与互斥规则（会导致该角色无人可用）」 |
| 说明为空 | 「请填写互斥原因（合规审计需要）」 |
| 角色已被删除 | 「角色「XX」已被删除，请重新选择」 |

### 5.4.3 用户自己遇到的提示（自助场景）

管理员在用户详情给某人加角色被拦时，如果**发起人是超管**，提示与 5.4.1 相同；**没有"超管可豁免"的口子**——互斥是对"被授予人"的约束，与操作者是谁无关（超管只能先改规则，而改规则会被 5.3.3 二次拦住）。

## 5.5 与"权限上限"的关系（批次 A 已有能力，本批必须能区分）

批次 A 已实现 **"非超管不能授予超管"**（权限上限：你不能把某角色授出去，如果它比你自己的权限更高）。本批是 **"角色之间不能共存"**。两者**语义不同、校验方向不同、界面位置不同**，必须让管理员一眼分清。

| 维度 | 权限上限（批次 A） | 角色互斥（批次 B） |
|---|---|---|
| **约束对象** | **操作者** vs **被授出的角色** | **被授予人** 与 **被授予人**（同一人的两个角色） |
| **回答的问题** | "你（管理员）有权把这个角色给别人吗？" | "这两个角色能落在同一个人身上吗？" |
| **超管是否受影响** | 是（超管是唯一的"上限顶点"） | 否（超管本身不参与互斥） |
| **配置位置** | **没有配置界面**（代码内置规则，只与 `SUPER_ADMIN` 编码相关） | **有配置界面**（「系统管理 → 角色互斥」） |
| **错误码** | `30001 PERMISSION_DENIED` | `30017 ROLE_MUTEX_CONFLICT` |
| **提示文案** | 「无权授予「超级管理员」角色」（批次 A 文案，以批次 A 为准） | 「角色「采购员」与「付款审批」互斥，不能同时授予」 |
| **能否被改配置绕过** | 不能（写死） | 能（停用规则即放开，但会留审计） |

### 5.5.1 界面上的三个区分点（必须都做）

1. **位置不同**：权限上限**没有界面**（它是内置约束）；互斥规则有独立菜单页（7 章）。
2. **在用户「分配角色」弹窗里的呈现顺序**：先算**权限上限**（你能否授出），再算**互斥**（能否共存）。两条都不过时，**只提示权限上限**（"你连给都无权给，谈共存没意义"），避免一次抛出两条令人困惑的错误。
3. **视觉区分**：互斥冲突用 **warning 色**（`--td-warning-color`）的 `t-alert`（是可配置的业务规则）；权限上限用 **error 色**（`--td-error-color`）（是安全边界）。文案里的措辞也不同——互斥写"互斥"、上限写"无权"。

### 5.5.2 给管理的说明文字（角色互斥页顶部，固定展示）

> 本页配置"两个角色不能由同一人同时持有"的内控规则（SoD，职责分离）。
> 与"权限上限"的区别：**权限上限**限制的是"管理员能把什么角色授出去"（内置规则，不可配置）；**互斥**限制的是"同一个人能同时拥有哪两个角色"（本页配置）。
> 规则保存时系统会扫描全部用户，存在冲突将拒绝保存。

## 5.6 存量数据与迁移（D12）

### 5.6.1 迁移策略：**只建表，不建规则**

| 项 | 结论 | 理由 |
|---|---|---|
| 迁移是否写入任何互斥规则 | **不写** | ①我们不知道客户的真实内控要求（采购与付款是否必须分离，取决于客户的组织与授权实践）；②若写入"推荐规则"且存量有冲突 → 迁移失败或被迫跳过，把发布卡住 |
| 存量若已存在违规组合 | **不阻止上线**（迁移期不做任何清理） | 迁移期无法判断"该撤谁的哪个角色"（这是人事决策）。**强制清理会在发布日引发 3 个部门的权限争议**；延迟到"合规配置规则时"再处理，责任主体清晰（合规决定规则 → 系统给清单 → HR 调整） |
| 上线后的自然衔接 | 合规在页面配第一条规则 → 若存量有冲突 → **被 5.3.3 阻断** → 拿到清单 → 处理 → 再配 | 谁决策谁承担，且全程有审计 |

### 5.6.2 首次上线的推荐动作（写进上线检查单）

1. 上线后由**合规/内控**在「角色互斥」页配置第一批规则（建议从最经典的 3 条起：采购↔付款审批、仓库管理员↔应付会计、制单↔审核）；
2. 每条规则保存时若被拦，走 5.4.2 的清单流程；
3. **配置完成后导出「互斥矩阵」（P1）或规则列表**，作为内控证据归档。

### 5.6.3 停用规则后的既有违规组合

停用规则**不会**撤销任何人的角色。表现：

- 这些用户重新出现在「冲突清单」里（列表页每行显示"当前冲突用户数"）；
- 列表页顶部对该规则显示 `t-tag` 主题 `warning`：「已停用（当前仍有 3 位用户同时持有）」；
- **重新启用时**必然走 5.3.3 的全量扫描，被拦或被放行都符合预期。

## 5.7 两个 P1 能力

| 能力 | 内容 | 价值 |
|---|---|---|
| **RM-09 互斥矩阵** | 角色 × 角色三角矩阵，命中规则标 `warning` 底、冲突用户数 > 0 标 `error` 边框。一眼看全"哪些角色对已被约束、哪些还有冲突用户" | 内控复核时不用逐条点开规则；也方便发现"漏配"（两个明显该互斥的角色是空白格） |

## 5.8 边界清单（逐条给行为，不留空白）

| 场景 | 行为 |
|---|---|
| 规则引用的角色被**删除** | 角色删除本身有 `ROLE_IN_USE` 保护（F11：有用户持有则拒绝）。若角色**无人持有**被删 → 规则变成"指向已删角色"→ 列表页该行标红「规则引用的角色已删除」，校验时**忽略该规则**（不会误拦），提供「清理失效规则」按钮 |
| 规则引用的角色被**停用** | 规则保留；因停用角色不算"持有"（D13），校验自然不触发。列表页标灰「引用的角色已停用」 |
| 用户被**停用**（`sys_user.status=0`） | 仍会出现在冲突清单里（因为绑定还在），但清单里标注「账号已停用」——**建议清理但不强制** |
| 用户被**删除**（软删） | 不计入冲突（查询按 `sys_user.deleted_at IS NULL`） |
| 两个角色互斥，但用户只有一个**过期**授权 | 不违规（D13）。用户详情里该角色标签显示「已过期」 |
| 同一用户的两个互斥角色**都由同一批次授予** | 同一批次内两两校验会发现并整批拒绝 |
| 互斥规则与数据范围**同时**影响一个人 | 两个机制**独立**：互斥挡"能不能拿到角色"，数据范围挡"拿到后能看到哪些行"。**互斥不会自动调整数据范围**，反之亦然 |

# 第 6 章 权限模型

## 6.0 三条设计原则

1. **一个动作一个码，绝不用前缀通配**——`hasPermission()` 是全等匹配（F2），写 `system:field-mask:*` 在前端**永远返回 false**，按钮永远不显示。这是本批最容易踩的坑。
2. **配置类动作全部独立授权**——配数据范围、配脱敏、配互斥都是**高敏感操作**（它们的产物直接决定谁能看什么），不能靠 `system:role:update` 一个码笼统带过。
3. **权限码不自动塞进现有角色**——沿用批次 A 的 `D-B6` 结论：迁移只写权限点与新角色包，线上已有角色由管理员手动补。自动塞会让"某人突然多出一条能改全公司数据范围的权限"，属安全事故。

## 6.2 敏感操作单独授权清单

| # | 操作 | 权限码 | 二次确认 | 审计 | 风险等级 | 为什么敏感 |
|---|---|---|---|---|---|---|
| 1 | **修改角色数据范围** | `system:data-scope:update` | 改 `ALL → 收窄` 不需确认；**改 `→ ALL` 必须二次确认** | **必审计**（含前后值） | 🔴 高 | 一行配置决定一个角色能看全公司多少数据；误配成 ALL = 静默泄露 |
| 2 | 配置自定义部门 | `system:data-scope:update` | 否 | 必审计（含部门清单） | 🔴 高 | 同上 |
| 3 | **新增/编辑脱敏规则** | `system:field-mask:create/update` | 否 | **必审计**（含规则全文） | 🔴 高 | 改一条规则 = 改一批人看到的内容 |
| 4 | **停用/删除脱敏规则** | `system:field-mask:status/delete` | **必须二次确认**（弹窗写明"停用后 N 个角色将看到明文"） | **必审计** | 🔴 高 | 停用即全量解锁，是最快的人为泄露路径 |
| 5 | **授予 `view-plain`** | `system:role:menu`（走角色菜单授权） | 否（但角色编辑页对含该码的角色打 ⚠ 标记） | 必审计（`ROLE_ASSIGN_MENU`，现有） | 🔴 高 | 这是"看原文"的总开关 |
| 6 | **明文导出** | `system:field-mask:view-plain` **且** `business:impexp:export:sensitive` | **必须二次确认**（列出字段 + 行数） | **必审计**（`FIELD_MASK_EXPORT_PLAIN`） | 🔴 高 | 数据离开系统 |
| 7 | 新增/编辑互斥规则 | `system:role-mutex:create/update` | 否（有存量冲突时自动阻断） | 必审计 | 🟡 中 | 配错会锁住业务（角色无法并存） |
| 8 | 停用互斥规则 | `system:role-mutex:status` | **必须二次确认**（写明"停用后该互斥约束失效，当前有 N 位用户同时持有"） | 必审计 | 🟡 中 | 内控失效，且是"绕过合规"的最短路径 |
| 9 | 删除互斥规则 | `system:role-mutex:delete` | 必须二次确认 | 必审计 | 🟡 中 | 规则丢失 = 内控无据可查 |
| 10 | 执行体检/扫描 | `system:data-scope:check` / `system:field-mask:scan` | 否 | 不审计（只读） | 🟢 低 | — |

**"二次确认"的统一规范**（3 处必须一模一样，避免前端各自发明）：

- 组件：`t-dialog` + `theme="warning"` + 标题「确认{操作名}？」；
- 正文必须包含**受影响范围的具体数字**（如「停用后，3 个角色（客服专员、销售员、实习生）将看到客户手机号明文，约影响 12,400 行数据」）；
- 按钮：主按钮文案是**动作本身**（「确认停用」），不用"确定"；取消按钮在最右（TDesign 默认）；
- **不可勾选"以后不再提示"**（敏感操作每次都要确认）。

## 6.3 判定链总览（一次请求里，三套机制的顺序）

```
① 认证：JWT → 用户 ID（现有）
② 功能权限：#[nik::permission] 校验 auth_code（现有，F7）
③ 数据范围：ScopeFilter 注入 WHERE（第 3 章）
④ 行数据组装
⑤ 列脱敏：field_mask::apply（第 4 章）
⑥ 响应
```

**角色互斥不在这条链里**——它是**写路径**的约束（授予/改规则时校验，第 5 章），与读路径无关。它**不会**让已违规的用户登录失败（那是"存量清理"的事，D12）。这个分工要在验收里说清（9.11 有一条反例）。

## 6.4 审计留痕（**结论：三个配置全部要留痕**）

### 6.4.1 为什么必须留痕

这三个配置的产物是"谁能看什么"，属于**权限体系本身**。出事时（数据泄露、内控审计），必须能回答："是谁、什么时候、把哪个角色/字段/规则改成了什么"。**没有这条链，等于系统无法自证清白。**

## 6.6 缓存、生效与"为什么改了没生效"排查表

| 场景 | 失效动作 | 生效延迟 | 排查线索 |
|---|---|---|---|
| 改角色数据范围 | `invalidate_role_holders(role_id)`（F10） | 下一请求即生效 | 若未生效：检查是否改了**别的角色**（用户可能还持有另一个更宽的角色 → 并集） |
| 部门增删改 | 失效相关用户主体缓存（`invalidate_users_principal`） | 下一请求即生效 | 若未生效：检查是否用了 `dept_path` 前缀匹配（F16 明令禁止） |
| 新增/改/停用脱敏规则 | ①重建内存规则表 ②广播版本号 ③失效受影响角色主体缓存 | **≤5 秒**（版本号轮询） | 若未生效：检查该实例是否收到版本号（多实例部署的广播） |
| 改互斥规则 | 无需失效（写路径实时查库） | 立即 | 若"没拦住"：检查规则是否 `status=0`；检查用户角色是否已过期/停用（D13） |

**"为什么改了没生效"的统一答复模板（写进运维手册）**：①先确认改的是不是"用户实际持有的那个角色"；②再确认用户的角色是否都生效（停用/过期不算）；③最后看缓存是否失效（看日志里的 invalidate 记录）。**不要**第一反应就重启服务——重启会掩盖缓存失效的 bug。

## 8.4 【页面 C】业务页面里的表现（普通用户视角，**最容易忽略但最影响体验**）

### 8.4.1 列表

| 项 | 要求 |
|---|---|
| 行数 | 按数据范围过滤后的总数（分页 `total` 同源，3.4.1） |
| 敏感列 | 打码值（`138****5678`），**不显示锁图标、不加 tooltip "已脱敏"**（保持业务界面干净） |
| 汇总行 | 用原值算、显示原值（4.8.2），**金额列的打码不影响合计** |
| 排序 | 按原值排序（脱敏只影响展示；若按打码值排序，`1****` 和 `2****` 的顺序会全乱） |
| 筛选 | 被打码的字段**不做模糊搜索**（4.9.3），只支持完整值精确搜索 |

### 8.4.2 详情页 404（**越权的统一落地页**）

用户按 ID 访问范围外数据时：

```
┌────────────────────────────────┐
│              🔒                 │
│   数据不存在或你没有访问权限      │
│   如需查看，请联系管理员调整数据范围 │
│        〔返回列表〕              │
└────────────────────────────────┘
```

- HTTP 状态：**404**（D4），业务码 `10002`；
- **不区分**"记录不存在"和"存在但无权"——两种情况的页面与文案**完全一致**（这是 404 而非 403 的意义）；
- 不使用"403 无权限"页（那会暴露存在性）；
- **不能**出现"返回列表"按钮点了还是白屏——返回列表走 `router.push` 到该模块列表路由，不是 `history.back()`（用户可能是从收藏夹直接进来的，`back` 会退出系统）。

### 8.4.3 列表为空的三种空态（**必须区分，否则用户分不清"没数据"和"没权限"**）

| 场景 | 判定依据 | 文案 |
|---|---|---|
| ①真的没数据 | 用户数据范围正常，只是没有符合筛选条件的记录 | 「没有符合条件的数据」+ 副文案「试试调整筛选条件或时间范围」 |
| ②数据范围导致为空（无部门） | 3.6.1 的判定 | 「你尚未归属部门，当前数据范围为「本部门」，暂时没有可查看的数据。请联系管理员分配部门。」 |
| ③数据范围导致为空（范围本身为空集，如自定义部门全被删） | 该用户所有角色都翻译成空集 | 「当前角色配置的数据范围未包含任何数据，请联系管理员检查数据权限配置。」 |

**实现要求**：后端在响应里带一个**非敏感**的标记，如 `empty_reason: "NO_DATA" | "NO_DEPT" | "SCOPE_EMPTY" | null`（**不能**在标记里带任何业务数据或部门名），前端按此选文案。

### 8.4.4 无部门提示的展示规范

- 位置：列表区上方、筛选区下方的一条 `t-alert theme="info"`（**不是弹窗**，不打断操作）；
- 频率：**每会话只显示一次**（`sessionStorage` 记标记），刷新不重复；
- 可关闭：右侧 `×`（关掉后本会话不再出现）。

### 8.4.5 为什么**没有**"你正在受数据范围限制"的横幅

这是刻意的产品决策（1.2 故事 7 提到）：

| 方案 | 问题 |
|---|---|
| **每页显示"当前仅显示本部门数据"** | ①对 90% 的用户是噪声（他们本就该只看自己部门的）；②暗示"上面还有更多数据"，会诱发"找关系要权限"的摩擦；③每个业务页面都要加，改造面巨大 |
| **只在"结果为空"时提示（采用）** | 用户只有在**真的困惑**（"我这里怎么没数据"）时才看到解释，其余时间零打扰 |

**例外**：管理类页面（如"数据范围体检"、"角色编辑"）**必须**显式展示范围，因为那里用户的关注点就是"范围对不对"。

# 第 10 章 后续规划

批次 B 交付后，云枢的权限体系具备"行级数据范围 + 列级脱敏 + 角色互斥"三件套，接下来按既定路线推进：**批次 C（内容管理）** 会在 CMS 的栏目/文章/素材表上**首次按附录 E.1 的接入契约**落地数据权限（这是对契约的第一次真实检验——如果 C 批次接入时发现契约不好用，应回头修 B 的契约而不是在 C 里打补丁），并把"内容审核"与"角色互斥"结合成"编辑 ↔ 审核不得同人"的 SoD 规则；**批次 D（工作流审批）** 才是本批留下的两个口子的真正归宿——①脱敏字段的"申请查看原文"（MK 明确不做，需审批流 + 时效 + 二次审计，届时新增 `sys_field_mask_request` 表与"临时明文令牌"机制，绝不做成"点一下就给明文"）；②数据权限的"临时提权"（如大促期间临时给某人开通全量范围 3 天，到期自动收回，同样依赖审批流与到期的机械回收）。此外，B 的三项 P1 收尾（数据范围体检清单、漏脱敏哨兵、互斥矩阵）与批次 C 的首个迭代并行排期，不单独占一个批次；若内控部门在 C 批次期间提出"互斥组（≥3 角色）"或"任职期间管理"的诉求，按附录 B/B3 的既有结论走——**先确认是"两两互斥够不够"的问题，还是"人事任职周期"的问题，前者用规则条数堆，后者属 HR 域，不在云枢权限体系内做**。

## E.1 表接入契约（C/D 批次必须遵守）

任何要纳入**数据权限**的业务表，必须同时满足：

| # | 要求 | 检查方式 |
