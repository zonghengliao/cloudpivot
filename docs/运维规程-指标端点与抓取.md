# 运维规程：指标端点（`GET /metrics`）与抓取

> 面向运维 / 后端。读完能回答三个问题：**指标在哪**、**谁能看**、**抓不到怎么定位**。
>
> 相关实现：`backend/src/shared/observability.rs`（业务指标目录）、
> `backend/src/task/metrics_sampler.rs`（每分钟采样）、
> `backend/config/config.toml` 的 `[metrics]`、`frontend/deploy/nginx.conf` 的 `location = /metrics`。
> 证据：`docs/evidence/2026-11-13-p105-metrics/`。

## 1. 端点在哪、开关是什么

| 项 | 值 |
|----|----|
| 路径 | `GET /metrics`（**根路径，不带 `/api` 前缀**——不参与 `[router].prefix`） |
| 鉴权 | **无**（Prometheus 抓取器带不了 Token）。访问控制靠来源 IP，见 §3 |
| 格式 | Prometheus 文本格式，`Content-Type: text/plain; version=0.0.4; charset=utf-8` |
| 实现 | 框架 `nik-web` 的 `metrics-prometheus` feature（`Cargo.toml` 已开）+ 运行时 `[metrics].enabled` |
| 配置 | `backend/config/config.toml` 的 `[metrics]`：`enabled` / `path` / `allow_ips` |

`[metrics]` 写在**基础配置**里（不是各 profile），两个原因：

1. `config-dev.toml` / `config-test.toml` 是 gitignore 的（仓库里只有 `.example`），
   空库首启、新机器部署只有基础配置 —— 写在 profile 里等于「新环境永远 404」；
2. nik-config 的 profile 合并只覆盖「与编译期默认值不同」的字段，`enabled = false` 正是默认值，
   **关不掉**基础配置里的 `true`：这是一个刻意的单向开关，要关只能改基础配置或摘 feature。

> 历史坑：2026-11-10 之间基础配置没有 `[metrics]`，145 的私有 `config-dev.toml` 少了这一段，
> `/metrics` 就是 404 而 `/health` 正常。现在不会了 —— 但**看到 404 先查 `enabled`**。

## 2. 指标清单（业务侧 `cloudpivot_*`）

业务指标的名字 / 类型 / HELP 文案统一登记在 `backend/src/shared/observability.rs` 的 `CATALOG`，
写入一律走 `observability::set_gauge` / `inc_counter`（内部 `Once` 登记元数据，
所以导出文本一定带 `# HELP` / `# TYPE`）。

| 指标 | 类型 | 含义 | 告警用法 |
|------|:--:|------|----------|
| `cloudpivot_auth_cache_degraded` | gauge | 1 = 鉴权缓存写失败/不可用（吊销判定仍以库为准） | 持续 60s = 1 报警 |
| `cloudpivot_token_blacklist_rows` | gauge | `sys_token_blacklist` 当前行数 | 单调增长 = 清理任务没跑 |
| `cloudpivot_token_blacklist_cleanup_deleted` | counter | 清理累计删除行数 | 观察任务在跑 |
| `cloudpivot_impexp_import_pending` / `_import_open` / `_import_stuck_seconds` / `_import_failed_24h` | gauge | 导入任务积压四视角 | `open` 长期 > 0 或 `stuck` > 1800 报警 |
| `cloudpivot_impexp_export_pending` / `_export_open` / `_export_stuck_seconds` / `_export_failed_24h` | gauge | 导出任务积压四视角 | 同上 |
| `cloudpivot_impexp_backlog_pending` / `_backlog_stuck_seconds` | gauge | 导入+导出合计 / 最早一张的等待秒数 | 总积压看这两条 |
| `cloudpivot_invariant_ok` | gauge | 1 通过 / 0 有失败 / **-1 从未跑过或未知** | `0` 报警；`-1` 报「无人值守」 |
| `cloudpivot_invariant_blockers` / `_invariant_failed` | gauge | 最近一次巡检的 BLOCKER / 失败项数 | > 0 报警 |
| `cloudpivot_invariant_age_seconds` | gauge | 最近一次巡检距今多少秒 | 超过一天 = 巡检任务死了 |
| `cloudpivot_metrics_sampler_last_success_timestamp` | gauge | 上次采样成功的 epoch 秒 | **不前进 = 采样器停了** |
| `cloudpivot_metrics_sampler_runs_total` | counter | 采样累计次数 | 进程重启归零，看速率 |

`-1` 是**刻意**的「未知」值，不是 0：把「没跑过」显示成「通过/正常」是巡检类告警最典型的事故姿势。
框架侧另有 `nik_http_requests_total`、`nik_http_request_duration_seconds`、`nik_db_*`、`nik_cache_*`，
含义见 `vendor/nik-web/src/metrics.rs` 的模块文档。

## 3. 谁能看：三种部署形态

后端判定顺序：`X-Forwarded-For` → `X-Real-IP` → TCP 对端；`allow_ips` 为空时**只放行回环**
（`127.0.0.1` / `::1`），其余一律 403 且返回体为空（不泄露端点存在与否）。

| 形态 | 做法 | 适用 |
|------|------|------|
| ① 同机抓取 | 什么都不用配，`allow_ips = []` 即可 | Prometheus / `alert_check.sh` 与服务同机 |
| ② 内网抓取、不过 nginx | `allow_ips = ["10.0.0.9"]`（填抓取端 IP） | 抓取器与后端同网段、直连 `:8023` |
| ③ 过 nginx + 白名单 | 用 `frontend/deploy/nginx.conf` 的 `location = /metrics` | **生产推荐**：访问控制只在一处（nginx） |

形态③的两个硬约束（模板里已写死）：

- **默认关**：`allow 127.0.0.1; allow ::1; deny all;`，要放开按实际抓取端加 `allow <IP>;`；
- **必须清空 `X-Forwarded-For` / `X-Real-IP`**：后端按这两个头判定来源。留着的话，
  后端看到的是客户端真实 IP，而 `allow_ips` 为空 ⇒ **白名单里的合法抓取端反而被后端 403**；
  反过来客户端自带 `X-Forwarded-For: 127.0.0.1` 也能让后端把它当回环。
  清空后后端看到的对端是 `127.0.0.1`，语义就是「nginx 已放行」。

> 现状（2026-11-13）：144 生产 nginx **还没有** `/metrics` 的 location，
> 请求会落到 `location /` 被回退成 `index.html`（200 + HTML，抓取器会解析失败）。
> 模板已就绪，随下次发布 `nginx -t && systemctl reload nginx` 生效。

## 5. 抓不到怎么定位

| 现象 | 原因 | 处理 |
|------|------|------|
| `404` | `[metrics].enabled = false`（或产物没开 `metrics-prometheus`） | 查 `cargo run -- print-config` 的 `[metrics]`；启动日志应有「指标端点已启用」 |
| `200` 但 **body 为空** | recorder 已装但没有任何指标写入（`describe` 早于安装会被丢弃） | 正常现象：没有任何请求/采样就无序列。`/health/deps` 一次即可看到身份 gauge |
| 只有 `nik_*`、没有 `cloudpivot_*` | 采样器没跑（调度器没起/库连不上）或进程刚启动且未到首个整分钟 | P1-05 起注册时**立即补采一次**；仍没有就查 `cloudpivot_metrics_sampler_last_success_timestamp` 是否前进 |
| `403` | 来源 IP 不在 `allow_ips`，或过 nginx 时没清空 `X-Forwarded-For` | 见 §3；用 `curl -H 'X-Forwarded-For: <抓取端IP>'` 复现 |
| 值恒为 `-1` | 该项查询失败或从未跑过（`-1` ≠ 0） | 查对应任务日志；`invariant_*` 全是 -1 说明巡检从未落库 |
| 通过 nginx 拿到 HTML | nginx 没配 `/metrics` location，被 SPA 回退 | 加模板里的 `location = /metrics` |

## 6. 新增一个业务指标

1. `backend/src/shared/observability.rs` 的 `CATALOG` 加一行（名字 / 类型 / 单位 / HELP 文案，
   HELP 里不能有换行和反斜杠）；
2. 写入处用 `observability::set_gauge(&NAME, value)` / `inc_counter(&NAME, delta)`，别直接调 `metrics::*`
   （直接调不会登记 HELP/TYPE，且名字未登记时 `debug_assert` 会炸 —— 这是故意的）；
3. `cargo test --lib shared::observability`：目录自检 + 「采样器写入的每个名字都已登记」+ 端点渲染。

## 7. 与告警脚本的关系

`scripts/ops/alert_check.sh` 的 ③⑥ 两项**优先读 `/metrics`**（应用自己采的，脚本不持有库口令），
读不到才退回只读 SQL。P1-05 之前基础配置没开端点，新环境上这两项实际上一直在走 psql 退路；
现在空库首启就有指标，脚本走的是主路径（见证据 05 的 `backlog: 数据源 = /metrics`）。
