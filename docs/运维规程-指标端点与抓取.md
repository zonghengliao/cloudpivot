# 运维规程：指标端点（`GET /metrics`）与抓取

> 面向运维 / 后端。读完能回答三个问题：**指标在哪**、**谁能看**、**抓不到怎么定位**。
>
> 相关实现：`backend/src/shared/observability.rs`（业务指标目录）、
> `backend/src/task/metrics_sampler.rs`（每分钟采样）、
> `backend/config/config.toml` 的 `[metrics]`、`frontend/deploy/nginx.conf` 的 `location = /metrics`。
> 证据：`docs/evidence/2026-11-13-p105-metrics/`。

## 1. 端点在哪、开关是什么

| 项 | 值 |
|----|----|
| 路径 | `GET /metrics`（**根路径，不带 `/api` 前缀**——不参与 `[router].prefix`） |
| 鉴权 | **无**（Prometheus 抓取器带不了 Token）。访问控制靠来源 IP，见 §3 |
| 格式 | Prometheus 文本格式，`Content-Type: text/plain; version=0.0.4; charset=utf-8` |
| 实现 | 框架 `nik-web` 的 `metrics-prometheus` feature（`Cargo.toml` 已开）+ 运行时 `[metrics].enabled` |
| 配置 | `backend/config/config.toml` 的 `[metrics]`：`enabled` / `path` / `allow_ips` |

`[metrics]` 写在**基础配置**里（不是各 profile），两个原因：

1. `config-dev.toml` / `config-test.toml` 是 gitignore 的（仓库里只有 `.example`），
   空库首启、新机器部署只有基础配置 —— 写在 profile 里等于「新环境永远 404」；
2. nik-config 的 profile 合并只覆盖「与编译期默认值不同」的字段，`enabled = false` 正是默认值，
   **关不掉**基础配置里的 `true`：这是一个刻意的单向开关，要关只能改基础配置或摘 feature。

> 历史坑：2026-11-10 之间基础配置没有 `[metrics]`，145 的私有 `config-dev.toml` 少了这一段，
> `/metrics` 就是 404 而 `/health` 正常。现在不会了 —— 但**看到 404 先查 `enabled`**。

## 2. 指标清单（业务侧 `cloudpivot_*`）

业务指标的名字 / 类型 / HELP 文案统一登记在 `backend/src/shared/observability.rs` 的 `CATALOG`，
写入一律走 `observability::set_gauge` / `inc_counter`（内部 `Once` 登记元数据，
所以导出文本一定带 `# HELP` / `# TYPE`）。

| 指标 | 类型 | 含义 | 告警用法 |
|------|:--:|------|----------|
| `cloudpivot_auth_cache_degraded` | gauge | 1 = 鉴权缓存写失败/不可用（吊销判定仍以库为准） | 持续 60s = 1 报警 |
| `cloudpivot_token_blacklist_rows` | gauge | `sys_token_blacklist` 当前行数 | 单调增长 = 清理任务没跑 |
| `cloudpivot_token_blacklist_cleanup_deleted` | counter | 清理累计删除行数 | 观察任务在跑 |
| `cloudpivot_impexp_import_pending` / `_import_open` / `_import_stuck_seconds` / `_import_failed_24h` | gauge | 导入任务积压四视角 | `open` 长期 > 0 或 `stuck` > 1800 报警 |
| `cloudpivot_impexp_export_pending` / `_export_open` / `_export_stuck_seconds` / `_export_failed_24h` | gauge | 导出任务积压四视角 | 同上 |
| `cloudpivot_impexp_backlog_pending` / `_backlog_stuck_seconds` | gauge | 导入+导出合计 / 最早一张的等待秒数 | 总积压看这两条 |
| `cloudpivot_invariant_ok` | gauge | 1 通过 / 0 有失败 / **-1 从未跑过或未知** | `0` 报警；`-1` 报「无人值守」 |
| `cloudpivot_invariant_blockers` / `_invariant_failed` | gauge | 最近一次巡检的 BLOCKER / 失败项数 | > 0 报警 |
| `cloudpivot_invariant_age_seconds` | gauge | 最近一次巡检距今多少秒 | 超过一天 = 巡检任务死了 |
| `cloudpivot_metrics_sampler_last_success_timestamp` | gauge | 上次采样成功的 epoch 秒 | **不前进 = 采样器停了** |
| `cloudpivot_metrics_sampler_runs_total` | counter | 采样累计次数 | 进程重启归零，看速率 |
| `cloudpivot_http_requests_total` | counter | 请求数，标签 `method` / `path`（归一化）/ `status`（**精确码**） | 4xx/5xx 按端点和具体码定位 |
| `cloudpivot_http_request_duration_seconds` | histogram | 请求耗时（秒，标签 `path`） | `histogram_quantile(0.95, …)` 出 p95 |
| `cloudpivot_http_errors_total` | counter | 5xx 总数（无标签，**启动即为 0**） | `rate(...[5m])` = 错误率分子 |
| `cloudpivot_db_pool_connections` | gauge | 连接数，标签 `state` = `idle` / `active` / `total` | `total / max > 0.8` 报警 |
| `cloudpivot_db_pool_max_connections` | gauge | 池配置上限（`[database.pool].max_connections`） | 与上一条相除算使用率 |

`-1` 是**刻意**的「未知」值，不是 0：把「没跑过」显示成「通过/正常」是巡检类告警最典型的事故姿势。
框架侧另有 `nik_http_requests_total`、`nik_http_request_duration_seconds`、`nik_db_*`、`nik_cache_*`，
含义见 `vendor/nik-web/src/metrics.rs` 的模块文档。

### 2.1 HTTP / DB 四项关键指标（P1-06 补）

四条指标解决四个具体问题，**不是**重复框架已有的 `nik_*`：

| 需求 | 框架 `nik_*` 有什么 | 本仓 `cloudpivot_*` 多出什么 |
|------|---------------------|------------------------------|
| 请求数 | `nik_http_requests_total{method,route,status}`，`status` 只到**类别**（`2xx`/`4xx`/`5xx`） | `status` 是**精确码**（`404`/`422`/`500` 分开），排障不用翻日志 |
| 延迟 | `nik_http_request_duration_seconds{method,route}` | 只按 `path` 切（少一层维度，`histogram_quantile` 更省） |
| 错误率 | 只能 `sum by (status="5xx")`，规则易写错 | `cloudpivot_http_errors_total` 一条序列直接 `rate()` |
| `/health` | **排除**（探针不污染 SLO） | **计入**（探针也是真实流量；`/api/health` 不存在，见下） |
| DB 连接 | 只有语句数与耗时，**没有连接水位** | `idle` / `active` / `total` + 配置上限 |

口径细节：

- **埋点位置**：`backend/src/middleware/http_metrics.rs`，挂 `App::layer_from_fn`（链**外**层）。
  只有在这里才能看到框架自己拒绝的 `401 / 403 / 429` 与 404 兜底；放 handler 里或链内层，
  故障时会得出「成功率 100%」的错觉。
- **计入范围 = 接口流量**：`[router].prefix`（`/api`）下的请求 + 根路径 `/health`、`/health/deps`。
  静态资源与 SPA 回退**不计数**：一体化部署（`[static_files].enabled`）时前端有 400+ 个带 hash
  的 chunk，全记会把 512 的标签预算吃光，之后真正的接口路径反而被归并成 `__other__`。
- **标签基数**：`path` 做过归一化（数字段 → `:id`、UUID → `:uuid`、≥24 字节随机串 → `:token`），
  且总量上限 512，超出归 `__other__`。**不要**把具体 id 传进标签，也不要新增按 `user_id`
  之类高基数维度切分的指标。
- **`cloudpivot_http_errors_total` 启动即有 0 序列**：Prometheus 文本格式不导出「没有任何数据点」
  的指标，不 seed 的话健康系统上 `grep errors_total` 什么都看不到（P1-05 的
  `cloudpivot_token_blacklist_cleanup_deleted` 就是这样消失的）。seed 由
  `observability::seed_zero_series()` 在采样器首次运行 + 首个 HTTP 请求时完成。
- **DB 连接水位是服务端口径**：`pg_stat_activity WHERE datname = current_database() AND pid <> pg_backend_pid()`
  （排除采样自己的连接，否则 `active` 永远 ≥ 1）。看的是「本库连接总数会不会撞上服务端
  `max_connections`」，外部客户端（psql / 迁移 / 运维脚本）也占配额，这正是想要的口径；
  池内部 `in_use` 在框架实现里是 `pub(crate)`，业务侧取不到。
  `total - idle - active` 非 0 说明有 `idle in transaction`（连接泄漏的典型形态）。
- **`/api/health` 不存在**：`/health` 是根路径探针，手动注册以豁免 `[router].prefix`（约定 8）。
  压测脚本写 `http://127.0.0.1:8023/api/health` 会得到 **404**（也会被计数，`status="404"`）；
  要压活的探针用 `/health`。

## 3. 谁能看：三种部署形态

后端判定顺序：`X-Forwarded-For` → `X-Real-IP` → TCP 对端；`allow_ips` 为空时**只放行回环**
（`127.0.0.1` / `::1`），其余一律 403 且返回体为空（不泄露端点存在与否）。

| 形态 | 做法 | 适用 |
|------|------|------|
| ① 同机抓取 | 什么都不用配，`allow_ips = []` 即可 | Prometheus / `alert_check.sh` 与服务同机 |
| ② 内网抓取、不过 nginx | `allow_ips = ["10.0.0.9"]`（填抓取端 IP） | 抓取器与后端同网段、直连 `:8023` |
| ③ 过 nginx + 白名单 | 用 `frontend/deploy/nginx.conf` 的 `location = /metrics` | **生产推荐**：访问控制只在一处（nginx） |

形态③的两个硬约束（模板里已写死）：

- **默认关**：`allow 127.0.0.1; allow ::1; deny all;`，要放开按实际抓取端加 `allow <IP>;`；
- **必须清空 `X-Forwarded-For` / `X-Real-IP`**：后端按这两个头判定来源。留着的话，
  后端看到的是客户端真实 IP，而 `allow_ips` 为空 ⇒ **白名单里的合法抓取端反而被后端 403**；
  反过来客户端自带 `X-Forwarded-For: 127.0.0.1` 也能让后端把它当回环。
  清空后后端看到的对端是 `127.0.0.1`，语义就是「nginx 已放行」。

> 现状（2026-11-13）：144 生产 nginx **还没有** `/metrics` 的 location，
> 请求会落到 `location /` 被回退成 `index.html`（200 + HTML，抓取器会解析失败）。
> 模板已就绪，随下次发布 `nginx -t && systemctl reload nginx` 生效。

### 4.1 门禁里的自检（P1-09 · `check.sh --l0`）

`bash scripts/check.sh --l0` 的 L0 层会跑 `scripts/verify/metrics_gate.sh`，判两条：
**HTTP 200** 且 **body 里有 `^# HELP cloudpivot_`**（P1-05 的真实故障是「200 但一条业务指标都没有」，
只看状态码发现不了；而 `alert_check.sh` 的 ③⑥ 正是读这些指标）。四档开关：

| `METRICS_GATE` | 行为 |
|:--|:--|
| `auto`（默认） | 本机有「部署证据」（`CI=1` / `/etc/cloudpivot*/*.env` / systemd 里注册过 cloudpivot 服务）→ 按 block 真跑；没有（开发机）→ 连不上就跳过 |
| `block` | 必须真跑，失败即红（CI / 144 / 145 / 演练用） |
| `warn` | 真跑但不阻断 |
| `off` | 跳过（`SKIP_METRICS_CHECK=1` 等价）——卡面要求的逃生门 |

为什么不能一刀切必跑：`check.sh --fast` 就是 pre-push 钩子，开发机上服务通常没起 ——
一律 block 等于「没起服务不能 push」，门禁迟早被绕过；一律 skip 则 145/144 上「服务挂了」被静默放过。
地址解析：`METRICS_URL` > `NIK_METRICS_URL` > `NIK_SERVER_LISTEN`（环境/`/etc/cloudpivot*/**.env`）
> `backend/config/config.toml` 的 `[server].listen` > `8023`（145 的实例是 `127.0.0.1:8033`）。

```bash
bash scripts/verify/metrics_gate.sh --self-test   # 判据自检：起假服务，12 条断言（不用真后端/库）
bash scripts/verify/metrics_gate.sh               # 只跑这一条（auto）
METRICS_GATE=block bash scripts/check.sh --l0     # 开发机上强制校验（服务没起就会红）
SKIP_METRICS_CHECK=1 bash scripts/check.sh --l0   # 本机没服务、又不是部署机时放行
```

## 5. 抓不到怎么定位

| 现象 | 原因 | 处理 |
|------|------|------|
| `404` | `[metrics].enabled = false`（或产物没开 `metrics-prometheus`） | 查 `cargo run -- print-config` 的 `[metrics]`；启动日志应有「指标端点已启用」 |
| `200` 但 **body 为空** | recorder 已装但没有任何指标写入（`describe` 早于安装会被丢弃） | 正常现象：没有任何请求/采样就无序列。`/health/deps` 一次即可看到身份 gauge |
| 只有 `nik_*`、没有 `cloudpivot_*` | 采样器没跑（调度器没起/库连不上）或进程刚启动且未到首个整分钟 | P1-05 起注册时**立即补采一次**；仍没有就查 `cloudpivot_metrics_sampler_last_success_timestamp` 是否前进 |
| `403` | 来源 IP 不在 `allow_ips`，或过 nginx 时没清空 `X-Forwarded-For` | 见 §3；用 `curl -H 'X-Forwarded-For: <抓取端IP>'` 复现 |
| 值恒为 `-1` | 该项查询失败或从未跑过（`-1` ≠ 0） | 查对应任务日志；`invariant_*` 全是 -1 说明巡检从未落库 |
| 通过 nginx 拿到 HTML | nginx 没配 `/metrics` location，被 SPA 回退 | 加模板里的 `location = /metrics` |

## 6. 新增一个业务指标

1. `backend/src/shared/observability.rs` 的 `CATALOG` 加一行（名字 / 类型 / 单位 / HELP 文案，
   HELP 里不能有换行和反斜杠）；
2. 写入处用 `observability::set_gauge(&NAME, value)` / `inc_counter(&NAME, delta)`，别直接调 `metrics::*`
   （直接调不会登记 HELP/TYPE，且名字未登记时 `debug_assert` 会炸 —— 这是故意的）。
   带标签用 `set_gauge_labeled` / `inc_counter_labeled`，分布型用 `observe_histogram`
   （标签**值**必须是 `'static`，别把运行时字符串直接塞进去，见 §2.1 的基数说明）；
3. 只在异常时才累加的 counter（错误数 / 清理数之类）要么从启动就 seed 一条 0 序列
   （`observability::seed_zero_series` 里加名字），要么在文档里写明「健康时看不到这条」——
   否则运维会以为指标没上线；
4. `cargo test --lib shared::observability`：目录自检 + 「采样器写入的每个名字都已登记」+ 端点渲染；
   带标签/直方图的埋点再加一条「真实 HTTP 请求后 `/metrics` 上数值正确」的用例
   （范本：`backend/src/middleware/http_metrics.rs` 的 `metrics_are_exported_after_real_requests`）。

## 8. 告警通道：`alert_check.sh` → 站内消息（P1-07）

巡检脚本检测到异常后，除了写 `ALERT.log` / 建 kanban / 发飞书，还会调后端内部接口把告警
落成**站内消息**（`notice` 模块的 `sys_notice`），收件人是**超管角色（`SUPER_ADMIN`）**，
超管在「消息中心」直接能看到、能标已读 —— 这是**主通道**（不需要外部 webhook 凭据）。

### 8.1 接口契约

```
POST /internal/alert
Content-Type: application/json
X-Internal-Token: <NIK_ALERT_INTERNAL_TOKEN>   # 仅跨机调用需要

{"level":"critical|warning","title":"…","content":"…","source":"alert_check","idempotency_key":"可选"}
```

| 项 | 说明 |
|----|------|
| 路径 | **根路径** `/internal/alert`，**不是** `/api/internal/alert`（宏路由会被 `[router].prefix` 嵌套，这里由 `App::post` 手动注册） |
| 免认证 | 处理器上的 `#[nik::no_auth("!/internal/alert")]`（`!` = 绝对路径） |
| 准入 | **只认对端地址**：回环放行；非回环必须带 `X-Internal-Token` 且等于 env `NIK_ALERT_INTERNAL_TOKEN`。**不看 `X-Forwarded-For` / `X-Real-IP`**（可伪造） |
| 为什么不放 `/api/` | nginx 只反代 `location /api/` 与 `location /metrics`；放进 `/api/` 等于挂到公网，而经 nginx 后对端恒为 `127.0.0.1`，准入闸会被抹平 |
| 落库 | `sys_notice`：`notice_type=ALERT`、`level=ERROR(critical)/WARN(warning)`、`target_type=ROLE`、`sender_name=<source>`、`biz_type=ALERT`；收件人由 `ROLE` 扇出写 `sys_notice_receiver` |
| 送达强度 | `force = true`：**不受**收件人 `notify.inbox` 偏好影响（关掉站内信的人更要看到告警） |
| 幂等 | 传了 `idempotency_key` 就保证同键只落一条（`uk_sys_notice_idem`），重放返回 `duplicated=true` + 首次的 `notice_id`；脚本默认不传，去重由自己的状态目录负责 |
| **去重（P1-08）** | 同一 `(source, title)` 在 **10 分钟**滑动窗口内只落**一条**，窗口内的重复只累加计数；窗口过后的下一条会在正文里带「近 10 分钟已重复 N 次」。状态在 `sys_notice_alert_dedup`（V0404），跨重启有效。窗口长度由 env `NIK_ALERT_DEDUP_WINDOW_SECONDS` 覆盖（默认 600，合法区间 1~86400） |
| 错误码 | `403 + 30001` 非回环无 token；`400 + 10001` 级别非法 / 标题正文为空或超长；`500 + 10004` 库异常或 `SUPER_ADMIN` 角色缺失 |

**响应体（三种结局，互斥）**

```json
{"code":0,"data":{
  "published":true,"deduped":false,"duplicated":false,
  "merged_count":0,"level":"ERROR","window_seconds":600,
  "notice_id":"…","notice_no":"NTA…","receiver_count":1
}}
```

| `published` | `deduped` | `duplicated` | 含义 | 调用方该做什么 |
|:--:|:--:|:--:|:--|:--|
| `true` | `false` | `false` | 真的落了一条通知 | 无需动作 |
| `false` | `true` | `false` | 窗口内重复，**已合并**（`merged_count` = 本窗口第几次） | **正常结局**，不要当失败重试 |
| `true` | `false` | `true` | 命中永久幂等键，返回首次那条 | 无需动作 |

`merged_count`：发布时是**上一窗口**被合并的次数（>0 表示正文已带「近 N 分钟已重复 X 次」）；
被合并时是**本窗口累计**次数（含本次）。

### 8.2 脚本侧

```bash
# 默认（同机部署）：什么都不用配，脚本 POST 到 http://127.0.0.1:8023/internal/alert
bash scripts/ops/alert_check.sh

NIK_ALERT_NOTICE=off              # 关掉站内消息通道（只留 ALERT.log）
```

### 8.4 分级与去重（P1-08）

**分级**：告警只有两档，落在 `sys_notice.level` 上（`sys_notice` 的 CHECK 只允许
`INFO/SUCCESS/WARN/ERROR`，所以是映射不是新枚举）：

| 巡检口径 `level` | 落库 `level` | 触发场景（运维口径） | 消息中心表现 |
|---|---|---|---|
| `critical` | `ERROR` | BLOCKER / 服务不可用 / 数据不一致 | 红色标签 + **置顶**（排在最前） |
| `warning` | `WARN` | 阈值越界 / 慢查询 / 磁盘 >80% | 黄色标签 |

置顶是 `GET /business/notice/mine` 的**排序契约**，不是前端排序：

```
GET /api/business/notice/mine?pin_critical=true|false     # 缺省 true
```

- `pin_critical=true`（缺省）：`ORDER BY (CASE WHEN n.level='ERROR' THEN 0 ELSE 1 END), created_at DESC, id DESC`
  —— 每条都带 `pinned` 字段（`level = ERROR` 时 `true`），前端据此打「置顶」角标；
- `pin_critical=false`：纯时间倒序（顶栏铃铛与消息浮层就用这个 —— 它们要「最新」，不是「最严重」）。

**去重窗口**（`sys_notice_alert_dedup`，迁移 `V0404`）：

- 键是 `(source, title)` 二元组：同一来源的同一条告警，10 分钟内只落一条；
- 状态列：`window_start`（本窗口发布时刻）、`repeat_count`（本窗口被合并的次数）、
  `notice_id`（本窗口实际落的那条，`NULL` = 还没发成功）；
- **`notice_id IS NULL` 时不抑制**：上次 dispatch 失败会立刻重发，不会留下"空窗口"把后面
  10 分钟的告警全吞掉（宁可多响，不可少响）；
- 窗口长度：`NIK_ALERT_DEDUP_WINDOW_SECONDS`（默认 600；验收脚本压到 2 秒跑端到端）。

排查用两行 SQL：

```sql
-- 现在有哪些告警还在窗口里（last_seen_at 是不是还在往前推 = 还在犯）
SELECT source, title, window_start, repeat_count, last_seen_at FROM sys_notice_alert_dedup
 WHERE last_seen_at > now() - interval '1 hour' ORDER BY last_seen_at DESC;
-- 某条告警最近落了几条通知（应该 ≤ 每小时 6 条：10 分钟窗口）
SELECT created_at, level, left(content, 60) FROM sys_notice
 WHERE sender_name = 'alert_check' AND title = '…' ORDER BY created_at DESC LIMIT 10;
```

**两层去重的关系**（脚本侧 300s + 服务端 600s，见 `alert_check.sh` 头部注释）：
脚本侧窗口管「别把 ALERT.log / kanban 刷爆」，服务端窗口管「消息中心里同类只有一条且知道自己
被重复了几次」。两者**不要求相等**：脚本每 5 分钟最多再发一次，所以服务端 10 分钟内最多看到
2 次（第 2 次被合并计数 +1），第 3 次（窗口已过）补发并在正文写「近 10 分钟已重复 1 次」。
