> 起因：卡 `t_d4e92b99`（2026-11-10）。生产 144 的「admin 登录成功」自查项连续失败，
> 并把自己唯一的超管锁了 30 分钟。根因不是认证链坏了，而是**凭据口径没定**：
> `NIK_ADMIN_PASSWORD` 被当成「admin 的现用口令」在用，实际它只是**空库首启的种子**，

## 1. 变量职责（**唯一口径**）

| 变量 | 语义 | 谁用 | 能不能登 `admin` |
|---|---|---|---|
| `CLOUDPIVOT_OPS_USER` / `CLOUDPIVOT_OPS_PASSWORD` | **运维自查账号**（真人账号，当前生产 = `henry.liao`） | 所有「登录一下证明服务/认证链正常」的脚本 | 不适用（它是另一个账号） |
| `NIK_OPS_USER` / `NIK_OPS_PASSWORD` | 同上，等价别名（兼容用） | 同上 | — |
| `NIK_ADMIN_PASSWORD` | **空库首启时 `admin` 的初始口令「种子」**；只在 `sys_user` 里没有 `admin` 那一行时才生效（`backend/src/bootstrap.rs::ensure_admin_user`，幂等） | 只有 bootstrap | ❌ 生产上必然 401 |
| `NIK_ADMIN_USERNAME` | 种子账号名（默认 `admin`） | 只有 bootstrap | — |
| `CLOUDPIVOT_ADMIN_PASSWORD` | 需要 SUPER_ADMIN 语义的验收脚本（如 `scripts/verify/n7_acceptance.sh`）**显式**注入 | 仅 dev/test | ✅（但别放进生产 env） |

解析器：`scripts/ops/ops_cred.sh`（生产机上同步一份在 `/root/ops_cred.sh`），
一律按 `CLOUDPIVOT_OPS_*` → `NIK_OPS_*` → `NIK_ADMIN_*`（回退时打黄字告警）的顺序取。

## 2. 为什么「重试」比「失败」更危险

`backend/src/shared/constants.rs`：

| 常量 | 值 | 后果 |
|---|---|---|
| `MAX_LOGIN_FAIL_COUNT` | 5 | 第 5 次失败把 `sys_user.is_locked` 置 `t` |
| `LOCK_MINUTES` | 30 | 锁 30 分钟（`lock_time`；到期由 `auth/handler.rs::is_locked_now` 自动解锁） |
| `LOGIN_RATE_MAX_ATTEMPTS` | 10 | 同一「用户名 + IP」60 秒内第 11 次起返回 429 |
| `LOGIN_RATE_WINDOW_SECS` | 60 | 固定窗口（从窗口内首次尝试起算） |

所以规矩只有一条：**脚本登录只尝试一次，401/403 立刻停并打印处置**。
401 = 口令与账号不匹配（去核对 env，别重试）；403 = 账号锁定/禁用；429 = 限流，等 60 秒。
`auth_logs` 与 `security_logs` 会把每次失败记在 `username` 名下 —— 重试等于自己把号锁了，
还给审计留下「有人在撞库」的假象。

历史证据：2026-11-10 03:20–03:35、06:03 两批失败把 `sys_user.admin` 顶到 `login_fail_count=6 / is_locked=t`。

## 3. 生产自查怎么跑

```bash
# 只看线上还好不好（不动代码/库/服务，不重启）
bash /root/prod_deploy.sh --verify-only

# 只跑自查本体（⑦ 步就是它）
bash /root/prod_selfcheck.sh
```

`prod_selfcheck.sh` 做五件事：health → 单次登录（`CLOUDPIVOT_OPS_*`）→ 三个业务列表页 →
菜单可见性（按登录账号角色过滤，仅供参考）→ 库侧 `admin` / 运维账号的 `is_locked`、
`login_fail_count`。硬失败 `exit 1`，告警不影响退出码。

仓库侧等价物：`scripts/ops/prod_selfcheck.sh`（部署后由 `scripts/ops/` 同步到 `/root`）。

## 5. 换成运维账号后：哪些断言不再是「回归」

运维账号（当前 `henry.liao` / `GENERAL_MANAGER`）**不是** SUPER_ADMIN，所以下面这些**后台管理面**
会返回 `403 + 20002`（缺权限码）。实测在 144 上跑出来的清单（2026-11-10）：

| 接口 | 需要的权限码 | 用运维账号 |
|---|---|---|
| `POST /api/business/erp/stock-in/batch-export`（d7 第 3 条） | `business:impexp:export:create` | 403（预期；400 才是参数闸生效） |
| `GET /api/system/menu/tree`（erpr3 第 5 条） | `system:menu:*` | 403（预期，已改成 SKIP） |
| `PATCH /api/system/user/{id}/password`（重置超管口令） | `system:user:password` + 权限上限 | 403（必须 SUPER_ADMIN 会话） |
| `POST /api/system/role`（n7 建角色） | `system:role:create` | 403（n7 只能用超管，脚本里已加护栏） |

规矩：**脚本要把这类结果记成 SKIP 并写明「要 SUPER_ADMIN」，不许记成 FAIL**，否则每次跑都红，
下一个人就会误以为是回归。真需要超管语义时，人工注入 `CLOUDPIVOT_ADMIN_PASSWORD`
（只进进程环境，不写进生产 env），跑完就把变量丢掉。

## 6. `admin` 口令重置（需要超管语义时）
`admin` 是唯一 `SUPER_ADMIN`，它的现用口令**只有人知道**，env 里没有、也推不出来。
两条路：

1. **接口**：`PATCH /api/system/user/{id}/password`（权限码 `system:user:password`）。
   ⚠ 有权限上限保护（`system/user/handler.rs::change_password` → `guard::ensure_role_grant_allowed`）：
   **非超管改不了超管口令**，运维账号会拿 403。必须由 SUPER_ADMIN 会话执行。
2. **DBA 维护窗口**：把 `sys_user.password` 更新为 argon2id PHC 串（后端 `nik::prelude::Crypto` 校验时
   按 PHC 串自带参数解析），同时 `must_change_password=true`（一次性凭据，首登强制改密）。

改完必须实测一次 `admin` 登录 200 + `is_locked=false / login_fail_count=0`；
新口令写进密管/保险柜，**不要**写进 `cloudpivot.env`。

## 7. 已知遗留（下一张卡）

现在生产自查借用真人账号 `henry.liao`（`GENERAL_MANAGER`），有两个问题：

1. **耦合**：henry.liao 一旦改密，自查立刻 401（同一类故障会再来一次）；
2. **审计**：`auth_logs` 里分不清「机器自查」与「henry 本人操作」。

正确做法是建一个**最小权限的专用自查账号**：
- 注意 `user_type='ROBOT'` 的账号**禁止网页登录**（`system/auth/handler.rs` → `ai_actor::login_forbidden`），
  所以只能是 HUMAN 类型的服务账号（如 `svc_selfcheck`），`real_name` 写明「自动化，勿删」；
- 角色只需要只读：`sys_role` + `sys_role_menu`（页面/只读权限码），`data_scope` 与自查需要的范围一致；
- 口令长度 ≥ 24，写入 env 的 `CLOUDPIVOT_OPS_*`（或密管注入）。

改造前，任何「换个账号」的动作都要先跑一遍 `bash /root/prod_selfcheck.sh` 验证登录 + 业务接口可见性。
