## 1. 开工第一步：实测表结构（卡面硬红线 ①）

`psql \d` 实测（cloudpivot_dev，2026-10-30），**四条事实直接改写了卡面的三个假设**：

```
biz_inventory（10 列，**没有 deleted_at**）
 id | material_id | warehouse_id | qty | locked_qty | avg_cost | amount | last_txn_at | created_at | updated_at
 索引：uk_biz_inv_mat_wh UNIQUE (material_id, warehouse_id) / idx_biz_inv_material / idx_biz_inv_warehouse
 CHECK：ck_biz_inv_locked (locked_qty >= 0)
 外键：**没有**（所以自检可以拿任意 UUID 造库存行）

biz_inventory_location（W1a 已建，库位级数量账）
 id | material_id | warehouse_id | location_id | qty | locked_qty | last_txn_at | created_at | updated_at
 uk_biz_inv_loc UNIQUE (material_id, warehouse_id, location_id) NULLS NOT DISTINCT

biz_warehouse（树列叫 warehouse_path / level / is_leaf，**不是** path）
 ck_biz_warehouse_type CHECK (warehouse_type IN ('NORMAL','RAW','FINISHED','SCRAP','IN_TRANSIT'))
   → **IN_TRANSIT 枚举早已存在**，本卡不需要动枚举
 ck_biz_warehouse_root  CHECK ((parent_id IS NULL) = (level = 1))
 uk_biz_warehouse_code  UNIQUE (warehouse_code) WHERE deleted_at IS NULL   ← 部分索引

biz_material_serial / biz_material / biz_location：W1a/W2a 已建，本轮只读
```

**结论**：
1. 卡面 §二① 的疑点定案 —— `biz_inventory` **确实没有 `deleted_at`**，三列唯一索引不能用部分索引，改用 `COALESCE(location_id, 全零 uuid)` 折叠 NULL。
2. `warehouse_type` **不需要新增 `IN_TRANSIT`**（卡面写成「或者新增枚举值」，实际不用）。
3. 在途仓种子的路径列叫 `warehouse_path`，且根节点必须 `parent_id IS NULL AND level = 1`。
4. `location_id` 在本仓的既定口径是 **`biz_inventory_location.id`（库位库存行 id）**，不是 `biz_location.id` —— W2a/W2b 的 `serial.location_id` 就是这么定的（见 `serial_model.rs` 模块头）。

## 2. 与卡面 / W0 设计的差异（逐条，别当 bug）

| # | 项 | 卡面 / W0 | 本轮落地 | 理由 |
|---|---|---|---|---|
| 1 | 三列唯一索引 | 卡面写「partial index 或 COALESCE」 | `COALESCE(location_id, '0000…'::uuid)`，**无** `WHERE deleted_at IS NULL` | 实测 `biz_inventory` 无 `deleted_at` |
| 2 | 在途仓枚举 | 卡面「用现有枚举或新增 IN_TRANSIT」 | 直接用 `IN_TRANSIT`，**不动 CHECK** | 枚举本来就在 |
| 3 | 明细数量列名 | 卡面 `qty` / W0 §2.6 `quantity` | **`qty`**（卡面优先） | 库存侧已统一 `qty`，W3b/前端不必记两套 |
| 4 | 主表原因列 | 卡面 `reason VARCHAR(255)` / W0 `transfer_reason VARCHAR(20) DEFAULT 'BALANCE'` | **`reason VARCHAR(255)`** | 不并列建同义列（数据不一致源头） |
| 5 | 序列号子表 | 卡面 `biz_stock_transfer_item_serial(item_id, serial_id)` / W0 `biz_stock_transfer_serial(transfer_id, item_id, serial_no)` | **按卡面** | 少一层冗余；代价：同一件货挂同一单两条明细 DB 不拦 → **W3b 必须跨明细去重** |
| 6 | 明细行号唯一 | W0 有 `uk(transfer_id, line_no)` | **不建** | 卡面 `line_no` 默认 1，唯一约束会让「不传 line_no 的多行明细」直接失败 |
| 7 | 状态机 CHECK | W0 §2.6 两条（state + cancel_reason） | 合并成一条 `ck_biz_transfer_state`（CANCELLED 必须同时有 `cancelled_at` + 非空 `cancel_reason`） | 一条约束表达同一件事，报错更清楚；`CASE … ELSE FALSE END` 避开 PG 三值逻辑 |
| 8 | 外键 | V0137「弱引用不建外键」 | 调拨三表**建硬外键**（卡面显式要求） | 引用的都是 W1a 已落的严格主数据；仓库/物料被删时调拨单本就不该存在 |
| 9 | 主外键目标 | 卡面 `REFERENCES biz_inventory_location(id)` | 照抄 | 与 W2a/W2b 的 `location_id` 口径一致；**代价**：建明细前对应库位库存行必须存在（W3b 用 create-or-get 保底） |
| 10 | 状态枚举 | 卡面 6 态 | 照抄 6 态 | 与 W0 §6.2 一致 |

## 5. 连带修复：三列唯一索引会把旧 `ON CONFLICT` 目标顶掉（42P10）

**这是本卡最容易被漏掉的一处**：`uk_biz_inv_mat_wh` 一删，代码里所有
`INSERT … ON CONFLICT (material_id, warehouse_id)` 的推断目标就不存在了，PG 直接报
`42P10 there is no unique or exclusion constraint matching the ON CONFLICT specification`
（不是性能问题，是语法层拒绝）。实测「旧写法必然失败」：

```
  [PASS] A1 旧 upsert 目标已失效（ERROR: there is no unique or exclusion constraint matching the ON CONFLICT specification）
  [PASS] A2 第一次 upsert（插入汇总桶） → 5.0000
  [PASS] A2 第二次 upsert（命汇总桶，走 DO UPDATE） → 5.0000
  [PASS] A2 汇总桶只有 1 行（ON CONFLICT 真命中，没有插重） → 1
```

受影响并已修的三处（另有 1 处是文档注释）：

> ⚠ **与 V0139 up 文件头注释 ④ 的差异（写清楚，别被误导）**：up 文件头只写了「两处」
> （`serial_model.rs::recompute_quantity` + `serial_handler.rs` 测试夹具）——写文件时确实只搜到这两处；
> 第三处 `inventory_audit.rs::fix_sql()` 是 W2c-2 在本卡开发期间新提交的文件，本卡是**跑
> `cargo test --lib business::erp` 时才发现的**（见下面的 128 passed / 1 failed）。
> 该 up 文件此时已被 dev 实例应用（checksum 冻结），**不能再改一个字**，所以以本文档为准。
> 同类隐患不排除还有：新增任何 `biz_inventory` upsert 时，请先 `grep -n "ON CONFLICT" <文件>` 自查。

| 文件 | 位置 | 性质 |
|---|---|---|
| `business/erp/serial_model.rs` | `recompute_quantity`（W2c-1 不变式①） | **生产路径**（序列号登记 / 入库重算数量） |
| `business/erp/inventory_audit.rs` | `fix_sql()`（W2c-2 巡检 dry_run=false 的修正语句） | **生产路径**（本卡实测时被 `cargo test` 抓到） |
| `business/erp/serial_handler.rs` | 真库测试夹具 | 测试路径 |
| `business/erp/model.rs` | 2 处文档注释里的索引名 | 文档 |

修法：冲突目标改成
`ON CONFLICT (material_id, warehouse_id, COALESCE(location_id, '00000000-0000-0000-0000-000000000000'::uuid))`。
**语义不变**：这几处算的都是「该物料该仓的全部件数」= 仓级汇总，正好落进 `location_id IS NULL`
汇总桶（与 W0 §2.4「NULL = 未分配库位/整仓汇总」一致）。

**回归证据**（`ERP_DB_URL` 指向已应用 V0139/V0140 的 `cloudpivot_w3a`）：

```
cargo test --lib business::erp -j 1
test result: ok. 129 passed; 0 failed; 0 ignored
```

> 教训（给 W3b / 后续卡）：**任何对 `biz_inventory` 的 upsert 都必须用表达式冲突目标**，
> 否则真库才炸、编译期看不出来。写新库存写入时先 `grep -n "ON CONFLICT" <文件>` 自查。

## 6. 影响面与未做项

- **dev 库（cloudpivot_dev）已被应用**：dev 实例是 `cargo-watch -w migrations` 起的，迁移文件一落地就自动重启并应用。
  实测 `schema_migrations`：139/140/143 全部 `success=true`，checksum 与本轮文件一致。
  所以**两个 up 文件已冻结**（改一个字符 = dev 启动 `migration version 139 was modified after it was applied`）。
- **prod（8023 / `cloudpivot` 库）未动**：prod 二进制不重启就不应用迁移；本卡没编 release、没重启任何服务。
- **本卡只建表**：没有业务代码（CRUD/发运/签收是 W3b）。W3b 需要自己补的：
  1. `biz_seq` 的 `TR` 取号规则种子（本卡不种）；
  2. 「同一件货挂同一单两条明细」的跨明细去重（卡面方案 DB 不拦）；
  3. 调拨明细的 `from_location_id / to_location_id` 指向 `biz_inventory_location.id`，
     建单前要 create-or-get 该库位库存行（硬外键会拦）；
  4. 状态流转必须按 `ck_biz_transfer_state` 写时间戳（`submitted_at` / `approved_at` / `shipped_at` /
     `received_at` / `transit_warehouse_id` / `cancel_reason`），否则插入即被拒；
  5. 单号唯一索引是**部分索引**，`ON CONFLICT (transfer_no)` 要写成
     `ON CONFLICT (transfer_no) WHERE deleted_at IS NULL`。
- **迁移不可重放**：V0137 up 的自检 ③ 断言 `uk_biz_inv_mat_wh` 存在，V0139 之后重放 V0137 up 会挂在那条断言上
  （符合仓里「迁移只前进 + checksum 不可改」的口径）。
- **hotspot**：`business/erp/serial_model.rs` 与 `inventory_audit.rs` 是 W2c-1 / W2c-2 的文件，本卡只改了
  ON CONFLICT 目标这一行（+注释）。若后续卡要动同一函数，请注意这是「三列索引」的约束相关代码。
