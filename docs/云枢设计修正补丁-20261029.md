## 🔴 严重级

### 修正 1：AI 用户不变式（`user_type` ⇔ `sys_ai_agent`）

**问题**：T5 用 `sys_user.user_type`，L1 建 `sys_ai_agent`，两者关系未定义 → 可能出现 ROBOT 无配置或配置无 ROBOT。

**决定（不变式，必须两侧同时保证）**：
```
user_type = 'ROBOT'  ⇔  sys_ai_agent 中存在该 user_id 的记录（双向，一一对应）
```

**三层保证**：
1. **应用层（同事务）**：建 AI 用户 = `INSERT sys_user(ROBOT)` + `INSERT sys_ai_agent` 在同一事务；删 = 同一事务软删两者
2. **DB 约束**（尽力）：`sys_ai_agent.user_id` 外键 + 应用层禁止 `user_type` 单独改（改 user_type 必须走 AI 用户接口 / 或从 ROBOT 改回 HUMAN 时强制要求先清 sys_ai_agent）
3. **启动自检**（每次启动跑，违反即 ERROR 日志 + 拒绝启动（prod））：
```sql
SELECT count(*) FROM sys_user u WHERE u.user_type='ROBOT'
  AND NOT EXISTS (SELECT 1 FROM sys_ai_agent a WHERE a.user_id=u.id)
  -- 应为 0
SELECT count(*) FROM sys_ai_agent a
  JOIN sys_user u ON u.id=a.user_id WHERE u.user_type<>'ROBOT'
  -- 应为 0
```

**落地**：L1 任务追加；T5 任务书引用本不变式。

### 修正 3：任务令牌（T5b）与 JWT 的认证边界

**问题**：两套认证，若混用可能绕过角色/数据权限。

**决定（硬边界）**：
| 项 | JWT（人类） | 任务令牌（AI） |
|---|---|---|
| 中间件 | `AuthMiddleware` | **独立 `TaskTokenMiddleware`** |
| 可访问 | 全平台按角色 | **仅白名单 4 个端点** |
| 绑定 | 无 | **强制 `path.task_id == token.task_id`**（否则 403） |
| 数据权限 | 全套 scope | **不做 scope**（令牌本身就限定了单个任务） |
| 过期 | 按 JWT | `max_runtime + 1h`，**任务结束立即失效** |
| 审计 | 记 operator | 记 `operator = AI用户`, `via = task_token` |

**实现要求**：
- 任务令牌**不得**能访问任何 `sys_*` 或 `business/` 其他端点（白名单外一律 403）
- 令牌校验放**路由层**（axum 的独立 Router 或 middleware），不放通用 AuthMiddleware 分支

**落地**：写入 T5b 设计（已追加）+ T5b 任务书。

### 修正 4：任务附件补 storage 策略

**问题**：现有 6 类（announcement/attachment/avatar/document/import/template）无任务类。

**决定**：新增两条策略
```sql
-- V0107__storage_task_policies.sql
INSERT INTO sys_storage_policy (category, max_size_mb, allowed_ext, ...) VALUES
('task',    50,  'jpg,jpeg,png,gif,webp,pdf,doc,docx,xls,xlsx,ppt,pptx,txt,md,csv,json,zip', ...),
('task_ai', 100, 'jpg,jpeg,png,gif,webp,pdf,txt,md,csv,json,zip,log', ...);  -- 禁 exe/sh/bat/ps1/so/dll
```
- `task`：人类上传的任务附件
- `task_ai`：AI 产出物（**可执行脚本一律禁止**，防止 AI 写个 .sh 让人点）
- 两者都走私有桶 + 签名 URL

**落地**：manong 修正卡（含迁移 + 策略校验单测）。

## 🟠 中等级

### 修正 5：表命名体系 —— 定判据，不改存量

**问题**：C 批次 `sys_announcement/sys_help_doc/sys_change_log` vs C+ `biz_task*`。

**决定**：
- **判据**（写进开发规范）：
  - `sys_` = **平台治理与系统能力**（用户、部门、角色、菜单、配置、文件、偏好、字典、任务日志等）
  - `biz_` = **业务对象**（由业务产生、有业务流程的数据：任务、项目、订单…）
- **存量不动**（C 批次三张表已上线，改名 = 迁移+代码+前端+权限码全改，风险远大于收益）
- **增量遵守**：新业务对象一律 `biz_`
- 在 `cailu-dev-standards.md` 加一条命名规则

### 修正 6：权限码前缀 —— 定判据，只纠正明确错误的

**问题**：`system:help:*`（终端用户看）与 `business:announcement:*`（同一性质）前缀不一致。

**决定**：
- **判据**：**终端用户日常可见/使用 → `business:`；仅管理员配置 → `system:`**
- 按此判据复核现有：
  - `business:announcement:*` ✅ 正确（员工要看公告）
  - `system:change-log:*` ✅ 正确（管理员查审计）
  - `system:help:*` ❌ **应为 `business:help:*`**（员工要看帮助）
- **执行**：帮助文档的权限码**不迁移**（已授权到角色，迁移风险大），但**新功能遵守判据**；在文档标注"help 为历史不一致，已知"
- 更彻底的方案（可选，需专门窗口）：`UPDATE sys_menu SET auth_code = replace(auth_code,'system:help:','business:help:')` + `sys_role_menu` 不用动（按 menu_id 授权）—— **待评估后再做**

### 修正 7：状态机统一 —— 前端统一组件

**问题**：任务 / 公告 / 导入导出三套命名。

**决定**：
- **后端语义不改**（各域状态本来就不同）
- **前端建 `StatusBadge` 统一组件**：`<StatusBadge domain="task|announcement|import" status="..."/>`
- 颜色/文案映射集中在一个 `status-map.ts`（一个文件管三套）
- **写进 T6（前端）任务书**

### 修正 8：通知偏好 —— 分级（T3 前必须定）

**问题**：任务通知未说明是否尊重 `notify.inbox/email` 偏好。

**决定（分级表）**：
| 通知类型 | 是否受偏好控制 | 理由 |
|---|---|---|
| **被分派任务** | ❌ **强制** | 漏掉会直接经济损失（没人干活） |
| **被 @ 提及** | ❌ 强制 | 同上 |
| **待你验收** | ❌ 强制 | 阻塞流转 |
| **被打回** | ❌ 强制 | 必须知道要返工 |
| 状态变更（他人） | ✅ 尊重 `notify.inbox` | 噪音 |
| 临期提醒 | ✅ 尊重 | 噪音 |
| 逾期汇总 | ✅ 尊重 | 噪音 |
| 评论（未@你） | ✅ 尊重 | 噪音 |

**实现**：`notice::dispatch(type, recipients, force: bool)` —— `force=true` 跳过偏好检查。

**落地**：写进 T3 任务书 + 核心设计 §九。
