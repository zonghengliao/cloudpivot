# 运维规程 · 进程清理安全（P0 铁律）

> 版本：v1.0 · 2026-11-05
> 触发事故：2026-11-05 19:47 生产环境清理遗留进程，误杀 PostgreSQL 连接池 9 个后端进程
> 状态：**强制规程，所有进程清理操作必须遵守**

---

## 一、事故复盘（必须读完）

### 1.1 发生了什么

2026-11-05 19:47，在 144 生产机清理 worker 测试遗留的 debug 版 cloudpivot 进程。

最初写的第一版脚本用了精确路径匹配：

```bash
case "$EXE" in
  */debug/cloudpivot) kill ... ;;
esac
```

**第一轮：一个都没杀掉。** 原因：测试二进制已被重新编译覆盖，`readlink /proc/PID/exe` 返回
`/opt/cloudpivot/backend/target/debug/cloudpivot (deleted)`，**带 ` (deleted)` 后缀**，
通配符 `*/debug/cloudpivot)` 匹配不上。

**第二轮：放宽匹配。** 改成 `ps -eo pid,cmd | grep "[c]loudpivot"` 取所有 PID，再用 `*debug*` 判定。

结果 `grep "[c]loudpivot"` **同时匹配到了 9 个 PostgreSQL 后端进程**：

```
postgres: cloudpivot cloudpivot 127.0.0.1(54321) idle
          ^^^^^^^^^        ^^^^^^^^^
          |                数据库名 —— 就在 cmdline 里
          用户名
```

这 9 个进程是生产服务（PID 1156249）的连接池子进程，被一起 `kill -TERM` 了。

### 1.2 实际影响：零（但不是设计出来的，是运气）

| 检查项 | 结果 |
|---|---|
| 生产进程 1156249 | 存活，未重启（NRestarts=0），启动时间未变 |
| 服务状态 | active，`/health` 200 |
| 未结束事务 | **0 条**（关键：没有事务被打断） |
| 数据核对 | 凭证 21 / 采购 14 / 收货 14 / 任务 71 / 用户 9 / 迁移 193，一条没丢 |
| 定时任务 | 19:40:00「审批超时扫描完成」正常执行 |
| 连接池 | sqlx 自动重连，连接数 11 → 2 → 恢复 |

**为什么没事**：sqlx 的连接池检测到连接断开后自动重连；当时恰好没有事务在跑。
**如果当时有一个收货过账事务正在执行**（一个事务要写库存 + 库位账 + 流水 + 凭证 + 应付 + 序列号六件事），
被 TERM 会触发事务回滚，或者更糟 —— 部分写入。

### 1.3 三个错误决策（逐条记下）

| # | 错误 | 正确做法 |
|---|---|---|
| 1 | 用`ps \| grep`按名字选进程 | 必须用 `readlink /proc/PID/exe` 取精确路径比对 |
| 2 | `case` 通配没考虑 ` (deleted)` 后缀 | 路径判定统一用 `*debug/cloudpivot*`（尾部星号） |
| 3 | 放宽匹配时没有加排除名单 | 必须先排除 `postgres` / `node` / `esbuild` 等 |

## 二、强制规程（四条铁律）

### 铁律 1：禁止按进程名 grep 选目标

```bash
# ❌ 绝对禁止
ps -eo pid,cmd | grep cloudpivot | awk '{print $1}' | xargs kill

# ❌ 也禁止（-f 会匹配 cmdline 里任何位置）
pkill -f cloudpivot
killall cloudpivot

# ✅ 唯一正确姿势
for p in $(ls /proc | grep -E '^[0-9]+$'); do
  EXE=$(readlink -f /proc/$p/exe 2>/dev/null) || continue
  # 用 EXE 精确判定，绝不用 CMD
done
```

**理由**：`postgres: cloudpivot cloudpivot ...` 的 cmdline 里必然含数据库名；任何按名字 grep 都会误伤。

### 铁律 2：路径判定统一用「前缀 + 尾部通配」

```bash
# ❌ 精确结尾匹配（会被 (deleted) 后缀击穿）
case "$EXE" in
  */debug/cloudpivot) ;;
esac

# ✅ 前缀 + 尾部通配（同时兼容 (deleted)）
case "$EXE" in
  *target/release/cloudpivot*) IS_PROD=1 ;;
  *target/debug/cloudpivot*)    IS_TEST=1 ;;
esac
```

**理由**：二进制被重新编译后，老进程的 `/proc/PID/exe` 变成 `原路径 (deleted)`。

### 铁律 3：杀之前必须过三道闸

```
闸 1 · 白名单保护
   生产 PID = $(systemctl show cloudpivot -p MainPID --value)
   任何操作前先 `[ "$p" = "$PROD_PID" ] && continue`

闸 2 · 黑名单排除（即使误匹配也不杀）
   case "$EXE" in
     */postgres*|*/node|*/esbuild*|*code-server*) 跳过 ;;
   esac

闸 3 · 归属确认（必须是本次要清的那一类）
   路径含 debug / 临时 target(*-target/) / /var/tmp/
   且在测试端口段(18085-18100) 或 无监听
```

**三闸全过才允许 kill。**

### 铁律 4：生产机上，先 SIGTERM 观察再决定

```
1. 打印待杀清单（PID + exe + 运行时长 + 监听端口 + 判定理由）
2. SIGTERM
3. sleep 5
4. 复查：生产 /health 是否 200、连接数是否正常、有无未结束事务
5. 只有确认生产健康，才继续对残留进程 SIGKILL
```

**绝不批量 SIGKILL，绝不在同一批里混生产和测试目标。**

## 三、标准作业流程（SOP）

### 3.1 清理遗留进程

```bash
# 1. 盘点（只看不动）
ps -eo pid,etime,rss,cmd | grep cloudpivot | grep -v grep

# 2. 用安全脚本做判定与清理（会打印三闸判定过程）
/opt/cloudpivot/scripts/maintenance/safe_kill_stale_cloudpivot.sh --dry-run   # 先看
/opt/cloudpivot/scripts/maintenance/safe_kill_stale_cloudpivot.sh             # 再执行

# 3. 事后必查
systemctl is-active cloudpivot
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8023/health
psql ... -c "select count(*) from pg_stat_activity where datname='cloudpivot';"
psql ... -c "select count(*) from pg_stat_activity where state <> 'idle' and pid <> pg_backend_pid();"
```

### 3.2 事后必查清单（缺一不可）

| 检查 | 命令 | 通过标准 |
|---|---|---|
| 服务存活 | `systemctl is-active cloudpivot` | `active` |
| 未重启 | `systemctl show cloudpivot -p NRestarts --value` | `0`（若 >0 说明被杀过） |
| 健康接口 | `curl .../health` | `200` |
| 登录可用 | `POST /api/system/auth/login` | `200` 且有 `access_token` |
| 连接池 | `select count(*) from pg_stat_activity` | ≥ 2，无异常增长 |
| 未结束事务 | `state <> 'idle'` 的条数 | 0（或只有当前查询） |
| 数据核对 | 核心表 count | 与清理前一致 |
| 错误日志 | `journalctl -u cloudpivot -p err` | 无新增 |

**任何一项不通过 → 立即停止后续操作，先报告。**

## 四、云枢特有的坑（必须知道）

### 4.1 PostgreSQL 进程一定含数据库名

```
postgres: cloudpivot cloudpivot 127.0.0.1(54321) idle
          ↑ 用户名    ↑ 数据库名
```
数据库名是 `cloudpivot` → cmdline 必含 `cloudpivot` → **任何按名字的匹配都会误伤。**

### 4.2 二进制被覆盖后 exe 带 (deleted)

worker 每次 `cargo build` 都会覆盖 `target/debug/cloudpivot`，
老进程的 exe 变成 `.../cloudpivot (deleted)`。判定时必须容忍这个后缀。

### 4.3 worker 会起很多临时 target

已知的测试 target 路径模式：
```
/root/t*[0-9]-target/debug/cloudpivot
/root/w3b-target/debug/cloudpivot
/root/p7-target/debug/cloudpivot
/root/regress-*-target/debug/cloudpivot
/var/tmp/e11-run/cloudpivot
```
这些跑完就该退出，不退出就是遗留。它们监听 18085-18100 段。

### 4.4 生产端口是 8023，测试端口是 180xx

```
生产:  127.0.0.1:8023
测试:  127.0.0.1:18085 ~ 18100
```
**看到 180xx 端口 = 测试实例，可以清；看到 8023 = 生产，绝对不碰。**

## 五、反例清单（做过就错）

| 反例 | 为什么错 |
|---|---|
| `pkill -f cloudpivot` | 会杀 PG 连接、node、esbuild |
| `killall cloudpivot` | 按可执行文件名匹配，会杀掉所有实例包括生产 |
| `ps \| grep cloudpivot \| awk '{print $1}' \| xargs kill -9` | 名字匹配 + 直接 SIGKILL，双重致命 |
| `for p in $(pgrep cloudpivot); do kill $p; done` | pgrep 默认匹配进程名，但 `-f` 会匹配 cmdline |
| 在同一批 kill 里混生产和测试 | 一旦误判，生产直接挂 |
| 只查 `/health` 就认为没问题 | 必须查未结束事务 + 数据核对 |

## 六、这个规程是怎么来的

**是用一次真实的误操作换来的。** 2026-11-05 19:47，清理 6 个测试实例时误杀了 9 个
PostgreSQL 连接进程，生产侥幸无损。

**记住一句话**：生产机上，任何 `kill` 都是高危操作，选错目标 = 数据可能不完整。
选择目标的**唯一合法依据**是 `/proc/PID/exe` 的精确路径，不是进程名、不是 cmdline、不是端口。
