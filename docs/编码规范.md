# 编码规范

> 本文列出后端 + 前端的**强制约定**，是 [AI二开指引.md](./AI二开指引.md) 的规范底稿，也是提交前评审的 checklist。违反任意一条都会导致 clippy 报错、运行 panic、SQL 注入或功能异常。

---

## 一、后端（Rust）

### 1.1 命名（强制）
| 对象 | 规则 | 示例 |
|------|------|------|
| 实体模型 | 后缀 `*Model` | `SysUserModel` |
| 请求 DTO | 后缀 `*Req` | `UserCreateReq` |
| 响应 DTO | 后缀 `*Res` | `UserDetailRes` |
| 布尔变量 / 函数 | `is_` / `has_` / `can_` 前缀 | `is_locked`、`has_permission` |
| 枚举类型 / 变体 | 帕斯卡 / snake_case | `AuthStatus::unauth` |
| 表名 | 蛇形，域前缀 | `sys_user`、`operation_logs` |

#### 1.1.1 表名前缀判据（2026-10-29 设计修正 A · 修正 5）

```
sys_ = 平台治理与系统能力（用户/部门/角色/菜单/配置/文件/偏好/字典/日志）
biz_ = 业务对象（由业务产生、有业务流程：任务、项目、订单…）
```

- **新业务对象一律 `biz_`**；平台能力（含「系统级」的配置、日志、文件、偏好、字典）才用 `sys_`。
- 判不准时问自己一句：**这张表的行是「人做业务做出来的」还是「平台自己维护的」**。前者 `biz_`，后者 `sys_`。
- **历史遗留（标注，不改名）**：C 批次的 `sys_announcement` / `sys_help_doc` / `sys_change_log` 已上线，
  改名要同时动迁移 + 后端 + 前端 + 权限码，风险远大于收益 —— 视为历史遗留，**保持原名**。
  后续新增同类业务对象（如「项目」「订单」）按判据用 `biz_`，不要跟这三张表对齐。


### 1.2 注释与文档（强制）
- 公共函数 / 结构体 / Trait 必须 `///` 文档注释（功能 / 参数 / 返回值 / 异常）；每个结构体字段必须有注释；注释语言**中文**。
- **杜绝隐式错误忽略**：禁止 `unwrap()` / `expect()`；序列化失败必须传播，禁止静默写空串。
- 命名清晰，禁止 `tmp / var / data` 类无意义命名。

### 1.3 错误处理（强制）
- 错误出口三名字：handler `ResResult<T>`、model `DbResult<T>`、启动/插件/任务 `nik::Result<T>`。
- handler 内 `DbError / io::Error / nik_core::Error` 直接 `?`；仅在需补充中文上下文时用 `utils::db_error(e, "上下文")`，**不要**写多余 `.map_err(ApiError::internal(...))`。

### 1.4 SQL 与注入防护（强制）
- 动态 SQL 一律用 `sql!` 宏的 `#if / #and / #or`，**绝不字符串拼接**；宏插值自动参数化。
- 动态表名 / 主键 / 列名必须经 `validate_identifier` + `quote_identifier` 校验引用，或改用 `enum` 在类型层杜绝注入。

### 1.5 依赖铁律（强制）
- `Cargo.toml` 只声明 `nik`（必要时 `nik-utils`）；**禁止**写 `nik-db` / `nik-db-core` / `nik-web` / `nik-config`。
- 业务代码统一 `use nik::prelude::*`；加能力只改 `features = [...]`。

### 1.6 迁移（强制）
- 文件名 `V{n}__{Name}.up.sql` / `.down.sql`（4 位补零）；种子 `S__{Name}.sql`。
- 基础版最大 `V0017`；**二开业务从 `V0020` 起**编号。
- 已应用迁移指纹校验不可改：演进只加新版本，不回改历史。
- 建表三段式：建表 → `COMMENT ON` → 索引（索引不单独占版本）。
- 软删表唯一列一律用**部分唯一索引** `... WHERE deleted_at IS NULL`，删除后可重建同名。

#### 1.6.1 菜单（sys_menu）迁移规范（强制，2026-11-08 · 卡 MENU-FIX-1 / MENU-FIX-2）

`sys_menu` 有两列最容易混淆，写反了侧栏就歪：

| 列 | 用途 | 规范 |
|---|---|---|
| `name` | 唯一标识 / 权限码关联 | 简短英文或中文，**不要长句**；已有 `business:erp:report:xxx` 这类编码形式属历史遗留，**新增一律用短名** |
| `title` | **侧边栏显示名** | **2-6 个字的菜单名**，名词短语，不带标点、不带说明、不带章节引用 |

`title` 的硬顶是 **12 字**（由 `scripts/verify/menu_invariants.sh` ⑥ 断言守）；12 只是给少量正常偏长业务名留的余量，**不是目标值**。

`icon` 必须是 **TDesign 图标库里真实存在的名字**（`menu_invariants.sh` ⑧ 断言，2026-11-09 · 卡 t_595098fe）：
- 只允许 `^[a-z0-9][a-z0-9-]*$`（`cart`、`file-add`、`chart-pie`）；不许大写、空格、换行。
- 名字不存在时 `<t-icon :name>` 渲染**空节点**，侧栏那项就没图标，而且 `icon` 非空所以组件里的
  `folder`/`app` 兜底不触发 —— **不报错、不告警，只能看界面才发现**。`shopping-cart` 就是这么
  在 dev/生产各躺了一轮（V0170 只修了 dev 的 `purchase-order`，生产那条 path 是 `purchase`，V0353 才补上）。
- 拿不准就先查：`ls frontend/node_modules/tdesign-icons-vue-next/esm/components/<名字>.js`
  （或看 `frontend/src/components/IconSelect/icons.ts` 的 `ICON_NAMES`，前端图标选择器同一份清单）。
- 迁移里改 icon 要**按 path 精确覆盖 prod/dev 两种写法**（同一逻辑菜单可能有两条不同 `path`，
  见 V0353 的 `path in ('/business/erp/purchase','/business/erp/purchase-order')`）。

**禁止**：
- ❌ 把功能说明写进 `title`（例：`即时 / 月末汇率维护 + 按月批量录入（ARCH-7 §15.6.3 ②）`）
- ❌ 在 `title` 里引用 ARCH 章节号 / 卡号（`P2-01`、`§15.6.3`）
- ❌ 用箭头 / 斜杠 / 括号堆砌流程（`选入库单带明细 → 审批 → 库存回冲`）

**功能说明放哪**：
- 有 `description` 列 → 放那儿
- 没有 → 写进 `docs/manual/` 对应章节
- 前端需要提示 → 用 tooltip（从 description 读），不要塞 `title`

**同一父节点下 `sort_order` 必须唯一**（`menu_invariants.sh` ⑦ 断言，口径：`menu_type=2`）：
- 迁移里插同目录多个菜单时，间隔 10 递增（10/20/30…）
- 后续插入用中间值（15/25）或末尾递增
- 改完跑 `bash scripts/verify/menu_invariants.sh <库>` 确认（⑦ 红了说明顺序会随行序漂移）

**改历史菜单只许新开迁移**：迁移体内只写幂等的 `UPDATE sys_menu SET … WHERE …`（带 `AND title <> '新名'` 之类的条件），**不回改历史迁移**（指纹校验会炸）；交付前在迁移末尾补 `DO` 自检块（点名行 title / 全库 `title≤12` / 同父 sort 无重复），让新环境跑首次迁移时就暴露问题，而不是等上线后看侧栏。

**校验 SQL（提交前自查，两个查询都应为 0 行）**：

```sql
-- title 过长（menu_type 1/2 = 侧栏真正显示的两层：目录 / 页面）
SELECT path, name, title, length(title) FROM sys_menu
WHERE deleted_at IS NULL AND menu_type IN (1,2) AND length(title) > 12;

-- sort 重复
SELECT parent_id, sort_order, count(*) FROM sys_menu
WHERE deleted_at IS NULL AND menu_type = 2
GROUP BY 1,2 HAVING count(*) > 1;
```

`icon` 名是否合法**纯 SQL 表达不了**（要比对图标库清单），直接跑断言：

```bash
bash scripts/verify/menu_invariants.sh <库>   # ⑧ icon 名合法 必须是 0 ✅
# 只看 icon 那一层（含坏名+path 明细）：
#   ⑧ 红了就照明细改迁移；「⏭ 跳过」说明本机没有图标库，别把它当通过
```

**已知边界（不在本条规范内，别顺手改）**：
- `menu_type=3`（按钮权限点）不进侧栏，`title` 不受 12 字限制；但它的长句会污染「角色-菜单」授权树（145 实测 155 条 >12 字、最长 73 字），属另一件事，另开卡处理。
- 跨类型同 `sort_order`（同父的目录 vs 页面）不在 ⑦ 范围（145 实测顶级 1 组：`通用底座`(mt=1) / `合同管理`(mt=2) 同为 75）。
- 反面样本与修复记录：`docs/evidence/20261108-menu-fix1/README.md`（V0335：25 条 title 收成 2-6 字 + 6 行 sort 重排、5 组撞车归零）。

### 1.7 路由与权限（强制）
- 路由宏路径**不含** `/api` 前缀（由 `[router] prefix` 注入）。
- 权限码三段式 `{模块}:{资源}:{动作}`，与 `sys_menu.auth_code` 和 `#[nik::permission(...)]` 三处一致。

#### 1.7.1 权限码前缀判据（2026-10-29 设计修正 A · 修正 6）

```
business: = 终端用户日常可见/使用的功能
system:   = 仅管理员配置的平台能力
support:  = 开发者/运维工具
```

- 判据只看**谁用**：员工每天点的用 `business:`；只有管理员在后台配置的用 `system:`；排障/运维工具用 `support:`。
- **历史不一致（标注，不迁移）**：`system:help:*`（帮助文档，员工日常要看）**本应是 `business:help:*`**。
  该权限码已授权到角色（`sys_role_menu`），迁移要么批量 UPDATE `sys_menu.auth_code`（需专门窗口评估），
  要么两套码并存，风险大于收益 —— **保持现状，标注为已知历史不一致**，**新功能按判据起名**。
- 复核过的正例：`business:announcement:*`（员工看公告）✅、`business:task:*`（员工用任务）✅、
  `system:change-log:*`（管理员查审计）✅、`system:user:*`（管理员配账号）✅。

### 1.8 事务安全（强制）
- 用 `db().transaction(|tx| async move { ... })` RAII 闭包；返回 `Err` 自动回滚，绝不让未提交事务的连接归还连接池。

### 1.9 分层（强制）
- 每模块四件套 `mod.rs + handler.rs + dto.rs + model.rs`；**不设 service 层**；二开业务放 `business/`，不侵入 `system/` / `support/` 底座。

### 1.10 主数据名称与快照（强制，2026-11-05 · 卡 P2-7）
- **关联 / 过滤 / 汇总 / JOIN 一律用 `id`**；禁止用名称列（`supplier_name` / `short_name` / `party_b_name` …）做 `JOIN` / `WHERE` / `GROUP BY`。
- **列表 / 报表 / 导出显示现值**（按 `id` 关联主档）；主档已删或查不到时回落到单据自己的快照名，**不得回落 uuid**。
- **快照只在两处出现**：① 冻结文书（合同签约名 / 资产卡 / 审批单 / 凭证科目名）；② 详情页与现值**并列展示**（范式：合同详情「乙方」+「签约时乙方快照」）。
- **快照永不修改**（改历史快照 = 销毁审计证据）；快照与现名的偏差由巡检 `DI-26` 只报不修（AP-8）。
- **简称只用于检索与导入**，不得出现在单据 / 报表 / 导出，也不得代替全名参与比较。
- 口径全文与盘点表：`docs/architecture/P2-7-供应商名口径盘点.md` §3（S1–S6）。

### 1.11 凭证摘要 / 业务单据号（强制，2026-11-09 · 卡 E2E-FIX-5）
- **凭证摘要（单头 + 每条分录）里禁止出现 UUID**：实体引用一律写名称，取名字走
  `erp::form_snapshot::{customer_name, supplier_name}` + `voucher::party_label(...)`
  （名字查不到退化成 `客户已删除(前 8 位)`，绝不回落整段 36 位 id）。反例（演练实测）：
  `收款 RC-20261109-000001 客户 01a1bdda-4947-…`。
- **`source_no` ≠ 业务单据号**：`source_no` 是「`source_id` 那张单的单号」（记账依据 / 子单据），
  `source_doc_no`（V0357）才是「用户手里那个业务单号」。「一张业务单据 → 多张凭证」的
  **退货**过账必须显式传 `PostVoucher.source_doc_no = 退货单号`，否则按退货单号查凭证 0 行。
  其余路径不传即可（落库按 `COALESCE(source_doc_no, source_no)` 兜底）。
- 查询面：`GET /business/erp/voucher/page?source_doc_no=SR-…`（精确）；关键词
  `voucher_no=` 同时模糊匹配 `source_no` 与 `source_doc_no`。红冲凭证 **继承** 原凭证的
  `source_doc_no`（红冲后按业务单号仍能查到两张）。

### 1.12 ERP 接口出参口径（强制，2026-11-09 · 卡 E2E01-FIX-4）

**单据类接口（返回「一张单 + 明细」的）一律三段式：**

```json
{
  "code": 0,
  "data": {
    "header": { },   // 单据主表（单头）—— 一个对象
    "items":  [ ],   // 单据明细 —— 一个数组（没明细给 []，不给 null）
    "meta":   { }    // 其他附属信息 —— 永远存在，最差是 {}
  }
}
```

- `meta` 的固定键是审批实例三元组：`instance_id` / `instance_no` / `flow_status`
  （`biz_flow_instance.status`：`PENDING`/`APPROVED`/`REJECTED`/`CANCELLED`/`WITHDRAWN`）；
  其余按接口自取（`merged_count` / `quote_count` / `can_to_po` …），**平铺**进 `meta`，不再套一层。
- **大体量附属数据不进 `meta`**：报价数组 / 比价表这类留在顶层原位置，`meta` 只给计数
  （`quote_count` / `comparison_count`）。理由：不为统一口径把同一份数组下发两遍。
- **后端唯一定义处**：`backend/src/business/erp/doc_shape.rs::DocMeta`；
  **前端唯一定义处**：`frontend/src/api/business/erp/doc-meta.ts::DocMeta`。别在别处另抄一份。

**兼容期规则（只做加法）**

1. 老字段（`order` / `head` / `purchase_order` / `lines` / `requisition`）**一律保留**，与新字段
   在同一份响应里并列下发 —— 删字段是破坏性变更，必须单独规划 + 前端全量验证。
2. 新旧字段**必须同源**：由 DTO 的 `XxxRes::new(...)` 一次 `clone` 出来，**禁止**两处分别赋值
   或两次查询。每个被统一的 DTO 都有 `#[cfg(test)]` 用例把 `header == 旧字段`、`items == 旧字段`
   钉住（`doc_shape_tests.rs`）。
3. 新接口直接只用三段式，**不要**再造 `xxx_detail` / `data` / `content` 之类的新包裹名。
4. 前端读新字段（`header` / `items` / `meta`），旧字段标 `@deprecated` 只为兼容保留。

## 二、前端（Vue 3 + TS）

### 2.1 API 路径（强制）
- 所有请求路径**写全 `/api/...`**（如 `/api/business/article/page`）；漏前缀命中 SPA fallback 返回 HTML，导致「响应体格式不符合统一响应规范」。

### 2.2 TDesign Grid（强制）
- 12 列制：`t-col-xl-2`=一行 6 个、`-xl-3`=一行 4 个；`t-col-xs-24` **不存在**（最大 `xs-12`）。

### 2.3 图标名（强制）
- `user-check` → `user-checked`、`speed` → `rocket`；用错名渲染空白。

### 2.4 类型与后端对齐
- 字段命名与后端 DTO 严格一致（`created_at`、`is_locked` 等）；可空文本列后端下发空串，前端不重复判 `null`。

### 2.5 权限码不要魔法字符串
- 页面级权限放 `router` 的 `meta.permission`；按钮级用 `v-privilege="'xxx:xxx:xxx'"` 指令，基于 `userStore.hasPermission`。

### 2.6 样式用主题变量
- 业务样式引用 `theme.less` 的 `--app-*` 变量（主色 / 渐变等），不写死色值，明暗主题自动跟随。

## 三、提交前检查（必跑）

```bash
# 后端
cd backend && cargo fmt && cargo clippy -- -D warnings && cargo check
# 前端
cd frontend && pnpm typecheck
# 或一键： bash scripts/check.sh
```
- clippy `-D warnings` 会把 `unwrap/expect`、未使用导入等直接升级为错误。
- 改完配置后用 `cargo run -- print-config` 核对生效，避免 TOML 语法错误静默回退全默认。

### 3.1 机械强制：`.githooks/pre-push`（2026-11-09 起）

光靠「记得跑」拦不住 —— 实测 HEAD 上 fmt / clippy 红着照样推得上去。所以编译期门禁
现在挂在 **push 前**，不再依赖人的记性：

| 钩子（仓内版本化，`.githooks/`） | 时机 | 跑什么 |
|---|---|---|
| `pre-commit` | 提交 | 密钥/口令扫描（`scripts/secret-scan.sh --staged`）+ 库存三本账唯一写入口闸 |
| `pre-push` | 推送 | `cargo fmt -- --check`、`cargo clippy --all-targets -- -D warnings`、`pnpm typecheck`（有 `frontend/node_modules` 时） |

安装（每个克隆执行一次；本仓库已设置 `core.hooksPath`）：

```bash
git config core.hooksPath .githooks
git config --get core.hooksPath      # 应输出 .githooks
```

绕过（仅限紧急，且必须在卡内写明理由）：`SKIP_PREPUSH=1 git push` /
`SKIP_PREPUSH_TYPECHECK=1 git push`。pre-push **不跑** `cargo test` / 真库用例 /
ERP 不变量 / 快照巡检 —— 那些要库、要几分钟，仍然归 `bash scripts/check.sh`
（`CHECK_WITH_DB=1`）与 CI；push 前这道只保证「推上去不会因编译期门禁变红」。
