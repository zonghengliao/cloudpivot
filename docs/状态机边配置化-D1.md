# 状态机边配置化（D1 · 流程全配置化 阶段 3）

> 实现：`backend/src/business/shared/state_machine.rs`
> 迁移：`backend/migrations/business/V0204__flow_state_edge.{up,down}.sql`
> 单测：`state_machine::tests::*`（17 条 D1 用例，真库事务内跑完回滚，库里零残留）
> 真机验收：`scripts/verify/d1_edge_config_e2e.py`

## 1. 为什么要有这一层，以及它的边界

用户原话是「流程全部用工作任务和审批流来实现，不要在程序中硬编码流程」。但**状态机**是账务的
最后一道物理闸：配错一条边就是「单据跳到非法状态 / 账务错乱 / 全公司流程停摆」。
所以这一步的定位不是「把边表搬进数据库」，而是**在硬约束之上加一层只能加严的配置**：

```
第 1 层  BASE_EDGES（代码，`Entity::base_edges()`）
         · 每个实体的边 + 每条边的 mandatory / 默认文案 / 是否必须给原因
         · 永远存在，配置删不掉；这是安全底线（作废必须能回冲、审批必须能落地）

第 2 层  biz_flow_state_edge（表，V0204）
         · 只能从 BASE_EDGES 里挑子集
         · 可加：enabled=false（禁用 optional 边）、requires_reason、label、auth_code
         · 不可加：BASE_EDGES 里没有的边、改方向、任意跳任意

第 3 层  运行时合并 `effective_edges()` / `edge_resolution()`
         · 有效边 = BASE_EDGES ∩ 配置 ∪ 硬约束边
         · 读失败 / 表不存在 / 数据脏 → **退化到 BASE_EDGES + WARN**（fail-safe）
```

**真相永远在代码里。** 配置只是「在合法边里挑 + 加约束」，不是第二份边表。

## 2. 三条铁律怎么落成代码

| 铁律 | 落点 |
|------|------|
| 配置只能在合法边里挑 | `upsert_edge_config` 里 `entity.base_edge(from, to)`，找不到 → 400（文案直接列出允许的边）；加载期遇到 BASE 里没有的 `(from,to)` → 忽略 + WARN |
| 配置只能加严 | `requires_reason` 取 `BASE ⊙ 配置` 的「或」；`auth_code` 只能追加；`enabled=false` 只对 `optional` 边生效（mandatory 边写了也无效 + WARN） |
| 加载失败静默退化 | `edge_resolution()` 永不返回 `Err`：读不到 → `BASE_EDGES` + 一条 WARN（同一条 60 秒内只打一次，避免刷爆日志） |

**只许加严，不许停摆**：合并后还有一道护栏 —— 任何一个 `from` 状态如果失去所有出边，
整份配置作废并退回 `BASE_EDGES`（否则单据会永久卡死）。

## 3. 可选边（能被禁用的）只有 4 条，而且有明确判据

可选边的判据：**关掉它之后，同一状态还有别的路能走，且等于要求走更严的那条路**。

| 实体 | 边 | 默认文案 | 关掉意味着 |
|------|----|----------|------------|
| `STOCK_IN` | `DRAFT → POSTED` | 直接过账 | 必须走「提交过账审批 → 审批通过过账」 |
| `STOCK_IN` | `PENDING_POST → CANCELLED` | 审批中作废 | 必须先打回草稿再作废 |
| `PURCHASE_ORDER` | `SUBMITTED → CLOSED` | 直接关闭 | 不收货就不能关闭（卡面点名的场景） |
| `STOCK_OUT` | `DRAFT → POSTED` | 直接过账 | 必须走「提交待过账 → 过账」 |

其余 48 条边全部 `mandatory`：主链（提交 / 审批落地 / 过账 / 收货收口）、撤销回位
（`PENDING_CANCEL → POSTED` / `PENDING_CANCEL → OPEN` / `SUBMITTED → DRAFT`）、
红冲与反结账（`POSTED → CANCELLED` / `CLOSED → OPEN` / `CLOSED → NOT_CLOSED`）、
收货作废回退（`RECEIVED → PARTIAL_RECEIVED`，D4 的「老板再也收不进这批货」就是缺这条边）。
把它们禁掉不是加严而是停摆（审批回调 500 / 账不可纠正），所以标 `mandatory`：
**配置写了禁用也会被忽略，并打 WARN**。

`optional_edges_are_exactly_the_documented_four` 这条单测把上表钉死：想多开放一条可禁用的边，
必须先改这张表 —— 免得「今天顺手放开一条」变成控制面悄悄变大。

## 4. 改配置要过三道门（SUPER_ADMIN + 二次确认 + 留痕）

```rust
state_machine::upsert_edge_config(&ex, &claims, &EdgeConfigPatch { .., confirm: true }).await?;
state_machine::delete_edge_config(&ex, &claims, "PURCHASE_ORDER", "SUBMITTED", "CLOSED").await?;
state_machine::list_edge_config(&ex, Some(Entity::PurchaseOrder)).await?;
```

1. **SUPER_ADMIN**：`claims.is_super_admin()` 或 `roles` 含 `SUPER_ADMIN`，否则 403
   （「能改状态机的人等于能放宽全公司的审批路径」）。
2. **二次确认**：`confirm = true` 必须显式给，否则 400。
3. **留痕**：每次写入/删除都往 `biz_status_log` 追加一行
   （`entity_type = 'FLOW_EDGE_CFG'`，只增不改），`reason` 里是「改前快照 → 改后快照」，
   例如 `改前 {enabled=true requires_reason=false label=(BASE) auth_code=(无)} → 改后 {...}`。

> 走**审批流**（改配置本身提交审批单）不在本卡：本卡先做「超管 + 二次确认 + 留痕」，
> 审批化留给后续卡（`biz_flow_state_edge` 的写入已经是唯一入口，接审批时不用改调用点）。

## 5. 运行时校验点只有一处：`transition` / `transition_if_changed`

`transition()` 的顺序：注册表核对（代码边表，防私放边）→ 自环 409 → **有效边判定**
（配置禁用的边在这里 409，文案点名「已被状态机配置禁用」）→ 必填原因（BASE ⊙ 配置）
→ 权限码（配置追加的 `auth_code`，令牌入口无码 403）→ 写 `biz_status_log`。

`auth_code` 的一个刻意选择：**内部路径（审批回调 / 定时任务，没有令牌快照）放行 + WARN**。
拦下来会让「审批通过 → 自动过账」的回调 500 —— 那是停摆，不是加严。
HTTP 入口（`&TokenClaims` → `Operator.auth`）一律按码判，超管短路。

## 6. 迁移号与表

- 卡面写「V0201」，**核对后发现 V0201 已被占用**（`V0201__erp_material_costing_moving_avg_only`），
  当前最大号 V0203，故取 **V0204**。
- 表结构照卡面，另加：`entity` 存活行索引 `idx_flow_state_edge_entity (entity) WHERE deleted_at IS NULL`。
- 唯一约束 `uk_flow_state_edge (entity, from_status, to_status)`：一条边只许一行配置；
  「删了再配」走 `ON CONFLICT … DO UPDATE SET deleted_at = NULL` 复活旧行，不需要第二条路径。
- **不种任何数据**：空表 = 行为与改动前逐字相同（全部使用 BASE_EDGES）。
- `down` 会先挡「还有存活配置」的情况（回滚 = 丢配置，必须有人确认），且**不动 `biz_status_log`**
  —— 配置变更的审计不在回滚范围。

## 8. 已知边界（本卡不做，但必须写清）

1. **前端按钮仍按 BASE 边显示**：`Entity::next_statuses()` / 各 DTO 的 `next_statuses` 字段读的是
   代码边表，配置禁用后按钮可能还在，点下去接口 409（卡面允许「被拒/按钮不显示」二选一）。
   要让按钮跟着配置走，需要一个「有效边」查询接口（后续卡）。
2. **状态机里的 `TASK` 实体不存在**：`biz_task` 的状态由 `task` 模块自己的判定推进，
   序列号 `biz_material_serial` 也有自己的状态模型；它们都不在 9 个 `Entity` 注册表里，
   所以不受本配置约束（表里写 `entity='TASK'` 会在合并期被当脏数据忽略 + WARN）。
3. **改配置走审批流**：未做（见 §4 末）。
