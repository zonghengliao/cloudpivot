# 新机器部署 · 纯迁移重建（保证菜单不乱）

> 版本：v1.0 · 2026-11-07
> 对应卡：MENU-03（t_e54be734）；上游：MENU-01 把菜单修正写进迁移（V0319/V0320）、MENU-02 做防回归断言（`scripts/verify/menu_invariants.sh`）
> 状态：**强制规程**——凡是要新开一个环境（新机器 / 新库 / 重建测试库），结构一律由迁移链生成

---

## 一、为什么要有这份规程

2026-11 出现过一次真实事故：145 测试环境侧栏「乱」——`/system/data-scope`、`/system/field-mask`、
`/system/role-mutex` 三条页面变成顶级孤立项，`/system/change-log` 挂到了「内容」目录下。

根因不是种子写错，而是**修正是直接 `UPDATE` 生产库做的，从未落进任何迁移**。
谁要是从生产库 `pg_dump | psql` 导一份到新机器，就把这套「别人手工改过的结构」一起搬过去；
反过来，直接跑迁移的新机器拿到的是另一套结构。两个环境从此**结构分叉**，再也没法靠比对
判断"新环境对不对"。

所以规程只有一句话：

> **新环境的结构只能来自迁移链（`backend/migrations`），不能来自任何一份别人的库。**

---

## 二、新机器部署（保证菜单不乱）

1. 装依赖 / 克隆代码 / 配置 env（参考现有步骤：Rust 1.94.1+、PostgreSQL ≥ 14、Redis，
   `backend/` 里 `cargo build`，`/etc/cloudpivot/cloudpivot.env` 配 `NIK_DATABASE_*` 与三把密钥）
2. `bash scripts/setup_new_env.sh <库名>`（例：`bash scripts/setup_new_env.sh cloudpivot_fresh`）
3. 验证：`bash scripts/verify/menu_invariants.sh <库名>` → 必须全绿
4. 启动服务

**禁止**：直接 `pg_dump | psql` 从别的机器复制库——那样会带上别人的手工修改，
导致各环境结构分叉（145 菜单乱就是这么来的）。

---

## 三、`scripts/setup_new_env.sh` 到底做了什么

```
bash scripts/setup_new_env.sh <新库名>          # 库已存在时拒绝，防误删
RECREATE=1 bash scripts/setup_new_env.sh <库名> # 确认可以删才用
```

| 步 | 动作 | 失败时 |
|---|---|---|
| 1 | 建空库（当前账号无 `CREATEDB` 时自动借 `postgres` 账号，owner 仍是业务账号） | rc=2 |
| 2 | **起一次真实后端实例**，让迁移引擎按 `schema_migrations` 跑完全部迁移 + bootstrap | rc=1，打印启动日志尾部 |
| 3 | 迁移完整性对账：`schema_migrations` 的 `versioned`/`seed` 条数必须等于仓库里的 `V*__*.up.sql` / `S__*.sql` 数量，且无失败 | rc=1 |
| 4 | 跑 `menu_invariants.sh <库>` —— 7 条断言必须全绿 | rc=1 |
| 5 | 打印菜单树摘要（总数 + 顶级菜单清单） | — |
| 6 | 结构比对 ①：新库 vs **生产结构快照**；②：新库 vs **迁移链基线**（`--strict`） | rc=1 |

> 为什么第 2 步要起实例而不是 `psql -f` 逐条 apply：迁移引擎除了建表还写 `schema_migrations`、
> 跑 seed 与 bootstrap（角色 / 超管 / 字典预热）。手写 apply 会漏掉这一档，得到的库"看起来能跑"、
> 实际少东西，正是"结构分叉"的另一种来源。

### 结构比对的口径

只比 **path / parent_path / menu_type**（`scripts/verify/menu_structure_dump.sh` 的归一化导出）：

- 不比 `name` / `title` / `sort_order` / `icon` / `is_visible` —— 它们是业务数据或审美差异，不会让侧栏"乱"；
- 孤儿父节点导出为 `-MISSING-`、父 path 为空的导出为 `~NULLPATH~`、自身 path 为空导出为 `~NULL~`，
  **不让结构缺陷被 `coalesce` 静默抹平**；
- 已论证过的**等价表示**登记在 `scripts/verify/baseline/menu_struct_equiv.tsv`（每条带理由 + 出处），
  比对前对两侧同时归一；输出永远同时打印「原始差异」和「归一后差异」，并统计每条规则命中几行。
  `--strict` 要求原始差异也为 0，用来审计"这条规则是不是已经不需要了"。

当前登记表里正好两条，都属于**不是缺陷**的表示差异：

| 规则 | 内容 | 为什么不是缺陷 |
|---|---|---|
| `path` | `/business/erp/purchase` ↔ `/business/erp/purchase-order` | 同一逻辑菜单的两种路径：`frontend/src/router/index.ts:545-546` 是 `path='business/erp/purchase-order'` + `alias=['business/erp/purchase']`，都指向 `views/business/erp/purchase/index.vue`。seed（V0141）用 `purchase-order`，144 生产存量是别名 `purchase`（V0319 已裁定不 INSERT 第二条） |
| `parent` | `/business/erp/seq` 的父：`/business/erp/finance-mgmt` → `/business/erp/master-data` | MENU-01B（`V0320__seq_menu_move_to_master_data`）判定「单号序列」属配置类，移到「基础数据」。145/新库已跑 V0320，144 生产部署该迁移后这条规则自然不再命中（脚本会打 ⚠ 提示清理） |

### 基线文件（都随仓库提交）

| 文件 | 是什么 | 什么时候更新 |
|---|---|---|
| `scripts/verify/baseline/menu_structure_baseline.txt` | **迁移链基线**：一份纯迁移重建得到的 canonical 结构（408 行） | 迁移里**故意**改了导航结构时，重新生成并写清原因 |
| `scripts/verify/baseline/prod_menu_structure.txt` | **生产结构快照**（md5 + 408 行，来源 144 `cloudpivot`） | 生产做了菜单结构变更后重新导出 |
| `scripts/verify/baseline/menu_struct_equiv.tsv` | 等价表示登记表 | 只登记"同一菜单的另一种写法"；**不是**用来掩盖手工改库的 |

重新生成基线：

```bash
bash scripts/verify/menu_structure_dump.sh <库名> \
     scripts/verify/baseline/menu_structure_baseline.txt
```

生产机导出快照（生产库只应在生产机本机连）：

```bash
bash scripts/verify/menu_structure_dump.sh cloudpivot \
     scripts/verify/baseline/prod_menu_structure.txt
```

## 五、日常怎么用（别让结构再次分叉）

| 场景 | 做法 |
|---|---|
| 发现某环境菜单不对 | 先 `menu_invariants.sh` 看是哪条断言红，再 `menu_struct_compare.sh <库> <基线>` 看差异行 → **补一条幂等迁移**把修正固化，绝不手工改完就算 |
| 生产做了菜单调整 | 补迁移 → 重新导出 `prod_menu_structure.txt` → 看 `menu_structure_baseline.txt` 是否需要同步（迁移链产物变了才变） |
| 部署后自检 | `test_deploy.sh` 第 ⑦ 步 / `deploy_check_v5.sh` 第 ⑦ 步已挂 `menu_invariants.sh` |
| 想严格审计等价规则 | `bash scripts/verify/menu_struct_compare.sh <库> <对照> --strict` → 原始差异非 0 即 rc=1 |

三个脚本的退出码统一：`0` 通过 ｜ `1` 有违规/差异 ｜ `2` 连库或参数问题（**把基础设施问题与结构问题分开**，
免得连不上库就去建"结构坏了"的卡）。
