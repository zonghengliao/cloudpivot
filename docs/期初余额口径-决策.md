## 二、为什么「审核」这条不能简单补（这是本次决策最关键的一段）

「现在录入人 = 记账人，与其它单据制单≠审核不一致」这个担忧是**对的，但补法不能是给期初加一个 `AUDITED` 态**。四条硬理由：

### 1. 报表取数只认 `POSTED` —— 加审核态 = 期间报表期初数变 0

- 总账 / 余额表 / 三张报表全部 `WHERE status = 'POSTED' AND deleted_at IS NULL`（`report.rs:900`、`income_statement.rs:64`）。
- 期初凭证若落 `DRAFT`（待审核），**资产负债表「期初数」直接为 0**，`期末 = 期初 + 本期` 立刻不成立，资产 ≠ 负债+权益。
- 要让「未审核期初不进报表」成立，就必须再加一道「未审核期初**不允许结账**」的闸，否则客户能看到一张**自相平衡但总体不平**的报表 —— 比现在危险得多。

### 2. 自动凭证一律直接 `POSTED`，**复核的对象是单据、不是凭证**（本仓已定型）

| 单据 | 复核形态 | 依据 |
|---|---|---|
| 手工凭证 | `DRAFT → AUDITED → POSTED` 双人复核链，**禁自审**（403 / `65019`） | `state_machine.rs:497-500`、`voucher_write.rs:463` `check_self_audit`、单测 `p4a_self_audit_is_forbidden` |
| 入库单 | **没有 `AUDITED` 态**：`DRAFT → POSTED` 或 `DRAFT → PENDING_POST`（走**审批流**）→ `POSTED` | `state_machine.rs:364` `STOCK_IN_EDGES`（10 条边，无 `AUDITED`） |
| 出库单 / 盘点单 / 调拨 | 同上：`DRAFT → POSTED` + `CANCELLED` 系，复核走审批流 | `state_machine.rs:132` / `:169` / `:436` |
| **期初（本卡）** | 无单据、无状态机实体，录入即生成 `POSTED` 自动凭证 | `opening.rs:718` / `:806`；`state_machine.rs` 里**没有** `OPENING_EDGES` |

⇒ 「期初凭证直接 POSTED」**不是期初的例外，而是本仓自动凭证的统一口径**（自动凭证单测明确断言「自动凭证必须直接已记账」，`voucher.rs:3138`）。真正的不一致不是「期初少了审核」，而是**卡面把一个「单据级审批」概念写成了一个「凭证级状态」概念**。

### 3. 期初凭证没有「草稿」可复核 —— 它的生成前提就是「借贷已平衡」

- 保存期初前 `ensure_balanced` 已拦死不平衡（`opening.rs:1012`，400 + 点名差额与科目；实测 `round1.txt` 1.1 返回 `balanced: true`）。
- 也就是说：**期初凭证从存在的那一秒起就是一张合法的、已平衡的凭证**。「审核」在这里能做的只是「再看一眼数字」，而这正是**试算平衡表**的职责，不需要一个新的状态位。

### 4. 期初真正的复核闸门已经存在两道（客户可执行、审计可留痕）

| 闸门 | 语义 | 依据 |
|---|---|---|
| ① 期间结账 | 结账后整页只读（再录 409），期初数被**冻结**进账本 | `opening.rs:372` `lock_period`（`:391` 期间须 `OPEN`）；单测「结账后是状态冲突(409)」`:2122` |
| ② 试算平衡表 / 资产负债表期初核对 | `借=贷` 断言 + 期初数对旧系统数 | `report_check.txt:3` `"balanced": true`；资产负债表期初列 |

⇒ **结论（问题 2）：不引入「审核」态。** 期初的复核 = 「人工核对 + 期间结账冻结」，与本仓自动凭证口径一致。
**何时改**：当客户审计**明确要求**「期初必须有第二人复核的签字/留痕」时，正确做法是**把期初录入接进审批流**（复用入库单的 `PENDING_POST` 模式：状态由审批驱动、凭证在审批通过时才生成），**不是**给凭证加 `AUDITED` 态。已登记 `RP-2026-004`（见 §四.5），触发前不做。

## 三、导入：要，但按「触发制」做（不在本迭代）

### 3.1 痛点是真的（已量化，不是猜）

| 事实 | 数据 | 依据 |
|---|---|---|
| 科目总数 / **可录末级科目** | 65 行 / **62 行**（前端下拉只显示 `is_leaf`） | 实测 `cloudpivot_st9`、`cloudpivot_ri8`（迁移至最新 198 条）：`select count(*) filter (where is_leaf=1), count(*) from biz_account` → `62\|65`；前端过滤 `opening/index.vue:561` `.filter(row => row.is_leaf)` |
| 录入交互 | **逐行**「选科目 + 填借方/贷方 + 备注」，行由用户点「添加科目」逐个加，**不是整表铺开填** | `opening/index.vue:60-140`（`.grid-row` + `addAccountRow()`） |
| 迁移期初的典型规模 | 客户从旧系统迁移，科目期初通常 **30–100 行**、库存期初 **几百 SKU** | 业务常识，非实测 |
| 折算 | 100 行 = 100 次「添加科目」+ 100 次带筛选的科目下拉选择；库存期初每行还要先选物料再选仓库 | 由上面交互推导 |

⇒ 结论（问题 1）：**要**。这不是「锦上添花的批量功能」，而是**客户上线的第一件事**（老系统迁移）里最重的人工步骤。

### 3.2 但成本不是「重写一个导入」，因为导入框架已经在仓里（这是关键发现）

| 已有能力 | 位置 | 对本需求的意义 |

| 6 个 ERP 主数据导入（供应商/物料/单位/会计科目/仓库/库位）已上线 | `impexp/builtin/mod.rs:36-46` | 有成熟范本可抄（`master_data/account.rs` 484 行含单测） |

1. `persist` 返回 `DbError`，而 `save_opening_in` 返回 `ApiError` → 需要**一次错误适配**（或把校验提到 `validate_row`，把平衡校验留在 `persist`）。
2. `batch_size` **必须 = `max_rows`**（整批一个事务、`allow_partial=false`）：借贷平衡是**整批约束**，一旦按批切开，第二批单独看永远不平。
