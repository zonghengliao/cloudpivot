# 运维规程 — 日志切割与保留（30 天）

**一句话**：云枢的日志分两处落，**一处 logrotate、一处 journald**，两套配置缺一不可；
落地件在 `scripts/ops/logrotate/`，一键装 + 一条命令就能验收。

- 落地卡：P3-15「日志按天切割 + 保留 30 天」
- 机器：145（测试）/ 144（生产）—— 2026-11-15 已双双落地并验收
- 证据：`docs/evidence/2026-11-15-p315-logrotate/`

---

## 1. 口径：为什么是两套配置

| 日志 | 实际落点 | 谁能切 | 配置文件 |
|:--|:--|:--|:--|
| 运维/告警/部署脚本日志 | `/var/log/cloudpivot/*.log`（cron 用 `>>` 追加） | **logrotate** | `/etc/logrotate.d/cloudpivot` |
| **应用进程日志** | **journald** | **journald** | `/etc/systemd/journald.conf.d/cloudpivot-retention.conf` |

三个 systemd 单元（144 的 `cloudpivot`、145 的 `cloudpivot-base` / `cloudpivot-test`）全是
`StandardOutput=journal` `SyslogIdentifier=cloudpivot*` —— **应用日志根本不在文件里**。
所以：

> ⚠️ 只写 `/var/log/cloudpivot/*.log` 的 logrotate 片段，「应用日志保留 30 天」是**空的**：
> 匹配不到文件，`missingok + notifempty` 让它安静地什么都不做。
> 这就是第二份配置（journald 保留期）必须存在的原因，也是本卡落地时实测发现的偏差。

journald 默认**只按容量回收、不按时间回收**（无 `MaxRetentionSec`），所以「保留 30 天」必须显式配。

## 2. 两套配置的语义

`/etc/logrotate.d/cloudpivot`（源：`scripts/ops/logrotate/cloudpivot`）：

```
/var/log/cloudpivot/*.log {
  daily        # 按天（logrotate.timer OnCalendar=daily + RandomDelay ≤1h）
  rotate 30    # 保留 30 份归档 → .1 … .30，第 31 天滚掉最老
  compress     # 归档 gzip（.1.gz）
  missingok    # 路径无匹配不报错
  notifempty   # 空文件不切
  copytruncate # 不换 inode，写方无需重开文件
}
```

`/etc/systemd/journald.conf.d/cloudpivot-retention.conf`：

```
[Journal]
Storage=persistent
MaxFileSec=1day          # 按天切分 journal 文件
MaxRetentionSec=30day    # 超过 30 天的条目在轮转时删除
SystemMaxUse=2G          # 容量兜底，防 journal 吃满 /var/log
SystemMaxFileSize=128M   # 单文件上限
```

## 3. 装 + 验收（唯一入口）

```bash
# 安装 + 断言（幂等；内容没变就不重启 journald）

bash scripts/ops/logrotate/install.sh --host 172.18.10.144

# 只检查（巡检 / 上线前复核，不改动）
bash scripts/ops/logrotate/install.sh --host 172.18.10.144 --check

bash scripts/ops/logrotate/install.sh --host 172.18.10.144 --rotate
```

## 5. 验证过的语义（`--self-test`，12/12）

在临时目录用**同一份** conf 连切 32 天后实测：

- `rotate 30` → 恰好保留 30 份；`.30.gz` 在、`.31.gz` 不存在（不会越滚越多）；
- 内容对位：`.1.gz` = 第 32 天、`.30.gz` = 第 3 天，第 1/2 天已滚出 → **「保留 30 天」是真的**；
- `copytruncate` → 基文件仍在且清零；`compress` → `.1.gz` 解压完整；
- `notifempty` → 空文件不切；`missingok` → 路径无匹配 rc=0（不会让每日 cron 报错）；
- 重复执行幂等（清空后的基文件被 `notifempty` 跳过，不产生空归档）。

## 6. 边界与坑（读一次省一次排查）

1. **journald 保留期是整机口径**，不按服务隔离。`MaxRetentionSec=30day` 对 144/145 上
   sshd / nginx / cron / hermes 等所有写 journal 的进程同样生效。journald 不提供 per-unit 保留期。
2. **`copytruncate` 有微秒级丢行窗口**（copy 与 truncate 之间的写入）。故只切运维脚本日志，
   不碰业务事务日志（云枢业务日志本来也不落文件）。
3. **logrotate 只管 `.1..rotate` 号段**：手工塞进 `xxx.log.31.gz` 这类超号归档不会被自动清理。
   这就是 `--self-test` 用「连切 32 天」而不是「预置 35 份」验证的原因（后者是错的前提，实测会红）。
4. **别在线手改 `/etc/logrotate.d/cloudpivot`**：下次 install 会按仓库覆盖，且断言②永远红。
   改法：改仓库 → 先 145 `--check`（乐观红）→ install → `--check` 绿 → 再上 144。
5. **不在范围内**：`snapshot-audit.log.2026-11-12` 这种自管日期的归档（脚本自己 `mv`）、
   `/var/log/cloudpivot/hermes/*.log`（hermes 自管）——都不匹配 `*.log` 通配，保持原样。
6. **99（开发机）未纳入**：卡口径是 145/144；99 的 `/var/log/cloudpivot` 是 agent 工具链日志
   （`deploy-check.log` / `concurrency-guard.log` 等），有自管状态语义，要纳入得单独审计后再开。
   若确认要做：`bash scripts/ops/logrotate/install.sh --no-journald`（只切文件，不动整机 journald 口径）。

## 7. 排查表

| 现象 | 先查 |
|:--|:--|
| 没生成 `.gz` | `logrotate -d /etc/logrotate.d/cloudpivot`；基文件是否为空（`notifempty` 会跳过） |
| 归档不减少 / 越攒越多 | 是否有人手工塞了超 `rotate` 号的归档（第 3 条坑）；`--self-test` 复验语义 |
| 应用日志找不到 30 天前的 | `systemd-analyze cat-config systemd/journald.conf` 看 `MaxRetentionSec`；`journalctl --disk-usage` |
| journald 配置没生效 | drop-in 目录名必须是 `/etc/systemd/journald.conf.d/*.conf`；改完要 `systemctl restart systemd-journald` |
| `logrotate -d` 报 `error:` | 断言③直接暴露；先看是不是有人手改了线上文件（断言②会同时红） |
