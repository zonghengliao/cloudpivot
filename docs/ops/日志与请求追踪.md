# 日志与请求追踪（request_id / trace 贯穿）

> 对应评审 5.8「journald 结构化文本…无 trace_id / 无请求 ID 贯穿，跨服务定位靠时间戳」的
> 落地说明（NEAR-FIX-4 / N-4）。实现入口：`backend/src/middleware/request_context.rs`。

## 1. 一次请求的 ID 从哪来、到哪去

```
客户端（前端 axios / 网关 / curl）
   │  X-Request-Id: <可选>            ← 带了就复用（经校验），没带就由服务端生成 UUID v7
   ▼
middleware::request_context（链最外层）
   ├─ 校验客户端值：≤128 字节、只含 [A-Za-z0-9._:-]，否则丢弃改用 UUID v7
   ├─ 把最终 ID 写回**请求头** x-request-id      → 框架 RequestLog / 操作日志 / changelog 都取它
   ├─ 开 tracing span：request{request_id, method, path}
   └─ 回写**响应头** X-Request-Id               → 前端错误提示、运维按 ID 反查
   ▼
框架中间件链 → 认证 → handler → model → SQL → 下游调用
   （全部在 span 内，每一条日志都带同一个 request_id）
```

三个出口是**同一个值**：

| 出口 | 位置 | 用途 |
|------|------|------|
| 日志 | `spans[].request_id` / 文本格式的 `request{request_id=…}:` 前缀 | 还原一次请求的全部处理过程 |
| 响应头 | `X-Request-Id` | 前端展示给用户；运维凭它 grep |
| 数据库 | `operation_logs.request_id`、`sys_change_log.request_id` | 事后审计 join |

## 2. 日志长什么样

生产（`profile=prod`，`[log] format = "json"`）—— 三段真实输出（145 实测，取自
`docs/evidence/20261110-n4-request-id/03_grep_client_id.jsonl`）：

```json
{"timestamp":"2026-11-09T19:42:19.291716Z","level":"INFO","fields":{"message":"请求完成","method":"POST",
 "path":"/api/system/auth/login","status":200,"duration":"269ms","request_id":"n4-gw-20261110034219-1524434",
 "ip":"Some(\"127.0.0.1\")"},"target":"nik_web::middleware::request_log",
 "span":{"method":"POST","path":"/api/system/auth/login","request_id":"n4-gw-20261110034219-1524434","name":"request"},
 "spans":[{"method":"POST","path":"/api/system/auth/login","request_id":"n4-gw-20261110034219-1524434","name":"request"}]}
```

（框架访问日志：`fields.request_id` 不再是 `-`，与 span 里是同一个值）

```json
{"timestamp":"2026-11-09T19:42:19.025450Z","level":"DEBUG","fields":{"message":"executing statement s28 with parameters: [Text(\"admin\")]",
 "log.target":"tokio_postgres::query","log.module_path":"tokio_postgres::query","log.file":"…/tokio-postgres-0.7.18/src/query.rs","log.line":45},
 "target":"tokio_postgres::query",
 "span":{"method":"POST","path":"/api/system/auth/login","request_id":"n4-gw-20261110034219-1524434","name":"request"},
 "spans":[{"method":"POST","path":"/api/system/auth/login","request_id":"n4-gw-20261110034219-1524434","name":"request"}]}
```

（SQL：`sql_logging`/`RUST_LOG=debug` 时每条语句都在 span 内，可看到它属于哪一个请求）

```json
{"timestamp":"2026-11-09T19:42:19.292317Z","level":"INFO","fields":{"message":"close","time.busy":"272ms","time.idle":"5.32ms"},
 "target":"cloudpivot::middleware::request_context",
 "span":{"method":"POST","path":"/api/system/auth/login","request_id":"n4-gw-20261110034219-1524434","name":"request"},"spans":[]}
```

（span 收尾事件：`FmtSpan::CLOSE` 给出的 busy/idle，用于判断这次请求在各段的时间分布）

开发（`[log] format = "text"`）则是带 span 前缀的文本：

```
2026-11-10T03:44:12.713Z  INFO request{request_id=0199c8a1-… method=POST path=/api/system/user/page}: cloudpivot::system::user::handler: 请求完成 status=200 duration_ms=12
```

> **为什么 `request_id` 在 `span` / `spans` 里而不是 `fields` 里**：`tracing_subscriber`
> 的 span 字段由订阅者按 span 上下文输出（JSON 格式下是 `span` / `spans` 对象，文本格式下是
> 事件前缀）。请求内**每个**事件的 `fields` 是各调用点自己写的键，无法也不该由框架统一注入；
> 检索统一用 `grep <request_id>`（两种格式都能命中，且同一请求的命中行数 = 该请求的日志行数）。

## 3. 常用排查命令

```bash
# ① 按 request_id 还原一次完整请求（最常见：用户报障截图里有请求 ID）
journalctl -u cloudpivot --since "-2h" | grep 0199c8a1-7f3e-7b21-9d0e-0f1a2b3c4d5e

# ② 只看这次请求的 finish 行，拿状态码与耗时
journalctl -u cloudpivot --since "-2h" -o cat | grep 0199c8a1-… | grep 请求完成

# ③ 与操作日志 join（谁在什么时间改了什么）
psql -U <db_user> -d <db_name> -c \
  "SELECT created_at, username, operation, request_path, status_code, duration_ms
     FROM operation_logs WHERE request_id = '0199c8a1-…';"

# ④ 最近 1 小时最慢的 20 个请求
journalctl -u cloudpivot --since "-1h" -o cat \
  | grep '"请求完成"' | sed -E 's/.*"duration_ms":([0-9]+).*"request_id":"([^"]+)".*/\1 \2/' \
  | sort -rn | head -20

# ⑤ 客户端主动传 ID（跨服务串联时用同一个 ID 发下游）
curl -sH "X-Request-Id: gw-20261110-0001" https://<host>/health -D-
```

## 4. 前端（`frontend/src/api/request.ts` + `api/request-id.ts`）

- 每个 axios 请求由请求拦截器写 `X-Request-Id`（`crypto.randomUUID()`；**内网 http 无安全上下文时**
  退化为 `web-<时间戳36进制>-<随机串>`，后端同样采信）。
- 失败时 `ApiError.requestId` 取**响应头里那个值**（它才在服务端日志里），并追加到
  `message` 末尾：`操作失败（请求 ID：0199c8a1-…）` —— 仓内 175 处 `showError(err.message)`
  因此无需逐个改。需要纯文案时读 `err.requestId`。
- 没有响应（网络层失败 / 超时）时退回「我们发出去的那个」，用户仍可报上来。

## 5. 已知边界（别误判）

| 场景 | 说明 |
|------|------|
| SSE（`/api/business/notice/stream`） | 走 `EventSource` + `?token=`，浏览器不允许自定义头 —— 该连接的日志无客户端 ID（服务端仍生成自己的 ID） |
| 定时任务 / 启动钩子 | 没有 HTTP 请求，没有 request span；相关日志用任务名检索 |
| 框架 `RequestLog` 的 `request_id` 字段 | 来自请求头，由本中间件注入；若哪天把本层摘掉，框架侧会退回 `-`（`nik-web` 里 RequestLog 在 RequestId 之外层，取不到刚生成的值） |
| 客户端伪造 ID | 允许但受限：只接受 `[A-Za-z0-9._:-]{1,128}`，其余丢弃重生成 —— 防日志注入 / 头注入 |
| 跨域读取响应头 | 生产由 nginx 同源托管静态 + 反代 `/api`，JS 直接可读 `X-Request-Id`；**若将来前后端分域部署**，需要在 CORS 上把 `x-request-id` 加进 `Access-Control-Expose-Headers`（框架 `CorsConfig` 目前没有该键，属于改动 vendored `nik-web` 才会生效的范围） |
