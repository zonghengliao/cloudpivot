# 运维告警接入说明（NEAR-FIX-3 · 告警）

> 一句话：**指标**由后端每分钟采进 `/metrics`（`backend/src/task/metrics_sampler.rs`），
> **规则 + 通道**由 `scripts/ops/alert_check.sh`（cron 每 5 分钟）负责，
> 告警落 **ALERT.log + kanban 卡（assignee=laoliu）+ 飞书（有凭据才发）**。

评审 5.8 的原始缺口是「无指标、无告警规则、无外部告警通道」，三块分别对应下面 §§1/2/3。

---

## 1. 指标：`/metrics`

### 1.1 开关

`/metrics` 由编译期 feature `metrics-prometheus` + 运行期 `[metrics]` 提供，
**三个 profile 都已打开**（`config-prod.toml` / `config-test.toml` / `config-dev.toml`）：

```toml
[metrics]
enabled = true
path = "/metrics"
allow_ips = []      # 空 = 只允许本机回环（127.0.0.1 / ::1），不对外暴露
```

- **没有独立端口**：`/metrics` 挂在主 HTTP 路由上（`[server].listen`），
  所以「监听地址/端口」由 `[server]` 决定，不需要也不存在 `listen = "127.0.0.1:9090"` 这样的键。
  抓取地址 = `http://127.0.0.1:<server.listen 端口>/metrics`（144 = 8023，145 base = 8024）。
- **公网抓不到**：`allow_ips = []` 只认回环 peer；nginx 也没配 `/metrics` 的 location，
  所以从外部 `curl http://<host>/metrics` 拿到的是 SPA fallback 的 index.html（HTTP 200 + HTML），
  **不是指标**。要外部抓取必须显式把抓取端 IP 加进 `allow_ips`。

### 1.2 指标清单

框架自带（请求 / DB / 缓存 / 认证）：

```
nik_http_requests_total / nik_http_request_duration_seconds / nik_http_requests_in_flight
nik_db_queries_total / nik_db_query_duration_seconds / nik_db_raw_sql_total
nik_cache_operations_total / nik_cache_operation_duration_seconds
cloudpivot_auth_cache_degraded / cloudpivot_token_blacklist_rows
```

运维采样器每分钟补上的告警指标（`metrics_snapshot` 任务）：

```
cloudpivot_impexp_backlog_pending            导入+导出未终态任务数
cloudpivot_impexp_backlog_stuck_seconds      最早一张未终态任务已等多少秒
cloudpivot_impexp_import_open / _pending / _stuck_seconds / _failed_24h
cloudpivot_impexp_export_open / _pending / _stuck_seconds / _failed_24h
cloudpivot_invariant_ok                      1 通过 / 0 未通过
cloudpivot_invariant_blockers                失败项里 BLOCKER 数
cloudpivot_invariant_failed                  失败项合计
cloudpivot_invariant_age_seconds             最近一次巡检距今秒数
cloudpivot_metrics_sampler_last_success_timestamp   采样器最后一次成功(epoch 秒)
cloudpivot_metrics_sampler_runs_total        采样累计次数
```

**`-1` 的语义是「未知」，不是「0」**（查询失败 / 从未跑过）。任何读这些指标的地方
（脚本、Prometheus、看板）都必须把 `-1` 当「说出来」，不能当正常值。

### 1.3 自查

```bash
curl -s http://127.0.0.1:8023/metrics | grep -c '^# TYPE'          # 指标家族数（144 现状 ≥ 20）
curl -s http://127.0.0.1:8023/metrics | grep '^cloudpivot_' | head -20
```

## 2. 规则：`scripts/ops/alert_check.sh`

### 2.1 六项检查

| key | 判定 | 数据源 |
|-----|------|--------|
| `health` | `GET /health` 非 200，或 `data.status != ok`，或返回体不是 JSON | HTTP |
| `deps` | `GET /health/deps` 的 db/cache 任一 `ok=false` | HTTP |
| `invariant` | 最近一次巡检 `status != OK`、`blockers > 0`、或距今 > 36h；**无记录 = INFO**（没有结论 ≠ 账对） | `/metrics` → 回退 `sys_invariant_result` |
| `disk` | `df -P /` ≥ 85% → ALERT；≥ 75% → WARN | 本机 |
| `secret_expiry` | TLS 证书剩余 < 30 天或已过期；**本机没有证书 = INFO**（当前是 HTTP；JWT/存储密钥是对称密钥无有效期） | openssl |
| `backlog` | 未终态导入/导出任务最早一张等 > 30 分钟，或总数 ≥ 10 | `/metrics` → 回退 `sys_import_task`+`sys_export_task` |

评审指定的三条核心告警 = `health` / `invariant` / `backlog`。

### 2.2 为什么 DB 类检查有两条路

- 优先 `/metrics`：脚本**不需要库口令**，也不会因为库慢而误报。
- 回退 `psql`（只读，口令从 `/etc/cloudpivot-base/base.env` → `/etc/cloudpivot/cloudpivot.env`
  → `/etc/cloudpivot/cloudpivot-dev.env` 自动探测，只取 `NIK_DATABASE_*` 几个键）：
  后端还没重新部署（例如 144 的 release 二进制先于本次改动）时，`/metrics` 里没有
  `cloudpivot_*` 采样指标，靠这条路仍能判「账错 / 积压」。

### 2.3 常用命令

```bash
bash scripts/ops/alert_check.sh --self-test      # 31 条判定逻辑自检（不需要服务/库/网络）
bash scripts/ops/alert_check.sh --dry-run        # 只判定、不动 sinks、不动去重状态
bash scripts/ops/alert_check.sh --list-checks    # 看生效参数与数据源
bash scripts/ops/alert_check.sh --only health,backlog --force   # 演练单项（忽略去重窗口）
```

退出码：`0` 巡检跑完（**有告警也是 0**，cron 不该因为报警刷错误邮件）、`2` 用法错误、`3` 自检失败。

### 2.4 cron（144 + 145 已装）

```cron
*/5 * * * * NIK_ALERT_BASE_URL=http://127.0.0.1:8023 NIK_ALERT_HOST_TAG=144 /opt/cloudpivot/scripts/ops/alert_check.sh >> /var/log/cloudpivot/alert-check.cron.log 2>&1
*/5 * * * * NIK_ALERT_BASE_URL=http://127.0.0.1:8024 NIK_ALERT_HOST_TAG=145 /opt/cloudpivot/scripts/ops/alert_check.sh >> /var/log/cloudpivot/alert-check.cron.log 2>&1
```

看是否在跑：

```bash
crontab -l | grep alert_check
tail -20 /var/log/cloudpivot/alert-check.cron.log
```

### 2.5 阈值怎么调

全走环境变量（cron 行里加即可，不用改脚本）：`NIK_ALERT_DISK_THRESHOLD`、
`NIK_ALERT_BACKLOG_MINUTES`、`NIK_ALERT_BACKLOG_COUNT`、`NIK_ALERT_INVARIANT_MAX_AGE_HOURS`、
`NIK_ALERT_SECRET_WARN_DAYS`、`NIK_ALERT_DEDUP_SECONDS`、`NIK_ALERT_CERT_FILES` ……
完整列表见 `scripts/ops/alert_check.sh` 头部注释或 `--list-checks`。

## 3. 通道

| 通道 | 开关 | 说明 |
|------|------|------|
| `ALERT.log` | 永远写 | `/var/log/cloudpivot/ALERT.log`，一行一条（含 `RECOVERED`）；kanban/飞书都挂时靠它 |
| kanban 卡 | `NIK_ALERT_KANBAN=auto\|local\|ssh\|off` | 标题 `【ALERT】<host> <现象>`，assignee=`laoliu`；`auto` = 本机是看板机则本地 CLI，否则 **ssh 到 172.18.10.99 建卡** |
| 飞书卡片 | `NIK_ALERT_FEISHU=auto\|off` | 复用 `scripts/cron/feishu_alert_send.py`；**144/145 当前没有 `FEISHU_*` 凭据，自动跳过** |

**为什么 144/145 不本地建卡**：两台机器上的 `/root/.hermes/kanban.db` 是 10-29 的旧副本
（空板），往那里建卡等于没人看得见。看板真身只有 172.18.10.99 的 `dev` 板，
所以异地主机一律 ssh 过去建卡（145 的使用 `cloudpivot-alert@145` 密钥，已授权到 99）。

### 3.1 告警去重

同一 `key` 在 `NIK_ALERT_DEDUP_SECONDS`（默认 300s）内只发一次：
状态目录 `/var/log/cloudpivot/alert-state/<key>.last` 存 epoch 秒。
检查恢复正常时打一条 `RECOVERED` 并删掉状态文件 —— **下次再犯立刻报，不会被上一条压住**。

`--force` 忽略窗口（演练用）；`--dry-run` 完全不动状态文件。

### 3.2 演练（造一个真异常建一张真卡）

```bash
# 把 BASE_URL 指到一个没人监听的端口 → health 必然 ALERT
NIK_ALERT_BASE_URL=http://127.0.0.1:9 bash scripts/ops/alert_check.sh --only health --force
```

## 4. 与 Prometheus（选项 A）的关系

`scripts/ops/prometheus/cloudpivot.rules.yml` 是同一批指标名的 Prometheus 规则
（`CloudpivotServiceDown` / `CloudpivotInvariantBlockers` / `CloudpivotImpexpBacklog` /
`CloudpivotMetricsSamplerStale` / 磁盘 / 5xx 比例）。**阈值与本文一致**，
上 Prometheus 时直接 `rule_files:` 引用，不会出现「脚本说红、面板说绿」两套口径。
当前没装 Prometheus（评审建议先做零依赖的 B 方案），是否上 A 由 ARCH-9 的发布节奏决定。
