## 一、改了什么（症状 → 原因 → 修法）

### 缺陷 1：R14 只看 `assignee_type`，不看 `assignees`

| 环节 | 修前 | 修后 |
|------|------|------|
| `PUT graph`（只给 `assignees`） | 200，落 `biz_flow_node_assignee` 1 行 | 200，**同时反推** `biz_flow_node.assignee_type='USER'` |
| `PUBLISH` | **400 + 65015**「节点 n5 未配置审批人」 | **200 + code=0**，版本 `PUBLISHED` |
| 运行时 `assignee::plan_of` | 读 `assignee_type` → `Unsupported("未配置审批人来源")` → 派单 0 人 | 拿到真实来源 → 正常解析候选人 |

两处代码：

- `src/business/flow/graph.rs`：R14 判据改为「`assignee_type` 或 `assignees` 任一有内容」，
  新增 `infer_assignee_kind()`（取第一条可解析的 `kind`）；
- `src/business/flow/dto.rs`：`into_graph` 里新增 `infer_assignee_type()`——没给来源类型时按
  `assignees[0].kind` 反推；**混用来源**（如 `USER` + `ROLE`）给中文 400；
  显式给了 `assignee_type` 时完全维持历史行为（以显式声明为准，不新增拒绝）。

### 缺陷 2：`PUT graph` 的 422 是纯文本

`axum::Json` 的 extractor 拒绝**不进 handler**，自己回 `text/plain` 的 400/415/422。
新增 `middleware::json_rejection`（`src/middleware/mod.rs`）+ `lib.rs` 的 `route_layer` 挂载：
状态码 ∈ {400,415,422} **且** `Content-Type` 是 `text/plain` 时才改写 body 为
`{code:10001, msg:"请求体参数校验失败：<反序列化原文>"}`，**状态码不变**、其余响应头保留。
业务错误走 `Res::fail`（`application/json`），双重条件保证不被误改。

## 五、已知边界（诚实清单）

1. **「混用多种来源」是本次新加的拒绝**（只在前端**没给** `assignee_type` 时生效）：
   `assignees:[{type:"USER"},{type:"ROLE"}]` → 400「一个节点只能选一种审批人来源」。
   显式给了 `assignee_type` 的老客户端行为不变（来源以显式声明为准，`assignees` 里另一类型的
   行仍会落库但不参与解析）——这是历史行为，本卡不扩大改动面。
2. **`415`（少带 `Content-Type: application/json`）也一并标准化**（同为 extractor 拒绝），
   状态码保持 415、body 同样变成 `{code:10001,…}`。
3. 生产侧未造业务数据验证 R14（生产库不该留验收数据）；R14 的 4 个分支在隔离实例 + 单测里
   全绿，生产只验证了「二进制含新逻辑 + 路由在位 + 422 行为 + 业务码不变」。
