> 出口：`backend/src/business/flow/edge_admin.rs`（新增）
> 迁移：`backend/migrations/business/V0206__flow_edge_config_admin.{up,down}.sql`
> 回调挂点：`backend/src/business/flow/handler.rs`（同意 / 驳回 / 撤回三处 + 自动通过）

D1 把「状态机的边」变成可配置的（`BASE_EDGES` 硬约束 + `biz_flow_state_edge` 只能加严 + 运行时
fail-safe 合并），并刻意留了三件事没做。本卡是那三件事的出口：

| # | D1 留下的边界 | 本卡怎么收口 |
|---|---|---|
| 1 | 没有管理面（只有 Rust 函数） | `GET/PUT/DELETE /api/business/flow/state-edge` + 两个权限码 |
| 2 | 改配置 = 超管点两下（一个人就能改全公司流程规则） | 改配置**本身走审批流** `flow_edge_config`，通过才落库 |
| 3 | 前端按钮仍按代码边表显示（点下去 409） | 单据详情 `next_statuses` 改写有效边 → 按钮跟着配置走 |

## 1. HTTP 管理面

| 方法 | 路径 | 权限码 | 干什么 |
|------|------|--------|--------|
| `GET` | `/api/business/flow/state-edge?entity=STOCK_OUT` | `business:flow:state-edge:list` | BASE 边 + 当前配置 + **合并后的有效边** + 在跑的审批单 |
| `PUT` | `/api/business/flow/state-edge` | `business:flow:state-edge:manage` | 改 / 加一条配置（**提交审批**） |
| `DELETE` | `/api/business/flow/state-edge?entity=&from_status=&to_status=&confirm=true` | `business:flow:state-edge:manage` | 删一条配置（回到 BASE_EDGES，**提交审批**） |

- `entity` 不传 = 9 个实体全列（`list` 形态，前端可以一次拿全）。
- 配置列表直接调 `list_edge_config`，有效边直接调 `effective_edges` —— **没有第二套合并逻辑**。
- 两个权限码都只授 `SUPER_ADMIN`（迁移 `V0206` 同时种 `sys_menu` + `sys_role_menu`，与注解逐字一致；
  `system/menu/tests.rs::n10` 的「注解 ↔ 菜单」一致性扫描覆盖）。
- **参数校验一行都没重复**：HTTP 层只做解析，`confirm` / 未知实体 / 不是 BASE 边 / 禁用 mandatory /
  放宽 requires_reason 全部由内核返回（报文原样透传）。

## 2. 改配置走审批流

```
PUT /state-edge
  ├─① 试写 + 回滚（dry-run）：把内核的 400/403 提前到**提交阶段**
  │     （否则用户会遇到「审批通过了才发现配不了」）
  ├─② flow_edge_config 已发布 → 起一张审批单，待变更内容写进 form_data
  │     同一条边同一时刻只允许一张在跑的审批单（409，报文带审批单号）
  └─③ 流程被下线 → 409（复用 approval_gate 的「默认拒绝」）；
        只有持 business:erp:skip-approval + 理由 ≥10 字才直接生效并留痕

审批中心：同意 → edge_admin::on_settled(APPROVED)
   → 以**发起人**身份调内核 upsert_edge_config / delete_edge_config（唯一写入入口）
   → 内核写「改前 → 改后」审计；再补一行「是哪张审批单让它生效的」
         驳回 / 撤回 → 一行配置都不写，只留一条 biz_status_log（配置未变更）
```

关键决策与理由：

1. **审批单就是「待变更内容」的载体**（`biz_flow_instance.form_data`），不另建影子表。
   `biz_id` = 从 `(entity, from, to)` 派生的确定性 UUID（v8），于是
   `uk_biz_flow_instance_biz_active` 天然保证「同一条边不许两张并行审批单」。
2. **回调里不写 SQL**：审批通过时重建发起人的 claims（角色 / 权限码从库里现读，
   与登录口径一致），再调 D1 的唯一入口。**通过那一刻还要再核一次「发起人是否仍是超管」**——
   撤了他的权限，之前提的单不该还能落地（不生效 + WARN + 留痕）。
3. **流程定义是种子，不是代码分支**：`flow_edge_config`（`biz_type=FLOW_EDGE_CFG`）
   `s → n_cfg（流程配置复核）→ e`，审批人 `ROLE = FLOW_CONFIG_APPROVER` +
   `empty_assignee=FALLBACK_ADMIN` ⇒ **开箱可跑**（没人绑角色时落到超管），客户把复核岗绑上人
   之后自动按岗位分权，流程一行不用改。
4. **单超管环境允许自助审批，但必须留一张审批单**：`FLOW_EDGE_CFG` **不在**
   `flow::internal_control` 的受控清单（那份清单是 6 个账务业务）。语义上「改配置」是管理员的
   内控动作，一个超管的部署要能自助完成；要**真正的双人复核**，把 `FLOW_CONFIG_APPROVER`
   角色绑一个非发起人即可（绑了人就不会再走 `FALLBACK_ADMIN`）。这条边界写在代码注释与本文档里，
   不藏着。

## 3. 前端按钮联动

- D1 之后「配置禁用一条边 → 接口 409」，但按钮仍按代码边表显示（D1 §8.1）。
- 本卡把**单据详情 DTO 的 `next_statuses` 改成读有效边**：`stockout_handler::detail_of` 取一次
  `effective_edges(STOCK_OUT)` 传进 DTO（DTO 仍是纯函数，不碰数据库）。
  前端本来就用 `next_statuses` 渲染按钮（`views/business/erp/stock-out` 不写第二份状态机），
  所以**前端一行没改**，按钮自己跟着配置走。
- 影响面评估（卡面要求「先评估再动」）：

  | 单据 | 详情 DTO 有 `next_statuses` 吗 | 处理 |
  |------|------------------------------|------|
  | 出库单 `stockout_dto` | 有（前端按钮直接读它） | **本卡改读有效边** |
  | 合同 `contract_dto` | 有 | 未动：合同 5 条边全是 mandatory，配置改不动它（`effective ≡ base`），改了等于白改代码 |
  | 采购 / 收货 / 调拨 | 详情 DTO **没有**这个字段（前端按钮走另一套动作） | 不在本卡范围 |

  这是「先评估影响面再动」的结论：只动真正会变的那一个，其余留证据不动。

## 5. 迁移号与种子 hash（两条容易踩的坑）

- **迁移号**：卡面没指定；复核当前最大号 V0205（D2 的 `flow_linkage_rule`），故取 **V0206**。
- **`graph_hash` 不能手抄**：D4d 的每日自检（`flow::maintain`）会拿 `biz_flow_node/edge/assignee`
  **重建快照**再算 sha256，与 `version.graph_hash` 和 `graph_snapshot` 三方比对。
  快照的**数组顺序**是确定的（节点按 key、边按 `(from,to,key)`），所以 JSON 里两段数组也必须按
  那个顺序写 —— 顺序错了 hash 仍然对得上（hash 用的是我自己算的那份），但
  `canonical(snapshot) ≠ graph.snapshot_json()`，日检会报 `SnapshotEdited`。
  单测 `seed_flow_hash_matches_rows` 同时钉住**两个**等式（hash 与快照），就是为了这个。
- 空库首启时迁移先于 bootstrap 跑（`sys_role` 为空），所以 `sys_role_menu` 的授权是空操作 ——
  与 V0192/V0197/V0202 同口径：**bootstrap 之后重放一次本迁移即可补齐超管授权**（幂等，已验证）。

## 6. 已知边界（本卡不做）

1. `GET` 的响应是 `{list, total}` 形态（传 `entity` 时 `total=1`），没有为单实体另开一个形状 ——
   前端一直按列表取第一个，少一个分叉。
2. 管理面只有 HTTP + 审批，**没有前端页面**（「系统管理 · 流程定义」下只挂了两个按钮级权限码，
   `is_visible=false`）。要页面是另一张卡（表单 + 列表 + 审批中徽标）。
3. `flow_edge_config` 是 `is_system=TRUE` 的预置模板：**改图 = 换流程**，不在本卡范围。
4. 采购 / 收货 / 调拨的详情 DTO 没有 `next_statuses` 字段（§3 的影响面表），它们的按钮联动
   要先把字段补上 —— 属于各自模块的卡。
