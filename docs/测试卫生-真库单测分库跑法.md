# 测试卫生：真库 lib 单测必须「按模块分库 + 分进程」跑

> 一句话：`ERP_DB_URL` 里那批**连真库**的 lib 用例，**不能把几个模块串在同一个库上跑**。
> 跑法固化在 [`scripts/verify/run_lib_tests_by_module.sh`](../scripts/verify/run_lib_tests_by_module.sh)：
> 每个模块一个干净库、一个独立进程，跑完汇总；交卡 / 发版前用 `RUNS=2`（同一个库连跑两遍）。
>
> 证据原始输出：[`docs/evidence/20261104-test-hygiene/`](./evidence/20261104-test-hygiene/)（60–66）。

---

## 1. 现象（2026-11-04，卡 D 真库回归时踩到）

把三段用例**串在同一个库**上按顺序跑：

```bash
ERP_DB_URL=postgres://alun:***@127.0.0.1:5432/hyg_shared \
TASK_DB_URL=$ERP_DB_URL P0FIX_DB_URL=postgres://alun:***@127.0.0.1:5432/hyg_p0fix_shared \
  cargo test --lib business::changelog -- --test-threads=1     # 51/0 绿
ERP_DB_URL=… cargo test --lib business::flow::      -- --test-threads=1   # 345/0 绿
ERP_DB_URL=… cargo test --lib business::erp::       -- --test-threads=1   # ✗ 不是 0 failed
```

| 跑法 | changelog | flow | erp |
|---|---|---|---|
| **同库串跑**（卡 D 首轮，`44b_first_run_shared_db.txt`） | 51/0 | 345/0 | **773 passed / 67 failed** |
| **同库串跑**（本卡复跑，`60_…txt`） | 51/0 | 345/0 | **838 passed / 2 failed** |
| **逐模块分库**（卡 D 第二版，`44_tests_changelog_flow_erp.txt`） | 51/0 | 345/0 | **840/0** |
| **逐模块分库 ×2 轮**（本脚本，`64_…txt`） | 51/0 ×2 | 345/0 ×2（+ flow_p0fix 7/0 ×2） | **840/0 ×2** |

同一份代码：分库就全绿，同库就红。**这是测试卫生问题，不是业务回归。**

两个值得先记住的细节：

1. 同库串跑的失败条数**不稳定**（67 → 2），说明它不是"某几条数据判死了某几条断言"这么简单，见 §4。
2. erp 段的失败里，只有 **2 条**（`dc01`、`zz_teardown`）能确定复现；其余几十条都是
   "同进程里更早的用例先失败过"之后被带偏的**传染性假红**——失败了也复现不出来，这才是最该消灭的东西。

## 2. 根因 A：同库数据残留（确定复现）

`business::flow::` 段自己会造业务数据，而且**造完不清**（它只按自己的前缀清场，这是对的；
错的是"别的模块跟它共用一个库"）。实测 `hyg_flowonly`（只跑过 flow 段）比干净库多出 **27 张表**的行：

| 表 | 干净库 | 跑完 flow 段 | 差 |
|---|---|---|---|
| `biz_flow_def` | 11 | 20 | **+9（其中 7 条是 `status=PUBLISHED` 且 `biz_type=PO_APPROVE` 的 `p0fix_*`）** |
| `biz_flow_instance` | 0 | 15 | **+15（`PO_APPROVE` 里 3 条 `PENDING`）** |
| `biz_flow_task` | 0 | 22 | +22 |
| `sys_user` | 1（admin） | 44 | +43 |
| `biz_purchase_order` / `_item` | 0 | 9 / 3 | +9 / +3 |
| `biz_task` / `biz_task_comment` | 0 | 10 / 6 | +10 / +6 |
| `sys_notice` / `sys_notice_receiver` | 0 | 16 / 18 | +16 / +18 |
| `sys_change_log` / `_2026_11` | 0 | 11 / 11 | +11 / +11 |
| 其余（`biz_material`、`biz_supplier`、`biz_unit`、`biz_seq`、`biz_stock_in*`、`biz_location`、`biz_warehouse`、`sys_role`、`sys_user_role`、`biz_flow_def_version`、`biz_flow_instance_node`、`biz_flow_linkage_rule`、`biz_status_log`） | — | — | 各有 1–22 行 |

erp 段里有两类断言天然是「**全库口径**」，只要库里还有别人的行就必红：

| 用例 | 断言 | 被谁判死 |
|---|---|---|
| `purchase_handler::tests::dc01_submit_without_published_flow_is_409` | 把 `po_approve` 置 `DISABLED` 后提交必须 409 | flow 段留下的 7 条 `PUBLISHED` + `biz_type=PO_APPROVE` 的 `p0fix_*` 定义仍能命中 → 提交成功，不 409 |
| `purchase_handler::tests::zz_teardown_purges_po_approval_residue` | `SELECT count(*) … WHERE biz_type='PO_APPROVE' AND status='PENDING'` 必须 **0** | flow 段正好留下 3 条 PENDING → `left: 3, right: 0` |

这两条是**唯一能稳定复现**的（同一份污染数据、单独进程、每次必红）。
卡 D 首轮里另一条 `cash_flow::tests::r3_real_config_covers_all_accounts`（"P2D1 测试现金 没有任何分类行"）
属于 §4 的偶发族：本卡用等价污染数据复跑时它是绿的。

**可复现命令**（只跑这一条，单独起进程，就能稳定复现）：

```bash
# ① 造一个"只跑过 flow 段"的污染库（或用任何跑过 flow 的库）
ERP_DB_URL=…/hyg_flowonly cargo test --lib \
  'business::erp::purchase_handler::tests::dc01_submit_without_published_flow_is_409' -- --test-threads=1
# → FAILED：没配流程必须 409，不能静默直接提交

ERP_DB_URL=…/hyg_flowonly cargo test --lib \
  'business::erp::purchase_handler::tests::zz_teardown_purges_po_approval_residue' -- --test-threads=1
# → FAILED：模块收尾后不许剩 PENDING 的采购审批实例（同库连跑第二遍的前提），left: 3, right: 0

# ② 同一份污染数据、只跑 a4 夹具子模块 → 13/13 全绿（证明这组不是被残留数据直接判死，见 §4）
ERP_DB_URL=…/hyg_flowonly cargo test --lib \
  'business::erp::stockin_handler::stockin_handler_tests_a4' -- --test-threads=1
```

## 3. 根因 B：进程级 `set_db` 先到先得 —— `P0FIX_DB_URL` 会被**静默忽略**

`set_db()` 是 `OnceLock`（`backend/vendor/nik-web/src/resources.rs`）：**一个进程只能装一个全局连接**，
且装不上时返回 `Err`。而 `backend/src/business/flow/internal_control.rs` 的 `ensure_db()` 是这么写的：

```rust
let Ok(url) = std::env::var("P0FIX_DB_URL") else { … skip … };
if try_db().is_some() { return true; }          // ← 同进程里别人已经 set_db，就静默用别人的库
match Db::connect_with(&url, config).await { Ok(connection) => set_db(connection) … }
```

于是：**只要同一个进程里更早的用例已经用 `ERP_DB_URL` 装好了全局连接，`internal_control` 就直接拿
那个库开跑**，`P0FIX_DB_URL`（以及它那条"库名必须含 p0fix"的硬断言）根本不会被执行。

实测三连（命令与原始输出见 [`62_setdb_firstwins_probe.txt`](./evidence/20261104-test-hygiene/62_setdb_firstwins_probe.txt)）：

| 实验 | 命令 | 结果 |
|---|---|---|
| 反例 | `cargo test --lib 'business::flow::'`，`P0FIX_DB_URL` 指向 `hyg_p0fix_shared` | flow 345/0 绿；但 7 条 `p0fix_*` 定义落在 **ERP 库**，`hyg_p0fix_shared` **一行没写** |
| 更硬的反例 | 同上，但 `P0FIX_DB_URL` 指向**根本不存在的库** `hyg_iso_p0fix2` | 照样 345/0 全绿 —— 证明这个进程压根没去连 P0FIX 库 |
| 正例 | `cargo test --lib 'business::flow::internal_control::db_tests'`（单独一个进程） | 7/0 全绿，7 条 `p0fix_*` 定义**正确地**落在 P0FIX 库，ERP 库 0 条 |

结论：`internal_control` 的真库用例**必须独占一个进程**。本脚本把它单列成 `flow_p0fix` 模块，
并在跑完之后**硬校验**「P0FIX 库拿到 ≥1 条 `p0fix_*`，模块库必须 0 条」——这条校验就是防这个坑复发的门。

### 3.1 已收口：`ensure_db()` 现在会**显式失败并指路**（卡 `t_f38d1f45`）

上面那段「`if try_db().is_some() { return true }`」已经改掉。现在的行为：

```rust
let wanted = db_name_of(&url);                 // P0FIX_DB_URL 里的库名
if try_db().is_some() {
    let current = current_db_name().await;      // SELECT current_database()
    if current != wanted { panic!(…) }          // ← 显式失败 + 下一步命令
    return true;                                // 同一个库：合法复用
}
```

**为什么选 `panic` 而不是「WARN + SKIP」**（卡面给了两个选项）：

1. 本组的价值**全在**「跑在 P0FIX 库上」——SKIP 之后 `test result` 仍然是 `ok`，
   正是这一串卡片要灭掉的**假绿**；而 panic 让「这条断言没跑」这件事**变成红色**，不可能被忽略。
2. 冲突只发生在操作者**显式设了 `P0FIX_DB_URL`** 的场合。没设 → 仍然是老老实实 SKIP
   （`cargo test --lib` 在没配库的机器上照旧全绿），所以 panic 不会打扰无库环境。
3. 失败信息本身就是「可执行的下一步」（三条：独占进程 / 用本脚本的 `flow_p0fix` / 整段跑时 `--skip` 掉本组），
   失败的代价极低。

前后对比（同一台机、同一份干净模板库、同一条命令，原始日志见
[`evidence/20261104-setdb-reuse-guard/`](./evidence/20261104-setdb-reuse-guard/README.md)）：

| | 修复前 | 修复后 |
|---|---|---|
| `cargo test --lib 'business::flow::'`（`ERP_DB_URL`=A、`P0FIX_DB_URL`=B，同进程） | **345/0 全绿**（假绿） | **338 passed / 7 failed**，panic 点名「当前连的是 A、要求的是 B」并给三条下一步 |
| 7 条 `p0fix_*` 定义落在哪 | **A（业务库）** | **哪都不落**（A=0；进程拒绝在 A 上跑） |
| 本组独占进程（`business::flow::internal_control`） | 7/0，落在 B | 7/0，落在 B（**不变**） |
| 三个变量指向**同一个** p0fix 库 | 345/0（复用） | 345/0 + 打印「复用同一库」（**合法复用不被误伤**） |
| `MODULES='flow_p0fix'` | 7/0 ×2，泄漏校验 7/0 | 7/0 ×2，泄漏校验 7/0（**守门保留**） |

**脚本随之改了一处**：`flow` 模块的过滤器 `business::flow::` 会把那 7 条一起捞进来，
现在会显式 `--skip business::flow::internal_control::db_tests`（`flow` = 338 条，`flow_p0fix` = 7 条，合计仍是 345）。
这不是放宽标准：那 7 条仍然跑，只是改由**真正连对了库**的 `flow_p0fix` 模块跑。

顺带把全仓 43 处「读 `xxx_DB_URL` + `try_db().is_some()` 早退」的入口逐一判定过一遍
（只有这一处对「库的身份」有断言 ⇒ 只有这一处必须独占）：见
[`docs/测试卫生-真库连库入口清单.md`](./测试卫生-真库连库入口清单.md)。

## 4. 那另外 60 多条失败是什么：不可复现的**传染性假红**

- 同一份污染数据上，a4 子模块（首轮失败最集中的 13 条）**单跑 13/13 全绿**；
- 换成"整段 erp 一起跑"，同一份污染数据两次跑出 **67** 条 / **2** 条（卡 D 首轮 vs 本卡复跑）。

也就是说：这些用例的失败**不由数据内容决定**，而是由"同进程里更早的用例在污染数据下走了不同分支
（其中 2 条直接 panic）"之后进程/连接状态漂移决定。典型症状是**自己刚写的数据自己读不到**
（`采购明细行不存在` 的外键报错、`收货入库单不存在或已删除`、`items.len()` 为 0）。

这正是「同库串跑」最恶劣的一面：

- 它**不是业务回归**，却会让回归报告红一片；
- 它**不稳定**，重跑可能变绿 —— 于是很容易被当成"偶发"忽略掉，直到某次发版卡在一条根本不是问题的红上。

消灭它的办法只有一个：**不让模块之间共享库，也不让它们共享进程**。

## 4.5 顺手挖出的第二个问题：**同一个库连跑第二遍**，erp 会红 2 条（已修）

跑「同一库 × 2 轮」时暴露出来的（`raw_prefix_2failed/erp_run2_同一库第二轮_2failed_修复前.txt`）：

```
business::erp::contract_approval_tests::large_amount_requires_two_levels_in_sequence
  assertion failed: 两级审批的第一级只有一条待办  left: 2  right: 1
business::erp::contract_approval_tests::small_amount_single_level_approval_signs_contract
  assertion failed: 小额分支是单级审批：只有一个节点应该有待办  left: 2  right: 1
```

**根因**：`contract_approve` 种子的审批节点是**按角色**（`PURCHASE_MANAGER` / `GENERAL_MANAGER`）展开的，
而 `purchase_handler::tests` 的 `p3a_*` 夹具账号也挂在同一个角色上、且**跑完不删**。于是第二轮
（`contract_approval_tests` 按字母序先跑）里，一个节点被展开成 **2 条待办**（本模块的 `U_PM` + 残留的
`p3a_0003`），不仅「一条待办」假红，连「一级审完就通过」也变成「还差一个人」（`PENDING != APPROVED`）。

**修法（测试侧，不动业务代码、不降断言）**：

1. `contract_approval_tests::setup()` 现在会先把这两个共享角色上**不属于本模块夹具**的绑定摘掉
   （与 `purchase_handler::tests::setup_approval()` 对称 —— 它早就这么干了；串行跑时「谁 setup 谁占位」，
   别的模块各自 setup 会挂回自己的）；
2. 待办断言从「**条数**」改成「**落到哪一级 / 谁**」：只数本模块夹具账号的待办，并**新增**两条更强的断言
   （小额分支不该给总经理派待办；两级审批的第二级必须落到总经理）。

修完在同一个（带残留的）库上连跑 3 遍 9/9 全绿，全量 `RUNS=2` 也全绿（见 §7 的 `64`／`65`）。

## 5. 修法：跑法固化成一个脚本（不改业务代码、不放宽任何断言）

```bash
bash scripts/verify/run_lib_tests_by_module.sh                 # 快速：各模块各 1 遍
RUNS=2 bash scripts/verify/run_lib_tests_by_module.sh          # 守门：同一个库连跑两遍都必须全绿
MODULES="erp" RUNS=2 bash scripts/verify/run_lib_tests_by_module.sh
```

脚本做的事（每一件都对应上面某个根因）：

| 步骤 | 作用 |
|---|---|
| 建/复用模板库 `cloudpivot_libtest_template` | 用后端二进制跑一次启动迁移 + 种子，得到"已迁移到最新版本的空库"；不存在时自动 `cargo build --bin cloudpivot` 并建 |
| 每个模块 `createdb -T 模板库` | 一个模块一个库（`cp_libtest_<模块>`），并额外配一个 `<库名>_p0fix` 给 `P0FIX_DB_URL` |
| **preflight 洁净断言** | 跑之前断言该库 `biz_flow_instance=0`、`biz_flow_task=0`、`biz_purchase_order=0`、`p0fix_*` 定义=0、用户数 ≤ 种子数 —— 一旦有人在脏库上跑，立刻红并说明原因 |
| 每模块**单独一个 `cargo test` 进程** + `--test-threads=1` | 一个进程只有一个全局 `db()`，天然免疫 §3 的 `set_db` 先到先得 |
| `flow_p0fix` 单列模块 | 让 `internal_control` 独占进程，`P0FIX_DB_URL` 才真正生效 |
| **泄漏校验** | `flow_p0fix` 跑完断言 P0FIX 库 ≥1 条 `p0fix_*` 且模块库 0 条 |
| **轮次计数一致性** | 第 2 轮 passed 数必须等于第 1 轮，否则判 FAIL（防止"某轮 SKIP 变多"式的假绿） |
| **`passed=0` 判 FAIL** | 过滤器打错 / 模块改名时 `cargo test` 会「0 个用例 + ok」，那不是通过 |
| 汇总 + 退出码 | 任一模块任一轮失败即 `exit 1`，可直接给 CI 用 |

脚本自身的负例自测（证明这些守门真的会红，不是摆设）见
[`65_negative_selftest.txt`](./evidence/20261104-test-hygiene/65_negative_selftest.txt)：
① 故意复用脏库 → preflight 点名 + `EXIT=1`；② 过滤器打不中任何用例 → `passed=0` 判 FAIL + `EXIT=1`。

模块表（`MODULES` 默认值）：

| 模块 | cargo test 过滤器 | 库 |
|---|---|---|
| `changelog` | `business::changelog` | `cp_libtest_changelog` |
| `flow_p0fix` | `business::flow::internal_control::db_tests` | `cp_libtest_flow_p0fix`（P0FIX：`…_p0fix`） |
| `flow` | `business::flow::` | `cp_libtest_flow` |
| `erp` | `business::erp::` | `cp_libtest_erp` |

也支持自定义条目：`MODULES="mymod=business::erp::contract_"`。

### 与 `scripts/check.sh` 的关系

`check.sh` 只做 fmt / clippy / check / typecheck + 门禁，**不跑真库用例**（没库的机器上那批用例会 SKIP）。
真库回归用本脚本；两者互不替代。

## 6. 铁律（以后写 / 跑真库用例都照这个来）

1. **一个模块一个库、一个进程。** 真库用例的隔离单位是「模块 × 进程 × 库」，不是"一次 `cargo test` 跑全部"。
   理由：进程里只有一个全局 `db()`（`OnceLock`），库里有别人的行时"全库口径"断言必红。
2. **`RUNS=2` 才算跑过。** 同一个库连跑两遍都必须 0 failed、且 passed 数一致。
   只跑一遍时，"上一轮残留把这一轮判死"这类问题看不出来；夹具清场不干净也只有第二遍才暴露。
3. **夹具只按自己的前缀 / 固定 id 清场，别做"整表 / 整期"清场。** 你的删除语句会踩到并行模块的夹具
   （历史事故见 `backend/src/test_db_guard.rs` 文件头）。
4. **写"全库口径"断言前先问一句：这条库是不是我独占？** 不是独占就别写（或者改成本模块口径），
   否则它在分库跑法下绿、在共享库下红 —— 红的那次你还要花半天排除它不是回归。
5. **共享角色是隐式全局状态。** `PURCHASE_MANAGER` / `GENERAL_MANAGER` / `DEPT_LEADER` 这类种子角色
   在真库里是**跨模块共享**的：审批节点按角色展开，角色上多一个人就多一条待办。所以
   （a）`setup()` 里先按"我的夹具"占位（摘掉别人的绑定，跑完不恢复，别人 setup 会挂回来）；
   （b）断言按「**落到哪一级 / 谁**」判，不要按「待办条数」判 —— 条数取决于角色里有几个人。
6. **需要独立库的模块（`internal_control` 这类读 `xxx_DB_URL` 的）必须独占进程**：跟别的模块同一个
   `cargo test` 进程时，它的 `set_db` 会静默输给先到者。判据：把它的 `*_DB_URL` 指向一个不存在的库，
   如果它照样全绿，就是踩了这个坑。

## 8. 复跑 / 清理

```bash
# 复跑（会先删后建模块库）
RUNS=2 bash scripts/verify/run_lib_tests_by_module.sh
# 只想看某个模块
MODULES="erp" RUNS=2 bash scripts/verify/run_lib_tests_by_module.sh
# 丢库（本机 PostgreSQL）
for d in changelog flow_p0fix flow erp; do su - postgres -c "dropdb --force --if-exists cp_libtest_$d"; done
for d in changelog flow_p0fix flow erp; do su - postgres -c "dropdb --force --if-exists cp_libtest_${d}_p0fix"; done
```

只读 / 无库环境（CI 没有 PostgreSQL）时不需要本脚本：`unset ERP_DB_URL TASK_DB_URL P0FIX_DB_URL`
后那批真库用例会 `SKIP`，`cargo test --lib` 仍然全绿（SKIP 不是通过，别把它当覆盖率）。
