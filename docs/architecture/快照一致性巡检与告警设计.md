## §1 术语与不变量

### 1.1 三个词必须分清（这是整个设计的灵魂）

| 词 | 定义 | 漂移是否合法 | 例子 |
|---|---|---|---|
| **快照** | 业务发生时刻的事实副本，**不可由上游重算**（重算出来的是今天的事实，不是当时的事实） | 合法（上游事后变更 → 历史快照**本来就该**与今天不同） | `biz_purchase_order.supplier_id`（建单时的合同乙方）、`biz_contract.party_b_name`（签约时名称） |
| **冗余拷贝** | 可由上游**无歧义重算**的副本，存在只为查询性能/免 JOIN | **不合法**，任何偏移都是缺陷 | `biz_stock_in.supplier_id`（有来源单时必须 = 采购单的供应商） |
| **真相（SSOT）** | 该事实唯一的权威存放处 | — | 供应商在采购链上的真相 = `biz_contract.party_b_id`（V0193 注释原文） |

> 判据一句话：**能重算的偏移是 bug，不能重算的偏移是历史**。这条规则同时决定了每条巡检项的分级（§2.3）与处置动作的合法性（§6）。

### 1.2 五条不变量（巡检就是这五条的守卫）

1. `purchase_type='CONTRACT'` ⇒ `contract_id` 非空且指向**存在且未软删**的合同。
2. 合同采购单的 `supplier_id` = 建单时刻的 `contract.party_b_id`。当前值不同**且无变更台账** ⇒ 疑似篡改。
3. 入库单有来源采购单时，`supplier_id` 必须等于采购单 `supplier_id`（可重算 ⇒ 恒等）。
4. 资金链上的供应商必须与实物链一致：`payable.supplier_id` = 其 `stock_in.supplier_id`。
5. 追溯链不许断：任何 `*_id` 弱引用要么指向有效行，要么明确为空（"空"必须是合法业务语义，不能是删出来的洞）。

### 1.3 与 ARCH-2 既有设计的接口（避免第二真相）

| ARCH-2 已定的东西 | 本设计的用法 |
|---|---|
| `biz_contract.party_b_id` 是乙方唯一真相 | DI-01/DI-02/DI-03/DI-13 的 `truth_source` |
| `biz_purchase_order.supplier_id` 是**快照**（V0193 注释） | DI-01 只报偏移，不自动改；DI-12 只查主档有效性 |
| `biz_stock_in.supplier_id` 是**冗余拷贝**（V0193 注释：可无歧义重算，漂移即缺陷） | DI-06 一律 `DEFECT`，无白名单 |
| `biz_snapshot_drift`（V0193 §4）+ 部分唯一索引 `uk_biz_drift_open` | 直接复用为结果表，只做 §4.2 的最小增强 |
| `v_biz_doc_edge` / `v_biz_doc_ref`（V0193 §5 追溯视图） | 本次不依赖；追溯 UI 与巡检各自读，互不耦合 |

## §2 巡检项清单（15 条，逐条业务含义 + 可执行 SQL）

### 2.0 先说清楚「旧表阶段怎么跑」

现状实测（2026-11-02，库 `cloudpivot_t7f4`，136 条迁移到 `V0192`）：

```
biz_purchase_order 27 列 → 无 contract_id、无 purchase_type（information_schema 实测）
biz_contract                  → 不存在（V0193 还是草案，未入 backend/migrations）
biz_contract_party_change     → 不存在
biz_stock_in                  → 有 source_order_id / supplier_id / status(DRAFT/POSTED/CANCELLED)
biz_payable                   → 有 source_type/source_id/supplier_id/status
biz_flow_instance             → 表在，但生产/测试库里没有 CONTRACT 类实例
```

所以「每条 SQL 现在就能跑」不能靠分支语句（PG 解析期就会因为引用不存在的列而报错），只能靠**一层只读兼容视图**：

```
di.v_po          ← 采购单：合同两列「有则直列、无则 to_jsonb(o)->>'contract_id' 取 NULL」
di.v_contract    ← 合同：V0193 之前 = WHERE FALSE 的零行空壳（JOIN 恒 0 行，不报错）
di.v_party_change← 乙方变更台账：无台账 = 零行空壳 ⇒ DI-01 一律按 P0 处理（保守）
di.di_capability ← capability 探测：contract_checks_ready = false 时合同类巡检必须记 SKIPPED
```

**关键纪律：0 行 ≠ 无缺陷。** 合同 schema 没就位时，DI-01…DI-05、DI-13 的 0 行必须被记成 `SKIPPED`（§3.4），否则看板上会出现「合同主体巡检全绿」的假象 —— 这比不巡检更危险。

安装脚本：`docs/architecture/snapshot-drift/00_install_compat.sql`（幂等，`CREATE OR REPLACE VIEW`，不建表、不写业务数据，回滚 `DROP SCHEMA di CASCADE`）。

### 2.1 输出契约（15 条共用）

每条巡检 = `di` schema 下一个只读视图，输出 11 列：

```
issue_code · entity_type · entity_id · entity_no · field_name
snapshot_value(实际观测) · truth_value(期望/真相) · truth_source
drift_kind(SNAPSHOT|DEFECT) · severity(INFO|WARN|ERROR) · affected_count
```

`severity` 就是告警分级载体：**ERROR = P0 / WARN = P1 / INFO = 白名单（只留痕不告警）**；`v_biz_data_integrity_issue` 视图（§4.3）把它翻成 `P0/P1/P2`。

### 2.2 卡面四条必做项 → 本设计的映射

| 卡面要求 | 本设计编号 | 说明 |
|---|---|---|
| `biz_purchase_order.supplier_id ≠ 其 contract.party_b_id` | **DI-01** | 三态判定（合法快照 / 快照未跟随 / 无台账疑似篡改），不是一律报错 |
| `biz_stock_in.supplier_id ≠ 其 source_order.supplier_id` | **DI-06** | 冗余拷贝 ⇒ 恒 DEFECT；已过账升级 P0 |
| `biz_purchase_order.contract_id` 指向的合同 `deleted_at` 非空 | **DI-02**（软删）+ **DI-03**（悬空） | 卡面只说软删；「指向的行根本不存在」是更严重的同级问题，拆开报 |
| `purchase_type='CONTRACT'` 但 `contract_id` 空 / `'SPOT'` 但 `supplier_id` 空 | **DI-04** / **DI-05** | 现状被 DB 约束拦住（恒 0 行）；价值在「约束被 drop 后立刻现形」，且 DI-14 会同时报护栏缺失 |

### 2.3 分级规则（P0/P1 的边界，一句话可判）

```
P0（ERROR）= 钱已经动过 或 追溯链已断 或 主体被无审批地改过
   ├ 合同采购单/入库单已 APPROVED/POSTED/RECEIVED/CLOSED，或其下游已有应付/凭证
   ├ 弱引用悬空（行根本不存在）
   └ DI-01 的「无变更台账」分支（疑似篡改，宁可错报）
P1（WARN） = 草稿态偏移、可重算的拷贝不一致、约束兜底命中、快照互斥
INFO       = 合法历史快照（合同确实换过乙方且PO建单在那之前）——只留痕，不进告警队列
```

### 2.4 逐条 SQL 与业务含义

> 全部 SQL 的规范版本在 `docs/architecture/snapshot-drift/10_checks.sql`（本节与它同文；若不一致以 SQL 文件为准，文件有自证脚本）。
> 每条都可单独执行，例：`select * from di.c_di06;`

#### DI-01 采购单供应商快照 ≠ 合同乙方（卡面第 1 条，P0/P1/INFO 三态）

**业务含义**：采购单建单时把合同乙方抄成 `supplier_id`（快照，审计要「当时是谁」）。合同事后换乙方是**真实合法业务**（供应关系转移），此时历史单据快照与今天真相必然不同 —— 那不是缺陷。真正要抓的是两种：① 合同乙方被**直接改库**（没有任何变更台账）→ 疑似篡改，涉资 P0；② 合同变更**之后新建**的单据还用了旧乙方 → 建单时快照没跟随真相，P1。

三态判定矩阵（**本设计的核心**）：

| 变更台账 | 采购单建单时刻 vs 变更时刻 | 判定 | 分级 | 粒度 |
|---|---|---|---|---|
| 有 | 建单 ≤ 变更 | `SNAPSHOT` 合法历史快照 | INFO（不告警） | 合同（聚合，`affected_count`=受影响单据数） |
| 有 | 建单 > 变更 | `DEFECT` 快照未跟随 | P1 | 单据 |
| 无 | —（且当前值 ≠ 快照） | `DEFECT` 疑似篡改 | **P0** | 合同（聚合，根因在合同，一张单一条会淹掉运维） |

**SQL**：

```sql
CREATE OR REPLACE VIEW di.c_di01 AS
WITH po AS (
    SELECT o.id AS po_id, o.order_no, o.supplier_id, o.status AS po_status,
           o.contract_id, o.created_at,
           c.contract_no, c.party_b_id,
           (SELECT max(pc.changed_at) FROM di.v_party_change pc WHERE pc.contract_id = c.id) AS changed_at
      FROM di.v_po o
      JOIN di.v_contract c ON c.id = o.contract_id
     WHERE o.deleted_at IS NULL
       AND c.deleted_at IS NULL
       AND o.purchase_type = 'CONTRACT'
       AND o.supplier_id IS DISTINCT FROM c.party_b_id      -- 用 IS DISTINCT FROM：NULL 不静默漏判
)
-- ① 有台账且建单不晚于变更 → 合法历史快照（合同粒度聚合，不进告警队列）
SELECT 'DI-01'::text, 'CONTRACT'::text, p.contract_id, p.contract_no::text, 'party_b_id'::text,
       min(p.supplier_id::text), min(p.party_b_id::text), 'biz_contract.party_b_id'::text,
       'SNAPSHOT'::text, 'INFO'::text, count(*)::int
  FROM po p WHERE p.changed_at IS NOT NULL AND p.created_at <= p.changed_at
 GROUP BY p.contract_id, p.contract_no, p.party_b_id
UNION ALL
-- ② 有台账但建单晚于变更 → 快照没跟随真相（单据粒度）
SELECT 'DI-01'::text, 'PURCHASE_ORDER'::text, p.po_id, p.order_no::text, 'supplier_id'::text,
       p.supplier_id::text, p.party_b_id::text, 'biz_contract.party_b_id'::text,
       'DEFECT'::text, 'WARN'::text, 1
  FROM po p WHERE p.changed_at IS NOT NULL AND p.created_at > p.changed_at
UNION ALL
-- ③ 无任何变更台账 → 主体被事后改过（合同粒度聚合 = P0 疑似篡改）
SELECT 'DI-01'::text, 'CONTRACT'::text, p.contract_id, p.contract_no::text, 'party_b_id'::text,
       min(p.supplier_id::text), min(p.party_b_id::text), 'biz_contract.party_b_id'::text,
       'DEFECT'::text, 'ERROR'::text, count(*)::int
  FROM po p WHERE p.changed_at IS NULL
 GROUP BY p.contract_id, p.contract_no;
```

> 白名单为什么不用 `contract.updated_at`？改一条备注也会推高它 —— 会把「合法变更」误判成「快照没跟随」，同时把「真篡改」掩盖成「有更新」。台账只认**乙方变更**这一种事实（`biz_contract_party_change`，草案 `V0195`，见 §7）。

#### DI-02 采购单引用的合同已软删（卡面第 3 条，P0/P1）

**业务含义**：合同被删了，但还在被有效单据引用 —— 说明删除时没看下游（应用层本该 409）。已审批/已过账的单据失去合同依据，等于「付了钱但没有合同」（涉资 P0）。

```sql
CREATE OR REPLACE VIEW di.c_di02 AS
SELECT 'DI-02'::text, 'PURCHASE_ORDER'::text, o.id, o.order_no::text, 'contract_id'::text,
       ('DELETED@' || to_char(c.deleted_at, 'YYYY-MM-DD HH24:MI:SS'))::text,
       ('CONTRACT# ' || c.contract_no)::text,
       'biz_contract.deleted_at'::text,
       'DEFECT'::text,
       CASE WHEN o.status IN ('APPROVED','PARTIAL_RECEIVED','RECEIVED','CLOSED')
             OR EXISTS (SELECT 1 FROM biz_stock_in s
                         WHERE s.source_order_id = o.id AND s.deleted_at IS NULL AND s.status = 'POSTED')
            THEN 'ERROR' ELSE 'WARN' END,
       1
  FROM di.v_po o
  JOIN di.v_contract c ON c.id = o.contract_id
 WHERE o.deleted_at IS NULL AND c.deleted_at IS NOT NULL;
```

#### DI-03 采购单 `contract_id` 悬空（P0）

**业务含义**：指向的行**根本不存在**（跨库拷贝、迁移漏行、手工改库）。追溯链到此断掉，比「指向已删」更严重 —— 已删至少还能读出当时是谁。

```sql
       'DEFECT'::text, 'ERROR'::text, 1
  FROM di.v_po o
  LEFT JOIN di.v_contract c ON c.id = o.contract_id
 WHERE o.deleted_at IS NULL AND o.contract_id IS NOT NULL AND c.id IS NULL;
```

#### DI-06 入库单供应商 ≠ 来源采购单供应商（卡面第 2 条，P0/P1）

**业务含义**：入库单这层的 `supplier_id` 是**冗余拷贝**（V0193 注释明说「能由上游无歧义重算，漂移即缺陷」），所以任何不一致都没有「合法变更」解释 —— 要么建单时取错，要么被人改过。已过账或已生成应付 = 钱和货的对手方不一致，一律 P0。

```sql
CREATE OR REPLACE VIEW di.c_di06 AS
SELECT 'DI-06'::text, 'STOCK_IN'::text, s.id, s.in_no::text, 'supplier_id'::text,
       s.supplier_id::text, o.supplier_id::text, 'biz_purchase_order.supplier_id'::text,
       'DEFECT'::text,
       CASE WHEN s.status = 'POSTED'
             OR EXISTS (SELECT 1 FROM biz_payable p
                         WHERE p.source_type = 'STOCK_IN' AND p.source_id = s.id
                           AND p.deleted_at IS NULL AND p.status <> 'CANCELLED')
            THEN 'ERROR' ELSE 'WARN' END,
       1
  FROM biz_stock_in s
  JOIN biz_purchase_order o ON o.id = s.source_order_id
 WHERE s.deleted_at IS NULL AND o.deleted_at IS NULL
   AND s.supplier_id IS DISTINCT FROM o.supplier_id;
```

```sql
CREATE OR REPLACE VIEW di.c_di07 AS
```


#### DI-09 采购入库（`in_type='PURCHASE'`）但供应商为空（P1）

**业务含义**：同上 DI-05，应付与凭证无法生成。`ck_biz_si_supplier` 已拦，本项为约束缺失时的兜底。

```sql
       'DEFECT'::text, 'WARN'::text, 1
  FROM biz_stock_in s
 WHERE s.deleted_at IS NULL AND s.in_type = 'PURCHASE' AND s.supplier_id IS NULL;
```

#### DI-10 应付单供应商 ≠ 来源入库单供应商（P0，资金链）

**业务含义**：钱付给了和实物入库不同的人 —— 「涉资」的典型形态。这条不依赖合同 schema，**今天就能跑**，是本设计里最快产生现实价值的一条。

```sql
CREATE OR REPLACE VIEW di.c_di10 AS
SELECT 'DI-10'::text, 'PAYABLE'::text, p.id, p.payable_no::text, 'supplier_id'::text,
       p.supplier_id::text, s.supplier_id::text, 'biz_stock_in.supplier_id'::text,
       'DEFECT'::text,
       CASE WHEN p.status = 'CANCELLED' THEN 'WARN' ELSE 'ERROR' END, 1
  FROM biz_payable p
  JOIN biz_stock_in s ON s.id = p.source_id
 WHERE p.deleted_at IS NULL AND s.deleted_at IS NULL
   AND p.source_type = 'STOCK_IN'
   AND p.supplier_id IS DISTINCT FROM s.supplier_id;
```

#### DI-11 应付来源入库单悬空 / 已软删（P0，扩展项）

**业务含义**：应付必须能追回入库单，否则无法对账、无法做三单匹配。这条与「快照」无关但与「可追溯」同源，扫描成本≈0，故一并纳入。

```sql
CREATE OR REPLACE VIEW di.c_di11 AS
SELECT 'DI-11'::text, 'PAYABLE'::text, p.id, p.payable_no::text, 'source_id'::text,
       p.source_id::text,
       CASE WHEN s.id IS NULL THEN 'STOCK_IN_ROW_MISSING' ELSE 'STOCK_IN_DELETED' END::text,
       'biz_stock_in.id'::text, 'DEFECT'::text, 'ERROR'::text, 1
  FROM biz_payable p
  LEFT JOIN biz_stock_in s ON s.id = p.source_id
 WHERE p.deleted_at IS NULL AND p.source_type = 'STOCK_IN'
   AND (s.id IS NULL OR s.deleted_at IS NOT NULL);
```

#### DI-12 采购单供应商主档悬空 / 已软删（P0/P1）

**业务含义**：供应商主档被删，历史单据还在引用。软删（WARN）本身不是错，但它让「当时是谁」只能靠快照名兜底；悬空（ERROR）则是追溯链彻底断掉。

```sql
CREATE OR REPLACE VIEW di.c_di12 AS
SELECT 'DI-12'::text, 'PURCHASE_ORDER'::text, o.id, o.order_no::text, 'supplier_id'::text,

  FROM di.v_po o
  LEFT JOIN biz_supplier sp ON sp.id = o.supplier_id
 WHERE o.deleted_at IS NULL AND (sp.id IS NULL OR sp.deleted_at IS NOT NULL);
```

#### DI-13 同一合同下快照互斥（P1）

**业务含义**：一份合同的乙方只有一个真相；若它名下的采购单快照出现**多个不同供应商**，至多一张是对的 —— 且这种分歧**不可能**由「合同换乙方」解释（换乙方只会造成「新旧两代」，不会造成同代内互斥）。它与 DI-01 不重复：DI-01 对比真相，DI-13 抓自相矛盾。

```sql
CREATE OR REPLACE VIEW di.c_di13 AS
SELECT 'DI-13'::text, 'CONTRACT'::text, o.contract_id, c.contract_no::text, 'supplier_id'::text,
       string_agg(DISTINCT o.supplier_id::text, ','), c.party_b_id::text,
       'biz_contract.party_b_id'::text, 'DEFECT'::text, 'WARN'::text,
       count(DISTINCT o.supplier_id)::int
  FROM di.v_po o
  JOIN di.v_contract c ON c.id = o.contract_id
 WHERE o.deleted_at IS NULL AND c.deleted_at IS NULL AND o.purchase_type = 'CONTRACT'
 GROUP BY o.contract_id, c.contract_no, c.party_b_id
HAVING count(DISTINCT o.supplier_id) > 1;
```

#### DI-14 结构护栏自检（P0，巡检自己的可信度）

**业务含义**：巡检依赖 DB 约束兜住上限（`ck_biz_po_contract_pair`、`ck_biz_si_supplier`、`ck_biz_po_tax_sum`）与自己的去重护栏（部分唯一索引 `uk_biz_drift_open`）。护栏被 drop 后：缺陷会先落库再被发现，且「修复后再发生」因索引丢失而永远写不进来（= 漏报）。所以护栏缺失本身必须是 P0。

```sql
CREATE OR REPLACE VIEW di.c_di14 AS
WITH expect AS (
    SELECT 'CONSTRAINT'::text AS kind, 'ck_biz_po_tax_sum'::text AS obj, 'public.biz_purchase_order'::text AS rel
    UNION ALL SELECT 'CONSTRAINT','ck_biz_po_purchase_type','public.biz_purchase_order'
     WHERE (SELECT contract_checks_ready FROM di.di_capability)
    UNION ALL SELECT 'CONSTRAINT','ck_biz_po_contract_pair','public.biz_purchase_order'
     WHERE (SELECT contract_checks_ready FROM di.di_capability)
    UNION ALL SELECT 'CONSTRAINT','ck_biz_si_supplier','public.biz_stock_in'
    UNION ALL SELECT 'PARTIAL_INDEX','uk_biz_drift_open','public.biz_snapshot_drift'
     WHERE to_regclass('public.biz_snapshot_drift') IS NOT NULL
), missing AS (
    SELECT e.kind, e.obj FROM expect e
     WHERE (e.kind = 'CONSTRAINT'
            AND NOT EXISTS (SELECT 1 FROM pg_constraint c
                             WHERE c.conname = e.obj AND c.conrelid = e.rel::regclass))
        OR (e.kind = 'PARTIAL_INDEX'
            AND NOT EXISTS (SELECT 1 FROM pg_indexes i
                             WHERE i.indexname = e.obj
                               AND i.schemaname = split_part(e.rel,'.',1)
                               AND i.tablename  = split_part(e.rel,'.',2)
                               AND i.indexdef LIKE '%resolved_at IS NULL%'))
)
SELECT 'DI-14'::text, 'SYSTEM'::text, '00000000-0000-0000-0000-000000000000'::uuid,
       'schema_guard'::text, 'constraint'::text,
       ('MISSING:' || string_agg(m.kind || ':' || m.obj, ',' ORDER BY m.obj))::text,
       'ALL_PRESENT'::text, 'pg_constraint / pg_indexes'::text,
       'DEFECT'::text, 'ERROR'::text, 1
  FROM missing m GROUP BY 1;
```

**业务含义**：合同 `TERMINATED`/`COMPLETED` 之后，其名下还有未走完的采购单 —— 这些单据的乙方真相来自一份「已经不被允许继续履约」的合同。跨卡对应：通用勾稽规则卡的 **I-P5**（本卡把它落成可执行 SQL，避免只停留在文字口径）。

## §3 巡检执行方式

### 3.1 Cron（与仓库既有调度同一套 6 段 cron，`sys_job.invoke_target` 命名同款）

| 档位 | cron | 触发内容 | 为什么这个时间 |
|---|---|---|---|
| 增量档 | `0 */30 * * * *` | 只扫「最近 40 分钟内 `updated_at` 变化」的主体 + 其直接下游 | 30 分钟足够让「改库」在半小时内被发现；错峰到整点后 0 秒，比 `*/30` 的边界更可控 |
| 全量档 | `0 20 2 * * *` | keyset 全表逐批（15 条全跑） | 02:20：在 02:00 备份之后、03:00 五张日志清理之前、04:30 存储回收之前，避开所有重任务 |
| 护栏档 | `0 45 2 * * *` | 只跑 DI-14（结构自检） | 独立一条：DI-14 挂了要单独可见，不能被别的项拖慢 |

> 与既有任务不撞车（实测自 `src/task/mod.rs` 的表：3:00/3:10/3:20/3:30/3:40 清理、3:50 令牌、4:30 存储、2:00 前后分区运维）。任务名建议 `di_snapshot_scan_incremental` / `di_snapshot_scan_full` / `di_schema_guard`。

### 3.1b 实现骨架直接沿用本仓现成的巡检范本

本仓已有一处「派生值 vs 真相」巡检：库存数量 vs 在库序列号件数（`backend/src/business/erp/inventory_audit.rs`，接口 `GET /business/erp/inventory/audit`，权限码 `business:erp:inventory:audit`，`dry_run` 默认 `true`，只报不修，反向缺账也查）。本设计的实现骨架与它保持一致，不自创：

| 维度 | 沿用范本的做法 |
|---|---|
| 手动触发 | `GET /api/business/erp/data-integrity/scan?dry_run=true`（默认只读；`dry_run=false` 才落 `biz_snapshot_drift`） |
| 只报不修 | 扫描接口无写业务表路径；处置必须走 §6 独立接口 + 权限码 |
| 权限码 | 四段式 `business:erp:data_integrity:{scan|list|fix|freeze|ignore}`，落 `sys_menu.auth_code`（V0143 同款） |
| 双向检查 | 不只查「有 A 无 B」，也查「有 B 无 A」：DI-03/08/11 就是反向缺账（引用悬空） |

### 3.2 单次扫描量控制：keyset 分页，绝不用 OFFSET

```
每批 2000 行 → 单轮最多 50 批（10 万行）→ 未扫完则记「本轮未完成」，watermark 留到下一轮继续
分页键：o.id（uuid 稳定有序且无热点），WHERE o.id > :last_id ORDER BY o.id LIMIT 2000
```

- **不用 `OFFSET`**：深翻页会退化成全表扫 + 丢弃，越跑越慢。
- **不用 `updated_at >= :since` 做唯一判据**（增量档做**预筛**可以）：时间戳会被长事务/时钟回拨打漏；全量档必须有一遍 keyset 兜底。
- **一批一事务**：批事务里「扫描 + upsert」一起提交，超时只丢一批，不会整轮回滚。
- 增量档的预筛写法（DI-06 为例）：`AND (s.updated_at >= :since - interval '10 min' OR o.updated_at >= :since - interval '10 min')`，多带 10 分钟重叠窗口防边界漏。

### 3.3 只读执行：三级保护

```sql
BEGIN READ ONLY;                                   -- ① 事务级只读：任何写操作直接报错，杜绝巡检改业务数据
SET LOCAL statement_timeout = '30s';               -- ② 单条语句上限：慢查询自己死，不拖垮库
SET LOCAL idle_in_transaction_session_timeout = '60s';
-- ③ 只扫「未删除」分区/索引可见行；不做 SELECT ... FOR UPDATE，不加任何表锁
```

- 结论：巡检**只读业务表**，唯一的写是结果表 `biz_snapshot_drift` 与告警表 `sys_notice`，且都是行级写（无表锁）。
- 副本策略：本仓当前**没有第二数据源**（实测 `config/*.toml` 无 replica/read-only 配置）→ 阶段 1 在主库以 `READ ONLY` 事务 + `statement_timeout` 跑；阶段 2 引入只读副本需框架支持第二 datasource，列为未决项（§10）。
- 若将来接副本，必须先做 **lag guard**：`now() - pg_last_xact_replay_timestamp()` 超过 60s 就跳过本轮（副本延迟会导致「缺陷看起来还在」的假收敛 → 误 RESOLVED）。

### 3.4 幂等：四个层次

1. **结果幂等**：`INSERT ... ON CONFLICT (issue_code, entity_type, entity_id, field_name) WHERE resolved_at IS NULL DO UPDATE` —— 重跑只刷新 `last_seen_at` 与观测值，`detected_at` 不变。
2. **告警幂等**：`sys_notice.idempotency_key = 'di:{drift_id}:OPEN'`（表已有 `uk_sys_notice_idem` 部分唯一索引），同一缺陷只发一次；摘要键 `di:digest:{issue_code}:{YYYYMMDDHH}` 一小时一封。
3. **执行幂等**：`SELECT pg_try_advisory_lock(hashtext('cloudpivot.di.job'))` —— 实测**跨会话互斥**（第二个会话返回 `f`，同会话可重入，实现时必须用独立连接），拿不到锁就跳过本轮（多实例/手工触发并发时不产生双份告警）。
4. **收敛幂等**：只按 `last_seen_at < run_started` 收敛，重复执行第二轮不会再改任何已收敛行。

### 3.5 SKIPPED 语义（0 行 ≠ 无缺陷）

`di.v_check_state` 把每个巡检项标成 `CHECKED` / `SKIPPED`（依赖合同 schema 的 5 项在 V0193 之前一律 `SKIPPED`）。两条用途：

- **看板**：「本轮 14 项、9 项 checked、5 项 skipped」必须可见，否则合同巡检永远是「全绿」的假象；
- **收敛**：`SKIPPED` 的项一行都不许收敛（否则 schema 未就绪时会把历史真缺陷自动「治好」，这是本设计最危险的失败模式）。

## §4 结果落库设计

### 4.1 ADR：为什么不新建 `biz_data_integrity_issue`（复用 `biz_snapshot_drift`）

| 选项 | 评价 |
|---|---|
| **A 复用 `biz_snapshot_drift`（V0193 §4 已设计）** ✅ | 表结构已覆盖 90%：`entity_type/entity_id/entity_no/field_name/snapshot_value/truth_value/truth_source/drift_kind/severity/affected_count/detected_at/last_seen_at/resolution/resolved_by/resolved_at/remark`；且已有部分唯一索引 `uk_biz_drift_open` 正好是去重所需的形状；`drift_kind=SNAPSHOT/DEFECT` 已经表达了「合法变更 vs 缺陷」——这正是本设计的分级基础 |
| B 新建 `biz_data_integrity_issue` | 同一事实两处维护。合同漂移会被架构师的合同卡写进 `biz_snapshot_drift`，巡检再写一张表 = 同一缺陷两份记录，谁先谁后必有一天打架。**违反 SSOT** |
| C 复用告警表 `sys_notice` | 告警是「通知」，不是「状态」。`sys_notice` 没有「未解决/已解决」生命周期、没有首次/末次检出时间，无法承载收敛与看板 |

**决定：A**。代价是必须给 `biz_snapshot_drift` 打两个小补丁（§4.2），这比引入第二张表便宜得多。卡面允许「或复用现有告警表」，本设计选的是「复用架构已设计的漂移表」，并在 §4.6 给出独立表 DDL 作为审查备选（两者二选一，禁止并存）。

```sql
 WHERE resolved_at IS NULL;
```

> V0193 尚未发版 ⇒ 表内无存量行，索引可无痛替换（有存量时须先回填 `issue_code`）。

### 4.3 卡面字段 → 实际列（派生视图，不新增第二列）

```sql
CREATE OR REPLACE VIEW v_biz_data_integrity_issue AS
SELECT d.id,
       d.issue_code                            AS issue_type,
       CASE d.entity_type
           WHEN 'PURCHASE_ORDER' THEN 'biz_purchase_order'
           WHEN 'STOCK_IN'       THEN 'biz_stock_in'
           WHEN 'CONTRACT'       THEN 'biz_contract'
           WHEN 'SUPPLIER'       THEN 'biz_supplier'
           WHEN 'PAYABLE'        THEN 'biz_payable'
           ELSE lower(d.entity_type) END       AS biz_table,
       d.entity_id                             AS biz_id,
       d.entity_no                             AS biz_no,
       d.field_name,
       d.truth_value                           AS expected_value,
       d.snapshot_value                        AS actual_value,
       d.truth_source,
       d.drift_kind,
       CASE d.severity WHEN 'ERROR' THEN 'P0' WHEN 'WARN' THEN 'P1' ELSE 'P2' END AS priority,
       d.severity, d.affected_count,
       d.detected_at                           AS first_detected_at,
       d.last_seen_at                          AS last_detected_at,
       CASE WHEN d.resolved_at IS NULL THEN 'OPEN'
            WHEN d.resolution = 'IGNORED' THEN 'IGNORED'
            ELSE 'RESOLVED' END                AS status,
       d.resolution, d.resolved_by, d.resolved_at, d.remark
  FROM biz_snapshot_drift d;
```

**为什么 `status` 派生而不是落列**：`status` 与 `resolution/resolved_at` 是同一事实的两种写法，落两列必然在某一天不一致（谁能保证两处同步改？）。派生视图零成本，且卡面要求的 `OPEN/RESOLVED/IGNORED` 语义完全可达：

| 卡面 status | 实际存储 | 含义 |
|---|---|---|
| `OPEN` | `resolution IS NULL` | 仍未解决（也是唯一键的过滤条件） |
| `RESOLVED` | `resolution IN ('REPAIRED','ACCEPTED')` | 已修复 / 已认可为合法变更 |
| `IGNORED` | `resolution = 'IGNORED'` | 人工忽略（见 §5.4：复发会自动新开一条，忽略不掩盖） |

### 4.4 RUN 级状态不另建表

一轮巡检的「跑了哪些项 / 有几项 skipped / 扫了多少行 / 耗时」写 `sys_job_log`（已有表，`sys_job.invoke_target` 与任务名同值）：

```
status   = 1 成功 / 0 失败
message  = 'checked=9 skipped=5 drift_open=19 p0=15 p1=3 batches=3 scanned=21480 new=4 converged=2'
error    = 异常原文（成功为空）
duration_ms
```

### 4.5 索引与容量

| 索引 | 用途 |
|---|---|
| `uk_biz_drift_open (issue_code, entity_type, entity_id, field_name) WHERE resolved_at IS NULL` | upsert 冲突目标 + 「同一缺陷只有一条未决」 |
| `idx_biz_drift_code_open (issue_code, severity) WHERE resolved_at IS NULL` | 看板「按巡检项看 P0/P1 未决数」 |
| `idx_biz_drift_open_time (detected_at DESC) WHERE resolved_at IS NULL`（V0193 已有） | 待办列表倒序 |
| `idx_biz_drift_entity (entity_type, entity_id, detected_at DESC)`（V0193 已有） | 单据详情页的「历史缺陷」时间线 |

容量估算：稳态下未决行数 = 真实缺陷数（正常情况下 < 50 行）；`SNAPSHOT` 类按合同聚合（POC 里一次合同换乙方影响 20,001 张单据 → 只落 1 行 + `affected_count=20001`），不会因批量变更把表撑爆。已解决行按年归档（`resolved_at < now() - interval '2 year'` 可删，与日志清理同款策略）。

### 4.6 备选方案 DDL（仅当架构裁决要独立表时启用）

文件：`V0194_alt__biz_data_integrity_issue.up.sql`。要点：`issue_type/biz_table/biz_id/biz_no/field_name/expected_value/actual_value/truth_source/drift_kind/severity/affected_count/first_detected_at/last_detected_at/status(OPEN/RESOLVED/IGNORED)/resolved_by/resolved_at/remark`，唯一键 `(issue_type, biz_table, biz_id, coalesce(field_name,'')) WHERE status='OPEN'`，`ck_dii_resolved` 用 `CASE WHEN status='OPEN' THEN resolved_at IS NULL AND resolved_by IS NULL ELSE resolved_at IS NOT NULL END` 钉死「已处置必有时间」。

⚠️ 若选独立表，则必须同时改造架构师 V0193 的那条巡检 SQL 写入点，否则同一缺陷会同时出现在两张表 —— 这是选 B 的隐性成本，请架构裁决时计入。

## §5 告警通道与分级

### 5.1 通道

| 通道 | 用途 | 落点 |
|---|---|---|
| 站内信 + SSE 实时推送 | P0 即时（在线用户 0 延迟看到） | `sys_notice` + 已有 `notice/sse_hub` |
| 定时摘要 | P1（每小时一封） | `sys_notice`（`channel_mask=1`） |
| Webhook / 邮件 | P0 值班群（生产配置项 `di.alert.p0_channels` 决定 `channel_mask`） | `sys_notice_delivery` |
| 指标 | 长周期趋势与告警 | `metrics` feature：`cloudpivot_di_open_issues{code,severity}` / `cloudpivot_di_scan_seconds` / `cloudpivot_di_skipped_checks` |

> 实现注意：告警**不要直接 INSERT `sys_notice`**（会绕过收件人扇出与 SSE），应调用 notice 域既有创建接口，幂等键同上；本文给出的 SQL 是它的等价语义与去重契约。

### 5.2 分级与路由

| 级别 | 判据（§2.3） | 投递 | 响应要求 |
|---|---|---|---|
| **P0** | 涉资（已过账/已生成应付）、追溯链断裂（悬空）、无审批的主体篡改、护栏缺失 | 逐条即时，站内信 + SSE + 值班群 | 当班处理；未处理则巡检每轮刷新 `last_seen_at`，不再重复发（同一 id） |
| **P1** | 草稿态偏移、可重算拷贝不一致、结构兜底命中、快照互斥 | 按「巡检项 + 小时」合并摘要 | 一个工作日内 |
| INFO | 合法历史快照（`drift_kind=SNAPSHOT`） | **不进告警队列**，只落表 + 看板「已认可变更」页签 | 无需处理，审计可查 |

### 5.3 去重（三层，缺一不可）

1. **数据层**：部分唯一索引 `uk_biz_drift_open` ⇒ 同一条缺陷永远只有一条未决行（P0 刷 1 万轮也只有 1 行）。
2. **通知层**：`idempotency_key='di:{drift_id}:OPEN'` ⇒ 同一条缺陷只发一次通知；升级（P1→P0）时补发一条 `:ESC`（键不同，允许一次升级提醒）。
3. **摘要层**：P1 按 `{issue_code}:{YYYYMMDDHH}` 合并 ⇒ 同一巡检项每小时最多一封，一封内是「N 条 + 样例」，不做逐条轰炸。

### 5.4 收敛（问题消失自动 RESOLVED）

```
S2: UPDATE biz_snapshot_drift
       SET resolution = CASE WHEN drift_kind='SNAPSHOT' THEN 'ACCEPTED' ELSE 'REPAIRED' END,
           resolved_at = now(), remark = ... 'auto-closed: 本轮未再检出'
     WHERE resolved_at IS NULL
       AND last_seen_at < :run_started                       -- 本轮没碰到
       AND issue_code IN (SELECT issue_code FROM di.v_check_state WHERE run_state='CHECKED')  -- 本轮真跑过
```

- `SNAPSHOT` 收敛写 `ACCEPTED`（它本来就不是缺陷），`DEFECT` 收敛写 `REPAIRED`。
- **自动收敛 ≠ 「人修好了」**：`remark` 明确写 auto-closed，`resolved_by` 保持 NULL；人工处置的才写 `resolved_by`（审计能区分「系统不再检出」与「某人修复」）。
- **恢复回执**：本轮新关闭的缺陷发一条「已恢复」通知（幂等键 `di:{id}:RESOLVED`，`level=SUCCESS`）。没有回执的话，P0 告警发出去后系统自己不再检出，值班会一直以为还坏着。
- **复发**：因为唯一索引只在 `resolved_at IS NULL` 上生效，复发会**新开一条**（新 `detected_at`）—— 历史那条仍是 REPAIRED。这正是审计要的「两次独立事件」，也是卡面第 6 条要求的语义。

### 5.5 误报控制（运维最关心的一件事）

| 噪音源 | 处置 |
|---|---|
| 合同合法变更波及大量历史单据 | `SNAPSHOT/INFO` + 合同粒度聚合，不进告警队列（§7 白名单） |
| 夹具/历史脏数据首跑刷屏 | 上线首轮 `di.alert.dry_run=true`：只落表不推送；人工基线处置后再开推送（实测证据见 §9.3：首跑即检出 6 条历史残留应付） |
| 同一缺陷反复横跳（修了又坏） | 每条独立成行 + P0 只在「新开」时推送；1 小时内反复横跳会产生多条 P0 —— 需要人查根因，这是**故意吵**（横跳通常意味着有人在改库） |
| 维护窗口批量改数据 | `sys_config` 白名单窗口（`di.scan.mute_window`）内 P1 不进摘要，P0 照发 |

## §6 修复路径设计（只报告，不自动改数据）

### 6.1 铁律

1. 巡检任务**没有任何写业务表的权限**（`READ ONLY` 事务 + 无 `UPDATE` 语句），从机制上保证「只报告」。
2. 处置只能由人在接口上发起，且**必须带原因**、**必须落审计**。
3. 任何处置**不级联**下游单据：DI-01 修了合同的台账，下游入库单/应付的各自 issue 仍要各自处置（每张单的判断依据不同）。

### 6.2 两个处置动作（接口语义）

#### 动作 A：`refresh-snapshot`（以真相为准刷新快照）

```
POST /api/business/erp/data-integrity/issue/{id}/refresh-snapshot
权限码：business:erp:data_integrity:fix（SUPER_ADMIN 短路；与既有 `business:erp:inventory:audit` 同款四段式）
Body  ：{ "expected_updated_at": "2026-11-02T10:11:12+08:00", "reason": "合同 HT-2026-0007 换乙方，P8 建单时取旧值" }
```

| 项 | 约定 |
|---|---|
| 适用范围 | 仅 `drift_kind='DEFECT'` 且 `issue_code IN (DI-01②, DI-06, DI-12)`（快照/拷贝类）；`SNAPSHOT` 类与悬空类拒绝（400 + 明确 reason） |
| 写入范围 | 只改 `field_name` 对应的**一列**（`supplier_id`），不碰金额、状态、任何下游 |
| 乐观锁 | `expected_updated_at` 必须等于主体当前 `updated_at`，否则 409 `DATA_INTEGRITY.STALE_READ`（避免用旧真相覆盖新变更） |
| 同一事务 | ① `UPDATE` 主体单列；② 关闭 issue（`resolution='REPAIRED'`, `resolved_by`, `resolved_at`）；③ 写 `audit_logs`（`operation='DI_REFRESH_SNAPSHOT'`, `before_data/after_data` = 该行改动前后的 JSON、`detail` = issue 快照） |
| 幂等 | issue 已关闭 ⇒ 409 `DATA_INTEGRITY.ISSUE_CLOSED`；`UPDATE` 加 `WHERE updated_at = :expected`，重复提交第二次影响 0 行 ⇒ 409 |
| 审计要求 | `audit_logs` 必写（不可关闭）；`operation_logs` 由中间件写；出参返回 `before/after` 与 `audit_id` |

#### 动作 B：`freeze-truth-as-snapshot`（以快照为准冻结真相，需审批）

```
POST /api/business/erp/data-integrity/issue/{id}/freeze-truth-as-snapshot
权限码：business:erp:data_integrity:freeze + business:erp:contract:amend（两个都要）
Body  ：{ "reason": "乙方主体被误改，实际合同主体应为 A 公司（见合同扫描件）", "attachment_ids": ["..."] }
```

| 项 | 约定 |
|---|---|
| 语义 | 不把上游改回去就完事，而是**发起一次正式变更**：以快照值为目标值，走合同乙方变更审批（`flow`，`biz_type='CONTRACT_AMEND'`）；审批通过后在同一事务里 ① 回写 `contract.party_b_id = 快照值`；② 追加 `biz_contract_party_change` 台账（`old/new/instance_id/operator`）；③ issue → `ACCEPTED`（等待审批期间保持 `OPEN` 但标记 `pending_instance_id`）；④ 写 `audit_logs` |
| 禁止场景 | `issue_code='DI-10'`（资金链供应商不一致）**禁止**用本动作（403 `DATA_INTEGRITY.MONEY_CHAIN_LOCKED`）—— 钱已付给第三方时，「把真相改成跟记录一致」就是掩盖挪用；必须走资金侧冲销/红冲流程 |
| 审批 | 必须走 `flow` 实例，不许直接改库；审批被驳回 ⇒ issue 回到 `OPEN` 并发 P0 |
| 审计 | 一个动作三处留痕：`audit_logs`（动作）+ `biz_contract_party_change`（业务台账）+ 审批实例（流程） |

#### 动作 C：`ignore`（忽略，仅 P1）

```
POST /api/business/erp/data-integrity/issue/{id}/ignore
Body: { "reason": "该单据为历史测试数据，2026-11 已确认", "expire_at": "2027-01-31" }
```

- 仅 `severity='WARN'` 且 `drift_kind='DEFECT'` 可忽略；P0 一律不可忽略（要关就修）。
- 写入 `resolution='IGNORED'` + `resolved_by` + `remark`；因唯一键只在未决行生效，**下一轮若仍检出就会新开一条 OPEN** —— 忽略不会掩盖复发，这是刻意的。
- `expire_at` 到期后巡检把 issue 重新置 OPEN（避免「一键永久静音」）。

### 6.3 处置动作 × 巡检项 矩阵

| 巡检项 | A 刷新快照 | B 冻结真相（审批） | C 忽略 |

| DI-01② 快照未跟随 | ✅ 首选 | 不适用 | ✅ |
| DI-01③ 无台账篡改 | ❌ | ✅ 首选 | ❌ |
| DI-02/03/07/08/11 悬空/软删 | ❌ | ❌ | ✅（仅 P1 的软删类） |

## §7 与合同变更流程的联动（白名单，避免巡检噪音）

### 7.1 结论：要联动，且联动的载体必须是「台账」而不是「updated_at」

合同 `party_b_id` 变更时，**主动**为该合同名下的单据登记「已知偏移」，但不能用一条 UPDATE 把巡检要报的东西提前抹掉（那等于让巡检闭嘴）。正确做法是**登记事实**：

1. 合同乙方变更**必须**走审批（`flow`，`biz_type='CONTRACT_AMEND'`），审批通过的事务内：
   - `UPDATE biz_contract SET party_b_id = :new`；
   - `INSERT INTO biz_contract_party_change (contract_id, old_party_b_id, new_party_b_id, changed_at=now(), instance_id, operator_id, reason)`；
   - 不触碰任何采购单/入库单（快照按定义不动）。
2. 巡检侧：`di.v_party_change` 读台账，DI-01 据此把偏移分成「合法历史快照（INFO）」与「快照未跟随（P1）」；**没有台账 ⇒ 一律 P0**。
3. 于是「白名单」不是一个需要维护的名单，而是**变更流程自己产生的证据**：流程走过 → 有台账 → 不吵；没走过 → 没台账 → 吵。白名单无法被遗忘，也无法被伪造（伪造要写台账，台账有 `instance_id` 与操作人）。

### 7.2 台账表（草案 `V0195__biz_contract_party_change.up.sql`）

```sql
CREATE TABLE IF NOT EXISTS biz_contract_party_change (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    contract_id    UUID        NOT NULL,        -- 弱引用 biz_contract.id（本仓零外键基线）
    old_party_b_id UUID,
    new_party_b_id UUID        NOT NULL,
    changed_at     TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    instance_id    UUID,                        -- 变更审批实例
    operator_id    UUID,
    reason         TEXT,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT ck_bcpc_no_self CHECK (old_party_b_id IS NULL OR old_party_b_id <> new_party_b_id)
);
CREATE INDEX IF NOT EXISTS idx_bcpc_contract ON biz_contract_party_change (contract_id, changed_at DESC);
```

> 若架构裁决「不建台账表」，退化方案：`di.v_party_change` 改读 `biz_flow_instance`（`biz_type='CONTRACT'` + `status='APPROVED'`），已实现并实测可跑；但精度更差（无法区分「改备注」与「改乙方」，也无法记录 old/new），**不建议**。

### 7.3 变更审批通过后的自动化（可选增强）

审批通过后，可对受影响单据**批量刷新快照**吗？**不行** —— 那会让历史单据显示今天的乙方，审计失去「当时是谁」。可选的是：对「变更之后才建、且用了旧乙方」的那批（DI-01②）在变更流程里顺手提示，但修复动作仍需人工确认（因为无法自动判断「建单时到底该用哪个」）。

## §9 验证证据（真机实测，非推演）

环境：PostgreSQL 18.6（`/var/run/postgresql`），两个库均由生产同源库模板复制：

- `cp_di_now` = `cloudpivot_t7f4`（136 迁移到 V0192）→ **旧表阶段**
- `cp_di_fut` = 同上 + 架构师 V0193 草案 + 本设计 V0194/V0195 → **合同 schema 就位阶段**

### 9.1 兼容层在两阶段都能装、都能跑

```
cp_di_now: has_contract_table=f has_po_contract_id=f contract_checks_ready=f
cp_di_fut: has_contract_table=t has_po_contract_id=t contract_checks_ready=t
```

15 条巡检在**旧表阶段**全部执行成功（无一条语法/解析错误），且合同类正确返回 0 行：

```
DI-01..DI-05, DI-13, DI-15 = 0 行（v_check_state 标 SKIPPED）
DI-06..DI-12, DI-14 → 正常执行（CHECKED），其中 DI-11 = 6 行
```

> 那 6 行是测试库里的**夹具残留**（`P2C2-AP-0001..0005`、`AP-D5-83676d26` 指向不存在的入库单），不是生产缺陷 —— 但它正好演示了「巡检上线首跑会先暴露历史脏数据」，所以上线首轮必须 `dry_run`（§5.5）。

### 9.2 每条巡检都能抓到它声称的缺陷（`cp_di_fut` + 构造夹具）

构造 10 张采购单 / 3 张入库单 / 2 张应付 / 4 份合同（含 1 份软删、1 份已终止、1 份有乙方变更台账），跑 15 条（11 条命中，DI-04/05/09/14 因护栏完好按设计返回 0 行）：

### 9.3 幂等 / 收敛 / 复发（跑同一轮 4 次）

```
run1（首次）      ：open=20  P0=16  total=20  通知=19（16 条 P0 逐条 + 3 条 P1 摘要）
run2（原样重跑）  ：open=20  P0=16  未决行 id 集合 md5 完全相同  detected_at 不变  通知=19（零新增）
修复夹具(P2 改回真相) → run3：open=18  P0=15  通知=21（+2「已恢复」回执）
                            DI-01/DI-13 的 CT-1 行自动 REPAIRED（remark=auto-closed）
再破坏(P2 改回错值)  → run4：open=20  total=22  通知=22（+1：新开的 P0；同小时 P1 摘要被幂等键挡住）
                            CT-1 新开 2 条（新 detected_at），旧 2 条保持 REPAIRED
```

结论：**同一缺陷不重复轰炸、问题消失自动收敛、修复后再次发生新开一条**——三条语义全部实测成立。

### 9.5 其它实测事实

- `BEGIN READ ONLY; SET LOCAL statement_timeout='5s';` → `transaction_read_only=on`、`statement_timeout=5s` 生效。
