# ARCH-8 · 审批职责分离与自审批处理设计

> 版本 v1.0 · 2026-11-07
> 状态：**设计定稿，待实现（并入 P3 工作流引擎补全）**
> 来源：用户提出「审批流里自己不能审自己的单子，会不会有问题？」→ 讨论确认

---

## 一、设计原则

### 1.1 核心矛盾

```
内控要求：制单人不能审批自己的单（防舞弊）
业务现实：一人多职、小企业、高管自己发起 —— 硬卡会让业务走不下去

成熟 ERP 的答案：不是「允许/禁止」二选一，
                而是「默认禁止 + 撞车后有优雅降级路径 + 极端情况留痕放开」
```

### 1.2 一句话原则

> **防住舞弊，但不防死流程。**

### 1.3 三个必须区分清楚的概念

| 概念 | 谁做 | 算不算审批 | 能否是自己 |
|---|---|---|---|
| **制单/提交** | 制单人 | ❌ 不算 | ✅ 必然是自己 |
| **审批** | 他人 | ✅ 算 | ❌ 不能是自己 |
| **过账/执行** | 财务/仓管 | ❌ 不算审批，算执行 | ❌ 不能是制单人（职责分离） |

**关键澄清**：用户提的「第一个节点」如果指"提交"，那本来就不是审批；如果不指提交而是第一个审批节点，**同样不能自审**。

**结论**：不是「第二个节点不能自审」，而是「**任何审批节点都不能自审**」。

## 二、现状盘点（已有能力，不用重建）

`backend/src/business/flow/assignee.rs` 已实现：

### 2.1 节点级自审批策略

```rust
pub enum SelfPolicy {
    /// 保留，待办打 is_self_approval = true（UI 显示「自审」标）
    Allow,
    /// 跳过这个人，落一条 SKIPPED 待办留痕（不静默丢弃）—— **默认**
    Skip,
    /// 422 + 65018，整单回滚（财务/法务这类"宁可卡住也不能漏审"的节点用）
    Forbid,
}
```

**落库**：`biz_flow_node.self_approval`（默认 `SKIP`）

### 2.2 三项职责分离开关（系统参数）

```
erp.separation_of_duties.enabled   总闸
erp.separation_of_duties.approve   制单 ↔ 审批
erp.separation_of_duties.post      制单 ↔ 过账
erp.separation_of_duties.pay       制单 ↔ 付款
```

### 2.3 空审批人策略

```
SKIP            自动通过（危险，慎用）
ERROR           65018
FALLBACK_ADMIN  回退给超管
```

### 2.4 现状的问题

```
P0-01/02 实测：
  销售经理自己建单 → 提交
  「销售主管审批」绑 SALES_SUPERVISOR，该角色只有他一人
  self_approval=SKIP → 跳过他自己 → 该节点 0 人
  → 422 / 65018「无审批人」→ 业务卡死

链条分析：
  「自审批」处理得对（SKIP 跳过）
  「跳过之后没人接手怎么办」没设计 ← 真正的缺口
```

**所以现状是**：内控防住了，但流程会卡死。

## 三、目标设计（五层处理）

### 第 1 层：保留三档节点策略（不改）

```
ALLOW / SKIP / FORBID 的节点级配置继续保留
默认 SKIP 不变
财务/法务/付款节点建议显式配 FORBID
```

### 第 2 层：SKIP 之后「向上升级」⭐ 核心新增

```
SKIP 跳过后该节点 0 人
  ↓
不再直接 65018，而是查「升级链」
  ↓
找到上一级角色有成员 → 用他们审批（并留痕「因自审跳过，升级至 X 角色」）
  ↓
上一级也没有 → 继续往上
  ↓
到顶还没有 → 进入第 3 层（兜底人）或 65018
```

**升级链数据模型**：

```sql
ALTER TABLE sys_role ADD COLUMN escalation_role_id uuid;
-- 例：SALES_SUPERVISOR.escalation_role_id = GM 的 id
```

**建议默认升级链**：

```
销售员 → 销售主管 → 销售总监 → 总经理
采购员 → 采购主管 → 采购总监 → 总经理
财务专员 → 财务主管 → 财务总监 → 总经理
仓管 → 仓库主管 → 运营总监 → 总经理
部门经理 → 分管副总 → 总经理
```

**重要**：升级链必须**可配置**，不能硬编码（遵循「不硬编码流程」原则）。

**升级时的留痕**：

```
biz_flow_task 增加字段：
  escalated_from_role   varchar(40)   -- 从哪个角色升上来的
  escalate_reason       varchar(100)  -- 'SKIP_SELF_APPROVAL' / 'NO_MEMBER'
```

**审批界面显示**：

```
⚠ 本节点原审批角色「销售主管」仅有一人且为制单人，已自动升级至「总经理」审批
```

### 第 3 层：节点「兜底审批人」

```sql
ALTER TABLE biz_flow_node ADD COLUMN fallback_user_id uuid;
-- 或 fallback_role_id（兜底角色）
```

**触发条件**：升级链走完仍无人（或没配升级链）

**适用场景**：小企业指定老板作为所有审批的兜底

**留痕**：`biz_flow_task.assigned_by_rule = 'FALLBACK'`

### 第 4 层：委托审批（出差/休假）

```sql
CREATE TABLE biz_flow_delegate (
  id uuid PRIMARY KEY,
  delegator_id uuid NOT NULL,      -- 委托人
  delegate_id  uuid NOT NULL,      -- 受托人
  start_at     timestamptz NOT NULL,
  end_at       timestamptz NOT NULL,
  scope        varchar(40),        -- NULL = 全部；或指定 biz_type
  reason       varchar(200),
  enabled      boolean NOT NULL DEFAULT true,
  created_at   timestamptz NOT NULL DEFAULT now()
);
```

**生效逻辑**：

```
分配审批人时，若候选人是 delegator 且当前时间在委托期内
  → 改为分配给 delegate
  → 待办上标注「代 X 审批」
```

**为什么重要**：审批人出差时，如果没有委托机制，整个流程会停滞等他回来。

### 第 5 层：极端情况放开（ALLOW + 强制留痕）

**触发**：显式配置 `self_approval = ALLOW`（不是默认）

**必须配套的约束**：

```
① 待办打 is_self_approval = true（已有字段）
② UI 显示醒目的「自审」标记（红色/黄色）
③ 写审计日志（operation_log）：谁在什么时候自审了哪张单
④ 报表体现：月度「自审批单数量 + 金额 + 占比」
⑤ 可选金额阈值：超过 X 元不允许自审（必须他人）
      配置：erp.separation_of_duties.self_approval_max_amount
```

**适用场景**：

```
· 一人公司（老板是唯一审批人）
· 总经理自己发起的单（没有更高层）
· 紧急情况（且事后补批记录）
```

**为什么允许**：

```
内控是为了防舞弊，不是为了把业务卡死。
单人企业没有别人可审，硬卡等于系统不可用。
但必须留痕，让审计能看见 —— 这叫「受控的例外」。
```

## 四、六种典型场景的处理矩阵

| 场景 | 现状 | 目标行为 |
|---|---|---|
| **A. 正常企业**：角色有 3 人，制单人是其中 1 人 | SKIP 跳过 → 其余 2 人审批 ✅ | 不变 |
| **B. 角色只有制单人一人** | SKIP → 0 人 → 65018 卡死 ❌ | 向上升级到上级角色 → 有人则审批 ✅ |
| **C. 角色只有制单人，且无上级** | 65018 ❌ | 用节点兜底人 → 有则审批 ✅ |
| **D. 一人公司（无兜底人）** | 65018 ❌ | 配 ALLOW → 自审 + 留痕 + 报表体现 ✅ |
| **E. 审批人出差** | 流程停滞等他 ❌ | 委托给他人代审 ✅ |
| **F. 财务/法务节点** | 配 FORBID → 65018 ✅ | 不变（宁可卡住也不能漏审）✅ |

## 五、职责分离（SoD）的完整清单

不只「制单↔审批」，还有：

| 职责对 | 开关 | 现状 | 说明 |
|---|---|---|---|
| 制单 ↔ 审批 | `approve` | ✅ 已有 | 制单人不能审批自己的单 |
| 制单 ↔ 过账 | `post` | ✅ 已有 | 制单人不能过账（如入库单） |
| 制单 ↔ 付款 | `pay` | ✅ 已有 | 制单人不能审批付款 |
| **审批 ↔ 执行** | 待加？ | ❌ | 审批人不能自己执行（如审批完自己付款） |
| **制单 ↔ 盘点** | 待加？ | ❌ | 制单人不能确认自己建的盘点单 |
| **采购 ↔ 验收** | 待加？ | ❌ | 采购员不能验收自己采的货（经典内控） |

**建议**：后三项作为 P3 扩展考虑，优先级低于前四项。

## 六、角色节点的签名模式（另一个问题）

**现状问题**（P0-05 实测）：

```
角色类审批节点（APPROVAL + ROLE）在角色有多个成员时要求全员签
实测：预算「部门主管审批」节点，demo_lead + lead_drill 都签才推进
```

**判断**：角色节点**默认应该是「或签」**（任一成员审批即可）。

**设计**：

```sql
ALTER TABLE biz_flow_node ADD COLUMN sign_mode varchar(10) DEFAULT 'ANY';
-- ANY  或签：任一成员审批即通过（默认）
-- ALL  会签：全部成员都要审批（董事会决议这类）
-- QUORUM 定额：达到 N/M 即通过
```

**注意**：改成 ANY 默认会影响现有流程 —— 要做**存量迁移**评估：
```
· 现有节点如果业务上确实需要会签 → 迁移时标 ALL
· 其余改 ANY
· 迁移前先列出现有节点的 sign_mode 分布
```

**这条与自审批无关，但同属「审批流合理性」，建议一起做。**

### 7.3 验收标准（整体）

```
① 场景 A：角色 3 人，制单人 1 人 → 剩余 2 人审批（回归不变）
② 场景 B：角色 1 人（制单人）→ 自动升级到上级角色 → 审批成功
③ 场景 C：角色 1 人 + 无上级 → 用兜底人 → 审批成功
④ 场景 D：一人公司 + ALLOW → 自审成功 + 审计日志 + 报表体现

⑥ 场景 F：财务节点 FORBID → 自审被拒（回归不变）
⑦ 角色节点默认或签：3 人角色任 1 人审批即通过
⑧ 所有升级/兜底/委托都有留痕（biz_flow_task 有字段记录原因）
```

## 八、待确认的问题

1. **默认升级链要不要预置？**
   ```
   建议预置一套（销售/采购/财务/仓库/部门经理 → 总经理）
   但允许管理员改
   ```

2. **ALLOW 的金额阈值默认多少？**
   ```
   建议：默认不限额（因为 ALLOW 本身要显式配置）
        或默认 1 万元以下允许自审
   ```

3. **sign_mode 存量迁移**
   ```
   需要先盘点现有节点：
     · 有多少节点是角色型（可能涉及多人）
     · 业务上哪些确实需要会签
   盘点后决定迁移策略
   ```

4. **委托的审批要不要再审批？**
   ```
   建议：委托生效不需要审批（信任机制），但要留痕
   ```
