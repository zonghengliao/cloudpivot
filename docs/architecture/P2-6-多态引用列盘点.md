## 1. 什么叫「多态引用」，为什么不能加外键

```
biz_inventory_txn.doc_type = 'STOCK_IN'   →  doc_id 是 biz_stock_in.id
biz_inventory_txn.doc_type = 'STOCK_OUT'  →  doc_id 是 biz_stock_out.id
biz_inventory_txn.doc_type = 'SERIAL_BATCH' → doc_id 是 biz_material_serial.id
```

`doc_id` 是**一个列对 N 张表**。PostgreSQL 的外键只能指向**一张**表，
所以这种引用**天生无法用 FK 表达**（卡面明确要求：不要给所有列都加外键）。
它只能靠两件事兜底：

1. **写入侧自律**（类型与 id 必须成对写、按类型写对表）；
2. **读取侧巡检**（就是本卡做的事：按类型解析目标表 → 目标行不存在/已软删 = 悬空）。

> 这也解释了为什么「单据软删了，引用它的流水/凭证还挂着」这类问题能长期存在：
> 数据库层面**没有任何约束**会拦它。

## 5. 盘点结论（4 条）

### 5.1 15 条既有巡检的盲区是真的

`erp_invariants.py`（40 条）与 DI-01…DI-16 全部只查**已知的单目标关联**
（`source_order_id`、`contract_id`、`supplier_id`…）。多态引用一个都没查 ——
因为它们的 SQL 需要「按类型选表」，写起来啰嗦，历史卡都跳过了。
本卡补的就是这块：**6 条巡检 = 5 类引用 + 1 条护栏**。

### 5.2 有一条真的会在生产命中有价值的东西

`doc_type='ADJUST'` + `doc_no='DATAFIX-20261101-P14'` 的库存流水
（`doc_id` 指向一个根本不存在的 uuid）→ 这是**手工修数**留下的痕迹。
它不是「指向已删的单据」，而是「没有单据却硬填了一个 id」——
所以 DI-18 把它单列成 `NO_TARGET`（INFO）：账是完整的，但「来源」栏位是假的，
审计要能一眼看到「这里有人动过手」。

### 5.3 有一类引用是**设计缺口**（卡面要求「停下来问」的情形）—— **P2-6b 已收口**

`biz_material_serial.source_type` + `source_id`：**类型有、id 恒空、且没有目标表映射**。
生产 31 个序列号、`source_id` **0 行有值**；代码侧 `serial_handler.rs` 4 处 `source_id: None`
（实测这 4 处**全是单测夹具**，真正的写入点另有其人 —— 见下表）。

P2-6 当时的处理是「不猜映射」（猜了就是造第二真相）。P2-6b 不再猜，而是**读代码定映射**：

| 来源 | 目标表 | 谁写 | 状态 |
|---|---|---|---|
| `PURCHASE` | `biz_stock_in` | 收货过账（`stockin_cancel::insert_serials`），`source_id` = 收货单 id | **已有写入**（P2-6b 起按 `in_type` 决定来源，不再硬编码） |
| `RETURN` | `biz_stock_in` | 同上（退货入库 `in_type=RETURN`，同一张表） | **P2-6b 新增写入**（以前一律写 `PURCHASE`，退货入库的来源是**错的**） |
| `TRANSFER` | `biz_stock_transfer` | —— 调拨只搬已有序列号、不新建号 | 登记备查；将来做「调拨入库新建号」按此写 |
| `PRODUCE` | （无） | 批量生成（`serial_model::batch_generate`）可传 `source_type=PRODUCE` | **只允许不带 id**（生产模块尚未落地）；带 id 会被 `ensure_source_pair` 400 拒绝 |

写入侧闸门：`serial_model::ensure_source_pair`（批量生成模型层入口，handler 把它翻成 400 + `10001`）——
① 有类型必须有 id、② 有 id 必须有类型、③ 有单据表的类型 id 必须指向**真实未软删**的行、
④ 无单据表的类型（PRODUCE）不许带 id。四种坏组合都有单测逐条钉住。

巡检侧：`di.v_poly_ref_map` 的 `SERIAL_SOURCE` 四行补上实表（`PRODUCE` 仍为空），
`di.v_poly_ref_dangling` 加两条 JOIN 分支 ⇒ **DI-21 从「INFO 残缺」升级为「悬空可查」**
（悬空 = WARN，历史有类型无 id = INFO）。

### 5.4 「0 命中」必须能解释，不能当绿灯

- DI-17 = 0：不是没查，是 15 张进项凭证 + 6 张出库凭证**全部能回跳**（逐条 JOIN 过）。
- DI-21 = 0：**不代表序列号来源没问题** —— 生产 31 个序列号全部在 2026-11-01
  被清场软删了（`deleted_at` 全非空），巡检按「不查已软删的源行」跳过它们；
  把类型/id 残缺的问题记在 DI-21 的设计缺口里（§5.3），不靠这条 0 命中来自证清白。
