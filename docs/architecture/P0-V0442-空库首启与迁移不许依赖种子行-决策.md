# P0 · V0442 让空库首启直接失败 —— 修复与「迁移不许依赖种子行」规矩

> 卡：**t_08e1816a**（上游 t_0fd37353 造全量库时实测发现）
> 日期：2026-11-17　分支：`main`
> 证据目录：`docs/evidence/2026-11-17-v0442-empty-db/`

---

## 一、一句话结论

V0442 的前置护栏断言了「系统管理」目录行（`1000…0001`）存在，而这一行**只由种子迁移
`S__menu_data.sql` 建出**，内核执行次序却是 **versioned 先、seed 后** ⇒ 任何空库首启
跑到 V0442 必然 `RAISE EXCEPTION`，启动 FATAL。修法只有一条路：**原地改 V0442**
（V0443 永远轮不到执行），把那条护栏降级成「目录缺席 ⇒ NOTICE + 跳过该层祖先闭包」，
并用一条 datafix 同步已应用过旧版的库的指纹；同时立规矩 + 加 L0 静态闸
`scripts/lint/seed_dependency_gate.py`，外加修掉「内核把真因吞成 `query failed: : db error`」。

## 三、现象与真因（逐条实测，不是推测）

### 3.1 现象

```text
$ ERP_DB=cloudpivot_test_<新库> bash scripts/verify/make_full_suite_db.sh
==> 已建空库 …
    ERROR nik_web::app: 数据库迁移失败: query failed: : db error
    FATAL: 服务启动失败: 配置错误: 数据库迁移失败: query failed: : db error
!! bootstrap 没跑完（库里没有 admin+SUPER_ADMIN）
```

### 3.2 内核吞掉的真因（手工 psql 重放同一文件才看得到）

```text
ERROR:  V0442: 祖先目录「系统管理」(1000…0001) 不存在，先应用系统菜单迁移
CONTEXT:  PL/pgSQL function inline_code_block line 62 at RAISE
```

### 3.3 失败那一刻的库状态（`cloudpivot_test_v0442a`，本卡实测）

| 观测 | 值 |
|---|---|
| `schema_migrations` 分布 | `versioned=361`，**`seed=0`** |
| `max(version)`（versioned） | 441 |
| `sys_menu`（活跃） | 492 |
| `sys_role`（活跃） | 10（SALES_CLERK / SALES_SUPERVISOR / FINANCE_MANAGER … 都在） |
| `sys_menu` 有 `1000…0001`（系统管理）吗 | **0 行** |
| `sys_menu` 有 `2000…2701`（销售管理）吗 | 1 行（V0267 建） |

### 3.4 机制（源码级）

| 事实 | 出处 |
|---|---|
| 执行次序固定 `baseline(0) → versioned(1) → repeatable(2) → seed(3)` | `backend/vendor/nik-db/src/migrate/kind.rs::execution_rank` |
| `1000…0001` 只由 `migrations/seed/S__menu_data.sql` 建出 | `grep -rln 10000000-0000-0000-0000-000000000001 migrations/`：版本化侧只有 V0319 的 `UPDATE parent_id`、V0322 的 `parent_id` 引用与 V0442 自己，都不建行 |
| 同一份 V0442 在**已种子**的库上完全正常 | 本卡复跑：`NOTICE: V0442 自检通过 … 目标角色 5 个`（与上游卡手工应用结果一致） |

⇒ 这不是「V0442 写错了表/列」，而是**依赖方向错了**：版本化层依赖了种子层的产物。

### 3.5 影响面

任何空库首启 / 新环境 / 演练库都在 V0442 处失败 ⇒ `make_full_suite_db.sh`（全量 lib 套件的
标准库）造不出来、L3 干净检出闸、新客户部署全被挡。

## 四、修法（只改 V0442 本身）

### 4.1 改了什么

| 位置 | 改法 | 理由 |
|---|---|---|
| ③「系统管理」护栏 | `IF n <> 1 THEN RAISE EXCEPTION` ⇒ `IF n = 0 THEN RAISE NOTICE '…跳过该层祖先闭包'` | 该行缺席是**空库首启的正常路径**，不是异常 |
| ③「销售管理」护栏 | **不动**（仍硬断言） | 它由 `V0267`（版本化）建出，实测空库首启确实存在 |
| 文件头 | 增加「2026-11-17 修订」段：现象 / 真因 / 改法 / 代价 / datafix 指针 / 规矩指针 | 让下一个人不用重新推一遍 |
| 前置 NOTICE 文案 | 改为「…+ 销售管理目录…；系统管理目录按空库首启情况可能缺席」 | 日志不再骗人 |

### 4.2 为什么「跳过」不等于「留隐患」（关键论证）

V0442 对 `1000…0001` **没有写死依赖**：

- ④ 祖先闭包本来就是动态形态 `JOIN sys_menu dir ON dir.id = p.parent_id`（不写死 0001）；
- ⑤c 的 touched 集合用确定性 id（`md5('v0442c.'||role||dir)`）反查，目录缺席时自然变小。

实测（`cloudpivot_test_v0442b`，全新库）：**`missing_ancestor_pairs = 0`** —— 没有任何角色
拿到「父目录缺位」的授权（`system/auth/handler.rs::build_menu_tree` 会静默丢弃这类节点，
是真隐患，这里没有）。原因：空库首启时**没有任何角色持有「系统管理」子树**，`role-mutex`
按钮码（`system:role-mutex:conflict`）在种子之前也无人持有 ⇒ ④ 这一段本来就授 0 行。

### 4.3 被否掉的两个写法

| 方案 | 为什么不选 |
|---|---|
| 在 V0442 里 `INSERT` 出 `1000…0001`（把依赖换成版本化迁移种下的行） | base 菜单行的唯一真相源是种子（`ON CONFLICT (id) DO UPDATE` 自愈）；在版本化侧再写一份 = 第二份真相，字段一漂移就出现「新库 / 老库同 id 不同字段」。而且实测没有功能收益（见 §4.2） |
| 保留护栏、加 V0443 事后补 | 永远轮不到执行（442 先炸） |

## 五、指纹后果与 datafix

### 5.1 框架行为

已应用迁移被改写 ⇒ `DbError::MigrationChecksum` 中止启动（`Divergent::Abort` 是默认策略，
仓库 config 未改）。指纹算法是**逐行 + `\n` 后 SHA-256**（`history.rs::checksum::content_checksum`），
**不是**对文件字节 `sha256sum`。

### 5.2 口径校准（先校准，再改库）

| 项 | 值 |
|---|---|
| 旧版 V0442（HEAD `e759628b`）实算 | `2e6fbee6a98c6ca081ada172f91623b922bad2ea459f431db50cce98b11cdafe` |
| `cloudpivot_dev` 记录值 | `2e6fbee6a98c6ca081ada172f91623b922bad2ea459f431db50cce98b11cdafe`（**逐字节一致**） |
| 新版 V0442 实算 | `e724407aed1f89e453c1f3fadd6caff1d7a362a70d4bd07488119cd5e8bc1641` |

⇒ 新值由 `scripts/datafix/v0442-checksum/recompute_checksum.py` 现算（**不写死**在该文件里，
避免「改文件→指纹变→再改文件」的自指）。

### 5.3 datafix 的三层安全阀

1. **只认已知旧指纹**：库内值 ≠ `2e6fbee6…` 时中止（说明是另一处未知改写，交人工）；
2. **只改 `checksum` 一列**（`WHERE kind='versioned' AND version='442'`），不动
   `applied_at/applied_seq/success/source` ⇒ 不影响回滚顺序；
3. **默认 dry-run**，`--apply` 才写；写完立刻回读校验；再跑一次是 no-op。

### 5.4 受影响面与处置（2026-11-17 实测）

## 六、规矩与静态闸（决策 2 的落地物）

### 6.1 规矩（写进 `docs/后端二开指南.md` §九）

**版本化迁移不得把「种子行」当作前置条件。** 三条正确写法，按优先级：

1. 该行由**版本化迁移**自己保证存在（固定 id + `ON CONFLICT (id) DO NOTHING`）；
2. 只是顺带补授权/补父节点 ⇒ 动态 `JOIN … ON dir.id = p.parent_id`，不写死那一行；
3. 该行确实只可能由种子建出 ⇒ 护栏降级成 `IF n = 0 THEN RAISE NOTICE '…跳过…'`。

### 6.2 静态闸 `scripts/lint/seed_dependency_gate.py`（L0）

判据（只管**会失败**的那种引用）：

1. 在 `DO $$ … $$` 里找 `SELECT count(*) INTO <v> … WHERE id = '<uuid>'`；
2. 其作用窗口内（到下一条 `INTO` 为止）出现 `IF <v> <> 1 THEN … RAISE EXCEPTION`
   （或 `IF <v> = 0 THEN … RAISE`）⇒ 存在性断言；
3. 该 `<uuid>` **从未被任何版本化迁移以 `id` 列 INSERT 过** ⇒ 判红。

不判红的三类（不会让迁移失败）：`IF <v> = 0 THEN RAISE NOTICE`、`UPDATE/DELETE … WHERE id=`、
动态 `JOIN … ON`。

**为什么要把「作用窗口」限定到下一条 `INTO`**：本仓护栏惯例都用变量名 `n`，不限定窗口时
V0442 修好后仍会被误报（0001 的 NOTICE 分支后面紧跟着 2701 的 `RAISE`）—— 这是本卡实际踩到的
一次假阳性，已写进脚本注释。

自证与接线：

| 项 | 结果 |
|---|---|
| `--selftest` 4 条语料（硬断言红 / NOTICE 分支绿 / 自己 INSERT 的 id 绿 / 动态 JOIN 绿） | 全绿 |
| 扫描全仓（363 个版本化迁移 / 12 个种子迁移） | **修后 0 命中** |
| 变异反证：把 V0442 换回旧版 ⇒ 重扫 | **1 命中**（`…依赖 10000000-…0001 —— seed 行（空库首启必炸）`） |
| `check.sh --l0` | `EXIT=0`（闸已挂载，`--dry-run` 也会列出它） |
| 豁免清单 | `scripts/lint/seed_dependency_allow.txt`（当前为空；豁免必须带理由） |

## 八、附带修掉的诊断力缺陷（本卡发现，同批修）

迁移失败时内核只打：

```text
数据库迁移失败: query failed: : db error
```

根因（源码级）：`nik-db-driver-postgres::map_pg_error` 已经把 `(SQLSTATE, message)` 拆出来了，
但 `nik-db-core::DbError::from_raw_driver_error` 的**未映射分支**（`P0001`
`RAISE EXCEPTION` 就走这里）只把原始错误对象放进 `source`，而
`tokio_postgres::Error` 的 `Display` 对服务端错误只有一句 `db error` ⇒ **消息被丢掉**。

修法：新增 `DriverMessage`（`Display` = `<驱动消息> [<SQLSTATE>]`，原始错误仍留在
`source()` 链上），未映射分支改用它；其余分支（唯一/外键/CHECK/死锁/锁等待）行为不变，
仍用「原始对象优先 + 消息兜底」。

效果（同一个旧版 V0442，同一个库，只换二进制）：

```text
修前：数据库迁移失败: query failed: : db error
修后：数据库迁移失败: query failed: : V0442: 祖先目录「系统管理」(1000…0001) 不存在，先应用系统菜单迁移 [P0001]
```

单测：`vendor/nik-db-core` 的 `error::tests` 4/4 通过（新增
`query_display_keeps_driver_message_when_source_present`，钉住「带 source 时也必须带消息」）。
