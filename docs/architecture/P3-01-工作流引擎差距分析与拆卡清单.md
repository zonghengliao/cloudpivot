### 3.2 卡面六问逐条回答

**问 1：`assignee.rs` 三档策略是否完整？SKIP 留痕真的落库了吗？**

- 三档**完整**：`SelfPolicy{Allow,Skip,Forbid}`（`assignee.rs:73-91`），`ALLOW` 保留并打 `is_self_approval`、`SKIP` 剔人且入 `skipped` 列表、`FORBID` 直接 422/65019。
- 留痕**真的落库**：`engine.rs:2655-2689` 对每个 `finalized.skipped` 插一行 `status='SKIPPED'` + `is_self_approval=true` + `comment='审批人是发起人本人（self_approval=SKIP），已跳过并留痕'`；内控（制单人/发起人）排除的人同样落 `SKIPPED`（`engine.rs:2731-2767`）。**实测有数据**：`cloudpivot_4b` 里 7 条 SKIPPED 行，注释分别写明「内控：审批单发起人不可审批自己发起的审批」/「内控：单据制单人不可审批自己制单的单据」。
- **但缺降级**：`assignee::finalize` 第 ⑤ 步 `approvers.is_empty()` 只按 `empty_assignee` 处理（`SKIP` 原本是自动通过 / `ERROR` 是 65018 / `FALLBACK_ADMIN` 回退超管），**没有「向上找上级角色」这一层**。而引擎侧（`engine.rs:2706`）为了让「内控剔光 ≠ 免审」已经改成 **0 人一律 422 fail-closed**，所以 SKIP 场景的实际结果是 **65018 卡死**（这与卡面描述一致；顺带说明 `engine.rs:2772` 那段 `empty_assignee=SKIP → 自动通过` 已成为**不可达死代码**，P3-02 一并清理并写注释）。

**问 2：`biz_flow_node` 有没有 `fallback_user_id`？** 没有。26 列里没有任何兜底人/兜底角色列（`V0120:139-180` 全表 DDL）；ripgrep `fallback_user_id|fallback_role_id` 在 `backend/src` + `migrations` **0 命中**。

**问 3：`sys_role` 有没有 `escalation_role_id`？** 没有。实际列 13 个（`id…deleted_at, data_scope`），ripgrep **0 命中**。

**问 4：角色节点多成员到底是全员签还是或签？实测确认。**
**全员签**。链路：APPROVAL 节点 `approval_mode IS NULL` → `engine.rs:881` `ApprovalMode::parse(...unwrap_or("ALL"))` → `judge(All, …)` 要求全部 PENDING 都同意。数据实测（`cloudpivot_deadmin`）：APPROVAL 节点 `approval_mode IS NULL` = **46 个（分布在 23 个版本上）**，显式 `ANY` = 1 个；`cloudpivot_prt03`：NULL-ROLE 33 个 / ANY-ROLE 1 个；种子快照同样写 `"approval_mode": null`（如 V0182 `n_dept`「部门主管审批」绑 ROLE 但 mode=null）。**P0-05 的结论成立。**

**问 5：委托机制完全没有？** 完全没有任何样子：无表、无字段、无分配时替换、无 UI（接口清单里也没有 `delegate` 路由）。

**问 6：`is_self_approval` 有没有被前端用到？** 用了，共 5 处：`flow-api.ts:829`（类型）、`FlowProgress.vue:55`（渲染警告色「自审」tag）、`flow-progress-tasks.ts:59`、`instance/detail.vue:594`（时间线 `isSelf`）、`erp/shared/approval-progress.ts:79` + `erp/transfer/transfer-logic.ts:971`（ERP 侧审批进度）。所以 P3-05 的「自审标记 UI」**已具备**，只需在「待办列表」再补一处一致性（`flow/task/index.vue` 目前不显示）；真正缺的是审计日志、报表、金额阈值。

### 3.3 核心结论（写进设计口径）

```
现状：防住了舞弊（SKIP 跳过自审 + 留痕落库 + FORBID 硬拒），但没防住流程卡死
      SKIP 后 0 人 → 引擎 fail-closed → 422 / 65018 → 业务走不下去
      现有的兜底只有 empty_assignee=FALLBACK_ADMIN，而新库里超管往往就是制单人
      → 被内控再剔一次 → 依然 0 人

目标：五层降级（自下而上兜住）
  ① 保留三档策略（ALLOW/SKIP/FORBID），默认 SKIP 不变
  ② SKIP 后向上找上级角色（sys_role.escalation_role_id，可配、不硬编码）
  ③ 升级链走完仍无人 → 节点兜底人（biz_flow_node.fallback_user_id / fallback_role_id）
  ④ 都没有 → 显式 ALLOW（留痕 + 审计日志 + 月度报表 + 金额阈值）
  ⑤ 全程支持委托（biz_flow_delegate，出差/休假不堵流程）

与 FIX-1 的分工：
  FIX-1（已完成）= 人工补救：422 带结构化诊断 + 前端引导指派审批人
  P3-02~05      = 自动降级：系统自己找人
```

## 6. 风险与红线

1. **不许重写并行/条件/版本/加签转签**（已交付），只在 P3-09 补回归用例。
2. **改默认签法必须带迁移与盘点输出**：`approval_mode` 的存量分布要落进证据文档，迁移脚本要能复跑（幂等 `WHERE`）。
3. **升级/兜底/委托的每一次「换人」都要留痕**（`biz_flow_task` 字段 + `operation_logs`），否则审计问「这票是谁的」答不出来。
4. **不许把找人逻辑写进 handler**：找人一律在 `assignee.rs`（唯一出口），handler/引擎只消费 `Finalized`。
5. **新增列必须同步** `ck_biz_flow_node_config_partition`（若挂 `config`）、前端 `flow-api.ts` 类型、`NodeProps.vue`、`flow-node-caps.ts` —— 「代码加了迁移没跟上」→ 生产 500 的典型路径。
6. **子流程**必须防自递归（R27）+ 深度限 3，且父子实例的结算回调必须幂等（重复回调不重复落状态，复用 `settle_guard`）。

## 7. 明确不做（防范围膨胀）

- ARCH-5 的表单设计器 / 检查清单 / 证据归档包 / 触发器四类 / WAIT / ACTION 节点（L2-L3，另立项目）。
- 有序多签 SEQUENTIAL、QUORUM、角色认领 CLAIM（L3，本轮只做 ANY/ALL 默认值修正）。
- 组织级升级链继承（部门树 + 角色链的合并策略），本轮只做角色级一条链。
