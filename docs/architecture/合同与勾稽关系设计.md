## §0 一页结论（先看这张表；细节在后续章节）

### 0.1 五问五答（每条一句话结论 + 决定性理由）

| 问题 | 结论 | 决定性理由（本仓实测，不是"最佳实践"） |
|---|---|---|
| **Q1 采购单是否保留 `supplier_id`** | **保留**，语义改为「业务发生时的乙方快照」，并新增 `contract_id / purchase_type / contract_no_snapshot / supplier_name_snapshot` 四列 | 方案 A（删列、全靠合同推导）在**零星采购**上结构性失效：没有合同就没有交易对手，而该列现为 `NOT NULL`、被 56 处代码引用、1 个索引与夹具清理依赖；性能不是决定性维度（首屏三方案同在 0.6–1.4ms、轮次波动大于方案差异） |
| **Q2 零星采购（无合同）怎么约束** | `purchase_type IN ('CONTRACT','SPOT')` + **`ck_biz_po_contract_pair` 双向钉死**（CONTRACT 必有 `contract_id` + 合同号快照；SPOT 两者必须为空）；「SPOT 必有供应商」由列 `NOT NULL` 天然覆盖；**跨表相等 DB 做不到**，落 handler + 巡检 | PostgreSQL 的 CHECK 不能引用别的表（实测 `cannot use subquery in check constraint`）；同表内的可判定事实必须落 DB，且必须用 `CASE … ELSE FALSE END`（三值逻辑下 NULL 会被当成"通过"） |
| **Q3 入库单是否保留 `supplier_id`** | **保留**，语义定为**「快照（受直接上游强约束）」**：有源时在建单事务内从采购单带出、禁止手改、写入校验等值；非采购入库强制为空（新增 `ck_biz_si_supplier_scope`）；`source_order_id` **不做 NOT NULL** | 只有快照能回答"合同换乙方之后，这张历史入库单当时是谁"；而"与其**直接上游**采购单恒等"是可重算的强约束 ⇒ 与直接上游比较恒为 DEFECT，与最终真相（合同）比较才可能合法。两个问题不同，见 §4.2 C-02 |
| **Q4 库存 `biz_inventory` 是否显示供应商** | **不加列**。只走 `biz_inventory → biz_inventory_txn(doc_type/doc_id/doc_no) → 入库单 → 采购单 → 合同 → 供应商` 逐跳追溯 | 库存结存行是「物料 × 仓库 × 库位」维度的汇总（唯一键 `uk_biz_inv_mat_wh_loc`），一行可能由几十次不同供应商的入库汇总而成 —— 塞一列只能表达"某一次"，其余全错，是**语义说谎**而不只是精度不足；批次成本属批次管理卡 |
| **Q5「触类旁通」具体指什么** | 三条通用规则（R1 单一数据源 / R2 只绑上一环 / R3 显示靠关联+快照可追溯）**形式化为可打勾的评审 checklist**，并给出 7 条业务链（采购/销售/生产/委外/财务/调拨/退货）的逐链映射与巡检项 | 规则不落到"某链某环某列"，就只是一句口号；7 条链里现状**已合规 1 条（调拨）/ 部分 2 条（采购、财务）/ 未 4 条**，缺口集中在「R2 在采购链主关联方向 1 处硬违规」与「R3 巡检全系统 0 覆盖」 |

## §2 三条核心原则（必须贯穿设计；本节即评审 checklist）

### 2.1 R1 — 单一数据源（Single Source of Truth）

**形式化定义**：对任一业务事实 `f`，存在唯一的权威存放点 `Owner(f)`；其它出现位置只能是下列三种之一，且必须可证明：

```
① 快照（Snapshot）  ：业务发生时刻的事实副本，上游事后合法变更**不回写**历史  → 允许与今天不同
② 派生（Derived）    ：由 Owner(f) 在查询时现算（视图 / 聚合 / 状态机推导）      → 不落库或落只读视图
③ 索引/缓存（Index） ：可从 Owner(f) 重建，且带重建机制与失效策略              → 必须有巡检或重建入口
```

不在这三类里的"第二份存储"一律违规。

**归属判定表（本批涉及的 6 个事实）**

| 事实 | 唯一真相 `Owner(f)` | 其它出现位置 | 类型 | 判定 |
|---|---|---|---|---|
| 供应商身份（采购链） | `biz_contract.party_b_id` | `po.supplier_id` | 快照 | ✅ |
| 供应商身份（入库链） | **其采购单** `po.supplier_id` | `si.supplier_id` | 快照（受强约束） | ✅（与直接上游恒等） |
| 供应商身份（资金链） | **其入库单** `si.supplier_id` | `payable.supplier_id` | 快照（受强约束） | ✅ |
| 供应商名称（可读） | `biz_supplier.supplier_name` | `po.supplier_name_snapshot`、`contract.party_b_name` | 快照 | ✅（主档改名不回溯） |
| 合同金额 | `biz_contract.amount` | — | — | ✅（累计下单额现算，不缓存） |
| 库存数量/成本 | `biz_inventory.qty / avg_cost / amount` | `biz_inventory_txn` 前后六列 | 派生（流水可重放） | ✅（V0137 已定） |

**R1 的 6 条评审问句**（任何模块都能问，答案必须是"唯一"）

1. 这个值**谁写**？写入点是不是只有一处（`|WriteSet| = 1`）？
2. 如果别处也存了一份，它是快照、派生还是索引？三选一，说清楚。
3. 上游**合法变更**后，这份副本是否被要求跟着变？要求跟着变的是冗余（漂移即缺陷），不要求的是快照。
4. 有没有第二个写入路径能绕过 Owner（含"直改库"、"导入脚本"、"另一个接口"）？
5. 这份副本坏了，**谁能发现**（巡检项编号是什么）？
6. 去掉这份副本，功能是否真的不可实现？如果不能证明"不可实现"，就不该存。

### 2.2 R2 — 只绑上一环（Single Parent Pointer）

**形式化定义**：业务单据的主关联指针**只能指向它的直接上游**，禁止跨环指针；跨环信息一律靠"逐跳 JOIN（显示）"或"快照（审计）"表达。

```
入库单 ──source_order_id──▶ 采购单 ──contract_id──▶ 合同 ──party_b_id──▶ 供应商
   └── ✗ 禁止在入库单上出现 contract_id / party_b_id（跨环）
```

**环间指针归属表（目标态，7 条链见 §8）**

| 链 | 环 1 → 环 2 → 环 3 → 环 4 | 允许的指针 |
|---|---|---|
| 采购 | 合同 → 采购单 → 入库单 → 库存 | `po.contract_id`、`si.source_order_id`、库存无单据指针（走流水 `doc_type/doc_id`） |
| 销售 | 销售合同 → 销售订单 → 出库单 → 应收 | `so.contract_id`、`ob.source_order_id`、`ar.source_type/source_id`（批次 2） |
| 生产 | 生产订单 → 领料单 / 完工入库单 | `source_production_id`（无交易对手列） |
| 委外 | 委外合同 → 委外订单 → 发料/收货单 | `oo.contract_id`、`source_outsourcing_id` |
| 财务 | 业务单据 → 凭证 → 分录 | `voucher.source_type/source_id`、分录 `aux_*_id` |
| 调拨 | 调拨单 →（收货=状态跃迁+流水） | `transfer_id`（明细外键），无交易对手列 |
| 退货 | 原单 ← 退货单 → 退货车 | `orig_doc_type/orig_doc_id`、`source_return_id` |

**R2 的 6 条评审问句**

1. 这条主关联指向的是**上一环**，还是跳了两环？（跳环 = 违规，除非有 ADR 背书）
2. 主关联是否 `NOT NULL`？如果可空，**空值是否有枚举化的合法语义**（而不是"说不清"）？
3. 是否同时存在"上一环指针"和"上一环的上一环指针"两个列（双指针必然打架）？
4. 明细行是否也做了同方向的绑定（`source_item_id` 必须属于 `source_order_id`）？
5. 有没有为了"查询方便"把上游单号/名称**当成关联键**参与 JOIN/WHERE？（文本只许显示）
6. 结构上能不能**不给列**就实现？（列不存在 = 没人能绕过去写，优于代码纪律）

### 2.3 R3 — 显示靠关联 + 快照可追溯（Display by Relation, Truth by Trace）

**形式化定义**：

```
列表/打印/审批表单  → 用快照列（快，且"当时是谁"正确）
详情/追溯            → 逐跳关联读真相（慢一点，但"现在是谁"正确）
快照 vs 真相不一致   → 巡检报出，人工判定 SNAPSHOT（合法）或 DEFECT（缺陷）
```

**三态判定表（区分"这是对的/这是缺陷/这是历史"）**

| 现象 | 判定 | 处置 |
|---|---|---|
| 快照 = 真相 | OK | 无动作 |
| 快照 ≠ 真相，且**上游存在合法变更记录**（合同换乙方台账 / 主档改名） | `SNAPSHOT`（合法历史） | 只留痕，可 `ACCEPTED`，**不修** |
| 快照 ≠ 真相，且**没有任何变更记录** | `DEFECT`（疑似篡改） | P0 告警，人工判定后修 |
| 快照 ≠ **直接上游**（拷贝断裂） | `DEFECT` | 必修（P0/P1 视是否涉资） |

**快照的四个必备属性（缺一即不达标）**

1. **有明确写入时刻**：建单/签约那一刻，不是"最后一次保存"。
2. **拒绝手改**：DTO 不接受输入或与上游强等值校验；否则快照退化成人人可写的第二真相。
3. **有对应巡检项**：快照列必须在 §7.2 的 15 条里找得到；找不到的"快照"是没人管的野列。
4. **不被当真相用**：判定"合同是否有效""能否下单""对账金额"一律读真相，不读快照。

### 2.4 三条规则冲突时的裁决树（评审遇歧义直接走这里）

```
问题：某个跨环字段该不该存？
 ├─ 该字段是"交易对手/单号/名称"这类上游事实？
 │    ├─ 是 → 存 ID 快照（R3），不存名称文本（R1-f）；显示用快照，追溯读真相
 │    └─ 否 → 它是本环自身的事实？→ 直接存（R1 无冲突）
 ├─ 该字段能否由上游无歧义重算，且上游不会被合法改写？
 │    ├─ 能且不会 → 它是冗余：要么删除，要么降级为"受强约束的快照"并上巡检（本文 Q3 选后者）
 │    └─ 不能或会被改写 → 它是快照：必须上巡检，且判定允许 SNAPSHOT
 ├─ 有没有"为了性能"的理由？→ 有，且能量化（§3.1 的性能表）→ 允许存快照，否则走关联
 └─ 存了之后谁来发现它坏了？→ 说不出巡检编号 → 不许存
```

### 2.5 本文最关键的一句话：快照 vs 冗余的唯一判据

> **能由上游在任意时刻无歧义重算、且上游不会被合法改写的副本，是冗余（漂移恒为缺陷）；记录"业务发生那一刻"、上游事后可合法变更的副本，是快照（漂移可能合法）。**

这句话同时决定了两件事：① 每列是"快照"还是"冗余"；② 巡检的分级与处置动作是否合法（自动回写快照 = 篡改审计证据，明令禁止）。

**用它量 `si.supplier_id`（四份输入在这里打了架，本文在此定稿）**：

| 维度 | `biz_stock_in.supplier_id` |
|---|---|
| 能否由上游在任意时刻无歧义重算？ | **与"直接上游"（采购单）比较，同一时刻可以重算** |
| 上游会被合法改写吗？ | **采购单 DRAFT 可改；合同换乙方后新采购单的 `supplier_id` 会变，但老采购单不变** |
| 结论 | 它记录"收货那一刻供应商是谁" → **快照**；但"与直接上游恒等"是**可重算的强约束** ⇒ 与直接上游的偏移**恒为 DEFECT** |
| 与最终真相（合同）比较 | 合同换乙方后，老入库单与其合同不再相等 —— 但这是**上游的上游**的合法变更，**不是**本环缺陷（这正是"只绑上一环"的推论） |

## §3 Q1–Q5 的明确结论

### 3.1 Q1：采购单保留 `supplier_id` —— 方案 B（关联 + 快照）

**结论**：保留 `supplier_id`（列定义与 `NOT NULL` 都不动），语义从"供应商外键"改为"**业务发生时的乙方快照**"，并新增四列把它升到可审计水平。

| 新列 | 类型 | 空 | 语义 |
|---|---|---|---|
| `contract_id` | UUID | 可空 | 合同（**弱引用** `biz_contract.id`，不建外键）；CONTRACT 必填 / SPOT 必须为空 |
| `purchase_type` | VARCHAR(8) | NOT NULL DEFAULT `'SPOT'` | `CONTRACT` 合同采购 / `SPOT` 零星采购 |
| `contract_no_snapshot` | VARCHAR(32) | 可空 | 合同号快照；列表/打印/审批表单不 JOIN 也能显示 |
| `supplier_name_snapshot` | VARCHAR(200) | 可空 | 供应商名称快照；存量行 `NULL`（当时名称不可知），显示端 `coalesce(snapshot, 主档当前名)` |

**三个维度的算账（不含"最佳实践"式空话）**

**维度① 零星采购（决定性）**

- 方案 A（删掉 `supplier_id`、全靠 `contract.party_b_id` 推导）**无法表达**零星采购：无合同 ⇒ 无 `party_b_id` ⇒ 采购单没有供应商。要么给零星采购伪造"一次性合同"（合同台账塞满无意义行，污染合同执行率统计），要么允许"没有合同时 `supplier_id` 有值" —— 那就已经是方案 B。
- 这列**不是想删就能删**：现为 `NOT NULL`；全仓 `grep -c supplier_id` 命中 56 处（采购链 19+11+6+8+10+2，入库链 36+14+8）；`idx_biz_po_supplier(supplier_id, order_date DESC)` 与两处夹具清理语句依赖它。
- 顺带：`supplier_id` 的 `NOT NULL` 已经保证"零星采购必有供应商"，**不需要**再写 `CHECK (purchase_type='SPOT' AND supplier_id IS NOT NULL)` —— 重复表达 = 制造两处真相。

**维度② 列表性能（不是决定性维度，但必须把数字摆出来）**

场景：10 万张采购单 / 2 千张合同 / 2 千个供应商（`arch2_bridge_poc`，`EXPLAIN ANALYZE`，同脚本跑 4 轮，下表取一次代表性量测）：

| 场景 | 现状（单表无 JOIN） | 方案 A（JOIN 合同+供应商） | 方案 B（同表快照列） |
|---|---|---|---|
| 列表首屏（`ORDER BY order_date DESC LIMIT 20`） | 1.04 ms | 1.22 ms | 0.91 ms |
| 深翻页（`OFFSET 2000`） | 8.28 ms | 7.38 ms | —（同首页路径） |
| 全量导出（10 万行） | — | 46.6 ms | **18.3 ms** |
| 按供应商**名称**模糊筛 | — | **0.082 ms**（走 `idx_biz_po_contract` 嵌套循环） | 0.484 ms（`LIKE '%…%'` 走不上索引 → 顺扫） |

诚实结论四条：

1. **首屏没有可辨差异**（三者 0.6–1.4ms）——"JOIN 三层所以慢"在这张表上是伪命题：`LIMIT 20` 下嵌套循环只回表 20 次。
2. **深翻页也一样**：真正成本是 `OFFSET` 扫（7–8ms），JOIN 增量在噪声内，方向都不稳定（本轮 JOIN 反而更快）。
3. **唯一稳定差异在全量导出/报表聚合**：约 2.5×（46.6 → 18.3ms）。导出本就该走单独查询，"列表用快照、导出用 JOIN"可以并存。
4. **反例必须写**：按名称模糊筛时**方案 A 反而快约 5 倍** —— 方案 B 的 `supplier_name_snapshot LIKE '%…%'` 用不上 btree。**别把快照列当筛选用列**；要模糊搜就 JOIN 主档或后续上 `pg_trgm`。这是方案 B 唯一的技术债。

**维度③ 合同改乙方后的历史显示（伦理问题）**

- 方案 A：历史采购单页面的"供应商"跟着合同**当前**乙方变。三年前的采购单显示成"乙"，而货是甲送的、发票是甲开的、应付是给甲的 —— **这是审计事故，不是显示问题**。
- 方案 B：`supplier_id` 冻结在业务发生那一刻；要看"现在是谁"点"追溯真相"（详情页两栏：当时供应商（快照）/ 合同当前乙方（实时））。
- 代价：多维护一份一致性 ⇒ 必须配写入校验（§6.3 V-22/V-23）+ 巡检（§7 DI-01）。这是本方案唯一的成本，且可度量。

### 3.2 Q2：零星采购怎么约束

| `purchase_type` | `contract_id` | `contract_no_snapshot` | `supplier_id`（现状列） | 谁保证 |
|---|---|---|---|---|
| `CONTRACT` | **必填** | **必填** | 必填（列 NOT NULL），且必须 = 合同 `party_b_id` | DB：`ck_biz_po_contract_pair`；跨表一半：handler + 巡检 DI-01 |
| `SPOT` | **必须为空** | **必须为空** | 必填（列 NOT NULL） | DB：`ck_biz_po_contract_pair` 另一半 + 列 NOT NULL |

**两个必须解释的写法细节**

1. **为什么 `CASE … ELSE FALSE END`**：CHECK 结果为 `SQL NULL` 时 PostgreSQL 判定**通过**。写成 `A OR (B AND C)` 在 `purchase_type` 为脏值（如 `'CONTRCAT'`）时整体可能是 NULL ⇒ 脏值静默入库。`ELSE FALSE` 让它必然为假（实测见 §4.4 反例 5/6）。
2. **为什么不用列级 `NOT NULL`**：列约束只能表达"全都要"或"全都不要"，表达不了"看 `purchase_type`"。可空 + 表级 CHECK 是唯一能表达"条件必填"的写法。

### 3.3 Q3：入库单保留 `supplier_id`，语义为「快照（受直接上游强约束）」

**结论**：保留；`source_order_id` 保持可空（**不加 NOT NULL**）；新增 `ck_biz_si_supplier_scope` 表达"非采购入库不能带供应商"。

**为什么不是"冗余拷贝"（对输入③口径的收敛，见 §4.2 C-02）**

| 维度 | 判定 |
|---|---|
| 与**直接上游**（采购单）比较 | 同刻可无歧义重算 ⇒ 偏移恒为 **DEFECT**（这一点输入②③一致） |
| 与**最终真相**（合同）比较 | 合同换乙方 ≠ 本环缺陷，因为本环的"上一环"没变 ⇒ 若拿合同当真相比，2000 张历史入库单会被误判成缺陷（实测：真缺陷 0） |
| 语义定位 | 记录"收货那一刻供应商是谁" ⇒ **快照**；同时接受"必须等于直接上游"的强约束 ⇒ 比普通快照更严 |

**保留的四条落地理由**

1. **历史显示**：无源入库（复制单 / 手工单）上 `source_order_id` 为空，靠反查采购单取供应商这条路直接断掉，而这类单确实存在（现状 2 张入库单**全部**无来源）。
2. **应付/凭证取数**：过账时 `payable_bridge` 直接用单据头 `supplier_id` 建应付；若入库单不存，每张应付都要多一跳反查，且无源单无解。
3. **审批不依赖 ERP 读权限**：审批人四个采购相关角色 `erp_perms = 0`（实测），入库单审批表单里的供应商名是冻结在 `form_data` 里的，其源头就是单据头 `supplier_id`。
4. **写时校验成本低**：一条 `si.supplier_id = po.supplier_id` 比较即可，比"每次读取反查一跳"便宜。

**「禁止手工修改」怎么真正做得到（现状只做到一半）**

| 层 | 做法 | 效果 |
|---|---|---|
| DTO | 有源单时 `supplier_id` 不接受输入：给了且不等 → 400；给了且相等 → 忽略（幂等）；不给 → 从采购单带出 | 前端不再需要传，也没有"填错"的机会 |
| handler | `create_stock_in` / `update_stock_in` 在 `require_purchase_order` 之后加 `guard_parent_supplier`；**DRAFT 与 POSTED 一视同仁**禁止改 `supplier_id` / `source_order_id`（现状只拦 POSTED：`ensure_remark_only` 只在 POSTED 调用） | 草稿态也不能把 A 的单换成 B 的供应商 |
| DB | 无法表达跨表相等（CHECK 不能子查询）；只能表达方向：`ck_biz_si_supplier_scope` | 兜住"非采购入库带供应商" |

> 容易漏的一条：**改 `source_order_id` 时也要重算供应商**。现状 DRAFT 可换来源单而不同步供应商 = 直接制造缺陷。新口径：换来源单必须同时满足 `supplier_id = 新采购单.supplier_id`，否则 400。

**为什么 `source_order_id` 不做 `NOT NULL`**（撤回通用规则卡 I-P3 的依据）

| # | 合法无源路径 | 证据 | 若加 NOT NULL |
|---|---|---|---|
| ① 复制为新单 | 新单必须清空 `source_order_id`（原单已占用该采购单待收额度，再挂会二次占用 `received_qty` 导致超收误判） | `stockin_handler.rs:686-692`、`:775-782` | 复制功能直接 400/500，用户失去"照原单再来一单" |
| ② 手工建单 | 只要 `items` 非空、有供应商即可，允许无源 | `stockin_handler.rs:595-602` | 现网"补录/无采购单收货"流程立刻死 |
| ③ ADR-20261031 无来源入库（未来序列号批量生成） | 规格已定稿、代码未落地（实测 `serial_handler.rs` 对 `biz_stock_in` 0 处引用） | `docs/adr-20261031-erp-serial-batch-generate-semantics.md:53` | 已定稿的未来能力被一个迁移堵死 |

**替代方案（可执行、可监控、可回滚）**：A 档手工无源单必须有供应商 + `remark` 写原因（不硬校验）；B 档复制单在 `remark` 自动追加 `| 复制自 IN-xxxx`；C 档巡检输出"采购入库无源单占比"（GAUGE，不是缺陷）。本批**只落 C**。

> **两处被误传的理由，本文不采用**（写在此处防止下一个卡照错的理由做决定）：
> ① "期初库存是采购入库 + 无来源单" —— **不成立**：期初不走 `biz_stock_in`，直接写 `biz_inventory_txn`（`biz_type='OPENING'`/`doc_type='OPENING'`）。
> ② "序列号批量生成会产生无来源入库" —— **目前不成立**：那是 ADR 定稿的**未来**口径，代码未落地。
> 结论不变（不加 NOT NULL），但理由必须用 ①②③ 里成立的 ①（复制）②（手工）③（未来能力），而不是期初。

### 3.4 Q4：库存 `biz_inventory` 不显示供应商

**结论**：不加供应商列，也不加"最近一次供应商"这类缓存列。供应商只能按流水回溯，且回溯必须落到**具体某一次入库**：

```
biz_inventory（物料 × 仓库 × 库位 结存）
  → biz_inventory_txn（doc_type='STOCK_IN' + doc_id / doc_no 定位入库单）
    → biz_stock_in（supplier_id = 当时供应商快照）
      → biz_purchase_order（source_order_id；purchase_type + supplier_id 快照）
        → biz_contract（contract_id；party_b_id = 当前乙方真相）
          → biz_supplier（主档：名称/账期/开票信息）
```

这条路径每一跳都是**现成的列**（实测 `biz_inventory_txn.doc_type/doc_id/doc_no` 齐全，索引 `idx_biz_inv_txn_doc` / `idx_biz_inv_txn_no` 在位），不需要新结构。

**为什么不能加一列（三条模型级硬理由）**

1. **基数不匹配**：一行结存可能由几十上百次不同供应商的入库汇总而成；塞一列只能表达"某一次"，其余全错 —— 语义说谎，不是精度不足。
2. **会变成第二真相**：一旦有列，列表/报表就会读它，而它只可能来自"最近一次入库"或"加权平均"，两种口径都不是财务要的"这批货是谁的"。
3. **会破坏成本口径唯一性**：按供应商拆库存行（唯一键变 `material_id, warehouse_id, supplier_id`）等于把移动加权平均从"物料×仓库"改成"物料×仓库×供应商"，`avg_cost` 语义分裂成 N 份，`biz_inventory_location` 两级账、期初、年结、成本审计全部要重写 —— 那是另一个产品。

**"库存里想看供应商"怎么满足**

| 需求 | 做法 | 数据来源 |
|---|---|---|
| 列表显示"最近入库来自哪家" | 行点开"流水"抽屉，按 `material_id + warehouse_id` 拉 `biz_inventory_txn` | 流水 → 入库单 |
| 某笔入库的供应商/采购单/合同 | 流水行"追溯"按钮逐跳展示 `IN-xxx → PO-xxx → HT-xxx → 供应商名` | §5.5 视图 + 逐跳查询 |
| 按供应商看库存（"我欠谁多少货"） | **不是库存报表**，是采购/应付报表（在途 + 已入库未结算），按 `supplier_id` 聚合 | `biz_stock_in.supplier_id` / `biz_payable.supplier_id` |

### 3.5 Q5：「触类旁通」= 三条规则 + 7 条链的映射（摘要）

| 链 | 交易对手真相 | 下游快照链 | 现状 | 本批动作 |
|---|---|---|---|---|
| 采购 | 采购合同 `party_b_id` | 采购单 → 入库单 → 应付/凭证 | **部分** | **本批落地**（V0193–V0197） |

### 4.2 冲突清单与收敛决定（C-01 … C-13）

> 每条格式：**冲突 → 决定 → 理由 → 影响谁**。落到实现卡时按"决定"列执行，不再二次讨论。

#### C-01 甲方列名：`party_a_dept_id`（草稿）vs `party_a_id`（合同卡）

- **决定**：`party_a_id`。
- **理由**：与 `party_b_id` 对称；语义用 `COMMENT` 补足（`NULL`=本组织本体；非空=`sys_dept.id`）；合同表只有一张，列名只能有一个。
- **影响**：V0193 DDL、前端表单字段、合同 DTO。

#### C-02 入库单 `supplier_id` 语义：「冗余拷贝」（输入③，引 V0193 注释）vs「快照」（输入①②）

- **决定**：术语统一为 **「快照（受直接上游强约束）」**；巡检口径不变（与直接上游比较恒为 `DEFECT`，无白名单分支）。
- **理由**（两种说法为什么会同时"对"）：

| 比较对象 | 偏移是否可能合法 | 因此该叫什么 |
|---|---|---|
| 与**直接上游**（其采购单）比 | **不可能**（同刻可无歧义重算） | 这一环看像"冗余拷贝" ⇒ 偏移恒 DEFECT |
| 与**最终真相**（合同乙方）比 | **可能**（合同换乙方是合法业务，老采购单快照不变） | 这一环看像"快照" ⇒ 偏移可能合法 |

  「快照/冗余」描述的是**这一列与谁比**，不是列本身的固定属性。输入③按"与上游比"叫它冗余拷贝，输入②按"与合同比"叫它快照 —— 两者在**可执行层面完全等价**：DI-06 永远只 JOIN 直接上游，因此永远没有白名单。

- **额外收益**：这个统一顺带解释了 Q1 的 `po.supplier_id` 为什么**是**快照（DI-01 与合同比、有三态），而 `si.supplier_id` **只能是**强约束快照（DI-06 与采购单比、无三态）。两者名字里都有"快照"，但比较对象不同 —— 这正是"只绑上一环"的直接推论。
- **影响**：V0194 的 `COMMENT`（本文按"快照"写，并注明"必须等于其采购单"）、DI-06 判定（不变）、巡检卡 §8 第 2 条待裁决点（本文裁决：采用快照表述 + 恒等校验）。

#### C-03 合同金额精度：`NUMERIC(20,4)`（草稿）vs `NUMERIC(18,4)`（合同卡）

- **决定**：`NUMERIC(18,4)`。
- **理由**：全仓金额统一 18,4（PO/IN/PAYABLE 实测）；取 20,4 会出现"合同写得下、单据写不下"的金额，人为引入跨表精度不对称。上限 ≈ 10^14，远超任何单份合同。
- **影响**：V0193；累计下单额比较（V-23）不需要任何 scale 转换。

#### C-04 合同金额下限：`amount >= 0`（草稿，0=不限额）vs `amount > 0`（合同卡）

- **决定**：`CHECK (amount > 0)`；框架/不限额合同本批次不支持。
- **理由**：`amount = 0` 会让"已下单额 / 合同额"除零，必须到处写 `if amount > 0` 特判；正确做法是新增维度（`limit_type IN ('FIXED','UNLIMITED')`），不是让 0 兼职无穷大。
- **影响**：V0193；框架合同列入批次 3 候选（§13 U4）。

#### C-05 迁移号冲突（**最危险的一处**）

- **冲突事实**：

| 卡 | 它说的 V0193 | 它说的 V0194 | 它说的 V0195 |
|---|---|---|---|
| 合同表卡 | 合同 + PO 三列 + 漂移表 + 两视图（一锅端） | — | — |
| 合同表卡（修正建议） | 合同表 | PO 四列 | 漂移表 |
| 采购入库卡 | （V0193 为前置，不落） | PO 四列 + 入库单侧约束/索引 | — |
| 巡检卡 | （前置） | 漂移表 `issue_code` + 唯一键升级 | 合同乙方变更台账 |

  ⇒ V0194 与 V0195 各被两张卡占用，且语义完全不同。若照抄，两个实现卡会写出同名不同内容的迁移文件，迁移器按文件名排序执行 ⇒ 后执行者报错或静默跳过（`IF NOT EXISTS`），**生产上会出现"表建了但唯一键是旧形状"的中间态**。
- **决定**：重排为 **V0193 合同表 → V0194 采购单四列/入库单约束 → V0195 巡检结果表（`issue_code` 内建）→ V0196 变更台账 → V0197 追溯视图**；V0198+ 仍空。
- **理由**：① 一次迁移一个关注点，出问题可单独回滚；② 漂移表既然还没建，`issue_code` 直接内建，**不需要** `ALTER + DROP INDEX + CREATE INDEX` 的窗口期；③ 顺序与依赖一致（视图依赖合同列；台账依赖合同表）。
- **影响**：所有实现卡的迁移文件名；本文 §5 给出可原样执行的 5 份 DDL。

#### C-06 通用规则卡 I-P3（`PURCHASE` 型入库单 `source_order_id` 非空）**必须撤回**

- **决定**：**撤回**该巡检项；替换为"采购入库无源单占比"GAUGE（§3.3 档 C）。
- **理由**：复制为新单、手工建单、未来 ADR 序列化批量生成三条合法路径都是"采购入库 + 无来源单"（代码实测，见 §3.3 表）。硬落会把合法数据全部报成 P0，运维第一周就会关掉整个巡检。
- **更正理由链**：V0193 草稿头注释把"期初库存（V0189）"列为合法无源路径 —— **不成立**（期初不走 `biz_stock_in`，直接写 `biz_inventory_txn`）。结论不变，但**理由必须换**，否则下一个卡会照错的理由做别的决定。
- **影响**：§8.1 表 A 采购链目标第 2 条（改为"按入口分档 + 无源标记预留"）；巡检卡 §2.6；后续"追溯链完整性"卡（I-P6 同行级另包）。

#### C-07 采购单新增列：3 列（草稿）vs 4 列（采购入库卡）

- **决定**：**4 列** —— `contract_id` / `purchase_type` / `contract_no_snapshot` / `supplier_name_snapshot`。
- **理由**：只有 `contract_id` 快照不了"人看的东西"；审批人四个采购相关角色 `erp_perms = 0`，JOIN 了也打不开接口 ⇒ 单号与名称必须落在单据行上（与既有 `form_snapshot` 同思路，只是把冻结时刻从"审批时"提前到"建单时"）。
- **影响**：V0194；`PurchaseOrderRes` / 过滤器 / 前端列表列。

#### C-08 库存唯一键表述：`uk_biz_inv_mat_wh`（采购入库卡）vs 实测 `uk_biz_inv_mat_wh_loc`

- **实测**（`docs/evidence/2026-11-02-arch2-synthesis/baseline_check.log` §3）：
  `uk_biz_inv_mat_wh_loc ON biz_inventory (material_id, warehouse_id, COALESCE(location_id,'00000000-…'::uuid))`
- **决定**：正文口径改为 **「物料 × 仓库 × 库位」**；结论（不加供应商列）**不变且更强** —— 库位维度已经让"一行结存"更细，供应商再进来就是把移动加权平均拆成 N 份。
- **影响**：§3.4 论证措辞；后续批次成本/库位卡的前置描述。

#### C-09 入库单状态枚举：文档写 3 值 vs 实测 5 值

- **实测**：`biz_stock_in.status ∈ {DRAFT, POSTED, PENDING_CANCEL, PENDING_POST, CANCELLED}`（约束 `ck_biz_si_status`，见 baseline_check.log §2）。
- **文档说法**：（输入②§1.1、输入③§2.0）都写 `DRAFT|POSTED|CANCELLED` —— **缺 PENDING_CANCEL / PENDING_POST**（V0191「财务取消/反审批」引入）。
- **决定**：全文按 **5 值**；并补记 `ck_biz_si_pending_cancel`（`PENDING_*` 必须有 `approval_instance_id`，且反之必须为空）。
- **为什么要紧**：DI-06 的分级用 `s.status = 'POSTED'` 判"已过账"，若枚举少两项，会把 `PENDING_POST`（即将过账、已进入审批）当作草稿 → 分级偏低。本文 §7.2 已把 `PENDING_POST` 纳入"涉资"判定。
- **影响**：§7.2 DI-06/DI-07 分级、入库单取消/反审批相关实现卡。

#### C-10 巡检结果表：建在 V0193（草稿）vs `ALTER` 增强（巡检卡）

- **决定**：独立成 **V0195**，`issue_code` 内建，唯一键一次成型 `(issue_code, entity_type, entity_id, field_name) WHERE resolved_at IS NULL`。
- **理由**：见 C-05；另：唯一键**必须**含 `issue_code`，否则 DI-01（采购单快照 vs 合同）与 DI-12（采购单供应商主档悬空）都落在 `entity_type=PURCHASE_ORDER, field_name=supplier_id` 上，会互相覆盖 ⇒ 必有一方永远漏报。
- **影响**：V0195；巡检落库 SQL 的 `ON CONFLICT` 目标。

#### C-11 合同状态机：任务书 4 条边 vs 合同卡 5 条边

- **决定**：**5 条边**（补 `SIGNED → TERMINATED`）。
- **理由**：严格 4 边会强迫用户把"已签但从未生效"的合同先点成 `ACTIVE`，在 `biz_status_log` 里留下一条从未真实发生的 `SIGNED→ACTIVE` —— 用状态机形状**伪造审计事实**。
- **影响**：§6.4 边表；`state_machine.rs` 七处注册；单测 15 条禁边。

#### C-12 合同表是否带 `approval_instance_id`：草稿有，合同卡明确不加

- **决定**：**不加**。
- **理由**：合同审批流不在本批范围（§14）；加列不难，但会诱导实现卡"顺手接审批"，与批次规划冲突。审批接入时再 `ALTER`（合同表基数小，加列是元数据操作）。
- **影响**：V0193（本文 DDL 无该列）；§14 不做清单。

#### C-13 错误码 66013/66014/66015 被两张卡各自占用（**会直接写出两套语义**）

- **冲突事实**：

- **影响**：§6.5；`shared/error_code.rs` 常量 + 注册表（实现卡两处都要加）。

### 4.4 DDL 与巡检 SQL 的字段自洽（逐条比对，脚本化）

**怎么验的**（可复跑）：

**字段自洽的边界（必须诚实说明的两点）**

1. `di.*` 巡检视图引用的是**兼容层**（`di.v_po` 等），不是直接引用业务表 —— 这样同一份 SQL 能在"合同 schema 未就位"的库上跑（返回 0 行 + `SKIPPED`），不会因解析期报错而整轮挂掉。审计脚本同时核了业务表列与视图列。

#### 5.1.3 软删下的唯一性（三种错误写法对照）

```sql
-- ✅ 部分唯一索引：只用活跃行建唯一性，软删行不进索引
CREATE UNIQUE INDEX uk_biz_contract_no ON biz_contract (contract_no) WHERE deleted_at IS NULL;

-- ❌ 以下三种都见过，全部不合格：
--   UNIQUE (contract_no) WHERE deleted_at IS NULL   -- 建表语法错误，PG 直接报错
--   UNIQUE (contract_no, deleted_at)                -- 同一号能重复插入多次
--   UNIQUE (contract_no)                            -- 软删后号码永久不可复用，与"审计留旧行"冲突
```

语义：活跃行重号 → `23505`（实测）；软删后同号重建 → 允许，表里出现两条同号行，`deleted_at` 一有一无，审计可查"作废 → 重签"全过程。

#### 5.1.4 索引清单与理由

| 索引 | 定义 | 服务的查询 | 为什么这样建 |
|---|---|---|---|
| `uk_biz_contract_no` | UNIQUE `(contract_no) WHERE deleted_at IS NULL` | 按号精确查、取号查重 | 见 §5.1.3 |
| `idx_biz_contract_party_b` | `(party_b_id, sign_date DESC) WHERE deleted_at IS NULL` | "某供应商的全部合同"、详情页关联、DI-01/DI-13 | 前导列满足必备要求；第二列让列表天然按签约倒序出 |
| `idx_biz_contract_status` | `(status) WHERE deleted_at IS NULL` | 按状态筛选、`status IN ('SIGNED','ACTIVE')` 可用性判定 | 必备；基数小，单列足够 |
| `idx_biz_contract_end` | `(end_date) WHERE deleted_at IS NULL` | 到期提醒、逾期扫描 | 必备；**不用** `WHERE status='ACTIVE'` 收窄（`SIGNED` 也参与到期提醒） |

**关键设计点三条**（每条都有"否则会怎样"）：

1. **`issue_code` 是列，不是从 `field_name` 推**：DI-01 与 DI-12 都落在 `PURCHASE_ORDER.supplier_id`，没有 `issue_code` 时唯一键会互相覆盖 ⇒ 必有一方永远漏报。

## §6 写入链路与校验

### 6.1 三条写入链路（逐环取值，不许跳）

```
① 采购单建单/改单（purchase_handler::create_purchase_order / update_purchase_order）
   req.purchase_type='CONTRACT'
     → 校验 contract_id：存在、未软删、contract_type='PURCHASE'、status ∈ {SIGNED,ACTIVE}
     → 校验 order_date ∈ [start_date, end_date]（end_date 为空视为无限期）
     → 从合同带出 supplier_id        ← 唯一取值点（用户传的值必须相等，否则 400）
     → 从合同带出 contract_no_snapshot / supplier_name_snapshot
     → 累计下单额校验（同一事务 SELECT ... FOR UPDATE 锁合同行）
   req.purchase_type='SPOT'
     → contract_id / contract_no_snapshot 必须为空（否则 DB CHECK 拒）
     → supplier_id 由用户选择（必填，列 NOT NULL）

② 入库单建单/改单（stockin_handler::create_stock_in / update_stock_in）
   有 source_order_id
     → require_purchase_order（现有：存在 / 状态可收 / 仓库一致）
     → 【新增】guard_parent_supplier：supplier_id 从采购单带出；用户传的值必须相等，否则 400
     → 合同号只在展示时一跳带出（source_order_id → po.contract_no_snapshot），**不落库**
   无 source_order_id（复制 / 手工）
     → supplier_id 用户必填（DTO 已强制）
     → purchase_type 与合同**不落库**（入库单没有这两列，且不许加）

③ 入库单过账（stockin_handler::post_stock_in / stockin_bridge::on_post_settled）
   → 事务内再查一次采购单 supplier_id 与单据头比对（兜"建单后被直接改库")
   → 生成应付：payable_bridge 用单据头 supplier_id（快照，语义不变）
   → 生成流水：biz_inventory_txn 写 doc_type='STOCK_IN' / doc_id / doc_no（追溯链最后一跳）
```

**状态门（每条链的"什么时候不许写"）**

| 环节 | 允许写的前提 | 说明 |
|---|---|---|
| PO 建单 | 合同 `SIGNED/ACTIVE`、下单日在有效期内、累计不超签 | 只在**建单与换合同**时校验合同状态 |
| PO 提交/审批/收货 | **不再复检合同状态** | 合同中途 `COMPLETED/TERMINATED` 是常态；复检会把"已成立的业务承诺"卡死 |
| SI 建单/改单 | 来源单存在、状态可收、仓库一致、供应商 = 采购单供应商 | DRAFT 与 POSTED 一视同仁禁改 `supplier_id`/`source_order_id` |
| SI 过账 | 上述 + 供应商复校（兜直改库） | 过账后只允许改 remark |

### 6.2 校验分层（谁拦什么，不许互相推）

| 层 | 拦什么 | 失败表现 |
|---|---|---|
| **DB CHECK**（单行内可判定） | 枚举脏值、CONTRACT/SPOT 与合同列双向钉死、非采购入库带供应商、采购入库缺供应商、金额恒等、日期顺序 | `23514` → handler 统一翻 400 |
| **唯一索引** | 活跃行合同号重号、同一未解决漂移重复 | `23505` → 转业务码（不透传 SQLSTATE） |
| **handler 编排层**（要读别的表/看操作人/给话术） | 合同存在性/类型/状态/有效期/超签；供应商 = 合同乙方；供应商 = 采购单供应商；仓库一致；来源单状态 | `400/409 + 业务码 + 中文文案` |
| **状态机** | 非法状态边、自环、冻结字段 | `409 66014/66015` |
| **巡检**（T+1，只读） | 一切"绕过接口直改库"造成的漂移与孤儿引用 | 告警，不阻断业务 |

**为什么校验不放在 service 层 / 领域事件 / 触发器**：

- 本仓 `AGENTS.md` 明令**不设 service 层**，业务编排在 handler、数据访问在 model；凭空加一层违反约定。
- 全仓**零触发器**（实测 0），**无事件总线**；触发器只抛 `P0001`，拿不到业务码，同一规则会出现"应用层 400 中文话术 / 触发器 500 英文报错"两套语义；且触发器救不了"已存在的数据"（漂移来源是直改库/导入/主档删除，这些路径不经过触发器）。
- 领域事件语义也不对：供应商不一致是**请求错误**，不是"已发生的业务事实"；事件无法阻止写入。

#### 6.3.3 V-27 的五步判定（每步一个明确话术，避免"合同不可用"这种笼统提示）

| 步 | 检查 | 失败话术（66013 细分 message） |
|---|---|---|
| 1 | `contract.deleted_at IS NULL` | 「合同已删除，不能下单」 |
| 2 | `status IN ('SIGNED','ACTIVE')` | 「合同状态为草稿/已完成/已终止，不能下单」 |
| 3 | `:order_date BETWEEN start_date AND end_date` | 「下单日期 2026-11-02 不在合同有效期 2026-01-01 ~ 2026-12-31 内」 |
| 4 | `party_b_type='SUPPLIER' AND party_b_id = :supplier_id` | 「合同乙方与所选供应商不一致」（防"拿 A 合同下 B 供应商的单"） |
| 5 | `Σ PO(未取消) + 本单 ≤ amount`（同事务 `FOR UPDATE`） | 「累计下单将超出合同金额（剩余 3,200.00）」 |

等价 SQL（一条查询拿全，省三次往返）：

```sql
SELECT id, contract_no, amount, party_b_id, start_date, end_date, status
  FROM biz_contract
 WHERE id = :contract_id AND deleted_at IS NULL AND status IN ('SIGNED','ACTIVE');
```

### 6.4 状态机：5 条合法边 / 15 条禁止边 / 5 条自环 + 冻结矩阵

**允许的边（5 条）**

| # | from | to | 触发动作 | 必须 reason | 前置 |
|---|---|---|---|:--:|---|
| E1 | `DRAFT` | `SIGNED` | 登记签订（填三个日期） | 否 | 三日期必填（V-08）；乙方存在（V-16） |
| E2 | `SIGNED` | `ACTIVE` | 生效（到达 `start_date` 或手工确认） | 否 | — |
| E3 | `SIGNED` | `TERMINATED` | 已签未生效即终止 | **是** | ADR-07 |
| E4 | `ACTIVE` | `COMPLETED` | 履约完成 | 否 | 无未关闭下游（建议，不硬拦） |
| E5 | `ACTIVE` | `TERMINATED` | 中途终止 | **是** | 同上 |

**禁止的边（15 条，实现卡照抄成单测）**

| from | to | 禁止理由 |
|---|---|---|
| `DRAFT` | `ACTIVE` | 跳签：没有签订日却已生效，`SIGNED` 的存在意义被抹掉 |
| `DRAFT` | `COMPLETED` | 跳两级，且"从未签过却已完成"无业务含义 |
| `DRAFT` | `TERMINATED` | 草稿作废应走**软删除**；"终止"是对已签合同的动作，混用会让终止率统计失真 |
| `SIGNED` | `DRAFT` | 回退：签订事实不可撤销，只能终止 |
| `SIGNED` | `COMPLETED` | 跳级：必须先 `ACTIVE`，否则"已完成"缺乏生效区间 |
| `ACTIVE` | `DRAFT` / `SIGNED` | 回退 |
| `COMPLETED` | `DRAFT` / `SIGNED` / `ACTIVE` / `TERMINATED` | 终态：完成后发现违约走新签，不改历史 |
| `TERMINATED` | `DRAFT` / `SIGNED` / `ACTIVE` / `COMPLETED` | 终态：终止不可撤销，恢复 = 新签 |
| 自环 `X→X`（5 条） | — | 一律 409 66014；`transition` 已拒绝自环，调用方**不得**自己写 `if from != to`（会绕过注册表核对） |

**为什么 DB 拦不住状态机（防"加个 CHECK 就以为搞定"）**：CHECK 只能看单行当前值，看不到"上一状态"；要表达"从什么变成什么"必须有历史，而本仓写库是普通 `UPDATE`（无 CDC、无触发器）。实测：直改库 `DRAFT→COMPLETED` **成功**。因此边表只存在于应用层（`state_machine` 注册表），审计靠 `biz_status_log`，防绕过靠代码评审 + 一条 grep 级 CI（`rg "SET status" business/erp/contract_*` 应为 0 命中）。

**合同终止/完成后，已有下游单据怎么处理**（一条都不许回溯）

| 对象 | 处理 | 理由 |
|---|---|---|
| 已存在的采购单（任何状态） | **不改**（状态/金额/供应商都不动） | 合同终止不改变已发生的收货与付款事实；改 PO 状态 = 回滚历史 = 编造 |

**DI-01（三态判定的核心，全文引用）**

```sql
CREATE OR REPLACE VIEW di.c_di01 AS
WITH po AS (
    SELECT o.id AS po_id, o.order_no, o.supplier_id, o.status AS po_status,
           o.contract_id, o.created_at,
           c.contract_no, c.party_b_id,
           (SELECT max(pc.changed_at) FROM di.v_party_change pc WHERE pc.contract_id = c.id) AS changed_at
      FROM di.v_po o
      JOIN di.v_contract c ON c.id = o.contract_id
     WHERE o.deleted_at IS NULL AND c.deleted_at IS NULL
       AND o.purchase_type = 'CONTRACT'
       AND o.supplier_id IS DISTINCT FROM c.party_b_id      -- NULL 不静默漏判
)
-- ① 有台账且建单 ≤ 变更 → 合法历史快照（合同粒度聚合，不进告警队列）
SELECT 'DI-01'::text,'CONTRACT'::text,p.contract_id,p.contract_no::text,'party_b_id'::text,
       min(p.supplier_id::text), min(p.party_b_id::text), 'biz_contract.party_b_id'::text,
       'SNAPSHOT'::text,'INFO'::text, count(*)::int
  FROM po p WHERE p.changed_at IS NOT NULL AND p.created_at <= p.changed_at
 GROUP BY p.contract_id, p.contract_no, p.party_b_id
UNION ALL
-- ② 有台账但建单 > 变更 → 快照没跟随真相（单据粒度，P1）
SELECT 'DI-01','PURCHASE_ORDER',p.po_id,p.order_no,'supplier_id',
       p.supplier_id::text, p.party_b_id::text,'biz_contract.party_b_id','DEFECT','WARN',1
  FROM po p WHERE p.changed_at IS NOT NULL AND p.created_at > p.changed_at
UNION ALL
-- ③ 无任何变更台账 → 主体被事后改过（合同粒度聚合 = P0 疑似篡改）
SELECT 'DI-01','CONTRACT',p.contract_id,p.contract_no,'party_b_id',
       min(p.supplier_id::text), min(p.party_b_id::text),'biz_contract.party_b_id','DEFECT','ERROR',count(*)::int
  FROM po p WHERE p.changed_at IS NULL
 GROUP BY p.contract_id, p.contract_no;
```

三态判定矩阵：

| 变更台账 | 建单时刻 vs 变更时刻 | 判定 | 分级 | 粒度 |
|---|---|---|---|---|
| 有 | 建单 ≤ 变更 | `SNAPSHOT` 合法历史 | INFO（不告警） | 合同（聚合 `affected_count`） |
| 有 | 建单 > 变更 | `DEFECT` 快照未跟随 | P1 | 单据 |
| 无 | —（当前值 ≠ 真相） | `DEFECT` 疑似篡改 | **P0** | 合同（聚合） |

### 7.3 执行方式

| 档位 | cron（6 段） | 内容 | 为什么这个时间 |
|---|---|---|---|
| 增量 | `0 */30 * * * *` | 扫最近 40 分钟内 `updated_at` 变化的主体 + 其直接下游 | 30 分钟足够让"改库"被发现；多带 10 分钟重叠窗防边界漏 |
| 全量 | `0 20 2 * * *` | keyset 全表逐批（15 条全跑） | 02:20：备份之后、日志清理（3:00–3:50）之前、存储回收（4:30）之前 |
| 护栏 | `0 45 2 * * *` | 只跑 DI-14 | DI-14 挂了要单独可见，不能被别的项拖慢 |

- **keyset 分页，绝不用 OFFSET**：每批 2000 行 → 单轮最多 50 批（10 万行）；分页键 `WHERE id > :last_id ORDER BY id LIMIT 2000`；一批一事务（超时只丢一批）。
- **三级只读保护**：`BEGIN READ ONLY`（任何写直接报错）+ `SET LOCAL statement_timeout='30s'` + 不加任何表锁/`FOR UPDATE`。唯一写是结果表 `biz_snapshot_drift` 与告警表 `sys_notice`（行级写）。
- **多实例互斥**：`pg_try_advisory_lock(hashtext('cloudpivot.di.job'))`（实测跨会话互斥，同会话可重入 ⇒ 实现必须用独立连接）；拿不到锁跳过本轮。
- **只读副本**：本仓当前无第二数据源 ⇒ 阶段 1 在主库以 `READ ONLY` 事务跑；阶段 2 接副本必须先做 lag guard（`now() - pg_last_xact_replay_timestamp() > 60s` 则跳过本轮，否则会造成"假收敛"）。

### 7.4 结果落库与幂等（四层）

```sql
-- ① 结果幂等：重跑只刷新 last_seen_at 与观测值，detected_at 不变
INSERT INTO biz_snapshot_drift (issue_code, entity_type, entity_id, entity_no, field_name,
                                drift_kind, severity, snapshot_value, truth_value, truth_source, affected_count)
SELECT issue_code, entity_type, entity_id, entity_no, field_name,
       drift_kind, severity, snapshot_value, truth_value, truth_source, affected_count
  FROM di.c_di01
ON CONFLICT (issue_code, entity_type, entity_id, field_name) WHERE resolved_at IS NULL
DO UPDATE SET last_seen_at = CURRENT_TIMESTAMP,
              snapshot_value = EXCLUDED.snapshot_value,
              truth_value    = EXCLUDED.truth_value,
              severity       = EXCLUDED.severity,
              affected_count = EXCLUDED.affected_count;
```

| 层 | 机制 | 失败后果（没有它会怎样） |
|---|---|---|
| 结果幂等 | 部分唯一索引 + `ON CONFLICT ... WHERE resolved_at IS NULL` | 每轮重复插一行，看板行数爆炸（实测：两轮 → 仍 1 行） |
| 告警幂等 | `sys_notice.idempotency_key='di:{drift_id}:OPEN'`；P1 摘要键 `di:digest:{issue_code}:{YYYYMMDDHH}` | 同一缺陷反复轰炸，运维关通知 |
| 执行幂等 | advisory lock | 多实例/手工触发并发 → 双份告警 |
| 收敛幂等 | 只按 `last_seen_at < run_started` 收敛 | 重复执行会把已收敛行再改一遍，`resolved_at` 乱跳 |

### 7.5 分级 / 去重 / 收敛

```
P0（ERROR）= 钱已经动过 或 追溯链已断 或 主体被无审批地改过
   ├ 已审批/已过账/已收货/已关闭，或其下游已有应付/凭证（含 PENDING_POST）
   ├ 弱引用悬空（行根本不存在）
   └ DI-01 的「无变更台账」分支（疑似篡改，宁可错报）
P1（WARN）= 草稿态偏移、可重算的拷贝不一致、约束兜底命中、快照互斥
INFO      = 合法历史快照（只留痕，不进告警队列）
```

- **三层去重**：同一 `drift_id` 只发一次（`di:{id}:OPEN`）→ 同小时同巡检项的 P1 合并成摘要 → 跨轮的 SNAPSHOT 类不告警只留痕。
- **自动收敛**：本轮未再检出的未解决项 ⇒ `resolution='REPAIRED'`、`resolved_at=now()`、`remark='auto-closed'`，并发一条"已恢复"回执（实测 run3：open 20 → 18，通知 +2 条回执）。
- **复发**：修复后再次出现 ⇒ 新开一行（新 `detected_at`），旧行保持 `REPAIRED`（实测 run4：total 22，open 回到 20）。

### 7.6 处置动作（只报告，不自动改数据）

| 动作 | 语义 | 边界 |
|---|---|---|
| A `refresh-snapshot` | 以真相为准刷新快照（如把 `po.supplier_id` 改成合同乙方） | 需乐观锁（带 `last_seen_at`/版本），并落 `audit_logs`；**仅 DEFECT** |
| B `freeze-truth-as-snapshot` | 以快照为准"冻结真相"（如给合同补一条变更台账，认可历史） | **需审批**（谁有权改真相）；**仅 SNAPSHOT** |
| C `ignore` | 忽略（仅 P1） | 必须写 remark + 到期复核时间 |

**铁律**：巡检发现漂移后**自动回写快照** = 篡改审计证据（AP-8）。一致性问题最终都要落到"人判定 + 审计留痕"。

### 7.7 合法变更的白名单（台账，不是时间戳）

- 唯一来源：`biz_contract_party_change`（V0196）。写入点只有一个：合同变更审批通过的那个事务。
- **禁止**用 `contract.updated_at` 当白名单：改个备注也会推高它。
- 没有台账行时：DI-01 一律按 P0 处理（保守，宁多报不放过）；台账上线后误报率才会降下来。

### 7.8 `SKIPPED` 语义（0 行 ≠ 无缺陷）

- 合同 schema 未就位时（V0193/V0194 之前），DI-01..05、DI-13、DI-15 的 0 行必须记 `SKIPPED`，**不能记 PASS**。
- 看板必须显示「本轮 15 项 / 10 项 checked / 5 项 skipped」，否则会出现"合同主体巡检全绿"的假象 —— 比不巡检更危险。
- **`SKIPPED` 的项一行都不许收敛**（否则 schema 未就绪时会把历史真缺陷自动"治好"，这是本设计最危险的失败模式）。
- 兼容层 `di.*`（`00_install_compat.sql`）保证同一份 SQL 在两个 schema 阶段都能跑：旧表阶段 `to_jsonb(o)->>'contract_id'` 取 NULL + `v_contract` 零行空壳。

## §11 决策记录（ADR 式：背景 / 选项 / 决定 / 后果）

### ADR-01 采购单是否保留 `supplier_id`（Q1）

- **背景**：合同建成后，供应商真相上移到 `contract.party_b_id`。采购单现有 `supplier_id NOT NULL`，被 56 处代码 + 1 索引 + 夹具依赖。
- **选项**：A 删列纯关联；B 保留 + 降级为快照 + 新增合同四列。
- **决定**：**B**。
- **后果**：① 零星采购有地方存供应商（A 做不到）；② 历史单据显示"当时是谁"（审计要求）；③ 代价是多一份一致性，必须配写入校验（V-27/V-28）+ 巡检（DI-01）；④ `supplier_name_snapshot` 的模糊搜无索引，属技术债（要支持就上 `pg_trgm`）。

### ADR-02 入库单是否保留 `supplier_id`，以及"快照 vs 冗余"的表述

- **背景**：输入②定"快照"，输入③按 V0193 注释定"冗余拷贝"，两者对 DI-06 白名单有无的结论必须统一。
- **选项**：A 删除（全靠反查采购单）；B 保留为"普通快照"（允许 SNAPSHOT 白名单）；C 保留为"受直接上游强约束的快照"（与上游恒等，无白名单）。
- **决定**：**C**，术语写"快照（受直接上游强约束）"。
- **后果**：① 无源入库（复制/手工）仍能显示与记账供应商（A 会断链）；② DI-06 恒 DEFECT，不产生"合同换乙方导致 2000 行误报"（B 若与合同比会误报）；③ DRAFT 态也禁止改 `supplier_id`/`source_order_id`（现状漏洞 F2 收口）；④ 应付/凭证取数路径不变。

### ADR-03 库存 `biz_inventory` 是否显示供应商（Q4）

- **背景**：老板说"可以在…库存商品…中显示供应商"，但同时说"不是简单的字段存储"。
- **选项**：A 加 `supplier_id` 列；B 加"最近供应商"缓存列；C 不加列，走流水追溯 + 前端追溯入口。
- **决定**：**C**。
- **后果**：① 库存维度保持"物料×仓库×库位"，移动加权平均语义不分裂；② "按供应商看货"改由采购/应付报表承担；③ 批次成本/供应商溯源需独立表（批次管理卡），不在本批。

### ADR-04 甲方列名与语义

- **背景**：本库无"公司/法人"表，只有 `sys_dept`；草稿用 `party_a_dept_id`，与 `party_b_id` 不对称。
- **选项**：A `party_a_dept_id`（自解释）；B `party_a_id`（对称，语义靠注释）。
- **决定**：**B**（`NULL`=本组织本体；非空=`sys_dept.id`），并加 `party_a_name` 快照。
- **后果**：列名不自我解释 ⇒ 必须有 `COMMENT`；跨表 JOIN 甲方名要走 `sys_dept` 或读快照。

### ADR-05 合同金额的精度与下限

- **背景**：全仓金额 18,4；草稿 20,4 且 `>=0` 表"不限额"。
- **选项**：A 照草稿；B `NUMERIC(18,4)` + `> 0`（框架合同另立维度）。
- **决定**：**B**。
- **后果**：① 与 PO/IN/PAYABLE 可直接比较，无 scale 转换；② 框架/不限额合同本批不支持，`amount=0` 会让超签校验除零 ⇒ 批次 3 用 `limit_type` 维度解决，不改既有数据。

### ADR-06 合同乙方不建外键（弱引用）

- **背景**：`party_b_id` 是多态引用（SUPPLIER→供应商表 / CUSTOMER→客户表，后者不存在）；同链 PO/IN/PAYABLE/VOUCHER 实测 0 外键。
- **选项**：A 两个可空列各带 FK；B 单列 + 无 FK + 应用层校验 + 巡检；C 单列 + 触发器。
- **决定**：**B**。C 否决（全库 0 触发器基线；触发器只抛 P0001 拿不到业务码；救不了已存在的数据）。
- **后果**：DB 层**允许**写入孤儿 `party_b_id` ⇒ V-16 + DI-12 是**必需项**；加外键还会让夹具清理/数据修复因 RESTRICT 被打死（本团队最近三张卡都在收拾同库二次运行残留）。

### ADR-07 合同状态机 5 条边（比任务书多 `SIGNED→TERMINATED`）

- **背景**：任务书 4 边；但"已签未生效即终止"是真实场景。
- **选项**：A 严格 4 边（必须先点 ACTIVE 再终止）；B 补第 5 边。
- **决定**：**B**。
- **后果**：`biz_status_log` 不会出现伪造的 `SIGNED→ACTIVE`；实现卡须在 `state_machine.rs` 同步七处（变体/ALL/as_str/label/edges/reason_edges/locked_statuses），漏一处运行期 500。

### ADR-08 采购入库 `source_order_id` 不做 NOT NULL（撤回 I-P3）

- **背景**：通用规则卡要求"PURCHASE 型入库必须有来源单"，但代码实测三条合法无源路径（复制/手工/未来批量生成）。
- **选项**：A 加 `CHECK (in_type<>'PURCHASE' OR source_order_id IS NOT NULL)`；B 不加，改"按入口分档 + 无源标记 + 巡检 GAUGE"。
- **决定**：**B**。
- **后果**：① 复制/手工路径不被堵死；② 代价是"无源"无法从结构上区分合法与违规 ⇒ 后续需 `si.source_kind` 枚举列（DI-16）；③ 上线首轮要输出"采购入库无源单占比"作为基线。

### ADR-09 迁移拆分与编号（V0193–V0197）

- **背景**：草稿一锅端；两张卡同时占用 V0194/V0195。
- **选项**：A 照草稿一锅端；B 按关注点拆 5 个（V0193 合同 / V0194 PO 列+SI 约束 / V0195 漂移表 / V0196 台账 / V0197 视图）。
- **决定**：**B**。
- **后果**：① 单点可回滚；② 漂移表 `issue_code` 一次建对，无需 ALTER + DROP INDEX 窗口期；③ 实现卡按序命名，不再抢号。

### ADR-10 巡检结果复用 `biz_snapshot_drift`（不新建 `biz_data_integrity_issue`）

- **背景**：卡面允许"复用现有"或新建。
- **选项**：A 复用 `biz_snapshot_drift`（+ `issue_code`）；B 新建独立表；C 复用 `sys_notice`。
- **决定**：**A**。C 否决（告警是"通知"不是"状态"，没有生命周期与收敛）。
- **后果**：① 一个事实一处维护；② 唯一键必须含 `issue_code`（否则 DI-01 与 DI-12 互相覆盖）；③ 卡面 `OPEN/RESOLVED/IGNORED` 由视图派生，不落第二列。

### ADR-11 巡检比较"直接上游"而非"最终真相"

- **背景**：2 万张采购单 + 2 千入库 + 2 千应付的实测：合同换乙方后，与合同比"全部偏移"，与直接上游比"缺陷 0"、人为断裂精确检出 1 行。
- **选项**：A 全部与合同（最终真相）比；B 与直接上游比、跨环只做 SNAPSHOT 统计。
- **决定**：**B**。
- **后果**：① 一次合同换乙方只产生 1 条 SNAPSHOT 聚合记录（`affected_count=20000`），不是 2 万行噪声；② 真缺陷不会被淹没；③ 巡检 SQL 的 JOIN 条件必须锚定 `source_order_id` / `source_id`，**不许** JOIN 到合同。

### ADR-12 合法变更白名单用台账，不用 `updated_at`

- **背景**：DI-01 要区分"合法历史快照"与"事后篡改"。
- **选项**：A 用 `contract.updated_at`；B 用 `biz_contract_party_change` 台账；C 不做区分（一律 P0）。
- **决定**：**B**。A 否决（改备注也推高，双向误判）；C 只在台账上线前作为临时态。
- **后果**：新增一张表 + 一个写入点（变更审批事务）；台账未上线期间 DI-01 误报偏高（保守可接受）。

### ADR-13 合同变更走"终止 + 新签"，不做变更单/版本链

- **背景**：合同换乙方是真实业务。
- **选项**：A 允许随时改（靠巡检兜底）；B 变更单 + 审批 + 版本链；C `DRAFT` 全可改、`SIGNED` 起冻结关键字段。
- **决定**：**C**。
- **后果**：① 正常路径下**不存在漂移**（换乙方只可能发生在 DRAFT，此时通常还没下游单据）；② 残留漂移只来自历史修复/直改库/主档改名；③ 变更单需求 → 批次 3 候选。

### ADR-14 CUSTOMER 分支"结构留位、写入降级"

- **背景**：客户表属批次 2。
- **选项**：A 本期只留 `SUPPLIER` 枚举；B 结构全留、写入拒绝。
- **决定**：**B**（400 / 66019）。
- **后果**：批次 2 只需改 4 处（删一行判断 / 加一个分支 / 加一个 UNION / 放开前端），**零 ALTER TABLE、零数据修复**；本期不造任何示例客户数据。

| **B4** | 巡检上线：`di.*` 兼容层 + 15 条 + 定时任务 + 告警 + 处置接口 + 一致性页面 | B1（漂移表）、B2/B3（数据链路） | `backend-developer` + `frontend-developer` | 首轮 `dry_run` 基线归档；幂等/收敛/复发三轮实测；P0 通知可达 | 停止定时任务 + `DROP SCHEMA di CASCADE`（结果表保留） |
| **B5** | 迁移存量：S0 备份 → S1–S6 → 存量漂移清单交业务 | B2+B3 上线观察 ≥1 周（无新增 5xx） | `backend-developer`（DBA 配合） | 行数不变、双向钉死零违反、巡检基线归档 | 见 §9.3 三档 |

**依赖顺序（一句话）**：**先建表 → 改采购单 → 改入库单 → 巡检上线 → 迁移存量**。理由：采购单是"合同存在下游"的第一步（没有它，DI-01 无对象）；入库单依赖采购单的 `supplier_id` 语义；巡检依赖两条链路都接通；存量迁移必须最后做（否则会把"迁移半途"误判成缺陷）。

**并行度建议**：B1 的 V0195/V0196/V0197 可与 B2 并行（互不依赖列）；B4 的兼容层与 15 条 SQL 可在 B3 之前先行开发（旧 schema 阶段可跑，返回 SKIPPED）。
