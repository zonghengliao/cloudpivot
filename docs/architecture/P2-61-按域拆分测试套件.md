## 4. 选中语义：为什么必须 `--exact`（这张卡最容易做错的地方）

第一版实现把域的前缀直接当 cargo 过滤器传给 libtest，结果**多跑了 252 条重复**：

```
==> 用例清单：… platform=293（应为 43）… support=43（应为 41）
合计 5959（真实 5707）
```

根因：**libtest 的过滤器是子串匹配，不是前缀匹配**。

* `platform` 的前缀 `task::` 命中了 `business::task::` 的 250 条（`task-biz` 也是它们）；
* `support::` 命中两条形如 `business::hr::…::support::…` 的名字。

于是同一批用例在两个域里各跑一遍：一份库互不干扰，**红绿看不出来**，但耗时白付、`failures.txt` 会重复。

改法：**归属在 Python 里算，跑的时候给全名**。

1. 登记表的前缀只用来**算归属**（`resolve_owner`：最长前缀者胜，和门禁同一份实现）；
2. 每域先 `cargo test -p <crate> --lib -- --list` 拿到该 crate 的全部用例名，按归属筛出本域的名字；
3. 跑的时候传 `cargo test -p <crate> --lib -- --exact <name1> <name2> … --test-threads=1`。

`--exact` 让 libtest 按「全名精确相等」筛，与归属口径完全一致；代价是命令行变长
（`erp-finance` 776 个名字 ≈ 40 KB，远低于 `ARG_MAX`）。改完 `合计 = 5707`，与登记表门禁一致。

> 另一条踩过的坑：`cargo test <a> <b>` 会报 `unexpected argument '<b>'`
> —— cargo 只收**一个**位置参数 `TESTNAME`，多过滤器和 `--exact` 都必须写在 `--` 之后。

## 5. 用法

```bash
python3 scripts/test_domain.py list                 # 19 个域 + crate + 前缀数 + 说明
python3 scripts/test_domain.py run --package hr      # 只跑 HR（8.5 s，695 条）
python3 scripts/test_domain.py run --package erp-cost,hr,flow --jobs 3
python3 scripts/test_domain.py run --package all     # 全量分域并行（默认 jobs = min(8, 2×nproc)）
python3 scripts/test_domain.py run --package cloudpivot   # 单进程全量（改前口径，A/B 用）
```

* **库**：默认模板 `cloudpivot_test_full`（`bash scripts/verify/make_full_suite_db.sh` 造一次，实测 7.9 s），
  每域 `CREATE DATABASE … TEMPLATE` 克隆一份（19 份 1.1~4.2 s），跑完自动 DROP；
  有红或 `--keep` 时保留现场并打印库名。库名一律 `cloudpivot_test_p261_<域>`（含 `cloudpivot_test`，
  满足 `hr::fixture_hygiene` / `flow::internal_control` 的库名闸）。
* **地址**：99 上默认 `172.18.10.145`，145 上默认 `127.0.0.1`（`hostname -I` 判本机地址，与卡面口径一致）。
* **CWD**：脚本自己在 `backend/app` 下跑 cargo（`business::permission::scope_model` 的登记表用例
  扫相对路径 `src/`，在 `backend/` 跑会红）。
* **环境**：只设四条 `*_DB_URL`（同库）+ `NIK_PROFILE=test` + `RUST_TEST_THREADS=1`；
  继承来的 `NIK_DATABASE_*` 一律删掉（那是造模板库用的整库串，留着会让部分用例连错库）。
* **产物**：`--out DIR` 下每域一个 `<域>.log`、`summary.tsv`、`failures.txt`（排序去重的失败全名，
  可直接和单进程口径 `diff`）。默认 `mktemp -d`。

## 7. 门禁（防「漏登记 = 静默少跑」）

```bash
bash scripts/verify/test_domains_gate.sh                    # 完整性：用例↔域恰好一一对应
python3 scripts/test_domain.py check --manifest-only        # 只校登记表（check.sh L0 用，秒级）
```

判据（`scripts/test_domain.py check`）：

1. 每条用例命中**恰好一个**域（无遗漏、无重叠）—— `sum(域) == 用例总数`；
2. 每个域**非空**（前缀写错 / 模块删了就红，并点名到具体前缀）；
3. 登记表里的 crate 必须在 `cargo metadata` 里真实存在；
4. 登记表自身：域名唯一、前缀必须以 `::` 结尾（不带尾 `::` 的 `business::task` 会吞 `business::taskflow`）。

**反证（门禁有牙）**：往用例清单里塞一条未登记前缀的用例：

```
✗ 有 1 条用例不属于任何域（新增模块后忘了登记？）：
    前缀 business::newthing::  → 在 backend/test-domains.tsv 里登记（或并进最近的域）
✗ 计数不平：分域合计 5707 ≠ 用例总数 5708      → exit=1
```

`check.sh` 的 L0 只跑 `--manifest-only`（不编译、不连库，`cargo metadata --no-deps` 约 0.2 s）；
完整性档要列用例（需已编译的测试二进制，热树 ~1 s），按需跑 / CI 跑。

## 8. 与 P2-C（域 crate 拆分）的关系 —— 本卡的边界要写清

卡面写「**依赖**：P2-C 完成后做（crate 拆完才好按域分套件）」。**实测 P2-C 只落地了 C1**：
`backend/crates/` 里只有 `cloudpivot-doc`（19 条）与 `cloudpivot-kernel`（240 条），
C2~C15 的 13 个域包（`cloudpivot-hr` / `-erp` / `-flow` …）**都还没建**（`docs/architecture/P2-5x-*收口` 逐条作废、
落点是 `docs/planning/20261113-新卡清单.md` §P2-C.2 的 C3~C15）。

所以本卡**不能**假装「每个域一个包」，做的是**与包边界解耦的分域**：

* 登记表第一列是**域**，第二列是**当前真实存在的 crate**，第三列是**该 crate 内的过滤前缀**；
* 「分域」的隔离单位是 **域 × 进程 × 库克隆**（和既有 `docs/测试卫生-真库单测分库跑法.md` 的结论一致，
  那套脚本只覆盖 4 个模块、按过滤器跑；本卡扩到 19 个域、用模板库克隆、全名精确匹配）；
* **域包落地后只改 crate 列**（例如 `hr` 行的 crate 改 `cloudpivot-hr`、前缀列改 `-`），
  `--package hr` 的用法、门禁、并行调度**一律不变**；`kernel` / `doc` 两行就是这形态的现成样本。

也就是说：本卡交付的「分域登记表 + 运行器 + 门禁」是 P2-C 后续 13 张卡的**铺路件**，
不是它的替代品 —— 包拆完后这条命令不用改，只是每个域从「app 里的一段」变成「自己的 target」。

## 9. 坑（都踩过）

| 坑 | 现象 | 处置 |
|---|---|---|
| libtest 过滤器是**子串**匹配 | `platform` 从 43 变 293，全量多跑 252 条 | 归属在 Python 算 + `--exact` 全名 |
| cargo 只收一个位置参数 | `cargo test a b` → `unexpected argument 'b'` | 过滤器与 `--exact` 都写在 `--` 之后 |
| 单进程全量在第一个 target 失败就停 | kernel/doc 从未被跑到 | 分域进程独立，失败不互相中止 |
| CWD 不是 `backend/app` | `scope_model::d8c` 扫不到 `src/` 变红 | 运行器固定 cwd=`backend/app` |
| 库名不含 `cloudpivot_test` | HR/flow 的库名闸拒跑 → 50 条假红 | 克隆名 `cloudpivot_test_p261_<域>` |
| `--test-threads` 并行跑同域 | 同库夹具互踩 | 每域进程内 `RUST_TEST_THREADS=1`，并行度放在**进程**层 |
| `jobs` 按核数设（4） | 54 s，没用满 DB 并发 | 默认 `min(8, 2×nproc)`：DB 往返瓶颈，超订更快（4→54 s、8→42 s、12→42 s） |
| 模板库随树重建 | 表数/迁移与树不符 → 假红 | 换树后重跑 `make_full_suite_db.sh`（P2-60 §9 同口径） |

## 10. 顺带修好的 `make_full_suite_db.sh`（不修就跑不起来）

99 上本机 PG 已 purge，脚本原样跑不动，且有三处会静静出错：

1. `PGHOST` 缺省写死 `127.0.0.1`（99 上是到 145 的转发，卡面禁止用它做 PG）→ 改成按本机地址自动选；
2. `DB_USER`/`DB_PASS` 缺省 `alun`（已删）→ 改成 `cloudpivot`；
3. 建库走 `su - postgres`（只有本机 PG 才有的系统用户）→ 远端改走 `createdb -h … -U cloudpivot -O …`
   （本机仍走 `su - postgres`，两种位置都能建）；
4. 打印的 `URL` 里密码是 `***`，`RUN=1` 直接拿它连库会失败 → 单独留一份 `REAL_URL`；
5. `RUN=1` 与提示里的 `cd backend && cargo test --lib` 是**错的 CWD**（`scope_model::d8c` 会红）
   → 改成 `cd backend/app` + `cargo test -p cloudpivot --lib`，并加一行分域跑法的提示。

实测（99 → 145）：`ERP_DB=cloudpivot_test_full bash scripts/verify/make_full_suite_db.sh`
→ 7.9 s，自检 20 项全 ✓（336 迁移 / 178 表 / `DEPT_DEMO` / 6 个关键角色在职成员 / 业务单据 0 行）。
