## 1. 为什么做

卡面只有一句：**「耗时预算告警（单测 >5000 时提示）」**。它要解决的问题是：

- 单测变慢**不会自己喊**。同一条 `assert` 绿着，只是从 20 ms 变成 9 s，评测不报错、CI 也绿，
  于是它一直耗在每个开发者的 `cargo test` 里。等到有人发现「全量怎么这么慢」，翻日志要一条条翻。
- P2-63 已经把**逐条耗时**量出来了（`junit.xml` 的 `testcase/@time`，5712 条全部是实测），
  但报告只给 CI 看曲线，**没有任何人/流水线会因为单条过慢而吭声**。
- 所以要一条**有判据、能被反证**的告警线：单条 > 5000 ms 就点名，而且**不阻断**（卡面口径是「提示」）。

## 2. 判据口径（改判据前先读这一节）

| 项 | 取值 | 为什么 |
|---|---|---|
| 阈值 | **5000 ms**（`--limit-ms` / 环境变量 `TEST_BUDGET_MS` 可覆盖） | 卡面「>5000」；CI 上单条 5 s 已足够怀疑它在等网络/起进程 |
| 比较 | **严格大于**（`ms > limit`） | 卡面写的是「> 5000 时提示」；正好 5000 ms 算合格。门禁有成对断言钉边界（5000 不抓、5001 抓） |
| 单位 | 毫秒（XML 里是秒，读入时 `×1000`） | 单位写错是这类告警最隐蔽的坏法，门禁反证专门打它 |
| 是否阻断 | **不阻断**（`rc=0`）；`--strict` 才 `exit 1` | 「提示」不是「门禁」。想让 CI 红才显式开严格档 |
| 未量到耗时 | **不计入合格**，单独报「未判定」 | `from-logs` 回填的 XML 里每条 `time` 都是 `0.000`；按 0 判就会得出「5712 条全部合格」的**假绿** |
| 判定对象 | 单条用例 | 卡面就是单测粒度；总时长由分域并行负责（P2-60/P2-61） |

## 3. 数据从哪来（为什么必须走这里，而不是 `cargo test` 的某个开关）

stable libtest **不吐机器可读输出**：`--format=junit|json` / `--report-time` 全是 nightly + `-Z unstable-options`
（P2-63 实测 rustc 1.94.1 直接报错）。所以逐条耗时只能由 `scripts/junit_report.py::run_capture()`
**逐行读 stdout 并打时间戳**得到：

- 口径：`--test-threads=1` 下，相邻两行「判定行」（`... ok` / `... FAILED` / `... ignored`）的时间差
  = 上一条用例的执行时间；第一条从 `running N tests` 起算；
- 判定行**可能被用例自己的日志挤到下一行**（实测 kernel/platform 有 3/5 条），所以耗时的锚点是
  **判定行**，不是 `test <name> ...` 那一行（否则跨行的那几条会算成上一条的时间）；
- 判定行时间戳的误差：读管道开销 <0.2 ms/行（P2-63 实测 0.03 ms/行），相对 5 s 的判据可忽略。

## 4. 三个使用入口

```bash
# ① 日常/CI：跑分域套件，结尾自动出告警（`--junit` 或 `--budget-ms` 任一都开逐条计时）
python3 scripts/test_domain.py run --package all --junit /tmp/junit
python3 scripts/test_domain.py run --package all --budget-ms 5000          # 只要告警、不要 XML
python3 scripts/test_domain.py run --package all --budget-ms 5000 --budget-strict   # CI 卡住慢用例
python3 scripts/test_domain.py run --package system --no-budget                      # 明确关掉

# ② CI 只有 artifact 时（不重跑）：直接判 junit.xml
python3 scripts/junit_report.py budget /tmp/junit/junit.xml --top 10 --tsv /tmp/budget.tsv
python3 scripts/junit_report.py budget /tmp/junit/junit.xml --limit-ms 2000 --strict

# ③ 单 crate 直跑（字面就是 `cargo test -p <crate> --lib -- --test-threads=1`，外面套一层计时）
python3 scripts/junit_report.py run -p cloudpivot --budget-ms 5000
```

产物：`<out>/budget.tsv`（`ms / suite / name / over_budget`，按耗时降序，**全部**已量用例）。
它比告警文本更适合做趋势：两个版本的 `budget.tsv` 一 diff，就知道「哪条变慢了多少」——
只是「超过阈值」那一眼看文本就够。

输出样例（真实产物 `/root/p264/after/junit/junit.xml`，5712 条）：

```
==> 耗时预算（单测 > 5000 ms 提示）：5712 条已量
    ✗ 1 条超预算（> 5000 ms）—— 单测里出现这个量级，通常是在等网络/起进程：
         9016.8 ms  system::menu::permission_audit_tests::n14_menu_auth_codes_have_source_action_point   [system]
    最慢 10 条（含未超预算的，便于提前看出变慢趋势）：
         9016.8 ms  system::menu::permission_audit_tests::n14_…  [system]  ← 超预算
         3059.8 ms  business::erp::stockin::stockin_handler::stockin_handler_tests_dc03::lockorder_concurrent_post_and_cancel_no_deadlock   [erp-inventory]
         1924.4 ms  system::user::tests::u05_repeated_login_failures_lock_account   [system]
         …
```

## 5. 静默合格防线（本卡最容易做错的地方）

「没有告警」有两种原因：**真的都合格**，和**根本没量到**。两者在 CI 上都渲染成一片绿。

- `from-logs` 路径（把老日志补成 XML）**没有**逐条耗时 → 每条 `time="0.000"`；
  suite 属性里带 `per_testcase_time="unavailable"`。
- 判定读这个属性：`unavailable` 的套件里所有用例算**未量**，输出「**预算未判定**」，
  并明确说「要判定请用 `test_domain.py run --junit` 真跑」。
- 需要机器可判时用 `--require-measured`：一条都没量到就 `exit 2`（不是 0）。
- `test_domain.py` 没开逐条计时时也只打印「未判定」一行，不会因为「没测」看起来像「合格」。

门禁里对这两件事都有**反证**：`budget_unmeasured.xml` 必须报「预算未判定」且**不得**出现
「全部在预算内」；把它改成 `per_testcase_time="measured"` 就必须变成「全部在预算内」
（证明 ⑦ 的断言打的是真形态，不是空转）。

## 7. 实测（都在 `docs/evidence/2026-11-15-p264-budget/` 里）

### 7.1 告警本身的开销：**12.8 ms**（对 38 s 的跑批是 0.03%）

| 环节 | 耗时（min / median，n=7） |
|---|---|
| `budget_from_xml`（读 730 KB XML + 判定 5712 条） | 10.6 / **10.8 ms** |
| `format_budget`（拼文本） | 0.094 / **0.095 ms** |
| `write_budget_tsv`（写 5712 行） | 1.6 / **1.9 ms** |
| CLI 端到端（含 Python 启动） | **57 ms** |

口径：告警是**纯后处理**（吃 P2-63 已经量好的逐条耗时），不额外读日志、不额外连库。

### 7.2 改前 / 改后（推荐口径：19 域并行 + JUnit，一次跑全部 5711 条）

| 轮次 | 命令 | real | harness 合计 | 结果 |
|---|---|---|---|---|
| 改前 r3 | `… run --package all --junit … --no-budget` | **38.45 s** | 36.5 s | 5699 pass / **12 红** |
| 改前 r4 | 同上 | **38.03 s** | 36.1 s | 5699 pass / **12 红** |
| 改后 r3 | `… run --package all --junit …`（告警开） | **37.90 s** | 36.1 s | 5699 pass / **12 红** |
| 改后 r4 | 同上 | **38.29 s** | 36.4 s | 5699 pass / **12 红** |

改前均值 38.24 s、改后均值 38.10 s —— 差在噪声内（告警后处理 12.8 ms = 0.03%）。
四轮的失败名单 `diff` 为空（逐条相同 12 条，与 P2-63/P2-62 基线一致）：**本卡 0 新增红**。

### 7.3 改前 / 改后（字面口径：一次单进程全量 `cargo test -p cloudpivot --lib -- --test-threads=1`）

| 轮次 | 命令 | real | libtest `finished in` |
|---|---|---|---|
| 改前 1 | `time cargo test -p cloudpivot --lib -- --test-threads=1` | **169.89 s** | 169.75 s |
| 改前 2 | 同上 | **169.60 s** | 169.44 s |
| 改后 1 | 同一条 cargo + `junit_report.py run`（逐条计时 + 告警） | **172.20 s** | 171.95 s |
| 改后 2 | 同上 | **169.81 s** | 169.70 s |

改前 169.60/169.89、改后 169.81/172.20 —— 改后第 1 轮落在改前区间外 1.4%，第 2 轮落在区间内；
逐行打戳的实测增量是 0.03 ms/行（约 0.2 s/5745 行），所以 **1~2 s 的差异来自共享主机抖动
（同机还有别的卡在跑测试/编译），不是告警**。判这个差异要看 7.1 的微基准，而不是两次全量的差。

> ⚠ 单进程全量的**红集合不稳定**：改前（stdout 直连文件）2 轮都是 **12 红**、改后（经 Python 逐行捕获）
> 2 轮都是 **10 红**；另跑一轮「stdout 接 `tee` 管道但不经 Python」得 **12 红**
> （164.53 s），所以差异**不是管道**带来的，而是这两条用例自身对同进程里前序状态的敏感：
> `cost_period_approval` 的 5 条与 `stockin_handler_tests_p16::p16_graph_snapshot_selfcheck_is_clean`
> 会互相牵连（p16 红 ⇒ 那 5 条反而绿）。这是 P2-60 之后已知的**单进程全量夹具互踩**
> （`docs/architecture/P2-60-夹具复用模板.md` §8），成因未定，与本卡无关 —— 但**口径一律用分域并行**：
> 6 轮（P2-63 基线 1 + 本卡改前 2 + 改后 2 + 改后单次基线 1）失败名单逐条相同 12 条。
> 本卡的告警是把这类差异摆到明面上的工具，不是它的成因。

## 9. 已知限制（别当成 bug）

1. **并行跑批下的单条耗时含 CPU 竞争**：19 域并行时 `n14` 量到 9016.8 ms，单进程 8874.7 ms（+1.6%）。
   判「是否超预算」够用；**别拿它做跨机器/跨并行度的绝对值比较**。
2. **delta 口径**：耗时是「上一条判定行 → 本条判定行」，含上一条的收尾与本条的准备。
   5 s 判据下单条抖动不会因此翻转（除非用例本身就在 1 s 上下）。
3. **不判定总时长**：总时长的责任在 P2-60/P2-61（夹具复用 + 分域并行）；本卡只管单条。
4. **`budget.tsv` 不可跨版本直接 `join` 名字**：用例改名/拆分后行会变。做趋势要按 `name` 匹配、
   缺失的行单独看（不要按行号对齐）。
5. 阈值只覆盖「单条」；「某个域整体变慢」要靠 `summary.tsv` 的逐域墙钟（P2-61 已有）。

## 10. 排障：告警没出 / 出的不对

| 现象 | 先查 |
|---|---|
| 完全没有「耗时预算」那段 | `test_domain.py run` 是否带了 `--junit` 或 `--budget-ms`（没开逐条计时就只打印「未判定」）；是否被 `--no-budget` 关掉 |
| 说「预算未判定」 | 用的是 `from-logs` 回填的 XML（`per_testcase_time=unavailable`）；要判定得真跑 |
| 明明很慢却没报 | `--limit-ms` / `TEST_BUDGET_MS` 是否被环境变量改大；`budget.tsv` 里看该条的真实 `ms` |
| 报的名字对不上代码 | JUnit 里 `classname` + `name` 拼回来的全名；`#[path=…] mod` 的模块名以 `mod.rs` 里的声明为准 |
| 想让它阻断 CI | `--budget-strict`（`test_domain.py`）或 `--strict`（`junit_report.py budget`） |
