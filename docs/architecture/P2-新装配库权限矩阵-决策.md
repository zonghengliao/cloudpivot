# P2 · 新装配库权限矩阵缺卡 —— 决策与交付（t_227464dd）

> 结论先行：**授权不在装配路径上**（不是「少写了几行」）。
> 修法 = **一条版本化迁移 V0258**，把「生产已在生效的业务角色矩阵」冻结进装配流水线：
> 空库首启自动收敛到生产，生产执行零变更（实测「缺授权对 = 0」）。
> 证据：`docs/evidence/20261106-t2274dd-role-matrix/`

## 2. 根因：两层失效，不是一层

### 2.1 第一层：空库上「授权段」必然空跑

`nik` 迁移执行器 `MigrationKind::execution_rank()`：**baseline=0 → versioned=1 → repeatable=2 → seed=3**。
`bootstrap()` 由 `App::on_startup()` 调用，**在所有迁移之后**。

```
时间线（空库首启）
  版本化迁移 V0141 … V0213 ── 27 条都带 `IF n_roles = 0 THEN RAISE NOTICE '…跳过授权…'`
        ↑ 此刻 sys_role 一行都没有（SUPER_ADMIN 在种子里，种子还没跑）⇒ 授权段 100% 空跑
  版本化迁移 V0182/V0191/V0206 ── 业务角色**这时才被建出来**
  种子 S__role_data.sql ── 建 SUPER_ADMIN，按 role_code 自动展开的授权在这里才有效
  bootstrap ── 建 admin 账号并绑超管角色
```

⇒ 「迁移先于 bootstrap」这条注释本身没错，错的是**没有任何机制在角色出现后回头补授权**。
「bootstrap 后重放本迁移即可补齐」这句话在流水线上不存在 —— 没人会去重放。

### 2.2 第二层：那 27 条迁移的角色码，生产上一个都不存在（更致命的发现）

扫描 27 条带空跑保护的迁移，统计它们引用的 `role_code`：

| 角色码 | 被多少条迁移引用 | 生产是否存在 |
|---|---|---|
| `SUPER_ADMIN` | 27 | ✅（唯一有效） |
| `ADMIN` | 20 | ❌ |
| `ACCOUNTANT` / `FINANCE` | 14 / 14 | ❌ / ❌ |
| `TEST_UADMIN` | 9 | ❌ |
| `BUYER` / `PURCHASER` / `WAREHOUSE_KEEPER` | 3 / 3 / 3 | ❌ |
| `WAREHOUSE` | 1 | ❌ |
| `FINANCE_MANAGER` / `FINANCE_DIRECTOR` / `GENERAL_MANAGER` / `PURCHASE_MANAGER` / `WAREHOUSE_MANAGER` | 5 / 4 / 4 / 2 / 3 | ✅ |

生产实际角色（12）：`DEPT_LEADER, FINANCE_DIRECTOR, FINANCE_MANAGER, FLOW_CONFIG_APPROVER,
GENERAL_MANAGER, MUTEX_A, MUTEX_B, PURCHASE_MANAGER, QA_LIMITED, QA_VIEWER, SUPER_ADMIN, WAREHOUSE_MANAGER`。

⇒ **即便在非空库上跑，这些迁移的授权段也只命中 SUPER_ADMIN 一行**（超管本来通配短路，等于没授）。
换句话说：**生产那套业务矩阵从来不是迁移给的** —— 它是历史手工授权 + t_34cee9ea 的
手工 datafix（`scripts/datafix/bizperm/`，`plan.sql` 为声明矩阵）施工的结果。

这条结论决定了修法：**不能靠「让老迁移重跑」来补**（角色码是错的，重跑还是 0 行）。

## 4. 方案取舍（卡面 A / B / C 的实际可行性）

### 方案 A：新增一条「bootstrap 之后」的版本化迁移
**卡面的说法在架构上不成立**：bootstrap 在所有迁移之后，不存在「bootstrap 之后的版本化迁移」。
但它的**修正版成立**：新增一条**版本号更大**的版本化迁移，执行时 V0182/V0191/V0206 已经把
业务角色建出来了 ⇒ 授权能命中。这是本卡采用的做法（V0258），并额外获得：
一次性语义 + 内容指纹锁定（不可被悄悄改写）+ 有 `down`。

代价（已实测并写进文件头）：**执行时机在种子之前**，所以
① 它拿不到 SUPER_ADMIN（超管通配 `*:*:*`，功能零影响，只在权限树展示上少勾几个）；
② 它与种子抢插的 22 行会带本迁移的确定性 id（`down` 后需再 `up` 一次才回到装配基线）。

### 方案 B：框架层在 bootstrap 后自动重放「空跑过的授权迁移」
否决。理由不是「风险高」这种空话，而是**判据不存在**：迁移器只在 `schema_migrations` 记
`(kind,name,checksum,success)`，**不记录某条迁移是否命中 0 行**。要做只能改 nik-db 执行器 +
新增「部分成功」状态，且重放会与既有数据产生难以审计的二次授权。收益（省一条迁移）远小于代价。

### 方案 C：`sys_role_menu` 预置矩阵改成数据种子
否决，且比 B 更危险。种子（`MigrationKind::Seed`）= **指纹一变就重跑**。权限表最不能有这种语义：
管理员在角色授权页撤销一个码 → 某人日后改了该种子文件的任意一行 → 撤销被静默加回来。
仓里已有反例：`S__voucher_three_state_permissions.sql` 用「谁已有 voucher:create 就送三码」的
动态判据来缓解，但它挡不住「指纹变化重灌」这个机制本身。

### 采用的方案（A 修正版）与本卡的额外约束

1. **按「码」判重，不按「行」判重**。同一 `auth_code` 可挂在多节点上（页面 2 与按钮 3 共码，本仓 26 例）。
   按行判重会在生产插入 9 行「同码异节点」行（功能零变化但行数变了）；按码判重 ⇒ 生产 **0 行**。
2. **祖先闭包只补「无码目录」或「本次要一并授的码」**。无条件补祖先会把矩阵外的码顺手送出：
   实测 FLOW_CONFIG_APPROVER 有 `business:flow:approve`（其父页 `/flow/def` 的码是
   `business:flow:read`），无条件补 = 给该角色多授 flow:read = 越出矩阵 + 改生产。
3. **矩阵 = 生产当前生效的 450 对（7 个角色 × business 码）**，不含 SUPER_ADMIN（见上）。

## 6. 回滚

```bash
# 1) 应用 down（只删本迁移插入的行，既有授权一行不碰）
psql "$DSN" -f backend/migrations/business/V0258__business_role_matrix.down.sql
# 2) 若要让库回到「装配基线」，再跑一次 up（幂等）：会补回被本迁移抢先插入的 22 行种子行
psql "$DSN" -f backend/migrations/business/V0258__business_role_matrix.up.sql
# 3) 校验：任意库都可跑
python3 scripts/verify/role_matrix_gate.py --migration backend/migrations/business/V0258__business_role_matrix.up.sql --dsn "$DSN"
```

生产若已部署过 V0258 再回滚：down 会把 367 行删掉（其中 22 行本应由种子插入），
业务角色会立刻失去这些码 —— 这是**预期**语义，不是 bug；回滚后应立刻再 `up`
或按 `scripts/datafix/bizperm/20_grant.up.sql` 重建。

## 7. 遗留（本卡明确不做，建议单独开卡）

1. **孤儿按钮**：`FLOW_CONFIG_APPROVER` / `FINANCE_DIRECTOR` 持有 `business:flow:approve`，
   但父页 `/flow/def` 的码 `business:flow:read` 未授 ⇒ 按钮挂在看不见的页下。生产当前就是这形状，
   本卡保持同形不改（改它会顺带改生产授权）。建议：一张卡统一处理「按钮码有、父页码无」的
   2 个 (角色,码) 对 + 加一条自检闸。
2. **27 条老迁移的角色码全是历史遗留**（`ADMIN/ACCOUNTANT/FINANCE/BUYER/PURCHASER/WAREHOUSE_KEEPER/TEST_UADMIN`）。
   已应用迁移不可改写，建议加一条 CI 闸：`migrations/` 里出现不存在的 `role_code` 即失败，
   防止新迁移继续复制这套过时词汇。
3. **SUPER_ADMIN 的矩阵展示**：新库超管 `sys_role_menu` 只有 33 行（生产 284）。
   功能无影响（通配短路），只是权限树勾选看着少。是否补，取决于产品对「超管权限树可读性」的要求。
4. **新库 business 页比生产少 7 个**（52 vs 59）—— 两侧菜单集存在漂移（`/business/erp/purchase` →
   `purchase-order` 等改名），本卡按码定位因而不受影响，但值得一次菜单对平。
