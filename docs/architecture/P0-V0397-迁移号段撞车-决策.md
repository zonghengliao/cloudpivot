## 1. 事故的真实形态（机制，不是现象）

`backend/vendor/nik-db/src/migrate/loader.rs` 的加载模型：

- `load_from_sources(&sources, …)`（`loader.rs:192`）把**多个来源目录递归扫描进同一张 `Slots`**；
- `collect_versioned` 在同一张表里给 `(kind, version)` 占位，第二个同号文件直接报
  `duplicate_direction_error`（`loader.rs:734`）——
  `identities must be globally unique across all sources`；
- `Migrator::run()`（`mod.rs:441`）的**第一行**就是 `let list = self.load()?`，
  也就是：**迁移清单加载 → 冲突判定 → 才轮到读迁移记录表**。

⇒ 重号不是「某张迁移会失败」，而是「这个二进制在这个树上**永远拿不到迁移清单**」。
所以失败与库的形态无关：空库、已迁满库、裸库、甚至库连不上（连库失败会更快返回另一条错）都一样。
`AGENTS.md` 约定 6 原来只写了「动手前 `ls backend/migrations/*/` 核对」「4 位补零、已应用不可改」，
**没有一句话说「跨目录全局唯一」**，也没有任何自动判据 —— 这就是它能进 main 的原因。

（顺带纠正卡面「生产 144 是既有库、重启不受影响」的猜测 —— 见 2.3。）

### 2.3 已迁移库重启：**同样 FATAL**（这是真正的 P0）

做法：先把 `system/V0397` 临时移出 → 空库迁满 329 条（`02_…log`）→ 把文件放回（重号复原）→
对**那个已迁满的库**重启：

```
03_migrated_db_restart_FATAL.out
  rc=1   duplicate up migration for version 397 … identities must be globally unique across all sources
  FATAL: 服务启动失败: 配置错误: 数据库迁移失败
  重启前 schema_migrations = 329 行；重启后 = 329 行（未变）
```

**「重启前后行数未变」是关键证据**：失败发生在读记录表之前，与库迁没迁满无关。
⇒ 生产 144 的下一次 `systemctl restart`（发布 / 重启 / 宿主机维护都会触发）**必然起不来**。
这不是「等空库演练时才会遇到」的问题，是**随时会响的定时炸弹**，按 P0 处理是对的。

## 3. 「哪一条改号」的三条判据（按权重）

### 3.1 判据一：是否已上生产 —— 平局（都未上）

见 §2.2。所以继续用下面两条打破平局。

### 3.2 判据二：改号后「要不要动内容」—— 只有配色那条能保证零内容变动

**这一条是本次最反直觉、也最值钱的发现。** 记录表主键 `PRIMARY KEY (kind, name)`、**没有 version**；
`needs_apply()` 与 `verify_checksums()` 都按 `(kind, name)` 查。于是：

- **纯改名**（`V0397__x.up.sql` → `V0399__x.up.sql`，内容逐字节一致）：
  已应用旧号的库 → 记录命中 → 不重跑；当前内容指纹 == 记录指纹 → 不报错。**干净无副作用**
  （`06_…log`：启动 OK、`应用 0 个迁移`）。
- **改名 + 改内容**（我第一版往文件头加了一段「为什么改号」的说明，一共 9 行注释）：
  同一库立刻 `rc=1`：
  `migration version 399 (preference_palette_ids_gallery77) was modified after it was applied:
   recorded checksum 00f1ef… != current 5535ea…` + `FATAL`
  （`07_…log`；`divergent_policy` 默认 `abort`，见 `vendor/nik-config/src/lib.rs:1038`）。

⇒ **架构口径：迁移改号 = 纯 `git mv`，一个字节都不许动。** 改号理由写进文档（本文 + 证据 README），
**不写进 SQL 注释** —— 否则 145 上 `cloudpivot_dev` / `hr41_drill` 这两个「已应用旧号」的库会当场起不来，
而且这种失败只会在别人机器上出现（他们的库应用过旧号），排查成本极高。

这条判据把选择空间压到很小：**只能选那条「改号时不需要任何内容修正」的迁移**。配色那条恰好是：
它是一次性 `ALTER COLUMN` + `UPDATE`，本次改号不需要动它本身。

### 3.3 判据三：执行顺序耦合 —— HR 那条不能往后挪

若改 HR-40 那条（→ V0399 或更后），它就要排在 `V0398__hr_selfcheck` **之后**。而
`V0398` 是「HR 静态种子收口自检」（一次性 `DO` 块，缺一项 `RAISE EXCEPTION`，自检范围明确写着
「写种子是 `V0383~V0397` 的事」）。HR-40 那条改的是 `uk_biz_sal_sheet_period` 的谓词，
是 **V0383 建表语义的一部分**。把它挪到自检之后 = **先自检、后改动自检所依托的 schema**，
顺序语义倒置。配色那条不依赖任何 HR 迁移（只依赖 `V0091` 建的 `sys_preference_def`），挪到哪都安全。

**引用耦合面（次要论据）**：全仓 `V0397` 提及 84 处，其中绝大多数在 HR 侧
（`salary_compute.rs` 注释、`hr_invariants_tests.rs` 断言文案、HR-26/39/40/45/46 的证据与设计文档）；
配色那条的引用只有 `palette_def_sync.py` 的 docstring、`palette_def_sync_selftest.py`（写死文件名）、
`docs/evidence/palette-77` 与 `hr-emp-crud` 两份 README。改号要动的附属文件差一个量级。

### 3.4 定案

> **`system/V0397__preference_palette_ids_gallery77.{up,down}.sql` → `system/V0399__…`，纯重命名；
> `business/V0397__hr_salary_period_after_reverse` 不动。**
> 号段取值：全局最大 `V0398` + 1 = `V0399`（`AGENTS.md` 约定 6 的「全局最大 + 1」口径）。

## 5. 门禁：`scripts/lint/migration_version_unique.py`（L0）

### 5.1 它判什么（A–E）

| 判据 | 内容 | 为什么必须在这一层 |
|---|---|---|
| **A** | 同一前缀（`V`/`B`）的版本号**数值**跨 `system`/`support`/`business` 全局唯一 | 这是本次事故 |
| **B** | 4 位补零（`V0399` 而不是 `V399`） | 真库回放脚本按 `sort -n` 排文件名，混位数会排错序；也让人工核对失效 |
| **C** | 同名（`__` 之后那段）不得跨版本复用 | 记录表 `PRIMARY KEY (kind,name)`，nik 报 `name is used by two versions` |
| **D** | up/down 成对 | 无 down 的迁移回滚时只能手工改库（违背约定 11 的"不许改库才能恢复"精神） |
| **E** | 文件名主干只允许 `[A-Za-z0-9_]` | 空格/连字符/中文会让加载器解析出意料之外的名字 |

### 5.2 为什么不是「几行 shell」（卡面建议的三行）

三行 `ls | grep -oE 'V[0-9]{4}' | sort | uniq -d` 有三个硬缺口：

1. **只比字符串**：`V97` 与 `V0097` 在 nik 眼里是同一个版本（`Version` 是数值），三行抓不到；
2. **抓不到 C/D/E**：同名跨版本、缺 down、非法文件名三类同样是「启动即 FATAL 或回滚不能」；
3. **不告诉下一张卡该取哪个号**——而「各目录各算一个号」正是这次事故的**根因**。

所以做成门禁脚本，并且**每次跑都先跑 `--selftest`**（8 条红/绿语料，覆盖 A/B/C/D/E 每一条 +
「零填充不同但数值相同」这个组合），判据被放宽或语料被改坏 → 自检先红。
脚本还会打印 **「下一个可用版本号：V0400」**，直接消灭「各算一个号」的动机。

### 5.3 挂在哪一层

`scripts/check.sh` 的 **L0（秒级、无编译、无库）**，紧跟已有的「偏好字典 ↔ 色板一致」同源门禁，
并在 `plan_all()`（`--dry-run` 的计划表）里同步登记 —— `check.sh` 头注释明确要求"加/删门禁要同步改计划表"。
`--fast`（`pre-push` 钩子）就会跑到它 ⇒ 撞号在 push 阶段被拦，不会再进 main。

### 5.4 有牙演练（证明它不是永远绿）

`08/09/10_gate_l0_*.out`：干净树 `rc=0`（`649 文件 / 319 对 up-down / 399 版本`）→ 注入
`business/V0399__dup_probe.{up,down}.sql` 后 `rc=1` 且**指名两个文件**并给出修法 →
撤掉后 `rc=0`。另：在 main 原样（未改号）的树上第一次跑它，输出的正是本次事故的两个文件。
