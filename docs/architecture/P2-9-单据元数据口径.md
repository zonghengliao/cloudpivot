# P2-9 单据元数据口径（任务挂单据 + 采购单仓库快照）

> 依据：`docs/architecture/ARCH-3-模块勾稽关系审计.md` §5 **DC-19**（业务单据挂不上跟进任务）
> 与 **DC-23**（采购单无仓库快照）。两条都是 P2，合并到一张卡（`t_bb2e4702`）落地。
>
> 迁移：`V0238__task_doc_link_and_po_warehouse_snapshot`（up/down 均可重放）。
> 证据：`docs/evidence/20261105-p2-9-doc-link-warehouse-snapshot/`。

---

## 0. 一句话口径

| 问题 | 结论 |
|---|---|
| 「任务挂单据」的列 | `biz_task.doc_type` + `biz_task.doc_id`（**两列，成对**），单号**不落列**、现查 |
| 单据类型词表 | 取 `DocKind`（`business/shared/doc_kind.rs`，DC-21 唯一真相）∩ `task/doc_ref.rs::DOC_TARGETS`（本版本允许挂的 5 种） |
| 挂单校验 | 白名单（`63022`）→ UUID → **存在且未软删**（`63023`）；两者不成对 → `63004`；库侧 `ck_biz_task_doc_pair` 兜底 |
| 反向查询 | `GET /business/task/by-doc?doc_type=&doc_id=`，**走任务可见性**（挂单不是共享权限） |
| 仓库名的列表口径 | **快照**（`warehouse_name_snapshot`）；老单快照为空 → 批量现查兜底（不写库） |
| 仓库名的详情口径 | **现值**（关联查）；仓库被软删 → 回落快照 |
| 两套任务表 | **不合并**（`biz_task` 工作任务 / `biz_flow_task` 审批待办），本卡只加一条边 |

## 1. DC-19：任务挂业务单据

### 1.1 为什么是两列，而不是审计建议的三列

审计原建议 `source_doc_type` / `source_doc_id` / `source_doc_no` 三列。本卡落 **两列**：

- **单号不落列**：单号是另一张表的属性，落一列就是「第二份真相」。单据改名 / 作废 /
  软删后，任务详情还挂着一个旧号，用户会以为那张单还在。现查（`doc_ref::doc_no`）
  失败 → 显示「单据已删除」，语义诚实。
- **列名用 `doc_type` / `doc_id`** 而不是 `source_doc_*`：`source` 列在 `biz_task` 里
  表示**任务来源**（`SELF` / `ASSIGNED` / `TRANSFERRED` / `FLOW`），`source_doc_*`
  会让人误以为「来源单据 = 产生这条任务的单据」。而本卡的语义是「这张任务**说的是**
  哪张单」（跟进任务挂采购单，任务本身是人工建的）。

### 1.2 类型白名单从哪来（不新开一套词表）

DC-21 已经把「业务对象」收敛成 `DocKind`（17 个，含前端 TS 镜像与巡检域校验）。
本卡**不新增词表**：

```text
DocKind（17 种业务对象，唯一真相）
   └── task/doc_ref.rs::DOC_TARGETS （本版本允许被任务挂的 5 种 + 各表的单号列名）
        PURCHASE_ORDER → biz_purchase_order.order_no
        STOCK_IN       → biz_stock_in.in_no
        CONTRACT       → biz_contract.contract_no
        PAYABLE        → biz_payable.payable_no
        VOUCHER        → biz_voucher.voucher_no
```

- **为什么不给全 17 种**：能被「跟进」的是会走时间线的单据。`PAYMENT` / `BUDGET` /
  `INVENTORY` 这些要么是瞬间动作、要么不是单据；放开只会让「关联任务」区变成垃圾场。
  要加一种 = `DOC_TARGETS` 加一行（**不需要迁移**：DDL 不写值域 CHECK）。
- **为什么 DDL 不写 CHECK**：词表唯一真相在 `DocKind`（+ 前端镜像 + `biz_type_domain.py`
  巡检）。写死 CHECK 等于把词表抄第二遍，DC-21 往字典表收敛时还要再改一次迁移。
  库侧只兜**结构性**约束：`ck_biz_task_doc_pair`（类型与 id 必须同时有值或同时为空）。
- **严格全等、不做大小写归一**：与 `DocKind::parse` 同口径。归一 =「新旧写法都认」，
  前端本来就从 `DOC_KINDS` 常量取值，后端放宽只会掩盖调用方错误。

### 1.3 反向查询与可见性（红线）

`GET /business/task/by-doc` 走 `model::list_by_doc`，它用的是**与任务列表同一套谓词**
（`VISIBLE_OR_TAIL` + 参与 id 数组）：数据范围 ∪ 我参与的。

> **挂单不是共享权限。** 同部门两个人各挂一条任务在同一张采购单上，各自只看得到自己那条；
> 采购单详情底部的「关联任务」区**不是**越权入口。
> 谁看得见采购单 ≠ 谁看得见别人挂在它上面的任务标题与负责人。

结果**不分页**（硬上限 500）：一张单上的跟进任务天然是个位数量级；分页会让详情页多一层状态。

### 1.4 子任务 / 副本**不继承**单据关联

`POST /business/task/{id}/copy`（副本）与建子任务都写 `doc_type = NULL`：

- 挂单是**显式业务声明**，静默继承会让单据侧的「关联任务」里冒出用户没主动挂的行；
- 要挂就编辑时显式再挂一次（`PUT /business/task/{id}` 支持整对替换）。

### 1.5 改任务：整对语义

`PUT /business/task/{id}`：

| 传法 | 语义 |
|---|---|
| 两个字段都不传 | 不改 |
| `doc_type` + `doc_id` 都给 | 挂 / 换单（重新校验白名单 + 存在性） |
| 两个都 `null` | 清单 |
| 只给一个 | `400 + 63004`（「只改类型不改 id」在语义上不存在） |

`TaskPatch.doc` 用 `Option<(Option<String>, Option<Uuid>)>` —— 一个字段对，从类型上
就不可能写出「半对」。

## 2. DC-23：采购单仓库名快照（只做采购单试点）

### 2.1 为什么仓库要快照、项目不要

| 维度 | 口径 | 理由 |
|---|---|---|
| 供应商名（A3） | 快照 | 业务发生那一刻的乙方，换名不回写（P2-7 S2） |
| **仓库名（P2-9）** | **快照** | 这批货当时就是进那个仓；改名后历史单据列表仍应显示当时的名字 |
| 项目名（P2-8） | **实时现值** | 成本归集看的是「同一个项目」，改名后旧单必须跟着变，否则按项目汇总会裂成两行 |

三者不混：判断标准是「这个值是**历史事实**还是**当前归属**」。

### 2.2 列表与详情的两套口径（卡面验收）

```
列表：warehouse_name = warehouse_name_snapshot        ← 改名后仍显示旧名
详情：warehouse_name = 关联查 biz_warehouse（现值）    ← 点进去看到「现在是哪个仓」
      warehouse_name_snapshot = 快照（原样下发）        ← 前端并列「现值（原：旧名）」
```

- 详情查不到现值（仓库已软删）→ **回落快照**，不清空（详情比列表更不能一片空白）；
- 两个口径都**绝不回落 uuid**（与 P2-7 S2 / P2-8 项目名同口径）。

### 2.3 老单（快照为 NULL）的过渡期方案

`warehouse_name_snapshot` 是 V0238 才加的列 ⇒ 存量单全是 `NULL`。

- **不回填**：那些单下单时仓库叫什么，数据库里没有依据，回填就是伪造历史（R1）；
- **显示兜底**：列表对「`warehouse_name` 为空」的行按 `warehouse_id` **批量**现查一次
  （`purchase_model::warehouse_names_of`，一页一次往返），**只读不写**；
- 因此过渡期的表现是：**老单列表显示「现在的名字」**（因为没有快照），
  新单列表显示「下单当时的名字」。两种情况都不会空白、不会出 uuid。
- 什么时候可以删掉兜底：等存量单都被业务自然覆盖（或产品接受「老单没名字」）——
  这是一次显示层降级，不涉及数据迁移。

### 2.4 本卡**没做**的事（DC-23 的另一半）

DC-23 的另一半是「**采购单提交后发现仓库选错**」：本卡只补了快照（显示层），
**没有**放宽「只有 DRAFT 能改仓库」，也没有「收货时指定实际入库仓」。
那两条属于 `R-P2-5 ③`（要动状态机 + 收货侧校验 + `biz_status_log` 留痕），单独成卡。

## 3. 边界（明确不做）

1. **不合并 `biz_task` / `biz_flow_task`**：前者是工作任务（有人负责、有截止日、有进度），
   后者是审批待办（流程引擎产生、批准即消失）。合并会把两种生命周期塞进一张表。
   本卡只加「任务 → 单据」一条边。
2. **不给所有单据都加快照**：只做采购单试点（收货单 / 调拨 / 盘点各自的口径不同，
   例如收货单的仓是**实际入库仓**，与采购单的**计划收货仓**不是一回事）。
3. **不回填老单快照**（见 §2.3）。
4. **不做「单据 → 任务」的自动创建**（例如「审批通过自动建跟进任务」属 DC-20 / `TASK_NODE` 试点）。

## 4. 接口契约（前端可直接照抄）

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/business/task` | 请求体加 `doc_type` / `doc_id`（可空；成对） |
| `PUT` | `/business/task/{id}` | 两字段缺席 = 不改；同时 `null` = 清单；只给一个 → 400+63004 |
| `GET` | `/business/task/{id}` | 响应加 `doc_type` / `doc_id` / `doc_no`（单号现查，查不到为 `null`） |
| `GET` | `/business/task/page` | 任务卡加 `doc_type` / `doc_id`（列表不需要单号，省一次查询） |
| `GET` | `/business/task/by-doc?doc_type=&doc_id=` | `{doc_type, doc_id, doc_no, total, list[]}`，**已按任务可见性过滤** |
| `GET` | `/business/erp/purchase-order/page` | 每行加 `warehouse_name`（快照优先 + 老单兜底）/ `warehouse_name_snapshot` |
| `GET` | `/business/erp/purchase-order/{id}` | `warehouse_name` = 现值（软删回落快照）/ `warehouse_name_snapshot` = 快照 |

错误码：

| 码 | HTTP | 含义 |
|---|---|---|
| `63022` | 400 | `doc_type` 不在白名单（报文列出允许值） |
| `63023` | 400 | 单据不存在 / 已软删 |
| `63004` | 400 | 两者不成对 / `doc_id` 非法 UUID |

## 5. 前端

- 采购单列表：新增「收货仓库」列，只读后端 `warehouse_name`；
- 采购单详情：`收货仓库（现名）` + `下单时仓库快照` 两行并列（范式同供应商 S2）；
- 采购单详情底部：`DocTaskPanel`（`views/business/task/components/DocTaskPanel.vue`）
  —— 列出本单关联任务 + 直接新建（自动带 `doc_type/doc_id`）；
- 任务详情「基本信息」：`关联单据 = 采购订单 PO-xxxx`，可点（采购单页支持 `?po_id=` 深链）。
  其它 4 种单据暂无前端深链，只显示「类型 + 单号」（给点不动的链接比不给更糟）。
