## §0 结论速查（先看这张表，Q1–Q4 每问一句话）

| 问题 | 结论 | 决定性理由（不是"推荐/最佳实践"，是本仓实测事实） |
|---|---|---|
| **Q1 采购单是否保留 `supplier_id`** | **保留（方案 B：关联 + 快照）** | 方案 A 在**零星采购**上结构性失效（无合同的采购单没有任何地方能存供应商，而该列现在是 `NOT NULL` 且被 56 处 `grep` 命中 + 1 个索引 + 夹具依赖）；**性能不是决定性维度**（首屏三方案同在 0.6–1.4ms 量级、轮次波动大于方案差异；深翻页 JOIN 增量在噪声内；唯一稳定差异是全量导出约 2.5×（45–47ms vs 18–19ms），可用"导出走单独 JOIN 查询"规避） |
| **Q2 零星采购怎么约束** | `purchase_type` 枚举 + **`ck_biz_po_contract_pair` 双向钉死**（CONTRACT 必有合同 id + 合同号快照；SPOT 两者必须为空）；`supplier_id NOT NULL` 天然覆盖"SPOT 必须填供应商"；**"供应商 = 合同乙方"跨表校验 DB 做不到，落 handler + 巡检** | PG 的 CHECK **不能引用别的表**（实测 `ERROR: cannot use subquery in check constraint`），所以"跨表"的那一半只能应用层；同表的那一半必须落 DB（三值逻辑坑用 `CASE … ELSE FALSE END` 绕开） |
| **Q3 入库单是否保留 `supplier_id`** | **保留，语义定为「快照」**（不是"可重算的冗余"）：有源时在**建单事务内**从采购单带出、禁止手工修改、写入校验 `入库单.supplier_id = 采购单.supplier_id`；非采购入库强制为空（新增 DB CHECK） | 只有"快照"才能回答**合同换了乙方之后，历史入库单当时是谁**；"冗余"这个词只对**能被上游无歧义重算且不受历史合法变更影响**的列成立，`supplier_id` 不满足后者。且现状**这个一致性校验根本不存在**（`require_purchase_order` 只校验存在/状态/仓库），已能把 A 的货记到 B 的供应商名下 |
| **Q4 库存是否显示供应商** | **`biz_inventory` 不加供应商列**。供应商只能**按流水追溯**：`biz_inventory` → `biz_inventory_txn(doc_id/doc_no)` → 入库单 → 采购单 → 合同 → 供应商 | 库存是「物料 × 仓库」维度的结存（`uk_biz_inv_mat_wh`），供应商是**每笔入库的批次属性**；塞一列会导致"一个库存行有多个供应商"时必然说谎。批次成本/供应商追溯属**批次管理卡**，不在本卡 |

补充三条**不是结论而是口径**的判定（本册反复用到）：

1. **快照 vs 冗余的判据**（这是整套设计的灵魂，别混用）：
   - **冗余**：能由上游在**任意时刻**无歧义重算，且上游不会被合法改写 → 漂移即缺陷（DEFECT）。
   - **快照**：记录"业务发生那一刻"的事实，上游**事后合法变更**（合同换乙方、供应商改名）**不允许**回写历史 → 漂移可能是合法的（SNAPSHOT），只告警不定罪。
2. **只绑上一环的机械保证**：`biz_stock_in` **不允许**出现 `contract_id` / `party_b_id` 这类跨越一环的列。这是**结构决策**，不是代码纪律——列不存在，就没人能绕过去写。
3. **存量不回填**：历史单据没有合同就是没有（落 `SPOT`），当时供应商名称不可知就留 `NULL`。回填等于编造审计事实。

## §2 Q1：采购单保留 `supplier_id` —— 方案 B（关联 + 快照）

### 2.1 结论

**选方案 B。** `biz_purchase_order.supplier_id` 保留（列定义不动，`NOT NULL` 不动），
语义从"供应商外键"改成"**业务发生时的乙方快照**"，并**新增两列**把它升到可审计的水平：

| 列 | 类型 | 空 | 语义 |
|---|---|---|---|
| `contract_id` | UUID | 可空 | 合同（**弱引用** `biz_contract.id`，不建外键）；CONTRACT 必填 / SPOT 必须为空 |
| `purchase_type` | VARCHAR(8) | NOT NULL DEFAULT `'SPOT'` | `CONTRACT` 合同采购 / `SPOT` 零星采购 |
| `contract_no_snapshot` | VARCHAR(32) | 可空 | 合同号快照；列表/打印/审批表单不 JOIN 合同也能显示 |
| `supplier_name_snapshot` | VARCHAR(200) | 可空 | 供应商名称快照；存量行 `NULL`（当时名称不可知） |

### 2.2 三个维度的取舍（逐个算账，不含"最佳实践"式空话）

**维度① 零星采购（决定性）**

- 方案 A（删掉 `supplier_id`、全链靠 `contract.party_b_id` 推导）**无法表达**零星采购：
  没有合同 → 没有 `party_b_id` → 采购单没有供应商。要么给零星采购伪造一张"一次性合同"（数据污染 +
  合同台账里塞满无意义行），要么让 `supplier_id` 在"没有合同时"有值 —— 那就已经是方案 B 了。
- 而且这列**不是想删就能删**：`supplier_id` 现在是 `NOT NULL`，全仓 `grep -c "supplier_id"` 命中 **56 处**
  （采购链：`purchase_handler.rs` 19 / `purchase_dto.rs` 11 / `purchase_model.rs` 6 / `dto.rs` 8 /
  `batch.rs` 10 / `payable_bridge.rs` 2；入库链另计 `stockin_handler.rs` 36 / `stockin_model.rs` 14 /
  `stockin_dto.rs` 8），还被 `idx_biz_po_supplier(supplier_id, order_date DESC)`
  与夹具清理语句（`purchase_handler.rs:1219-1308`、`stockin_handler.rs:2963-3070` 按 `supplier_id` 删）
  依赖。删列的迁移成本与回归面远大于它的收益。
- **顺带**：零星采购也必须落供应商 —— 这一点 DB 已经保证了（列 `NOT NULL`），**不需要再写 `CHECK (purchase_type='SPOT' AND supplier_id IS NOT NULL)`**，写了只是重复表达同一个约束。

**维度② 列表性能（不是决定性维度，但必须把数字摆出来）**

场景：10 万张采购单 / 2 千张合同 / 2 千个供应商（`arch2_bridge_poc`，`EXPLAIN ANALYZE`，同一脚本跑 4 轮，
下表取**一次代表性量测**；4 轮的波动范围写在表下方的注里——单次值会让 0.1ms 的噪声看起来像结论）：

| 场景 | 现状（单表，无 JOIN） | 方案 A（JOIN 合同 + 供应商） | 方案 B（同表快照列） |
|---|---|---|---|
| 列表首屏（`ORDER BY order_date DESC, order_no DESC LIMIT 20`） | 1.04 ms | 1.22 ms | 0.91 ms |
| 深翻页（`OFFSET 2000`） | 8.28 ms | 7.38 ms | —（同首页路径） |
| **全量导出**（无 LIMIT，10 万行） | — | **46.6 ms** | **18.3 ms** |
| 按供应商**名称**模糊筛（列表筛选框） | — | **0.082 ms**（走 `idx_biz_po_contract` 嵌套循环） | 0.484 ms（`LIKE '%…%'` 用不上索引 → 顺序扫） |

> 上表是**一次代表性量测**（原始计划见 `bench_q1.log` / `bench_q1b.log`）。同一脚本跑了 4 轮，
> 首屏三方案在 **0.56–1.41 ms** 之间来回，**轮次之间的波动（可到 0.5 ms 以上）比方案差异还大**，
> 深翻页甚至出现过"有 JOIN 比无 JOIN 更快"（本轮 7.38 vs 8.28 ms）。所以下面的结论只谈**量级**，不谈小数点。

诚实结论（四点，都要写进汇总卡，别只抄"JOIN 三层会慢"）：

1. **首屏没有可辨差异**：三者同量级（0.6–1.4ms）。"JOIN 三层所以慢"在这张表上是**伪命题**——
   `LIMIT 20` 下嵌套循环只回表 20 次，成本被分页吃掉。
2. **深翻页也一样**：真正的成本是 `OFFSET` 扫（7–8ms 级别），JOIN 的增量在噪声以内、方向都不稳定。
3. **唯一稳定差异在全量导出/报表聚合**：约 **2.5×**（45–47ms → 18–19ms @10 万行）。
   但导出本来就应该走**单独的导出查询**，不必复用列表 SQL；"列表用快照、导出用 JOIN"可以并存。
4. **反例必须写**：按名称模糊筛时**方案 A 反而快 5 倍上下**（0.08–0.12ms vs 0.48–0.62ms）——合同维度有索引、
   供应商名走主档索引；方案 B 的 `supplier_name_snapshot LIKE '%…%'` 无索引用不上，退化成顺序扫。
   → **结论**：`supplier_name_snapshot` 只用于**展示与精确/前缀筛选**；按名称模糊搜仍允许 JOIN 主档，
   或后续给快照列加 `pg_trgm` 索引。**别把快照列当筛选用列**，这是方案 B 唯一的技术债，写在这里免得后人再踩。

**维度③ 合同改乙方后的历史显示（方案的伦理问题）**

- 方案 A：历史采购单页面的"供应商"跟着合同**当前**乙方变。合同从"甲供应"改成"乙供应"（真实业务：供应关系转移），
  三年前的采购单会显示成"乙"——而当时的货是甲送的、发票是甲开的、应付是给甲的。**这是审计事故，不是显示问题。**
- 方案 B：`supplier_id` 冻结在业务发生那一刻；合同维度要"现在是谁"就点"追溯真相"另看（详情页两栏：
  「当时供应商（快照）」/「合同当前乙方（实时）」）。
- 代价：多维护一份一致性 → 必须配**写入校验**（§7）+ **巡检**（§8），否则快照会腐烂成"随便写的一列"。这是本方案唯一的成本，且**可度量**。

### 2.3 为什么 `contract_no_snapshot` 与 `supplier_name_snapshot` 要**一起**加

只有 `contract_id` 快照不了"人看的东西"：列表要显示 `HT-20261102-000001` 就得 JOIN 合同表；
而审批人（岗位角色）在本仓实测**没有 ERP 读权限**（`form_snapshot.rs:1-30` 的实测注释：
四个采购相关角色 `erp_perms = 0`），JOIN 了他们也打不开接口。
所以**单号与名称必须落在单据行上**，这与现有 `form_snapshot` 的做法一致（只是把它从"审批时刻"提前到"建单时刻"）。

### 2.4 与 V0193 草案的差异（必须显式记录，供汇总卡收敛）

| 项 | V0193 草案 | 本册 | 处理 |
|---|---|---|---|
| `biz_stock_in.supplier_id` 语义 | 「冗余拷贝…**不是快照**…漂移即缺陷」 | 「**快照**…漂移可能是合法业务变更」 | **以本册为准**：草案措辞与 ARCH-2 卡面 Q3 自相矛盾；且"合同换乙方后入库单仍显示当时供应商"是财务口径的硬需求 |
| 存量 `supplier_name_snapshot` | 留 `NULL`，coalesce 兜底 | 同 | 一致 |

## §3 Q2：零星采购的约束写法与索引

### 3.1 结论表

| `purchase_type` | `contract_id` | `contract_no_snapshot` | `supplier_id`（现状列） | 谁保证 |
|---|---|---|---|---|
| `CONTRACT` | **必填** | **必填** | 必填（列 `NOT NULL`），且必须 = 合同 `party_b_id` | DB：`ck_biz_po_contract_pair`；跨表一半：handler（§7）+ 巡检（§8） |
| `SPOT` | **必须为空** | **必须为空** | 必填（列 `NOT NULL`） | DB：`ck_biz_po_contract_pair`（另一半）+ 列 `NOT NULL` |

### 3.2 约束写法（DB 能做的必须落 DB）

```sql
-- ① 枚举（同表、可判定 → 落 DB）
ALTER TABLE biz_purchase_order ADD CONSTRAINT ck_biz_po_purchase_type
    CHECK (purchase_type IN ('CONTRACT', 'SPOT'));

-- ② 双向钉死：一条 CHECK 同时管两个方向（同表、可判定 → 落 DB）
ALTER TABLE biz_purchase_order ADD CONSTRAINT ck_biz_po_contract_pair
    CHECK (CASE purchase_type
             WHEN 'CONTRACT' THEN contract_id IS NOT NULL AND contract_no_snapshot IS NOT NULL
             WHEN 'SPOT'     THEN contract_id IS NULL     AND contract_no_snapshot IS NULL
             ELSE FALSE     -- ← 关键：PG 的 CHECK 遇 NULL 视为"通过"，ELSE FALSE 才拦得住脏值
           END);
```

三个**必须解释的写法细节**：

1. **为什么 `CASE … ELSE FALSE END`**：本仓 V0137 头注释的「写法纪律②」已经踩过——`CHECK` 的结果为 `SQL NULL`
   时 PG 判定**通过**。写成 `A OR (B AND C)` 在 `purchase_type` 为脏值（如 `'CONTRCAT'`）时整体可能是 `NULL`，
   脏值静默入库。`ELSE FALSE` 让它必然为假。实测反例见 §3.4-③。
2. **为什么不用 `contract_id NOT NULL` 列约束**：列约束只能表达"全都要"或"全都不要"，表达不了"看 `purchase_type`"。
   可空 + 表级 CHECK 是唯一能表达"条件必填"的写法。
3. **为什么"SPOT 必须有供应商"不另写 CHECK**：`supplier_id` 从 V0137 起就是 `NOT NULL`，已经覆盖。重复写一条
   只会让后人以为那条列约束不存在，制造两处真相。

### 3.3 索引策略

```sql
-- 合同维度回查（"这张合同下有哪些采购单"/ 合同执行情况汇总）
CREATE INDEX idx_biz_po_contract
    ON biz_purchase_order (contract_id, order_date DESC) WHERE contract_id IS NOT NULL;
```

| 决策 | 理由 | 实测 |
|---|---|---|
| **部分索引**（`WHERE contract_id IS NOT NULL`） | 零星采购（`NULL`）不占索引体积；合同回查必然带 `contract_id = ?`，谓词与部分索引完全匹配 | 计划里出现 `Index Scan using idx_biz_po_contract`（§2.2 场景 I 原文） |
| **列序 `(contract_id, order_date DESC)`** | 合同页按时间倒序列单，第二列让排序在索引内完成，不走 `Incremental Sort` | 同上，`rows=20` 无 sort 节点 |
| **保留 `idx_biz_po_supplier(supplier_id, order_date DESC)`** | 按供应商筛（现状列表筛选框在用，`model.rs:1478-1520` `purchase_order_page` 的 `supplier_id` 等值条件） | 不新增、不删 |
| **不给 `purchase_type` 建索引** | 取值只有 2 个，选择度极低（10 万行里 9 万 CONTRACT），全表扫都比索引随机 IO 快；真要按类型筛，走 `idx_biz_po_contract` 部分索引即可区分 | — |
| **不给 `supplier_name_snapshot` 建普通 btree** | 名称模糊搜 `LIKE '%…%'` 用不上 btree；真要支持前缀搜，用 `text_pattern_ops` 前缀索引或 `pg_trgm`，属后续卡 | §2.2 场景 J 实测顺序扫 0.532ms |

`idx_biz_si_no_source`（部分索引）的收益已实测：`SELECT count(*) FROM biz_stock_in WHERE source_order_id IS NULL
AND deleted_at IS NULL` → `Index Only Scan using idx_biz_si_no_source`，`Heap Fetches: 0`，0.042ms
（"采购入库无源单占比"这条口径监控就靠它，别退化成全表扫）。

### 3.4 反例（DB 真的拦得住，不是纸面约束）

| # | 尝试写入 | 结果 | 拦它的约束 |
|---|---|---|---|
| ① | `purchase_type='CONTRACT'`，`contract_id IS NULL` | 被拒 | `ck_biz_po_contract_pair` |
| ② | `purchase_type='SPOT'`，带 `contract_id` | 被拒 | `ck_biz_po_contract_pair` |

### 3.5 `contract_id` 的外键问题（卡面写"外键"，这里给出决定与代价）

**决定：不加硬外键，用弱引用 + 索引 + handler 校验 + 巡检。** 依据三条：

1. **同链基线**：`biz_purchase_order` / `biz_stock_in` / `biz_payable` / `biz_voucher` 的引用列**外键数为 0**
   （§1.2 实测）。只给 `contract_id` 加一个硬约束，等于在同一个表里搞两套口径，
   下一个写代码的人一定以为 `supplier_id` / `warehouse_id` 也该有外键。
2. **外键收益本来就窄**：合同的"删除"是**软删**（`deleted_at`），外键拦不住软删。硬外键唯一能防的是
   "手滑写入一个不存在的 UUID"，而这恰好可以用 handler 的 400 + 巡检覆盖（§7、§8）。
3. **代价明确**：加外键后，任何"清理测试夹具 / 数据修复"的 `DELETE FROM biz_contract` 都会因
   `biz_purchase_order` 的存在而被 RESTRICT 打死；本团队最近三张卡（`t_06c528fc`、`t_7f47221c`、`t_2287c331`）
   都在收拾"同库二次运行残留"，加硬外键只会把残留问题从"孤儿行"升级成"删不掉"。

如果总管坚持要外键，等价写法与代价如下（**本册不采用**，仅备查）：

```sql
-- 前置：V0193 必须先落地（表存在才能建外键）；且合同删除改走软删纪律
ALTER TABLE biz_purchase_order
    ADD CONSTRAINT fk_biz_po_contract FOREIGN KEY (contract_id) REFERENCES biz_contract(id)
    ON UPDATE RESTRICT ON DELETE RESTRICT;   -- 不可用 CASCADE：删合同顺带删采购单是灾难
-- 代价：① biz_contract 成为全库唯一"单据引用目标"，与仓库/物料/供应商口径不一致
--      ② 夹具清理必须按 FK 拓扑序删（PO → 合同），现有 teardown 会大面积失败
--      ③ 建/改单事务会对合同行加 KEY SHARE 锁，合同并发改乙方时与下单互相阻塞
```

## §4 Q3：入库单保留 `supplier_id`，语义为「快照」

### 4.1 结论与"为什么不是冗余"

**保留 `supplier_id`，并把它定义为快照。** 这个判断不是口味问题，用 §0 的判据量一遍：

| 维度 | `biz_stock_in.supplier_id` |
|---|---|
| 能否由上游在任意时刻无歧义重算？ | **同一时刻可以**（= `biz_purchase_order.supplier_id`） |
| 上游会被**合法**改写吗？ | **会**：采购单 `supplier_id` 在 DRAFT 可改；合同换乙方后新采购单的 `supplier_id` 会变，老采购单不变 |
| 结论 | 它记录的是"**这份货收货那一刻，供应商是谁**" → **快照**，不是冗余 |

"冗余"这个词只配给"重算结果恒等于快照"的列。`supplier_id` 不满足，所以 V0193 草案把它写成
"冗余拷贝、漂移即缺陷"是**错的**——按那个口径，合同换乙方之后的每次巡检都会把历史入库单判成缺陷，
运维会去"修复"历史数据，等于把审计事实改掉。

**同时必须承认的一半**：入库单 → 采购单这一环的 `supplier_id` 在**建单那一刻**确实是"从采购单带出的拷贝"，
所以这一环的漂移**是**缺陷（DEFECT）；而"采购单 → 合同"那一环的漂移**可能是**合法快照（SNAPSHOT）。
两类漂移的判据必须分开写（§8.2 的巡检 SQL 就是这么分流的），不能一刀切。

### 4.2 保留的四条理由（每条都能落到代码/账务）

1. **历史显示**：合同换乙方后，历史入库单仍要显示"当时是谁"。靠 `source_order_id` 反查
   `biz_purchase_order.supplier_id` 也能得到同样的值——但在**无源入库**（复制单、手工单）上这条链断了，
   而这类单确实存在（§1.3-F6）。
2. **应付/凭证取数**：过账时 `payable_bridge` 的应付单直接取入库单头的 `supplier_id`
   （`payable_bridge.rs:1153` `INSERT INTO biz_payable (… supplier_id …)`）。
   若入库单不存供应商，每一张应付单都要多一跳反查采购单，且无源单无解。
3. **列表/审批不依赖读权限**：审批人没有 ERP 读权限（`form_snapshot.rs` 实测），入库单审批表单里
   `supplier_id` + `supplier_name` 是冻结在 `form_data` 里的（`stockin_handler.rs:2210-2235`），
   这份快照的源头就是单据头的 `supplier_id`。
4. **写时校验成本低**：一条 `supplier_id = order.supplier_id` 的比较就能保住一致性（§7.2），
   比"每次读取都反查一跳"便宜得多。

### 4.3 「禁止手工修改」怎么真正做得到（现状只做到一半）

现状：`ensure_remark_only`（`stockin_handler.rs:838-850`）只拦 **POSTED** 状态；**DRAFT 可随便改**（F2）。
三层收口：

| 层 | 做法 | 效果 |
|---|---|---|
| **DTO 层** | 有源单（`source_order_id` 非空）时，`supplier_id` **不接受输入**：给了且不等 → 400；给了且相等 → 忽略（幂等）；不给 → 从采购单带出 | 前端不再需要传，也没有"填错"的机会 |
| **handler 层** | `create_stock_in` / `update_stock_in` 在 `require_purchase_order` 之后加一条 `guard_parent_supplier`（§7.2）；`update_stock_in` 对**非 DRAFT 与 DRAFT 一视同仁**地禁止修改 `supplier_id` / `source_order_id`（现状只拦 POSTED） | 草稿态也不能把 A 的单换成 B 的供应商 |
| **DB 层** | 无法表达"跨表相等"（§3.2-实测 `cannot use subquery in check constraint`）；只能表达范围：`ck_biz_si_supplier_scope`（§4.4） | 兜住"非采购入库带供应商"这类方向性错误 |

> 补一条容易漏的：**改 `source_order_id` 时也要重算供应商**。现状 `update_stock_in` 允许在 DRAFT 换来源单，
> 换了来源单却没换供应商 = 直接制造 F1。新口径：换来源单必须同时满足 `supplier_id = 新采购单.supplier_id`，
> 否则 400（文案告诉用户"来源单变了，供应商请一并按新单填写或留空自动带出"）。

### 4.4 非采购入库 `supplier_id` 为空 —— 新增 DB CHECK

```sql
ALTER TABLE biz_stock_in ADD CONSTRAINT ck_biz_si_supplier_scope
    CHECK (CASE WHEN in_type = 'PURCHASE' THEN TRUE ELSE supplier_id IS NULL END);
```

- **为什么能加**：`stockin_model.rs:995` 把 `in_type` 硬编码成 `'PURCHASE'`，现网全是 PURCHASE，
  存量不可能违反（本机 4 个库实测 0 违反）。所以这条是**能力约束**，不是**存量约束**，加不加存量都过。
- **与既有 `ck_biz_si_supplier` 的关系**：那条只管"采购入库必须有供应商"（正向），这条管
  "非采购入库不能有供应商"（反向），两条合起来才是完整的两向约束。
- **必须先纠正一个事实**：卡面写"非采购入库（**调拨**/生产/退货）`supplier_id` 为空"——但**调拨根本不写
  `biz_stock_in`**，它有独立的 `biz_stock_transfer`（V0140，`transfer_handler.rs` 全程不碰 `biz_stock_in`，
  `grep` 实测 0 处）。所以这条约束在 `biz_stock_in` 上真正覆盖的是 `RETURN` / `OTHER`。
- **未来的坑（写给后续卡）**：如果以后要支持"供应商换货入库"（采购退货后补货，需要带供应商），
  **不要在 `in_type='RETURN'` 上放宽这条约束**，而是**新增枚举值**（如 `PURCHASE_RETURN`）并同步
  `ck_biz_si_type`。放宽 = 让"退货入库"这个语义同时表示两件事。

### 4.5 `source_order_id` 必填化评估（卡面交付 1 的后半）

**结论：不做 `NOT NULL`，改为"按入口分档强制 + 口径巡检"。**

三条理由，全部是代码实测出来的：

| # | 路径 | 证据 | 若加 NOT NULL |

## §5 Q4：库存 `biz_inventory` 是否显示供应商

### 5.1 结论

**不显示。** `biz_inventory`（物料 × 仓库的结存行，唯一键 `uk_biz_inv_mat_wh`）**不加**供应商列，
也不加"最近一次供应商"这类缓存列。供应商信息只能**按流水回溯**，且回溯必须落到**具体某一次入库**：

```
biz_inventory（物料 × 仓库结存）
   → biz_inventory_txn（该物料该仓库的流水；按 doc_type='STOCK_IN' + doc_id / doc_no 定位到入库单）
      → biz_stock_in（入库单；supplier_id = 当时供应商快照）
         → biz_purchase_order（source_order_id；SPOT/CONTRACT + supplier_id 快照）
            → biz_contract（contract_id；party_b_id = 当前乙方真相）
               → biz_supplier（主档：名称/账期/开票信息）
```

这条路径的每一跳在库里都是**现成的列**，不需要任何新结构（实测 `biz_inventory_txn.doc_type / doc_id /
doc_no` 三列齐全，索引 `idx_biz_inv_txn_doc(doc_type, doc_id)`、`idx_biz_inv_txn_no(doc_no)` 在位）。

### 5.2 为什么不能加一列（三条，都是模型层面的硬理由）

1. **基数不匹配**：`biz_inventory` 一行 = 一个（物料, 仓库）的结存，可能由**几十上百次不同供应商的入库**
   汇总而成。塞一列只能表达"某一次"，其余全错 —— 这不是"精度不够"，是**语义说谎**。
2. **它会变成第二真相**：一旦有列，列表/报表就会读它，而它只可能来自"最近一次入库"或"加权平均"，
   两种口径都不是财务要的"这批货是谁的"。本仓的同类教训：`biz_inventory` 只存 `qty / avg_cost / amount`，
   成本口径的真相在 `biz_inventory_txn` 的前后六列快照（V0137 头注释「成本可审计性的硬要求」）。
3. **会破坏成本口径的唯一性**：按供应商拆库存行（唯一键变成 `material_id, warehouse_id, supplier_id`）等于把
   移动加权平均从"物料×仓库"改成"物料×仓库×供应商"，`avg_cost` 的语义立刻分裂成 N 份，
   现有 `biz_inventory_location` 两级账、期初、年结、成本审计全部要重写。**这是另一个产品，不是本卡。**

### 5.3 那"库存里想看供应商"怎么满足（前端/接口口径）

| 需求 | 做法 | 数据来源 |
|---|---|---|
| 库存列表显示"最近入库来自哪家" | 列表行点开「流水」抽屉，按 `material_id + warehouse_id` 拉 `biz_inventory_txn`（已有索引 `idx_biz_inv_txn_mat`） | `biz_inventory_txn` → 入库单 |
| 某笔入库的供应商 / 采购单 / 合同 | 流水行上「追溯」按钮，逐跳展示：`IN-xxx → PO-xxx → HT-xxx → 供应商名` | §5.1 的链路，每跳一次单表查询（不必写 recursive CTE） |
| 按供应商看库存（"我欠谁多少货"） | **不是库存报表**，是采购/应付报表（在途 + 已入库未结算），走 `biz_stock_in` / `biz_payable` 按 `supplier_id` 聚合 | `biz_stock_in.supplier_id`（本卡定稿的快照列） |

### 5.4 明确不在本卡范围（写清楚，别让下游卡重复设计）

- **批次成本 / 按批次的供应商追溯**（食品、医药要的"这批货从哪家来的、成本多少"）→ 属**批次管理卡**：
  需要 `biz_inventory_batch`（`material_id + warehouse_id + lot_no + supplier_id + qty + unit_cost`）+
  入出库按批次扣减，是**独立的数据模型**，不是给 `biz_inventory` 加一列。
- **库位维度的供应商** → 同属批次/库位卡，`biz_inventory_location` 同样只记数量不记供应商（V0137 已定）。
- **库龄/周转分析里的供应商维度** → 报表卡，基于 `biz_inventory_txn.doc_id` 回溯，不需要新列。

## §6 「只绑上一环」的强约束怎么保证

### 6.1 机械保证（结构层，不是纪律层）

| 保证 | 手段 | 现状 |
|---|---|---|
| `biz_stock_in` **不能**直接引用合同 | 表里**没有** `contract_id` 列；本卡**明确不加** | 已满足（本册 DDL 不含该列） |
| `biz_stock_in` **不能**跨环"另立供应商真相" | `supplier_id` 只是快照，写入被 handler 强制等于采购单；DB 层有方向性 CHECK | 本卡新增（§4.3/§4.4） |
| `biz_purchase_order` **不能**没有合同却声称 CONTRACT | `ck_biz_po_contract_pair` | 本卡新增 |
| 合同 → 供应商只有一条真相 | `biz_contract.party_b_id`（合同卡定义）；采购单 `supplier_id` 是快照 | 依赖合同卡 V0193 |

一句话：**"只绑上一环"不是靠"大家别跨环查"，是靠"跨环的列根本不存在"**。`biz_stock_in` 要合同信息，
只能走 `source_order_id → purchase_order.contract_id`，路径唯一。

### 6.2 写入链路（三条，逐环取值，不许跳）

```
① 采购单建单 / 改单（purchase_handler::create_purchase_order / update_purchase_order）
   req.purchase_type='CONTRACT'
     → 校验 contract_id 存在、未软删、contract_type='PURCHASE'、status ∈ {SIGNED, ACTIVE}、
       order_date 落在 [start_date, end_date] 内（end_date 为空视为无限期）
     → 从合同带出 supplier_id  ← **唯一取值点**（用户传的 supplier_id 必须相等，否则 400）
     → 从合同带出 contract_no_snapshot / supplier_name_snapshot
   req.purchase_type='SPOT'
     → contract_id / contract_no_snapshot 必须为空（否则 DB CHECK 拒）
     → supplier_id 由用户选择（必填，列 NOT NULL）

② 入库单建单 / 改单（stockin_handler::create_stock_in / update_stock_in）
   有 source_order_id
     → require_purchase_order（现有：存在 / 状态可收 / 仓库一致）
     → **新增** guard_parent_supplier：supplier_id 从采购单带出；用户传的值必须相等，否则 400
     → contract_no 只在展示时从采购单一跳带出（不落库，见 §6.4）
   无 source_order_id（复制 / 手工）
     → supplier_id 用户必填（DTO 已强制）
     → purchase_type 与合同**不落库**（入库单没有这两列）

③ 入库单过账（stockin_handler::post_stock_in / 审批回调 stockin_bridge::on_post_settled）
   → 事务内再查一次采购单的 supplier_id 与单据头比对（兜的是"建单后被直接改库"）
   → 生成应付：payable_bridge 用单据头 supplier_id（快照，语义不变）
   → 生成凭证/流水：biz_inventory_txn 写 doc_type='STOCK_IN' / doc_id / doc_no
     → 追溯链最后一跳由此建立（§9）
```

    }
    Ok(Some(ContractRef { .. }))

fn guard_parent_supplier(order: &model::PurchaseOrderRow, got: Uuid) -> Result<(), ApiError> {
    if got != order.supplier_id {

### 6.4 明令**不落库**的两样东西（否则"只绑上一环"破功）

| 想在入库单上存的 | 结论 | 理由 |
|---|---|---|
| `contract_id` | **禁止加列** | 一旦存在，就会出现"入库单的合同"与"其采购单的合同"不一致的第二种状态 → 两处真相 |
| `party_b_id` / 合同乙方 | **禁止加列** | 同上，且与 `supplier_id` 快照重复 |

入库单详情页展示的"合同 HT-xxx"是**一跳带出**（`source_order_id → purchase_order.contract_no_snapshot`），
与现有 `source_order_no` 的做法完全一致（`stockin_dto.rs:558-575` 的 `source_order_no` 就是这么打的）。

## §7 校验位置与报错语义

### 7.1 分层职责（谁拦什么，不许互相推）

| 层 | 拦什么 | 失败表现 |
|---|---|---|
| **DB CHECK**（同表可判定） | 枚举脏值、`CONTRACT`/`SPOT` 与合同列的双向钉死、非采购入库带供应商、采购入库缺供应商、金额恒等 | `DbError::CheckViolation` → handler `write_error` 统一翻 400（本仓既有口径） |
| **handler 编排层**（跨表 / 需要读别的表） | 合同存在性/类型/状态/有效期；供应商 = 采购单供应商；供应商 = 合同乙方；仓库一致；来源单状态可收 | `ApiError::new(400, …)` |
| **状态机守卫**（已有） | POSTED 之后只允许改 remark；非法状态边 | `409 RESOURCE_CONFLICT`（`locked_change`） |
| **巡检**（异步，T+1） | 一切"绕过接口直接改库"造成的历史漂移 | 告警，不阻断业务 |

**为什么校验不放在"Service 层钩子/领域事件"**（本仓硬事实，写给不熟悉本仓的人）：

- 本仓 AGENTS.md 明令**不设 service 层**，业务编排在 `handler`、数据访问在 `model`。凭空加一层违反约定。
- 全仓**零触发器**（`grep TRIGGER backend/migrations/**/*.up.sql` = 0）、**无事件总线**
  （`grep event_bus\|EventBus\|publish(` = 0）。要做"输入即校验"只能落 handler，这是唯一符合本仓结构的位置。
- 领域事件的语义也不对：供应商与采购单不一致是**请求错误（400）**，不是"已经发生了的业务事实"。
  事件只能描述已发生的事，无法阻止写入。

### 7.2 具体落点（文件:函数:行，实现卡照着改就行）

> 不返回空 msg（前端直接把 msg 弹给用户，空串等于"点了没反应"）。

### 8.3 回滚（三档，默认档 A 无损）

见 `V0194__erp_po_contract_bridge.down.sql`：

| **C** | 再删 `contract_id` | 丢合同关联 | 方案整体否决 |

**不可逆点只有一个**：`purchase_type='SPOT'` 是**默认值落下来的**，档 B 删列后无法区分"历史零星"与"曾经是合同采购"。
所以档 B/C 之前必须 `pg_dump` 那几列（down 文件头部已写明）。
