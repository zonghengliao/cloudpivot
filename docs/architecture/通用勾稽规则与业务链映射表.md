### 0.3 术语（全文统一，评审时按此对齐）

| 术语 | 定义 | 反例（不是术语） |
|---|---|---|
| **环（Ring）** | 链条上一个业务单据层级。一环 = 一个单据主表 + 其明细表 | 不要把「明细行」当一环 |
| **主单（Head）** | 链条上承载「业务事实真相」或「交易对手真相」的那一环 | 采购链主单是合同，不是入库单 |
| **真相（Truth）** | 某一事实**唯一**被维护的地方。改真相要改这里 | 供应商真相 = 合同交易对手，不是入库单的供应商字段 |
| **快照（Snapshot）** | 业务发生时从真相**复制过来冻结**的值，用于审计与列表显示，**写入后不得手改** | 不是「缓存」（缓存可随时重算，快照不可） |
| **冗余（Redundancy）** | 同一事实在第二处被**独立维护**（两处都能改），必然漂移 | 与快照的本质区别：冗余可写，快照只读 |
| **回填指针（Back-pointer）** | 下游单据生成后，把自己的 ID 写回上游某一列（如入库单回填凭证 ID），**只用于查询，不参与业务判断** | 上游拿回填指针做状态推导 = 违规 |
| **跨环显示** | 列表里显示**非本环**的字段（如入库单列表显示合同号） | — |
| **交易对手（Counterparty）** | 供应商 / 客户的上位概念。一个合同只有一方交易对手 | 建议架构统一命名 `counterparty_*`，见附录 B BR-1 |

## 1 三条通用规则的形式化表述（可直接当评审 checklist）

> 编号约定：`R{规则号}-{条款号}`。评审时逐条打 ✅ / ❌ / N/A，**任何一条 ❌ 即该模块不通过**。

### 1.1 R1 — 单一数据源（Single Source of Truth）

#### R1.1 形式化定义

设某事实 `X` 的属性集合为 `Attrs(X)`。若在系统中存在两处结构 `S1`、`S2` 都能**写入** `Attrs(X)` 的同一属性 `a`，则 `S1`、`S2` 互为冗余，系统违反 R1。

形式化表述：

```
对任一事实 X 的任一属性 a：
  WriteSet(a) = { 结构 S | 存在操作路径使 S 成为 a 的写入点 }
  必须满足  |WriteSet(a)| ≤ 1
```

唯一允许的「第二个写入点」是**快照写入**（写一次、按真相冻结、之后只读），其性质必须由结构声明清楚（列注释 / 字段名 / 权限）并在 R3 里有巡检覆盖。

#### R1.2 一条事实归属哪一环（归属判定表）

| 事实 | 唯一维护处（真相） | 允许快照的地方 | 明确禁止出现 |
|---|---|---|---|
| 供应商是谁（采购的对方） | 采购合同交易对手 | 采购订单、入库单、应付单、凭证分录 aux、库存流水（如需） | 库存结存表、物料主数据 |
| 客户是谁（销售的对方） | 销售合同交易对手 | 销售订单、出库单、应收单、凭证分录 aux | 库存结存表、物料主数据 |
| 账期 / 信用额度 | 供应商/客户主数据（静态属性）+ 合同（约定值） | 采购订单（下单时冻结，见 F3）、应付单 | 入库单（不经订单直接抄） |
| 单价 / 税率 | 订单明细（成交价） | 入库单明细、凭证分录 aux_qty/金额 | 库存结存表（库存只有均价，见 F8） |
| 结存数量 / 结存金额 | 库存结存表（`amount` 以本列为准，F8） | 库存流水的 before/after 快照（F9） | 任何「库存汇总冗余表」 |
| 余额 / 期间归属 | 凭证分录 + 期间表 | 报表快照 | 业务单据上自算余额 |
| 单据状态 | 单据主表 + 状态日志（F16） | 列表页状态徽标缓存（可重算） | 用下游回填指针推导上游状态（见 R2.4） |
| 组织/人员归属 | 用户/部门主数据 | 单据上的姓名快照（F13 `applicant_name`） | 多处独立维护的「负责人」 |

### 1.2 R2 — 只绑上一环（Single Parent Pointer）

#### R2.1 形式化定义

设链条为 `R₁ → R₂ → … → Rₙ`（`R₁` 为主单）。对每一环 `Rᵢ (i>1)`：

```
必须存在唯一「主关联」指针 Pᵢ : Rᵢ → Rᵢ₋₁（且 Rᵢ₋₁ 是直接上游，不是 Rᵢ₋₂ 或更远）
禁止存在任何「跨环指针」 Q : Rᵢ → Rⱼ，其中 j ≤ i-2
下游可以回填 Back-pointer 到上游，但上游不得用 Back-pointer 做业务判断
```

三条推论（评审最常踩）：

1. **必要性**：`Pᵢ` 在业务上「必须有上游」的场景里必须 NOT NULL（如：采购入库必须有采购单）。可为空只允许两种情形：该环是主单；或该单据被明确标记为**无源单据**（E4），且无源时其对手快照必须由人工确认并留痕。
2. **不可跳跃**：入库单不得有 `contract_id`；出库单不得有 `customer_id`；退货单不得有 `supplier_id`（退货的对方从原单读）。
3. **多上游的合法形态**：只有「同一环的两类来源」时，用**类型 + 双指针**表达（如入库单 `in_type` + `source_order_id`（采购）/`source_issue_id`（生产）），**不是**放宽成「想绑谁绑谁」。

#### R2.2 环间指针归属表（目标态，逐链）

| 环（下游） | 主关联指针 | 直接上游 | 明令禁止的跨环指针 |
|---|---|---|---|
| 采购订单 | `contract_id` | 采购合同 | `supplier_id` 作为**真相**（可作快照，见 ARCH-2 Q1 方案B） |
| 入库单（采购型） | `source_order_id` | 采购订单 | `contract_id`、`supplier_id` 作为必填真相 |
| 入库单（生产型） | `source_production_id` | 生产订单 | 采购/销售任何指针 |
| 入库单（委外收货） | `source_outsourcing_id` | 委外订单 | 加工方作为必填真相（快照可以） |
| 出库单（销售型） | `source_order_id` | 销售订单 | `customer_id`、`contract_id` |
| 出库单（领料/发料） | `source_production_id` / `source_outsourcing_id` | 生产/委外订单 | 交易对手任何列 |
| 应付单 | `source_id`（= 入库单） | 入库单 | `contract_id`（对方从入库单读） |
| 应收单 | `source_id`（= 出库单） | 出库单 | `customer_id` 作为真相 |
| 凭证 | `source_type + source_id` | 业务单据 | 直接绑合同 |
| 库存流水 | `doc_type + doc_id` | 生成流水的单据 | 绑定多于一张单据 |
| 退货单 | `orig_doc_type + orig_doc_id` | 原销售/采购订单 | `supplier_id`、`customer_id` 任何列 |
| 调拨单 | （无上游，是主单） | — | 任何供应链/客户列 |
| 调拨收货 | `transfer_id` | 调拨单 | 仓库作为「对方」快照以外的任何东西 |

#### R2.3 评审 checklist（R2）

| 编号 | 检查项 | 判定方式 | 通过标准 |
|---|---|---|---|
| **R2-a** | 该单据有且只有一个「主关联」列指向直接上游 | 看表结构 + 前端「来源单据」字段 | 单指针、指向上一层 |
| **R2-b** | 业务上必须有上游的，`Pᵢ` 为 NOT NULL（或由 CHECK 强制） | 查约束 / 写入校验 | 数据库层或写入层强约束 |
| **R2-c** | 不存在跨环指针（跳环引用） | 用 §2.2 的「外键溯源法」走一层 | j = i-1 |
| **R2-d** | 允许为空的主关联，**只能**来自白名单（主单 / 无源单据 E4） | 看空值产生路径 | 空值路径可枚举 |
| **R2-e** | 上游不读取下游回填指针做业务判断 | 查上游 handler 是否读 `voucher_id/payable_id` 之类 | 只做展示/追溯 |
| **R2-f** | 跨环信息不落列，只落「显示 / 追溯」 | 看详情页是否用 JOIN 或多段查询推导 | 列表快照、详情关联 |

#### R2.4 关于「回填指针」的边界（最容易争议的一条）

```
允许：入库单过账后回填 voucher_id / payable_id（下游生成物，上游只用于「我的凭证在哪」）
允许：单据回填 approval_instance_id（审批实例）
禁止：采购订单的 status 由「有没有凭证」推导
禁止：库存数量由「已入库单数量 - 已出库单数量」在查询里现算（库存以结存表为准，见 R1.2）
```

### 1.3 R3 — 显示靠关联 + 快照可追溯（Display by Relation, Truth by Trace）

#### R3.1 形式化定义

对任一跨环显示字段 `f`：

```
1. 列表（高并发、只读、要性能）：f 必须来自本环已存的快照列
2. 详情（低频、要点准）：允许 JOIN 真相反查，且必须提供「追溯真相」入口（点得下去）
3. 快照与真相的偏差：必须有巡检 → 偏差必须被记录 → 偏差不得静默
4. 稽核结论：快照是「业务发生时的声明」，真相是「现在的状态」；两者不同不是错误，是审计事实
```

#### R3.2 三态判定表（评审时用来区分「这是对的/这是错的」）

| 形态 | 特征 | 判定 | 处置 |
|---|---|---|---|
| **真相（Truth）** | 唯一写入点、其他环只读 | ✅ 必须存在 | 不许有第二个写入点 |
| **快照（Snapshot）** | 写一次冻结、只读、有巡检、有注释 | ✅ 允许 | 补巡检；禁止手改 |
| **冗余（Redundancy）** | 可写、可改、可独立维护、无巡检 | ❌ 违规 | 要么降级为快照（去写入口 + 上巡检），要么删列改关联 |
| **派生缓存（Cache）** | 可随时按真相重算、可过期 | ⚠️ 有条件允许 | 必须写明重算时机；不得当作对账依据 |

**判据一句话**：*能不能改？能改就是冗余（除非是主单）；改完会不会被巡检抓？不会被抓就是默许漂移。*

#### R3.3 评审 checklist（R3）

| 编号 | 检查项 | 判定方式 | 通过标准 |
|---|---|---|---|
| **R3-a** | 列表页每个跨环字段都有对应快照列，不靠运行时 JOIN 三层 | 看列表查询与 DTO | 列表查询不跨两环以上 |
| **R3-b** | 每个快照列都有**巡检项**（判定式唯一、可复算） | 对照 §3 各链「巡检项」列 | 巡检项明确到字段级 |
| **R3-c** | 巡检有**定时执行**、有告警出口、有权限码 | 看任务清单与权限表 | 进任务调度 + 通知 |
| **R3-d** | 详情页能「追到真相」（链路可点、不靠人脑记） | 走一遍详情页 | 点得下去 |
| **R3-e** | 巡检**只报不修**，修正必须人工确认（范本：F20 `dry_run=true`） | 看接口语义 | 默认不写库 |
| **R3-f** | 派生值有唯一算法，不出现「两套算法各自算」 | 查同一指标的多处实现 | 单算法 |

#### R3.4 快照的四个必备属性（缺一即不达标）

| 属性 | 含义 | 反例 |
|---|---|---|
| **可注释** | 列注释写明「快照 + 来源 + 写入时机」 | 只写「供应商ID」 |
| **只读** | 无写入路径可改（前端不可编、后端无分支改写） | 「允许修正」按钮 |
| **可巡检** | 有字段级判定式 | 巡检只查行数不查字段 |
| **不参与真相判断** | 不用快照做业务校验（除「与真相比对」这一种用途） | 用快照判定合同是否有效 |

### 1.4 三条规则的冲突判定树（评审遇歧义时按此裁决）

```
这个字段能不能存？
├─ 是本环自己的业务属性（下单日期、数量、单价、状态）
│   └─ ✅ 存（它本来就是本环的真相）
├─ 是上游的事实（供应商、客户、合同号、订单号）
│   ├─ 上游就在**上一环** → ✅ 存指针（R2 主关联）
│   └─ 上游在**更远环** →
│       ├─ 列表要显示 / 审计要留痕 → ✅ 存快照（R3）+ 必须有巡检
│       └─ 只是偶尔查一下 → ❌ 不存，走关联追溯
└─ 是下游才对的事实（凭证号、付款状态）
    └─ ✅ 只允许回填指针（R2.4），且本环不得用它做业务判断
```

**优先级**：R1（唯一真相）> R2（单指针）> R3（显示与追溯）。即：当「显示方便」与「不允许跨环冗余」冲突时，**宁可多一层追溯也不加冗余列**；只有当该字段是「业务发生时必须冻结的证据」（金额、对手、账期、成本）才允许做快照，且必须上巡检。

## 2 违规识别方法（怎样一眼看出某个模块违反了它）

### 2.1 识别 R1 违规：字段来源三问法

对模块里每一个「指向他表 / 名称类文本」的列，问三个问题，有一个答不上来就是违规嫌疑：

```
问1：这个值是谁写的？（WriteSet 有几处）
问2：如果真相变了，这个值要不要跟着变？——要跟着变 = 它不可能是快照 → 判为冗余
问3：如果这个值被手改，系统能不能发现？——不能发现 = 默许漂移
```

| 反例 | 违规类型 | 判定问句 | 现状有无 |
|---|---|---|---|
| 库存结存表加一列 `supplier_id`（「方便查批次供应商」） | R1 冗余 | 「库存是物料×仓库维度，供应商在哪一列被维护？谁改？」→ 两处都能改 → 违规 | 无（F8 合规） |
| 采购单上有 `supplier_id`，合同上也有交易对手，但**两处都能手改** | R1 冗余 | 「合同改乙方，采购单的供应商会跟着变吗？」→ 不会，且都能填 → 违规（ARCH-2 Q1 方案A/B 就是在解这个） | **有嫌疑**（F2：合同表还没建，采购单 `supplier_id` 是唯一写入点，暂不算违规；建合同后必须立即降级为快照） |
| 凭证分录 `aux_extra` JSONB 里塞 `{"supplier_name": "XX公司"}` | R1 冗余（文本真相） | 「供应商改名后，这个字符串怎么更新？」→ 不更新 → 违规 | 结构上可能（F12 `aux_extra` 自由 JSONB） |
| 入库单备注自动拼接「供应商：XX，采购单：PO-001」并用于对账 | R1 冗余（文本真相） | 「对账脚本读的是备注还是字段？」→ 读备注 → 违规 | 未发现代码如此做，属**预防性反模式** |
| 同一指标两套算法（结存金额：`qty×avg_cost` vs `amount` 列） | R1 冗余 | 「哪个是准的？」→ 若答不出唯一 → 违规 | 无（F8 明确 `amount` 以本列为准）✅ |

### 2.2 识别 R2 违规：外键溯源法（走一层）

**操作步骤（对任一单据模块，2 分钟）**：

```
Step 1 列出该单据所有「指向他表」的列（ID 列 + 单号文本列）
Step 2 对每一列问：它指向的这张表，是「我的直接上一环」吗？
        ├─ 是 → ✅ 主关联
        ├─ 是更远的环（跳过一层） → ❌ 跨环引用
        └─ 不是链条上的表（主数据：物料/单位/仓库/科目） → ✅ 主数据引用，不受限
Step 3 检查主关联是否可为空：空值路径能否枚举？（只有「无源单据」能空）
Step 4 检查有没有「两个上游指针」同时存在且都能填（该用类型 + 双指针表达）
```

| 反例 | 为什么是跨环 | 判定问句 | 现状有无 |
|---|---|---|---|
| 出库单直接带 `customer_id`（跳过销售订单） | 客户在「销售合同」，出库单应绑销售订单 | 「这张出库单是哪张销售订单的？」→ 答不出 → 违规 | 未建（属**设计红线**，建销售链时必须避免） |
| 入库单带 `supplier_id` 且可空 `source_order_id`，`PURCHASE` 型只强约束供应商 | 供应商在合同，入库单应绑采购订单 | 「这张采购入库单收的是哪张采购单？」→ 可以是空的 → 违规 | **有（F4/F5）** |
| 退货单自带 `supplier_id` | 退货的对方由原单决定 | 「这张退货单的原采购单是哪张？」→ 若无此列 → 违规 | 未建（未来红线） |
| 入库单加 `contract_id`（「便于查合同」） | 合同在订单之上两环 | 「合同号从采购单就能查到，为什么单独存？」→ 无正当理由 → 违规 | 无（预防） |
| 生产领料单带 `customer_id`（「备查最终客户」） | 客户与领料无直接业务关系 | 「领料业务里的客户是谁的业务？」→ 无 → 违规 | 未建（未来红线） |

**现成的违规样本（可直接拿去当评审示例）**：
- 复制入库单 → `PURCHASE` 型 + 有供应商 + 无采购单（F7）。**这是被设计允许的例外（E4）**，但如果它不被打上「无源」标记、不进巡检，就是长期违规数据的温床 → 处置见 §3.3.1 巡检项 I-P4。

### 2.3 识别 R3 违规：列表口径法

```
Step 1 打开列表页，数一数「有几个字段不属于本单据」
Step 2 对每个跨环字段问：这个值是「查出来的」还是「存在本行的」？
        ├─ 查出来的（每次 JOIN）→ 违反 R3-a（性能与口径双风险）
        └─ 存在本行的 → 再问：它能不能被手改 / 有没有巡检？
                ├─ 能改 → 冗余（R1 违规）
                └─ 不能改但无巡检 → 默许漂移（R3-b 违规）
Step 3 打开详情页：能不能点进上游单据？
        └─ 点不进去 → 违反 R3-d（追溯断裂）
```

| 反例 | 判定问句 | 现状有无 |
|---|---|---|
| 入库单列表每行 JOIN 采购单、合同、供应商三张表出「合同号+供应商名」 | 「合同改名/换乙方，这行列表显示会变吗？」→ 会变 → 说明它是实时真相，不是快照；一旦展示给审计就是「当时的账」被今天的值覆盖 | 部分（采购单详情用 `supplier_ref` 实时查名，F 见 `purchase_handler.rs:362`；因该场景是表单回填，可接受） |
| 库存列表显示「供应商」 | 「库存维度是物料×仓库，供应商从哪来？」→ 只能从最近一笔流水猜 → 违规且会给出**错误的唯一答案** | 无（F8 合规）✅ |
| 有快照列但全系统无人巡检 | 「这个快照漂移了，谁知道？」→ 没人 → 违约 | **全系统空白（F19/F21）** ❌ |
| 巡检只报不修被改成「自动修正」 | 「巡检把历史单改了，谁负责？」→ 无人审 → 违规（R3-e） | 无（F20 `dry_run` 默认 true）✅ |

### 2.4 通用 5 分钟扫描法（对任意模块一键体检）

| # | 动作 | 命中即问题 |
|---|---|---|
| 1 | 数这个模块主表的「ID 列 + 单号文本列」 | 出现 `*_no` 文本列 → 快照或冗余，需归类 |
| 2 | 对每个 ID 列标注「本环 / 上一环 / 更远环 / 主数据」 | 出现「更远环」→ R2 违规 |
| 3 | 数「名称类文本列」（`*_name`） | 出现供应商/客户名 → R1-f 违规 |
| 4 | 找主关联列的空值产生路径 | 空值路径不可枚举 → R2-d 违规 |
| 5 | 搜该模块有无「快照」「巡检」「dump/audit」关键词 | 有快照无巡检 → R3-b 违规 |
| 6 | 打开列表页看跨环字段来源 | 实时 JOIN 两层以上 → R3-a 违规 |

### 3.3 逐链细说（评审时按链查，每条含「现状证据 / 目标 / 已合规的正例 / 施工顺序」）

#### 3.3.1 采购链（部分 → 目标：合规）

**现状证据**
- 采购单直绑供应商、无合同（F2）：`biz_purchase_order.supplier_id NOT NULL`，无 `contract_id`。
- 入库单主关联方向错（F4/F5）：`PURCHASE` 型只保证「有供应商」，不保证「有采购单」；数据库层无 `source_order_id` 非空约束。
- 复制单制造「无源 + 有供应商」单据（F7）：设计上合理（避免重复占用待收额度），但缺「无源标记」，巡检无法与真违规区分。
- 明细层已做对（F6）：`source_item_id` + 单位/成本快照，主表未跟上。
- 库存层已做对（F8）：无供应商列，靠流水追溯（F9）。

**目标**
1. 合同层补入，交易对手（供应商）真相上移；采购单 `supplier_id` 降级为快照（ARCH-2 Q1 方案 B），加 `purchase_type`（`CONTRACT`/`SPOT`）区分有无合同。
2. 入库单：`PURCHASE` 型 `source_order_id` 必填；`supplier_id` 只从采购单带出、不可手改；复制单打无源标记（`is_sourceless` 或等价语义）。
3. 巡检 I-P1 ~ I-P6 进每日任务，输出进通知中心。

**正例可抄**：`po.credit_days`（F3，账期快照）、`stock_in_item.source_item_id`（F6，明细单指针）、`inventory_txn.doc_*`（F9，追溯通道）。

**施工顺序**：建合同表 → 采购单加 `contract_id/purchase_type` + 供应商语义改快照 → 入库单加主关联约束 + 供应商只读带出 → 巡检上线 → 存量迁移（历史采购单标 `SPOT`，不编造合同）。

#### 3.3.2 销售链（未 → 目标：一次做对）

**现状证据**：无客户表、无销售订单、无出库单、无应收单（F17）；「应收账款」仅报表科目（F18）。→ 本链是**纯新建**，最大价值是「别把采购链的错误再犯一遍」。

**目标（红线）**
1. 交易对手（客户）真相只放销售合同；订单/出库/应收都是快照。
2. 出库单只绑销售订单（`source_order_id`），**绝不允许** `customer_id` 作为主关联。
3. 应收单只绑出库单（沿用应付单的 `source_type/source_id` 形态，F10）。
4. 库存表永不出现客户列。

**风险提示（口径冲突）**：本任务书写「销售合同（甲方 = 客户）」，而 ARCH-2 合同草案用 `party_b_id` 承载交易对手。二者混用会让「同一列在不同合同类型下语义翻转」→ 见附录 B BR-1，必须先定口径再建表。

#### 3.3.3 生产链（未）

**现状证据**：生产订单/领料单不存在（F17）；入库单 `in_type` 只有 `PURCHASE/RETURN/OTHER`（F4），无生产枚举。

**目标**：生产订单为主单（无交易对手）；领料单、完工入库单都只绑生产订单；结构上**不建**供应商/客户列；完工入库若复用 `biz_stock_in`，用「类型 + 生产来源指针」表达，不新增跨环列。

**顺序建议**：等 BOM 与成本归集方案确定后再开工（否则完工入库成本无来源，会把采购价错当生产成本 → 违反 R1 的「成本真相唯一」）。

#### 3.3.4 委外链（未）

**目标**：委外订单绑委外加工合同（复用 `biz_contract`，`contract_type=OUTSOURCING`）；加工方 = 交易对手（供应商维度，**是这条链唯一有交易对手的非采销链**）；发料单（出库向）、收货单（入库向）都只绑委外订单，加工方一律快照。

**依赖顺序**：出库单据能力（与销售链共用）→ 委外订单 → 发料/收货单 → 巡检 I-O4（在加工方处数量）。

**目标**

2. 巡检 I-F1（`aux_supplier_id` 与来源单据的供应商快照一致）+ I-F3/I-F4（孤儿凭证双向）。
3. `aux_customer_id` 随批次2 客户表补列（先登记为「已知缺口」，不要用文本字段顶替）。

#### 3.3.6 调拨链（已 → 保持，可选增强）

**现状证据**：主表与明细无任何交易对手列（F13）；申请人姓名与成本是正确快照（F13/F14）；收货是状态跃迁 + 流水，不是独立单据。

**目标**：保持现状。若老板要求「调拨收货单」作为纸面单据（打印/签字），新增单据只绑 `transfer_id`，**不引入任何供应商/客户列**；否则不做（多一张单据 = 多一处漂移源）。

#### 3.3.7 退货链（未）

**现状证据**：仅入库单有 `in_type='RETURN'` 枚举预留（F4），无退货单、无原单绑定、无出库侧退货能力。

**目标**
1. 退货单只绑原单（`orig_doc_type + orig_doc_id`），**不建** `supplier_id/customer_id` 列（对方由原单决定，显示靠关联）。
2. 退货入库单的供应商快照取「原采购单的供应商」，不取退货单（退货单没有这个字段）。
3. 数量闭环：累计退货 ≤ 原单已入/已出 − 已退。

**顺序**：采购退货先做（只依赖采购链）→ 销售退货等批次2。

> 列「现状有无」是为了让评审知道这是「已在犯」还是「预防针」。

| **AP-3** | 在凭证分录冗余「供应商名称」文本（或用 `aux_extra` 塞名称） | 文本是第二真相，改名即过期（R1-f）；按文本汇总必然错 | `aux_supplier_id` + 关联主数据取名；`aux_extra` 键名白名单 | 结构上可能（F12 `aux_extra`），上线前必须白名单化 |

## 6 评审使用说明（非作者如何直接拿去评审）

### 6.1 三步评审法（单个模块 ≤ 10 分钟）

```
Step 1 结构扫描（2 分钟）
   用 §2.4 的 6 项扫描法过一遍表结构 → 列出所有可疑列（ID 列、单号文本、名称文本）

Step 2 规则打勾（5 分钟）
   R1-a~f、R2-a~f、R3-a~f 共 18 项，逐项 ✅/❌/N/A
   任何一项 ❌ → 记一条问题，带上「字段名 + 违反的条款号 + 判定问句的答案」

Step 3 链条对号（1 分钟）
   在 §3.1 表 A 里找该模块所属的环，对照「环与环之间的外键」列：
   它的主关联是否与表 A 一致？不一致 → 要么设计错，要么表 A 需要修订（二者必须同步）
```

### 6.2 评审输出模板

```
模块：<模块名>
所属链 / 环：<链名> / 环 <i>
R1：✅/❌（问题：<字段> — 依据 R1-<x>）
R2：✅/❌（问题：<字段> — 依据 R2-<x>）
R3：✅/❌（问题：<字段> — 依据 R3-<x>）
巡检覆盖：<有/无>（缺哪几条 I-xx）
结论：通过 / 有条件通过（须修 N 条）/ 不通过
```

### 6.3 常见争议的现成裁决（直接引用，不用二次讨论）

| 争议 | 裁决 | 依据 |
|---|---|---|
| 「供应商名就存一列文本，省一次 JOIN」 | ❌ 禁止。要性能就存 ID 快照 + 主数据缓存，不存名称文本 | R1-f、AP-3 |
| 「入库单也存合同号，方便查」 | ❌ 禁止。合同号是两环之上，走关联 | R2.1 推论 2、AP-6 |
| 「快照漂移了，巡检顺手改回来」 | ❌ 禁止自动修。只报，人工确认 | R3-e、AP-8 |
| 「这张入库单是复制出来的，没采购单，怎么办」 | ✅ 允许，但必须打无源标记 + 进巡检（E4） | E4、AP-5、I-P4 |
| 「历史采购单没有合同，补一个合同吧」 | ❌ 禁止编造历史。标 `SPOT`（零星采购）即可 | ARCH-2 父卡硬红线 5 |
| 「客户表还没建，先用文本字段顶着」 | ❌ 禁止。留空列位/等批次2，不建文本字段 | R1、§3.2 财务链 |
