## 决定 D-2 ｜② WARN 47（审批实例指向已清场对象）：审批实例不随业务删除，历史 47 条零 DML；按实例状态分级

### 取证结论（与卡面假设不同，卡面的「点进去 404」不成立）
1. **47 条全部终态，零 PENDING**（只读实测，按 biz_type × 实例状态）：

   | biz_type | 实例状态 | 条数 |
   |---|---|---|
   | TASK_ACCEPT | APPROVED | 27 |
   | TASK_ACCEPT | CANCELLED | 11 |
   | CONTRACT_APPROVE | CANCELLED | 5 |
   | FLOW_EDGE_CFG | WITHDRAWN | 3 |
   | FLOW_EDGE_CFG | REJECTED | 1 |

   ⇒ **没有任何一条「活待办」挂在死对象上**，用户不会被卡在一条点不开的待办里。
2. **现行代码口径本来就是这样，47 条是该口径的历史产物，不是缺陷**：
   - T12（`backend/src/business/flow/task_bridge.rs:650` `TASK_DELETE_CANCEL_COMMENT="任务已删除，审批单自动终止"`）：
     任务软删时**只终止 PENDING**，终态实例保留作审计；
   - R-P1-1（`backend/src/business/erp/contract_handler.rs:1144` 起 `contract_bridge::cancel_approval_of`，注释明写「在跑的审批必须先终止」）：
     合同删除同理。
3. **审批详情页不请求业务单**：`frontend/src/views/business/flow/instance/detail.vue` 明细与字段全读 `form_data` 冻结快照
   （注释：`明细只读 form_data.items（后端 dbc99c3 起的审批快照），不再请求业务单接口`）⇒ 业务对象删了页面照样渲染。
4. 真实的体验缺口只有一个：详情页顶部「关联业务」按钮 `router.push('/task?keyword=' + biz_no)`——
   软删任务搜不到 → **空列表（不是 404）**；且 `CONTRACT_APPROVE` / `FLOW_EDGE_CFG` 也被跳去任务列表，**路由本身是错的**。
5. 4 条 `FLOW_EDGE_CFG` 的成因确认：实例是 2026-11-03 的 WITHDRAWN/REJECTED，`entity_id` 是申请时的草稿 id，
   从未落成 `biz_flow_edge` 行（`state_machine.rs::note_edge_config` 注释写明）⇒ 同规则下应为 INFO；
   真正的缺陷是「APPROVED 却查不到配置行」，生产目前 **0 条**。

### 处置
- **数据**：零 DML。不补删审批实例，不动终态实例（它们是不可变的审批证据）。
- **巡检口径（改）**：DI-19 从「恒 WARN」改为按实例状态分级 ——
  `PENDING` ⇒ **WARN**（活待办指向死对象，这才是 P1）；`APPROVED/CANCELLED/WITHDRAWN/REJECTED` ⇒ **INFO**（历史清场，保留可见性）；
  「有 biz_type 无 biz_id」保持 WARN。
- **体验（改）**：详情页「关联业务」按 `biz_type` 路由到正确页面；探测到对象已软删/不存在 ⇒ 按钮置灰 + tooltip
  「业务对象已清场，仅可查看审批快照」，不再跳空列表。
- **规范（写）**：清场/演示数据清理时**不连带软删审批实例**（终态是审计证据），但清理脚本收尾必须跑一次
  `di.v_poly_ref_dangling`，把新增命中写进清理报告。

## 决定 D-4 ｜cron 接线：**先降噪、再挂**

### 现状核实（两处必须分清，别踩错机器）
- **生产 144**（`cloudpivot@144`）：`crontab -l` **没有** snapshot_audit；`/etc/cloudpivot/` 下只有
  `cloudpivot.env` / `cloudpivot-dev.env` / `cloudpivot-test.env`，**没有** `snapshot-audit.env` ⇒ 卡面「巡检没挂 cron」属实。
- **开发机 .99**（本卡取证所在）：crontab **已挂** `0 2 * * * scripts/cron/snapshot_audit.sh`，
  跑的是 `cp_lockorder_t`、16 条视图（P2-6 之前的口径）——**不等于生产巡检上线**，不要拿它当证据。

### 顺序（硬约束）
1. 卡 A 的巡检改动先落，生产只读复跑到 **BLOCKER 0 / WARN 0**（DI-18 豁免 1 条 + DI-19 47 条都以 INFO 呈现）；
2. 再挂 `0 2 * * * /opt/cloudpivot/scripts/cron/snapshot_audit.sh`；
3. 先写 `/etc/cloudpivot/snapshot-audit.env`（chmod 600，含 `NIK_DATABASE_*` + `SNAPSHOT_AUDIT_NOTIFY_CMD`），
   否则脚本会回落到当前环境变量（历史上踩过：连成默认库报 "no password supplied"）；
4. 挂后必须留：首跑日志（`/var/log/cloudpivot/snapshot-audit.log`）+ `echo $?` + JSON 结果文件；
   **若首跑仍有 BLOCKER，立即撤 cron 并回到卡 A**（不允许「先挂上再说」）。
