## 4. 契约（四条，别破）

1. **幂等**：同一 `code` 调两次落同一行（`ON CONFLICT DO NOTHING`；被吃掉时才回读）；
2. **确定性 id**：`fixture_uuid(key)`（SHA-256 前 16 字节 + version 8），不是 `Uuid::now_v7()`
   ⇒ 同一夹具跨进程/跨机器同一个 id，断言可复现；
3. **只碰自己的行**：清场按自己的 `code` 精确匹配 / 自己的 id，绝不按前缀扫全表；
4. **缺才补**：库里已有可用行（单位 / 部门 / 审批岗位成员）**先用现成的**，一行都不加
   ⇒ 种子库零新增，列表类断言基线不漂移。

另外两条工程约束：

* **一次往返**：`upsert_id` 用 `execute` 的**受影响行数**判断是否插入成功——成功即我派生的 id，
  **不再 `SELECT` 回读**（每份夹具省一次 99→145 往返）；
* **进程级缓存**：`ensure_unit()` 用 `OnceLock` 缓存（单位是只读维度）。
  缓存不能乱加：`aux_tests` 会按固定 id 删单位，其它维度没有这种「自己删自己」的语义，故只缓存单位。

## 5. API

| 函数 | 造什么 | 语义 |
|---|---|---|
| `uniq_suffix()` / `uniq_u64()` | 唯一后缀 | 纳秒取模 1e9 + 进程内序号；跨进程不撞 |
| `tail_code(s, take)` / `last_chars(s, n)` | 编码尾巴 | 编码列有长度上限时截尾（只留数字 / 保留 n 字符） |
| `year_seq(base, span)` / `period_code(y, m)` | 年度 / 期间码 | 每个夹具独占一个年度（远离真实数据） |
| `ensure_unit()` | 计量单位 | 现有启用单位直接用（`ORDER BY created_at, unit_code` 保证跨进程挑同一行） |
| `ensure_material(code, name)` / `ensure_material_kind(code, name, kind)` | 物料 | 默认 `FINISHED`；id 由 `material:<code>` 派生 |
| `ensure_warehouse(code, name)` | 叶子仓 | `is_leaf=1`、`level=1`、`path=/<code>` |
| `ensure_account(code, name, category)` | 末级科目 | `level=2`、`is_leaf=1`、`DEBIT`；类别由调用方给 |
| `ensure_supplier` / `ensure_customer` / `ensure_location` / `ensure_accounting_period` | 维度 | 编码唯一、幂等 |
| `sweep_once(key, &[sql])` | 清场 | 同一 key **每进程只扫一次**（清上一轮崩溃残留） |
| `ensure_dept` / `ensure_user` / `ensure_two_users` / `ensure_role_member` / `ensure_approver_roles` / `fixture_uuid` … | 底座 `sys_*` | **re-export** 自 `cloudpivot_kernel::shared::test_helpers`（实现留在内核 crate） |

新用例怎么写（改前 10 行 → 改后 2 行）：

```rust
// 改前：自己 uniq + 现查单位 + 手写 10 行 INSERT
let suffix = uniq();
let unit: Uuid = db().scalar_with_params("SELECT id FROM biz_unit … LIMIT 1", vec![]).await?;
let product = Uuid::now_v7();
db().exec_sql("INSERT INTO biz_material (id, material_code, …, unit_id, material_type, status, \
               created_at, updated_at) VALUES (?::uuid, ?, ?, ?::uuid, 'FINISHED', 1, now(), now())"…)

// 改后
let suffix = test_seed::uniq_suffix();
let product = test_seed::ensure_material(&format!("CB210-{suffix}"), "分摊夹具产出品").await;
```

**边界**：单据 / 明细（`biz_stock_out` / `biz_cost_collect` / `biz_voucher` …）**不进**本模块 ——
它们的列清单随用例语义变化（状态、金额、来源单据），用例外显式写 SQL 才看得见断言前提。
统一的是**主数据**：同一种东西在所有用例里长得一样，才值得收进 `ensure_*`。

## 8. 踩到的坑（都留了注释在代码里）

1. **单位口径不一致 ⇒ 一条新红**：`ensure_material_kind` 内部取单位（`ORDER BY created_at, unit_code`），
   但 `cost_settle_finish_db_tests` 的 `fx.unit` 还是老的无序 `LIMIT 1`；`biz_unit` 有 3 行
   `created_at` 完全相同 ⇒ 两边挑到不同行 ⇒ `入库明细的 unit_id ≠ 夹具单位` 断言红（实测复现）。
   修法：**同一维度只能有一个入口** —— 那 3 个文件里 `let unit = …` 也换成 `ensure_unit()`，然后全绿。
2. **`ON CONFLICT DO NOTHING` 的 id 不能想当然**：冲突被吃掉时插的是别人的行，必须回读；
   因此 `upsert_id` 用受影响行数分流（成功走快路径，冲突才 `SELECT`）。
3. **`sweep_once` 不是纯优化，要看语义**：它清的是「上一轮进程崩溃留下的行」；本进程内的夹具
   编码带唯一后缀、年度由 `year_seq` 递增，天然不撞 —— 所以每进程一次是安全的，
   但**前提是清场语句只含自己的前缀**（`LIKE 'CB34-%'`），写全表删除就会误伤别人的夹具。
4. **P2-61 分域门禁会抓新模块**：新增 `test_seed::tests::*` 必须登记到 `platform` 域，
   否则 `test_domains_gate.sh` 判「用例未登记」。
