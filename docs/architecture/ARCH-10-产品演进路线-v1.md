## 0. 定位（用户拍板）

**云枢 = 可验证、可定制的业务中台**

不是「又一个通用 ERP」（比不过用友金蝶 30 年积累），而是：

| 护城河 | 载体 | 现状 |
|---|---|---|
| **改得快** | 表单设计器 + 流程引擎 + 任务模块的三角组合 | ✅ 已有（原生架构，不是附件品） |
| **算得准** | 3034 条断言 + 152 组勾稽 + 13 域全覆盖演练 | ✅ 已有（但**客户看不见**） |
| **改得起** | NIK 框架自研，不受厂商锁死 | ✅ 已有 |

**核心洞察**：云枢真正值钱的不是「ERP 功能」，是**「可验证性」本身**。

```
行业现状：
· 客户上 ERP 最大的恐惧是「算错了我不知道」
· 实施商最大痛点是「客户不相信这是对的」
· 审计最难的是「怎么证明这个数是这么算出来的」

云枢已经有做「可验证」的全部素材（断言/勾稽/审计日志），
缺的只是「把它变成客户能看见的产品能力」。
```

## 0.2 两大 AI 护城河（用户 2026-11-09 补充）

### 护城河四：AI 快速二次开发

**这不是设想，本次对话就是活证据**：

```
2026-11-09 这一天发生的：
· 13 个业务域演练（3034 条断言 + 152 组勾稽）—— 全 AI 跑完
· 100 条问题清单 + 3.45/5 评审报告 —— 全 AI 产出
· 44 张修复卡（拆卡 + 实现 + 测试 + 提交）—— 全 AI 执行
· 从「发现问题」到「修好提交」从**周级变成小时级**

传统 ERP 二次开发：
  客户提需求 → 实施顾问写方案（1 周）→ 开发排期（2 周）→ 测试（1 周）→ 上线（1 周）
  = 5 周起，还经常返工

云枢 AI 二次开发：
  客户提需求（自然语言）→ AI 拆卡 → AI 写代码 → AI 测试 → AI 提交
  = **小时级**，且每张卡都有机械可验证的验收
```

**产品化方向**：
```
· 客户说「我要在采购订单加一个『预算占用』字段」
  → AI 读懂 → 生成迁移 + DTO + 前端 + 测试
  → 客户确认 → 自动部署到他的环境
  
· 客户说「我们的审批要加一个『法务会签』节点」
  → AI 读懂 → 改流程定义 + 加节点兜底人 + 测试
  → 客户确认 → 上线
```

**技术要求（关键，不能省）**：
```
① 每张 AI 生成的改动必须有机械可验证的验收（不能"看着对"）
② 必须过 15 道门禁（fmt/clippy/test/invariants）
③ 必须能回滚（一键退回上一版）
④ 客户能看懂改了什么（人话报告，不是 diff）
⑤ 关键改动要人确认（不能全自动上生产）
```

### 护城河五：AI 机器人用户（数字员工）

**不是「AI 辅助人」，是「AI 作为用户执行任务」**：

```
传统：人用软件
AI 辅助：软件给人建议，人点确认
AI 机器人用户：**AI 就是一个"员工"，有自己的账号、权限、待办、KPI**

示例：
· 财务机器人
  · 每天 9:00 自动跑：待审凭证 → 校验勾稽 → 通过的低风险自动过账
  · 每月 1 号：自动对账（银行流水 ↔ 收款单），差异列给人
  · 应收超期 30 天 → 自动发催收短信/邮件
  
· 采购机器人
  · 库存低于安全库存 → 自动生成采购申请（按历史用量算量）
  · 询价单到期未回 → 自动催询
  
· 客服机器人
  · 客户投诉工单 → 自动分类 + 派单 + 首次响应
  
· 质检机器人
  · 每天巡检 152 组勾稽 → 有红的立刻建卡给人
```

**架构要求（这是新产品能力，要设计）**：

| 要求 | 说明 |
|---|---|
| **Agent 身份** | 不是复用 sys_user，要有独立的 `agent_id`（可区分「人做的」和「机器人做的」） |
| **细粒度权限** | 机器人能做什么、不能做什么，要精确到接口级 |
| **完整审计** | 每一步可追溯（谁/哪个机器人/什么依据/输出了什么） |
| **人在环上** | 关键动作（过账/付款/删除）必须人确认，机器人只能提议 |
| **可解释** | 机器人做的每个决定要能说清「为什么」 |
| **可停可刹** | 一个开关停掉某个机器人，不影响系统 |

**这是真正的差异化**：用友金蝶的「RPA」是模拟点鼠标，云枢的机器人是**原生 API 级集成 + 全权限模型**。

## A. 凭证溯源 + 报表勾稽自检

### A1 目标

把「可验证」从内部能力变成**客户能点的产品功能**。

### A2 做法

**① 凭证溯源（每张凭证一个「溯源」按钮）**

```
点开 → 弹出全链路：
  凭证号 PZ-20261109-0001
    ↓ 分录
    借 1122 应收账款  113,000
    贷 6001 主营业务收入 100,000
    贷 2221 应交税费-销项 13,000
    ↓ 来源单据
    销售发票  IV-20261109-000003（含税 113,000）
    ↓ 业务链条
    销售订单 SO-20261031-000012 → 出库单 OUT-20261101-000005 → 发票 IV-…
    ↓ 原始附件
    发票PDF（点击预览）
    ↓ 操作日志
    2026-11-09 10:23 张三 创建
    2026-11-09 10:25 李四 审核
    2026-11-09 14:00 王五 过账
```

**技术要求**：
```
· 后端：GET /voucher/{id}/trace → 返回完整链路（一次查完，不能点一次查一次）
· 数据来源：
  - biz_voucher.source_type + source_id（已有）
  - biz_voucher_entry 的辅助核算（已有）
  - sys_attachment（已有）
  - operation_logs（已有）
· 前端：时间轴组件（竖排 + 可折叠）
· 性能：链路不超过 6 层，超过就截断（防循环）
```

**② 报表勾稽自检（每个报表一个「自检」按钮）**

```
点开 → 跑该报表的校验规则 → 全绿打勾 / 红的说明哪条不对

资产负债表自检（示例）：
  ✅ 资产总计 = 负债 + 所有者权益        4,520,000 = 4,520,000
  ✅ 流动资产 + 非流动资产 = 资产总计      1,200,000 + 3,320,000 = 4,520,000
  ✅ 应交税费 ≥ 0 或已重分类到待抵扣      0（无留抵）
  ✅ 期初 + 本期发生 = 期末               4,100,000 + 420,000 = 4,520,000
  ✅ 与总账科目余额表一致                 通过
```

**技术要求**：
```
· 后端：GET /report/{kind}/selfcheck → 逐条返回 {name, passed, expected, actual, hint}
· 规则从哪来：
  - 现有的 verify 脚本（scripts/verify/*.py）已有 152 组勾稽
  - 要把它从「脚本」变成「API 可调用的规则集」
  - 建议：规则表 biz_invariant_rule（code / name / kind / sql / expect / severity）
· 前端：勾选列表 + 可展开看 SQL/明细
· 客户价值：他自己就能验证「这个数是对的」，不用信你
```

### A3 验收

```
① 凭证页有「溯源」按钮，点开能看到 6 层链路（单据/分录/附件/日志）
② 链路数据准确（抽查 10 张凭证，与库核对一致）
```

## C. 智能填单（发票 OCR → 凭证）

### C1 目标

做出「用友金蝶没有」的差异化能力。

### C2 做法

**① 场景**

```
财务收到一张增值税专用发票（PDF 或照片）
  ↓ 上传到云枢
  ↓ OCR 识别：发票号/开票日期/购销方/金额/税额/明细
  ↓ 自动生成凭证草稿：
     借 1401 原材料      100,000
     借 2221 应交税费-进项 13,000
     贷 2202 应付账款     113,000
  ↓ 财务复核（改一下科目/辅助核算）
  ↓ 提交审批 → 过账
```

**② 技术方案**

```
OCR 选型（三选一）：
A. 云厂商 OCR（阿里/腾讯/百度）—— 准确率高，但要外网 + 按次收费
B. 本地部署（PaddleOCR / RapidOCR）—— 免费，但准确率略低，要装模型
C. 大模型多模态（GPT-4V / Qwen-VL）—— 灵活，但也要外网

建议：**先做 B（本地 PaddleOCR）**，理由：
· 云枢定位「数据自己掌握」
· 财务发票涉及客户信息，不该传出去
· PaddleOCR 对中文发票准确率足够（实测 95%+）

科目推荐逻辑：
· 规则优先：供应商 → 默认科目（供应商档案里配）
· 历史学习：同供应商历史凭证用的科目
· 大模型兜底：如果规则和历史都没有，用 LLM 推荐

关键：**AI 只给草稿，人必须复核**（不能自动过账）
```

**③ 与现有模块的关系**

```
复用：
· sys_attachment（上传已有）
· biz_voucher（凭证草稿已有）
· biz_supplier（供应商匹配）
```

## E. 错误码体系化

### E1 目标

让前端/客户/运维能按「类型」处理错误，而不是逐个 if。

### E2 现状（乱）

```
现在看到的错误码：
  65018  审批无审批人
  66001  编码重复
  66054  allow_manual_code=false
  60015  导出超 1 万行
  65042  节点无兜底人
  
问题：
· 前缀有规律吗？（6 开头都是业务错？但 60015 是什么）
· 前端怎么分类处理？
· 客户看到 66001 知道怎么办吗？
```

### E3 设计

**6 位码规则**：`{大类1}{模块2}{序号3}`

```
大类：
  1xxxxx  参数/校验错误（400）
  2xxxxx  认证/授权错误（401/403）
  3xxxxx  资源不存在（404）
  4xxxxx  状态冲突（409）
  5xxxxx  服务器错误（500）
  6xxxxx  业务规则拒绝（422）

模块（大类后 2 位）：
  01 系统 / 02 采购 / 03 销售 / 04 库存 / 05 财务
  06 资产 / 07 预算 / 08 合同 / 09 流程 / 10 附件
  11 任务 / 12 主数据 / 13 平台

序号（后 3 位）：模块内递增

示例：
  103001  参数缺失（系统-参数校验-001）
  202001  令牌过期（认证-001）
  403001  库存不足（状态冲突-库存-001）
  602001  审批无审批人（业务规则-采购-001）
```

**响应体结构**：
```json
{
  "code": 602001,
  "message": "该审批节点没有可指派的审批人",
  "hint": "请管理员为该节点配置角色成员，或设置兜底审批人",
  "docs": "https://docs.../error/602001",
  "trace_id": "a1b2c3d4",
  "details": {
    "node_id": "...",
    "node_name": "部门经理审批",
    "role_code": "DEPT_MANAGER"
  }
}
```

**关键：`hint` 是人话，不是技术描述**。

### E4 验收

```
① 全部错误码按新规则重编（或建立映射表，老码保留兼容）
② 每个错误码有 message（技术）+ hint（人话）
③ 前端能按大类统一提示（不用逐个 if）
④ 有错误码字典页（客户/运维可查）
```

### E5 工作量

| 卡 | 内容 | 工时 |
|---|---|---|
| ERRCODE-01 | 错误码规划表（全仓扫描现有码 → 重编） | 3h |
| ERRCODE-02 | 后端 NikError 改造 + 兼容层 | 4h |
| ERRCODE-03 | 前端统一错误处理 + 字典页 | 3h |

**合计约 10 小时**

### E6 风险

```

```

## G. AI 快速二次开发工作台

### G1 目标

把「本次对话正在做的事」产品化：**客户提一句话，AI 改好代码并上线**。

```
现状（已验证可行）：
  laoliu（AI 主助手）→ 拆卡 → worker agent 写码 → 测试 → 提交 → 部署
  = 44 张卡、13 域演练、100 条问题清单全 AI 完成

目标（产品化）：
  客户在云枢里说「采购订单要加预算占用字段」
  → AI 读出意图 → 生成需求卡 → 生成迁移/DTO/前端/测试
  → 客户在界面上确认 → 自动部署到他自己的环境
  → 全程有人话报告 + 一键回滚
```

### G2 五层架构

```
① 需求理解层
   输入：客户自然语言（"我要在采购订单加一个预算占用字段"）
   处理：LLM 理解 → 结构化需求
         {entity: "采购订单", change: "add_field",
          field: {name: "预算占用", type: "decimal",
                  source: "biz_budget.occupied_amount"}}
   输出：结构化需求单（客户可确认）

② 拆卡层
   处理：需求单 → 实现卡序列（含依赖链）
   依据：现有代码结构（读 AST / grep 定位要改的文件）
   输出：卡列表 + task_links 单链
   
   关键：必须复用「单链 + 父子依赖」模型（不能并行失控）

③ 实现层
   执行：worker agent 按卡写代码
   约束：每张卡 ≤1.5 小时 + ≤2 个源文件（现有规则）
   
④ 验证层（这是能落地的关键）
   ① 后端 cargo test（现有 3880 用例）
   ② 前端 typecheck + build
   ③ 迁移幂等（空库跑一遍）
   ④ 不变量（80 项）不退化
   ⑤ 勾稽（152 组）不退化
   ⑥ **对该需求新增的机械断言**（不能只靠"看着对"）
   
⑤ 交付层
   · 人话报告：「我在采购订单加了『预算占用』字段（只读，取自预算模块），
                 改了 4 个文件，新增 1 个迁移，8 条测试全过」
   · **提交到测试区**（隔离环境：独立分支 + 独立库 + 独立进程）
   · 客户在测试区**真实试用验收**（不是看截图）
   · **走部署审批流**（技术负责人 → 业务负责人 → 客户决策人，三级）
   · 审批通过 + 打 tag → 人工执行 deploy.sh（脚本硬校验审批单）
   · 一键回滚：同样走审批流（source_type=ROLLBACK）
```

### G3 关键设计决策（用户 2026-11-09 修正）

| 决策点 | 方案 | 理由 |
|---|---|---|
| **AI 在哪改代码** | ❌ **绝不碰生产**。只能在**开发沙箱**改，改完**提交到测试区（隔离环境）** | 三层隔离：沙箱 / 测试区 / 生产 |
| **改完怎么上线** | **必须走「部署审批流」**（多级审批通过才允许），**不是"客户点确认"** | 吃自己的狗粮：连部署都走流程 |
| **改动怎么证明对** | 机械断言 + 15 道门禁 | 云枢相对其他「AI 编程」的核心差异 |
| **改不了怎么办** | AI 明确说「这个我做不了，需要人」 | 不编造（比"假成功"重要 100 倍） |
| **客户不懂代码怎么办** | 人话报告 + 测试区试用 | 客户在测试区真实操作，不看 diff |

**用户原话（2026-11-09）**：
> 「AI 不能自动改生产代码（只能改客户环境的副本），代码可以提交到测试区，注意，**这个功能测试区非常重要，相当于一个隔离的环境**。改完不能自动上线（客户点「确认」才部署），**这个硬约束不够，需要通过特定审批流才能部署**。」

**这两条把「人环确认」从「点个按钮」升级成「走一套流程」，从制度上兜住风险。**

### G3.1 三层环境隔离（这是新设计的核心）

```
┌─────────────────────────────────────────────────────────┐
│  ① 开发沙箱 Sandbox                                      │
│     · 用途：AI 在这里写代码、跑测试                       │
│     · 分支：feature/ai-<需求号>                          │
│     · 数据库：sandbox_db（独立实例，可随时重置）            │
│     · 服务：无（只编译不常驻）                             │
│     · 客户：看不到                                       │
│     · 谁能进：AI only                                    │
└─────────────────────────────────────────────────────────┘
                        ↓ 代码测试通过后「提交」
┌─────────────────────────────────────────────────────────┐
│  ② 测试区 Staging  ★ 关键隔离环境 ★                      │
│     · 用途：客户试用 + 验收                               │
│     · 分支：staging（AI 只能推到这里）                     │
│     · 数据库：staging_db（独立实例）                       │
│              可选：生产数据的**脱敏副本**（客户能看真实场景）  │
│     · 服务：独立进程 + 独立端口（如 8033）                  │
│     · 客户：能登录、能操作、能验收                          │
│     · 隔离性：**怎么折腾都不影响生产**（独立库独立进程）      │
│     · 谁能进：AI 推代码、客户试用、技术负责人审查             │
└─────────────────────────────────────────────────────────┘
                        ↓ 客户验收通过 + 部署审批流通过
┌─────────────────────────────────────────────────────────┐
│  ③ 生产区 Production                                     │
│     · 用途：真实业务                                        │
│     · 分支：main（打 tag 才能进）                          │
│     · 数据库：prod_db                                    │
│     · 服务：主服务 + 监控 + 备份                            │
│     · 客户：日常使用                                       │
│     · 谁能进：**只有审批通过的部署流程**（人工执行脚本）        │
└─────────────────────────────────────────────────────────┘
```

**三条铁律**：

| # | 铁律 | 校验方式 |
|---|---|---|
| **1** | **AI 的写权限止于测试区**（`staging` 分支 + `staging_db`） | 代码层：AI 的 git 凭据只有 staging 分支写权限；数据库层：AI 用 staging 库的独立账号 |
| **2** | **测试区必须与生产物理隔离**（独立实例，不是同库不同 schema） | 部署层：两个库在不同实例/不同端口；校验：staging 的连接串不能指向 prod |
| **3** | **测试区永远能重置**（跑乱了就回滚到干净快照） | 运维层：每日自动快照 + 一键恢复 |

**为什么必须物理隔离（不能同库不同 schema）**：
```
· 同库不同 schema → 一个 DROP SCHEMA 就可能误伤
· 共享连接池 → 连接串配错就串库
· 共享实例 → 测试把 CPU/内存打满，生产跟着卡
· 备份混在一起 → 恢复时容易搞错对象
```

**分层校验（防越界）**：
```sql
-- 测试区启动时自检：绝对不能连到生产库
DO $$
BEGIN
    IF current_setting('cloudpivot.env') <> 'staging' THEN
        RAISE EXCEPTION '测试区环境标识错误，拒绝启动';
    END IF;
    IF current_database() = 'cloudpivot' THEN   -- 生产库名
        RAISE EXCEPTION '测试区连到生产库，拒绝启动';
    END IF;
END $$;
```

**代码流转（唯一合法路径）**：
```
sandbox/feature/ai-xxx
    ↓ 门禁全绿（15 道）
    ↓ 自动合并
staging
    ↓ 客户验收 + 部署审批流通过
    ↓ 打 tag（v1.2.3-ai-xxx）
main
    ↓ 人工执行 deploy.sh
生产
```

**AI 的 git 权限只能推 `staging`**（`main` 只有人在审批后推）。

### G3.2 部署审批流（不是"点确认"）

**核心设计**：部署走**云枢自己的流程引擎**，不是硬编码的"确认按钮"。

**新单据 `biz_deploy_request`（部署申请单）**：

```sql
CREATE TABLE biz_deploy_request (
    id              uuid PRIMARY KEY,
    request_no      varchar(32) UNIQUE NOT NULL,   -- DEP-20261109-0001
    source_type     varchar(16) NOT NULL,          -- AI_DEV / HOTFIX / RELEASE
    requirement     text,                           -- 需求描述（人话）
    commit_from     varchar(64),                    -- 起始 commit
    commit_to       varchar(64),                    -- 目标 commit（要上生产的）
    tag_name        varchar(64),                    -- 打好的 tag
    changelog       text,                           -- 变更摘要（人话报告）
    impact_scope    text,                           -- 影响面（改了哪些模块）
    rollback_plan   text,                           -- 回滚方案
    gate_result     jsonb,                          -- 15 道门禁结果快照
    invariants      jsonb,                          -- 80 项不变量 + 152 组勾稽结果
    staging_proof   text,                           -- 测试区验收证据（截图/日志路径）
    status          varchar(16) DEFAULT 'DRAFT',   -- DRAFT/PENDING_APPROVAL/APPROVED/REJECTED/DEPLOYED/ROLLED_BACK
    flow_instance_id uuid REFERENCES biz_flow_instance(id),
    deployed_at     timestamptz,
    deployed_by     uuid,
    created_at      timestamptz DEFAULT now()
);
```

**审批流（默认三级，可配置）**：

```
节点 1：技术负责人（APPROVE）
  · 看什么：门禁结果（15 道全绿？）、代码审查（变更是否合理）
  · 能干什么：通过 / 驳回（附意见）/ 加签
  · 驳回 → 退回申请（可改完重提，不是终止）

节点 2：业务负责人（APPROVE）
  · 看什么：功能验收（是否符合需求）、影响面（会不会影响别人）
  · 能干什么：通过 / 驳回 / 加签

节点 3：客户决策人（APPROVE）
  · 看什么：changelog（人话）、staging_proof（测试区证据）、rollback_plan
  · 能干什么：通过 / 驳回
  · 注意：小型客户可以合并到节点 2

全部通过 → status=APPROVED → 允许部署（但还是要人工执行脚本）
任一级驳回 → status=REJECTED → 退回（可改完重提，不是终止）
```

**关键设计（吃自己的狗粮）**：

| 要素 | 用什么 |
|---|---|
| 审批流定义 | **`biz_flow_def`**（现有流程引擎，可配置，不硬编码） |
| 审批实例 | **`biz_flow_instance`**（现有） |
| 审批节点 | **`biz_flow_node`**（现有，支持会签/加签/驳回/升级/兜底） |
| 权限 | 现有 `{模块}:{资源}:{动作}` 权限码 |
| 审计 | 现有 operation_logs + 流程节点记录 |

**这意味着**：
```
✅ 客户可以按自己的组织架构配审批链（不给 AI 特权）
✅ 支持会签（技术 + 业务 + 客户一起批）
✅ 支持加签（遇到复杂改动拉更多人）
✅ 支持升级（没人批自动找上级）
✅ 支持兜底人（P3-03 的 fallback）
✅ 全过程可追溯（谁批的/什么时候/什么意见）
✅ 复用现有流程设计器（客户自己就能改审批链）
```

**部署执行的硬约束**：

```bash
# deploy.sh 的第一道检查
bash scripts/ops/deploy.sh --tag v1.2.3-ai-xxx

# 内部逻辑：
① 查 biz_deploy_request
   WHERE tag_name = 'v1.2.3-ai-xxx' AND status = 'APPROVED'
② 如果查不到 → 报错退出：
   "❌ 该版本没有通过的部署审批（或无审批单据），拒绝部署"
③ 如果查到 → 继续（记录 request_id 到部署日志）
④ 部署完成后 → 回写 biz_deploy_request.status='DEPLOYED'
```

**没有审批单 = 部署脚本拒绝执行**（技术强制，不是靠自觉）。

**回滚也走同样的路**：
```
回滚 → 生成新的部署申请单（source_type=ROLLBACK）→ 走审批流 → 批准 → 执行
（紧急回滚可以配置「快速通道」：只有节点 3 一人批，但事后要补说明）
```

```
【第一组：AI 改代码的边界】
① AI 的 git 凭据推不进 main（实测：git push origin main 被拒）
② AI 只能推 staging 分支

【第三组：部署审批流】
```

## H. AI 机器人用户（数字员工）

### H1 目标

让 AI **作为员工**在云枢里干活，不是「辅助人点按钮」。

### H2 六块架构

#### ① Agent 身份表（新）

```sql
CREATE TABLE sys_agent (
    id              uuid PRIMARY KEY,
    agent_code      varchar(32) UNIQUE NOT NULL,   -- FIN_BOT_01
    agent_name      varchar(64) NOT NULL,          -- 财务机器人
    agent_type      varchar(32) NOT NULL,          -- FINANCE / PURCHASE / SERVICE / QA
    owner_dept_id   uuid REFERENCES sys_dept(id),  -- 归属部门（KPI 归属）
    status          smallint DEFAULT 1,            -- 1启用 0停用
    run_mode        varchar(16) DEFAULT 'CRON',    -- CRON / EVENT / MANUAL
    cron_expr       varchar(64),                   -- 定时表达式
    config          jsonb,                          -- 机器人专属配置
    created_at      timestamptz DEFAULT now()
);
```

**关键**：`agent_id` 与 `user_id` 分离（能区分「人做的」和「机器人做的」）。

#### ② 权限模型（复用 + 扩展）

```
复用现有 {模块}:{资源}:{动作} 权限码
新增 agent 维度：
  sys_agent_permission(agent_id, permission_code, can_execute, need_human_confirm)

示例（财务机器人）：
  finance:voucher:read            can_execute=true,  need_human_confirm=false
  finance:voucher:create          can_execute=true,  need_human_confirm=false
  finance:voucher:post            can_execute=true,  **need_human_confirm=true**  ← 过账要人确认
  finance:voucher:delete          can_execute=false  ← 机器人不能删
  finance:payment:create          can_execute=true,  **need_human_confirm=true**  ← 付款要人确认
```

#### ③ 任务调度

```
三种触发：
① CRON（定时）   每天 9:00 跑财务巡检
② EVENT（事件）  应收超期 → 触发催收机器人
③ MANUAL（手工） 用户点「让机器人跑一次」

复用现有 sys_job（已有 cron 框架）
```

#### ④ 工具/动作库（关键设计）

```
机器人不能直接调 API（太危险），要经过「动作库」：

sys_agent_action：
  action_code    FIN_CHECK_VOUCHER
  agent_id       FIN_BOT_01
  http_method    POST
  http_path      /api/business/erp/voucher/{id}/check
  params_schema  {"voucher_id": "string"}
  risk_level     LOW / MEDIUM / HIGH
  need_confirm   false / true

好处：
· 机器人能做什么 = 白名单（不是「什么都能做」）
· 每个动作有风险分级
· 审计时能看「机器人调了哪些动作」
```

#### ⑤ 审计（比人更严）

```
sys_agent_run_log：
  run_id, agent_id, trigger_type(CRON/EVENT/MANUAL),
  started_at, ended_at, status,
  actions[]: [{action_code, target_id, result, reason}],
  output_summary,  -- 「处理了 12 张凭证，8 张通过，4 张转人工」
  trace_id

关键：
· 机器人做的每个动作都要留痕
· 要能回答「为什么这么做」（reason 字段）
· 要能回答「依据是什么」（引用了哪条规则/哪个数据）
```

#### ⑥ 人环确认 + 紧急停止

```
人环确认：
  风险 HIGH 的动作 → 生成「待确认」条目 → 人点确认才执行
  （不是机器人直接做，是机器人提议 + 人批准）

紧急停止：
  sys_agent.status = 0 → 立刻停（不等当前任务跑完）
  或「暂停 N 小时」
  一个开关停掉所有机器人（全局 kill switch）
```

### H3 四个首发机器人（按 ROI 排序）

| 机器人 | 做什么 | 价值 | 风险 |
|---|---|---|---|
| **质检机器人**（QA_BOT） | 每天跑 152 组勾稽 + 80 项不变量，有红就报告 | 无人值守兜底 | 低（只读） |
| **财务机器人**（FIN_BOT） | 凭证预审（勾稽+科目异常）、自动对账、应收催收 | 会计省 2h/天 | 中（过账要人确认） |

## 2. 启动顺序建议

### 依赖关系（关键，别搞错顺序）

```
G（AI 二次开发）的「验证层」依赖 A（可验证性）
G 的「部署层」依赖 B（一键交付）
H（AI 机器人）的「审计」依赖 A，「权限」依赖现有权限模型

A ──┐
    ├──→ G（AI 二次开发）
B ──┘
A ──→ H（AI 机器人）
```

**所以不能先做 G/H**（地基没有，会返工）。

### 四批启动

```
第 1 批（地基）：A 凭证溯源 + 勾稽自检
  → 把「可验证」变成产品能力（G 的验证层要用它）
  → 也是最能打动客户的东西

第 2 批（地基）：B 一键交付
  → G 的部署要靠它
  → 也是「能不能卖」的前提

第 3 批（护城河）：G + H
  → G AI 二次开发（有 A/B 的地基，能落了）
  → H AI 机器人（有 A 的审计，能落了）
  → **这两项是真正的差异化**

第 4 批（工程化 + 体验）：D + E + C + F
  → D 大表分区（越晚越难）
  → E 错误码
  → C 智能填单
  → F H5 移动端
```

### 为什么 G/H 排第 3 批而不是第 1 批

```
❌ 如果先做 G（AI 改代码）：
   验证层没依据 → AI 改完不知道对不对 → 等于「AI 瞎改」
   部署层没工具 → 改完没法安全上线 → 等于「没改」

✅ 如果先做 A+B：
   A 给出「怎么证明对」的规则和 API
   B 给出「怎么安全上线」的工具
   G 就是把 A+B 串起来的自动化
```

**一句话**：**A 是「度量衡」，B 是「运输工具」，G 是「用度量衡 + 运输工具造东西」。**
