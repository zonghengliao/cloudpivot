## 1. 结论摘要（先看这 6 条）

| # | 结论 |
|---|---|
| 1 | 「7 套词表」成立，但**不是 1 根轴上的 7 种写法**，而是 **7 根互相独立的概念轴**（§2）。把它们硬合并成一个字符串会毁掉业务语义，所以按「一个文件、七根轴、一套拼写规则、显式的跨轴映射」收敛。 |
| 2 | 卡面举的「同一张采购单 4 个名字」中，**`biz_flow_instance.biz_type = 'purchase_order'` 这条不成立**：生产库实测是 `PO_APPROVE`，与流程定义同名同值（§3）。真正需要改数据的**只有一处**：`biz_status_log.entity_type` 的调拨值 `TRANSFER`。 |

| 4 | 存量数据统一：`biz_status_log.entity_type` 的 `TRANSFER` → `STOCK_TRANSFER`（迁移 `V0219`，带 down）。其余 13 列**不需要改数据**（值域本来就一致），只加了值域巡检。 |
| 5 | 防护三层：**编译期**（只能拿枚举，拿不到裸字符串）+ **单测**（Rust ↔ 前端 TS ↔ 值域配置三方逐字比对）+ **巡检**（`scripts/verify/biz_type_domain.py` 查库，域外值即 FAIL）。 |
| 6 | 没有动任何业务流程语义：审批流 `flow_code` / 状态机边 / 权限码 / 单据状态全部未变，只统一「同一个对象的同一个名字」。 |

## 3. 「同一张采购单 4 个名字」——逐条核对（卡面假设有 1 条是错的）

| 卡面说法 | 实测结果 | 定性 |
|---|---|---|
| `biz_flow_def.biz_type = 'PO_APPROVE'` | ✅ 正确 | 审批动作轴（正常） |
| `biz_flow_instance.biz_type = 'purchase_order'` | ❌ **不成立**。生产库实测 = `PO_APPROVE`（6 行），与流程定义**同名同值**；`purchase_bridge::BIZ_TYPE = "PO_APPROVE"` 是唯一写入口 | 本来就是统一的，**不需要迁移流程实例** |
| `biz_purchase_order 的某种标识 = 'PO'` | 部分是：`PO` 是**单号前缀**（`PO-yyyyMMdd-000001`，`purchase_model::SEQ_TYPE`），不是类型词表 | 不同概念，不合并（单号前缀属于取号器） |
| 前端某处 = `purchaseOrder` | 前端没有 `purchaseOrder`；实测是 `purchase-order`（联动作废 URL 路径段）+ 4 处硬编码 `'PURCHASE_ORDER'` 当成 `biz_type` 用（`TaskPreview.vue` ×3、`notify-node-config.ts` ×1） | **确实是 bug**：把「实体类型」当「审批类型」用，预览里显示的业务类型永远对不上 → 本卡改为 `PO_APPROVE` |

**所以同一张采购单实际有 4 个名字，但它们分属 4 根不同的轴**：

```
审批轴     biz_flow_def/instance.biz_type      = PO_APPROVE      ← 「走哪一类审批」
对象轴     biz_status_log.entity_type          = PURCHASE_ORDER  ← 「这是哪张单据」
URL 轴     REST 路径段                          = purchase-order  ← REST 惯例（kebab）
取号轴     单号前缀                             = PO              ← 不是类型
```

前三个是**必须分开的四/三根轴**（同一张收货单有好几条审批：`STOCK_IN_POST` + `STOCK_IN_CANCEL`，
所以审批轴天生比对象轴细）；第四个根本不是类型。四者之间的关系现在**只在 `doc_kind.rs` 里写一次**
（`FlowBizType::doc_kind()` / `DocKind::route()` / `DocKind::as_str()`）。

## 4. 找到的真不一致（3 条）

### 4.1 调拨单的 `entity_type` 与其余三处不同名（本卡改数据）

```
biz_status_log.entity_type            = 'TRANSFER'        ← 只有这里
biz_stock_transfer（表名）             = STOCK_TRANSFER
biz_inventory_txn.doc_type            = 'STOCK_TRANSFER'
biz_flow_def.biz_type（审批）          = 'STOCK_TRANSFER'
```

后果：按 `entity_type` 分组的报表/巡检/夹具清场把调拨拆成两行；
`fixture_hygiene` 的「entity_type → 单据表」映射表也得单独写一行 `("TRANSFER", "biz_stock_transfer")`。

**处理**：`state_machine::ENTITY_TRANSFER` 改为从 `DocKind::StockTransfer.as_str()` 取值（= `STOCK_TRANSFER`），
迁移 `V0219` 把存量 1 行（生产）改过来，带 down。

### 4.2 前端把「实体类型」当「审批类型」用（本卡改代码）

`TaskPreview.vue`（3 处）、`notify-node-config.ts`（1 处）把示例变量的 `instance.biz_type`
硬编码成 `'PURCHASE_ORDER'`。`instance.biz_type` 是**审批轴**的值，采购单是 `PO_APPROVE`。
模板变量预览里「本流程业务类型」因此永远对不上真实流程。

**处理**：改为引用 `PO_APPROVE_BIZ_TYPE`（派生自 `FLOW_BIZ_TYPES`）。

### 4.3 前端自造了 5 个后端不存在的 key（第 8 套词表的真身）

`views/business/erp/inventory/inventory-logic.ts` 的 `BIZ_TYPE_LABELS` 有 13 个 key，其中 5 个
**后端任何地方都不写**：`PURCHASE_RETURN_OUT` / `SALE_RETURN_IN` / `PRODUCE_IN` /
`MATERIAL_ISSUE_OUT` / `INIT_IN`。这些「中文标签」永远不会被命中，但会让人误以为系统支持
这些业务类型；同时后端真实的 `PURCHASE_RETURN` / `PRODUCTION_IN` 反而没有标签（显示英文码）。

**处理**：整张表删掉，`bizTypeLabel` / `docTypeLabel` 直接走 `doc-kinds.ts` 的
`TXN_BIZ_TYPE_LABELS` / `TXN_DOC_TYPE_LABELS`；单测里加了「自造 key 必须原样返回英文码」的断言。

## 6. 为什么不全合并（卡面「不改业务流程语义」的落地判断）

盘点证明这 7 根轴问的是**不同问题**，合并会丢语义：

| 轴 | 反例（合并就错） |
|---|---|
| 审批动作 vs 业务对象 | 一张收货单有 `STOCK_IN_POST`（过账）和 `STOCK_IN_CANCEL`（作废）两条审批 → 审批轴必须更细 |
| 库存变动 vs 业务对象 | 一次调拨产生 `TRANSFER_OUT` + `TRANSFER_IN` 两条流水；一次收货有 `PURCHASE_IN` + `PURCHASE_IN_CANCEL` |
| 流水来源 vs 业务对象 | 一物一码的流水来源是 `SERIAL_BATCH` / `MATERIAL_SERIAL`（**子表级**），不是任何单据 |
| 凭证来源 vs 业务对象 | `MANUAL`（手工录入）/ `YEAR_END`（年结）/ `OPENING`（期初）**没有对应单据** |
| 序列号来源 vs 单据子类型 | 序列号来源多 `TRANSFER` / `PRODUCE`，`in_type` 只有 `PURCHASE/RETURN/OTHER` |
| 审批动作 vs 对象（任务/费用） | `TASK_ACCEPT` / `EXPENSE` / `OTHER` 不挂在任何 ERP 单据上（`doc_kind()` 返回 `None`） |

**登记在案、明确不合并的「同名不同义」列**（连轴都不是，别误当业务类型）：

| 列 | 真实语义 | 域 |
|---|---|---|
| `biz_flow_cc.source_type` | 抄送人的**来源**（与 `assignee_source` 同域） | `USER` / `ROLE` / `DEPT` / `ADMIN` … |
| `sys_import_task.biz_type` / `sys_export_task.biz_type` | **导入导出定义编码**（点分命名空间） | `system.dict_item` … |
| `sys_notice.biz_type` / `sys_notice.target_type` | 站内信**分组** / 接收人范围 | `flow` / `task` / `USER` / `ROLE` / `ALL` … |
| `operation_logs.target_type` / `audit_logs.target_type` | 审计对象的**类名** | `User` / `Role` / `Menu` / `Auth` … |
| 各单据的 `SEQ_TYPE` | 单号前缀 | `PO` / `IN` / `TK` / `AP` / `PZ` … |

## 7. 防护三层（新增业务类型时只改一处）

| 层 | 机制 | 位置 |
|---|---|---|
| ① 编译期 | 调用方只能拿枚举 / TS 联合类型，拿不到裸字符串 | `doc_kind.rs` / `doc-kinds.ts` |
| ② 单测 | 15 条断言钉住「枚举 ↔ 前端 TS 数组 ↔ 值域配置 ↔ state_machine 实体表 ↔ 审批健康检查清单 ↔ 各模块 `BIZ_TYPE` 常量」逐字一致 | `doc_kind_tests.rs`（`cargo test --lib business::shared::doc_kind`） |
| ③ 巡检 | 按 `COLUMN_DOMAINS`（14 列）查库，任何域外值 FAIL；`--self-check` 自证只读 | `scripts/verify/biz_type_domain.py` |

新增一种业务类型的动作清单（一眼看出比原来少）：

1. `doc_kind.rs` 加枚举成员（`FlowBizType` / `TxnBizType` / …）→ 值域常量同步（单测会逼你改）；
2. `doc-kinds.ts` 镜像同一行（单测会逼你改）；
3. 需要审批的 → 加一条 `biz_flow_def` 种子（`biz_type` 从枚举取）。

**不再需要**：改 `fixture_hygiene` 的映射表、改前端某个页面的标签表、改 `cancel_cascade` 的常量、
改好几处 `match`。

## 8. 复跑盘点的命令

```bash
# ① 后端：所有含这些列的列定义
grep -rn "biz_type\|doc_type\|entity_type\|source_type\|in_type\|out_type" backend/migrations/ --include=*.up.sql

# ② 前端：命名 + 取值
grep -rn "bizType\|docType\|entityType" frontend/src/ --include=*.ts --include=*.vue

# ③ 库里每列的实际取值（域字典 → 动态 SQL → distinct）
psql -tAc "select string_agg(format('select %L as col, coalesce(%I::text,''<NULL>'') as v, count(*) from %I group by 2',
           table_name||'.'||column_name, column_name, table_name), ' union all ')
           from information_schema.columns
           where table_schema='public'
             and column_name in ('biz_type','doc_type','entity_type','source_type','in_type','out_type')" \
  | psql -tA -f - | sort

# ④ 值域巡检（唯一真相取自 doc_kind.rs）
python3 scripts/verify/biz_type_domain.py
```

## 9. 本卡没做的事（有意）

| 项 | 理由 |
|---|---|
| 建 `sys_biz_type` 字典表 + 只读对账页（ARCH-3 DC-21 建议的最终形态） | 词表是**编译期枚举**（跟着代码走、能编译期拦截），做成字典表反而变成运行期数据：多一次 IO、可被脏数据污染、加类型要发数据迁移。本卡的 `doc_kind.rs` + 巡检已经提供了「只读对账」的等价能力（`biz_type_domain.py` 就是那个对账页的命令行版）。真要做页面，另开卡。 |
| 合并其余 6 根轴到一个字符串 | 会改变业务语义（§6） |
| 迁移 `biz_flow_instance` 的历史实例 | 实测本来就统一，没必要动历史审批记录 |
| 清生产库 132 条 `E2E_*` 软删流程 / `E2E_*` 实例 | 那是「e2e 跑在生产库」的数据卫生问题，属另一张卡 |

## 10. 补记（2026-11-13，卡 t_c49010bf）：4 个「库里有、词表里没有」的审批业务类型

### 10.1 现象

`scripts/verify/biz_type_domain.py --strict` 在**任何全量迁移库**上红：

```
✗ biz_flow_def.biz_type × 4：
  PRT_APPROVE × 1   ← V0332__purchase_return
  COST_SETTLE  × 1  ← V0381__cost_flow_def
  PR_APPROVE   × 1  ← V0331__purchase_requisition
  SO_APPROVE   × 1  ← V0281__sales_order_flow
```

这 4 个值在各自的 bridge 里是 `pub const BIZ_TYPE`（`sales_approval_bridge` /
`requisition_bridge` / `purchase_return_bridge` / `cost_period_bridge`），单测逐字钉住；
**只有** `doc_kind.rs::FlowBizType` 漏登记。它们是「词表的空白」，不是「拼写错误」。

### 10.2 处置：补登记（不映射到已有值），存量行不动

| 方案 | 结论 | 理由 |
|---|---|---|
| ① 4 个值补进 `FlowBizType`（本卡采用） | ✅ | 字面量早就在生产库里（`biz_flow_def` / `biz_flow_instance` 存量行 + 客户已配好的流程定义），补登记 = 让词表追上事实；审批详情 / 通知 / 联动靠 `biz_type` 认领实例，改值就等于改历史 |
| ② 映射到已有值（如 `SO_APPROVE → PO_APPROVE`） | ❌ | 销售订单审批伪装成采购订单审批：审批详情点错单据、通知写错业务、报表按 `biz_type` 分组直接串味。**语义事故，不是拼写美化** |
| ③ 用迁移把存量行改成域内值 | ❌ | 同上：存量的 `biz_flow_instance` 是历史审批记录，改值等于篡改审批档案 |
