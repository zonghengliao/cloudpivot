### P2-C：拆 Cargo workspace —— 改「层次切」（15 卡，实测可落地）

> **重切结论（2026-11-25 · 卡 `t_b287611c` · 推翻 2026-11-13 的「18 域 18 卡」）**
>
> 「每个业务域抽成一个 crate」**做不成**，且不是工作量问题：Cargo 的包依赖图**必须无环**，而
> 本仓实测 **顶层业务域 24 个节点塌成一个 SCC**（`erp/flow/hr/impexp/business/shared/business/task/system/
> support/shared/utils/middleware/…`），`erp` 内部 **51 个节点一个 SCC**。按域编号切，第一张卡就落在
> 环内部，抽出后第二个域必然顶在环上 —— 无论先抽哪个。
>
> 改为**按层切**：`L1 内核` → `L3 装配层（bin）` → `L2 各域`（**`erp` 整体一个包**）。
> 卡序不再按业务重要度，而按**出边闭包**（依赖深度）排；每张卡开工前先付清自己那一笔解环账。
> **实测全序解环账只要 66 行**（28 个节点 / 25 个新包），不是几百行 —— 环是「由很多条 1~13 行的
> 小口子互相咬住」形成的，不是几处大纠缠。
>
> 证据与复现：`scripts/verify/crate_split_readiness.py`（本次新增 `--plan-order` 卡序校验，
> 以及 `business/shared`、`business/task` 节点名冲突导致的**度量盲区修复**，见 §P2-C.1）。
> 完整分析：`docs/architecture/P2-41-成本域抽crate可行性分析.md`。

#### P2-C.1 判据：抽 crate 看**出边**，不是看入边

Cargo 包图里两个方向不对称，这一点决定了整个切法：

| 方向 | 含义 | 对抽包的影响 |
|---|---|---|
| **入边**（装配层 / 别的域 → 本域） | 别人引用本域 | **合法方向，不用切**。它只决定「改 import 的面」有多大，也就是 `--domain <域>` 报的**回边数** |
| **出边**（本域 → 还留在单体的代码） | 本域引用别人 | **环的唯一来源，必须切**（port / 注册表 / 词表上提 / 事件订阅） |

⇒ 抽 X 的条件：**X 的出边全部落在「更下层已抽出的包」里**。旧卡清单按「回边数为 0 才可抽」判，
把方向判反了（`dashboard` 回边 0 但出边 6 行，按旧判据是「可抽」，实际抽出来照样成环）。

实测口径（2026-11-25，main=a7a60f4e + 本卡的工作区修复）：

**验收口径说明**：本清单的「卡序与工具输出不矛盾」用 `--plan-order` 判（退 0），
**不用旧 `--check`**。原因见 §P2-C.1：`--check` 数的**入边**，而本仓多数域入边恒不为 0
（`erp` 28、`flow` 128、`business/shared` 480），任何需要切接缝的计划在旧 `--check` 下都会退 1

`--plan-order` 是把整条卡序一次模拟完，等价于「每张卡开工时 `--layer-check` 已绿」。

#### P2-C.4 每张卡的通用施工单（照抄）

1. **先付解环账**：按本卡「本步要切」清单，把那几行倒转成接缝（照抄 P2-B 先例：
   `business::shared::voucher_port` / `flow::doc_reader` 注册表 / `hr::employee_reader` / `task::approval_port`）。
   切完 `--plan-order` 必须绿，`cargo check --workspace` 必须过。
2. **建包搬文件**：`git mv` 到 `backend/crates/cloudpivot-<域>/src/`，包内 `crate::business::<域>::x` → `crate::x`。
3. **改跨包路径**：别的包引用本域 → `cloudpivot_<域>::…`；本域引用内核 → `cloudpivot_kernel::…`。
4. **`include_str!` 相对路径重算**：本仓有 99 处 `include_str!("../../../migrations/…")`，
   一律改**锚定式**，之后不再受目录深度影响：
   `include_str!(concat!(env!("CARGO_MANIFEST_DIR"), "/../../app/migrations/…"))`。
   （`migrations/` 仍留在 `backend/app/migrations/`，运行时路径 `config/config.toml` 不动。）
5. **测试夹具**：`shared::test_helpers`（`ensure_any_dept` / `ensure_any_user`）随 C1 进内核，
   以 `#[cfg(any(test, feature = "test-support"))]` 暴露；域包在 `[dev-dependencies]` 打开该 feature。
   各域自己的 `fixture_hygiene`（`hr`、`erp` 各一份）随所在域走，不跨包。
6. **路由不许静默少**：每张域卡合并前，`inventory` 断言条数必须是「拆前 - 0」。口径：
   `permission_audit_tests` 类全量断言**统一放在 C2 的 bin 包**（bin 链接全部域 crate，`inventory`
   才完整）；域包内只断言自己那几条。`#[nik::get]` 收集发生在最终链接单元，域包漏进 bin 的
   `[dependencies]` ⇒ 该域所有路由**静默 404**，所以 bin 的依赖清单要有门禁核对（C2 交付）。
7. **脚本/文档面**：`cargo run` → `cargo run -p cloudpivot-server`（产物名仍是
   `backend/target/{debug,release}/cloudpivot`，Docker/systemd 的二进制路径不用改）；实测 **25 个以上**
   文件（脚本/文档/配置，不含 `vendor`/`target`）提到 `cargo run`，`scripts/dev.sh`、`scripts/dev-up.sh`、
   `scripts/verify/clean_checkout_gate.sh`（`cargo test -p cloudpivot --lib` 会漏掉已抽出的包）、
   `docker/backend/Dockerfile`、`AGENTS.md` 逐条改。

#### P2-C.5 为什么**不**走「域 crate 反向依赖单体」的过渡路线

那条路的做法是：域包 `cloudpivot-erp-cost` 依赖 `cloudpivot`（其余全部），靠 bin 拆包解包级环。
它必须付三笔账，付完却拿不到要的东西：

1. 切掉该域所有回边（cost 是 14 行 —— 可做，P2-B 已有三个接缝先例）；
2. bin 拆包（与 C2 同量级，躲不掉）；
3. **`#[cfg(test)]` 夹具跨包不可见**：`cost` 的 18 个真库用例用了 `crate::shared::test_helpers::*`（15 处）
   与 `erp::fixture_hygiene::SEED_ROLE_LOCK`，两者都是 `#[cfg(test)]`——依赖包在非 test 配置下
   编译，这些符号根本不存在。要么特性化（C1 的做法，反正也要做），要么 18 个用例留在 `app`（等于空跑）。

付完之后，`cargo tree -p <域>` 显示的仍是 `<域> → cloudpivot(含其余 20 个域)`：
**拿不到依赖方向信息，增量编译也不会变快**（改任何一个域都要重编整个单体，域包还是跟着重编）。
而它会给后面每张卡定下错误范式：第二张卡抽出后，第一张会顶在
`域A → cloudpivot(含域B)` + `域B → cloudpivot(含域A)` 的间接环上，越往后越只能往单体里加接缝。
**结论：不采用。**唯一的合法用法是「内核先行」——内核对下不依赖任何域，`域 → 内核` 是真正的向下箭头，
这也是本卡序 C1 的位置。
