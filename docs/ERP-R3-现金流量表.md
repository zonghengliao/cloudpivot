> 依赖：ERP-R1（`biz_report_item` / 期间口径 / 金额格式 / 导出 / 快照模式）、ERP-R2（两表勾稽的写法）

## 一、这张表做什么

从凭证里读**现金类科目的收支流水**，按**对方科目**自动分成「经营 / 投资 / 筹资」三类，
并当场把「期末现金及现金等价物余额」与**资产负债表「货币资金」**勾稽：

```text
核心不变量
  期末现金及现金等价物余额 ≡ 资产负债表「货币资金」
  期末余额                 ≡ 期初余额 + 本期净增加额
```

不平不是"四舍五入"，而是「现金类科目的流向没被完整捕获」的报警（分录被删、借贷不平、
现金类科目口径不一致），差一分也要报出来（`check.diff` 精确、`check.diff_text` 4 位兜底）。

| 接口 | 权限码 |
|------|--------|
| `GET /business/erp/report/cash-flow?period=yyyy-MM` | `business:erp:report:cash-flow` |
| `GET /business/erp/report/cash-flow/export?period=yyyy-MM` | `business:erp:report:export`（复用 R1） |

## 二、简化口径（**为什么不做完整版**）

完整现金流量表要三件事：

1. **三大活动分类**（经营 / 投资 / 筹资）；
2. **直接法 / 间接法**（间接法要从净利润倒推，牵涉存货、应收应付、折旧摊销的变动）；
3. **现金流量项目表 + 会计人工指定**（每张凭证上再录一遍"现金流量项目"）。

本卡做 **①+直接法**，明确不做 ②③：

| 维度 | 完整版 | 本卡（简化版） |
|------|--------|----------------|
| 分类 | 手工指定现金流量项目 | **按对方科目自动分类**（`biz_cashflow_item` 配置驱动） |
| 间接法 | 净利润 → 经营活动现金流 | 不做（只出直接法的收支流水） |
| 粒度 | 现金流量项目（几十项） | 三大活动 × 12 个标准明细行 |
| 未分类 | 必须手工指定，否则无法出表 | 归「其他」+ `warnings` 点名科目与笔数（**不许静默丢**） |

**为什么**：手工指定现金流量项目要求会计在每张凭证上多录一遍，工作量翻倍、漏录率极高
（漏了就整张表不平，还查不出是漏了哪张）。按对方科目自动分类在 90% 的中小企业场景
（采购、销售、工资、税费、借款、投资）已经足够准确，且**任何一笔都能追溯到凭证与科目**。
后续要做间接法 / 手工指定，另建卡升级（配置表已经是独立的，不用动代码结构）。

### 2.1 分类规则（`classify`）

```text
现金类科目   = 科目编码以 '1001'（库存现金）/ '1002'（银行存款）开头
               —— 卡面 §一 的口径，**不含 1012 其他货币资金**（见 §2.3）
对方科目     = 同一张凭证里的非现金分录，按科目汇总「贷 − 借」
对方净额 > 0 → 现金流入，金额 = 净额
对方净额 < 0 → 现金流出，金额 = |净额|
对方净额 = 0 → 本凭证内该科目借贷抵消，没有现金流含义（跳过）
```

**金额取「对方科目净额」，不取「现金分录金额」**，因为复式记账下每张 POSTED 凭证
`Σ借 = Σ贷`，于是同一张凭证里：

```text
Σ非现金(贷−借) = Σ现金(借−贷) = 现金净流量
```

多借多贷的复合凭证（一笔收款对应 应收账款 + 工资 + 收入）**按对方科目精确拆分**，
不用比例分摊（分摊会引入尾差，报表上出现 0.01 的假不平）。
差额 `现金净流量 − Σ对方净额` 只有一种来源：**凭证本身借贷不平**（分录被删 / 被改），
这部分进「其他 - 分录不平差额」并进 `warnings`。

### 2.2 12 条标准明细行（`V0185` 种子）

| 活动 | 方向 | 明细行 | 对方科目 |
|------|------|--------|----------|
| 经营 | 流入 | 销售商品、提供劳务收到的现金 | `1122,1121,2203,5001,5051` |
| 经营 | 流入 | 收到的其他与经营活动有关的现金 | `1221,2241,2401,5301,1901` |
| 经营 | 流出 | 购买商品、接受劳务支付的现金 | `2202,1123,1401..1408,4001,4101,5401,5402,6401` |
| 经营 | 流出 | 支付给职工以及为职工支付的现金 | `2211` |
| 经营 | 流出 | 支付的各项税费 | `2221,5801,5403` |
| 经营 | 流出 | 支付的其他与经营活动有关的现金 | `5601,5602,5603,5711,1221,2241,1901` |
| 投资 | 流入 | 收回投资、取得投资收益和处置长期资产收到的现金 | `1601,1602,1604,1605,1606,1701,1702,1801,5111,1131,1132` |
| 投资 | 流出 | 购建固定资产、无形资产和其他长期资产支付的现金 | `1601,1602,1604,1605,1606,1701,1702,1801` |
| 筹资 | 流入 | 吸收投资收到的现金 | `3001,3101,3102` |
| 筹资 | 流入 | 取得借款收到的现金 | `2101,2501,2701` |
| 筹资 | 流出 | 偿还债务支付的现金 | `2101,2501,2701` |
| 筹资 | 流出 | 分配股利、利润或偿付利息支付的现金 | `3104,3103,2231,3001` |

改映射**不用发版**：往 `biz_cashflow_item` 加/改一行即可（`account_pattern` 复用
`report::match_pattern` 语法：编码清单 / 编码+下级 / 前缀 `1*` / `@CATEGORY:...`）。
同一科目可以同时出现在**流入**和**流出**两行（借 1002 / 贷 2501 取得借款 vs
借 2501 / 贷 1002 偿还借款）；**同一方向内**不许两行匹配同一科目（迁移自检会拦，
运行时命中多行会取 `sort_order` 最小者并进 `warnings`）。

### 2.3 1012 其他货币资金：刻意的口径差异（闹钟，不是漏洞）

卡面 §一 定义现金类 = `1001` / `1002`，而资产负债表「货币资金」= `1001,1002,1012`。
两边口径不同，所以：

* 钱只在 1002 ↔ 1012 之间划转时，本表把它当「其他 - 流出/流入」并进 `warnings`，
  勾稽会差这一块 → **报表立刻红**，`hints` 直接点名「1012 其他货币资金」；
* 这不是漏配：把 1012 折进现金类会让「内部划转」看起来像真实的经营/投资现金流出，
  比口径差异更误导。要统一口径，改 `CASH_PREFIXES` 或把这类资金记到 1002（都是配置/账务决定，
  不是代码 bug）。

勾稽右式同理**不写死**科目清单：运行时读资产负债表 `MONETARY_FUNDS` 报表项的
`account_pattern`（取不到时回退 `1001,1002,1012`），再用 R1 的 `report::compute`
出数 —— 两张报表只有**一份**「货币资金」口径（与 ERP-R2 对「未分配利润」的处理同构）。

## 三、口径细节

### 3.1 两列：本期 / 本年累计

```text
本期     = voucher_date ∈ [期间开始日, 期间结束日]
本年累计 = voucher_date ∈ [本年 1 月 1 日, 期间结束日]
期初余额 = 现金类科目在「本期开始日之前」的余额（累计列：本年 1 月 1 日之前）
期末余额 = 期初 + 净增加（两列都是期间结束日，所以期末相同）
```

一张宽窗口（`[ytd_start, period_end]`）查一次，本期 / 累计在内存里切窗口 —— 同一快照、
同一份数据，不会出现"两列来自两个不同时刻"。

### 3.2 快照隔离（L11）

整张表在一个 **REPEATABLE READ** 事务里算完（期间 + 分类配置 + 凭证分录 + 科目余额 +
资产负债表口径，同一个快照）。`SET TRANSACTION ISOLATION LEVEL REPEATABLE READ` 必须是
`BEGIN` 之后第一条语句（PG 规定，否则 25001）。

### 3.3 期间 / 错误码（与 R1/R2 完全一致）

| 情况 | HTTP | 业务码 |
|------|------|--------|
| `period` 缺失 / 不是 `yyyy-MM` | 400 | `10001` |
| 期间不存在且该月没有任何已记账凭证 | 400 | `66010` |
| 分类配置为空 / 表读不到 | 500 | `66011` |
| 期间有账但没建期间行 | 200 + `period_status = DERIVED` + 提示开账 | — |

只算 `status = 'POSTED'` 且未删除的凭证（草稿不进报表）。

### 3.4 响应字段（`CashFlowRes`）

```jsonc
{
  "period": "2026-10", "period_name": "2026年10月", "period_status": "OPEN",
  "current_label": "本期金额", "ytd_label": "本年累计",
  "simplified": true, "simplified_note": "简化版：按凭证里……",
  "operating": {            // 投资 investing / 筹资 financing / 其他 other 同构
    "activity": "OPERATING", "activity_name": "一、经营活动产生的现金流量",
    "inflow": [ {"item_code","item_name","current","ytd","accounts","detail"} ],
    "inflow_total": {"current","ytd"},
    "outflow": [ ... ], "outflow_total": {"current","ytd"},
    "net": {"current","ytd"}
  },
  "net_increase": {"current","ytd"},
  "opening_balance": {"current","ytd"},   // 期初
  "closing_balance": {"current","ytd"},   // 期末
  "check": {
    "balanced": true, "closing_balance","balance_sheet_cash","diff","diff_text","message",
    "closing_by_ledger",   // 总账现金类科目余额（第三方视角，独立算一遍）
    "cash_entry_count", "unclassified_count", "unclassified_inflow", "unclassified_outflow",
    "unbalanced_vouchers": [...], "hints": [...]
  },
  "warnings": ["N 笔现金分录未能分类，已归入「其他」……", "..."]
}
```

金额是**字符串**（`numeric(20,4)` → `rust_decimal` → JSON 字符串），前端只做千分位格式化，
不做任何加减（前端 `Number()` 会引入浮点误差，报表金额不能这么玩）。

`balanced` 用**精确比较**（`diff == 0`），`diff_text` 在 2 位会被舍成 0.00 时保留 4 位
（`0.0001` 也必须红）。

## 四、前端

`frontend/src/views/business/erp/report/cash-flow/index.vue`：

* 三大活动分区（经营 / 投资 / 筹资），每区：流入明细 → 流入小计 → 流出明细 → 流出小计 → 净额；
* 底部：净增加额 → 加期初 → 期末（与纸面报表同序）；
* 勾稽条：绿（一致）/ 红（不平），列出期末现金、货币资金、差额、总账现金类余额、未分类笔数，
  不平还列 `hints` 与"分录合计 ≠ 单头"的凭证；
* `warnings` 非空时**顶部黄条**（未分类笔数 / 科目 / 金额，分录不平凭证号）；
* 「其他」分区只在真有未分类收支时出现；
* 导出 Excel（与资产负债表 / 利润表同一套 `write_sheet`）。

菜单：`sys_menu` …1018（`business:erp:report:cash-flow`，页面 `/business/erp/report/cash-flow`）；

```bash

```

**迁移里种了菜单的，部署后必须清菜单树缓存**（本卡实测踩到）：

```bash
redis-cli -n 0 DEL cloudpivot:menu:tree:all
for k in $(redis-cli -n 0 --scan --pattern "cloudpivot:perm:user_menus:*"); do redis-cli -n 0 DEL "$k" >/dev/null; done
```

`/system/menu/tree` 的全量树缓存 TTL 是 1 小时（`CACHE_HOT_QUERY_TTL_SECS = 3600`），
而**重启服务不会清 Redis** —— 不清的话新菜单节点（…1018）在缓存过期前不会出现在菜单树里，
看起来像"迁移没生效"（库里明明有行、也有授权）。只删缓存，无副作用。
