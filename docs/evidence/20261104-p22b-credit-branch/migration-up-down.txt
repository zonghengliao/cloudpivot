-- ======================================================
-- V0216：po_approve 加「超信用额度 → 财务复核」条件分支（P2-2b）
--
-- 依据：卡 t_c79af27a「拍板 + 配一条边」；上游 P2-2（t_dfdbfcaf，提交 45038a2）已把
--       `biz_supplier.credit_limit` 做成真生效：采购单**提交时**现算「该供应商累计未结
--       采购额（含本单）」，超限则单据三列冻结（`over_credit_limit` / `credit_exposure` /
--       `credit_limit_snapshot`），且超限单**必须走审批**（无已发布 po_approve → 409 + 66036，
--       `business:erp:skip-approval` 对超限单不开放）。
--
-- ── 决策：B（加一条复核），并且是**前置串行** ────────────────────────────
--   `START → 超信用额度判定 ─┬─ over_credit_limit = true ─▶ 财务复核 ─┬─▶ 金额分级① ─▶ …（原三档）─▶ END
--                            └─ 兜底（额度内 / 未评估）──────────────┘
--   · 复核岗位 = `FINANCE_MANAGER`（V0191 已种，财务链标准岗位；不新增岗位）；
--   · **一律复核**，不按超额比例/绝对额分级：`over_credit_limit` 已是布尔判定，分级要多维护
--     一套阈值、且会放行「额度 100 万超 1 万」这类本该走「调额度」的单；金额维度的升级由
--     原有三档（< 1 万部门主管 / 1–10 万采购经理 / ≥ 10 万采购经理+总经理会签）承担 ——
--     超限 + 大额 = 财务 + 会签，天然是二维升级，不需要第三套阈值；
--   · **不做「临时提额白名单」**：单据级白名单 = 把内控开关交给采购员，等于额度失效。
--     紧急采购的正路是「调供应商额度」（主数据权限控制 + 每单 `credit_limit_snapshot`
--     冻结当时额度 ⇒ 调完之后历史单仍显示当时的判定，审计可追）；
--   · 复核节点 **空审批人兜底超管**（`FALLBACK_ADMIN`），绝不 SKIP —— SKIP 等于
--     「没人可派就自动通过」，超限控制静默失效；
--   · 复核超时 8 小时只 **REMIND**（不自动通过），提前 2 小时提醒。
--
-- ── 为什么是「前置」而不是「金额分级之后」 ─────────────────────────────
--   ① 前置只需**一个新插入点**（e_start 改向 + 3 条边），后置要把三个金额档位的出边全部
--      改向，图更大、改一次要改三处；
--   ② 后置汇聚在引擎结构校验里**根本立不住**：三个档位分别来自 c_low / c_mid 两个不同的
--      条件网关，R8「禁止混流汇聚」直接拒（本卡实测，见 docs/evidence/20261104-p22b-credit-branch/
--      bad-topology-issues.json：`汇聚节点 c_credit2 的入边来自不同分支网关（n_board ← c_mid,
--      n_dept ← c_low, n_pm ← c_mid）`）；
--   ③ 财务先看，业务后批：额度风险在「业务还没背书」时就由财务定量（避免锚定在「采购经理已批」上），
--      且财务驳回时不会白烧一轮业务审批；机制上制单人 ≠ 复核人（`purchase_bridge::guard_self_approval`）。
--
-- ── 顺带修掉的引擎缺陷（本卡唯一一处代码改动）──────────────────────────
--   `flow::graph::nearest_upstream_fork` 只往**上游**找网关，入边**直接来自网关**时返 None，
--   于是 R8 把「一支加了一道审批、另一支直过再汇合」（BPMN 最常见的写法）判成
--   「入边 c_low 上游没有分支网关」假阳性 —— 该函数现在先认 `from_key` 自身。附单测
--   `r8_allows_a_bypass_branch_rejoining_the_fork_itself`（AND 汇聚仍必须被拦）。
--
-- ── 为什么用迁移发布、而不是「只在设计器里点」──────────────────────────
--   本卡的验收要求「新版本已发布 + 真机跑通」，而**新部署/新租户**没有任何人点过设计器。
--   所以 v2 的图在这里以**种子**形态落库（固定 UUID、幂等、带自检），与 V0182 种 v1 同一套

--   v1 上的审批单按各自版本的快照继续跑完，不会被这次发布改道。
