# 统一收货过账 / 作废的加锁顺序（消除 40P01）— P2

- 卡：`t_d47a1b2b`【ERP-P2】统一收货过账 / 作废的加锁顺序（避免 40P01 死锁）
- 来源：`t_2624e527`（DC-03，`82b19e1`）交付时登记的已知限制 —— 过账与作废两条路径加锁顺序相反
- 基线：`8b88cf5`（DC-09 补口后 origin/main）
- 提交：`40646ea`（3 文件，+463/−5；推送后 `origin/main == 40646ea`）
- 方案：**卡面方案 1「统一顺序」**（先量再动：改前 20/20 轮各被判一次死锁，改后 0 次）
- 结论：作废路径把**采购单头 `FOR UPDATE` 提到库存冲减之前**，全序统一为
  `收货单头 → 采购单头 → 库存行`；并发用例 20 轮死锁数 **20 → 0**；全量套件零回归。

## 1. 问题（改前实测，不是推断）

两条路径处理**同一物料 + 同一仓库 + 同一张采购单**时构成环：

```text
过账 post_in_tx : ①收货单头 FOR UPDATE → ①b 采购单头 FOR UPDATE → ③库存行
作废 cancel_in_tx: ①收货单头 FOR UPDATE → ③库存行(reverse_cost) → … → ⑥采购单头 FOR UPDATE
                                                            ↑ sync_purchase_status 才锁
```

- 过账持**采购单行**等**库存行**；作废持**库存行**等**采购单行** ⇒ PG 在 `deadlock_timeout`（默认 1s）内判 `40P01`，
  中止其中一笔（**整笔回滚、可重试、不留半笔账**），但用户看到的是 `500 服务器内部错误`
  （`DbError::Deadlock` → `utils::db_error` → 500 脱敏文案）。

> 关键前提：两条单必须挂在**同一张采购单**上。挂在不同采购单上时 B 等的采购单行 A 并不持有，
> 只是普通等待、不构成环 —— 这一点决定了并发用例怎么造，见 §3。

## 2. 改了什么

| 文件 | 改动 |
|---|---|
| `backend/src/business/erp/stockin_handler.rs` | `cancel_in_tx` 在「六本账回滚」块开头新增 **⓪ 锁采购单头**（`stockin_model::lock_purchase_order`，`FOR UPDATE`），位置在 `cancel_plan_of` / `void_serials_of` / `reverse_cost` **之前**。来源采购单已被软删时只打 `warn!` 并继续（维持原口径：`sync_purchase_status` 查不到单返回 0，不新增失败分支） |
| `backend/src/business/erp/stockin_handler.rs` | 新增并发回归用例 `stockin_handler::tests::lockorder_concurrent_post_and_cancel_no_deadlock`（+ 两个探针 helper `waiting_locks` / `wait_waiters` / `deadlocks_detected`） |
| `backend/src/business/erp/stockin_purchase.rs` | `lock_purchase_order` 的「⚠️ 已知取舍（锁顺序）」段落改写为**已收口的全序约定** + 一条给后来者的红线（「采购单头的 `FOR UPDATE` 必须始终早于第一次碰 `biz_inventory`」） |

### 为什么不会削弱任何互斥力

- `sync_purchase_status` 稍后再 `SELECT … FOR UPDATE` 同一行时，是**同一事务的重入**（不再产生等待）；
- 「并发取消采购单」「另一张收货单过账」照样要等本事务结束 —— 与 DC-03 的语义完全一致；
- 代价只是**持锁时间**从「作废尾部」变成「作废全程」：毫秒级（作废本身就在同一事务里做完
  计划测算 / 序列号退回 / 库存冲减 / 红字凭证 / 应付作废）。

### 没动的部分（卡面约束）

- 状态机 DDL / 合法边：未动；
- `POSTED_RECEIVED_SQL` 口径：未动；
- 建单期校验：未动；
- 作废的业务结果（六本账回滚、红字凭证、应付作废、序列号软删、已收数量回退）**一行逻辑没改**，
  只是把「锁采购单头」这一步从尾部提到头部。

### 顺带确认：作废路径原来也没有「库存 → 采购单」之外的环

- `voucher::reverse_for_stock_in` / `payable::cancel_for_stock_in` 锁的是**本单**的凭证 / 应付行，
  与另一张单不同的行，不参与这条环；
- `biz_seq`（凭证蓝/红号段）两边取的是**不同 `seq_type`** 的行，不共享。

## 3. 并发用例怎么造（为什么第一版 20 轮一次都撞不上）

**自然并发不可靠**：`tokio::spawn` 两个任务 + 递增延迟（0.2ms → 7.8ms）跑 20 轮，
`pg_stat_database.deadlocks` 增量 **= 0**，两边都成功 —— 窗口太窄，且这套测试池
（`ensure_db` 把 `max_lifetime` 设成 0，每次查询都新建连接）里
`tokio::time::sleep(1ms)` 实测被连接握手拖到 **37ms** 才醒，靠睡固定时长根本对不齐。

**改成用库里的行锁当红绿灯**（确定性交错，20/20 复现）：

```text
①测试事务 inv_hold：SELECT … FROM biz_inventory(物料A×仓库×未分配库位) FOR UPDATE
②起 B（作废）：轮询 pg_locks 直到出现「等待中」的锁  ⇒ B 已走到 reverse_cost、卡在库存行
③起 A（过账）：轮询直到等待数 ≥ 2                    ⇒ A 也落到锁上
④inv_hold 提交（松手）
   · 改前：B 排在前面先拿到库存行 → 走到 sync_purchase_status 要采购单行（A 持着）
           而 A 还在等库存行（B 持着） ⇒ 环闭合 ⇒ PG 判 40P01
   · 改后：B 早在第 3 条 SQL 就锁了采购单头 ⇒ A 只能排在采购单锁上 ⇒ 无环
```

两个实测坑（都写进用例注释了，免得下一张卡重踩）：

1. **`FOR UPDATE` 没有争用时不会在 `pg_locks` 留 `locktype='tuple'` 行**（只有关系级 `RowShareLock`）
   ⇒ 「谁持有」不可靠，「谁在等」才可靠；
2. 等一把被 `UPDATE` 占住的行锁时，PG 记的是 **`locktype='transactionid'`（`relation` 为空）**
   ⇒ 探针**不能**按表名过滤 —— 第一版按 `relname` 过滤，20 轮全部漏判。

- B 走 `cancel_after_approval`（= 审批回调 `on_cancel_settled` 内部调的那个函数，
  `stockin_bridge.rs:178`），一个事务、一字不差；不走 `engine::approve` 的编排
  （那几笔查询与业务行锁无关，只会把两边起跑线拉开十几毫秒）；
- 每轮单据独立：采购单 200 → 先过账 60（作废对象 victim）+ 再建 40（过账对象 poster，仍 DRAFT）。

## 7. 已知残留与决策

- **方案 3（`40P01` → `409 + 并发冲突，请重试`）本卡未采纳**：它是「不统一顺序、只把报错翻译得好看」，
  卡面把它列为备选。统一顺序后这条环消失，用例断言的是「死锁 0 次」而不是「翻成 409」。
- 残留风险：若**将来**又出现别的环（新加一条「先库存行、后采购单头」的路径），
  `DbError::Deadlock` 仍会经 `utils::db_error` 走 `500「服务器内部错误」`（`internal_detail` 里有
  `deadlock detected`）。这类通用收口影响面是**整个 ERP 的写路径**（不只收货），属独立专项，
  需要单独立卡评估文案与前端提示管道，本卡不夹带。
- 数据侧：本卡只改**加锁顺序**，不改任何账务结果 ⇒ **无存量数据需要修复**；
  生产 144 上此前的 40P01 现场（若有）都已整笔回滚，不会留半笔账。
- 前端：无改动（死锁消失后不再触发 500；正常路径报文一字未改）。
