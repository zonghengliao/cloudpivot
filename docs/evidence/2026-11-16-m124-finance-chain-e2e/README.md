## 1. 为什么还要一张 E2E 卡

M1 的 23 张卡各自钉住了自己那一段（M1-10 多币种链、M1-17 底稿链、M1-22 账龄链），但没有一条用例
把三段放在**同一个库、同一个实例**上跑一遍。单卡全绿仍可能出问题的地方正是跨域那一层：

| 跨域失效方式 | 后果 | 本卡怎么挡 |
|:--|:--|:--|
| 调汇凭证把外币原币口径污染（余额表 / 明细账 / 报表各算各的尺子） | 原币从 1000 变 1500，账龄/报表与总账永久对不上 | ⑤ 三处逐位对拍 + 反证 D3① |
| 底稿期初与上期货币资金不同源 | 现金流量表与资产负债表永久差一笔 | ⑥ 三处对拍（上期期末 → 本期期初 → 本月现金变动） |
| 应付账龄与应收账龄档位表分家（M1-21 之前就是 5 档 vs 7 档） | 同一张表两种刻度，看的人以为数据错了 | ⑩ 两份出参 `buckets[]` 逐字相同 |
| 账龄用「应收金额」而不是「未收余额」 | 收了一半的单虚增欠款 | ⑧ 1000 收 300 只出 700，整笔落自身档位 |
| 迁移只验证「应用成功」不看自检 | 自检块失效也照样起服务 | 环境段逐条断言 V0405..V0418 的 NOTICE 自检 |

## 6. 诚实说明（本次没做 / 已知边界）

1. **没有代码级变异反证**。M1-17 用的是「改坏源码 → 编译 → 跑红 → 还原」，本卡只做了 §5 的
   **数据级**反证。理由：M1-24 零业务改动，且仓库是多 worker 共用的同一工作区，临时改源码再
   `git checkout` 有被别人 `commit -a` 卷走的风险。若要代码级反证，建议另开卡在独立 worktree 里做。
2. **应付账龄的写侧没进链**（原因见 §2 的引用块）：应付单只能由采购入库过账产生，本卡只验读侧。
3. **底稿与总账之间没有「强制勾稽闸」**。本卡把底稿期初 / 期末 / 净增加额做到与总账逐位相等，
   是靠**夹具设计**（V3 那笔 200 现金流入）实现的；产品侧出表闸只校验底稿内部闭合
   （`balanced` + `arithmetic_ok`），**不会**阻断「底稿期末 ≠ 总账货币资金」的出表。
   这是 M1 范围内的已知边界（是否要加这道闸是产品决策，不在本卡范围），在此显式记录。
4. 演练库清过 `admin.must_change_password`（只为跑通接口链路）；生产环境不许这么干。
5. 账龄夹具年份 1997-12 ~ 1998-03 是「全库最早年度」策略，避免与其它卡的夹具年度撞车；
   模板库 2026 年以后的既有单据靠 `period_code <= 基准期间` 被截断，所以断言是绝对值。
