# DC-01 审批流「未配置即直接生效」改为默认拒绝 — 代码、迁移与验收证据

- 卡：`t_4130a770`【ERP-P0】审批流未配置时的「静默降级」改为显式 409 + 流程配置自检
- 来源：ARCH-3 审计 §5 **DC-01**（P0）/ §6 R-P0-2
- 基线：`82b19e1`（DC-03 过账复核来源采购单）
- 结论：审计实测的 **6 处**静默降级全部改为**默认拒绝**（`409 + APPROVAL_FLOW_NOT_CONFIGURED` / 66033，
  报文点名缺哪个 `flow_code`）；新增**显式跳过**（权限码 `business:erp:skip-approval` + 理由 ≥10 字 +
  写 `biz_status_log`）；新增**自检端点** `GET /business/erp/approval-flow/health`
  （8 个 `biz_type` 逐个返回发布状态 / 版本号 / 图形校验结果，复用 `flow::graph` 的校验函数）。
  配套迁移 `V0202` 把 2 个权限码种进 `sys_menu` 并自检 8 个流程是否都已发布。

## 1. 病灶（审计原文逐条复核）

`git grep -n "降级" -- backend/src` 复核后，6 处「审批流未配置 → 直接生效」的位置与卡面一致：

| # | 位置（改造前） | 当时的动作 | 只留下的痕迹 |
|---|---|---|---|
| 1 | `purchase_handler.rs::submit_approval`（原 :984） | 采购单 `DRAFT → SUBMITTED`，**没有审批单** | 一条 `tracing::warn!` |
| 2 | `stockin_handler.rs::submit_post`（原 :2136） | 收货单直接过账（三本账 + 凭证 + 应付一起动） | 同上 |
| 3 | `stockin_handler.rs::change_stock_in_status`（原 :1486） | 已过账收货单直接作废（六本账立即回滚） | 同上 |
| 4 | `payable_payment.rs::submit_payment`（原 :1186） | 应付直接付款（出付款凭证） | 同上 |
| 5 | `payable_payment.rs::submit_cancel`（原 :1970） | 应付直接作废（联动红冲凭证） | 同上 |
| 6 | `voucher_write.rs::submit_reverse`（原 :663） | 凭证直接红冲 | 同上 |

为什么这是 P0：同一次点击，**配置齐全的客户走两道复核、没配流程的客户一个人说了算**，
而界面上完全看不出差别 —— 内控的价值恰恰在「不配置时业务走不通」，默认放行等于

### 判据矩阵（唯一入口 `authorize_missing_flow`）

```text
有已发布流程 ──→ 走审批（行为不变）；若同时请求 skip_approval → 400（不许绕过已配置的内控）
没有已发布流程 ─┬─→ 没请求 skip_approval                  → 409 + 66033（点名 flow_code）
                ├─→ 请求了但没有 business:erp:skip-approval → 403（跳过审批不能自助开启）
                ├─→ 有权限但理由 < 10 字                  → 400（理由要进 biz_status_log 供审计追溯）
                └─→ 有权限 + 理由齐全                     → 放行，理由写进 biz_status_log
```

六处入口只是调用点，判据只有一份 —— 与 P10 铁律③「状态变更只有一个入口」同一个理由。

### 权限码为什么**不**按老码矩阵批量授予

`V0192` 的做法是「凡是持有老码的角色一律补上新码」。本次**反其道**：
`business:erp:skip-approval` 等于「谁可以不经复核让单据生效」，是内控例外，
**默认只给 SUPER_ADMIN**，由管理员按单据类型、按角色逐个开（与卡面的风险提示一致）。
`V0202` 的头注释写清了这一点，避免后续卡「顺手按矩阵补齐」。

## 3. 报文（逐字，HTTP 实测）

```text
# 409 + 66033（没配流程、也没请求跳过）
没有配置已发布的审批流程 `po_approve`（业务类型 PO_APPROVE）：为避免「没有审批就直接生效」，本次操作已被拒绝。
两条出路：① 让管理员在「审批配置」里发布 `po_approve`；② 如果这类单据暂时不走审批，请给对应角色授予
`business:erp:skip-approval`，并在请求里显式传 skip_approval=true + skip_reason（≥10 字）

# 403 + 30001（请求了跳过但没有权限码）
跳过审批需要权限码 `business:erp:skip-approval`（当前账号未持有）：「跳过审批」意味着这次单据不经复核直接生效，
属内控例外，只能由管理员在「系统管理 · 菜单权限」里授予，不能自助开启

# 400 + 10001（有权限但理由不足）
跳过审批必须写清理由（≥10 字，当前 3 字）：理由会写进单据状态日志（biz_status_log），
财务 / 审计据此追溯「为什么这一次没有复核」——不写理由的跳过等于没有复核记录

# 400 + 10001（有已发布流程时请求跳过）
审批流程 `po_approve` 已发布：有流程时必须走审批，不能跳过。如果这类单据确实不该审批，
请先让管理员**下线**该流程（配置变更要留痕），再在请求里显式传 skip_approval + skip_reason
```

## 4. 自检端点

`GET /business/erp/approval-flow/health`（权限码 `business:erp:approval-flow:health`）

逐项返回：`biz_type` / `flow_code` / `published`（是否有已发布版本）/ `version_no`（当前版本号）/
`has_snapshot` / `graph_ok`（图形校验）/ `graph_issues`（R1–R21 的不通过项）/ `def_status`（能区分「停用」与「从来没有」）。

### 7.1 顺带发现（**不在本卡范围**，已另开卡）

- **种子 `po_approve` 的 `n_creator` 节点 `empty_assignee=SKIP` ⇒ 提交即自动批**：
  「流程已发布、但第一个节点没人可派」被引擎当成「跳过该节点」处理，采购单 `DRAFT → SUBMITTED`
  会在同一事务里直接走到 `APPROVED`。这不是本卡的「未配置流程」问题（流程是配置了的），
  而是**流程种子/引擎语义**的问题：一个人可以在没有任何人看过的情况下把单据批掉。
  证据：`scripts/verify/d4_po_to_stockin.sh` 在 DC-03 交付时正是被这一点打红（48/1）。
  处置：本卡只把 d4 改成「显式跳过审批」绕过审批层（断言口径未改，见 §6.4），
  问题本身另开卡（**不是** DC-01 的 6 处之一，审计 §5 也未列）。

## 8. 发布说明（可直接贴到变更公告）

> **【重要】审批流未配置时不再「直接生效」**
>
> 从本版本起，采购单提交审批、收货单过账、收货单作废、应付付款、应付作废、凭证红冲这 6 个动作，
> **如果对应的审批流程没有已发布版本，请求会被拒绝（409，错误码 66033）**，报文里会点名缺哪个流程。
> 以前这种情况是「没有审批就直接生效」，只留一行日志。
>
> **上线前请确认 8 个审批流程都已发布**：`GET /api/business/erp/approval-flow/health`
> 返回 `unhealthy: 0` 即正常；也可以直接看「流程定义」页里这 8 个流程的状态：
> `po_approve` / `stock_in_post` / `stock_in_cancel` / `payable_pay` / `payable_cancel` /
> `voucher_reverse` / `stock_transfer` / `task_accept`。
>
> **如果某个单据类型暂时不审批**：请把权限码 `business:erp:skip-approval` 授予对应角色
> （系统管理 · 菜单权限 · 流程定义 → 跳过审批），然后调用方在请求体里显式带上
> `{"skip_approval": true, "skip_reason": "<至少 10 个字的原因>"}`；原因会写进单据状态日志，
> 财务与审计可以按「跳过审批」检索到每一次例外。**该权限码默认只给超级管理员**。
