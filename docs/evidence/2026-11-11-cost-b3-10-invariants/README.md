## 1. 做了什么

`erp_invariants.py --group 成本` 新增 8 条检查（6 个编号，C-COST-2 与 C-COST-4 各拆两个子判据）：

| 编号 | 级别 | 判据 |
|---|---|---|
| `C-COST-0` | INFO | 表存在 / 有已结算批次（没有就整组跳过，不算通过也不报警） |
| `C-COST-1` | BLOCKER | 池（**池行 + 直接行**） = `4101.*` 借方发生额，逐 (期间, 车间, 科目) 组对平 —— 卡面「4101 对账」 |
| `C-COST-2` | BLOCKER | `Σ 生产入库金额` = 完工凭证借 `1405` = `Σ 计算单完工成本`，且凭证自身借贷平衡 —— 卡面「凭证平衡」 |
| `C-COST-2·账` | BLOCKER | 完工入库单 ↔ 库存三本账（库存表 / 库位账 / 流水）数量金额同源 —— 卡面「三本账一致」 |
| `C-COST-3` | BLOCKER | `4001.01+.02+.03` 余额 = `Σ(每对象最新已结算批次期末在制)` + 在途未结转（全库余额版） |
| `C-COST-4①` | BLOCKER | 每个 (期间, 车间, 科目) 的 `4101.*` 结算后借贷相等（池清零） |
| `C-COST-4②` | BLOCKER | `Σ biz_cost_alloc_result.alloc_amount` = `Σ 池行`（分摊守恒 / 无漏摊） |
| `C-COST-5` | WARN | 料归集完整（漏归集 / 孤儿归集 / 金额不符，逐行双向） |
| `C-COST-6` | BLOCKER | 每张计算单 `完工 + 期末在制 = 期初 + 料 + 工 + 费` |

### 判据范围为什么收口到「已结算批次所属期间」

成本核算是两阶段的：领料 / 折旧 / 报销在**上游过账**时就写了分录，而人工计提、手工台账、费用结转、
完工结转这四张凭证是**结算事务内**才生成的。所以正在做账的期间天然存在「账上已借 4001.01、
台账凭证还没发」的中间态 —— 拿它对账必假红。已红冲（REVERSED）未重结的期间同理不判。
库里没有任何 `SETTLED/CLOSED` 批次时整组 INFO 跳过。

### C-COST-1 为什么取「池行 + 直接行」

设计 §4.7.3 明确写了这条接口：`biz_cost_collect` 里 `element='OVERHEAD'` 的行有两类 ——
`cost_object_id IS NULL` 的池行（参与分摊）和挂了对象的**直接行**（不参与分摊，但它的 4101 借方
同样真实存在、同样靠分摊凭证清零）。只取池行会在「手工台账挂了成本对象」的期间恒差一笔
（差额 = 直接行金额）。自测夹具的第二个期间就是专门造的直接行场景（`CS-280512-0001`），
它在这条判据下必须绿 —— 这条正是本次「零误报」验收的关键。

### C-COST-3 为什么需要「在途」项

设计原文「`Σ wip_end_cost`（最新已结算批次）= 4001 期末余额」落到全库判据上，必须补在途，
否则「本月已领料、批次还没结算」这种正常状态会天天红。在途两段（互斥、不重复计）：

1. **已归集未结转**：`element='MATERIAL'` 且该 (成本对象, 期间) 没有已结算批次；
2. **已过账未归集**：挂了成本对象的已过账领料行，calc 还没跑、还没有归集行。

自测第 [2] 步（在途闸：已归集 190 + 未归集 190）就是证明这条不假红。

第 [2b] 步更进一步：把批次 A 的四张凭证**全部红冲**、批次置 `REVERSED`、入库单置 `CANCELLED`
（红冲后还没来得及重结的常见中间态）—— 此时领料凭证**不**随结算红冲（它来自出库单过账），
`4001.01` 仍挂 19000，正好由在途项解释成 19000，巡检仍全绿。

## 4. 已知偏差（卡内报备）

1. **判据范围收口到已结算期间**（见 §1）。不这么做，「正在做账的期间」每次都会假红；
   未结算期间的合理性由 C-COST-3 的在途项解释。这是设计 §4.11 未写明、但不收口就无法「零误报」的一处口径细化。
2. **C-COST-5 用逐行双向对账，而不是设计原文的单个金额合计**。逐行等价于「合计相等」，
   但能直接点到出库单行（设计原则 2：不给定位的检查等于没查）。
3. **C-COST-2 多拆一个 `C-COST-2·账`**：卡面验收要求「三本账一致」，而设计 §4.11 的 C-COST-2
   只写账账（入库 = 凭证）。三本账判据放这里最贴：完工入库是成本模块唯一动库存的出口。
4. **C-COST-3 的「在途」两段是我的口径补充**（设计只写余额等式）。理由与判据见 §1；
   在途项不算差错，会在巡检输出的「覆盖」行里照实打印（本次实测：已归集 0 + 未归集 0 = 0）。
5. **没有 Rust 改动** ⇒ 卡面「后端改动必须带 `#[cfg(test)] mod tests`、cargo test 全绿」不适用；
   巡检判据的「单测」形态就是本自测脚本的 8 个造错场景（比 Rust 单测更贴近真实账）。
   静态同步闸（脚本第 [0] 步）替代了「代码常量 ↔ 巡检常量」的 Rust 侧钉死。
6. **没有迁移** ⇒ 卡面「迁移幂等 + `.down.sql`」不适用（`git status backend/migrations` 零行）。
7. **没有前端改动** ⇒ `pnpm typecheck/build` 不适用（本卡不碰前端）。
8. 单卡耗时约 2h20m（超 1.5h）：大头是手写「内部自洽的最小成本数据集」（七张凭证 +
   库存三本账 + 分摊结果 + 两个期间）并让它逐项对平 —— 这是「造错报红 / 零误报」唯一真实的验法，
   不是范围膨胀。
