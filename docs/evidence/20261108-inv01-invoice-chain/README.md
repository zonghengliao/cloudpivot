## 2. 重点验证

### 2.1 税率标度（FIX-6 统一成百分数后，发票也对）

| 场景 | 入参 | 落库 `tax_rate` / `tax_rate_mode` | 税额 | 判定 |
|---|---|---|---|---|
| 新前端显式百分数 | `tax_rate=13, mode=PERCENT` | `13.0000` / `PERCENT` | 2260 → 260 | ✅ |
| 9% | `tax_rate=9` | `9.0000` / `PERCENT` | 10900 → 900 | ✅ |
| 6% | `tax_rate=6` | `6.0000` / `PERCENT` | 1060 → 60 | ✅ |
| 0%（免税） | `tax_rate=0` | `0.0000` / `PERCENT` | 500 → 0，凭证**不出** `2221.02` 行 | ✅ |
| 1%（显式百分数） | `tax_rate=1, mode=PERCENT` | `1.0000` / `PERCENT` | 1010 → 10 | ✅ |
| 老前端小数（过渡期） | `tax_rate=0.13`（不声明 mode） | `13.0000` / **`DECIMAL`** | 1130 → 130（按 13%） | ✅ ×100 生效，日志打 WARN |
| 越界 | `tax_rate=100.01` / 负数 | 拒绝 | — | ✅ 400（`validate_tax_rate`） |
| **显式 PERCENT + 0.13** | `tax_rate=0.13, mode=PERCENT` | `0.1300` / `PERCENT` | 1130 → **1.4671**（0.13%） | ⚠️ **F2**：模块文档说该场景 400，实测 200 |

> 结论：**发票侧的税率标度与订单 / 收货同口径（百分数）**，`tax_rate_mode` 审计位也落了；
> 唯一的坑是「显式声明 PERCENT 却传小数」这条，实现放行、文档说拦（差 ~88 倍税额），见 F2。

### 2.2 价税分离（不含税 = 含税 / (1 + 税率)）

| 含税 | 税率 | 实测不含税 | 实测税额 | 校验 |
|---|---|---|---|---|
| 2260.00 | 13% | 2000.0000 | 260.0000 | ✅ `2260/1.13` |
| 3390.00 | 13% | 3000.0000 | 390.0000 | ✅ |
| 10900.00 | 9% | 10000.0000 | 900.0000 | ✅ `10900/1.09` |
| 1060.00 | 6% | 1000.0000 | 60.0000 | ✅ |
| 500.00 | 0% | 500.0000 | 0.0000 | ✅ 免税不清算 |
| 1000.00 | 13%（指向不存在订单） | 884.9558 | 115.0442 | ✅ 尾差进不含税，`合计 ≡ 不含税 + 税` |

全库抽样 `Σ(amount + tax_amount − total_with_tax) = 0.0000` ✅。

## 3. 税会差异与报表取数（口径说明）

### 3.1 三方勾稽（`raw/s13_*`）

```
总账 1122 净额（POSTED）= 2760.0000 = 已开票价税合计（2260 + 500）
应收台账（OPEN）        = 5650.0000
  其中 已开票           = 2260.0000
  其中 未开票（出库已挂账、总账 1122 尚未记账）= 3390.0000
从应收开的票合计 2260 ≤ 应收金额 5650 ✅
发票号无重复（count - count(distinct) = 0）✅
```

⚠️ **口径提醒**：本仓按 ARCH-7 SO-22「开票时确认收入」，所以**出库挂应收 5650 时总账不动 1122**，
1122 只在开票时借记。⇒ `biz_receivable` 台账与总账 1122 在「已出库未开票」期间**必然不相等**（差 3390）。
这不是本卡要修的 bug（是设计口径），但如果对账报表拿 1122 直接对 `biz_receivable`，会天天报差 ——
建议在对账口径里显式加「未开票应收」这一项（见 F5 建议）。

### 3.2 应交税费的取数

- 报表项 `TAXES_PAYABLE` 的 `account_pattern = 2221`（包含 `2221.01` 进项 / `2221.02` 销项两个叶子）
- 净额 = `Σ(credit − debit)`；为负 ⇒ 留抵 ⇒ 重分类
- 与库层直算完全一致（三个时点都比对过，见 §2.4）

### 3.3 利润表 / 现金流量表

- 利润表 `TAX_SURCHARGE`（pattern `5403`）本期 **100.0000**
- 现金流量表 `OPER_TAX_PAYMENTS`（pattern `2221,5801,5403`）本期 **150.0000**，`accounts = [2221.02]`
  （简化版现金流量表按「现金科目 1001/1002 的对方科目」自动分类，不需要人工指定现金流量项目）

### 3.4 「进项税额 = 采购发票」的口径差异

本仓**没有「进项发票」单据**：`biz_invoice` 只承载销项（`OUT` / `OUT_RED`，红字票由退货流程生成，
手工建红字票 400 已被拦）。进项税随**采购入库过账**产生（`voucher::stock_in` 借 `2221.01`）。
⇒ 卡面 ④「进项税额 = 采购发票」在本仓应理解为「进项税额 = 采购入库过账产生的 `2221.01`」；
如果业务要按票管进项（发票号、认证、抵扣勾选），需要新增采购发票单据（不在本卡范围）。

## 5. 本轮修复（F1，1 个文件）

**文件**：`backend/src/business/erp/invoice.rs`

**改法**：
1. 新增纯逻辑 `pub fn surviving_pointer(candidates, exclude) -> Option<&PointerCandidate>`：
   在同一应收的候选票里挑「**已开票（ISSUED / POSTED）**、排除刚作废那张、按（开票日, 创建时间）最新」的一张。
   `DRAFT` / `VOID` 不算（前者没开票、后者凭证已红冲）。
2. 新增 `restore_receivable_pointer(...)`：`VOID` 分支在 `clear_receivable_writeback` 之后调用，
   把 `invoice_no / invoice_date / voucher_id` 三个拷贝列改指选出的那张；
   `UPDATE … WHERE id = ? AND invoice_no IS NULL` —— **只在指针确实被本次作废清空时才回填**，
   不覆盖别人写的号；没有可指的票就保持清空（与改造前一致）。
3. 单测 `surviving_pointer_skips_void_and_draft`：钉住「跳过 VOID/DRAFT」「同日取创建时间更晚的那张」「刚作废那张不会被自己选回来」。

**为什么必须修**：撤号只该撤掉**作废那张**。原实现把指针整个清空，导致
(a) 一张「开了 2260 / 还差 3390」的应收在界面显示「未开票」（审计看不清已开票情况）；
(b) `receivable::cancel_for_stock_out` 靠 `voucher_id IS NOT NULL` 判断「这条应收已有收入凭证，取消出库时要一起红冲」——指针被清成 NULL 后，
出库作废会**漏冲 1122**，总账上留下一笔没有业务对应物的应收账款。
