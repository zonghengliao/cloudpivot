## 4. 与 W0 设计（`docs/ERP-仓库管理-技术架构.md` §2.5 / 架构师草稿 V0138）的 6 处差异

卡面是契约源（`business/erp/dto.rs`、注解、前端都按卡面写），所以**按卡面落地**，差异记账如下：

| # | 卡面（本卡落地） | W0 / 架构师草稿 | 取舍 |
|---|------------------|-----------------|------|
| 1 | `external_sn` 在 `biz_material`（物料级厂商序列号） | 在 `biz_material_serial`（单品外部码，唯一） | 按卡面；单品级厂商码若需要，属 W2b 的加列/加表 |
| 2 | `serial_required BOOLEAN NOT NULL DEFAULT FALSE` | `SMALLINT 0/1` | 按卡面 —— 仓内 `dto.rs` 已是 `Option<bool>` |
| 3 | 3 态 `IN_STOCK/OUTBOUND/SCRAPPED` | 4 态（多 `TRANSIT` 在途） | 按卡面；在途属 V0139 调拨域，不预埋（加状态 = 重建 CHECK） |
| 4 | 有 `deleted_at`，唯一索引带 `WHERE deleted_at IS NULL`（软删可重用号） | 声明「单品身份永久、无软删」 | 按卡面（卡面验收⑥ 就是「软删后可重用号」） |
| 5 | `location_id REFERENCES biz_inventory_location(id)`（硬外键） | 弱引用 `biz_location.id` | 按卡面；代价：库位库存行被序列号引用时删不掉 |
| 6 | 卡面没要 `biz_seq` 取号规则 | 草稿 §3 种 `biz_seq(seq_type='SN')` | **按 W0 补种**（幂等）：`SN-yyyyMMdd-6位` 必须由 `biz_seq` 原子取号，否则 W2b 无号可取 |

状态机 `IN_STOCK → OUTBOUND → SCRAPPED`（不可逆）**不在 DB 层拦**：DB 只拦「非法枚举值」，
「合法值之间的非法跳转」需要读旧行，属写路径规则，由 W2b 的 model 层保证（本卡红线：不加业务代码）。

## 5. 已知债务（写给 W2b / 评审，不掩盖）

1. **V0137 §5.9 的 `serial_required <> 1` 在 BOOLEAN 列上会报错**（PG 18.6 实测：
   `ERROR: operator does not exist: boolean <> integer`）。它只在**重放 V0137 up**（库里已有本迁移的 BOOLEAN 列）时才会执行，
   正常路径（V0137 先于 V0138）永远走「列不存在 → 跳过」分支，所以线上不受影响。
   **不要**为此改 V0137（checksum 一变，已有库全部启动失败）；将来真要重放 V0137，把那一句改成
   `serial_required IS DISTINCT FROM TRUE` 即可。
2. **硬外键让回滚顺序变成硬要求**：`biz_material_serial` 引用 `biz_material` / `biz_warehouse` / `biz_inventory_location`，
   所以回滚必须先 V0138、后 V0137（迁移器按版本逆序，天然满足）。手工只回滚 V0137 会被 PG 的依赖保护挡住
   （安全失败，不会静默丢数据）。
3. **dev 库会被自动种上**：`/opt/cloudpivot` 的 dev 实例是 `cargo-watch -w migrations` 起的（8024），
   本迁移文件落到共享工作区后 dev 会自动重启并应用 → **`cloudpivot_dev` 已有 `biz_material_serial` 与
   `schema_migrations(version=138)`**（实测 `dev health=200`）。prod（8023）不动：不重启不应用，
   且本卡没碰 release 二进制。
4. **乱序补迁 WARN**：V0141（W1c）先于本迁移落地，启动日志会出现一条「待应用迁移的版本低于已应用最大值（乱序补迁）」，
   不阻断；应用成功后重启即「应用 0 个迁移」（本次验收② 已实证）。
