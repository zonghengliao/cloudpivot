判据在 SQL 里是「四条件 + 形状复核 + 无引用」三层：

1. **四条件**：`source_type='PRODUCE'` ∧ `source_id IS NULL` ∧ `create_by=henry.liao.id`
   ∧ `created_at ∈ [2026-10-31 16:17:00+08, 16:18:00+08)`；
2. **形状复核**：命中的行必须同时是 `M-W1A-004 / WH01 / IN_STOCK / location_id IS NULL / 号段 SN-20261031-000011~000020`，
   一条不符就 `RAISE EXCEPTION`；
3. **无引用**：`biz_stock_transfer_item_serial.serial_id` 有引用就停（那说明这批号进过调拨单，应走单据作废）；
4. **硬行数**：命中总数（含已软删）必须**恰好 10**；存活数只允许 10（首跑）或 0（已清，幂等跳过），
   其它值一律抛异常停下让人查。

## 3. 三个必须先查库、不能照卡面硬写的地方（实测结论）

| 卡面写法 | 库里真实约束（`pg_constraint` / `information_schema` 实测） | 落地处理 |
|----------|------------------------------------------------------------|----------|
| `biz_type='PRODUCE_CANCEL'`「如果不在 CHECK 白名单里就换值或加迁移」 | `biz_inventory_txn` **只有 3 条 CHECK**：`ck_biz_inv_txn_type (txn_type IN ('IN','OUT'))`、`ck_biz_inv_txn_qty (qty > 0)`、`ck_biz_inv_txn_amt (amount >= 0)`。**`biz_type` 没有白名单** | 按卡面写 `PRODUCE_CANCEL`，**不需要加迁移**。取值说明：库里既有冲销约定是「原 biz_type + `_CANCEL`」（`PURCHASE_IN_CANCEL`），本批原始流水是 `SERIAL_IN`，字面约定该叫 `SERIAL_IN_CANCEL`；卡面点名 `PRODUCE_CANCEL`（对应序列号 `source_type`），两者都不违约 ⇒ **按卡面**。将来若有人给 `biz_type` 加白名单迁移，必须把这两个值一起放进白名单 |
| 冲销「数量 10」`qty = -10` 之类 | `ck_biz_inv_txn_qty CHECK (qty > 0)` —— **负数直接违约** | 出库写**正数 10**，方向由 `txn_type='OUT'` 表达（与 `PURCHASE_IN_CANCEL` 同款） |

| 金额 0 的流水是否允许 | `ck_biz_inv_txn_amt CHECK (amount >= 0)` ⇒ 0 合法 | `amount=0 / unit_cost=0` 直接写 |
| `period_code` | 库里**没有** `biz_period` 表；会计期间表是 `biz_accounting_period`，`2026-10` 当前 `OPEN` | 按卡面写 `2026-10`（冲销归原期间），无期间闸阻挡 |

## 6. 为什么不动凭证（这是本次唯一「本该有动作但不动」的项）

```
这 10 件的金额是 0.0000（unit_cost=0）
→ biz_voucher 里没有对应这笔的凭证：select count(*) from biz_voucher
     where source_no like '%SN-20261031-000011%'  → 0（修前 0、修后 0，已实测两次）
→ 分录金额 0 无会计意义，原功能（旧代码 batch-generate 不校验 unit_cost）就没生成凭证
→ 所以清理不需要红冲；本次执行**没有向 biz_voucher / biz_voucher_entry 写入任何一行**
   （凭证 9 张 / 分录 25 行，修前修后一致）
若当初意外有凭证 → 按卡面要求**停下报告，不自己红冲**；本卡未触发该分支。
```

推论一致性：`B2 库存金额 = 1405 余额` 修前修后都是 `435.0000 vs 435.0000` —— 因为这次清理动的是
「零金额的库存数量」，不动金额，账实两侧同时不变。

## 7. 为什么「写冲销流水」而不是直接改 qty

* `B4 流水累计 = 当前库存` 的口径是 `Σ(IN) − Σ(OUT) = biz_inventory.qty`。这 10 件是靠
  `IN / SERIAL_IN / SN-20261031-000011` 记进来的；只把 `qty` 抹成 0 会把一条 BLOCKER（B1）
  换成另一条 BLOCKER（B4 报「流水累计 10 ≠ 库存 0」）。
* 冲销流水单独成行 = **原始流水一行不动**（审计不改历史），符合既有作废口径
  （`PURCHASE_IN_CANCEL` 也是这么做的）。
* 库位账本来 0 行 ⇒ 冲销后成本账 0 与库位账 0 相等，B1 因此转绿；不动库位账是对的，
  往里补一行 `-10` 反而会造出负库位（C2）。

## 9. 遗留与建议（不藏）

1. **`doc_type='ADJUST'` / `biz_type='PRODUCE_CANCEL'` 是新取值**：两者都没有 CHECK 约束，
   但前端/台账报表的中文标签映射里可能没有它们 —— 前端若按 `doc_type/biz_type` switch 出标签，
   这条冲销流水在列表里可能显示原始英文值。**不影响账**，如需美化请前端加两条映射（本卡不动前端）。
2. **`biz_type` 白名单**：将来若有人给 `biz_inventory_txn.biz_type` 加 CHECK，必须包含
   `PRODUCE_CANCEL`（本次）与 `SERIAL_IN_CANCEL`（同族命名），否则这条历史流水会让迁移自检失败。
3. **根因在旧代码**：prod 跑的还是旧二进制（`target/release/cloudpivot` mtime 2026-10-31 13:32，
   代码修复 `t_421d8aa1` 已在 main）。**新代码上线后** `batch-generate` 必录 `unit_cost` 且同事务写
   成本账/库位账/凭证，同形态数据不会再产生 —— 但旧二进制**不重启就不会生效**，发布时记得核一次
   `grep -ac "unit_cost" target/release/cloudpivot` 与迁移版本。
4. **同类复发的判据**：若再出现「有货零成本」，先查是不是 `biz_type='SERIAL_IN' AND doc_type='SERIAL_BATCH'`
   + 序列号 `source_id IS NULL` 的批量生成签名（P10 的 `20_residue_report.up.sql` 已做成只读扫描）。
5. **未动的东西**：业务代码（P13 在合并 `lnk-f12`）、`biz_seq` 的 SN 号段（只前进不回退，宁可留空号）、
   21 条 `PURCHASE` 无来源的历史序列号（早已软删）、`biz_period`/`biz_accounting_period` 状态。
