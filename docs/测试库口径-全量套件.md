# 全量 lib 套件的「测试库口径」（后端）

> 卡：`t_13ddcb84`【TEST-DB】
> 适用：`backend/` 的 **lib 单元/真库用例全量**（`cargo test --lib`），即 3000+ 条的那一套。
> 不适用：集成 target（`cargo test --test testd` 等）、前端测试、生产库巡检 —— 见 §6。

## 0. 一句话口径

**后端全量 lib 套件的验收库 = `scripts/verify/make_full_suite_db.sh` 造出来的「全量迁移 + 演示组织种子」库**，
四条连接串（`ERP_DB_URL` / `SYS_DB_URL` / `TASK_DB_URL` / `P0FIX_DB_URL`）**指向同一个库**，
用 `--test-threads=1` 跑，判据是 **`0 failed`**（不许 `--skip`、不许 `--ignored`、「SKIP 了」不算跑过）。

```bash
# 造库（约 20 秒；先删后建，重跑结果一致）
bash scripts/verify/make_full_suite_db.sh            # 默认库名 cloudpivot_test_full

# 验收（约 28 分钟，建议 setsid/nohup 甩到后台，别用会 600s 超时的前台）
export ERP_DB_URL='postgres://alun:<口令>@127.0.0.1:5432/cloudpivot_test_full'
export SYS_DB_URL="$ERP_DB_URL" TASK_DB_URL="$ERP_DB_URL" P0FIX_DB_URL="$ERP_DB_URL"
cd backend && cargo test --lib -- --test-threads=1
```

## 1. 为什么必须把「库」写死成一个口径

同一个提交，`cargo test --lib` 在两种「看起来都干净」的库上红的是**两批完全不同的用例**
（实测，2026-11-08，HEAD `50a9063` 前后）：

| 库 | 长什么样 | 红的是什么 | 根因 |
|---|---|---|---|
| **A. 只有 migrations 的空库** | `createdb` + 起一次实例跑完迁移 | `asset_linkage_tests`（11 条「库里没有部门」）、`expense_linkage_tests`（6 条「库里必须有一名带部门的用户」）、`sales_approval_bridge`（审批人）、`receivable_aging` 等 | **没有演示组织**：`sys_dept` 空、没有部门用户、关键角色（`FINANCE_MANAGER` / `SALES_SUPERVISOR` …）0 成员 ⇒ 单据发起即 `65018 本节点没有有效审批人`，或夹具直接 panic |
| **B. 生产/测试环境快照库**（`cloudpivot_dev` 拷贝等） | 有历史卡 e2e 留下的单据与凭证 | `cash_flow::r3_real_unclassified_is_visible`（「本期间恰好 1 条未分类」实际 2）、`cash_flow::r3_real_statement_ties_to_balance_sheet_cash`、`income_statement::r2_real_*`（「用例前提：基线必须平」差 1000） | **有别人的历史数据**：这几条断言是「恰好 N 条」「基线必须平」，任何历史凭证都会把它们打红 |

⇒ 「干净库」这个词过去只写在 skill 里，没说清**干净到什么程度**：既要**有**演示组织（否则审批链跑不动），
又要**没有任何历史单据**（否则整表/整期口径的断言被别人的数据打红）。本口径就是这两个条件的交集：
**迁移全量 + 产品自带的演示组织种子 + 零业务单据**。

## 2. 种子从哪来（不手写 SQL、不拷贝别人的库）

演示组织用的就是产品自己的「开箱即用」种子，`src/system/setup/model.rs::seed_demo_users`：

* 开关：`NIK_SEED_DEMO_USERS=true`（**缺省关**，生产默认不建）；
* 产出：`sys_dept` 一行（`DEPT_DEMO` / 演示事业部，`leader_id` = `demo_lead`）+ 9 个演示账号
  （`demo_sales` / `demo_sales_mgr` / `demo_purchase` / `demo_purchase_mgr` / `demo_finance` /
  `demo_finance_mgr` / `demo_wh` / `demo_lead` / `demo_gm`）+ 关键角色绑定；
* 幂等：按 `username` / `dept_code` 判重 ⇒ 跑 1 次和跑 100 次行数一样（脚本 `KEEP_DB=1` 复跑可以自证）。

`make_full_suite_db.sh` 做的事：`createdb`（owner = 表属主）→ 用**被测树自己编译的二进制**起一次实例
（`migrations/` 编译期内嵌 + bootstrap + 演示种子）→ 等到「超管 + 演示账号」都落库再停实例 → 自检 → 打印连接串。

自检项（脚本里逐条打印 ✓/✗，任一 ✗ 直接退出 1）：

| 项 | 期望 |
|---|---|
| `schema_migrations` 条数 / 最新版本 / `public` 表数 | 非 0（对照本树 `migrations/` 的实际条数） |
| `sys_user` / `sys_role` / `sys_menu` / `biz_account` | 非 0 |
| `biz_flow_def(status='PUBLISHED')` | 非 0（种子审批流都发布着） |
| `biz_report_item` | 非 0（报表项） |
| `sys_dept` / `DEPT_DEMO` | 非 0 / 存在（演示组织） |
| 6 个关键角色（`SALES_SUPERVISOR`/`PURCHASE_MANAGER`/`FINANCE_MANAGER`/`DEPT_LEADER`/`WAREHOUSE_MANAGER`/`GENERAL_MANAGER`）在职成员数 | 都 > 0 |
| `biz_voucher` / `biz_sales_order` / `biz_purchase_order` / `biz_flow_instance` | **都 = 0**（零历史单据） |

## 3. 四条 URL 为什么必须同一个库

1. `set_db()` 是**进程级 `OnceLock`（先到先得）**。四条 URL 指同一个库时，谁先连都连到同一个库，
   `master_data` / `support::job::db_tests` 里「`SELECT current_database()` 必须等于我这条 URL 的库名」
   的守卫才成立；否则它们打印 SKIP 后 return —— 而 libtest 把 SKIP 记成 **passed**，就是假绿。
2. `flow::internal_control::db_tests`（内控 / 会签 7 条）要求 `P0FIX_DB_URL` 的库名含 `p0fix`
   或 `cloudpivot_test`，且**必须**与进程里已装的全局连接是同一个库；本口径的库名以
   `cloudpivot_test` 开头（默认 `cloudpivot_test_full`）⇒ 天然满足，**不需要**
   `--skip business::flow::internal_control::db_tests`（那 7 条是「同库多进程」时代的绕法）。
3. `tests/testd` 的 `ensure_db` 也会硬校验连接串里含 `/cloudpivot_test` —— 同一个库名对它同样成立。

> 库名别改掉 `cloudpivot_test` 前缀，否则上面三处守卫会以 SKIP 或 panic 的形式找上门。

## 4. 判据与反模式

* **判据**：`test result: ok. N passed; 0 failed; 0 ignored`，且 `N` 与本树用例数（`grep -c '#\[test\]'` /
  `#[tokio::test]`）对得上——`filtered out` 不能大。
* **不许**：`--skip` / `--ignored` / `--test-threads>1` 冲绿（并行会互踩，见技能包 §11）；
  也不许把 `SKIP: …` 当成通过（加 `--nocapture` 数 SKIP 行数，>0 就该查是不是 URL 没指对）。
* **重跑口径**：脚本默认**先删后建**；要验「残留不影响下一轮」就在同一个库上连跑两轮（第二轮带第一轮残留），
  两轮都必须 `0 failed`。
* 只跑受影响模块时可以用过滤器（多过滤器是 OR），但**交卡前必须给一次全量 `0 failed`**。

## 5. 本卡修的 5 处「夹具/接线卫生」（不是放宽判据）

全量在种子完备库上仍然有红（`50a9063` 实测：空库 3315 passed / 28 failed；种子完备库 3282 / 47），
其中 4 类是真·夹具缺陷或产品接线缺口，与业务逻辑无关，逐条修在用例侧 + 一处接线：

## 6. 不属于这条口径的东西

* **集成 target**（`tests/testd`、`batchC_c5`、`fix04`、`pflow5` …）：各自读自己的 URL（`TESTD_DB_URL` /
  `FIX04_DB_URL` …），不设就 `SKIP` 且**仍然计 passed**。它们要单独验，报告里别混。
* **前端**（`tests/unit` / `vite build` / `pnpm typecheck`）：与库无关。
* **生产 / 145 服役库**：只读巡检（`scripts/verify/erp_invariants.py`）用它，全量 lib 套件**不要**跑在它上面
  （会写夹具，且历史数据把整表口径断言打红）。
* **别人的未提交改动**：共享主仓 `/opt/cloudpivot` 常有别的卡未跟踪文件（新迁移 / 新模块）。
  拿「全量 0 failed」当交付证据时，用 `git archive HEAD` 的干净树 + 该树自己的二进制，
  否则你会替别人的半成品背红（实测：别人的 `V0321__price_inquiry` 菜单会让
  `system::menu::tests::n08` 判 404、旧二进制里缺 `SOURCELESS` 会让 `doc_kind` 镜像用例红）。

## 8. 依赖种子的用例：从「库里没有部门」到「缺什么 / 怎么补」（TST-02）

> 实现：`backend/src/shared/test_helpers.rs`（`#[cfg(test)]`），22 条用例接入。

`make_full_suite_db.sh` 解决了「库从哪来」，但**用例本身**并不知道自己依赖种子：
空库上它们以前是这样红的（实测，迁移 352 的一次性空库 `cloudpivot_test_tst02_empty`）：

```text
thread '…::st02_idle_triggers_once' panicked at asset_linkage_tests.rs:195:
库里没有部门（先跑基础种子迁移）
thread '…::lnk05_submit_triggers_linkage_notice' panicked at expense_linkage_tests.rs:155:
库里必须有一名带部门的用户
```

这句话既没说「本套件需要什么」，也没说「怎么补」，还容易被当成代码 bug 去查接线。
更麻烦的是 `voucher_linkage_tests::two_users()` 在只有 1 个账号的库上 `return None`、
调用方 `else { return; }` ⇒ **用例静默 pass，一行断言没跑**（假绿）。

### 用法（每条用例的 setup，在 `ensure_db()` 之后、造夹具之前）

```rust
use crate::shared::test_helpers as seed_guard;

seed_guard::require_seed_data(
    "asset_linkage_tests",                 // 只用于报错文案
    &[seed_guard::DEPT, seed_guard::ACCOUNT],
)
.await;
```

清单是「一句人话 + 一条 `SELECT count(*)` + 最少行数 + 缺了会怎样」：

| 项 | 判据 | 谁在用 |
|---|---|---|
| `DEPT` | `sys_dept` 未删行 ≥ 1 | 资产 / 报销 / 预算 |
| `DEPT_USER` | 在职且 `dept_id IS NOT NULL` 的用户 ≥ 1 | 报销（部门取自报销人） |
| `TWO_USERS` | 在职用户 ≥ 2 | 凭证（制单人 ≠ 审核人） |
| `ACCOUNT` | `biz_account` ≥ 1 | 一切凭证 |
| `EXPENSE_TYPE` | `biz_expense_type` ≥ 1（V0242） | 报销明细 |
| `ASSET_CATEGORY` | `biz_asset_category` 启用行 ≥ 1（V0229） | 资产卡 |
| `PUBLISHED_FLOW` | `biz_flow_def` PUBLISHED ≥ 1 | 需要发起审批的套件 |
| `APPROVER_ROLES` | 六个关键岗位各 ≥ 1 名在职成员 | 报销（否则提交 422 / 65018） |

缺一项就 panic，**一次把所有缺口列全**，并给出修复路径（`bash scripts/verify/make_full_suite_db.sh`
+ 四条 URL + 不许 `--skip` / `--ignored`）。查询本身报错（表/列不存在）也算缺 —— 那说明这个库的迁移
不是当前版本，同样得重建，而不是让用例跑到一半炸在无关断言上。

### 仍待收口（另开卡）

`asset_model_tests` / `budget_model_tests` / `expense_model_tests` 走的是另一条路：缺部门/用户时
`let (Some(dept), …) = … else { return; }` ⇒ 也是**静默 pass**（不是红）。它们需要的是 A 方案
（setup 自建部门/用户，固定 UUID + `ON CONFLICT DO NOTHING`），比加闸更彻底。
