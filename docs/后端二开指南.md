# 后端二开指南

> 目标：让开发者 / AI 以**最短路径**新增一个业务模块。请先读 [项目结构与设计亮点.md](./项目结构与设计亮点.md) 建立心智模型，再照本文的「7 步流程 + 四件套模板」落地。
> 所有范本优先照抄 `backend/src/system/user/`（用户模块四件套）。

---

## 一、新增业务模块的标准 7 步

> 二开业务统一放 `backend/src/business/<模块>/`，**不要**放进 `system/` 或 `support/` 底座。

1. **建迁移**：在 `backend/migrations/business/` 新建 `V0020__create_<表>.up.sql` / `.down.sql`（号段从 **`V0020`** 起，4 位补零）。建表文件采用「建表 → `COMMENT ON` → 索引」三段式，索引不单独占版本。
2. **写模型** `model.rs`：用 `#[derive(Model)]` + `#[table("your_table")]` 声明实体；需要自写 SQL / 领域逻辑的函数集中放这里。
3. **写 DTO** `dto.rs`：请求 `*Req`（带 `validator::Validate`）、响应 `*Res`（带 `from_model` 构造器，可空文本列统一降级为空串）。
4. **写处理器** `handler.rs`：用 `#[nik::permission(path, method, permission)]` + `#[nik::get/post/...]` 声明路由；参数校验与响应组装在 handler，SQL 下沉到 model。
5. **声明模块** `mod.rs`：写模块文档（含接口一览表），`pub mod dto; pub mod handler; pub mod model;`。
6. **挂菜单种子**：在 `backend/migrations/seed/` 追加菜单与按钮权限点，`module_code = 'business'`，用 `ON CONFLICT ... WHERE deleted_at IS NULL` 幂等。
7. **编译验证**：`cargo fmt && cargo clippy -- -D warnings && cargo check`；`cargo run` 自动迁移并启动。

> 权限码三段式 `{模块}:{资源}:{动作}`（如 `business:article:create`），必须与 `sys_menu.auth_code` 和 `#[nik::permission(...)]` 三处一致。

## 二、四件套模板（可照抄）

### 2.1 `mod.rs`（模块文档 + 声明）
```rust
//! 文章管理子模块。
//!
//! | 文件 | 内容 |
//! |------|------|
//! | [`model`] | [`model::ArticleModel`]（`biz_article`） |
//! | [`dto`] | 列表 / 详情 / 增改请求与响应 |
//! | [`handler`] | 分页、详情、增删改 |
//!
//! 对外路径前缀 `/api/business/article`。

pub mod dto;
pub mod handler;
pub mod model;
```

### 2.2 `model.rs`（实体 + 数据访问）
```rust
use nik::prelude::*;
use crate::utils;

#[derive(Debug, Clone, Model)]
#[table("biz_article")]
pub struct ArticleModel {
    pub id: uuid::Uuid,
    pub title: String,
    pub content: Option<String>,
    pub status: crate::shared::constants::EnableStatus,
    pub created_at: chrono::DateTime<chrono::Utc>,
    pub updated_at: chrono::DateTime<chrono::Utc>,
    pub deleted_at: Option<chrono::DateTime<chrono::Utc>>,
}

// 需要自写 SQL / 领域逻辑的函数集中在此（仅调用框架快捷方法时可在 handler 直接写）。
pub(crate) async fn page_articles(
    filter: &ArticleFilter, page: u64, page_size: u64,
) -> DbResult<PageData<Vec<ArticleModel>>> {
    let rows = ArticleModel::query()
        // #if / #and 自动参数化，绝不做字符串拼接
        #if let Some(kw) = &filter.keyword {
            .sql(#and "title ILIKE #{kw}")   // kw 已在 handler 拼成 %kw%
        }
        .paginate(page, page_size)
        .await?;
    Ok(rows)
}
```

### 2.3 `dto.rs`（请求 / 响应）
```rust
use nik::prelude::*;
use serde::{Deserialize, Serialize};
use validator::Validate;
use crate::business::article::model::ArticleModel;

#[derive(Debug, Clone, Serialize)]
pub struct ArticleRes {
    pub id: String,
    pub title: String,
    pub content: String,            // 可空文本列统一降级为空串
    pub status: i16,
    pub created_at: chrono::DateTime<chrono::Utc>,
}
impl ArticleRes {
    pub fn from_model(m: &ArticleModel) -> Self {
        Self {
            id: m.id.to_string(),
            title: m.title.clone(),
            content: m.content.clone().unwrap_or_default(),
            status: m.status.as_i16(),
            created_at: m.created_at,
        }
    }
}

#[derive(Debug, Clone, Deserialize, Validate)]
pub struct ArticleCreateReq {
    #[validate(length(min = 1, max = 120))]
    pub title: String,
    pub content: Option<String>,
}
```

### 2.4 `handler.rs`（路由 + 编排）
```rust
use nik::prelude::*;
use axum::http::HeaderMap;
use std::net::SocketAddr;
use crate::shared::constants::EnableStatus;
use crate::business::article::dto::{ArticleCreateReq, ArticleRes};
use crate::business::article::model::{self, ArticleModel};
use crate::utils;

#[nik::permission(path = "/business/article/page", method = "GET", permission = "business:article:list")]
#[nik::get("/business/article/page")]
pub async fn page(Query(query): Query<ArticlePageQuery>) -> ResResult<PageData<Vec<ArticleRes>>> {
    let (page, page_size) = utils::normalize_page(query.page, query.page_size);
    let filter = model::ArticleFilter { keyword: query.keyword.map(|k| format!("%{k}%")) };
    let page_data = model::page_articles(&filter, page, page_size)
        .await
        .map_err(|e| utils::db_error(e, "分页查询文章"))?;
    let list = page_data.list.iter().map(ArticleRes::from_model).collect();
    Ok(Res::page(list, page_data.total, page_data.page, page_data.size))
}

#[nik::permission(path = "/business/article", method = "POST", permission = "business:article:create")]
#[nik::post("/business/article")]
pub async fn create(
    headers: HeaderMap,
    ConnectInfo(_conn): ConnectInfo<SocketAddr>,
    Extension(AuthClaims(claims)): Extension<AuthClaims>,
    ValidatedJson(req): ValidatedJson<ArticleCreateReq>,
) -> ResResult<ArticleRes> {
    let mut m = ArticleModel {
        id: uuid::Uuid::now_v7(),
        title: req.title.trim().to_string(),
        content: req.content.map(|v| v.trim().to_string()),
        status: EnableStatus::enabled,
        created_at: chrono::Utc::now(),
        updated_at: chrono::Utc::now(),
        deleted_at: None,
    };
    m.insert().await.map_err(|e| utils::db_error(e, "新建文章"))?;
    Ok(Res::ok(ArticleRes::from_model(&m)))
}
```

## 三、路由与权限

- **宏声明**：`#[nik::get("/business/article/page")]`；路径**不含** `/api` 前缀（由 `[router] prefix` 注入）。
- **权限**：`#[nik::permission(path, method, permission)]`；`SUPER_ADMIN` 以 `role_code == 'SUPER_ADMIN'` 短路全部校验。
- **免鉴权**：用 `#[nik::no_auth("/path")]`；`/health` 在 `lib.rs` 里手动 `.get()` 注册豁免前缀。
- **常用提取器**：`Query<T>`、`Path<String>`、`ValidatedJson<T>`、`Extension(AuthClaims)`、`ConnectInfo<SocketAddr>`、`HeaderMap`。

## 四、错误处理（出口只有三个名字）

| 位置 | 返回类型 | 说明 |
|------|----------|------|
| handler | `ResResult<T>` | 业务处理器；`Ok(Res::ok(x))` / `Ok(Res::page(...))` |
| model | `DbResult<T>` | 数据访问层 |
| 启动 / 插件 / 任务 | `nik::Result<T>` | 框架级 |

**铁律**：handler 内 `DbError / io::Error / nik_core::Error` 直接 `?` 传播：
```rust
let user = load_user(&id).await?;                       // 自定义辅助返回 ResResult
let rows = model::page_x(&f, p, s).await
    .map_err(|e| utils::db_error(e, "分页查询X"))?;      // 仅在需补充中文上下文时包一层
```
**不要**写多余的 `.map_err(ApiError::internal(...))`；**禁止** `unwrap()` / `expect()`（clippy `-D warnings` 会拦）。

## 九、迁移编写细则

- 文件名 `V{n}__{Name}.up.sql` / `.down.sql`（成对）；种子 `S__{Name}.sql`。
- **已应用迁移指纹校验不可改**：演进只加新版本，不要回改历史迁移。
- 建表文件三段式：建表 → `COMMENT ON TABLE/COLUMN` → 索引（索引随表一起删，down 无需单独 `DROP INDEX`）。
- 种子 `ON CONFLICT ... WHERE deleted_at IS NULL DO NOTHING` 幂等；菜单/权限点属纯数据，一律追加种子 SQL，**不写 Rust**。
- 二开业务迁移号段 `V0020+`，与 `src/business/` 对应。
- **号段以 `ls backend/migrations/business/` 的实际最大值为准**，动手前必查；文档/历史迁移注释里
  写死的「预留号段」（例如某迁移注释说「ARCH-5 从 V0230 起」）会随时间被别的卡占掉，按它编号必撞车。
  已应用到某个库的迁移版本号视为占用，即使后来被回滚。例如：截至 2026-11 实占已到 `V0234`
  （`V0233` = P2-6b-follow 流程种子补标，`V0234` = 流程模板库菜单收口），下一条从 `V0235` 起。
- **新增预置流程（`biz_flow_def` 种子）必须显式写 `is_system = TRUE`**：该列是
  `BOOLEAN NOT NULL DEFAULT FALSE`（`V0193`），漏写就吃默认值 FALSE —— 系统预置、客户不该改图的流程
  会被当成「客户自建」，在流程定义 / 模板库页里以可改身份露出却挂不上「标准」标签。
  这不是假想，`V0193` 之后**已经犯了四次**：`V0209`（`contract_approve`）、`V0211`（`stock_take_post`）
  → 由 `V0220` 按 `flow_code` 回补；`V0228`（`budget_approve`）、`V0231`（`asset_disposal`）
  → 由 `V0233` 回补（已应用迁移有指纹校验，**不许**回头改 V0209/V0211/V0228/V0231）。
  后果是**静默**的：P2-6b 把模板列表收口为「标准流程」（`AND d.is_system`）后，这两条直接从
  「流程模板库」里消失，直到有人数卡片才发现。
  防回归（三条，前两条必跑，详见 `scripts/verify/erp_invariants.py --group 审批`）：
  - `H6`（**静态**，不连库）：扫 `backend/migrations/**` 里所有 `INSERT INTO biz_flow_def (...)`
    的列清单，版本 ≥ `V0193` 却缺 `is_system` 且没有更晚的迁移按 `flow_code` 补偿 → BLOCKER；
    照抄旧种子漏列时当场红，不用等库跑起来。加新预置流程后先跑它。
  - `H5`（库内，`WARN`）：只认「名字含『标准』却 `is_system=FALSE`」这一个方向，
    名字里没有「标准」的（如 `budget_approve`）抓不到 —— 所以 H6 才是主力。
  - `V0220` / `V0233` 迁移体内各带一段 fail-closed 自检（预置白名单里不许有非系统行），
    再犯则对应迁移之后的启动直接失败。
  同理适用于其它**带「系统预置」语义的 flag 列**（`is_default` / `is_builtin` …）：
  种子 INSERT 一律显式写值，不依赖 DEFAULT。

## 十、数据权限检查清单（新增列表接口必过）

> 落地状态：表与索引已就位（`V0060` 角色数据范围 / `V0061` 自定义部门集合，见 `docs/批次B-DDL.md`）；
> 代码侧入口 `business/shared/scope.rs`（`ScopeKind` / `RowFilter` / `filter_for` / `paginate` /
> `ScopedPrincipal`）由批次 B 的 B2、底座接入由 B3、其它登记表接入由 B5 落地。**本节是那几步之后
> 团队必须遵守的约束**，`scripts/check.sh` 的两条门禁已经在度量它（B5 前为失败状态，属预期）。

新增任何「列表 / 分页」接口，逐条自查：

- [ ] **分页必须走 `scope::paginate`**，不允许直接调 `db().paginate_with_params(...)`。
      `scope::paginate` 要求传入 `&ScopedPrincipal`，而它只能由 `scope::resolve()` 构造 —— 于是
      「想分页就必须先解析数据范围」由类型系统强制，不靠记性。
      （门禁 闸①：`bash scripts/check.sh`，白名单只放 `business/shared/scope.rs` 自身。）
- [ ] **非分页取数**（详情、下拉、导出取数）用 `scope::filter_for(...)`，并把返回的 `RowFilter`
      显式拼进 `WHERE`。注意：Rust 不会因为「没用返回值」报错，这是闸②存在的原因。
- [ ] **scope 只打在主体表别名上**，且一律进 `WHERE`；**绝不用 `LEFT JOIN ... AND scope`**
      —— 那样只会让关联列变 NULL、行数不变（最隐蔽的漏洞）。需要二次裁剪的表（如部门树）单独再注入一次。
- [ ] **新表若属「业务数据」必须登记 `SCOPED_TABLES`**（`(table, dept_col, owner_col)` 三元组），
      并同时给出注册表语义的理由；登记后启动自检会核对表/列真实存在（部署即失败，而不是运行期 500）。
- [ ] **确实不需要数据权限的查询**（清理任务、聚合计数、通知扇出、装载自身上下文…）在函数上方写一行
      `// SCOPE-EXEMPT: <理由>`。理由必须写「为什么注入 scope 反而是错的」，不能只写「不需要」。
- [ ] 新增权限点：`sys_menu.auth_code` = `#[nik::permission]` = 前端 `meta.permission` **三处逐字一致**。
- [ ] **闸② 的登记表清单是「表的集合」，不是「目录的集合」**：新表进来就要加进
      `scripts/check.sh` 的 `BATCHB_SCOPED_TABLES`（2026-10-29 设计修正 A 已补入 C+ 的
      `biz_task*` 全家族 7 张表）。判据是「这张表会不会被直接分页/查询」，不是「它在哪个模块」。
      注意闸② **只看真实代码行**：整行注释里举例的 `FROM <表>` 不算查询，注释里写一句
      「参考 `scope::…`」也不算已接入（否则门禁会被注释骗成假绿）。

**踩坑提醒**：`support/dashboard/model.rs` 的聚合 SQL 里带一个叫 `scope` 的日期 CTE，容易被误看成
「已经接入数据权限」；门禁口径是 `scope::` 前缀 / `SCOPE-EXEMPT` 注释，两者都不是，所以要显式豁免。

## 十一、列级脱敏检查清单（新 DTO 含敏感列必过）

> 落地状态：`sys_field_mask` 表 + `uk_sys_field_mask_rule`（`NULLS NOT DISTINCT`）+ 标识符
> `CHECK` 已就位（`V0062`）；`sys_export_task.mask_applied` 已就位（`V0067`）。脱敏实现
> （`MaskType` / `MaskRule` / `MaskSet` / `Maskable`、导出 fail-closed）由 B6 落地。**本节是 B6 之后
> 的强制约束**。

新增/修改 DTO 时逐条自查：

- [ ] **DTO 里若含敏感列**（手机号、身份证、邮箱、姓名、银行卡、金额、地址…），该 DTO 必须实现
      `Maskable`，并提供**样例函数**（返回一份代表性实例，供编译期/单测期「敏感值扫描」用）。
      没有样例 = 扫描覆盖不到 = 视为未实现。
- [ ] 敏感列的判定**不靠字段名猜**：能落到 `sys_field_mask(table_name, column_name)` 的，以规则表为准；
      规则表里该列没有生效规则时，导出侧**必须 fail-closed**（返回 422 `FIELD_MASK_RULE_MISSING`，
      且不产出文件），不允许「没配规则就发明文」。
- [ ] 新增敏感列时，同时在种子迁移里补默认规则（参考批次 B 的 `V0066`），
      `mask_type` 1–7 与 `mask_param` 格式见 `docs/批次B-DDL.md` §2.3。
- [ ] **导出/导入路径**：`ExportColumn` 要带上来源表名，`format_export_rows` 要接收 mask 参数，
      并把结果写入 `sys_export_task.mask_applied`（TRUE = 已脱敏）。**同步导出与异步 worker 两个调用点都要改**
      —— 只改一处等于留了一条明文出口。
- [ ] 明文出口只有一条：持 `system:field-mask:plain` 权限者可看明文，且必须写 `audit_logs` 留痕。
- [ ] 不要用 `nik_utils::Mask::mask_by_type` 的兜底分支处理多字节字符串（实测会 panic，
      byte index 落在 UTF-8 字符中间），自定义类型一律走自研 `apply_value`。

## 十二、角色互斥检查清单（授予 / 改角色必过）

> 落地状态：`sys_role_mutex` 表 + `uk_sys_role_mutex_pair`（`LEAST/GREATEST` 对称唯一）+
> `ck_sys_role_mutex_distinct`（反自反）已就位（`V0063`）。`sod::ensure_no_mutex` 与
> `assign_roles` 的一行接线由 B7 落地。**本节是 B7 之后的强制约束**。

- [ ] **任何授予 / 修改用户角色的写路径，必须过 `role_mutex` 守卫**（`sod::ensure_no_mutex`）。
      权威写入点是 `system/user/handler.rs::assign_roles`；`replace_user_roles` 是事务内部函数，
      **绕开它写 `sys_user_role` 就等于绕开所有校验** —— 新增接口若碰角色绑定，必须复用该入口。
- [ ] 守卫位置在批次 A 的「权限上限（delegation cap）」校验**之后**、写库**之前**：
      先判「你有没有资格授这个角色」，再判「这两个角色互不互斥」，顺序反过来会给出误导性的 409。
- [ ] 同一次请求里**同时授予两个互斥角色**也要被拦住（不能只比对「已持有的角色」）；
      已过期的绑定（`expire_time <= now()`）**不算持有**。
- [ ] 超管**不短路**互斥：超管双持同样 409（与权限码不同，互斥是合规要求，不是能力裁剪）。
- [ ] 建立互斥关系前先做存量冲突预检（架构文档附录 A.9 的 SQL），有双持用户时返回 409 并列出用户名，
      不允许「先建规则、再让线上用户变成违规状态」。
- [ ] 错误码：`61009 ROLE_MUTEX_CONFLICT` / `61010 ROLE_MUTEX_HAS_HOLDERS` /
      `61011 ROLE_MUTEX_DUPLICATE`（含反向重复）/ `61012 ROLE_MUTEX_SELF_PAIR`。

## 十三、上传分类与存储策略（新增上传口必看）

> 落地：`sys_storage_policy`（V0040 建表、V0048 种 5 类、V0086 种 `announcement`、
> **V0107 种 `task` / `task_ai`**）+ `business/storage/model.rs::check_upload`。

- [ ] **每个新上传分类必须有一条策略行**，用固定 UUID + `ON CONFLICT (category) WHERE deleted_at IS NULL DO NOTHING`；
      漏种会回落到内置默认策略（50 MB、**不限制扩展名**、不允许直传）—— 等于静默放宽。
- [ ] **白名单 fail-closed**：`allowed_extensions` 里没有的一律拒绝；「禁用某类型」的正确写法是
      **不把它写进白名单**，不要幻想有黑名单列（表里确实没有）。
- [ ] **可执行/脚本扩展名是代码级硬禁止**：`FORBIDDEN_EXECUTABLE_EXTENSIONS`
      （exe,sh,bat,ps1,so,dll,jar,py,js + 若干同类）在 `check_upload` 里**先于白名单**判定，

- [ ] 迁移里带**自检块**（`DO $$ … RAISE EXCEPTION`）核对策略值：值被改错时让迁移失败，

## 十四、库存三本账唯一写入口（新增 / 修改库存写路径必看）

> 落地：`backend/src/business/erp/inventory_writer.rs`（P2-5A 收口）。
> 闸门：`scripts/verify/inventory_write_gate.py`。三处生效：
> ① `bash scripts/check.sh`（本仓 CI 入口，先跑 `--self-test` 校验判据本身、再扫全树）；
> ② pre-commit 钩子 `.githooks/pre-commit`（装法 `git config core.hooksPath .githooks`，
> 与密钥扫描同一道提交闸）；③ 手动 `python3 scripts/verify/inventory_write_gate.py`。
> 有越界写入直接 exit 1，报告精确到 `文件:行号:表名`。

库存有**三本账**，同一笔业务必须同时动它们，口径还必须一致：

| 表 | 记什么 | 谁在写（业务层） |
|---|---|---|
| `biz_inventory` | 数量 + 金额 + 移动加权单价（成本账） | 收货过账 / 出库扣减 / 调拨 / 盘点 / 期初 / 序列号派生 / 巡检修正 |
| `biz_inventory_location` | 只记数量（库位账，明细到库位桶） | 同上 + 库位账行 find-or-create |
| `biz_inventory_txn` | 流水（**只增不改**，22 列含前后快照） | 所有动账的业务 |

收口前这三张表分别被 **13 / 13 / 8 个文件**直接写 SQL，同一件事（加法、减法、
整桶归零、`ROUND` 位数）在不同文件里各写一遍 —— 任何一处漂移都不会当场报错，
只在巡检里变成「账不对」。现在：

- [ ] **写 SQL 只许住在 `erp/inventory_writer.rs`**。业务模块（`stockin_write` /
      `stockout_model` / `stockin_cancel` / `transfer_settle` / `serial_model` /
      `stocktake_model` / `opening` / `inventory_audit` / `stockin_location`）只保留
      「算什么、什么时候写」的编排，函数体委托给写入口。
- [ ] 新增一种动账方式：先在写入口加一个**语义命名**的函数（`add_cost` / `subtract_cost` /
      `restore_cost` / `deduct_cost` / `try_deduct_cost` / `credit_cost` /
      `sync_cost_qty_from_serials` / `align_cost_qty_batch` / `add_location_qty` /
      `subtract_location_qty` / `lock_cost` / `insert_txn` …），再在业务侧调用；
      **不要**在业务侧拼 SQL。
- [ ] **同义不同法，别顺手合并**：出库扣减（整桶取完金额归零）与调拨调出（均价不动、
      条件扣减）是两种口径；入库加法（upsert、`ROUND(…,6)`）与调拨调入（汇总桶优先锁行后移动加权）
      也是两种。合并会打破巡检 C4 / B2 的恒等式。
- [ ] **流水只增不改**：任何「改历史流水」的念头都是错的（B4「流水累计 = 当前库存」靠它）。
      `insert_txn` 的 `period_code` 默认按 `now` 折算，**期初**这类「按会计期间录入」的场景
      必须显式传 `period_code: Some("2034-09")`，否则今天录的期初会落到今天的月份。
- [ ] 测试夹具**不受闸门约束**（按命名的测试文件 `*_tests.rs` / `tests.rs` / `test_*.rs`
      等，或文件内 `#[cfg(test)]` 标记的项）：巡检用例需要能直写脏数据
      （`UPDATE biz_inventory SET qty = 999`）去验「能抓到」，走写入口反而造不出来。
- [ ] **别试图靠换写法绕过闸门**：跨行 SQL（`UPDATE\n  biz_inventory …`）、
      `public.biz_inventory` / `{schema}.biz_inventory`、`"biz_inventory"`（含源码里的
      `\"biz_inventory\"`）、`TRUNCATE` / `COPY` 都在判据里；把文件改名叫 `latest_*.rs`
      也不豁免（豁免只看**明确的测试命名**，不看"含 test 子串"）。判据本身由
      `--self-test` 的 22 条红/绿语料守住，改坏判据 `check.sh` 会先红。
