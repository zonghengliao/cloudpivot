# 后端二开指南

> 目标：让开发者 / AI 以**最短路径**新增一个业务模块。请先读 [项目结构与设计亮点.md](./项目结构与设计亮点.md) 建立心智模型，再照本文的「7 步流程 + 四件套模板」落地。
> 所有范本优先照抄 `backend/src/system/user/`（用户模块四件套）。

---

## 一、新增业务模块的标准 7 步

> 二开业务统一放 `backend/src/business/<模块>/`，**不要**放进 `system/` 或 `support/` 底座。

1. **建迁移**：在 `backend/migrations/business/` 新建 `V0020__create_<表>.up.sql` / `.down.sql`（号段从 **`V0020`** 起，4 位补零）。建表文件采用「建表 → `COMMENT ON` → 索引」三段式，索引不单独占版本。
2. **写模型** `model.rs`：用 `#[derive(Model)]` + `#[table("your_table")]` 声明实体；需要自写 SQL / 领域逻辑的函数集中放这里。
3. **写 DTO** `dto.rs`：请求 `*Req`（带 `validator::Validate`）、响应 `*Res`（带 `from_model` 构造器，可空文本列统一降级为空串）。
4. **写处理器** `handler.rs`：用 `#[nik::permission(path, method, permission)]` + `#[nik::get/post/...]` 声明路由；参数校验与响应组装在 handler，SQL 下沉到 model。
5. **声明模块** `mod.rs`：写模块文档（含接口一览表），`pub mod dto; pub mod handler; pub mod model;`。
6. **挂菜单种子**：在 `backend/migrations/seed/` 追加菜单与按钮权限点，`module_code = 'business'`，用 `ON CONFLICT ... WHERE deleted_at IS NULL` 幂等。
7. **编译验证**：`cargo fmt && cargo clippy -- -D warnings && cargo check`；`cargo run` 自动迁移并启动。

> 权限码三段式 `{模块}:{资源}:{动作}`（如 `business:article:create`），必须与 `sys_menu.auth_code` 和 `#[nik::permission(...)]` 三处一致。

## 二、四件套模板（可照抄）

### 2.1 `mod.rs`（模块文档 + 声明）
```rust
//! 文章管理子模块。
//!
//! | 文件 | 内容 |
//! |------|------|
//! | [`model`] | [`model::ArticleModel`]（`biz_article`） |
//! | [`dto`] | 列表 / 详情 / 增改请求与响应 |
//! | [`handler`] | 分页、详情、增删改 |
//!
//! 对外路径前缀 `/api/business/article`。

pub mod dto;
pub mod handler;
pub mod model;
```

### 2.2 `model.rs`（实体 + 数据访问）
```rust
use nik::prelude::*;
use crate::utils;

#[derive(Debug, Clone, Model)]
#[table("biz_article")]
pub struct ArticleModel {
    pub id: uuid::Uuid,
    pub title: String,
    pub content: Option<String>,
    pub status: crate::shared::constants::EnableStatus,
    pub created_at: chrono::DateTime<chrono::Utc>,
    pub updated_at: chrono::DateTime<chrono::Utc>,
    pub deleted_at: Option<chrono::DateTime<chrono::Utc>>,
}

// 需要自写 SQL / 领域逻辑的函数集中在此（仅调用框架快捷方法时可在 handler 直接写）。
pub(crate) async fn page_articles(
    filter: &ArticleFilter, page: u64, page_size: u64,
) -> DbResult<PageData<Vec<ArticleModel>>> {
    let rows = ArticleModel::query()
        // #if / #and 自动参数化，绝不做字符串拼接
        #if let Some(kw) = &filter.keyword {
            .sql(#and "title ILIKE #{kw}")   // kw 已在 handler 拼成 %kw%
        }
        .paginate(page, page_size)
        .await?;
    Ok(rows)
}
```

### 2.3 `dto.rs`（请求 / 响应）
```rust
use nik::prelude::*;
use serde::{Deserialize, Serialize};
use validator::Validate;
use crate::business::article::model::ArticleModel;

#[derive(Debug, Clone, Serialize)]
pub struct ArticleRes {
    pub id: String,
    pub title: String,
    pub content: String,            // 可空文本列统一降级为空串
    pub status: i16,
    pub created_at: chrono::DateTime<chrono::Utc>,
}
impl ArticleRes {
    pub fn from_model(m: &ArticleModel) -> Self {
        Self {
            id: m.id.to_string(),
            title: m.title.clone(),
            content: m.content.clone().unwrap_or_default(),
            status: m.status.as_i16(),
            created_at: m.created_at,
        }
    }
}

#[derive(Debug, Clone, Deserialize, Validate)]
pub struct ArticleCreateReq {
    #[validate(length(min = 1, max = 120))]
    pub title: String,
    pub content: Option<String>,
}
```

### 2.4 `handler.rs`（路由 + 编排）
```rust
use nik::prelude::*;
use axum::http::HeaderMap;
use std::net::SocketAddr;
use crate::shared::constants::EnableStatus;
use crate::business::article::dto::{ArticleCreateReq, ArticleRes};
use crate::business::article::model::{self, ArticleModel};
use crate::utils;

#[nik::permission(path = "/business/article/page", method = "GET", permission = "business:article:list")]
#[nik::get("/business/article/page")]
pub async fn page(Query(query): Query<ArticlePageQuery>) -> ResResult<PageData<Vec<ArticleRes>>> {
    let (page, page_size) = utils::normalize_page(query.page, query.page_size);
    let filter = model::ArticleFilter { keyword: query.keyword.map(|k| format!("%{k}%")) };
    let page_data = model::page_articles(&filter, page, page_size)
        .await
        .map_err(|e| utils::db_error(e, "分页查询文章"))?;
    let list = page_data.list.iter().map(ArticleRes::from_model).collect();
    Ok(Res::page(list, page_data.total, page_data.page, page_data.size))
}

#[nik::permission(path = "/business/article", method = "POST", permission = "business:article:create")]
#[nik::post("/business/article")]
pub async fn create(
    headers: HeaderMap,
    ConnectInfo(_conn): ConnectInfo<SocketAddr>,
    Extension(AuthClaims(claims)): Extension<AuthClaims>,
    ValidatedJson(req): ValidatedJson<ArticleCreateReq>,
) -> ResResult<ArticleRes> {
    let mut m = ArticleModel {
        id: uuid::Uuid::now_v7(),
        title: req.title.trim().to_string(),
        content: req.content.map(|v| v.trim().to_string()),
        status: EnableStatus::enabled,
        created_at: chrono::Utc::now(),
        updated_at: chrono::Utc::now(),
        deleted_at: None,
    };
    m.insert().await.map_err(|e| utils::db_error(e, "新建文章"))?;
    Ok(Res::ok(ArticleRes::from_model(&m)))
}
```

## 三、路由与权限

- **宏声明**：`#[nik::get("/business/article/page")]`；路径**不含** `/api` 前缀（由 `[router] prefix` 注入）。
- **权限**：`#[nik::permission(path, method, permission)]`；`SUPER_ADMIN` 以 `role_code == 'SUPER_ADMIN'` 短路全部校验。
- **免鉴权**：用 `#[nik::no_auth("/path")]`；`/health` 在 `lib.rs` 里手动 `.get()` 注册豁免前缀。
- **常用提取器**：`Query<T>`、`Path<String>`、`ValidatedJson<T>`、`Extension(AuthClaims)`、`ConnectInfo<SocketAddr>`、`HeaderMap`。

## 四、错误处理（出口只有三个名字）

| 位置 | 返回类型 | 说明 |
|------|----------|------|
| handler | `ResResult<T>` | 业务处理器；`Ok(Res::ok(x))` / `Ok(Res::page(...))` |
| model | `DbResult<T>` | 数据访问层 |
| 启动 / 插件 / 任务 | `nik::Result<T>` | 框架级 |

**铁律**：handler 内 `DbError / io::Error / nik_core::Error` 直接 `?` 传播：
```rust
let user = load_user(&id).await?;                       // 自定义辅助返回 ResResult
let rows = model::page_x(&f, p, s).await
    .map_err(|e| utils::db_error(e, "分页查询X"))?;      // 仅在需补充中文上下文时包一层
```
**不要**写多余的 `.map_err(ApiError::internal(...))`；**禁止** `unwrap()` / `expect()`（clippy `-D warnings` 会拦）。

## 九、迁移编写细则

- 文件名 `V{n}__{Name}.up.sql` / `.down.sql`（成对）；种子 `S__{Name}.sql`。
- **已应用迁移指纹校验不可改**：演进只加新版本，不要回改历史迁移。
- 建表文件三段式：建表 → `COMMENT ON TABLE/COLUMN` → 索引（索引随表一起删，down 无需单独 `DROP INDEX`）。
- 种子 `ON CONFLICT ... WHERE deleted_at IS NULL DO NOTHING` 幂等；菜单/权限点属纯数据，一律追加种子 SQL，**不写 Rust**。
- 二开业务迁移号段 `V0020+`，与 `src/business/` 对应。
- **号段以 `ls backend/migrations/business/` 的实际最大值为准**，动手前必查；文档/历史迁移注释里
  写死的「预留号段」（例如某迁移注释说「ARCH-5 从 V0230 起」）会随时间被别的卡占掉，按它编号必撞车。
  已应用到某个库的迁移版本号视为占用，即使后来被回滚。例如：截至 2026-11 实占已到 `V0234`
  （`V0233` = P2-6b-follow 流程种子补标，`V0234` = 流程模板库菜单收口），下一条从 `V0235` 起。
- **新增预置流程（`biz_flow_def` 种子）必须显式写 `is_system = TRUE`**：该列是
  `BOOLEAN NOT NULL DEFAULT FALSE`（`V0193`），漏写就吃默认值 FALSE —— 系统预置、客户不该改图的流程
  会被当成「客户自建」，在流程定义 / 模板库页里以可改身份露出却挂不上「标准」标签。
  这不是假想，`V0193` 之后**已经犯了四次**：`V0209`（`contract_approve`）、`V0211`（`stock_take_post`）
  → 由 `V0220` 按 `flow_code` 回补；`V0228`（`budget_approve`）、`V0231`（`asset_disposal`）
  → 由 `V0233` 回补（已应用迁移有指纹校验，**不许**回头改 V0209/V0211/V0228/V0231）。
  后果是**静默**的：P2-6b 把模板列表收口为「标准流程」（`AND d.is_system`）后，这两条直接从
  「流程模板库」里消失，直到有人数卡片才发现。
  防回归（三条，前两条必跑，详见 `scripts/verify/erp_invariants.py --group 审批`）：
  - `H6`（**静态**，不连库）：扫 `backend/migrations/**` 里所有 `INSERT INTO biz_flow_def (...)`
    的列清单，版本 ≥ `V0193` 却缺 `is_system` 且没有更晚的迁移按 `flow_code` 补偿 → BLOCKER；
    照抄旧种子漏列时当场红，不用等库跑起来。加新预置流程后先跑它。
  - `H5`（库内，`WARN`）：只认「名字含『标准』却 `is_system=FALSE`」这一个方向，
    名字里没有「标准」的（如 `budget_approve`）抓不到 —— 所以 H6 才是主力。
  - `V0220` / `V0233` 迁移体内各带一段 fail-closed 自检（预置白名单里不许有非系统行），
    再犯则对应迁移之后的启动直接失败。
  同理适用于其它**带「系统预置」语义的 flag 列**（`is_default` / `is_builtin` …）：
  种子 INSERT 一律显式写值，不依赖 DEFAULT。

### 9.1 迁移授权段怎么拿角色码（写 `sys_role_menu` 前必读）

**症状：授权写错码不报错，只是「什么都授不上」。** `sys_role_menu` 挂的是 `menu_id`，
`role_code` 只是 `sys_role` 表里的字符串。`WHERE r.role_code IN ('ADMIN', …)` 若一个都没匹配上，
`INSERT … SELECT` 选中 0 行 —— 迁移照样成功、指纹照样记账，**授权等于从没发生过**。

这不是假想：2026-11-06 扫 27 条「授权段带 `n_roles = 0` 空跑保护」的迁移，
`ADMIN`(20) / `ACCOUNTANT`(14) / `FINANCE`(14) / `TEST_UADMIN`(9) / `BUYER` / `PURCHASER` /
`WAREHOUSE_KEEPER` / `WAREHOUSE` **在生产一个都不存在**，只有 `SUPER_ADMIN` 命中 ——
而超管的 `*:*:*` 通配把它掩盖了（证据：`docs/evidence/20261106-t2274dd-role-matrix/`）。
把这些码抄进新迁移 = 抄一份「无效授权」。

**拿角色码的唯一正确姿势（查库，不抄老迁移）**：

```sql
-- 生产（root@172.18.10.144；装配库/本地库换成自己的库名）
select role_code, role_name from sys_role where deleted_at is null and status = 1 order by role_code;
```

截至 2026-11 生产在用的 12 个角色码（**活角色**，逐字抄录）：

```
SUPER_ADMIN  DEPT_LEADER  FINANCE_DIRECTOR  FINANCE_MANAGER  FLOW_CONFIG_APPROVER
GENERAL_MANAGER  PURCHASE_MANAGER  WAREHOUSE_MANAGER
MUTEX_A  MUTEX_B  QA_LIMITED  QA_VIEWER      -- 后 4 个是验收夹具角色（互斥/只读用例），生产活着
```

**三条写迁移的规矩**：

1. **优先改矩阵，不新写授权段**。生产在生效的业务矩阵已由 `V0258__business_role_matrix.up.sql`
   冻结成版本化迁移（7 个业务角色 × business 码）。要加权限点就走矩阵这条线；
   在业务迁移里再手写一份 `WHERE role_code IN (…)` 只会长出第二份真相。
2. **新业务角色先建再授**：`INSERT INTO sys_role (…, role_code, …) VALUES (…, 'BRANCH_MANAGER', …)`
   必须在**同一次提交**（同一迁移或更早迁移）里，闸会自动把这个码纳入白名单。
3. **确实要显式豁免**（历史个例 / 码由外部系统种）：在 `INSERT INTO sys_role_menu` 上方 5 行内写
   `-- ROLE-EXEMPT: <为什么这个码可以不存在>`，理由 ≥8 字符，脚本只认带理由的写法。

**闸⑧（`scripts/check.sh` 最后一道，静态、不连库）**：
`python3 scripts/verify/role_code_gate.py`

- 白名单 = 生产 12 个活跃角色 ∪ 迁移 `INSERT INTO sys_role` 种出来的角色；
- 扫 `backend/migrations/**/*.up.sql` 里 `INSERT INTO sys_role_menu` 的 `role_code`
  字面量（`= 'X'` / `<> 'X'` / `[NOT] IN (…)`，以及 V0258 那套「(role_code, auth_code) VALUES 矩阵块」）；
- **认的写法**（换一种合法写法也绕不过，`--self-test` 逐形状有语料）：
  `= ANY (ARRAY[…])`、`(role_code) IN (…)`、`INSERT INTO ONLY`、schema 限定 `public.sys_role_menu`、
  小写/多行/字符串里带分号；
- **静态判不了的写法**（`lower(role_code) LIKE '%admin%'`、`IN (SELECT …)`、脚本没见过的形状）
  ⇒ 打 `⚠ 策略提示 … ← 动态表达式` 点名 `文件:行` 并要求人工确认：不判红（会误红），
  也**绝不静默绿** —— 静态闸不假装看得懂正则；
- **历史 25 个文件按 `sha256` 冻结在 `scripts/verify/role_code_gate_baseline.json`**：
  逐字不改 ⇒ 豁免（29 条语句）；改动历史文件 ⇒ sha 不符 ⇒ 全部重报（已应用迁移不可改，这是对的）；
- 命中 ⇒ `exit 1` 并点名 `文件:行 → '未知码'@L行号`；
- 新增迁移里出现 `INSERT INTO sys_role_menu` ⇒ **WARN**（不判红）提示「授权走 V0258 矩阵」；
- 基线只能通过 `--write-baseline` 更新，且会把「新增文件」拒写（防「跑红了就重冻基线」）——
  确需历史补录要 `--force` 并走评审。
- 判据自检 `--self-test`（37 条语料，不读仓库、不连库）；另有「扫描面自证」：
  冻结时为 `191 文件 / 75 条语句 / 59 条带字面量 / 5 条动态` —— 新迁移会让数字变大，
  数字**异常下降**说明解析退化（闸会假绿），先查脚本再查迁移。
- 开关：`ROLE_CODE_GATE=warn|off bash scripts/check.sh`。

## 十、数据权限检查清单（新增列表接口必过）

> 落地状态：表与索引已就位（`V0060` 角色数据范围 / `V0061` 自定义部门集合，见 `docs/批次B-DDL.md`）；
> 代码侧入口 `business/shared/scope.rs`（`ScopeKind` / `RowFilter` / `filter_for` / `paginate` /
> `ScopedPrincipal`）由批次 B 的 B2、底座接入由 B3、其它登记表接入由 B5 落地。**本节是那几步之后
> 团队必须遵守的约束**，`scripts/check.sh` 的两条门禁已经在度量它（B5 前为失败状态，属预期）。

新增任何「列表 / 分页」接口，逐条自查：

- [ ] **分页必须走 `scope::paginate`**，不允许直接调 `db().paginate_with_params(...)`。
      `scope::paginate` 要求传入 `&ScopedPrincipal`，而它只能由 `scope::resolve()` 构造 —— 于是
      「想分页就必须先解析数据范围」由类型系统强制，不靠记性。
      （门禁 闸①：`bash scripts/check.sh`，白名单只放 `business/shared/scope.rs` 自身。）
- [ ] **非分页取数**（详情、下拉、导出取数）用 `scope::filter_for(...)`，并把返回的 `RowFilter`
      显式拼进 `WHERE`。注意：Rust 不会因为「没用返回值」报错，这是闸②存在的原因。
- [ ] **scope 只打在主体表别名上**，且一律进 `WHERE`；**绝不用 `LEFT JOIN ... AND scope`**
      —— 那样只会让关联列变 NULL、行数不变（最隐蔽的漏洞）。需要二次裁剪的表（如部门树）单独再注入一次。
- [ ] **新表若属「业务数据」必须登记 `SCOPED_TABLES`**（`(table, dept_col, owner_col)` 三元组），
      并同时给出注册表语义的理由；登记后启动自检会核对表/列真实存在（部署即失败，而不是运行期 500）。
- [ ] **确实不需要数据权限的查询**（清理任务、聚合计数、通知扇出、装载自身上下文…）在函数上方写一行
      `// SCOPE-EXEMPT: <理由>`。理由必须写「为什么注入 scope 反而是错的」，不能只写「不需要」。
- [ ] 新增权限点：`sys_menu.auth_code` = `#[nik::permission]` = 前端 `meta.permission` **三处逐字一致**。
- [ ] **闸② 的登记表清单是「表的集合」，不是「目录的集合」**：新表进来就要加进

## 十四、库存三本账唯一写入口（新增 / 修改库存写路径必看）

> 落地：`backend/src/business/erp/inventory_writer.rs`（P2-5A 收口）。
> 闸门：`scripts/verify/inventory_write_gate.py`。三处生效：
> ① `bash scripts/check.sh`（本仓 CI 入口，先跑 `--self-test` 校验判据本身、再扫全树）；
> ② pre-commit 钩子 `.githooks/pre-commit`（装法 `git config core.hooksPath .githooks`，
> 与密钥扫描同一道提交闸）；③ 手动 `python3 scripts/verify/inventory_write_gate.py`。
> 有越界写入直接 exit 1，报告精确到 `文件:行号:表名`。

库存有**三本账**，同一笔业务必须同时动它们，口径还必须一致：

| 表 | 记什么 | 谁在写（业务层） |
|---|---|---|
| `biz_inventory` | 数量 + 金额 + 移动加权单价（成本账） | 收货过账 / 出库扣减 / 调拨 / 盘点 / 期初 / 序列号派生 / 巡检修正 |
| `biz_inventory_location` | 只记数量（库位账，明细到库位桶） | 同上 + 库位账行 find-or-create |
| `biz_inventory_txn` | 流水（**只增不改**，22 列含前后快照） | 所有动账的业务 |

收口前这三张表分别被 **13 / 13 / 8 个文件**直接写 SQL，同一件事（加法、减法、
整桶归零、`ROUND` 位数）在不同文件里各写一遍 —— 任何一处漂移都不会当场报错，
只在巡检里变成「账不对」。现在：

- [ ] **写 SQL 只许住在 `erp/inventory_writer.rs`**。业务模块（`stockin_write` /
      `stockout_model` / `stockin_cancel` / `transfer_settle` / `serial_model` /
      `stocktake_model` / `opening` / `inventory_audit` / `stockin_location`）只保留
      「算什么、什么时候写」的编排，函数体委托给写入口。
- [ ] 新增一种动账方式：先在写入口加一个**语义命名**的函数（`add_cost` / `subtract_cost` /
      `restore_cost` / `deduct_cost` / `try_deduct_cost` / `credit_cost` /
      `sync_cost_qty_from_serials` / `align_cost_qty_batch` / `add_location_qty` /
      `subtract_location_qty` / `lock_cost` / `insert_txn` …），再在业务侧调用；
      **不要**在业务侧拼 SQL。
- [ ] **同义不同法，别顺手合并**：出库扣减（整桶取完金额归零）与调拨调出（均价不动、
      条件扣减）是两种口径；入库加法（upsert、`ROUND(…,6)`）与调拨调入（汇总桶优先锁行后移动加权）
      也是两种。合并会打破巡检 C4 / B2 的恒等式。
- [ ] **流水只增不改**：任何「改历史流水」的念头都是错的（B4「流水累计 = 当前库存」靠它）。
      `insert_txn` 的 `period_code` 默认按 `now` 折算，**期初**这类「按会计期间录入」的场景
      必须显式传 `period_code: Some("2034-09")`，否则今天录的期初会落到今天的月份。
- [ ] 测试夹具**不受闸门约束**（按命名的测试文件 `*_tests.rs` / `tests.rs` / `test_*.rs`
      等，或文件内 `#[cfg(test)]` 标记的项）：巡检用例需要能直写脏数据
      （`UPDATE biz_inventory SET qty = 999`）去验「能抓到」，走写入口反而造不出来。
- [ ] **别试图靠换写法绕过闸门**：跨行 SQL（`UPDATE\n  biz_inventory …`）、
      `public.biz_inventory` / `{schema}.biz_inventory`、`"biz_inventory"`（含源码里的
      `\"biz_inventory\"`）、`TRUNCATE` / `COPY` 都在判据里；把文件改名叫 `latest_*.rs`
      也不豁免（豁免只看**明确的测试命名**，不看"含 test 子串"）。判据本身由
      `--self-test` 的 22 条红/绿语料守住，改坏判据 `check.sh` 会先红。

## 十五、导出状态过滤的契约（新增 / 修改导出定义必看）

> 落地：`backend/src/business/impexp/definition.rs`（`ExportFilter` + `check_export_filter`）。
> 起因：导出通道曾对 ERP 单据**静默忽略** `status`（`i16` 只为「启用 / 停用」设计，
> 而单据状态是 `varchar` 文本码），用户以为筛了状态、实际拿到全量文件（卡 `t_93cba3f4`）。

导出只有**两种**状态过滤，定义必须显式声明自己认哪一种：

| 传参 | 语义 | 谁支持 | 定义侧怎么声明 |
|------|------|--------|----------------|
| `status=1` / `status=0` | 启用 / 停用 | `system.dict_item` / `system.user` | `fn supports_status_flag(&self) -> bool { true }` |
| `status_code=POSTED` | 单据状态文本码（不区分大小写） | `erp.stock_in` / `erp.payable` / `erp.voucher` | `fn status_codes(&self) -> Vec<&'static str>` 返回白名单 |

- [ ] **白名单不要另抄一份常量**。ERP 单据的 `status_codes()` 现取导出列里
      `key == "status"` 的 `ColumnKind::Enum` 的 `code` —— 与导出回显的中文同一份
      `EnumItem`。列定义里加一个状态而忘了白名单，就会出现「导出里看得到、却筛不出来」。
- [ ] **状态码 SQL 一律 `AND {status_expr} = ANY(?::text::text[])`**，绑 `{A,B}` 文本
      字面量。本栈驱动**不支持 `Value::Array`**，直接绑 `?::text[]` 会报
      `cannot bind parameter to column type _text`（真库踩过）。
- [ ] **三种过滤条件都不许静默忽略**。`handler::export_sync` / `export_create`、
      `batch_export::create_by_ids` 与 `worker::do_export` 都必须先调
      `definition::check_export_filter(&*def, &mut filter)?`：
      传了本定义不认的字段 → **422 + 10001**，非法码 → 422 且消息**点名合法码**。
      新增导出入口时漏调这一步，等于给用户开一条「筛了等于没筛」的静默错导通道。
- [ ] **`status_code` 会被原地规范化**（去空白 + 大写），下游 SQL 直接绑这个值；
      不要在 SQL 侧再做一次映射，否则两处口径会漂。
- [ ] 加新定义时顺手补三类用例：①白名单与导出列 `Enum` 逐字一致；②非法码 422 且
      消息含全部合法码；③不传状态下 `count` 与修复前一致（真库用例走 `ERP_DB_URL`，
      无库时打印 `SKIP`，**不许假绿**）。

| `sys_menu` / `sys_role_menu` | V0378 | 6 个页面菜单 + 20 个按钮权限码，挂财务管理 `e02`，`sort` 60/62/64/66/68 |

配套：`V0379`（`CS` 号段 + 字典）、`V0380`（存量批号回填）、`V0381`（审批流 `cost_settle_approve`，两级）。

四条全局口径，改任何一张表前先确认没破：

- **期间** `period_code` 一律 `yyyy-MM`（库层 CHECK `^\d{4}-(0[1-9]|1[0-2])$`）。归集**按过账期间**，
  不按单据日期 —— 9 月的领料 10 月才过账就归 10 月（设计 §4.10）。
- **金额** `NUMERIC(18,4)`、单价 `NUMERIC(18,6)`；Rust 侧一律 `Decimal`（`nik::prelude::rust_decimal`），
  成本模块**不出现 f64**，除法用 `round_dp(4)` / 最大余数法收尾差。
- **守恒是库层 CHECK，不是「算完再校验」**：`biz_cost_period_item` 行级
  `完工转出 + 期末在制 = 期初在制 + 料 + 工 + 费`，`biz_cost_period` 单头
  `total_cost = total_material+labor+overhead = total_finished + total_wip`。写错一格插不进去。
  「说结算了但没有凭证」也被库层堵：`SETTLED` 必须 `settled_at` + `finish_voucher_id` 同时非空。
- **名字分两类**（AGENTS 约定 13）：`dept_name` / `source_no` / `unit_price` 存**快照**（审计口径，
  车间改名、物料调价后仍能回溯当时）；对象号 / 物料名 / 车间名在 DTO 里 join 实时取，批量 join 防 N+1。

### 16.2 calc 六段口径

**先接受一个事实：六段没有 HTTP 入口，这是有意的。** 设计 §5.2 只给了一个入口
`POST /business/erp/cost-period/calc`（#27，六段编排），**该接口至今未落地**（前端
`api/business/erp/cost-period.ts` 的 `calcCostPeriod()` 也是留空的）。六段各自是库内函数，
每个模块头都写着同一句话：「单独暴露一个『只归集料』的接口会让期间停在半算状态（料有了、工费没有），
比不给接口更危险」。所以改归集逻辑时不要去 handler 里找，直接在 `cost_calc_*.rs` 改。

要跑整条链（演练 / 临时算一期）用探针，它按同一顺序调用同一批 `pub` 函数：

```bash
NIK_DATABASE_NAME=<库名> cargo run --quiet --example cost_calc_probe -- 2026-11
# 输出 CALC_STAGE=MATERIAL|LABOR|OVERHEAD|RECONCILE|ALLOC|ITEM 各一行 + CALC_OK 汇总
```

| 序 | 段 | 函数（文件） | 读 | 写 | 拦什么 |
|---|---|---|---|---|---|
| 1 | **料** | `collect_material`（`cost_calc_material.rs`） | 当期已过账 + 挂了成本对象的领料明细 | `biz_cost_collect`(MATERIAL)，幂等键 `(STOCK_OUT, 明细 id, 行号)` | 账面非法 400 + `66064` |
| 2 | **工** | `collect_labor`（`cost_calc_labor.rs`） | 当期 `biz_cost_labor` 仅 `CONFIRMED` 行 | `biz_cost_collect`(LABOR)，键 `(LABOR_TICKET, 工时行 id, 0)` | 缺费率 → 进未归集清单（不按 0 计）；账面非法 `66064` |
| 3 | **费** | `collect_overhead`（`cost_calc_overhead.rs`） | 折旧 POSTED / 报销 APPROVED,PAID / 手工费用台账，科目 `4101.*` | `biz_cost_collect`(OVERHEAD)：不挂对象的成**池行**，挂对象的成直接行 | `66064` |
| 4 | **池对账** | `reconcile_pool_with_ledger(period, Stage::Calc)`（`cost_calc_reconcile.rs`） | 池行 vs `biz_voucher_entry` 的 `4101.*` 借方（带凭证号） | 不写，只判 | 409 + `66065`，报文点名差额凭证 |
| 5 | **分摊** | `allocate_overhead`（`cost_calc_alloc.rs`） | 池行 + 该期间生效的规则版本 + 四种基数 | `biz_cost_alloc_result` 一行 + `biz_cost_collect`(ALLOC) 一行，同一事务 | `66066` 期间锁 / `66062` 无在产对象 / `66063` 基数合计 0 |
| 6 | **计算单** | `calc_items`（`cost_calc_item.rs`） | 归集行 + 上期已结算计算单（期初在制）+ 对象产量/进度 | `biz_cost_period_item`（整删重灌，`SETTLED` 行不动） | `66067` ~ `66071`（见 §16.4） |

三条硬口径（改这段代码前必须守住）：

1. **段序不可交换**：料 → 工 → 费 → 池对账 → 分摊 → 计算单。分摊必须**晚于**池对账 ——
   账上多出来的费用（旁路记账）如果先摊下去，错的不是成本而是全部存货。
2. **每段一个事务**；每段都另有 `*_in_tx(ex, …)` 版本，给自己不开事务、不 `commit`，
   供「将来 #27 在一次事务里跑六段」或结算事务内复用。两个版本的逻辑必须是同一份（`_in_tx` 是真身，
   外面那层只负责 `begin/commit/rollback`）。
3. **重算 = 整删重灌**（`DELETE … WHERE period_code = ?` 再插），且只允许
   `DRAFT / CANCELLED / REVERSED`。`SUBMITTED` 之后一律 `66066`（分摊）/ `66070`（计算单）——
   数字已经给审批人看过或已入账，重算等于改写历史成本。

算例 A 的库层数字（`docs/evidence/2026-11-10-arch9-3-cost-ddl/02_cost_calc_drill.out`，
`scripts/verify/cost_e2e.sh` 每次重跑都会复核）：

- 投入 27000 = 完工转出 **22311.1104**（单位 27.888888）+ 期末在制 **4688.8896**；
- 分摊：池 4000 + 基数 60/20/20 → 2400 / 800 / 800；池 1000 + 基数 1/1/1 →
  **333.3334 / 333.3333 / 333.3333**（尾差 0.0001 只落一行 `rounding_adj`）。

改归集/分摊时**先跑** `bash scripts/verify/cost_e2e.sh`：它断言的是库里真实金额（归集表、分摊结果、
计算单、凭证分录、库存三本账），不是接口自报。

### 16.3 结算与红冲（最容易造出「死单」的一段）

`settle_period(id, operator)` 在**一个事务**里做完 6 件事（`cost_settle_run.rs` 模块头有编号）：

1. 生成完工入库：`cost_settle_finish.rs::generate` → `biz_stock_in`（`in_type='PRODUCTION'`，
   带 `cost_object_id` / `cost_period_id`）+ 库存三本账（**只能**走 `inventory_writer`，见第十四章）；
2. 凭证 ④-a 人工计提：`借 4001.02 / 贷 2211.01`（`labor_source='PAYROLL'` 时不生成，防与薪资单双计提）；
3. 凭证 ④-b 手工费用台账：`借 4101.xx / 贷 对方科目`（台账行先「进 4101」，随后被 ④-c 清零）；
4. 凭证 ④-c 制造费用结转：`借 4001.03 / 贷 4101.xx`（按 `(车间,科目)` 分行，把池清零 = C-COST-4①）；
5. 凭证 ④-d 完工入库结转：`借 1405 / 贷 4001.01/.02/.03`（按要素三行，合计 = `finished_cost`）；
6. 6 条事务内断言 `run_asserts`（C-COST-1 ~ C-COST-4 的事务内版）→ 任一条不平整笔回滚。

凭证金额**一律来自计算单 / 归集行，绝不重算**（`cost_settle_voucher.rs` 三条硬断言，
不平报 409 + `66076`）。演练实测一次结算最多 4 张凭证，各自借贷平衡。

**失败语义（AGENTS 约定 11 的落地）**：任何一步失败（含断言）⇒ 整笔回滚，入库单 / 凭证 / 流水
一条不留，批次仍是 `APPROVED`，**修数据后同一张单重试**。可复现的两种造错：
`bash scripts/verify/cost_e2e.sh --inject bypass4101`（→ `66065`）、
`--inject drop_material_voucher`（→ `66077`）。

> ⚠️ **已知缺口（卡外，未修，别当成能用的功能）**：`state_machine::COST_PERIOD_EDGES` 里 `APPROVED` 只有
> `→ SETTLED` 一条边。所以「结算被拦 → 需要重新分摊」时，既不能撤回（只允许 `SUBMITTED`，`66073`），
> 也不能重算分摊（要求 `DRAFT`，`66066`）。运维口径：**先把外部数据修好再重试**（补凭证 / 补领料 /
> 改产量），不要改库；若缺的正是分摊结果本身，当前产品上没有回头路（属 B3-1 / B3-6 待修项，
> 见 `docs/evidence/2026-11-11-cost-b4-5-e2e/README.md` 的「已知缺口」）。

`reverse_period(id, reason ≥10 字, operator)`：红字凭证 + 库存回冲 + 入库单置 `CANCELLED` +
计算单回 `CALC` + 批次 `REVERSED`（唯一键排除 `REVERSED`，所以同期可重新建批次、重算、再结算）。
库存退不回来（货已出库 / 报废）→ `66078`，修法是先销售退货入库 / 盘点盘盈把货补回再红冲。

### 16.5 如何加一种新的分配标准

现有四种：`LABOR_HOURS` / `MACHINE_HOURS` / `OUTPUT_QTY` / `MATERIAL_COST`（设计 §4.4.2）。
加第五种（例：`SALES_AMOUNT` 按销售金额）要走**六处**，漏一处就会出现「试算对、结算错」或
「界面上能选、写库报 400」：

1. **后端词表 + 纯函数**（`cost_alloc_rule_dto.rs`）
   - 加 `pub const BASIS_SALES_AMOUNT: &str = "SALES_AMOUNT";`
   - `BASES: [&str; 4]` → 改成 `[&str; 5]` 并加入（长度是编译期常量，改漏了编译不过 —— 这是有意的）
   - `basis_label()` / `basis_requirement()` 各加一条中文（前端下拉与详情回显都读它）
   - `ObjectBasis` 加字段（新基数需要的聚合量）+ `basis_value()` 加分支（未知标准返回 `Decimal::ZERO`，不 panic）
   - 补单测：`BASES` 遍历断言（`cost_alloc_rule_dto.rs` 约 1128 行）、`basis_value` 每个分支一行（约 1278 行起）
2. **库层值域**（新迁移 `V0386__cost_alloc_basis_sales_amount.up/.down.sql`）
   `V0372` 的 `ck_biz_cost_rule_basis` 把四值写死在 CHECK 里 ⇒ 必须
   `ALTER TABLE biz_cost_alloc_rule DROP CONSTRAINT ck_biz_cost_rule_basis` 再 `ADD CONSTRAINT … CHECK (basis IN (…,'SALES_AMOUNT'))`。
   迁移里带自检块（旧值仍能插、新值能插、乱值被拒），并与 `BASES` 逐字一致。
   **号段**：动手前 `ls backend/migrations/*/` 核对（当前最大 `V0385`，B4-4 的模块开关用它）。
3. **基数取数（两条路径都要改，这是最容易漏的一步）**
   - calc 路径：`cost_calc_alloc.rs` 的 `DeptBasis::ensure_loaded`（加 loader）+ `DeptBasis::objects`（拼 `ObjectBasis`）
   - 试算路径：`cost_alloc_rule_handler.rs::basis_map_of`（按 `basis` 只查需要的那张表）
   - loader 写在 `cost_alloc_rule_model.rs`，照 `labor_basis` / `material_basis` / `completed_qty` 三个模板
     （返回 `Vec<ObjectAmountRow>`，按 `cost_object_id` 聚合；`SqlExecutor` 走 `db()`）
4. **前端词表**（`frontend/src/api/business/erp/cost-alloc-rule-kinds.ts`）
   `ALLOC_BASES`（`as const`）、`ALLOC_BASIS_LABELS`、`ALLOC_BASIS_HINTS` 三处。
   `Record<AllocBasis, string>` 缺键会让 `pnpm typecheck` 当场报错 —— **别用 `Partial` 绕过去**。
5. **验证三条全跑**
   - `cargo test cost_alloc`（纯函数）；真库用例 `ERP_DB_URL=… cargo test -- --ignored`
     （无库时打印 `SKIP`，**不许假绿**）
   - `POST /business/erp/cost-alloc-rule/preview` 拿一个真实期间试算：`basis_total > 0` 且 `Σ alloc = pool`
   - `bash scripts/verify/cost_e2e.sh`（全链重跑，断言一行不改）
6. **文档**：本文 §16.5 上方的四种表、设计 §4.4.2 的基数定义表、`cost-alloc-rule-kinds.ts` 头注释的
   四行表格，三处一起加 —— 它们是给人看的，漏了不会报错，但下一个人会算错。

### 16.6 巡检、灰度开关、已知风险

**巡检 6 条**（`scripts/verify/erp_invariants.py --group 成本`，`COST_SCOPED_STATUSES = SETTLED/CLOSED`）：

| 判据 | 级别 | 平不平说明什么 |
|---|---|---|
| C-COST-1 池（池行+直接行）= `4101.*` 借方，逐 `(车间,科目)` | BLOCKER | 有人绕过成本模块记了 4101（R-3） |
| C-COST-2 Σ生产入库 = 完工凭证借 1405 = Σ计算单完工成本（含凭证平衡） | BLOCKER | 入库金额与结转金额不是同一次 calc 的结果 |
| C-COST-2·账 完工入库单 ↔ 库存三本账（单据级 + 物料×仓库级） | BLOCKER | 入库写了但账没动 / 动了但数不同源 |
| C-COST-3 `4001.01/.02/.03` 余额 = Σ最新已结算期末在制 + 在途未结转 | BLOCKER | 在制结转与总账不符 |
| C-COST-4① 每 `(期间,车间,科目)` 的 4101 期借贷相等（池清零） | BLOCKER | 有费用没进成本 |
| C-COST-4② Σ 分摊结果 = Σ 池行（分摊守恒 / 无漏摊） | BLOCKER | 池没摊完或摊重了 |
| C-COST-5 Σ collect(MATERIAL) = Σ 已过账挂对象领料行 | **WARN** | 料归集漏了（不影响试算，影响准确性） |
| C-COST-6 每张计算单 完工+期末在制 = 期初+料+工+费 | BLOCKER | 约当产量算错（这一条最容易红） |

巡检只判**已结算批次所属期间**：正在做账的期间天然有「账上已借 4001.01、4101 台账凭证还没发」的
中间态，拿它去对 C-COST-1 必然差一笔（差额恒等于当期手工台账金额）—— 那不是错账，是没结完。
