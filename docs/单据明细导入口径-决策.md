## 2. 为什么选 2 而不是 1

### R1 · 单据导入不是「表头 + 明细」，是要复刻勾稽链

主数据导入（6 个定义）本质是**写一张宽表**，框架包掉 90%（`impexp/definition.rs` 的 `ColumnKind` + `validate`）。
单据不是：

| 单据 | 导入时必须处理、而主数据不需要的 |
|:--|:--|
| 入库单 | **单据来源**（采购入库 / 无源，A6）；有源时必须能对上采购单待收行，无源必须显式声明 |
| 采购退货 | 来源入库单（可退量 = 已入库 − 已退） |
| 调拨单 | 两仓 + 库位 + 调出仓可用量校验；有序列号物料还要带出序列号 |
| 出库单 | 仓库 + 库位 + 可用量 |
| 采购订单 / 采购申请 / 询价单 | 物料价目、含税口径、金额重算、单号取号 |

即：每个定义都要写「外键解析 + 数量勾稽 + 金额重算 + 取号 + 幂等（重复上传不能造出两张单）」，
**框架只送到逐行单元格校验为止**，剩下的全在业务侧。

### R2 · 2 万行 / 单 与「200 行上限的存在理由」直接冲突

200 行上限不是为了省服务器 —— 是为了「一张单人能看得完、能核对、能过账」。
给它开一条 2 万行的导入通道 = 造出一张**永远不好处理**的巨型草稿：
前端明细表渲染、审批人过目、财务对峙、作废/冲销全都要面对一张 2 万行的单。
真要 2 万行，正确形态是**多张单**，不是一张大单 —— 那正好就是我们选 2 让用户做的事。

### R3 · 过账侧没评估，不能先承诺

库存三本账的写入口收敛在 `backend/app/src/business/erp/inventory_writer.rs`（`insert_txn` / `align_cost_qty_batch` 等），
单张 2 万行明细过账 = 单事务 2 万行写入 + 逐行成本计算 + 凭证落地。
**批大小、事务时长、锁竞争、失败回滚代价**一个都没评估（上游卡也只写到「要再评估」）。
在没做这项评估前把导入通道打开，等于把一个已知风险直接放进生产。

### R4 · 「要 5000 行」的真实诉求大概率是集成，不是 Excel

能用 Excel 表达的单据需求，通常是三种：
①上游系统（MES/WMS/电商）导出 → 想直接进单据（= **集成需求**，Excel 只是临时桥）；
②历史单据补录（= **迁移需求**，一次性）；
③某天真的有一张 300 行的大单（= **偶发**）。

①和②用 Excel 导入覆盖会掩盖真问题（①天天跑 Excel 是运维税，②该走迁移工具/期初），
③用拆单就能解决。**用导入去接 ①，是让产品去背集成的债。**

### R5 · 成本对比（粗估，供排期判断）

| 方案 | 工程量 | 风险 |
|:--|:--|:--|
| **选 1**（7 个单据明细导入） | 单个定义参考现有主数据实测规模（`supplier.rs` 240 行、`material.rs` 322 行、`unit.rs` 485 行、`account.rs` 459 行 + `db_tests.rs` 807 行）；单据定义还要多 R1 那 5 类逻辑 ⇒ **1.5–2.5 人日/单据 + 过账批量评估 ≈2 人日 ⇒ 12–18 人日**，不含回归 | 高（金额/库存/凭证算错 = 账错） |
| **选 2**（改文案） | 1 处常量 + 1 处前端函数 + 1 个组件去链接 + 5 条单测 ⇒ **≤0.5 人日** | 极低（不动逻辑、不动错误码、不动上限） |

### 反方最强论证（steelman，我为什么仍然不选 1）

> 「如果客户天天有 300 行的单据，『拆单』就是长期税：单据变碎、来源单勾稽碎、审批次数翻倍、
> 对账要按 N 张单拼回去。这种税比一次性做导入贵得多。」

**这个论证成立**，所以我没有把结论写成「永远不做导入」，而是把触发条件写成**「日常级大批量」**（§7 / `RP-2026-009`）：
出现「≥1000 行/单 或 ≥20 张/天」这种拆单明显不合理的量级时，立刻立项做导入 —— 那时也才有真实数据可以定模板列。

## 3. 最终文案

### 3.1 主文案（7 个单据共用，中文）

```text
明细最多 200 行（当前 301 行）。请拆成多张单据提交，每张不超过 200 行。
```

- **断句**：句号切两句。第一句「超了什么」（上限 + 当前行数，保留 P1-04 已有的信息量），
  第二句「怎么办」（一个动作 + 一个可校验的边界）。
- **为什么是「多张单据提交」不是「分次提交」**：单据是原子对象（审批/过账/作废都以「张」为单位），
  「分次」听起来像同一张单分几次保存，会误导。
- **为什么把「每张不超过 200 行」写出来**：用户拆的时候需要一个可自检的数，否则拆出 201 行又撞一次墙。
- 模板里的 `200` 是 `limit` 插值（盘点单 2000 走同一函数，数字自动跟着走），`301` 是 `actual`。

### 3.2 英文（仅口径存档 —— 仓内无 i18n 落点，见 F7）

```text
At most 200 detail lines per document (currently 301). Submit as multiple documents, ≤200 lines each.
```

### 3.3 被否掉的写法（连同原因，防止下一手又改回去）

| 候选 | 为什么不用 |
|:--|:--|
| `大批量请用「导入向导」…（支持 2 万行）` | **本卡起因**：导入向导里没有这 7 个单据，空头支票 |
| `请减少明细行数` | 没说减到多少、也没说减不下来的部分去哪 —— 等于没说 |
| `请联系管理员` | 这个系统的用户多半**自己就是**管理员 |
| `请按来源单分批带出` | 只有入库/退货/采购订单（有来源单）成立；询价单、出库单、调拨单没有来源单，7 单据共用一份文案不能写死 |
| `请升级到更高版本`（假装是版本限制） | 不存在这个分档，属于虚构承诺 |

### 3.4 前端按钮的处置：**删掉，不换指向**

上游卡在黄条上放了「打开导入向导」链接（`DetailLineLimitAlert.vue:34`）。文案改成拆单后：

- 用户此刻**已经在一个单据表单里**，「去哪里新建单据」他知道；
- 保留链接 → 点进导入向导仍然找不到对应单据 → 二次挫折；
- 换成「去列表页新建」→ 用户在编辑态点它，等于丢弃当前 301 行明细，**更糟**。

⇒ 黄条只给句子，不给按钮。`IMPORT_WIZARD_ROUTE_NAME` 常量随之删除（唯一引用点消失）。

### 3.5 盘点单（2000 行）顺手的口径统一

```text
抽盘明细最多 2000 行（当前 2001 行）。请按仓库或物料分类分多次抽盘。
```

- 上限 2000 **不动**（按 P1-04 卡面「保持不动」）；
- 只统一两件事：①`收到 N 行` → `当前 N 行`（与前端及其余 7 单据一致）；②补一个「怎么办」的尾句；
- 盘点的动作是「按范围抽盘」，所以尾句用「分多次抽盘」，**不能**写「拆成多张单据提交/用导入向导」——
  盘点单没有导入通道，也不该有。

## 5. 假设与待验（说清哪些是判断，不是事实）

### A1 · 「>200 行是低频场景」—— 这是**假设**，本轮无数据（F8）

本机拿不到库口令，无法统计真实行数分布。若有人有只读副本，一条 SQL 就能定：

```sql
-- 7 个单据：明细行数 > 200 的单据张数 + 最大值（只读副本执行）
SELECT 'stock_in'    AS doc, count(*) FILTER (WHERE n > 200) AS over_200, max(n) AS max_lines
FROM (SELECT stock_in_id AS id, count(*) n FROM biz_stock_in_item GROUP BY 1) t
UNION ALL SELECT 'purchase_order',
  count(*) FILTER (WHERE n > 200), max(n)
FROM (SELECT order_id AS id, count(*) n FROM biz_purchase_order_item GROUP BY 1) t
UNION ALL SELECT 'stock_transfer',
  count(*) FILTER (WHERE n > 200), max(n)
FROM (SELECT transfer_id AS id, count(*) n FROM biz_stock_transfer_item GROUP BY 1) t
UNION ALL SELECT 'stock_out',
  count(*) FILTER (WHERE n > 200), max(n)
FROM (SELECT stock_out_id AS id, count(*) n FROM biz_stock_out_item GROUP BY 1) t
UNION ALL SELECT 'price_inquiry',
  count(*) FILTER (WHERE n > 200), max(n)
FROM (SELECT inquiry_id AS id, count(*) n FROM biz_price_inquiry_item GROUP BY 1) t
UNION ALL SELECT 'purchase_requisition',
  count(*) FILTER (WHERE n > 200), max(n)
FROM (SELECT requisition_id AS id, count(*) n FROM biz_purchase_requisition_item GROUP BY 1) t
UNION ALL SELECT 'purchase_return',
  count(*) FILTER (WHERE n > 200), max(n)
FROM (SELECT return_id AS id, count(*) n FROM biz_purchase_return_item GROUP BY 1) t;
```

**这条 SQL 只影响「优先级」，不推翻本决策**：即便真有大单，选 2 的文案依然是对的（它给的就是可执行动作），
只是需求池条目应该从「待触发」提前到「本迭代候选」。谁有条件跑，把结果回填到本文件 §5 即可。
