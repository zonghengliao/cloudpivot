# 运维规程 — PG 慢查询日志（>1s）

**一句话**：145 / 144 的 PG 18 都开了 `log_min_duration_statement = 1000`，
执行超过 1 秒的语句会带 `时间 [pid] user@db` 前缀落到 `/var/log/postgresql/postgresql-18-main.log`；
落地件在 `scripts/ops/postgres/pg_slowlog.sh`，一条命令就能落地 / 检查 / 回滚 / 探针。

- 落地卡：P3-16「PG 慢查询日志（>1s）」
- 机器：145（测试）/ 144（生产）—— 2026-11-16 00:18–00:24 已双双落地并验收（各 20 项断言全绿 = 检查 16 + 探针 4）
- 证据：`docs/evidence/2026-11-16-p316-pg-slowlog/`

---

## 1. 生效口径（两台机器一致）

| 参数 | 值 | 语义 |
|:--|:--|:--|
| `log_min_duration_statement` | `1000` | 执行 **≥ 1000ms** 的语句整条记录（`-1` = 关，`0` = 记全部 —— 别用） |
| `log_line_prefix` | `'%m [%p] %q%u@%d '` | `时间 [pid] user@db ` |
| `log_destination` | `stderr`（默认） | 由 Debian/Ubuntu 的 `pg_ctlcluster` 重定向到 `/var/log/postgresql/postgresql-18-main.log` |
| `logging_collector` | `off`（默认） | 不需要开：日志已经在文件里（开了会多一套 PG 自己的切分，与现有轮转打架） |

实测样例行（2026-11-16 00:18:50，145）：

```
2026-11-16 00:18:50.806 CST [1387947] postgres@cloudpivot_test LOG:  duration: 2009.065 ms  statement: select pg_backend_pid() as pid, pg_sleep(2);
```

144（生产）：`2026-11-16 00:19:19.402 CST [1006257] postgres@postgres LOG:  duration: 2004.974 ms  statement: select pg_backend_pid() as pid, pg_sleep(2);`

## 2. `%q` 的取舍（**卡面与实现的唯一差异，故意的**）

卡片原文是 `log_line_prefix = '%m [%p] %u@%d '`；Debian/Ubuntu 交付的默认值已经是 `'%m [%p] %q%u@%d '`。

- `%q` **只在「非会话进程」**（checkpointer / bgwriter / walwriter / autovacuum launcher 等）里抑制后面 `%u@%d` 的渲染；
- **会话进程（含所有慢查询行）渲染结果与卡片要求逐字节一致** —— 断言④/探针正则钉死了：
  `^\d{4}-\d\d-\d\d \d\d:\d\d:\d\d\.\d+ \S+ \[\d+\] user@db LOG:  duration: \d+\.\d+ ms  statement: ...`
- 去掉 `%q` 会让 144 生产日志里**每一条**后台行变成 `... [507425] @ LOG:  checkpoint ...` 的空 `user@db` 噪声。

结论：**保留 `%q`**。要让断言与卡片原文完全同形，只能连 `%q` 一起删——那是降级，不做。

## 3. 落地方式：追加「托管块」，不动文件中部

在 `/etc/postgresql/18/main/postgresql.conf` **末尾**追加（脚本 `apply` 模式写入）：

```conf
# >>> cloudpivot P3-16 pg slowlog (managed by scripts/ops/postgres/pg_slowlog.sh) >>>
# 卡片 P3-16：慢查询（>=1000ms）进 PG 日志。由 scripts/ops/postgres/pg_slowlog.sh 托管，手改会被覆盖。
log_min_duration_statement = 1000		# 记录执行 >= 1000ms 的语句（-1 = 关闭）
log_line_prefix = '%m [%p] %q%u@%d '	# 会话行 = 时间 [pid] user@db；%q 只抑制后台进程的空 user@db
# <<< cloudpivot P3-16 pg slowlog <<<
```

为什么这么写：

1. **后写者生效**：`postgresql.conf` 顺序解析，块在末尾 → 覆盖中部 `#log_min_duration_statement = -1` 与老的 `log_line_prefix`，不用改交付文件（二开不侵入底座）。
2. **幂等**：先删旧块再追加，重复执行只有一块；配置漂移可反复纠正。
3. **不用 `ALTER SYSTEM`**：那会写进 `postgresql.auto.conf`（不可 grep、不可进仓库、与配置管理抢方向盘）。脚本断言 ③ 钉死 auto.conf 里没有这两个参数。
4. **可精确回滚**：块前那一个空行由脚本加、也由脚本删，`strip_block()` 输出与落地前**逐字节一致**（apply 阶段与 `--self-test` 各断言一次 sha256）；真要回滚有 `--rollback`（用 `/etc/postgresql/18/main/postgresql.conf.bak-p316.<ts>` 还原）。
5. **改前预校验**：`postgres -D <datadir> -c config_file=<conf> -C log_min_duration_statement` 先跑一遍语法，**坏配置不 reload**（否则下一次重启直接起不来）。

## 4. reload，不 restart

两条参数都是 **SIGHUP 级**（`pg_settings.context = superuser`，`pending_restart` 在 reload 后为 `false`），

```bash
pg_ctlcluster 18 main reload
```

即生效。**不要 restart**：144 是生产库（实测 21 个连接），restart 会掐断全部连接。
reload 后实测（`docs/evidence/2026-11-16-p316-pg-slowlog/05_prod_impact_144.txt`）：
`MainPID 633825` 未变、`cloudpivot.service` `ActiveEnterTimestamp` 仍是 2026-11-14 16:45:28、
`/health` 200、`pg_postmaster_start_time()` 仍是 2026-11-14 06:58:19（PG 本身没重启）。

**卡片写的是「重启后验证」，我们没重启——理由与替代证据**：

1. 两条参数都是 SIGHUP 级，reload 后 `pg_settings` 直接显示新值且 `source = configuration file`（断言②），这已经是「值生效」的充分证据；
2. 「重启后会不会变回去」用断言④回答：`postgres -C` 解析的**就是重启时读的那份 conf**，输出 `1000` / 前缀正确 → 重启后是同一结果；
3. 真重启的代价是中断：145 上当时正有别的卡在跑 DB 测试（`06_observe_window.txt` 里 `cpb@cloudpivot_base` 的语句），144 是生产库。
   为了一个已被 ②④ 证明的结论去掐断生产连接，不值。

## 5. 一条命令验收

```bash
bash scripts/ops/postgres/pg_slowlog.sh --host 172.18.10.145            # 落地 + 检查 + 探针
bash scripts/ops/postgres/pg_slowlog.sh --host 172.18.10.144 --check    # 生产只读巡检
bash scripts/ops/postgres/pg_slowlog.sh --host 172.18.10.145 --probe    # 只跑探针
bash scripts/ops/postgres/pg_slowlog.sh --self-test                     # 临时目录自证（不碰真配置）
```

断言清单（20 项 = 检查 16 + 探针 4，2026-11-16 实测 145 / 144 均 20/20）：

| # | 断言 | 抓什么 |
|:--:|:--|:--|
| ① | 托管块存在 / 唯一 / 两条参数值正确 | 手改被覆盖、块被复制两份 |
| ② | `pg_settings` 生效值 = `1000ms`、`source = configuration file`、`pending_restart = false`、`context = superuser` | 改了文件没 reload（还是 `default`/`-1`） |
| ③ | `postgresql.auto.conf` 不含这两个参数 | `ALTER SYSTEM` 覆盖了我们的值 |
| ④ | `postgres -C`（= 重启时会读到的那份 conf）得 `1000` 且前缀正确 | **「重启后会怎样」**：证明值在配置里持久化，不依赖本次 reload 的运行时状态（不真重启也能回答卡片那句「重启后验证」） |
| ⑤ | 日志文件存在 + `log_destination = stderr` | 日志落点错（开了 `logging_collector` 会落到别处） |
| 探针 | `select pg_backend_pid(), pg_sleep(2)` 的 pid 必须出现在日志里，且行形匹配 `时间 [pid] user@db LOG:  duration: 2xxx ms  statement: ...` | 「配了但没落盘」 |
| 反证 | `select pg_sleep(0.4)` 的 pid **不应**进日志 | 门限失效 / 变成 `log_statement=all` |

探针库：145 用 `cloudpivot_test`；**144 上没有 `cloudpivot_test`**（该机库：`cloudpivot` / `cloudpivot_e2e_iso` / `cloudpivot_fix10_demo` / `cp_e2e05fix2` / `cp_e2efix3` / `cp_fix3_probe` / `postgres`），
脚本自动降级到 `postgres` 库探针——**不碰任何业务库**。要指定库：`--db-name <库>`。

探针一律以 `postgres` 超级用户走本机 socket 执行（`su - postgres`），不落密码、不依赖 `.pgpass`。
日志里因此显示 `postgres@<库>`；应用连接则显示 `cloudpivot@cloudpivot`，前缀规则相同。

## 6. 日志落点与轮转（**别和 P3-15 混了**）

| 项 | 值 |
|:--|:--|
| 文件 | `/var/log/postgresql/postgresql-18-main.log` |
| 谁在切 | `/etc/logrotate.d/postgresql-common`（Debian 自带）：`weekly` / `rotate 10` / `compress` / `copytruncate` |
| 与 P3-15 的关系 | **无关**。P3-15 那份 `cloudpivot` 片段只 glob `/var/log/cloudpivot/*.log`，切不到 PG 日志 |

> 如果要 PG 日志也「按天 + 保留 30 天」，改的是 `/etc/logrotate.d/postgresql-common`（或加一份同路径片段），
> **不是** `cloudpivot` 那份。本卡不动它，登记为后续优化（见 §9）。

音量预期：144 生产开启后 2 分钟观测窗口内**只有探针那 1 行**（`06_observe_window.txt`），
即真实业务流量目前没有 >1s 的语句；日志增长风险可忽略。要盯音量：

```bash
grep -cE 'duration: [0-9]+\.[0-9]+ ms' /var/log/postgresql/postgresql-18-main.log   # 累计条数
wc -c /var/log/postgresql/postgresql-18-main.log                                   # 当前体积
```

## 7. 排查表

| 症状 | 先看什么 |
|:--|:--|
| 日志里没有 `duration:` 行 | `SHOW log_min_duration_statement` 是不是 `-1`；`pg_settings.source` 是不是 `default`（= 没 reload）；`postgresql.auto.conf` 里有没有被覆盖 |
| 改完 `SHOW` 还是旧值 | 是不是 reload 到了别的集群（`pg_lsclusters` 看端口）；`pg_ctlcluster <VER> <CLUSTER> reload` 的 VER/CLUSTER 对不对 |
| 配了但文件没长大 | `log_destination` 是否 `stderr`；`logging_collector=on` 时日志在 `<datadir>/log/` 而不是 `/var/log/postgresql/`；`pg_lsclusters` 第 7 列才是真落点 |
| 日志全是 `STATEMENT:` 没有 `duration:` | 那是**错误**语句日志（`ERROR` 后面的 `STATEMENT:`），与慢查询无关，别当噪声清掉 |
| 后台行看不出是谁 | 正常：`%q` 让非会话进程的 `user@db` 静默（§2） |
| 慢查询太多刷屏 | 调 `--threshold-ms 3000` 重跑（会把块里的值改成 3000），或用 `log_min_duration_sample` 采样 |
| 想临时关掉 | `--rollback` 还原配置文件，或把块里改成 `-1` 再 reload（下一个人跑 apply 会被纠正回来） |

## 9. 待办（本卡不做）

- PG 日志轮转从 `weekly / rotate 10` 改成「按天 / 30 天」→ 改 `/etc/logrotate.d/postgresql-common`（与 P3-15 的口径统一）。
- 慢查询出告警：`duration: > 5000 ms` 接 Prometheus/告警（需日志采集侧解析，当前无采集器）。
- 应用侧慢 SQL 归因：与 `sqlx` 慢日志（若启用）合并看，避免只看到 PG 侧不知业务入口。
