## 〇、一句话口径（对外只说这一句）

> **本期开放 `SERVICE` / `LEASE` 两类合同**：乙方一律从**供应商主档**选（不新建主档），
> 审批沿用现有 `contract_approve`（阈值 10 万不变、**不按类型分流审批人**），
> **不挂**采购单 / 销售单 —— 因此「已执行金额 / 未关闭单据」对这两类**口径不适用**，
> 接口必须显式返回「不适用」而不是 0 元；真正的履约单据「合同付款计划」进需求池（RP-2026-005）。

判定口诀（前端表单 tooltip 与对客手册同步）：

| 场景 | 用哪类 |
|---|---|
| 会**下采购单**（收货 / 入库 / 应付）的采购行为（货物**或**服务 SKU） | `PURCHASE` |
| 会**开销售单**的销售行为 | `SALES` |
| **不下任何订单**的长期服务（物业、维保、外包年框、软件订阅） | `SERVICE` |
| **不下任何订单**的租赁（房租、设备租用） | `LEASE` |

> ⚠️ 合同类型是**已签冻结字段**（`V-19`，ARCH-2 §5.3）：签完发现类型选错只能「终止 → 新签」，
> 所以选择指引必须**建单时就给**，不能只在文档里。

## 二、D1 · 乙方主档类型：**固定 `SUPPLIER`，不新建主档**

**决定**：`SERVICE` / `LEASE` 的 `party_b_type` 一律为 `SUPPLIER`，乙方从 `biz_supplier` 选；
`PURCHASE` → `SUPPLIER`、`SALES` → `CUSTOMER`、`SERVICE`/`LEASE` → `SUPPLIER`（**单向**，应用层强制）。

**为什么不是新主档 / 不是 `CUSTOMER`**

1. **与应付侧同构**：出租方/服务商付款要用到的字段全在供应商主档里 —— `payable_account_id`（应付科目）、
   `credit_days`（账期）、`credit_limit`、开票四件套（`invoice_title/invoice_bank_name/invoice_bank_account/tax_no`）
   （`V0137:135-160`）。新建「服务商/出租方」主档 = 把这一整套重建一遍，并让应付、付款、凭证、开票按主档类型分叉。
2. **客户主档语义不对**：`biz_customer` 是**销售方向**的交易对手（`status ACTIVE/FROZEN` + 信用额度，无应付科目，
   `V0260__sales_customer.up.sql` 表注释「销售链交易对手真相」）。出租方/服务商是**我们付钱**，用它会把付款对象塞进销售域。
3. **改造成本不对称**：加第三值要动 `party_b_type` CHECK、`ck_..._party_pair`、`party_b_ref` 两函数、
   巡检 SQL（ARCH-2 §3.3 Q1）、前端选择器、权限码 —— 而这三种主体的**语义差别只有一个「备注」**。
4. **这是原设计，不是新发明**（F5）：ARCH-2 §3.2.3 的 P0 方案原文就写了「乙方=供应商」的 `SERVICE`/`LEASE` 可用。

**已知代价与处置（不藏着）**

- 代价：供应商列表与采购单的供应商下拉里会混入服务商/出租方。
- 处置 A（本期做）：合同表单乙方选择器的 label 与 tooltip 写清「服务商 / 出租方在系统中登记为**供应商**」，
  文案分类型：采购→「乙方供应商」、服务→「乙方服务商」、租赁→「乙方出租方」、销售→「乙方客户」。
- 处置 B（本期**不做**，进需求池）：给 `biz_supplier` 加分类列（`GOODS/SERVICE/LEASE/MIXED`）并按合同类型做兼容校验 ——
  属主数据分类（MDM）范畴，触发条件见 **RP-2026-006**。
- **DDL 不收紧**：`ck_biz_contract_type_party_pair` 的 ELSE 分支继续允许两值（DB 宽容、应用层收窄）。
  理由：收紧是「减少合法集」，对未来「我们向客户提供租赁/服务」（应走 `SALES`）没有任何收益，却要付一次迁移风险。

## 三、D2 · 审批人映射：**沿用一套流程、阈值 10 万不变、不按类型分流**

**决定**：`SERVICE` / `LEASE` 与 `PURCHASE` / `SALES` 共用 `contract_approve`：
`amount < 100000` → 采购经理单级；`amount ≥ 100000` → 采购经理 + 总经理两级。**不新增角色、不新增流程、不改阈值。**

**为什么**（三条，逐条可反驳）

1. **服务/租赁与采购同属「对外付款承诺」**，现有唯一审批岗位 `PURCHASE_MANAGER` 承担的正是对外付款审批；
   仓里种过的审批岗位只有 `DEPT_LEADER / PURCHASE_MANAGER / GENERAL_MANAGER / WAREHOUSE_MANAGER /
   FINANCE_MANAGER / FINANCE_DIRECTOR`（`V0182` / `V0191` / `V0239:40`）—— 没有行政/法务岗。
   要按类型分流，先得建角色 + 权限包 + 组织配置，那是**审批治理**，不是合同卡能顺手带的。
2. **分流技术上很便宜，恰恰是现在不该做的理由**：`form.contract_type` 已经冻在审批表单里（F9），
   加一条 `form.contract_type eq "SERVICE"` 的条件边即可。但一旦按类型分，就必须同时回答
   「**销售合同为什么还由采购经理批**」（CTR-01 §3 F5，至今未收口），否则同一系统里会出现三套映射口径。
   先把「类型齐全」跑起来，再一次性按**资金流向**重构审批人（RP-2026-007）。
3. **阈值保守不改**：服务/租赁多为年框，`≥10 万` 必走两级（采购经理+总经理），比降到 5 万更保守。
   阈值在流程定义里（不改代码、不发版），上线跑一段按实际单据量再调。

**连带口径（必须一起说清）**

- 到期提醒（`erp_contract_expire_scan`，提前 30/15/7/1 天）通知对象仍是 `PURCHASE_MANAGER`（F10）——
  与审批人一致，本期不改。**若将来审批人分流，提醒对象必须一起分流**（已写成 RP-2026-007 的依赖项）。
- 销售合同由采购经理批 = 既有缺口，**不在本卡扩围**，登记 RP-2026-007。

## 四、D3 · 额度 / 履约口径：**不挂订单，显式「不适用」，付款计划进池**

**决定**：

1. 服务/租赁合同**不挂**采购单 / 销售单 —— 订单侧类型闸（F7）**保持原样**，本期不放开。
2. 因此 `committed_amount` / `remaining_amount` / `open_order_count` 对这两类**口径不适用**。
   接口必须**显式区分**：
   - `commitment_scope = "ORDER_LINKED"`（`PURCHASE` / `SALES`）：已执行金额、剩余额度、未关闭单据**有意义**；
   - `commitment_scope = "NOT_APPLICABLE"`（`SERVICE` / `LEASE`）：三个字段仍照旧返回（`0` / `0` / 合同额），
     但**前端不得把它渲染成 `0.00`**，必须显示「不适用（服务/租赁合同不走订单勾稽）」。
3. 报表侧：凡按 `committed_amount` 算「履约率 / 已执行占比」的地方，**必须过滤 `commitment_scope = ORDER_LINKED`**，
   否则服务/租赁合同永远按 0% 计入，把整体履约率拉低（口径写进实现卡与 ARCH-2 §4.1 注）。
4. 这两类合同的可执行口径 = **期限**（`start_date`/`end_date` + 到期提醒），它不是替代品，但对租赁/服务恰恰是最有商业价值的一项。

**为什么不放开订单侧（放开 = 假勾稽）**

- 放开一行 `if contract.contract_type != "PURCHASE"` 容易，**后果不轻**：采购单强制 `warehouse_id`
  （F13）、明细强制 `material_id` + `qty > 0`；而收货/入库对 `material_type='SERVICE'` **没有任何分支**
  （F12），服务行货一到就写 `biz_inventory` 与存货成本 —— 直接制造**虚假库存与虚假存货金额**。
  要把服务采购做对，必须先做「**费用化采购**」（收货不入库存、直接进费用科目 + 生成应付），那是独立一张卡（RP-2026-008）。
- 服务/租赁真正的履约单据是**付款**，而付款链挂不上合同（F11）：`biz_payable` 只从收货单等 `(source_type, source_id)`
  生成，`biz_payment` 挂在应付下，费用报销「对员工、不挂供应商」。⇒ 今天强行「挂订单」只能得到**错的账**，不是**快的账**。

**付款计划（真正的履约单据）—— 进池，不做**

- 目标形态：合同 → **付款计划**（期次 / 到期日 / 金额 / 状态）→ 到期生成应付（`biz_payable.source_type='CONTRACT'`）
  → 付款登记复用既有付款与凭证（`V0158`：借 `2202` / 贷 `1002`）。
- 粗估 4–6 人日（需架构/后端复核）；触发条件与验收要点见 **RP-2026-005**。
