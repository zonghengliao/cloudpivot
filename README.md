**云枢是一个「可验证、可定制」的业务中台**：以 ERP 业务域（采购 / 销售 / 库存 / 财务）为落地场景，
把**流程、权限、审计、验证**四件事做成底座能力，再用 AI 把「定制」的成本压到接近于零。

它不是又一个通用后台模板，也不是又一个功能堆砌的 ERP。

## 我们解决什么问题

传统 ERP 的二开有三个死结：

| 死结 | 传统做法 | 云枢的做法 |
|---|---|---|
| **流程改不动** | 流程写在代码里，改一次流程要发一次版 | 流程全部由**工作任务 + 审批流配置**驱动，代码里不硬编码业务流程 |
| **改完不敢信** | 改完靠人测，测完靠运气 | 每个业务动作都有**勾稽自检**，每张凭证可**溯源**到原始单据，改动必须通过自动化断言 |
| **定制太贵** | 一个客户一套代码，维护成本线性增长 | 用 **AI + 三环境隔离 + 审批流部署**，让定制变成配置与受控变更 |

云枢的答案是：**把"可信"做成基础设施，让"定制"变成可审计的动作。**

## 三个坚持

### 1️⃣ 流程不硬编码

> 「我要求流程全部用工作任务和审批流来实现。不要在程序中硬编码流程。」

- 审批流是**数据**，不是代码：`biz_flow_def` / `biz_flow_instance` / `biz_flow_node`
- 支持多版本流程定义、按角色/按人/按金额分支、自审拦截（SoD）、升级链、节点兜底人
- 流程配置错误可以在运行时修正，不需要重新编译部署
- 当前内置 **18 条正式流程**（采购申请、采购订单、合同、付款、报销、资产等）

**这条坚持的代价**：流程引擎本身要足够强（节点类型、会签/或签、条件表达式、降级策略、版本迁移），
我们为此付出的工作量，远超"写死几个 if"。

### 2️⃣ 可验证优于可演示

> 「可验证、可定制的业务中台。」

一个功能"能点开"和"算得对"是两件事。云枢选择了后者：

- **凭证溯源**：每张会计凭证可反查来源单据与业务动作
- **勾稽自检**：库存三本账（数量/金额/批次）、应收应付与总账、报表与科目余额，自动比对
- **断言式验收**：13 个业务域的端到端演练，累计 **3000+ 条断言**、**150+ 组勾稽比对**
- **反假完成机制**：卡片的"完成"必须带可机械验证的产物（提交哈希、测试输出、接口实测记录）

### 3️⃣ AI 是协作者，不是玩具

> 「我们不能定位是通用 ERP。我们可验证、可定制的业务中台，并且通过 AI 快速进行二次开发，AI 机器人用户执行任务，这也是我们的亮点。」

- **AI 参与开发**：本项目全部二开代码由 AI 编写（人类决策 + 验收）
- **AI 作为用户**：`sys_user.user_type = ROBOT`，AI 员工拥有独立的权限、审计、菜单与执行日志
- **AI 有边界**：19 条安全红线写进每个 AI 用户的 SOUL 配置；AI 只能改沙箱/staging，**不能直接改生产**

## 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 后端语言 | **Rust**（edition 2024） | 内存安全 + 无 GC，财务计算不担心停顿 |
| 后端框架 | **NIK**（基于 alun 修改） | axum 0.8 之上的门面：配置三层覆盖、迁移 runner、缓存抽象、JWT 双令牌 |
| 数据库 | **PostgreSQL ≥ 14** | 软删 + 部分唯一索引；迁移幂等且只追加不修改 |
| 缓存 | **Redis** | 会话、幂等键、分布式锁、AI 会话活跃时间 |
| 前端 | **Vue 3.5 + TypeScript 5.8 + Vite** | TDesign 组件库、Pinia、Vue Router、ECharts |
| 包管理 | **pnpm** | 版本固定，Node ≥ 22 |
| 测试 | Rust 内置测试 + `node:test` + Playwright | 后端单测 / 前端纯逻辑单测 / 端到端 |

## 快速开始

### 环境要求

```
Rust ≥ 1.94        Node ≥ 22        pnpm 10.5+
PostgreSQL ≥ 14    Redis ≥ 7
```

### 1. 准备依赖

```bash
# 用 Docker（推荐）
docker compose -f docker/docker-compose.yml up -d

# 或本地已装 PG/Redis，初始化数据库
bash scripts/init-db.sh
```

### 2. 启动后端

```bash
cd backend

# 首次启动需要注入管理员口令种子（空库时生效）
export NIK_ADMIN_PASSWORD='你的初始口令'

cargo run    # 自动执行迁移并启动，默认 http://127.0.0.1:8023

# 核对配置生效结果
cargo run -- print-config
```

### 3. 启动前端

```bash
cd frontend
pnpm install
pnpm dev     # http://localhost:5173（/api、/health 代理到 8023）
```

### 4. 跑测试

```bash
# 后端单测（内存受限机器请用脚本，见下）
./scripts/ops/run_tests.sh backend

# 前端单测（1300+ 条）
./scripts/ops/run_tests.sh frontend

# 两端一起
./scripts/ops/run_tests.sh all
```

> **为什么用脚本而不是直接 `cargo test`**：`run_tests.sh` 固定了单 job + 关闭 debuginfo +
> 产物超阈值自动清理。直接跑在多 job 机器上会让 `target/debug` 膨胀到 70G+，
> 在 8G 内存机器上还会被 OOM killer 杀掉。

## 安全设计

### 空闲自动退出（会话超时）

防止离开工位被他人操作：

| 规则 | 值 |
|---|---|
| 默认超时 | **15 分钟无操作** |
| 范围 | **1–60 分钟** |
| `0 = 禁用` | **仅超级管理员可设，且不走审批流**（避免功能被绕过） |
| 配置位置 | 支撑功能 → 参数配置 → `auth.idle_timeout_minutes` |
| 超时前 | 提前 1 分钟弹窗提示「即将退出，点击继续」 |
| 超时后 | 吊销 token（服务端滑动过期 + 前端计时双保险），跳登录页并记住原路由 |

**实现要点**：后端按会话记录"最后一次用户操作"，超时返回 `401 + 20009` 并吊销该会话的 refresh token
（不能靠刷新复活）；前端只监听真实用户事件，**后台轮询不续期**（否则功能形同虚设）。

### 其他安全能力

```
· 职责分离（SoD）：制单人不能自审；超出金额阈值强制走升级链
· 三签法：关键单据制单/审核/记账分离，任一人不能包办全流程
· 审批降级链：自审 SKIP → 升级链 → 节点兜底人 → 系统兜底
· 数据权限：按部门/自定义范围过滤，字段级脱敏
· 角色互斥：同一人不能同时持有互斥角色
· 操作审计：关键配置变更（含空闲超时）记录旧值、新值、操作者、是否超管
· 附件安全：上传类型/大小/角色校验，预览与下载分流
· AI 边界：19 条安全红线随 SOUL 注入；AI 写权限止于沙箱/staging
```

## 可验证：我们怎么证明它是对的

云枢不接受"看起来没问题"作为完成标准。

### 三层验证

| 层 | 手段 | 规模 |
|---|---|---|
| **单元** | Rust `#[cfg(test)]` + 前端 `node:test` | 后端 4000+ 用例，前端 1300+ 用例 |
| **端到端** | 13 个业务域演练（E2E-01~14） | **3000+ 断言**、**150+ 组勾稽比对**、0 FAIL |
| **评审** | 八维度系统评审（功能/流程/一致性/权限/性能/易用/可维护/运维） | 输出分级问题清单（P0–P4） |

### 证据可追溯

每一次交付都要求留下**可机械复核**的产物：

```
docs/evidence/<日期>-<卡片>/README.md    # 断言清单 + 实测输出
docs/evidence/<日期>-<卡片>/raw/         # 原始接口返回、SQL 输出
docs/review/                              # 系统评审报告
docs/architecture/                        # 设计与决策记录（含否决理由）
```

### 勾稽自检示例

```
库存三本账：数量账 = 金额账 = 批次账
应收明细合计 = 应收账款科目余额
应付明细合计 = 应付账款科目余额
凭证借贷合计平衡，且来源单据可反查
调拨在途：发出仓 - 在途仓 + 接收仓 = 0
```

## AI 二次开发

这是云枢最不一样的地方：**AI 不是辅助工具，是开发主体。**

### 人类做什么

```
· 定方向：做什么、不做什么、优先级
· 定边界：什么绝对不能碰（生产、安全红线、财务口径）
· 验收：看证据，不看描述
```

### AI 做什么

```
· 读代码、写代码、写迁移、写测试
· 跑测试、修失败、写证据文档
· 写设计文档、做代码评审、生成部署脚本
```

### 怎么保证 AI 不闯祸

| 机制 | 说明 |
|---|---|
| **三环境隔离** | `sandbox`（AI 可写）/ `staging`（客户验收，物理独立）/ `prod`（人工部署） |
| **生产写权限** | AI **没有**。部署必须走审批流，`deploy.sh` 硬校验 `status='APPROVED'` |
| **迁移不可变** | 已应用的迁移绝不修改，只能追加新迁移，且必须幂等 |
| **反假完成** | 卡片"完成"必须带提交哈希 + 测试输出 + 接口实测，缺一不算完成 |
| **安全红线** | 19 条写进 SOUL，版本化，删除自动补回，启动自检 |
| **并发控制** | 同时最多 2 个 AI 任务，避免互相踩踏 |

### 三个环境的链路

```
开发（可写）  ──push──▶  测试（自动编译/迁移/重启）  ──人工──▶  生产（审批后部署）
   sandbox                  staging                          prod
```

## 三环境与部署

### 部署必须走审批流

```
① 变更申请（biz_deploy_request）
② 技术负责人审批
③ 业务负责人审批
④ 客户决策人审批
⑤ deploy.sh 校验 status='APPROVED' 才执行
```

**回滚同样走审批**（`source_type = ROLLBACK`），不存在"紧急绕过"的暗道；
紧急通道需要双人确认 + 24 小时内补审 + 全程留痕。

### 部署脚本做了什么

`scripts/ops/deploy.sh` 的固定顺序（缺一步都算失败）：

```
① 全库备份              ② 后端 release 编译
③ 前端构建              ④ 迁移预演（恢复备份到临时库 → 跑迁移 → 校验）
⑤ 重启（失败自动回滚）    ⑥ nginx 配置检查 + reload
⑦ 冒烟（health / 首页 / 登录 / 关键接口）  ⑧ 收尾报告
```

> **为什么要有第 ④ 步**：我们曾经在生产上被一次迁移失败击穿（唯一约束冲突，服务中断 30 分钟）。
> 从那以后，所有迁移必须先在"生产备份的临时库"里跑通。

## 项目结构

```text
cloudpivot/
├── backend/
│   ├── Cargo.toml              # 只声明 nik 门面 + feature
│   ├── config/                 # config.toml + dev/test/prod profile
│   ├── migrations/             # 迁移，按域分目录（system/ support/ business/ seed/）
│   ├── src/
│   │   ├── system/             # 框架底座：认证、用户、角色、部门、菜单、日志
│   │   ├── support/            # 支撑：参数、字典、附件、导入导出、任务调度
│   │   ├── business/           # 业务域：erp / flow / task / notice / aiagent / monitor
│   │   └── middleware/         # 认证、会话守卫（含空闲超时）、审计
│   └── vendor/nik*/            # NIK 框架（基于 alun 修改）
├── frontend/
│   ├── src/api/                # 按域分目录，与后端一一对应
│   ├── src/views/              # 页面
│   ├── src/components/         # 通用组件
│   └── tests/unit/             # node:test 单测
├── docs/
│   ├── architecture/           # 设计文档（ARCH-x），含决策与否决理由
│   ├── review/                 # 系统评审报告
│   └── evidence/               # 每张交付卡的可复核证据
├── scripts/
│   ├── ops/run_tests.sh        # 测试入口（内存友好的标准姿势）
│   ├── ops/deploy.sh           # 生产部署（校验审批）
│   ├── ops/backup_db.sh        # 备份/恢复
│   └── check.sh                # 提交前检查
└── docker/                     # 本地依赖与生产编排
```

### 二次开发约定

```
业务代码统一放 business/            不侵入框架底座
后端 backend/src/business/<模块>/    前端 frontend/src/api|views/business/<模块>/
新表必须带：软删字段、创建/更新时间、创建人/更新人、审计日志
新迁移必须：幂等、只追加、有对应 down 脚本
```
